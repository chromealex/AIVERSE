Game data format (AIVERSE)#

A game is a folder <project>/:

game.json        manifest: name, id, version, rules file, maps list, orientation, desktop window, icon, input
rules.json       resources, types (units/structures/objects), techs, factions, game rules, triggers
maps/*.json      terrain, players, objects, waves, triggers, areas, victory overrides
audio.json       sounds, music and which sound plays on which game event (optional: no file = silent)
models/ ui/ ...  assets (glTF models, textures, UI, sounds); 2D images may be packed into atlases (see Texture atlases)

JSON allows // comments. Numbers are plain decimals (1.5, never 1e3): the simulation is fixed-point and deterministic. Seconds are game seconds, distances are map cells. Every block below is optional — the blocks present on a type decide what it can do.

PRISMA scene/camera post-processing#

game.json.postfx retains the original global HDR/bloom/color-grade settings. Optional game.json.prismaVolumes and map prismaVolumes add position-dependent camera looks (no gameplay/ECS simulation mutation). Each block holds {"volumes":[{"id":"area","shape":"sphere","center":[0,0,0],"radius":8,"blendDistance":3,"priority":4,"weight":1,"profile":{"effects":[{"type":"colorGrade","saturation":0.6}]}}]}. The map may override a game volume by identical id, or set "replace":true to discard game volumes. Supported shapes are global, sphere, and axis-aligned box (center + halfExtents). The profile uses the existing postfx effect schema. Only explicit profile hdr/enabled overrides global HDR or chain enable state. Engine/runtime C++ owners: engine/render/PrismaVolumeData.{h,cpp} and PrismaVolumes.h; see docs/prisma.md for full semantics and quality caveats. The postfx_* MCP operations remain compatible.

  "module": "game", "rules": "rules.json",
  "maps": [{ "file": "maps/valley.json", "title": "River Valley (1v1)" }],
  "orientation": "landscape", "icon": "icon.png" }

"audio": another name for the sound file (default audio.json).

"module": the game module — "rts", "fps", "voxel", or "scene". A "scene" project has no game module: it needs only game.json (name, id, version, build, "module": "scene", optional "background": "#rrggbb"). aiversebuild packages it with the minimal scene client (apps/client/SceneMain.cpp, CMake AIVERSE_SCENE_CLIENT): window or canvas, content pack and an empty scene cleared to the background colour — no simulation, renderer, UI, scripting or audio, and no engine/assets in the pack. Web Release with the default -Oz + LTO, 2026-11-21: about 150 KB to download (brotli: index.wasm 108 KB, index.js 40 KB). Projects without "module" remain RTS projects.

"icons" and "splash": game icons for every platform and the loading screen — see "Icons and splash" below (the old single "icon" still works as the master icon).

Optional "graphics": the RHI backend on Windows, Linux and Android — "gl" (default) or "vulkan", or per platform {"windows": "vulkan", "android": "gl"}. Vulkan falls back to GL when the machine has no driver; --gfx and AIVERSE_GFX override it (docs/vulkan.md). macOS / iOS use Metal, the web WebGL2.

Optional "window" block: how the game window opens on desktops (macOS, Windows, Linux; phones and tablets are always fullscreen, the web build fills the page). Editor: Сборка → Окно игры (window «Сборка»).

Optional "ui" block: how the in-game UI (RmlUi documents) blends. "ui": {"blend": "linear"} makes translucent UI blend in linear light, as a Unity project in linear colour space does (faded icons, dims, glows and soft edges over lighter art come out lighter than with the default); "srgb" (default, also when the block is missing) blends the sRGB-encoded values, byte-identical to builds without the key. In linear mode vertex colours (CSS colours, opacity, vertex gradients) and images are decoded to linear light (images are premultiplied in linear light and uploaded as sRGB textures), font atlases stay coverage (alpha only), the UI is blended into its own sRGB-encoded layer and one full-screen pass composites it over the scene in linear light (skipped when the UI draws nothing). GPUs without sRGB render targets silently keep the default. Code: engine/ui/UiColor.h (curves, key), UiLinear.* (layer + composite, GLSL and MSL), RHI PixelFormat::RGBA8_sRGB, Device::copyColor.

Optional "camera" block (2D games, see "2D games" below): {"projection": "ortho", "pitch": 90, "yaw": 0, "fov": 43, "zoom": 20, "zoomMin": 8, "zoomMax": 40, "pixelsPerCell": 32, "rotate": false}. The block may start from a preset ({"preset": "overhead-pixel"}; list: camera-behaviors.md).

Optional "playerColors": [neutral, slot 1, ..., slot 8] (overlay colour syntax: "#rrggbb", [r, g, b] 0..1 or 0..255; null keeps a slot) replaces the built-in player palette used for team colours, overlays and the territory overlay default (RtsOverlayData::configurePlayerColors, applied when a match starts in the client and the editor).

Lighting block (game.json / map "lighting"), flat-art keys: "day": {"sun", "sky", "ground", "fog": [r, g, b], "sunK": k} replaces fields of the day palette (of the preset or the renderer), "night" (same keys) the night / moonlight palette (sunK 0..1: moon strength, so shadows stay readable at night), "fogDensity" (0 = no distance fog), "tonemap": false (lit shaders clamp instead of the ACES fit; with sunK 0 and white sky / ground an unlit material shows its colour unchanged), "modelOutput": "srgb" (model shaders encode their linear result with the exact sRGB curve, as a Unity project in linear colour space does, instead of the engine's default sqrt, which renders midtones darker; GLSL and MSL). Map keys win over game keys.

Optional "editor": {"hierarchy": {...}}: how the editor's world tree (Hierarchy / Inspector «Детали») shows this game's objects — previewTicks (ticks the edit-mode preview runs after setup, default 2), label (a game.data(h) key naming the row), categories (tags in priority order: an object's category), groupings ([{"title", "by": [keys]}], keys owner, type, kind, category, origin, region, parent, tag, component, data:<key>). Only the editor reads it. Details: docs/editor-world-tree.md § Game hooks.

Splitting rules.json#

A big game does not keep everything in one rules.json. The loader assembles the rules from several files and lets entries inherit from shared bases (engine/data/JsonCompose.h). The simulation sees one document either way: same results, same checksums, old single-file games load unchanged.

include — more files, paths relative to the file that lists them (inside the game folder):

// rules.json
{"include": ["rules/resources.json", "rules/units.json", "rules/abilities.json"],
 "supplyCap": 200, "victory": "noStructures"}
// rules/units.json (may include further files itself)
{"types": {"footman": {...}, "archer": {...}}, "include": ["heroes.json"]}
  • Top-level objects (types, techs, resources, ai, ...) merge key by key; top-level arrays (playerAbilities, triggers, ...) append in reading order (the file's own content, then its includes, depth first); scalars (supplyCap) are set once.
  • Entries keep the reading order, and the order of types is part of the game (types are numbered in it): moving types between files in another order is a different game for replays and network matches.
  • A key or an array entry "id" defined in two files is an error naming both (rules/b.json: 'types.knight' is already defined in rules/a.json); so are an include cycle, a missing file and a path outside the game folder.
  • Everything reads the assembled rules: client, network host, headless, replays, aiversebuild, the editor. Network and replay data hashes cover every included file. Packs ship the included files like any other data.
  • The editor and MCP edit the rules as one document (rules_get / rules_set / rules_merge); saving writes each entry back into the file it came from and leaves unchanged files untouched. A new entry goes into the file that holds the previous entry of its collection (a new type lands next to the other types). rules_get returns files when the rules are split; game_file_write refuses rules files (use the rules ops).

extends / abstract — an entry of a top-level collection (a member of an object of entries such as types, techs, statuses, or an array item with an "id" such as playerAbilities) starts as a copy of its base(s) in the same collection; its own keys go on top. Objects merge key by key, anything else (numbers, strings, arrays) replaces. "abstract": true entries are bases only: they are removed before loading (not types, not in the editor palette of the game).

"types": {
  "_infantry": {"abstract": true, "health": {"max": 420, "armor": 2}, "move": {"speed": 2.6, "radius": 0.4},
                "sight": 8, "cost": {"gold": 135, "time": 15, "supply": 2}},
  "footman":   {"extends": "_infantry", "name": "Footman", "weapons": [{"id": "sword", "range": 0.6, "damage": 12, "cooldown": 1.2}]},
  "spearman":  {"extends": "_infantry", "name": "Spearman", "health": {"armor": 1}, "weapons": [{"id": "spear", "range": 1.2, "damage": 10, "cooldown": 1.4}]}
}

extends takes a name or a list (applied left to right, then the entry itself); bases may extend other bases. Unknown bases and cycles are errors (types 'knight': extends unknown 'cavalry'). rules_get {"resolved": true} shows the entries as the game loads them; rules_lint checks the resolved entries.

Levels are overrides. levels of abilities and player abilities already merge into the base entry (objects key by key, arrays of the same length element by element): write only what changes per level, "levels": [{"cooldown": 37.5, "effects": [{"duration": 5.5}]}], never a full copy of the ability.

Movement and bodies#

"move": {"speed": 2.8, "radius": 0.4, "mass": 0.64, "layer": "ground", "maxSlope": 1.6}

  • maxSlope (heightfield terrain only): the steepest cell this type can enter (rise per cell); default terrain.maxSlope of its layer. At most 15 different values per game.
  • radius is the real body size (cells): units keep r1 + r2 apart, weapon and ability ranges are measured edge to edge (range + both radii, structures by their footprint), and paths keep clearance from walls and buildings for bodies larger than half a cell (tight gaps cost more; nothing becomes unreachable).
  • mass (default 4 * radius²) decides who yields when bodies overlap. Units that are fighting, holding position or working (gathering, building, digging) are anchored (x8) and are barely pushed; moving units (x2) push idle ones (x1) aside. A 0.03-cell dead zone and a per-tick push cap remove jitter.
  • With movement.avoidance: "rvo" moving units steer around each other with reciprocal velocity obstacles (nearest neighbors, deterministic order). Idle allies in the way are asked to yield: they step to a free side cell and walk back once the way is clear, so a unit can pass a gap of standing units; units blocked by anchored ones re-path around them.
  • movement.avoidance: "none" disables ORCA and mobile body separation, for games whose Lua formation logic supplies positions. It does not disable terrain pathfinding or combat. Keep real positive body radii; do not emulate this mode with near-zero radii.
  • Melee units (range < 2) attacking a target pick a free slot on a ring around it (slots by angle, claimed per target, ties by entity index) and path around allies already fighting instead of pushing into the front rank; ranged units stop and shoot. A group given an attack-move spreads into an arc whose flanks run ahead.
  • Flow fields (movement.flowField, off unless a game or map opts in; docs/pathfinding.md): big groups and hordes share one integration field per goal area instead of one path search per unit. jsonc "movement": {"flowField": {"minGroup": 12, // move / attack-move / patrol / right-click orders of >= 12 units (0 = never) "minCells": 0, // ... only for units at least this many cells from the goal (0 = all) "waves": true, // units released by map waves and lane waves march on fields "spread": 0.4, // goal area radius = 0.3 + spread * sqrt(units) (they arrive spread out) "maxFields": 64, "budgetMB": 32}} // cache: LRU of unreferenced fields beyond these A map may carry the same block ("movement": {"flowField": {...}} at the map's top level) to switch fields on for itself only (e.g. templates/lastcolony/maps/horde_plain.json, templates/planets/maps/big_planet.json). Fliers keep flying straight; units pushed off the field or stuck repeatedly fall back to their own A* path. Followers settle around the goal from the inside out (arrival contagion) and don't block each other.
  • movement.blockedGoals: "nearest" (rules or map, default "search"): paths to a goal inside a structure or obstacle (attacking a building) end at the free cell around it nearest to the unit - much cheaper for hordes; different cells than the classic search, so it is opt-in (on in templates/lastcolony/maps/horde_plain.json).
  • movement.pathfinding: "navmesh" (rules or map, default "grid"): unit paths on flat maps come from the engine navigation mesh (engine/nav, docs/navmesh.md): passable cells of each path layer merge into rectangles, A* runs over them and a funnel pulls the corridor into an any-angle path (fewer waypoints, ~7% shorter than 8-direction grid paths, cheap on 1024x1024 maps). Cliffs, ramps, slopes and structures are respected; searches it can't answer (start or goal off the mesh, unreachable goals, surround-allies paths) use the grid search as before. Planets keep the grid / HPA*. Different waypoints than the grid, so it is opt-in.
  • movement.pathfinding: "hybrid" (rules or map): one portal graph for the map (the 16x16 HPA* clusters, at any map size) and a solver per cluster - navmesh rectangles in open clusters, grid A* in maze clusters (more than movement.hybrid.mazeRatio rectangles per cell, default 0.15: "hybrid": {"mazeRatio": 0.15}). Long trips follow the graph, legs use their cluster's solver, the result is string-pulled; flow fields use the same cluster graph. For big or mixed maps (cities, caves, mazes next to open land); measure a map with aiverse_headless --bench-nav N (docs/navmesh.md § Which solver where).
  • movement.airOverRock: false (default true): fliers are confined to open cells - ground and water - so they follow tunnels like everyone else instead of crossing undug rock and # (MapGrid::airSolid; their paths are searched like walkers', structures and units still don't block them). Dungeon games (underlord).

spatial — 3D sound and distance#

Positional sounds are placed in 3D around the listener (the RTS client puts the ear on the view ray above the camera's focus; units on cliffs and flyers are higher). Distances are world units (map cells). Zooming out raises the ear, so the battle sounds farther away; the audible area grows with the square root of the zoom.

keymeaning
modeldistance curve: inverse (default, natural), linear, exponential
minDistance, maxDistancefull volume up to min, silent at max (12, 60); the last 20 % of the range always fades out
rolloffsteepness of the curve (1)
airAbsorptionHz of the low-pass at max distance: far sounds lose their highs (2500; false = off)
reverbfalse, or {"size": 0.5, "damping": 0.5, "wet": 0.35, "near": 0.05, "far": 0.6} — near / far = reverb send at min / max distance: far sounds get roomy and lose their attack
speedOfSoundworld units per second; distant sounds arrive late (0 = off; capped at 3 s)
rear0..1: sources behind the listener get duller and a bit quieter (0)

The distance keys (model, minDistance, maxDistance, rolloff) are defaults for every sound; a sound can override them and add air / reverb multipliers (below).

Compression at build time#

aiversebuild re-encodes the referenced sound and music files for each target before packing; the project folder is never changed. Profiles: desktop (macOS, Windows, Linux), mobile (iOS, Android), web. --audio mobile forces a profile, --audio off ships the files as they are; aiverse_audiopack --project <game> --profile mobile shows what a profile would do.

"build": {
  "desktop": {"sounds": "keep", "music": "vorbis", "musicQuality": 0.6},
  "mobile":  {"sounds": "adpcm", "music": "vorbis", "musicQuality": 0.3, "maxRate": 32000},
  "web":     {"musicQuality": 0.25}
}
keymeaning
sounds, musiccodec: keep (file as is), pcm (16-bit WAV), adpcm (IMA ADPCM WAV: 4:1, nearly free to decode — short effects), vorbis (OGG: music, long sounds)
soundQuality, musicQualityVorbis quality -0.1..1 (0.5 / 0.4; mobile 0.4 / 0.3, web 0.4 / 0.25)
maxRateresample anything above this rate (0 = never; mobile and web 32000)
monoSoundspositional sounds become mono: the mixer pans them anyway (true)
longSoundseconds: longer sounds (ambient loops, stingers) use the music codec (8)
reencodeLossyalso re-encode files that are already OGG/MP3 (false: lossy to lossy only loses quality)

Defaults without a build section: desktop keeps everything; mobile and web use ADPCM for sounds and Vorbis for music at 32 kHz. Sounds on the music bus count as music. A sound or a playlist can override with "compress" and "quality". Re-encoded files get the extension of their codec and audio.json in the build points at them; a result that isn't smaller keeps the original. Loop points stay exact (Vorbis is sample-accurate; ADPCM pads a loop with its own start).

Dungeon management and territory#

For Lua-owned front lines, see Territory brushes and scripted formations. The optional visual block terrain.territory also supports smooth: true (default false), transition (0..2 seconds, default 0.2) and lift (0..2 world units, default 0.045). On flat maps smooth mode filters ownership with a compact binomial kernel, reconstructs it bilinearly, applies a soft contour threshold, and interpolates changed cells over transition seconds. It uses the existing RHI mesh pipeline on both Metal and GL; material quality selects 4 subdivisions per cell (medium/high) or 2 (low). Fog memory is respected. Legacy square territory/room-floor rendering remains the default; smooth mode is for territory surfaces and does not draw room-floor tints. Planet visuals retain their existing renderer. Counts, capture tests and victory still use exact simulation ownership. The ground-overlay Metal shader uses the shared LightU lighting block (matching GLSL's U2 layout); older builds referenced the obsolete U2 MSL type and silently lost the entire layer. Shader/pipeline failures now report the backend error to stderr.

The player's stock of a good is the sum of its storehouses (storehouse.capacity = total goods); paying takes goods out of storehouses, income and bounties are put into them. Starting goods (resource start, map player resources) go into the first storehouses; map entities can carry "inventory": {"wood": 5}.
  • Recipes: a workplace consumes in from its own inventory and produces out into it every time seconds (productionSpeed stat and power apply); it keeps buffer cycles of inputs and stops when buffer cycles of output are waiting. Raw producers have no in; from + radius deplete the nearest resource node or field cell of that resource (wood from trees, stone from a quarry, fish from water fields).
  • Carriers (carrier.capacity per trip) haul on request, deterministically (every 0.5 s, buildings in entity order): construction sites and workplace inputs first (source: workplace output, else nearest storehouse), then workplace outputs to the nearest storehouse with room.   • Recruits: trainFrom consumes an idle own unit of that type within 15 cells of the producer.
  • Food: needs with "at": "<structure type>" are satisfied at the nearest own structure of that type (cost taken from the stock); starve hp per second is lost while the need is active.

Lanes (Mushroom Wars 2)#

"lanes": {"left": 4, "right": 2, "spacing": 0.35}: for every pair of garrison buildings the sim finds an A* path around obstacles and other buildings, smooths it into a fixed-point Catmull-Rom spline (about two samples per cell) and adds left + right parallel lanes spacing cells apart (pulled back towards the main lane where they would hit an obstacle). Sent units are spread over the lanes round-robin and follow their lane exactly. Lanes are rebuilt when garrison buildings or obstacles change (GameState::lanes, lanesDirty, event kEvLanesChanged).

Routes, groups, multiscreen#

Hand-authored routes between garrison structures, sends in rows, and a screen-sized play window over a larger map (modules/rts/RtsRoutes*.cpp). Lengths are map cells; every number is a rules / map key the game sets.

With trim > 0 nodes within trim of both ends are cut (lines start and end a little off the points). Lanes keep the route direction (Lane::a = from), offsets are -1, +1, -2, +2... in line order (lanesBetween returns line 0 first). Lanes exist for the whole match (stable indices).
  • Sends need an open route: kCmdSend between garrisons without one is ignored; GameCore::canSend / routeLength (line 0) / routeAiLength and Lua game.can_send(a, b) / game.route_length(a, b) tell. A closed route (a blocker alive) only refuses new sends; units already on it keep walking. The built-in AI only sends along routes.
  • Every line is walked at the progress of line 0 (lane speed x length k / length 0), so a row stays abreast in bends.
  • Units on crossing or shared routes do not fight each other by themselves; a skill can make walkers shoot with GameCore::routeWalkerTargets (hostile walkers in an ellipse / forward sector, nearest first) and routeWalkerDistances (walked / left along the line). Walkers are ordinary unit entities with a LaneWalker.
  • A route between entities whose screenGroups (map entity key, list of ints) do not match does not exist: both empty match, one empty does not, else any shared group.
  • zone (game-defined bits, 2 = slowdown) / slowdown per point feed routeAiLength only.
  • towersCoverage (for computer players): per tower entity the route length inside its range, for ranges 0, 1, 2 ... x routes.coverageStep (at most 21 values, the last holds beyond). GameCore::towerCoverage interpolates; towerUnitsDamage / towerDamageBySpline estimate losses of a group passing it.
  • Walkers get a random diagonal offset (routes.jitter, one sim.rng() draw per unit) that fades in over routes.fade from both route ends; the same fade is the unit's opacity in the view (SceneObject::fade, routeAlpha).
  • Flying sends: a garrison with a status carrying the flying flag sends along a straight flying route made on first use for that pair (in / out points routes.inOut from the ends, columns flyColumnPadding), even where no ground route exists or it is closed; rows are flyRowSpacing apart. groups.flyAll: such a send takes the whole garrison; groups.flySingle: one flying group per garrison at a time. Abilities and effects#

Everything a skill does is a list of effects (a payload). Effects can carry their own payload ("effects": [...]): a projectile delivers it on impact, an area applies it when it triggers, a chain applies it on every jump, a status ticks it, a weapon applies it on hit. Skills are compositions of these primitives; nothing is coded per skill. All keys below are optional; a game that uses none of them runs exactly as before (bit-identical replays).

Save states (agent-mech)#

Simulation::serialize() returns the whole dynamic state as bytes (versioned, little-endian, identical on every platform: engine/core/Archive.h); deserialize(bytes) loads it into a simulation set up from the same rules, map and seed and checks the state checksum stored in the file. Saved: tick, RNG, players and teams, pending and executed commands (replays continue), the entity allocator, every component pool in dense order and the dynamic part of GameState (per-cell layers run-length encoded). Not saved: rules, triggers, the planet surface (from setup) and derived caches (clearance, HPA*, rebuilt on demand). The computer players keep their own memory, so bots resume from the loaded state with fresh plans. Module side: GameCore::serializeState (engine/game/Save.cpp); a component type missing from its list makes saving fail. aiverse_headless --save F --save-at S / --load F; MCP match_run with saveCheck (seconds). A skirmish match at 90 s is ~150 KB. Since save version 9 the frozen match outcome (MatchOutcome) is saved too: a state from before the end, loaded into a simulation that had already finished, no longer keeps the old result (the computer players stopped and --verify-restore-at windows across the match end desynced on the serialized pass); older saves load with no outcome, latched again on the next tick.

Texture atlases (game.json atlas, optional)#

The editor's Build window shows oversized atlas candidates under “Не в атласе”. “Исправить размеры текстур” applies the proposed maximum sizes as exact, first-priority packaging.targets.<platform>.files rules and refreshes the size estimate. This reduces image detail in the built pack; original assets are unchanged. Sprite sheets, tile atlases, and UI @spritesheet sources in RCSS with pixel-based coordinates are never offered this fix. Existing resize rules for these sources are ignored during packaging to preserve their frame coordinates. Other exclusions (repeat wrapping, noAtlas, decode failures, a lone image in a group) require manual decisions. Recalculate a stale report before applying fixes; the button is disabled while settings differ from the report.

When a game is packaged (aiversebuild, assetpipe pack --atlas <profile>), small 2D images are packed into atlas pages: fewer texture switches/draw calls, trimmed transparent borders, identical images stored once, and pages compressed by the pack's zstd. Game code keeps using the original paths (units/orc/grunt/walk_0.png); the lookup is transparent at runtime. Loose-folder builds (--no-pack, editor) use the images as they are. The whole block is optional:

"atlas": {
  "enable": true,                                   // false (or aiversebuild --no-atlas): ship images as is
  "maxPage": { "web": 2048, "android": 2048, "default": 4096 },  // or a single number
  "pageSize": "mul4",          // page sides: multiples of 4 (default) or "pow2"
  "padding": 2,                // empty texels between images
  "extrude": 1,                // edge texels repeated around each image (no filtering seams)
  "trim": true,                // cut fully transparent borders (offsets are kept)
  "maxTextureSize": 0,         // larger images stay standalone; 0 = maxPage / 4
  "mipLevels": 2,              // groups with "mips": padding/alignment safe down to 2^levels
  "pageFormat": "rtex",        // "rtex" (raw RGBA, zstd in the pack, fastest load) or "png"
  "groups": { "units": { "rotate": false, "mips": true }, "tiles": { "trim": false } },
  "files": {                   // glob -> settings; `*` also matches '/'; later rules win
    "ui/splash/*": { "noAtlas": true },
    "units/orcs/*": { "group": "orcs" },
    "textures/water.png": { "wrap": "repeat" },
    "units/*/shadow.png": { "kind": "mask" }
  }
}

Profiles are aiversebuild targets (macos, ios, android, web, windows, linux); built-in page limits: 2048 for web/android, 4096 otherwise. Targets with equal settings share one pack.

What goes together. An image's group key is usage group + kind (+ opaque/alpha when the group splits by alpha, + mips). Images only share a page with the same key:

usage groupdefault folders (first path component, engine/ prefix ignored)defaults
uiui/, icons/, portraits/, cursors/, hud/trim
unitssprites/, units/, buildings/, structures/, characters/trim
tilestiles/, tilesets/, terrain/no trim (sheet grids stay intact), opaque and alpha tiles on separate pages
effectseffects/, fx/, vfx/, particles/trim
any nameset with "group" (or "atlasGroup") in filesas units

Other folders (models/, textures/, ...) are not atlased unless a files rule names a group: 3D meshes use UVs outside 0..1 and wrap. Kind is color, normal (*_n, *_nrm, *_normal, normals/) or mask (*_mask) — normal maps and masks are never mixed with colour and never trimmed. Never atlased: noAtlas, "wrap": "repeat" (also *_repeat, *_tiling, *_wrap), images above maxTextureSize (after trimming), and an image that would be alone in its group (one page = no saved texture switch, only padding). Images referenced as a frame-grid sprite sheet anywhere in the game's JSON ("sheet": "sprites/tank.png") are never trimmed or rotated, so frame uvs map linearly onto the atlas region. Inside a group, images of one folder (one unit's frames, one faction) stay on the same page whenever they fit; pages are shrunk to the smallest size that holds them. Per-file keys: group/atlasGroup, noAtlas, wrap, kind, rotate (allow a 90° turn, off by default so facings never rotate), trim, mips, splitAlpha, padding, extrude, mesh, tight, frames, meshVertices; the same keys (except group) work per group in groups.

Meshes, tight packing, framed sheets (all off by default, colour images only):

"files": { "sprites/*": { "frames": true, "tight": true, "rotate": true, "meshVertices": 8 } }
  • mesh — a convex polygon around the visible pixels (alpha ≠ 0) of each trimmed image, at most about meshVertices corners (4..32, default 8), conservative (every visible pixel is inside), kept only when it saves at least ~12% of the rectangle. Sprites are drawn as that polygon: less overdraw on mostly transparent images.
  • tight (implies mesh) — pack by those polygons instead of rectangles: an image may sit in the empty corner of another one's rectangle (padding still separates the shapes; the texels a polygon touches plus max(extrude, 1) around it belong to its image). The rectangle layout is computed too and kept when it is not larger, so pages never grow (typically 15–20% smaller pages for diagonal / round sprites, little for sprites that fill their rectangles). The page of a tight group is only correct when drawn through the meshes. Off in groups with mips. Costs build time: about a second per 500 unique frames (bit-row search), rectangles take milliseconds.
  • frames — a sprite sheet ("sheet" + "frame": [w, h] in the game's JSON, h = w when omitted, no frame = the whole image) is split into its frames, each trimmed, rotated, meshed and packed on its own. A sheet used with different frame sizes, or whose frame size does not divide it, is kept whole (and untrimmed, with a build warning).

Who draws what: the 2D sprite renderer (sprite blocks, Rts2DView) draws trimmed, rotated, meshed and framed images straight from the pages (TextureCache::resolveSprite + SpriteBatch::spriteShape: billboards, upright and ground sprites, decals on uneven ground, sun shadow casters). Every other consumer (TextureCache::resolve, the UI, particles, overlays) gets such an image rebuilt as its own texture (through the mesh), as before — correct, but without the page's savings; images that are on a page as they are still resolve to the page.

In the pack. Atlased images are removed; _atlas/ is reserved and holds the pages (_atlas/<group>-<n>.rtex) and _atlas/atlas.json:

{ "version": 1,
  "pages": [ { "file": "_atlas/units-0.rtex", "group": "units", "w": 1016, "h": 864, "alpha": true, "mips": false } ],

Optional, when used: "meshes": { "<path>": [x0, y0, x1, y1, ...] } — the convex mesh in content pixels × 16 (1/16 pixel grid, original orientation, origin at the trimmed content's top-left), and "sheets": { "<sheet>": [cols, rows, sourceW, sourceH] } — a framed sheet whose frame i (row-major) is the texture entry "<sheet>#<i>" (its sourceW x sourceH = one frame, offsets inside the frame).

Texture entry: [page, x, y, w, h, offsetX, offsetY, sourceW, sourceH, rotated] — integer pixels. (x, y, w, h) is the trimmed content in the page (when rotated = 1 it occupies h x w turned 90° clockwise); (offsetX, offsetY) is its position in the original sourceW x sourceH image, so pivots given in original-image pixels stay valid. .rtex: 24-byte header (RTEX, version, width, height, flags: 1 alpha, 2 mips, 4 left-delta filtered rows) + RGBA8 rows top to bottom, straight alpha. Output is byte-identical for the same input.

Runtime API (engine/atlas/TextureLibrary.h, link aiverse_atlas):

atlas::TextureLibrary lib(dev, [](const std::string& p, std::string& o) { return platform::readContentFile(p, o); });
const atlas::TextureRef* t = lib.get("units/orc/grunt/walk_0.png");   // nullptr if missing
// quad: t->w x t->h source pixels at (t->offsetX, t->offsetY) from the original image's top-left
// (pivot in original pixels: pos - pivot + offset); UVs t->uv = TL, TR, BR, BL (rotation applied);
// t->texture equal for images on one page -> batch by it; t->opaque -> draw without blending.
// t->mesh != nullptr: draw that polygon (content pixels; + offset, map with mapUV), never the quad.
// A framed sheet comes back rebuilt as its own texture.

atlas::mapUV(*t, px, py, u, v) maps a point in original-image pixels to the texture (trim and rotation included) — e.g. frame corners of a sheet. For a renderer that already maps frames via a rect (u0 + (u1 - u0) * lu), the rect of an atlased sheet is t->uv[0..1] .. t->uv[4..5]. The 2D sprite/tile renderer's render::TextureCache::resolve() already understands atlases: an atlased image resolves to the page texture + its rect (sprite sheets are never trimmed, so frame uvs stay exact); a trimmed, rotated, meshed or framed image is rebuilt as a standalone texture. resolveSprite(path, nearest, base, frameW, frameH) returns it on its page instead (TextureRef::sprite: frames with region, mesh and page texture) for renderers that draw render::spriteShape(ref, uvRect, shape) — a convex polygon in rect parameters plus the affine map to page uv (SpriteBatch::quad / polygon / casterPolygon). Plain (non-atlased) images come back the same way (own texture, full UVs, no trim). CPU pixels of an original image: lib.loadImage(path, img) or atlas::ImageSource (the UI uses it, so RmlUi <img src> and decorators keep working with atlased files).

Heightfield terrain#

rules.terrain.model: "heightfield" + a map with terrain.corners / cornersFile (without corners the map plays like "levels"). Corner (x, y) is the top-left corner of cell (x, y); heights in 1/16 world units. Everything is integer / fixed point and deterministic.

  • Surface: ground height at any point is bilinear between the 4 corners of its cell; ground units (and the y of every mobile unit) stand on it; projectiles start at the shooter's ground + 0.6 and aim at the target's ground + 0.4.
  • Slopes: per cell steepness = max(gradient length, steepest cell edge), in height units per cell. A unit can't enter cells steeper than its move.maxSlope (or terrain.maxSlope of its layer; sand for layer: "sand"); pathfinding, local avoidance and spawning follow the same rule. Cliff/ramp rules (levels, /) are replaced by slopes. Structures need cells no steeper than terrain.buildSlope.
  • Speed: speed * (1 - uphillSpeed * climb) going up, * (1 + downhillSpeed * descent) going down, where climb/descent = height change per cell along the move; clamped to 0.25..2.
  • Vision: line of sight from eyeHeight above the unit's cell to targetHeight above each cell in sight range; a cell behind a ridge is hidden (heights.blockVision: false turns this off, air units see over). Targeting only picks enemies in a cell the player sees.
  • Cliff level of a cell = floor(cell height / levelHeight) (0..9), so level-based rules and triggers keep working. Range / damage / miss bonuses use the exact height difference (see heights).
  • Checksums: corners and the model are part of the state hash only for heightfield games.
  • Big maps (256x256 cells and more): long paths use hierarchical pathfinding (16x16 clusters with border entrances, refined with A*), built at match start and rebuilt only around structures that block cells. aiverse_headless --project DIR --bench-paths N times path queries; python3 templates/_tools/mapgen.py --big 1024 <scratch>/maps/big.json writes a 1024x1024 test map (keep it out of templates/).

MCP: map_info.heightfield (corners, min, max, storage, model), map_heightfield {"enabled"} adds a flat heightfield or removes it, map_validate warns when the model is heightfield but the map has no corners and flags units/structures standing on slopes too steep for them. Sculpting: terrain_sculpt, heightmap PNG import/export (see Terrain materials). The view draws the relief from the corners (two triangles per cell, diagonal (0,0)-(1,1)); GameView::heightAt follows the same triangles, so models and overlays sit on the drawn ground.

  • Flat maps: top-level generate. Planets: world.bodies[].generate (presets rocky, ocean, moon; see docs/planets.md §4).
  • What the generator writes: size, terrain.rows (. ~ # , = / R, diggable characters for caves), terrain.levels (rules terrain.model levels), terrain.corners (heightfield), fields, entities, regions (if the template has them), roads (garrison games), terrainMaterial (from the biome and the game's visual terrain.layers ids: grass / forest / sand / dirt / earth / rock / snow / mud ...), players' start, and a summary block generated (preset, seed, symmetry, starts, path lengths between starts measured with the engine's A*, connected, pathSpread in per mille, object counts, warnings). Every other key of the map (victory, triggers, waves, lighting, ...) is kept.
  • Objects come from the game's own types: player 1's objects of the template (or of the map itself) are the start kit, placed for every player in the symmetric frame (rotated by quarter turns so footprints stay aligned); neutral objects are counted near the template's bases / far / at the centre and placed the same way (mines and metal spots near each base, forests in forest biomes, creep camps away from bases, garrison buildings, portals...). Without a template the rules decide: a structure that produces workers + 4 workers (or a key unit, or the biggest garrison), resource nodes, structure.on spots, field spawners, neutral creeps. Resource fields of the template are reproduced (near ones keep their offset).
  • Fair starts: the start of player 1 is chosen in the fundamental domain of the symmetry and copied to every image; base areas are flattened (one cliff level / gentle corners, never water); starts are connected (ramps cut through cliffs, shallows = through water, a graded road on heightfields, the cheapest route through diggable rock); objects never block the route between starts (an unblock pass removes them); the result is validated with the pathfinder. "connect": "none" keeps islands separate (naval / air games).
  • Determinism: integers / Fixed only (no float), seeded hashing, ordered containers; the generator runs inside GameCore::setup before the map is loaded, so replays and the server arbiter regenerate identically. Golden hashes of the presets are in tests/tests.cpp (gen_golden_maps and friends): a change of the generator's output shows there. Same seed + params + engine version = same map.

Where shadows fall is the sun's direction: "lighting": {"sunDir": [x, y, z]} (game.json or the map, towards the sun at noon; the day cycle swings around it). Flat drawings hide shadows that fall straight behind them, and a sun behind the scene leaves camera-facing cliff walls unlit, so sprite games usually want it from the side and a little in front (km2d: [-1.0, 1.2, 0.45], shadows to the right). "shadowSoftness" (world units, default 0.22) is the maximum penumbra radius. Medium/high sun shadows harden at contact and widen with caster/receiver separation (PCSS); pixel-art games look cleaner with a tight one (km2d 0.07): kernels of a few shadow-map texels are filtered without the per-pixel noise rotation, so they stay smooth on every tier.

Blobs and ground sprites are projected: a blob (and any "mode": "ground" sprite) is cut from the ground triangles under it — the exact triangles of the terrain mesh or the tile map — and drawn with a depth bias, so it bends over slopes and cliff edges and never z-fights or hovers. Sprite types get no extra contact-shadow decal from the lighting system (their blob does that job).

Map environment#

Optional block "environment" in rules.json (defaults) and in the map (map keys win, key by key). Code: modules/rts/RtsEnv*.cpp. A game without the block has no environment state and keeps its checksums and saves. State: the EnvState world resource (hashed, saved after the grid fields, rolled back with the world). 3D line of sight#

With "fogOfWar": {"lineOfSight": true} (always on for heightfield maps with heights.blockVision) each ground unit sees a cell only if the straight line from its eyes to the cell clears every cell in between. Heights: heightfield surface, or cliff level × levelHeight on level maps; plus dynamic occluders, recomputed every vision pass (5 ticks):

Computer player (ComputerPlayer, agent-ai-terrain)#

The bot reads the state and submits commands like a player (replays don't re-run it). Generic for every template; knobs in rules ai (above). What it does with the terrain:

  • Analysis at match start (RtsAITerrain.*, integer, rebuilt identically after loading a save): per cell the elevation in height-advantage units (cliff level, or heightfield / planet height divided by levelHeight), the walkable mask of the ground layer (terrain only), corridor width (steps to the nearest wall: chokepoints), over (how far higher ground within 4 cells rises above the cell) and crest (prominence). Flat maps, heightfields and cube-sphere planets (neighbours across face seams) alike.
  • Routes: weighted Dijkstra from our base to the nearest enemy base: climbing into the enemy and cells overlooked by higher ground cost extra (climbWeight, exposureWeight), so waves come through saddles and ramps instead of up a ridge under fire; an alternate route avoids the main corridor (used on odd waves when stalemated).
  • Posts on the route: rally point on the highest well-covered ground 9-14 steps out of the base (the army waits there, producers rally there); the narrowest cell on our side (towers after a raid); a watch post on the most prominent ground in the middle of the route for a scout (vision over ridges). Idle units are not re-sent to the rally point (a unit walking back would not count as ready for the next wave).
  • Waves follow waypoints every 12 cells, stop at a siege spot on high ground short of the target, then attack; they hold up to 30 s instead of charging uphill into a stronger enemy (and pull in reinforcements), retreat to the rally point below 25% of their start size without a kill (until stalemate level 3), launch early with what is at home when our army is twice the enemy's whole armed force, stop at a stuck-wave watchdog (30 s without moving), retarget the next structure, attack construction sites by name.
  • Economy guards: own build spots (lanes between dropoffs and resources kept free, the rally area kept free, random tie-breaks), stuck builders released and their spots avoided, the first army producer early, converters (metal makers) only with a surplus, one more producer when resources float, expansion (a dropoff at the next node) when the near nodes are gone, workers spread over crowded nodes and spawned on the side of their resource.
  • Breaking stalemates: an enemy without armed units is finished by the whole army (its weakest structure that counts); at stalemate level 1+ a smaller strength edge launches a wave and at level 2+ waves are capped at 3/4 of firstAttackArmy; the bot builds / researches what unlocks units clearly better against the enemy's toughest building (damage table, bonuses, armor) and saves for it; garrison play sends from full garrisons first, funnels them to the front and after 10 min lets every garrison join a push; settlers economies build the main building material chain first, then what the army costs; a stock the population eats running dry stops housing; regions that must be seen first get a scout; slow gatherers (no workersPerBase in the rules) get more workers.
  • Planets: an orbit fleet (invasionSize + 2 per invasion) transfers together to the body with enemy structures and fights there until the body is clear, then the next body; more orbital yards when the enemy can be reached only through orbit; towers that hit the orbit when attacks come from there.
  • Per-slot styles: map players[i].ai (see "Maps") gives one slot a preset and its own knobs; applied before the first think (and again identically after a load), so thinkTicks from the slot is used from the start.
  • Save states: ComputerPlayer::saveState() / loadState() (headless --save F writes F.ai next to the sim state, --load F reads it): a restored bot plays on exactly like the saved one.

Optional rules block progression: the match-progression library format (stats, perks, units, deck, xp with toNext / curve / kill, offers with default / levels / variants / preferNewRecruitAtLevel / recruitWeight / recruitAiPriority, summonPoints with id / team / position / radiusMilli / progressTicks / cooldownTicks / singleUse / action; perks with key, hook, scope, bearer, effects (stat, op, value, stage), maxSelections, minLevel, weight, requires, excludes, tags, upgrades, offerable, aiPriority, aiPriorityLowHealth) on real units, plus engine keys: units[].type, perks[].bullet (modifiers: split / ricochet / flyThrough / damage / speed / radius appended to the bearer's projectile programs), perks[].onHit / onHitChance (effects payload on hit: burn, stun, ...), players, killXp, orbs, orbOwner, autoOpen, offerAt, offerChoices, offerRerolls, rerollAvoidsRepeat, maxLevel, xpGrowthPerLevel, maxRecruitsPerSlot, maxSquad, pickups (radius, magnetRadius, grabRadius, attractSpeed, attractAccel, maxSpeed, landing, lifetime, maxOrbs), summons (progress, cooldown, maxAllies, charges, chargeRecharge, resetOnExit), squad (follow, lifetime), critDamage, decks, defaultDeck (battle deck payloads: player, techLevel, choiceCount, enforceUnlocks, slots with slot, unit, level, opened, inTeam, perks). Map: progression.summonPoints, players[i].deck (the match start payload). Hero xp from kills and xp orbs, seeded level-up offers chosen with kCmdProgression (UI, bot, Lua, MCP), perk stats on damage / incoming damage / speed / fire interval / range / max health / splash / crits / regen, summon circles and recruits as real units. Full reference: progression.md; sample: templates/perk_arena.

Boss encounters#

Rules block encounters (boss-encounters library on real units; reference docs/encounters.md, sample templates/boss_arena). Map players with "monsters": true and hostile creeps (owner 255) are driven by it (the computer player skips them).

  • attacks.<id>: shape (circle / cone / line / ring), radius, inner, angle, length, width, anchor (source / aim), offset, windup, active, recovery, interval, cooldown, damage, damageMin, falloff, damageType, statuses (rules status ids or {"status", "duration"}), statusDuration, oncePerTarget, trackAim, sweep, cancelOnDeath, friendlyFire, minRange, maxRange, ability (a unit ability starts it).
  • bosses.<unit type>: engageRange, loseRange, approach, immune, archetype, phases[] (hpBelow, after, damage, speed, cooldown, globalCooldown, transition, mode byRange / sequence / weighted, pattern[] (attack, alternate, minRange, maxRange, weight), adds[] (unit, count, every, maxAlive, minRadius, maxRadius)), enrage (after, hpBelow, damage, speed, cooldown).
  • mobs.<unit type>: aggroRange, loseRange, stopDistance, switchMargin, wanderMin, wanderMax, arriveRadius, leash, wanderDelay, wanderLeg, wanderAttempts, fleeBelow, fleeRecover, fleeRange, fleeTime, wander, spacing, correction, lookAhead, neighbours, attack, think, flowDistance.
  • schedule: personal, rotation, archetypes, spawnDistance [min, max], windows[] (start, end, breather, excludePrevious, pauseWaves, variants[] (boss, weight, archetype)).

Lua events boss_engaged, boss_phase, boss_enraged, boss_adds, boss_defeated, boss_window, telegraph_start, telegraph_strike, telegraph_end (statuses: status_start); table encounters.

City traffic#

Rules block traffic (with topDown + driving): computer-driven cars on lanes built from the map's tile characters, signalised junctions with light props, pedestrians on the sidewalks who cross on "walk" and panic at gunfire; map "traffic": false switches it off. Keys, defaults and behaviour: docs/traffic.md.

Ordered projectile flight programs#

Weapons and projectile deliveries accept an optional flight object with ordered Split, Ricochet, Fly Through and scalar modifiers. See Projectile programs for the schema, inheritance rules, collision boundaries, save version and executable example. Legacy projectiles are unchanged when this block is absent.
