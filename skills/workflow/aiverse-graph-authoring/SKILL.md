# Shared graph authoring
Read docs/agents/graph-framework.md, docs/agents/feature-contract.md and the owning subsystem rules. Reuse GraphRegistry, GraphAdapter, validateTopology and GraphCanvas in apps/studio-web/src/graphs. Define domain-specific typed ports, cycle policy and native validation; do not introduce a second runtime or change persisted formats merely to match UI. Use typed Studio bridge and existing MCP operations. The current shader adapter covers three shader domains. DraftHistory is local only; preserve domain commit semantics. This workflow has no runtime target. Run npm run test:graphs, typecheck, build and real native QA. Record handoff and exact evidence. For new authoring domains update graph inventory, feature manifest, catalog, and the owner roadmap.

Use graphSelection.ts for marquee selection and rigid grouped movement. Preserve stable IDs, remap only internal clipboard links, validate domain compatibility, and commit each group edit to local draft history once. Never paste native file paths or bypass domain validation.

GraphCanvas consumes GraphView and PortRef ({node,port}) from graphGeometry.ts. Provide named typed ports, including multiple outputs if the native domain supports them. Use graphGeometry for transient wire positions and domain mutations for real edits; never persist preview geometry or apply another domain's cycle rules. Supply scoped commands and catalog-validated templates as appropriate.

For SpectraFX and MotionWeave, see nativeGraphAdapters.ts and NativeGraphPanel.tsx. Use the allowlisted studio.op bridge with each domain's existing operations. Keep execution/data ports distinct, preserve pose DAG ordering and state transition loops, and use the native validator before any save. MotionWeave supports expected document concurrency checks; SpectraFX published save currently has only a non-atomic read-back preflight. Do not advertise concurrent writer safety for SpectraFX.

For model sources use ModelGraphPanel and modelProjection: distinguish transform-parent edges from geometry operands and embedded pose/state graphs. Native modeling_edit requires expectedRevision and builds the full source before commit. Never write project source from the browser. Visual state links create an explicit unconditional transition draft; configure conditions/order before saving and use native validation.

For geometry dependencies use geometryProjection and connectGeometryOperand rather than transform parent links; native boolean operands must precede consumers, and modifier ordering is semantic. Reuse AnimationConditions/AnimationParameters for declared scalar conditions and preserve vector parameters and all native data. Native validation and revision-safe save are mandatory.

For procedural generators use generatorProjections.ts only as a read-only dependency representation of actual owner recipes. TerraWeave is connected to its existing panel; Building and Caverns projections await their owner branches. Do not treat a diagram as an executable graph. Preserve native material IDs and texture dependencies, revisions and owner validation. Add or remove model modifiers only in draft and compile before commit.

For material dependencies use materialGraph.ts and MaterialGraphPanel. Keep PBR channel meanings distinct; resolve generated texture assets by GUID through Studio Assets, never pass arbitrary project paths to studio.materialPatch. Generate through existing texture_patterns/texture_generate and explicitly assign then save the material draft. The no-overwrite option checks existing files but is not cross-process atomic. Do not confuse the dependency diagram with an executable procedural texture graph or treat PNG creation as undoable material editing.

For STRATA use StrataAnalysisPanel and the native strata_capabilities/strata_model_analyze operations. Never infer GPU timing, live LOD selection, GPU parity or cooked assets from the CPU staging report. Select an actual exported model, not an unsaved source. GraphDiagnostics is advisory; configure the domain cycle policy (SpectraFX separates exec/data, states allow cycles), retain native validation, and label editor timings as editor-only.

Use graph_catalog first for generic MCP graph work. Call graph_list/get, then graph_validate or graph_diagnostics with the returned native graph (or document for modeling). graph_edit currently supports native SpectraFX in-memory edits only; other edits retain their domain contracts. graph_save requires expected original MotionWeave document, expectedRevision for Modeling, or explicit allowUnversionedWrite for shader/SpectraFX; never label unversioned writes concurrency-safe. graph_dependencies returns explicit authoring references, not an asset closure. Native owner APIs remain available; generic shader results omit generated code. Do not bypass the graph catalog or invent support for unregistered domains.

Stage 12 supersedes the earlier SpectraFX-only graph_edit limitation: all four registered families accept one edit or an ordered batch of up to 64 edits. Read graph_catalog.editActions and docs/agents/graph-framework.md for family-specific fields. Modeling uses native op/collection/id/value commands, other families use action commands. Check result.valid and native validation; applied does not mean valid or saved. Use graph_save separately with original expected document/revision or explicit unversioned write consent. Never infer runtime execution or filesystem atomicity from in-memory edit transactions.

Use graph_property_schema for the supported node property subset before graph_edit setProperty (Modeling uses op:setProperty). Do not modify immutable IDs through property edits. Use graph_asset_dependencies for literal references and embedded animation subgraph recursion; file-present means existence only, not valid imports or transitive closure. SpectraFX schema response is native catalog defaults, not exhaustive constraints. Keep native validation and revision guards.

Use graph_runtime_capabilities before graph_runtime_probe. Only MotionWeave and SpectraFX have isolated CPU probes; max 60 fixed steps. The results are actual native owner counters when the probe runs, not live-game telemetry. Do not describe active pose program as per-node execution trace, state changes as all transitions, or CPU times as GPU times. STRATA remains analysis-only. No project writes, runtime attachment or GPU profiling.

Use graph_live_snapshot only for read-only current owner data. MotionWeave requires the exact packed entity generation ID as a decimal string. The native editor adapter is optional; unavailable is not zero or a successful sample. Never map live node IDs onto an unsaved graph without asset/program provenance. SpectraFX counters are shared-owner aggregates and existing GPU preview counts are estimates. No live pause/step/breakpoints or modern ECS runtime attachment are provided by this stage.

For isolated debugging use graph_debug_session start/status/step/continue/breakpoints/stop. Always pass returned session string to commands except start/status. Only explicit calls advance time; max 60 steps per continue, 600 per session. Breakpoints match MotionWeave state/program after a complete step; not per-node execution breakpoints. Session program token is not a content hash. Stop before switching graphs. GraphTelemetry.h is a value-only owner-thread history contract, not a registered ECS telemetry producer; actual live owners must supply world epoch, generation and program identity. No gameplay mutation or live pause.

For shared MotionWeave ECS telemetry call View::animationTelemetry or captureAnimationTelemetry on the committed View after workers join, with the host-owned non-reused world epoch. Never capture a preparation candidate or add another graph evaluator. Native editor graph_live_snapshot captureHistory=true captures requested samples only; history is keyed by lifetime identities, not asset content hashes. Generic host integration requires its own epoch/publication barrier. Distinguish update/evaluation counters from per-node timings and legacy fallback from common ECS source. No continuous collection or live control is implied.

Use graph_live_watch {action:start,domain:motionweave,entity:<packed ID string>} or {action:start,domain:spectrafx,entity:preview} only with supported native editor play owner; status/stop are explicit. One subscription, last 120 published samples, no replacement following, no background process or GPU timing. FX serial pins actual CPU preview instance, not its asset revision. Never infer a live owner in headless/HTML5 host from registry presence. Do not equate viewport frame sampling with simulation ticks.

For actual MotionWeave per-node CPU scopes, start an isolated graph_debug_session, call profileEnable with its session ID, step/continue, then profileRead. Use profileReset or profileDisable explicitly. Report phase totals and max durations are inclusive wall-clock microseconds, with trace of the last step (max 512 intervals); no shader/GPU or FX authored-node timings. Prepared View clones and graph resets drop instrumentation. Do not equate scope calls with all graph execution or profile overhead with gameplay cost. Use the immutable session source for heatmaps, not edited drafts.

For live selected MotionWeave CPU profiling use graph_live_profile {action:enable|read|reset|disable,entity:<exact packed ID string>} only when native editor play host has a committed common View instance. The profile follows one pinned publication identity; graph/Entity replacement disables it. Prepared View copies counters only for that explicit selection, never shares mutable profile storage. Do not read failed candidates, map reports onto unrelated drafts, or interpret inclusive CPU timings as GPU measurements. Stop disables instrumentation; unsupported hosts report unavailable.

Use graph_gpu_profile {action:start|read|stop} for opt-in native editor scope capture. Only valid completed RHI queries are reported; viewport samples cover combined rendering, FX and post-processing, not authored nodes or individual passes. SpectraFX step requires accepted scope and step. Metal/GL33 have existing scope implementations, Vulkan/GLES3 do not in this branch. A backend implementation or pending query is not proof of measured GPU timing. Do not independently drain Device::takeGpuScopeTimings or takeGpuTimings; preserve the existing collection owners. Unsupported hosts return unavailable.

Texture graphs: use texture_graph_catalog or graph_catalog domain texture. Version 1 nodes have id/op/inputs/properties, size and typed outputs. Native validation is authoritative, max 32 nodes and 4,194,304 pixel-nodes. Use texture_graph_preview for one node/output, texture_graph_set to save source (expected on existing), texture_graph_bake for one new output PNG. Do not overwrite or auto-assign material channels; resolve actual asset GUID and set correct data/normal importer settings before Apply. Use glTF packed G roughness/B metallic for metallicRoughnessMap. No automatic AO, GPU texture DAG, or full visual wiring in this stage.

Stage 23: use texture_graph_catalog properties/outputTypes for typed authoring and texture_graph_templates for native starter documents. texture_graph_bake_set {graph,textureName} stages all declared outputs in a new content/textures/<name>/ directory, evaluates shared dependencies once, and returns files with output/path/sRGB. Resolve GUIDs through existing asset catalog; Studio patches and reads back sRGB using studio.assetMetaPatch before explicit material draft assignment. This is color-space metadata only, not a dedicated normal-map import mode or proven GPU behavior. Existing sets are not overwritten; no arbitrary-writer atomicity or cross-edit cache.

Stage 24: declare texture parameters as {name:{default,bindings:[{node,property}]}}; pass overrides separately to validation/preview/bake. Use texture_graph_cache for per-Workspace bounded memory cache status/clear. Bake set includes texture-set.json provenance. texture_graph_material_variant {textureName,materialName,base} creates an inherited material via material_set from verified baked paths; configure importer separately. Never claim runtime procedural material instances, on-disk cache or GPU evaluator. Source graph remains unchanged.

Stage 25: texture_graph_gpu_preview {action:start,graph,overrides,output|node,requireGpu} queues one native Metal preview; action:read reports exact request identity, pending/ready/failed/unavailable and backend. Only completed GPU readback within one RGBA8 unit of CPU reference counts as Metal; unsupported normal/pattern closures fall back unless requireGpu. At most 32x32, no full-resolution GPU bake or speed evidence. Native owner must be registered; do not claim headless/HTML5 or other backend support. CPU bake remains authoritative.

Stage 26: texture_graph_gpu_preview accepts resolution 8..128 (clamped to source graph size). Native Metal/Vulkan routes use actual asynchronous storage buffer readback. Terminal height-to-normal uses four wrapped scalar graph samples; pattern and patternMask still fall back. This is fused neighborhood evaluation, not general multi-pass compute. Only verified completed readback can be labeled GPU; CPU bake remains authoritative. No real GPU acceptance yet.

Stage 27: GPU preview compiler supports default Pattern/PatternMask recipes from TextureGen palette plus pointwise graph ops. Terminal normal uses explicit two-pass float scratch plan; inspect encodedPasses and plannedScratchBytes, but count actual GPU success only after completed CPU-parity-checked readback. No generic multi-pass DAG, persistent GPU cache, full-resolution GPU bake or real hardware evidence yet.

Stage 28: texture_graph_gpu_preview {action:start,graph,overrides,output,bake:true,requireGpu} requests full-size single-output generation; read status until ready, busy=false; then action:publish with exact request and new textureName. No pixel upload through MCP. Backend label identifies GPU only after complete block readback and CPU parity check. Preview remains <=128; bake <=1024 and existing graph budget. CPU fallback allowed unless requireGpu. One completed plan cache per native editor; no multi-output GPU bake, direct runtime texture binding or measured speedup. Headless owner unavailable.

Stage 29: texture_graph_gpu_preview {action:start,graph,overrides,bakeSet:true,requireGpu} processes all declared outputs sequentially. Read status until ready and busy=false; then publish with exact request and new textureName. Per-output backend is recorded in the shared texture-set.json manifest. Exact duplicate target results reuse validated pixels; distinct graph closures still compute separately. Same-sized storage reused only on completed plan boundary. RequireGpu fails whole set on fallback; no partial publication. CPU fallback mixed sets are explicitly labeled. No runtime binding or GPU timing evidence.

Stage 30: call texture_graph_gpu_preview {action:cancel,request:<exact ID>} for an active or ready unpublished request; do not cancel a different project or stale ID. Optional start timeoutMs is 1000–300000 (default 60000), checked at owner frame boundaries. Timeout fails the request, even when CPU fallback is allowed. After cancel/failure, read until busy=false before starting another request; draining=true means native GPU resources still await retirement. Never interpret cancellation as a completed bake or force device destruction to unblock it. A missing callback can keep the owner draining until teardown. No GPU acceptance evidence yet.

Stage 31A native integration: use engine/render/graph/TextureGraphMaterialBinding.h prepareMaterialImages and stageMaterialImages, or TextureGraphGpuPreview::stageCompletedMaterial for the exact completed unpublished PBR request. Provide a unique immutable generation per model, use the existing ModelImageUploadTransaction and publish the returned candidate only after committing staged images; abort the outer transaction on any error. Preserve material owner and GPU retirement, do not mutate shared live Model or bind height/standalone scalar outputs as packed PBR. This is CPU-pixel staging/upload (including validated GPU readback), not zero-copy or a registered runtime material editor operation. Host wiring and native GPU evidence pending.

Stage 31B: native hosts may call AppearanceAssetRegistry::publishTextureGraphMaterial with exact appearance version and model publication generation, current host-owned mutable Model, valid RenderDeviceLifetime lease, persistent ModelImageRollbackPool and complete graph outputs. Call only after joining readers at the owner frame boundary. TextureGraphGpuPreview::publishCompletedMaterial checks project/request before forwarding. Old snapshots keep their original image indices and graph epoch. Limit: 24 generated images per Model; reject on budget exhaustion, use existing Model owner retirement/reload rather than deleting individual textures. No live host call site, MCP/Studio apply action or GPU-to-GPU transport yet; tests NOT RUN.

Stage 32A: inspect pipelineCacheHit, pipelineCacheHits and idlePipelinePlans in texture_graph_gpu_preview read. Cache retains three idle exact backend/source pairs plus the active pair; only parity-accepted completed plans are stashed. Studio request status is independent of draft parsing; mismatched drafts cannot render/publish that result. Do not infer intermediate DAG caching or GPU performance from pipeline cache hits.

Stage 33A: request-local shared float scratch for PBR sets. When a declared scalar output is the exact input of the declared normal output, the scalar pack and normal passes consume the same float producer; independent pointwise outputs retain the fused path. Reuse requires completed CPU-parity acceptance, same immutable request/node/resolution/backend and retained scratch buffer. Invalidate on failure, cancellation, new request, device loss or storage replacement. `reusedScratch` describes the current skipped producer dispatch, `sharedScratchHits` counts accepted consumers in the request. Every output still gets CPU reference acceptance; no additional GPU buffers, arbitrary DAG cache, direct GPU texture binding or measured speedup.

Stage 33B: use TextureGraphLiveness.h planDagLifetime for a validated dependency-only graph closure and release-after-consumer plan. Targets are pinned through output packing; duplicate edges count independently. Existing CPU evaluateMany uses it for float-array release. peakLive is a count of simultaneously live node arrays, not measured CPU/GPU bytes or a GPU fence. Never use this logical plan alone to destroy submitted GPU resources. Standalone policy test PASS, integrated parity/GPU tests pending.

Stage 34B (parallel storage planning): `gpu::planDagSlots` derives the reachable validated closure from `planDagLifetime`, assigns deterministic smallest-free float4 slots, preserves input port order/duplicate edges, and packs each unique requested target at its producer step with explicit ordered output indices. Release slots only after all step compute, packing and readback are completed by the native owner; never alias input/output within a dispatch. At most eight slots and 64 MiB logical payload including one reusable RGBA8 staging buffer; the limit excludes driver overhead, retained CPU images and pipelines. A rejected budget returns no executable steps, allowing the existing fused route. This is pure planning only, not GPU allocation, dispatch, synchronization or an MCP/Studio execution mode. Existing Program graph work budget and backend binding limits still apply. The 32-node 1024 synthetic allocation fixture deliberately tests policy independently of the Program work budget.

Stage 35A: `gpu::compileMaterializedDag` lowers a validated Program and ordered targets to `DagSlotPlan`, per-step `compileNodeKernel` source and a reusable `compilePackKernel`. Fused and materialized pointwise expressions share the existing numeric/compiler code. Float4 intermediate ABI is 16 bytes/pixel; Metal storage slots 0..3, Vulkan TextureResources bindings 12..15, at most three ordered inputs. Normal samples wrapped neighbors from its scalar input; pack emits the established RGBA8 format. No source plan on budget rejection or unsupported node; existing fused route stays intact. A source plan is not executable GPU work: native owner must allocate buffers, enforce per-step compute/pack/readback retirement and provenance, and preserve requireGpu semantics. No new MCP/Studio execution mode, performance or hardware claim.

Stage 35B experimental native early-pack execution: `texture_graph_gpu_preview {action:start,graph,overrides,bakeSet:true,materializedDag:true,requireGpu:true}` requests a materialized set; the default start remains fused. Existing TextureGraphGpuPreview owns one embedded TextureGraphGpuExecution, mutually exclusive with fused storage. Up to eight float4 slots and one RGBA8 staging buffer, 64 MiB logical payload cap; destroys existing idle fused resources before allocating. Uses parent 34A validPassSchedule for resident-slot preflight; issues at most one node, pack or readback submission per tick; requires nonzero current GPU fence and completed token before reuse, destruction or progress. Every unique output receives full CPU reference acceptance, fanout maps to ordered set indices; only full completed set is exposed for explicit publication. Failure drains and restarts the existing fused path; requireGpu prevents CPU fallback in that path, not materialized-to-fused fallback. Cancel/timeout/project change discards unpublished output and drains; unhealthy device abandons handles. Read `executionMode`, `materializedRequested`, `materializedFallbackReason`, `materializedCompletedOutputs`, `materializedEncodedPasses`, `materializedReadbackBlocks`, `materializedPlannedBytes`, `materializedAllocatedBytes`. Require ready, busy=false, executionMode=materialized and actual Metal/Vulkan backend to claim materialized success; no performance claim. Studio has a separate experimental set button. Source-only integration; full build and hardware acceptance NOT RUN. Parallel parent 34B/34C uses a distinct pinned-output typed lowering; reconcile to one canonical compiler/planner before merging. No direct runtime/zero-copy binding.
