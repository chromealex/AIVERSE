AIVERSE PHYSIS#

PHYSIS is the genre-independent nature simulation for AIVERSE. Weather, local climate zones, wet ground, snowfall, fire, shallow flooding and quake intensity are authoritative ECS state. It is not coupled to FPS/RTS or any renderer.

Current implementation boundary#

  • The implemented weather evolution is a deterministic simplified local model, not a physically accurate global circulation model; seasons are triangle waves, fronts have Manhattan falloff.
  • Fire, flood and quakes are base ECS mechanics; hurricane/tornado are simplified deterministic vortex/forcing fields, not complete atmospheric CFD, volcano, avalanche, fluid, terrain deformation or destruction solvers.
  • Responses like traction multiplier and runoff potential are coefficients/hints. An optional, explicit engine/physics/PhysisBox3D.h adapter now applies PHYSIS wind/ gravity corrections to physics::Scene dynamic bodies, but no automatic Scene/WorldScene hookup is wired. Since 2026-11-21 an opt-in nature presentation host drives TerraWeave grass (burn/wind), SpectraFX fire/smoke, fire light and audio, and the editor shows it live without a play-test (see «Nature presentation host» below); the native game client is not hooked up yet.
  • Grid updates can run on several threads (bit-identical) and only in active chunks (see "Automatic integration, parallel update and streaming" below). Still no distributed weather, disk paging of cells or grids above 1,048,576 cells.
  • No compile/CTest/CI verification has been completed in this connector session; code present does not mean tests passed.

Automatic integration, parallel update and streaming (2026-11-22)#

PHYSIS from map data in every game#

Simulation::setup calls physis::autoInstallFromMap (engine/physis/PhysisAutoInstall.cpp) after GameModule::setup, for every module. A map with an enabled "physis" block now runs the nature simulation in the client, headless, server and editor play-test alike (lockstep peers and replays agree). Opt-outs: "physis.enabled": false, "physis.autoInstall": false (the module installs it itself later), or a module that already called installFromMap in its own setup. Parallel grid update — engine/physis/PhysisParallel.h#

InstallOptions::workerThreads / map "physis.workerThreads" (1 = serial default, 0 = hardware, N lanes). Atmosphere, surface and the disaster read/compute/commit passes split their cell ranges over a persistent thread pool; flood transfer is gathered per receiving cell, so results are bit-identical to serial for every lane count (test physis_parallel; serial checksum A/B against the previous sources is equal). Custom providers passed to advanceWith while lanes are active must only read the World. Measured on the user's Mac (Release, 28 logical cores, other builds running, load ≈24), 1024×768 grid with storms + disasters, 10 ticks, 3 runs: 1 lane 161.6–162.5 ms/tick; 2 lanes ×1.92–1.95; 4 lanes ×3.69–3.73; 6 lanes ×5.33–5.40; 8 lanes ×6.62–7.00. Linux VM (Debug, 4 cores): ×3.54 on 4 lanes.

Chunk streaming — engine/physis/PhysisStreaming.h#

"physis.streaming": {"chunkCells": 32} splits the grid into chunks. Any entity with an ActivityAnchor (position + radius; players, cameras, vehicles, scripted regions) keeps chunks within its radius simulated; other chunks are dormant (weather, surface, fire, flood frozen; dormant cells are walls for flood transfer and never ignite). The mask (ActiveChunks) and anchors are persistent, hashed ECS data recomputed by the physis.streaming system at the start of every tick. No anchors = whole grid. Static anchors can be listed in "physis.anchors". This is simulation streaming (what is updated); cell data stays resident — no disk paging. Test physis_streaming; bench aiverse_physis_streaming_test bench 1024 10.

Tornadoes (2026-11-22) — engine/physis/PhysisTornado.h#

A tornado is simulation, not a visual: a StormEvent (kind Tornado) plus a TornadoTrack on the same entity. Every PHYSIS wind reader already sees the vortex through windWithStormsAt (tangential swirl, radial inflow, updraft): forces, nature contacts / stress (trees fracture), sampleNatureField, the presentation frame. The system physis.tornadoes runs once per tick right after the climate/storm/disaster pass and before forces:

PartRule
Pathdrift (StormEvent driftPerTick), wander (heading + random turn from the track's own RNG state, reflected inside bounds or the PHYSIS grid), waypoints (constant speed, optional loop)
LifestartTick/durationTicks of the storm + rampTicks spin-up/decay; TornadoTrack::intensity 0..1 scales tangential wind, updraft and inflow
Fire (enableDisasters)cells under the core lose fire.suppression of their fire per second (blown out); burning cells with fuel in the ring grow by fire.fanning per second (fanned)
Debrisdebris.perSecond pieces torn up in the core (up to debris.max per tornado), carried by the same wind with quadratic drag + PHYSIS gravity, land on the cell elevation, expire after lifeSeconds or 3 s on the ground. Stored in the TornadoDebrisField resource — no entities, so other modules' entity allocation is unchanged
Carried objectshost entities with Transform + NatureCarriable (mass, area, drag, liftWindSpeed) are lifted when the horizontal wind exceeds the lift speed and carried until they land. Not for Box3D bodies (use applyPhysisToBody)
Damageentities with a Transform within damageRadiusMeters (full in the core, linear to 0 at the radius) get damagePerSecond × intensity through GameModule::environmentDamage(sim, target, amount, tornado); the module applies its own health/armour rules. RTS: pure damage via dealDamage (invulnerable types such as trees and units off the map are skipped). Default implementation: no damage
Vegetationtrees/structures with NatureStressReceiverComponent (forces + nature contacts + stress enabled) load from the vortex wind and fracture through the existing outbox → TerraWeave fall bridge. RTS tree units are invulnerable in the sample rules

Determinism: Fixed-point only, tornadoes and carried objects in entity-index order, debris in creation order, explicit RNG in the track. Persistent + hashed: physis.tornado_track, physis.nature_carriable, physis.tornado_debris (registered only when tornadoes are enabled, so maps without them keep the old save manifest and checksums).

Fire whirls, water and ground (2026-11-22) — engine/physis/PhysisTornadoNature.h#

Every map tornado carries a TornadoNature next to its TornadoTrack (C++: the spawnTornado(world, storm, track, nature) overload, defaults from defaultTornadoNature(tickRate)). A tornado without it keeps exactly the rules above.

PartRule
Fire drawn inEach tick the vortex takes fire.intake (share per second) × intensity × ring weight of the fire of every PHYSIS cell under its core and ring (1 in the core, linear to 0 at the outer radius). The drawn fire (in burning m²) is added to heat, which loses fire.decay per second. fireness = heat / (heat + fire.halfHeat) (0..1): it grows with the amount and strength of the fire, a small fire gives a weak whirl, without fire it fades.
Blow-out vs. fire whirlCore blow-out is fire.suppression × (1 − fireness): a dust tornado still snuffs fire in its core, a fire whirl no longer does. Ring fanning is multiplied by 1 + fireness.
IgnitionEvery fuel cell under the vortex (not over water) catches fire with chance fire.ignite × fireness × intensity × weight per second, strength fire.igniteStrength × fireness. Random numbers come from the tornado's own RNG state (TornadoNature::rng), in grid order.
Embersfire.embersPerSecond × fireness burning embers are thrown from the ring (up to fire.maxEmbers), carried by the vortex wind like debris (TornadoEmberField), burn out after fire.emberLifeSeconds, and set a fuel cell on fire with chance fire.emberIgnite where they land.
Heat damageEntities with a Transform inside the outer radius take fire.heatDamagePerSecond × fireness × intensity (full in the core, linear to 0 at the outer radius) through GameModule::environmentDamage, in addition to the wind damage.
WaterOpen water comes from GameModule::environmentWaterDepth(sim, x, z) (new, default 0; the generic game core returns 2 m for ~ cells and 0.3 m for = fords) or the PHYSIS local flood depth. The vortex is over water when 3 of 5 samples (centre + 4 on the core ring) are deeper than surface.waterThresholdMeters.
Land tornado over waterLoses surface.waterDecay vigor per second, recovers surface.recover on land; at 0 it dissipates (intensity 0, storm disabled). Heat is quenched by fire.quench per second, no ignition, no embers.
Waterspoutsurface: "auto" decides at the first active tick: born over water = waterspout ("water" / "land" force it). Its wind is surface.spoutStrength × the authored wind, it raises spray (presentation) and loses surface.spoutLandDecay vigor per second on land, so it breaks up within seconds ashore.
Ground scourOn land the core (out to 1.5 core radii) removes erosion.rate × intensity² metres per second from GroundScourField cells (physis.scourCellMeters, default 1 m, sparse, at most 65536 cells) down to erosion.maxDepthMeters; the soil (up to erosion.capacityCubicMeters) is carried and dropped (erosion.deposit share per second) in a band 1.5–2.5 core radii around the centre. Over water the carried soil sinks. groundScourAt(world, x, z) gives the change in metres (negative = scoured).

Cross-system ownership (PHYSIS / NEREID / TerraWeave)#

PHYSIS owns climate/weather, natural event fields and environmental force/gravity policies, but never Box3D rigid-body integration itself. NEREID (Water agent, draft PR #23) owns water-body geometry, flow, contacts and buoyancy; TerraWeave (Terra agent, draft PR #24) owns terrain, biomes, vegetation and land rendering. Use the opt-in host integration plan and precise metre/centimetre conversion in physis-nereid-terraweave-integration.md. The existing PHYSIS shallow-flood prototype is not an authoritative replacement for NEREID water. When a host uses NEREID as the water authority, set InstallOptions::floodMode = FloodMode::ExternalAuthority: PHYSIS continues to update fire and quake but clears/skips its local shallow-flood depth. This opt-in switch is authored and covered by tests; cross-module NEREID/Terra integration and real build/CTest verification remain pending.

This is a design contract only. Terra/NEREID integration, rendering and cross-system tests remain NOT IMPLEMENTED / NOT RUN on this branch.

#include "engine/physis/PhysisIntegration.h"
#include "engine/physics/PhysisBox3D.h" // link AIVERSE::physics, if enabled

// During GameModule::setup:
aiverse::physis::InstallOptions options;
options.enableStorms = true;
options.enableForces = true; // only if generic ECS force outputs are required
aiverse::physis::install(sim, options);

aiverse::physis::StormEvent tornado;
tornado.kind = aiverse::physis::StormKind::Tornado;

tornado.eyeRadiusMeters = 20_fx;
tornado.outerRadiusMeters = 150_fx;
tornado.heightMeters = 500_fx;

// Physics owner: after the authoritative PHYSIS tick, just before Box3D Scene::step:
for (aiverse::physics::BodyHandle body : optedInBodies)
    aiverse::physics::applyPhysisToBody(box3dScene, sim.world(), body);
box3dScene.step();

PHYSIS authoritative types are Fixed ECS data. The external Box3D bridge converts from/to Box3D floats only at this boundary. Box3D already applies scene gravity; the adapter applies delta gravity and wind drag via Scene::applyForce, not a second gravity force. Do not also apply ForceResult::totalForce to the same Box3D body. Opt-in kinematic character controllers need a separate locomotion integration; neither hardcoded scalar CharacterParams::gravity nor native Body motion is overridden here.

Physics is opt-in. Run ./run-tests.sh --filter '^physis_' and, with -DAIVERSE_ENABLE_PHYSICS=ON, run CTest physis_box3d and the existing physics_runtime / physics_scene. These tests are authored but NOT RUN. There are no physically accurate Navier–Stokes hurricanes, tornado debris destruction, N-body orbital solvers, Terra foliage wind deform or water surge in the current implementation.

Read-only combined sampling (for Terra, VFX, Physics and tools)#

#include "engine/physis/PhysisPresentation.h"

aiverse::physis::NatureFieldSample nature;
if (aiverse::physis::sampleNatureField(sim.world(), queryPosition, nature)) {
    const auto wind = nature.windVelocity; // 3D Fixed metres per second
    const auto gravity = nature.gravityAcceleration; // m/s squared
    if (nature.hasAtmosphere) {
        const auto rain = nature.environment.rain; // normalized, not water volume
        const auto snow = nature.environment.snowpack;
    }
    if (nature.hasHazards) {
        const auto fire = nature.hazards.fire;
    }
}

sampleNatureField is immutable and returns true when PHYSIS is initialized, including outside the climate grid; hasAtmosphere/hasHazards indicate which grid data is present. It does not depend on TerraWeave/NEREID/Box3D headers. Terra should consume this as a read-only environment overlay and sample NEREID's canonical waterline separately. No production Terra/NEREID adapter or render scene is linked yet.

Stage 23 — opt-in authoritative field reconciliation and command replay#

The new engine/physis/PhysisFieldRuntime.h connects the existing pure PhysisFieldChangePlan with an explicit, rollback-owned ECS field identity registry. Unlike static startup-only installFromMap, this optional path supports replacing a set of authored WindZone, StormEvent and GravityField sources at the Simulation command boundary. It is intentionally generic and has NO dependency on FPS, RTS, Box3D, NEREID, TerraWeave or the editor.

Host integration example (choose a unique command ID in your own module):

constexpr uint16_t kPhysisEdit = 53123;

void MyGame::setup(Simulation& sim, const Json& rules, const Json& map) { if (!physis::installEditableFromMap(sim, map)) return; // PHYSIS absent or disabled }

void MyGame::applyCommand(Simulation& sim, const Command& cmd) { if (cmd.type == kPhysisEdit) { // The authoritative server MUST authorize system player=0. std::string error; (void)physis::applyFieldEditCommand(sim, cmd, kPhysisEdit, &error); return; } // Other genre-independent gameplay commands ... }

// Trusted editor/server-side action; NEVER apply World edits in Scene. uint32_t scheduledTick = 0; std::string error; const bool queued = physis::submitEditableFieldsFromMap( sim, editedMap, kPhysisEdit, scheduledTick, &error);

This queued result only means the command was accepted for submission; the authorizing host can reject it later on expected-revision mismatch. Simulation::submit and CommandSink provide the existing command transport. The host must reserve a command ID, reject spoofed system commands at the network ingress, and implement the applyCommand dispatch above. A client cannot gain authority simply by using Command.player=0.

The runtime registry is a new opt-in persistent World resource named physis.field_runtime (version 1). It contains monotonic edit revision, stable authored ID -> (Entity, kind, canonical serialized fingerprint). A snapshot and native file save therefore retain the same identity and revision; rollback restores both. Unchanged fields retain dynamic runtime state (including a drifting storm); edited fields of the same kind keep the same Entity handle; removed sources are destroyed; type changes cause Remove+Add with a fresh Entity generation. Changes are staged on a copy of World and committed together, so validation/plan failures leave it untouched. A no-op command still consumes one edit revision.

The new optional install enables persistent component schemas for ALL three field kinds so they can be added/retyped while a session is running. This deliberately changes the strict save manifest; it must be enabled on both save and load. Existing installFromMap and saves remain unchanged. No implicit save migration has been implemented.

The edit wire payload is a field-wise binary snapshot with a protocol ID, expected revision, sorted unique sources and a size bound. It packs into the standard Simulation Command.args, so the payload must fit within 4096 total int64 words (up to 32760 bytes, one word reserved for length). Larger replacement sets are rejected; atomic multi-command chunking is NOT implemented. The actual maximum number of fields depends on encoded source properties, not the standalone 2048-field parser limit. Because the full source set is transmitted, edits with obsolete revisions reject rather than overwriting concurrent changes.

Only authored field collections are editable at this stage. Changes to climate grid settings are rejected by submitEditableFieldsFromMap, and changes to the overall flood/disaster policy are NOT hot-reloaded. There is no automatic map Inspector -> active GameModule command registration, network authorization layer or GUI acknowledgement yet; a native host must opt in and use its existing command system explicitly.

Stage 26 — durable admin journal and authenticated loopback endpoint#

PHYSIS remote editing now includes a file-backed write-ahead receipt journal and an opt-in, native loopback-only admin WebSocket listener. The existing FieldRuntimeState / installEditableFromMap / GameModule::applyCommand / applyFieldEditCommand remains the canonical editor authority. The separate RuntimeFieldRegistry / FieldCommandHost path introduced concurrently by other agents is NOT connected to this editor and must not be enabled at the same time.

New generic engine files:

  • engine/physis/PhysisRemoteJournal.h: FileJournal stores a bounded checksummed snapshot of the server's request/receipt cache in an operator-owned private directory. Entries include trusted principal, client instance and request ID, exact original edit bytes, typed authored fingerprints, expected revision, scheduled tick and status. It uses unpredictable exclusive temporary file creation, write flush/ fsync, atomic rename/replacement and POSIX directory sync. A bad checksum or missing permission rejects startup rather than silently dropping history. Only ONE server process may own a journal path.
  • engine/physis/PhysisAdminAuth.h: versioned admin challenge/proof handshake using a new random nonce and keyed BLAKE2b. The shared secret is not sent. Principal string is tied to proof, checked against a host-supplied key lookup, followed by server ACL and reserved PHYSIS command type. Client-supplied player=0 / instance tokens never grant rights.
  • engine/physis/PhysisAdminEndpoint.h: LoopbackAdminEndpoint owns a real net::WsListener listening at 127.0.0.1 ONLY, and admits authenticated connections to the Stage 25 ServerGateway. It requires a nonzero host-reserved PHYSIS command ID, ACL callbacks and a private journal file. LoopbackAdminConnector can authenticate a native editor connecting over local ws://127.0.0.1. The PHYSIS window uses its EditorLink bridge to poll this connection and show pending/status.
  • apps/editor/PhysisRemoteEdit.h: EditorLink::connectLocalAdmin accepts host-supplied principal, secret from secure storage, nonzero instance ID, assigned slot and command type. It does not auto-generate secrets, open anonymous network connections or grant admin rights.

Example native setup: aiverse::physis::remote::admin::LoopbackAdminEndpoint endpoint( privateJournalFile); endpoint.open(localPort, reservedFieldCommandType, serverKeyLookup, canRead, canWrite, &error); // Restore matching Simulation checkpoint BEFORE opening endpoint. // In host event loop: endpoint.poll(sim, monotonicMs); sim.step(); endpoint.afterTick(sim);

Credential lookup, key rotation and ACL are host-owned. The admin port is never allowed to bind publicly from this API. IMPORTANT: the current native AIVERSE WebSocket client supports ws:// but NOT wss://; this handshake alone is not transport encryption. For off-machine admin access, use an already encrypted authenticated tunnel to local loopback or implement real native TLS/WSS. Never expose plain remote ws:// and call it secure.

Crash recovery:

  1. Persist the original edit intent BEFORE scheduling the Simulation command. A failed journal write prevents any new admission.
  2. Persist Queued and later Applied/Rejected/Conflict receipts. Restored Unknown intents may be reconciled against saved ECS revision+fingerprints; same original packet can be re-admitted only after ACL and revision checks. Duplicated packet IDs cannot apply twice.
  3. On restart, restore the matching Simulation World/checkpoint and pending command state first, then attach the file journal, and only then accept authenticated admin connections.
  4. The journal and the Simulation checkpoint are two separate stores, not a single atomic DB transaction. A power failure between writing them can leave an ambiguous outcome. Receipt recovery must report Unknown/Conflict rather than inventing Applied. This is more robust than Stage 25's volatile-only receipt cache, but it is not a blanket guarantee of crash-atomic exactly-once acknowledgment.

Stage 26 crash-recovery correction — persisted Queued != pending command#

During Stage 26 hardening, ServerGateway::restoreJournal was changed to restore every persisted Queued receipt as Unknown and clear the old scheduledTick. The previous server's in-memory Simulation command queue may have vanished on restart, even when the sidecar journal still says Queued. A loaded Queued receipt is not proof of execution.

After the host restores its matching ECS World/checkpoint, observe() reconciles Unknown against FieldRuntimeState and authored fingerprints. If already committed, the request is Applied. If revision advanced incompatibly, it is Conflict. If unchanged, keep Unknown; the EXACT original authenticated Submit can be re-admitted with the same ID after ACL and revision checks. No new PHYSIS permission or public listener is created by this fix.

New source fixtures in physis_admin_journal test both crash before the queued command executes and crash after its ECS effect but before the Applied sidecar flush. These tests are AUTHORED, NOT RUN. The journal and Simulation save remain separate durability domains: this is safe resubmission/reconciliation, NOT full cross-file crash-atomic exactly-once commit.

Stage 64 — ignore stale remote ACK after Apply#

RemoteClient enforces monotonic receipt handling on an active connection: an accepted terminal receipt cannot be overwritten by late Queued/Unknown/etc. When an Applied operation is checked after reconnect, a Query for the original ID must actually be sent before accepting its reply; a pre-query response and stale Queued are ignored. An Unknown during Applied verification is Uncertain: never automatically replay a formerly acknowledged Submit. Manual retry() after a verification timeout is a Query-only operation, and begin() rejects uncertain/in-progress verification.

No wire format, ECS schema, NEREID Water, TerraWeave or Box3D changes. V1 has no per-Query correlation nonce, so arrival after a Query is not cryptographic proof that a delayed Applied packet was generated for that Query. A future protocol version should add correlation and server generation. Source fixtures are authored, but native engine CTest has NOT RUN. See docs/agent-handoffs/physis-stage64-monotonic-ack-2026-11-19.md.
