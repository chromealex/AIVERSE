TerraWeave — procedural terrain, biomes and vegetation (AIVERSE)#

Status (2026-11-19): Core + Arbor/Flora, Horizon HLOD, async forest/terrain scene adapters, authored near/far Q16 stitching and Stage 22 diagnostics implemented in source. GPU, editor, integration and performance verification remain pending; see the Draft PR and handoff for exact test status. Implementation: engine/world/TerraWeave.h. Test: tests/terraweave_test.cpp. Handoff: docs/terrain/AGENT_HANDOFF.md.

Relationship to existing terrain#

AIVERSE already has chunked RTS heightfield rendering, editor sculpt/paint operations, MapGrid heightfield simulation, modules/rts/gen/GenNoise.* and water/roads. Do not duplicate or replace these. TerraWeave supplies genre-independent, pure CPU world-generation outputs. Genre adapters consume them without changing legacy project, save, replay or networking contracts.

The existing RTS terrain uses map corners in 1/16 map units; TerraWeave uses integer world centimetres. The adapter must explicitly convert units and coordinate handedness/axis orientation, then update dirty chunks through the existing surface API. Never silently cast centimetres into old map units.

Phase 1 API#

Namespace: aiverse::terraweave.

  • heightAtCm(TerrainSettings, worldXcm, worldZcm) -> int32_t: signed terrain elevation in cm.
  • climateAt(TerrainSettings, BiomeSettings, xCm, zCm) -> ClimateSample: temperature, humidity in [0,1000], and one categorical Biome.
  • generateChunk(TerrainSettings, BiomeSettings, ChunkKey, resolution, spacingCm) returns TerrainChunk with (resolution+1)^2 signed heights and biome ids. Coordinates are absolute; adjacent chunk borders are identical.
  • scatter(TerrainSettings, BiomeSettings, ScatterSettings, RectCm worldBounds, vector<FoliageSpecies>, vector<RectCm> exclusions) returns stable sorted row-major foliage instances. Prototype ids are uint32 and unique within the invocation. Candidate selection is anchored to a global lattice; chunk partitioning and prototype order cannot change the result.
  • slopePermilleAt estimates local max-axis slope from signed height differences.
  • TerrainChunkComponent, VegetationPatchComponent are small ECS-ready descriptors; these are not yet registered into an ECS scheduler.
  • FoliageInstance::key is the stable hash of global lattice coordinates and scatter seed. Persist removals/harvests by key and world-generation revision, not by GPU buffer index.

Sample (C++20; no renderer or RTS dependency):

#include "engine/world/TerraWeave.h"
using namespace aiverse::terraweave;

TerrainSettings terrain;
BiomeSettings climate;
auto tile = generateChunk(terrain, climate, {0, 0}, 32, 100);
FoliageSpecies oak;
oak.id = 1001;
oak.biomeMask = biomeBit(Biome::Forest) | biomeBit(Biome::Grassland);
auto trees = scatter(terrain, climate, {}, {0, 0, 3200, 3200},
                     {oak}, {{1000, 1000, 1600, 1600}}); // building exclusion

Determinism and threading#

All phase 1 outputs are integer-only, seeded and independent of call order. No rand(), platform time, global mutable state, or float. Helpers use stable 64-bit mixing and signed floor-division for negative world coordinates. Pure generators can be called concurrently. The host job system schedules them; the ECS main-thread/guarded commit order must remain deterministic. CPU outputs are authoritative; GPU placement or rendering must not affect gameplay RNG or collision. Changes to generator parameters, coordinate transforms or hashing are world-format version changes, requiring migration or explicit revision.

Use one ECS entity per terrain/vegetation patch or interactive tree, not per grass blade. Render-only millions of blades belong in instance buffers. Decorative foliage may not have gameplay state. Harvestable foliage must have a stable removal record, replicated and hashed by the game's simulation owner.

Algorithm / limitations#

  • Height: 2D multi-octave signed value noise (Q16) in integer centimetres. No erosion, caves, stamps or mesh triangulation yet.
  • Biomes: deterministic temperature/moisture samples with simple threshold classification, including Ocean/Tundra/Desert/Grassland/Forest/Wetland/Alpine. Not yet physical climate simulation or biome blend weights.
  • Scatter: jittered one-candidate-per-world-lattice-cell placement; deterministic density/weighted species selection, biomes, height, slope, world-space rectangular exclusions and scale/yaw variance. It is not exact Bridson Poisson-disk, nor does it currently guarantee separation of full tree crowns.
  • Limits: nonempty region up to 1,000,000 lattice cells per scatter call, max 1024 terrain quads per tile. Do not feed untrusted arbitrary 64-bit coordinates; future validation should enforce a supported world extent.
  • No automatic spawn into ECS, GPU buffers, RHI draws, editor UI, road/water subscriptions, tree meshing, streaming residency, erosion, virtual textures, physics collisions, terrain navmesh updates or season/wind simulation yet. These are future phases, not features of the phase 1 header.

Integrating a scene#

  1. A world config selects TerraWeave seed/settings and an explicit generator version.
  2. Visible-world streaming chooses chunk keys; workers call pure generateChunk.
  3. An adapter maps centimetres to the existing heightfield MapGrid/editor document or to a generic terrain mesh; changes go through the existing dirty-chunk pipeline, never a second competing terrain renderer.
  4. Query roads, buildings, waterways and designer overrides as exclusion/stamp sources before scattering.
  5. scatter returns instance descriptors for prototype render groups; only interactable objects become separate ECS entities.
  6. All rendering uploads and GPU work go through gfx::Device, using GLSL+MSL parity and quality tiers; no direct graphics backend calls in generation.

Stage 2a: Arbor procedural tree geometry#

Added engine/world/TerraWeaveArbor.h (integer-authoritative tree skeleton) and engine/world/TerraWeaveArborMesh.h (render-only CPU tessellation). This is independent of any genre, and a native C++ module can include it.

#include "engine/world/TerraWeaveArborMesh.h"
using namespace aiverse::terraweave;

TreeProfile oak;
oak.speciesId = 1001;
oak.shape = CrownShape::Broadleaf;
oak.primaryBranches = 22;
const TreeSkeleton skeleton = generateTree(oak, instance.key, TreeLOD::High);
const ArborMesh renderGeometry = buildArborMesh(skeleton, {6, true});
// Upload through gfx::Device (not implemented in this stage).

TreeProfile defines tree height range, trunk radius, crown start, primary branches, branch reach/rise, leaf-cluster radius and broadleaf/conifer/columnar shape. Tree seed is derived from stable foliage instance key + species ID; the same inputs yield the same integer local-space structure regardless of worker thread or scene partition. TreeLOD High/Medium/Low reduce branch counts and leaf clusters. Impostor returns bounds only; actual billboard atlas baking is not implemented.

TreeSkeleton contains a root trunk, child branch segments with parent indices, leaf clusters and conservative height/crown radius bounds. buildArborMesh converts branches to cylindrical bark tubes and clusters to crossed alpha-card quads with UVs, normals and a bark/leaf material discriminator. The returned mesh uses float only for presentation, not gameplay state. Meshes have no tangents or GPU material binding yet. The first visual pass is simple card foliage, not photorealistic SpeedTree-equivalent geometry.

The mesh is local-space in centimetres. Instance translation, rotation and scale are supplied by FoliageInstance externally. If gameplay needs tree collision/hitboxes, derive deterministic proxies from TreeSkeleton, not from float render vertices. View LOD selection and GPU uploads must live in a renderer adapter and not in lockstep ECS simulation.

Test source: tests/terraweave_arbor_test.cpp. CTest name: terraweave_arbor. Check seeded determinism, all crown archetypes, branch parent validity, LOD topology, independent parallel evaluation, render geometry index validity, and invalid profiles. Compilation/CTest results are tracked in docs/terrain/AGENT_HANDOFF.md.

for (const FloraBatch& batch : batches) {
    // Resolve species prototype + TreeLOD, pack instance transforms.
    // Upload/submit via gfx::Device in a future renderer adapter.
}

FloraView selects radial ranges for High/Medium/Low/Impostor mesh tiers, a hard culling radius, and stable seeded far-density thinning. FloraBatch groups copies of FoliageInstance by (speciesId, lod). Ordering is canonical regardless of worker/chunk completion order, and overlapping identical placements are deduplicated within the resulting group. This is draw-list preparation only, not GPU instancing/culling/indirect drawing, frustum/Hi-Z occlusion or crossfade. Screen-space LOD, camera-frustum culling and distance-field shadows remain future stages.

World extent validation (Stage 2c)#

Core generator explicitly supports world positions [-1,000,000,000, +1,000,000,000] centimetres on X/Z. heightAtCm, generateChunk, slopePermilleAt and scatter validate inputs before coordinate multiplication/offset sampling. Chunk keys that would leave this world box are rejected, as are scatter bounds that fall within the 100-cm boundary margin required by slope sampling. This is intended to fail cleanly on malformed/extreme world coordinates, not to impose a practical memory-residency or render-distance budget.

Do not remove these guards when introducing a streamed world. Large-world support additionally needs camera-relative rendering, origin rebasing and bounded chunk residency, which are not yet implemented.

Stage 2d: standard AIVERSE render::Model adapter#

engine/render/TerraWeaveModelAdapter.h is a thin render-only adapter into the pre-existing render::Model and its prepareModelUpload / uploadModel(gfx::Device&, Model&) path:

#include "engine/render/TerraWeaveModelAdapter.h"
auto tree = aiverse::terraweave::makeArborModel(profile, instance.key);
// On the render-owning thread:
aiverse::render::prepareModelUpload(*tree);
aiverse::render::uploadModel(device, *tree);

The adapter builds explicit High/Medium/Low mesh variants in a single render::Model, with mesh-0 LOD switches at 128 and 32 projected pixels. It uses standard render::ModelVertex, Primitive, Material, Node and Model::finalize(); positions convert from integer cm to floating-point metres. Existing model renderer infrastructure owns the shaders, LOD fade, frustum culling, backend upload and instanced draws.

The default bark and leaf materials have simple untextured PBR colours. Leaf cards are opaque rectangles until a caller binds a real alpha-cutout foliage texture and sets AlphaMode::Mask; do not misrepresent this as production-quality foliage. Billboard atlas generation, material/texture registry, wind deformation and actual scene draw submission remain unfinished.

tests/terraweave_model_test.cpp checks three LOD meshes, range/index correctness, bounds, and stable topology. It links aiverse_models; the target aiverse_terraweave_model_test and CTest terraweave_model are registered in CMake. All four TerraWeave test targets explicitly undefine NDEBUG on GCC/Clang so their assertions execute in Release builds.

Important: using makeArborModel per individual tree is not the final scalable forest strategy. Generate a bounded catalogue of species/variant prototypes and reuse meshes across instance transforms. buildFloraBatches already groups placement data; the next renderer adapter must submit these groups through existing model instancing.

Stage 2f: baking TerraWeave into existing editor MapDoc heightfields#

engine/world/TerraWeaveHeightmap.h provides a pure generateLegacyCorners(TerrainSettings, widthCells, heightCells, LegacyHeightfieldOptions) adapter. Inputs use centimetres; output is the existing MapData signed-int16 corner format, 1/16 map metre per sample. Coordinates and output ranges are validated; overflow/saturation throws instead of corrupting map heights. Offset/spacing can be configured.

apps/editor/core/TerraWeaveMapAdapter.h provides:

#include "apps/editor/core/TerraWeaveMapAdapter.h"
aiverse::editor::bakeTerraWeaveTerrain(
    mapDoc, terrainSettings, {0, 0, 100});
// For intentional regeneration replacing authored corner data:
aiverse::editor::bakeTerraWeaveTerrain(
    mapDoc, terrainSettings, {0, 0, 100},
    aiverse::editor::TerraWeaveExistingTerrain::ReplaceExplicitly);

The editor adapter writes through MapDoc::beginEdit() and MapDoc::touched() after constructing all generated heights, preserving undo and the existing view-revision notification. It never silently overwrites manual sculpting, never changes rules.terrain.model, and rejects planet maps (separate cube-sphere adapter needed). This is one-shot baking API, not yet an editor button, regeneration graph, streaming terrain or painted override stack.

Source test: tests/terraweave_heightmap_test.cpp (CTest terraweave_heightmap) verifies signed heights, seam continuity, legacy overflow rejection and invalid inputs. The inline MapDoc helper is not yet exercised end-to-end in a running editor.

Stage 2f — shared forest model submission adapter (CPU / RHI bridge)#

engine/render/TerraWeaveForestAdapter.h exposes aiverse::terraweave::ArborForestAdapter. It bridges deterministic FloraBatch instances to the existing render::Renderer3D::drawModel path. It does not own or replace Renderer3D, ECS, streaming or shaders.

  • addPrototype(TreeProfile, meshSeed, ArborMeshSettings) builds one render::Model per species. Duplicate/zero species IDs are rejected. Changing the tree's mesh on every instance defeats batching; only transform, yaw and scale vary by FoliageInstance. All nodes use existing model projected-size LODs.
  • prototype(speciesId) gives the stable shared model pointer, valid while the adapter lives. uploadModels(gfx::Device&) and releaseModels(gfx::Device&) MUST run on the GPU-owning render thread. Release GPU resources before destroying the device or the adapter.
  • forEachDraw(batches, ForestRenderOriginCm, callback) is a GPU-free inspection/submission primitive, and submit(Renderer3D&, batches, origin) forwards directly to Renderer3D::drawModel. Call submit between beginScene and render, only after model upload.
  • ForestRenderOriginCm is signed world centimetres, with fields x,y,z. For X/Z, subtract origin using int64 BEFORE float metre conversion, to preserve precision in large worlds. Camera and renderer must use the same rebased coordinate frame; model draw transforms are metres.
  • ModelDraw::persistentId is a namespaced stable hash of FoliageInstance::key and species, independent of the draw index. Draw flags are kDrawStatic. An Impostor Flora batch now selects a separate camera-facing alpha-mask tree billboard model (one quad and one procedural RGBA silhouette), not the lowest geometry mesh. This is a single-view silhouette, not a multi-angle atlas.

Minimal native / host render integration sketch:

#include "engine/render/TerraWeaveForestAdapter.h"
using namespace aiverse::terraweave;

ArborForestAdapter forest;
TreeProfile pine;
pine.speciesId = 21;
pine.shape = CrownShape::Conifer;
forest.addPrototype(pine, 0x5678);           // CPU / setup stage
forest.uploadModels(device);                 // render thread, check bool
auto batches = buildFloraBatches(placements, view);
renderer.beginScene(camera, width, height);
forest.submit(renderer, batches, {originXcm, originYcm, originZcm});
// ... other scene draws and renderer.render(pass)
forest.releaseModels(device);                // render thread at shutdown

The adapter does not register with WorldScene or the editor yet. It does not provide per-tree geometry variation, guaranteed indirect draw counts, actual impostors, material cutout textures, scene screenshots, GPU validation, or an opt-in manifest format. Existing projects remain untouched. Validation is added to tests/terraweave_model_test.cpp; see AGENT_HANDOFF.md for observed test results and next task.

Hierarchical BranchLOD — independent tree parts (Stage 2g)#

The new engine/world/TerraWeaveBranchLod.h and makeArborBranchLodModel(profile, seed, BranchLodSettings) in engine/render/TerraWeaveModelAdapter.h build a reusable native render::Model containing one render node per tree branch. Each node retains TreeBranch::parent and has its own three MeshDef variants. Renderer3D already chooses a node's LOD by its projected size using its existing selectModelLod path, considering camera and shadow views. This allows, e.g., a large near-side trunk to remain fully detailed while individual smaller background branches switch to their cheapest shape. There is no whole-tree mesh switch for these three geometric tiers.

Per-branch geometry levels:

  • BranchDetail::Full: full radial bark mesh, local foliage clusters with crossed leaf cards.
  • BranchDetail::Reduced: about half the bark radial segments, one distal local foliage cluster, crossed cards.
  • BranchDetail::Minimal: three bark radial sides, one distal cluster represented by one card plane.
  • BranchLodSettings::reducedPixels (default 96) and minimalPixels (default 30) set independent projected screen-diameter thresholds. The renderer's own LOD fade settings control transition blending.

LeafCluster::parentBranch is the original high-detail structural branch index (new metadata). It is used by buildArborBranchMesh(tree, branchIndex, BranchDetail, ArborMeshSettings). No branch is dropped, and tree skeleton generation/gameplay remains deterministic; branch geometry and resolution choices are presentation only. A single prototype is shared by all instances of a species; do not create a distinct render::Model for each tree. Tree silhouette geometry still uses the existing opaque leaf material if no project alpha-cutout texture is assigned.

Merged whole-tree LOD (draw-call merging)#

makeArborTreeLodModel(profile, seed, TreeLodSettings) builds the same branch geometry as BranchLOD, but merges every branch of a detail tier into ONE mesh: one node, three MeshDefs (Full -> Reduced -> Minimal via MeshDef::lods), each with exactly two primitives (bark, foliage). All trees of one species share these primitives, so Renderer3D instancing draws a whole species tier with one draw per material (per instance-limit chunk) instead of one draw per branch node. vertexOwners keep the structural branch per vertex, so GPU hierarchical wind masks (docs/wind-masks.md) still bend each branch.

The tier comes from Terra's own FloraView distance ranges: ArborForestAdapter sets ModelDraw::lodLevel (High=Full, Medium=Reduced, Low=Minimal; Impostor stays the atlas card). ModelDraw::lodLevel is a general renderer feature: a host-chosen level of every node's LOD chain, skipping projected-size selection. The renderer's projected-size metric is conservative (nearest box corner, divided by w*(w-size)) and kept whole 20 m trees at Full inside the near range.

ArborForestAdapter::setTreeGeometry(ArborTreeGeometry, TreeLodSettings) (before the first addPrototype): PerBranch = classic BranchLOD (needed for CPU per-branch wind poses), Merged, or Auto (default): Merged when enableHierarchicalWind() is on, else PerBranch. ForestSceneSettings::treeGeometry / manifest world.terraweaveForest.treeGeometry: "auto" | "merged" | "perBranch".

Renderer fixes found on the way (Renderer3DModels.cpp):

  • LOD selection no longer adds the vertex-offset (wind) culling margin to the projected size. With wind on, a 2 m branch plus a multi-metre margin pinned every node at LOD0, so BranchLOD never switched.
  • Rigged trees in calm air declare a 1 cm maxVertexOffsetMetres. Zero means "unbounded displacement" and turned off culling and LOD.

Far impostors baked from the near tree#

bakeArborImpostorFromModel(atlas, nearModel) re-bakes the azimuth atlas by CPU rasterization of the near tree itself (every node's base mesh, with the material base-colour textures and alpha cutout), 2x2 supersampled, simple wrap lighting, colour bled into transparent texels against mip halos. Bark and foliage keep separate pages (winter bark-only still works). The card is resized to the mesh's real extent. ArborForestAdapter does this by default right after the prototype decorator (textures) and before GPU upload; setImpostorFromNearModel(false) keeps the legacy skeleton disk/line silhouette. Deterministic: the same model gives the same bytes.

Whole-tree final billboard (Stage 2h)#

engine/render/TerraWeaveArborBillboard.h provides makeArborBillboardModel(TreeProfile, seed, ArborBillboardSettings). It projects the procedural bark/leaf silhouette to an RGBA8 image (default 128x256), creates a full-tree XY quad, and assigns the image to a standard render::Material with AlphaMode::Mask. Transparent pixels are genuine alpha holes, not a green rectangle; no new GLSL, MSL or custom rendering backend is required.

ArborForestAdapter now caches two models per species: a hierarchical near model via prototype(speciesId), and a full-tree far quad via billboardPrototype(speciesId). uploadModels(device) and releaseModels(device) manage both through the engine's existing GPU model uploader. forEachDraw selects the billboard model only for FloraBatch::lod == TreeLOD::Impostor, while near/medium/low batches use the per-branch LOD chain. The far quad's rotation faces the horizontal camera direction; the native submit path reads Renderer3D::cameraPos(). For CPU draw-list tests / custom callers, pass ForestCameraCm to the optional fourth argument of forEachDraw(batches, origin, callback, camera). Billboard and near representations retain the same stable instance ID.

The billboard image is intentionally a single-view, deterministic silhouette, not yet a high-quality baked 8/16-view albedo+normal/depth impostor atlas. Near-to-far switching presently follows FloraView distance buckets and has no whole-tree temporal crossfade; the per-branch transitions are handled independently by Renderer3D. The billboard currently disables cast shadows to avoid fake flat shadows. Test screen-space pop, alpha halo/mipmaps and multi-angle visual quality on actual GPUs before claiming production readiness.

Tests added but not confirmed executed: tests/terraweave_model_test.cpp now verifies branch counts, parent graph, three independent geometry tiers, index bounds, deterministic mesh and silhouette image, material cutout, transparent/bark/leaf pixels, model switching, camera orientation and stable identity. Isolated CI contains this target. See docs/terrain/AGENT_HANDOFF.md for commands and exact verification status.

Stage 3a — editor and MCP integration (opt-in heightfield baking)#

The legacy RTS TerrainWindow now has a TerraWeave section with seed, average height, relief, noise period and octaves. It exposes two actions using the same Workspace::call operations as agents:

  • terraweave_preview: returns an integer-cm 9×9 height sample grid plus minCm and maxCm; does not edit the map.
  • terraweave_generate: explicitly bakes a full heightfield into the existing MapDoc::corners, creates an undo snapshot, calls MapDoc::touched(), queues a Change::Map invalidation and writes sanitized generator metadata into map.extra.terraweave (version 1).

Both operations are registered in apps/editor/core/TerraWeaveOps.h via registerTerrainOps and are reachable through the existing editor/MCP registry. Example:

{
  "seed": 42,
  "baseHeightCm": 0,
  "reliefCm": 5000,
  "basePeriodCm": 6400,
  "octaves": 5,
  "originXcm": 0,
  "originZcm": 0,
  "cellSizeCm": 100,
  "overwrite": false
}

Safety/compatibility: Without explicit overwrite: true, the adapter refuses to replace either an existing corner heightfield or an authored detail surface. With explicit replacement, the previous detail layer (including splat/file/scale) is cleared after recording the undo snapshot so it cannot mask the new corners in the renderer. Planet and FPS maps are rejected by this legacy MapDoc adapter; TerraWeave's generic C++ world generator and ForestAdapter still work independently of genre. The operation does not silently change rules.terrain.model; game authors choose whether corners influence simulation. No project changes occur until the user calls Generate.

Limitations: preview is a 9×9 numeric sample, not a live 3D preview. Generation is a one-shot bake, not procedural streaming, a persistent non-destructive graph or a paintable biome editor. The terraweave map block records generator inputs but is not yet automatically re-evaluated on load.

Testing: tests/terraweave_ops_test.cpp checks param defaults, bounds rejection, versioned metadata and deterministic preview. The test does not construct a live Workspace or render screenshots; an end-to-end editor/GUI/MCP regression remains mandatory.

Stage 3b — multi-azimuth Arbor impostor atlas#

engine/render/TerraWeaveImpostorAtlas.h adds ArborImpostorAtlasSettings, ArborImpostorAtlas, makeArborImpostorAtlas(profile, seed, settings) and selectArborImpostorAzimuth(instanceYawMilliDegrees, treeXcm, treeZcm, cameraXcm, cameraZcm, views).

The CPU baker uses one deterministic tree skeleton to render 4, 8 (default) or 16 azimuth silhouettes into one RGBA8 horizontal atlas (default 8 × 128 × 256). One render::Model and one atlas image are reused across all trees of a species. Each of the views std::vector<render::Material> overrides references the same baseTex but has a different uvOffset/uvScale with a half-texel inset. Renderer3D already handles those overrides via render::ModelDraw::materials; no new shader or GPU API is added.

ArborForestAdapter now caches near BranchLOD geometry, a far atlas model and per-view material overrides per species. billboardAzimuthCount(speciesId) returns the atlas view count. forEachDraw(..., ForestCameraCm) selects the nearest tree-local azimuth (camera world heading minus each instance's own yaw), and submit(renderer, ...) uses the real renderer camera position. Storage for the material override vectors must outlive the frame until Renderer3D::render() returns. The billboard is camera-facing but depicts the corresponding view of the tree, avoiding a fixed flat silhouette during orbit.

The older single-view makeArborBillboardModel API remains intact. The new atlas is silhouette/albedo only: no depth, normal or parallax impostor, no interpolation between adjacent views, and no whole-tree temporal alpha transition. The source assertions have been updated for later execution; CMake/CTest and GPU verification have not been run by request.

Stage 3c — stable spatial transition to impostor#

FloraView::impostorBlendWidthCm (default 0, preserving legacy hard-ring selection) spreads the TreeLOD::Low → TreeLOD::Impostor threshold over a bounded interval around FloraView::lowRangeCm. Each FoliageInstance selects a stable threshold based on its persistent key and species ID. The same tree does not flicker when camera position changes within the band, and all trees no longer swap on one circular boundary. The interval is validated to stay between mediumRangeCm and cullRangeCm.

Example: view.lowRangeCm = 18000; view.impostorBlendWidthCm = 4000; distributes transitions over 160–200 metres. Because thresholds are stable, this is population dithering, not a true per-object temporal or alpha crossfade. No additional draw calls or extra transparent meshes are required. tests/terraweave_flora_test.cpp has deferred assertions; test execution is intentionally postponed.

Stage 3d — opt-in streaming forest host and WorldScene manifest#

engine/world/TerraWeaveForestScene.h introduces the reusable, genre-independent native C++ TerraWeaveForestScene and ForestSceneSettings. The scene owns:

  • per-species shared near BranchLOD and far impostor atlas prototypes through ArborForestAdapter;
  • integer-centimetre, globally keyed foliage placements and stable IDs;
  • an explicitly bounded maxResidentChunks patch cache;
  • streamAt(ForestCameraCm): generate nearest resident chunks and release patches outside the current budget/radius;
  • setExclusions(vector<RectCm>): regenerate for road/building/clearing rectangles, with cache revision invalidation;
  • visibleBatches(): per-view Flora LOD/culling, including staggered impostor transition; uploadModels(gfx::Device&), submit(Renderer3D&, ForestRenderOriginCm) and releaseModels(gfx::Device&) for the existing RHI lifecycle;
  • stats(): number of resident chunks, placements, prototypes and generation revision (not actual GPU draw counters).

Native projects can instantiate it independently of an RTS/FPS module. addSpecies(TreeProfile, FoliageSpecies, prototypeSeed) must be called before streaming/upload. streamAt is currently synchronous CPU generation, bounded by the cache limits and current scatter settings. Do not invoke it concurrently with submit, setExclusions or releaseModels. Worker-stage streaming, cancellation and generation revision commit validation are future work.

Stage 5 — authored terrain and placement providers for generic forests#

Stage 6 — actual WorldScene terrain heights and footprint placement#

The opt-in WorldScene path now uses a typed, immutable bridge from loaded world::ChunkCollision::terrain to TerraWeave forest placement. engine/world/TerraWeaveWorldHeightSource.h contains AuthoredHeightTileCm and AuthoredWorldHeightSnapshot. The snapshot's sample(worldXcm, worldZcm) returns an optional signed centimetre elevation from loaded terrain tiles. It uses WorldAssets::cellSize and negative-safe global floor division, then piecewise triangular interpolation matching the exact readChunkCollision triangles (a,c,b) / (a,d,c), not bilinear smoothing across the diagonal. Source height samples are converted from world::Fixed metres to integer centimetres at the worker preparation boundary. The difference from the underlying Fixed collision surface is at most centimetre-scale sampling/rounding, and the operation is presentation-only.

WorldScene::Prepared caches authored height samples and collision box footprints only when terraweaveForest was explicitly enabled. On terrain/footprint-bearing chunk publish or unload, WorldScene::update assembles one immutable snapshot from all resident tiles, plus an exclusion mask from resident collision-box X/Z footprints. It calls the new TerraWeaveForestScene::setLandscapeSources(heightSource, mask) exactly once per update: one generation revision invalidation, with old snapshots safely held by any in-flight asynchronous work. The forest's own revision-safe async publisher discards stale results.

For areas with no currently loaded authored height tile, the adapter falls back to TerraWeave's configured deterministic heightAtCm. This can create a seam between authored and procedural terrain when loading/unloading tiles; it is not a full world terrain replacement or a solution for arbitrary physics triangle meshes. The footprint mask conservatively excludes the X/Z projections of all resident collision boxes, regardless of altitude. WorldSpace kWorldLimitCm checks and explicit chunk CPU reservation accounting remain in effect. Legacy scenes without terraweaveForest keep the original code path and do not allocate these snapshots.

FoliageExclusionMask now buckets building rectangles into 64 m spatial buckets for per-candidate checks. Large rectangles (>256 buckets) use a bounded per-shape overflow path rather than being duplicated across tens of thousands of buckets. Road and polygon queries preserve their prior behaviour.

TerraWeave Horizon — kilometre-scale landscape and forest HLOD#

engine/world/TerraWeaveHorizon.h generates a coarse forest landscape snapshot without expanding distant trees to individual objects. engine/render/TerraWeaveHorizonModel.h packs the entire snapshot into one standard AIVERSE render::Model with two materials/primitives: (1) a very low resolution far-terrain heightfield, with biome vertex colours and slope normals, and (2) hundreds of cluster-level crossed billboards sharing one RGBA8 silhouette atlas. Renderer3D therefore does not submit one draw per tree, nor one draw per 128/512-metre forest cluster. Shadow casting is disabled on far impostors.

Unlike near tree LODs, the cluster silhouettes are generated directly from low-frequency climate/heightfield samples; individual trees are never generated at this tier. This makes the cost bounded by the terrain grid and number of cluster tiles, not the number of simulated or visually implied trees.

Default range hierarchy#

The ranges are adjustable through HorizonSettings. The nearest range is coordinated with ForestSceneSettings.view.cullRangeCm (default 240 m) to avoid duplicate detailed trees. The single large proxy is not a substitute for collision, walkable ground, pathfinding, close-up rocks or detailed tree meshes.

Approximate upper bounds, not measured GPU performance#

Default estimateHorizonBudget(HorizonSettings{}):

  • 832 possible forest cluster slots in total (16×16 middle + 24×24 distant).
  • One 1392×1392 RGBA8 texture, 7,750,656 bytes before mipmaps.
  • At most 9,253 vertices and 8,320 triangles (including outer skirts and two crossed quads per forest cluster; many clusters skipped in sparse biomes).
  • One Model with at most two material primitives. Actual main-pass draw count varies by renderer/backends/visibility; shadows, reflections, render passes and hardware have not been benchmarked.

This is much cheaper geometrically than distant individual foliage but not literally free: alpha overdraw, one-time CPU bake, texture upload, memory and shadow/atmospheric composition still cost resources.

Known limitations and next work#

  • Cluster textures are procedural silhouette/colour approximations, not full multiview photographic or normal/depth-accurate atlases.   • Far terrain is a coarse mesh with a central hole (to avoid z-fight with nearby authored geometry), not a depth-aware mountain panorama. It must be disabled or coordinated with independently authored far-terrain patches to prevent overlap/double rendering.
  • Rebuilding the atlas when the camera crosses a 128m cell runs on the existing background worker but is still CPU work; pack/cache prebaked assets for entirely static game worlds and profile the upload latency. The renderer and WorldScene still need screenshots and actual GPU measurements.

Stage 8 — layered cluster crowns, stable transition bands and atlas quality tiers#

TerraWeaveHorizon.h now rasterizes a cluster as a deterministic overlapping canopy instead of a row of vertical green strips. Each texture tile contains hashed broadleaf ellipses, occasional tapered conifer crowns, variable heights/colours, gentle alpha-test edge coverage and sparse exposed trunks. This is intentionally a stylized procedural approximation of a forest silhouette, not a render of real 3D foliage assets. The GPU still sees the same two crossed cluster cards and one shared atlas.

HorizonSettings has these optional quality and LOD properties:

C++ / JSON fieldDefaultPurpose

orientationViews11: use the same atlas frame for both crossed cards; 2: bake separate X/Z projections
nearBlendCm6000 (60m)Spread spatial HLOD entrance into the final 60m of detailed forest
tierBlendCm16000 (160m)Stagger 128m→512m cluster coverage around the 1km boundary

The band logic uses deterministic spatial stochastic alpha masking. A cluster's canopy coverage ramps in/out through hashed pixel thresholds based on distance to the snapped bake camera. The near-to-mid layer starts partially visible before individual trees stop, and mid/far clusters overlap at reduced coverage rather than switching all cards at once. This has no additional per-cluster draw calls or new GL/Metal shader. It is not a continuous per-frame alpha crossfade: the atlas is still recomputed only when the background Horizon region is updated. Camera movement across a region boundary may cause residual small pops; only actual orbit/zoom screenshot tests can establish perceived continuity.

When both opt-in terraweaveForest and terraweaveHorizon blocks exist, the default closeForestEndCm is inherited from the detailed forest's FloraView::cullRangeCm unless explicitly overridden. This avoids the former 240m vs 250m gap in the default near/far ownership. If Horizon is used alone, it retains its 250m close boundary. Existing scenes with no Horizon block do not change.

orientationViews=2 stores independent azimuth-orthogonal projections of each cluster and uses a different UV subrectangle for the corresponding crossed card. It still uses one shared image and one model with two primitives, exactly the same card geometry and draw submission topology. High-quality mode costs more atlas memory/CPU bake work, but not more triangles. orientationViews=1 remains the mobile/low-memory default.

Stage 9a — authored landscape inputs for Horizon#

bakeHorizon(..., const HorizonSurfaceSources* source = nullptr) now accepts optional immutable host-provided functions: heightAtCm(x,z), biomeAt(x,z) and allowsCanopyAt(x,z). The old overload remains source-compatible and uses procedural TerraWeave noise whenever a callback is absent.

This resolves the previous pure-noise-only limitation at the CPU bake boundary: independently authored worlds can supply their heightfield tiles, biome masks and road/shore/structure clearings. A disallowed canopy sample is skipped before rasterization; it does not require another draw call or an individual-tree entity. Both forest/terrain vertex colours and their heights sample the same source snapshot, so distant ground can be made consistent with nearby collision/terrain.

The input pointer is borrowed during a single bake; asynchronous hosts must hold a shared_ptr<const HorizonSurfaceSources> or equivalent immutable snapshot while worker jobs are running. Do not capture mutable ECS world objects in worker callbacks. Callback source values and GPU visual agreement have not been verified by tests or screenshots in this stage.

Horizon snapshot connection in WorldScene (stage 9b)#

TerraWeaveHorizonScene::setSurfaceSources( std::shared_ptr<const HorizonSurfaceSources>) accepts an immutable sampling snapshot from the owner thread. Internally the worker copies the shared pointer before invoking bakeHorizon. Replacing a snapshot cancels the selected asynchronous cell and queues a new revision on the next update(); the last successfully uploaded model remains available until a replacement succeeds.

WorldScene now populates authored AuthoredWorldHeightSnapshot and FoliageExclusionMask whenever either an opt-in near forest or an opt-in Horizon renderer is active. It supplies resident height tiles to the far-terrain sampler and uses resident collision-box footprints to clear canopy. It does not modify source collision, gameplay ECS or deterministic placement IDs. Unloaded terrain tiles fall back to the Horizon procedural height seed; this is not yet a guarantee of seamless authored terrain beyond the resident world.

Do not call setSurfaceSources once per frame: it invalidates the current pending region and would cause repeated CPU bakes. Only publish an updated snapshot when the underlying authored terrain/obstacle residency changes, as WorldScene currently does.

Horizon cache and camera-cell hysteresis (stage 9c)#

HorizonSettings::maxCachedRegions (default 2, range 0–4) enables a bounded CPU-side LRU cache of immutable baked Horizon regions. Re-entering a recently visited camera region reuses its already rasterized forest/terrain snapshot, while a new GPU model is still uploaded through the existing Renderer3D RHI path. This saves CPU canopy baking, not GPU upload work. 0 disables retention for constrained devices. A new authored landscape setSurfaceSources() revision invalidates cached regions and cancels the current pending publication. Old worker snapshots continue to exist only as long as jobs need them.

HorizonSettings::regionHysteresisCm (default 3200 cm) holds the selected 128-metre camera cell until the observer moves a further 32 metres past its previous boundary, reducing repeated streaming near grid edges. It must be less than half the middleTileCm cell side. Both fields are configurable through terraweaveHorizon JSON.

TerraWeaveHorizonScene::runtimeStats() now returns cachedRegions and cacheHits in addition to previous CPU/GPU/geometry stats. The default cache can retain two packed RGBA atlases in addition to the current render model, so memory grows predictably; cache capacity is not a hard ceiling for all temporary worker/upload staging allocations.

No disk cache or runtime skip-GPU-upload was implemented by this stage. Benchmarks and cache-key/invalidation/camera-boundary tests are explicitly delegated to a separate test agent.

Prebaked Horizon archive assets (stage 9e)#

Static worlds may avoid the expensive canopy rasterization across game restarts by preparing a region offline and shipping a .twh asset. engine/world/TerraWeaveHorizonArchive.h provides pure portable C++20 APIs (no filesystem, OS or rendering dependencies):

const uint64_t fingerprint =
    terraweave::horizonArchiveFingerprint(terrain, biomes, settings);
auto bake = terraweave::bakeHorizon(terrain, biomes, settings,
                                    regionCenterXcm, regionCenterZcm);
std::vector<uint8_t> bytes =
    terraweave::encodeHorizonArchive(bake, fingerprint);
// The game/editor build tool writes bytes into its own asset pack.

// At runtime, given the *same* settings and matching world content:
terraweave::HorizonBake decoded =
    terraweave::decodeHorizonArchive(bytes, fingerprint);

Archive wire format is currently versioned TWH3, explicit little-endian integer fields, packed RGBA atlas, terrain vertices and cluster metadata, with a 64-bit FNV payload checksum and 20 MiB maximum serialized size. It is intended for trusted application assets; the checksum is not cryptographic authentication. Decoder checks version, fingerprint, sizes, atlas frame bounds, payload integrity and trailing bytes before returning any bake.

TerraWeaveHorizonScene::setArchiveStore(...) accepts an optional shared HorizonArchiveStore with read and/or write callbacks and an optional stable authoredContentHash. Configure it before the first update(), because callbacks are then invoked by the bounded worker. The worker checks the in-memory LRU first, then a prebaked archive, then falls back to a fresh procedural bake. Failed/corrupt/stale archive reads and write failures are best-effort cache misses, not fatal. The runtime keeps only one uploaded Horizon GPU model, regardless of how many CPU archives are available. runtimeStats().archiveHits counts successful archive restores.

For WorldScene game manifests, optionally add:

{
  "terraweaveHorizon": {
    "quality": "balanced",
    "archivePrefix": "world/horizon-cache"
  }
}

It looks for world/horizon-cache/<cellX>_<cellZ>.twh, where X/Z are signed middle-Horizon camera-grid keys, through the normal game AssetReader. No configured prefix means no asset lookups. The WorldScene adapter is read-only; the build pipeline is responsible for producing and packing the blobs.

Important for authored terrain/roads: if the async Horizon has an external HorizonSurfaceSources snapshot, disk archive reuse is disabled unless the caller provides a nonzero stable content fingerprint via HorizonArchiveStore::authoredContentHash (or manifest archiveContentHash). That value must change whenever surface heights, biome paints, road/water/structure masks or other region-affecting authored data change. This avoids silently loading a stale canopy/terrain snapshot. Without an external authored source, a zero hash denotes a purely procedural world and archive lookup remains available.

Verification explicitly delegated: portability (AppleClang/Clang/GCC/MSVC), archive round-trip, corrupt/truncated bytes, stale fingerprints, missing pack asset fallback, alpha atlas GPU upload and races with source invalidation. The authoring agent has NOT built or run tests for this code.

Stage 10 — bulk asset baking and selective Horizon regeneration#

Host-only bulk bake#

The reusable engine/world/TerraWeaveHorizonBatch.h declares HorizonBatchBounds, HorizonBatchOptions, HorizonBatchStorage (game-supplied read/write/cancel callbacks), HorizonBatchProgress and bakeHorizonBatch(...). It generates deterministic signed camera region keys in z-major, x-minor order, using the same grid and fingerprints as runtime HorizonScene. Up to 4,096 regions are allowed by default. Existing valid TWH2 archives are skipped; wrong settings/version/CRC/missing assets are regenerated. The tool never accesses the GPU or authoritative ECS.

aiverse_horizon_bake is a host-only CMake target built with AIVERSE_BUILD_TOOLS=ON, disabled for Emscripten. Example:

aiverse_horizon_bake \
  --manifest content/world.json \
  --out content/world/horizon-cache \
  --cells -4 -4 4 4

Each region produces <x>_<z>.twh in that output folder. Pack the files as normal content and configure the same terraweaveHorizon.archivePrefix in the runtime manifest. --force bypasses skip-existing; --max-regions N limits work. The executable builds procedural Horizon surfaces only. Projects with authored collisions/roads/water instead use bakeHorizonBatch directly with their immutable HorizonSurfaceSources snapshot and a nonzero authoredContentHash.

Stable atlas slots and partial CPU updates#

Before partial regeneration each cluster receives a stable atlas slot independent of visible cluster count: (layerBase + row*rowCount + col) * orientationViews. Changes to road/shore mask, terrain height or biome in one region do not move unrelated cluster UV subrectangles. This atlas-layout change advanced the archive format to TWH2/version 2; previous TWH1 blobs must be regenerated.

bakeHorizon(..., source, previous, editedRegions) can reuse an immutable previous HorizonBake when its snapped camera, atlas dimensions, terrain grid and region origin match and editedRegions is nonempty. It copies the previous atlas, reuses unchanged cluster records and their pixels, clears only affected stable atlas tiles, redraws affected canopy pixels, and recalculates only edited terrain vertices. A conservative cluster-width margin captures affected neighbouring canopy/slope samples. Incompatible previous bakes or empty change bounds perform a full bake.

TerraWeaveHorizonScene::setSurfaceSources(source, editedRegions) now captures old CPU bake and an immutable source generation snapshot for the background job. The GPU model remains visible during regeneration. Regions not intersecting the currently displayed Horizon footprint do not need an immediate rebake. On mobile/minimal configurations with maxCachedRegions=0, the full-regeneration path avoids retaining an extra CPU Horizon bake. Authored source changes bypass stale static archives rather than silently restoring old foliage.

WorldScene::update records touched loaded/unloaded authored height/obstacle cells as world-centimetre RectCm bounds and passes them only to the Horizon snapshot adapter. The near forest maintains its separate revision-safe streaming model; no gameplay collision, navmesh or ECS entities are modified.

Scope limit: partial updates reduce CPU atlas rasterization but still rebuild and upload the combined GPU model/atlas. There is no partial GPU texture update and no dynamic material-driven temporal crossfade in this stage. Both require actual backend quality/performance validation.

Verification: These are implemented source APIs only. The separate testing agent is responsible for builds, CTest, archive round trips, moving-camera snapshots, memory and GPU captures. None were executed by the feature agent.

Stage 11b — incremental GPU atlas subregion uploads#

Horizon can now skip replacing an entire GPU render::Model for atlas-only changes that preserve every terrain vertex (including colour), camera-clipped near terrain topology, forest cluster positions, heights, sizes and UV slots. This is a conservative optimization, not a new shading backend:

  • engine/render/TerraWeaveHorizonGpuPatch.h: horizonCanReuseModelGeometry(oldBake,newBake), planHorizonAtlasUpload(oldBake,newBake,atlasTilePixels), applyHorizonAtlasUpload(gfx::Device&,Model&,newBake,plan).
  • The pure CPU planner identifies changed fixed atlas slots, coalesces horizontally adjacent/vertically equal runs, and defaults to at most six rectangle updates totalling at most 25% of the current atlas RGBA bytes. Larger updates, invalid resident atlas textures or any changed geometry use the existing full uploadModel path.
  • On the GPU owner thread, gfx::Device::updateTexture updates RGBA8 subregions. The engine's existing GL/Metal/ Vulkan implementations regenerate mipmaps as required. No new graphics backend calls or per-tree draw calls.
  • TerraWeaveHorizonScene::runtimeStats() exposes atlasPatchCount, atlasPatchBytes, atlasPatchRegions and fullUploadCount. The counters are meaningful only when an actual scene runs; no frame-rate claims have been made.

Only atlas pixels are patched; changes to cluster count, geometry, base colour, far terrain vertices or authored heightfield force a full model swap. This stage does not provide partial GPU vertex buffers, continuous per-frame crossfade, or eliminate the CPU worker's model preparation. The user assigned validation to another agent: test partial uploads including mips/row-pitch on Metal, GL, Vulkan and real mobile/desktop workloads before marking production-ready.

Stage 12 — GPU terrain vertex subrange updates (geometry-safe)#

Horizon may now commit small terrain height/normal/vertex-colour edits directly into the existing GPU vertex buffer, instead of reuploading an entire distant forest/terrain Model. This uses the same cross-genre RHI:

  • render::Model::batching.allowGeometryPool is a generic bool, default true. TerraWeaveHorizonModel sets it to false to guarantee a dedicated GPU vertex/index allocation. Never blindly call updateBuffer with model-relative offsets when model.geometryPoolPage is present: the pooled VB can contain several unrelated models with nonzero base offsets.
  • TerraWeaveHorizonGpuPatch.h has horizonCanReuseHorizonLayout(): preserves source camera region, terrain X/Z positions, atlas footprint, all cluster crosscard/UV geometry and index topology while allowing changes in terrain height/colour/normal.
  • TerraWeaveHorizonVertexPatch.h exports the pure CPU planHorizonVertexUpload(), and owner-thread horizonCanApplyVertexUpload() / applyHorizonVertexUpload(). Planning requires exact unchanged index data, node and primitive topology, unchanged crossed-card vertex bytes, and new computed model/primitive bounds contained in the resident conservative bounds. Other changes trigger the existing full RHI model upload.
  • The default vertex patch budget is at most 20 contiguous ranges and 35% of terrain vertices. A successful patch issues gfx::Device::updateBuffer on the same owning thread that publishes the CPU forest atlas and renders models; changed atlas tiles can be patched in the same publication.
  • The previous CPU ModelVertex and index snapshots are captured after prepareModelUpload, before uploadModel discards its CPU arrays. They are retained only with an enabled Horizon CPU cache (maxCachedRegions>0). This avoids keeping an extra 7–15 MiB atlas CPU copy inside the resident GPU Model. Minimal and mobile presets keep full-upload fallback to minimize memory.
  • HorizonRuntimeStats adds vertexPatchCount, vertexPatchBytes, and vertexPatchRanges alongside atlas patch/full upload counters.

Important safety limits: gfx::Device::updateBuffer is a void/nontransactional device API; a backend or GPU device loss cannot provide a partial-patch success guarantee. All geometry/data/range validation happens before issuing GPU writes, but true rollback requires general RHI device-loss recovery. Renderer culling bound expansion is deliberately NOT part of this optimization; edits that would grow any draw bounds use the full upload. This is a correctness-first fast path. GPU/device/CTest testing is owned by another agent and has not been executed in this development stage.

Stage 13 — bounded GPU residency for Horizon regions#

TerraWeaveHorizonScene now reuses previously uploaded region render::Model resources after the observer returns to an earlier camera cell. This GPU residency is distinct from the existing CPU maxCachedRegions atlas LRU and from the streaming/staging worker budget.

engine/render/TerraWeaveHorizonGpuCache.h implements render-thread-only HorizonGpuRegionCache. An inactive entry owns its uploaded RHI Model, matching immutable CPU bake when available, optional terrain CPU vertex/index data for incremental updates, camera coordinates, model bounds-related metadata and a source-generation tag. take transfers model ownership without copying or reuploading geometry; retain can evict LRU entries by count and estimated GPU bytes; prune rejects authored-terrain revisions, and clear(device) explicitly destroys cached buffers and textures.

Configurable terraweaveHorizon manifest properties:

  • maxCachedGpuRegions: 0–3 additional GPU region models (Balanced default 1; Minimal/Mobile 0, High requests 2).
  • gpuCacheBudgetMiB: 8–96 MiB for the additional cached regions (default 32 MiB). The current visible model and async upload staging are separate, bounded through their existing contracts. Approximate byte accounting includes vertex/index buffers, atlas RGBA8 and 4/3 mip allowance, but not exact driver overhead.

Navigation A→B retains the visible A model while B is prepared. On successful B publication, A can enter the bounded GPU cache. On B→A cache hit, A becomes active immediately with no new CPU region bake and no full GPU model upload; meanwhile canceled background jobs are still drained to release staging reservations. Source revisions invalidate all stale cache entries and reject late CPU results from old landscape snapshots.

TerraWeaveHorizonScene::runtimeStats() now reports gpuCachedRegions, gpuCachedBytes (estimated extra GPU use), and gpuCacheHits. These are instrumented counters, not measured FPS.

Lifecycle and correctness: all GPU resource retirement goes through render::releaseModel(device) on the owning RHI thread and explicit shutdown(device). No per-tree ECS entities, separate renderer, backend-specific calls, or unbounded GPU caching. A disabled/opt-out Horizon creates no new caches. Quality presets and native projects can opt out by setting maxCachedGpuRegions=0.

Status: source code was committed, but builds, CTest, platform GPU screenshots, GPU memory tracking, and frame-time measurements are the separate validation agent's responsibility. Runtime GPU reuse and lifecycle are not yet verified.

The GPU residency counters additionally include gpuCacheEvictions, counting models explicitly released from the inactive LRU due to count/byte limits or stale terrain revisions. This excludes active-region replacement when no cache could retain the old model and does not measure GPU driver allocations or frame time.

Stage 14 — temporal transition between GPU Horizon regions#

Horizon now has an optional neighbor-only temporal crossfade when the camera crosses a 128m-region key and the next proxy has been uploaded (or found in the GPU residency LRU). HorizonSettings::regionTransitionMs is a bounded 0..1000 milliseconds, default 240. It can be overridden through terraweaveHorizon.regionTransitionMs. 0 disables the fade for all platforms. The Minimal and Mobile quality presets choose 0 automatically to conserve GPU memory and avoid alpha-overdraw costs.

During the bounded transition only, the renderer draws the outgoing and incoming already-uploaded render::Model proxies with complementary smoothstep alpha using existing Renderer3D::ModelDraw.tint.w and kDrawTransparent rendering flags. Both are non-shadow-casting during the effect. The normal single, opaque, static model draw path resumes immediately afterwards. There is no new shader, per-tree foliage model, framebuffer or RHI backend.

The outgoing model occupies ONE of the existing inactive GPU residency slots and is subject to maxCachedGpuRegions and gpuCacheBudgetMiB. HorizonGpuRegionCache::reserveTransient evicts inactive LRU models as necessary. On completion, the outgoing model is stored back into that GPU LRU when the authored source revision still matches; otherwise it is explicitly freed using render::releaseModel(device). Camera changes across more than one grid cell, updates to terrain/ water/road masks or insufficient GPU budget skip temporal blending to avoid stale/outlandish visuals.

New diagnostics: HorizonRuntimeStats::transitionStarts, transitioning and transitionProgressPermille.

Important: Conventional alpha blending can produce sorting/depth artifacts when two terrain rings overlap or when crossed forest billboards intersect. This is a short, bounded visual transition, not order-independent transparency or a depth-aware geomorph. It is unverified on real render backends. The user assigned all CMake/CTest, GPU screenshots and performance testing to a separate agent.

Stage 15 — opaque far-ground ownership during Horizon transitions#

The previous Horizon crossfade blended two entire combined terrain+canopy models. On overlapping coarse ground grids this could cause semi-transparent terrain to double-composite, incorrect depth ordering or Z-fighting.

Now render::ModelDraw::primitiveMaterialFilter is an optional engine-generic source material selector (-1 default, 0 only source material 0, 1 only source material 1). The standard Renderer3D::drawModel skips unrelated Primitive entries, disabling aggregate material/shadow batches and static-cache acceleration only for these filtered calls. All ordinary unfiltered model submissions keep their existing batching, LOD and shadow logic. The new field is placed at the end of ModelDraw to preserve source compatibility with positional aggregate initializers.

Horizon has two established material slots in one GPU model: 0 = distant terrain, 1 = canopy cluster cards. During short regionTransitionMs crossfades:

  1. Submit incoming terrain only, opaque, once, with primitiveMaterialFilter=0. It writes the depth surface.
  2. Submit outgoing canopy material 1 at alpha 1 - t through the existing transparent pass.
  3. Submit incoming canopy material 1 at alpha t through that same pass.
  4. Once the fade is over, go back to one full combined model draw with filter -1.

The GPU model is not copied or split into multiple GPU allocations; draw calls reuse its existing buffers and texture atlas. Temporarily drawing two forest materials costs two transparent model submissions plus one opaque ground submission. Shadow/light-bake capture is skipped for partial transient draws. This is still alpha blending and may show canopy sorting artifacts, but it prevents simultaneous semi-transparent far-ground meshes.

Navigation also supports direct A→B→A reversal during the fade: the old region is reclaimed from its temporary transition slot rather than being evicted by an over-subscribed LRU. When camera teleporting far outside the current region's safe footprint, an obsolete proxy is not submitted while the async worker prepares the replacement, even on low-memory devices whose maxCachedRegions=0.

Remaining functional/visual caveats:

  • Far terrain changes instantly (instead of crossfading its geometry). Large mountain skyline changes may still pop at a region boundary.
  • Transparent canopy cards may intersect/sort poorly; real Metal/GL/Vulkan recordings are needed to decide whether shared shader-driven dither is worthwhile.
  • The safe-footprint teleport gate may temporarily leave no horizon when a new region is not ready. This is preferable to drawing a distant proxy around a camera tens of kilometres away.
  • All compilation, CTest, GPU validation and FPS measurements belong to the separate test agent; code is currently NOT RUN / UNVERIFIED.

Stage 16 — globally aligned Horizon terrain and edge skirts#

Horizon terrain vertices now lie on a globally anchored, signed rational world lattice, using floorDiv(gridIndex * regionSide, terrainResolution). Adjacent camera regions therefore sample the same terrain positions even at High 64×64 or custom resolutions where the 512m camera-region shift is not divisible by the coarse grid spacing. Negative world coordinates remain stable.

Each HorizonTerrainVertex stores slopeXPermille and slopeZPermille. Normals are obtained from height samples one global grid step on either side of the vertex, including outside the current region. Authoring a small terrain edit also marks the surrounding one-grid-step normal footprint dirty for partial CPU re-baking. This avoids the old region-dependent one-sided lighting normals.

terrainSkirtDepthCm is an optional downward, outer-edge skirt on the coarse terrain material, from 0 to 5000cm. It preserves sampled top heights and adds no new material primitive or separate draw call. Default Balanced/High 1200cm, Mobile 600cm and Minimal off. From a high vantage point, downward geometry can be visible and should be tuned with atmospheric fog; it is not terrain geomorphing.

With default 48×48 terrain and 832 possible forest clusters, analytic worst-case geometry is 9,253 vertices and 8,320 triangles, including 196 outer-skirt vertices and 384 skirt triangles. The 1392×1392 shared one-view RGBA atlas still uses 7,750,656 bytes before mipmaps. Top terrain and forest remain in the same standard GPU Model.

Archive format: TWH3 (version/magic 3) stores both global slopes and skirt depth; its fingerprint also changes to reflect the new lattice. Previous TWH1/TWH2 binaries are deliberately rejected. Use aiverse_horizon_bake to rebuild static-world .twh assets or rely on the existing runtime regeneration fallback. Earlier TWH1/TWH2 references in this document describe historical stages, not the current on-disk format.

Limitations: matching border geometry requires the same immutable source heightfield in the overlapping area. Authored terrain streaming changes may still require incremental re-baking; a source swap can visibly change the true landform. The skirt hides small outer-edge cracks, not abrupt skyline changes or inner near-terrain cutout mismatches. GPU screenshots, builds, CTest and platform performance have not been run by this agent; testing belongs to the dedicated validation agent. See Stage 16 handoff.

Stage 17 — near-ground ownership, inner seam and stable outer skyline#

HorizonSurfaceSources exposes an optional ownsNearTerrainRect(minXcm,minZcm,maxXcm,maxZcm) callback. It must return true only when a full half-open coarse world rectangle is covered by live near-terrain geometry. WorldScene supplies it from AuthoredWorldHeightSnapshot::coversRect, which checks all resident near ground tiles and returns false if any are absent. The generator stores a HorizonBake::nearOwnedQuads byte map (terrainResolution × terrainResolution).

During makeHorizonModel, far-ground quads are omitted where the near mesh owns the whole coarse cell. With a callback present, this replaces the old uniform radial cutout, so a missing/unloaded near tile is filled by far Horizon ground instead of exposing sky. Without any callback, existing procedural Horizon settings continue to use the legacy radial terrainBeginCm cutout.

The optional innerTerrainLipCm (default 40cm, valid 0–200cm) makes a tiny downward seam along near-owned/far-owned quad boundaries. At most 512 segments are generated. Each segment adds 2 bottom vertices and 2 triangles, using existing material 0; above that cap the inner lip is omitted without losing the near ownership mask. This is not exact polygon clipping: far quads overlapping only part of an authored near tile remain rendered and may still exhibit coplanar depth overlaps.

terrainGridSnapSteps (1..16; default 4) stabilizes mountain silhouettes. Terrain sample positions snap to the nearest coarse global lattice anchor. Forest atlases can still stream on their 128m keys without moving the distant terrain grid every time. Minimal preset uses 1, Mobile 2 and Balanced/High 4. When distant terrain is on, the outer forest radius is conservatively limited to the region still guaranteed to have distant ground at any allowed snap offset, typically 5+ kilometres; without distant ground, forest keeps its original far radius.

New analytic default worst-case with outer skirt and maximum optional inner seam: 10,277 vertices / 9,344 triangles across terrain and up to 832 cluster cards. This includes the conservative 512-segment inner seam cap. A procedural scene with no near ownership needs fewer vertices and has no inner seam. One shared forest atlas and at most two material primitives remain.

Stage 18 — precise partial near-ground tile clipping (TWH5)#

Stage 17 omitted a far-ground whole coarse quad only when every portion was owned by resident authored near terrain. The gap-free fallback avoided missing geometry but a partially covered 256m cell could still render an overlapping distant triangle.

The new optional HorizonSurfaceSources::collectNearTerrainRects returns at most 1024 immutable, world-centimetre, half-open resident near-ground rectangles for the currently prepared Horizon footprint. AuthoredWorldHeightSnapshot::coveredRectsIn exposes this directly to WorldScene, using deterministic geometric ordering. The CPU HorizonBake stores these rectangles in nearClipRects alongside the existing full-quad nearOwnedQuads mask.

engine/render/TerraWeaveHorizonClip.h implements planHorizonNearGroundClipping(bake):

  • Each affected coarse far-ground cell is split into the same two original triangles.
  • Subtract overlapping near-tile rectangles using convex half-plane polygons; retain only regions not owned by near terrain. Convert them back into bounded triangles with their original winding and source-triangle plane.
  • Reconstruct clipped vertex positions, normals, UVs and RGBA8 colors through barycentric interpolation of the original far-terrain triangle, so the new mesh does not invent a second, divergent far-ground surface.
  • Keep all terrain triangles in the same material 0 primitive and existing shared GPU model. No new shader, per-tile draw calls, FPS/RTS module or parallel renderer is introduced.
  • Enforce a global per-region cap; on excessive geometric fragmentation, the planner returns no plan, and the entire bake falls back to conservative Stage 17 full-quad ownership. Invalid or unbounded near input never produces an unbounded GPU mesh.

HorizonSettings::maxNearClipTriangles controls the maximum new clipped triangles (0=disabled, 0–8192 accepted). Default presets are:

With default Balanced, the worst-case analytic bound becomes 16,421 vertices and 11,392 triangles, including the prior outer skirt, inner 512-segment lip cap and the extra 2,048 clipped triangles. Actual forests typically use substantially fewer. The shared atlas budget, additional GPU cache limits and usual RHI path do not change.

Diagnostic fields HorizonRuntimeStats::nearClipQuads, nearClipTriangles and nearClipFallback identify how many coarse cells were partially clipped, resulting triangles, and whether the safe budget fallback was triggered. Values persist through GPU-region caching.

Limits: This is precise horizontal X/Z coverage against axis-aligned near terrain tile rectangles, NOT vertical geomorphing. If the authored near terrain lies higher/lower than its coarse distant representation, the clipped boundary may still have a vertical crack. The previously existing 40cm inner lip covers only whole coarse ownership boundaries, not every new partial cut edge. Real GPU visual acceptance and any height-aware stitching remain separate work. Stage 19 — near/far terrain height-welded clip boundaries (TWH6)#

Following Stage 18's exact 2D subtraction of authored near-tile rectangles from distant Horizon triangles, the clipped perimeter can now be snapped to the actual authored near-terrain height, leaving the triangle interior on the existing far-ground surface. This removes a vertical boundary height gap when the source terrain is resident and the optional sampler is supplied.

HorizonSurfaceSources::nearGroundHeightAtCm(worldXcm,worldZcm) returns optional<int32_t> (near height in signed centimetres); WorldScene connects it to the same immutable resident AuthoredWorldHeightSnapshot used for near coverage rectangles and terrain sampling. The CPU helper populateHorizonNearSeamSamples(HorizonBake&,source) finds clipped polygon vertices along near-tile boundaries, deduplicates them in world-centimetre Q16 space (fractional positions preserved) and samples at most 4096 unique near-ground heights. A half-open tile's high edge is sampled at most 1cm inside that already resident tile to avoid reading an unloaded neighbor. If a required point cannot be sampled, the entire seam-height table is withheld and the prior Stage 18 exact horizontal clipping remains available without half-welded geometry.

HorizonBake::nearSeamSamples is an immutable, serialized list of {xQ16cm,zQ16cm,nearHeightCm}. During makeHorizonModel, only clipped-edge position.y is replaced with the matching authored near-surface height. Far-interior vertices stay on their coarse parent triangle. No new GPU vertex topology, material, draw call, graphics backend, gameplay ECS entity or collision modification is introduced by welding.

Both the runtime CPU worker (TerraWeaveHorizonScene) and native bakeHorizonBatch offline API populate these samples before storing/serializing the immutable HorizonBake. Reading an archive or GPU model cache restores the same data without consulting the mutable current WorldScene from the renderer.

New diagnostics: HorizonModelBuildStats::weldedVertices/maxWeldHeightDeltaCm, HorizonRuntimeStats::weldedNearVertices/maxNearWeldDeltaCm. They survive GPU-cache region restoration. The maximum delta measures the absolute Y correction applied to a clipped vertex in centimetres. No measured GPU timings or screenshot-quality guarantees are implied.

Stage 20 — slope-safe height welding and shared seam normals (TWH7)#

Stage 19 welded the exact near/far clipped-edge Y to the authored near terrain. This could create a nearly vertical far triangle if the coarse original height differed sharply across a tiny clipped polygon. A normal-map fix alone cannot change the actual steep wedge.

Now HorizonSettings exposes two bounded, optional C++/manifest settings:

  • maxNearWeldSlopePermille (0–8000; default 2500). 0 disables the slope guard. The CPU seam sampler preflights each proposed welded triangle using its actual barycentric original far heights and near-boundary heights. A newly induced triangle gradient above the limit rejects the ENTIRE optional height weld for that Horizon bake, retaining the exact Stage 18 X/Z clipping and setting nearWeldSlopeFallback=true. Existing naturally steep far terrain is not flattened. This deliberately can leave a vertical seam; no algorithm can simultaneously keep an arbitrarily high near edge, an unchanged nearby far vertex, zero additional horizontal distance and a strict slope cap. Avoid lying about a perfectly seamless result.
  • nearSeamNormalBlendPercent (0–100; default 65). While constructing an already existing partial near-clip triangle mesh, makeHorizonModel computes upward-facing, area-weighted geometric face normals after any valid near-height weld. It groups shared clipped corners by signed Q16 world X/Z and height to average adjacent face normals. Near-edge vertices blend 65% of the repaired normal, interior near-border vertices blend 16.25% by default. 0 leaves the original far-grid interpolated normals. This changes only the CPU-built existing ModelVertex normal attributes: no extra geometry, shader, material, GPU buffer or draw call.

The CPU worker, offline bake and runtime Model all consume the exact same immutable seam-height snapshots as in Stage 19. HorizonRuntimeStats adds smoothedNearNormals and nearWeldSlopeFallback; these metrics are also preserved when the GPU LRU restores a previously uploaded region.

Archive migration: TWH7#

TerraWeaveHorizonArchive.h is now TWH7, version/magic 7. It adds the seam slope limit, normal blend percentage and per-bake slope-fallback flag to the binary payload. The fingerprint includes both configuration settings. Earlier TWH1–TWH6 .twh files are intentionally rejected and must be regenerated by aiverse_horizon_bake or the existing runtime fallback.

Known limits: the default 2500 permille is a guard for new weld-induced slopes, not an upper bound on all terrain gradients. On extremely narrow clip polygons the guard may reject a weld for the full region, preserving accurate X/Z ground ownership but allowing a vertical height mismatch. Normals are smoothed only on clipped triangles, not on the authoritative near mesh; this is not shared tessellation or true normal-field matching. Captured GPU images and geometry regression tests are REQUIRED before claiming the terrain is visually seamless.

Stage 21 — precise Q16 seam sampling and authored near normals (TWH8)#

Stage 20 already implemented an all-or-none welded-slope guard and area-weighted geometric normal smoothing. The current stage improves the precision and source agreement of the underlying near terrain data.

AuthoredWorldHeightSnapshot::sampleQ16(xQ16cm,zQ16cm) samples the same immutable authored two-triangle height tiles as the existing integer-centimetre sample method, but at signed fractional world-centimetre Q16 coordinates. Integral inputs retain the exact old integer-height result. Fractional points use bounded fixed-point barycentric weights, not floating GPU interpolation.

HorizonSurfaceSources::nearGroundHeightAtQ16Cm is optional. WorldScene supplies it from the same immutable near-ground snapshot that provides collectNearTerrainRects and ownsNearTerrainRect. A native authored provider may omit it and retain the legacy whole-centimetre height path.

During populateHorizonNearSeamSamples, exact clipped polygon coordinates are sampled at Q16 precision. At the high side of a half-open tile the query moves only one Q16 unit (1/65536 cm) into the already resident tile, rather than shifting by up to 1 cm. A bounded +/-200cm stencil entirely inside the same tile derives near-surface slopeXPermille and slopeZPermille. Missing derivative data merely marks the normal unavailable; missing height still disables the entire seam height weld for that region.

Each baked NearSeamSample now contains:

  • xQ16cm, zQ16cm (the same seam identity as Stage 19);
  • nearHeightCm (exact authored Q16-sampled near height, rounded to signed centimetres);
  • nearSlopeXPermille, nearSlopeZPermille, plus nearNormalValid.

makeHorizonModel continues using the existing bounded clipped far triangles. At a welded point with nearNormalValid=true, lighting normals blend toward the authored near-source normal, under the existing nearSeamNormalBlendPercent setting. Interior clipped far triangles retain the Stage 20 area-weighted face-normal blending. Neither clipping topology, vertex/triangle counts, materials nor draw submissions increase.

HorizonRuntimeStats::matchedAuthoredNearNormals counts the clipped render vertices where an authored Q16 surface normal was actually blended. Existing smoothedNearNormals includes the geometric normal path. Both counters survive GPU LRU restoration. The strict atlas-only patch planner refuses modified seam heights/gradients; safe index-compatible edits can still use the combined partial vertex upload or full-model fallback.

Current archive: TWH8. The .twh payload now stores 32 bytes per near-seam point (Q16 X/Z, height, two slopes and encoded validity). The bounded 4096-point table adds at most 48KiB of normal metadata compared to TWH7; no new GPU memory allocation is required beyond existing model vertex attributes. TWH1–TWH7 archives are intentionally stale and should be rebaked with aiverse_horizon_bake or regenerated through the existing worker fallback. Old version sections below/above are historical only.

Seam sampling across resident authored terrain tiles#

AuthoredWorldHeightSnapshot::continuousSlopeQ16(xQ16cm,zQ16cm, radiusCm=200,toleranceCm=1) returns std::optional<std::pair<int32_t,int32_t>> with signed X/Z slopes in permille (-dY/dX, -dY/dZ), or nullopt if a neighboring tile is unavailable or the crossed tile-edge heights disagree. Input X/Z is signed Q16 world centimetres (multiply whole centimetres by 65536). The bounded stencil radius accepts 1–4096cm; discontinuity tolerance is 0–100cm (default 1cm). The snapshot probes the original authored two-triangle heightfields, including negative world tile coordinates, and never changes collision or authoritative terrain.

HorizonSurfaceSources::nearGroundContinuousSlopeAtQ16Cm is an optional CPU-bake callback supplied by WorldScene from the same immutable AuthoredWorldHeightSnapshot used for authored near-ground heights. During populateHorizonNearSeamSamples, the worker prefers a continuous neighbor-aware slope for each unique Q16 clipped perimeter point. When that query returns nullopt it falls back to the previous tile-local +/-200cm derivative when that data is available. If neither yields a valid normal, nearNormalValid remains false and the existing area-weighted clipped-face normal path is used.

This affects render shading only. Stage 24 — sparse deterministic forest regrowth and presentation ticks#

Status: native C++ source committed, runtime/compiler/CTest/GPU verification intentionally deferred until the separate testing phase. This feature extends the already-existing persisted ForestTreeIdentity removals; it does not introduce per-tree ECS entities, a new shader, another RHI backend, a new save file format, or a second GPU forest model.

A TerraWeaveForestScene now supports ForestRegrowthSchedule, a sparse value type:

struct ForestRegrowthSchedule {
    ForestTreeIdentity tree;        // {key, speciesId}: stable across chunks
    uint64_t regrowAtTick;          // hidden before this tick
    uint64_t matureAtTick;          // full generator scale at/after this tick
    uint32_t initialScalePermille;  // 1..1000, defaults to 150
};

Use the game's own deterministic simulation tick — not wall-clock time — with setPresentationTick(uint64_t). scheduleRegrowth(schedule) removes the tree from the persistent removedTrees set and hides it before regrowAtTick. For ticks between appearance and maturity, visibleBatches() modifies the presentation copy of FoliageInstance::scalePermille using bounded integer interpolation, from initialScalePermille to 1000 permille of its original generated scale. matureAtTick == regrowAtTick means instant restoration. Nothing changes in the authoritative scatter keys, heights, seed, collision, navmesh or GPU prototype models. On later camera movement/re-streaming the same identity gets the same scale for the same tick.

#include "engine/world/TerraWeaveForestScene.h"
using namespace aiverse::terraweave;

// Use an existing configured scene and a stable ID obtained from foliage.
ForestTreeIdentity oak{stableTreeKey, 1001};
forest.removeTree(oak); // optional gameplay-driven harvest
forest.scheduleRegrowth({oak, 6000, 12000, 120});
forest.setPresentationTick(gameplayTick);
const auto batches = forest.visibleBatches();
// Host still calls uploadModels()/submit() on the renderer owner thread.
// Persist forest.removedTrees() and forest.regrowthSchedules() in game saves.

Here stableTreeKey and gameplayTick are native-game values, not engine globals. setRegrowthSchedules(...) atomically validates and replaces a saved sorted list; regrowthSchedules() exposes a stable sorted snapshot for persistence/replication. cancelRegrowth(id) cancels a schedule without automatically hiding or removing the tree. removeTree(id) cancels any pending regrowth and hides the tree; restoreTree(id) clears both hidden and scheduled states; setRemovedTrees(...) clears any overlapping regrowth schedules so explicitly removed trees remain hidden. Use the caller's save/network authority for lifecycle decisions.

The implementation limits regrowth to at most 1,000,000 sparse records, rejects zero species, duplicate replacement keys, initialScalePermille outside 1..1000, backward schedules, and maturity intervals greater than 1e12 ticks. These bounds keep elapsed * (1000 - minScale) within signed/unsigned 64-bit integer range without platform-specific 128-bit arithmetic. Even with asynchronous forest generation, tick changes are evaluated at presentation time and do not cancel/rebuild chunk workers.

ForestSceneStats exposes the additional trailing fields scheduledRegrowth and presentationTick, without breaking earlier aggregate uses of its existing members.

Access from WorldScene#

An opt-in world::WorldScene exposes terraweave::TerraWeaveForestScene* forestScene() noexcept (and the const overload). It returns null if the world manifest does not enable terraweaveForest. Native games can include both engine/world/WorldScene.h and engine/world/TerraWeaveForestScene.h and feed game time or saved lifecycle records directly without any genre-specific API:

    forest->setPresentationTick(gameplayTick);

}

Ownership and limitations: this is cosmetic presentation only. An authoritative game layer is responsible for deciding when harvests occur and for modifying collision/navmesh/resources, save versioning, replay/network replication and any wider ecosystem simulation. Harvesting a single tree does not yet punch an individual hole in the far Horizon HLOD cluster silhouettes; coordinate harvested-area masks with Horizon in a later stage to avoid near/far inconsistencies. The implementation has not been built or visually tested in this feature-first phase.

Stage 25 — runtime forest clearings shared by near Flora and Horizon HLOD#

Source implemented, tests deferred at user request. A native world::WorldScene now exposes:

// Call worldScene.update(device, observers, radius) from the owner thread.
// Later: worldScene.setVegetationClearings({}) to restore the area.

Stage 26 — resident tree spatial queries for native gameplay#

TerraWeave now supports presentation-resident tree selection without forcing every decorative tree into ECS:

// TerraWeaveForestScene forest already configured / streamed.
const auto closest=forest.nearestTreeAt(playerXcm,playerZcm,500);
if(closest) {
    forest.removeTree({closest->key,closest->speciesId});
    // The authoritative game must still update lumber, collider and save.

const auto trees=forest.treesInRect(
    {plotMinXcm,plotMinZcm,plotMaxXcm,plotMaxZcm},1024);

The coordinates above are game-provided signed world centimetres.

  • nearestTreeAt(xCm,zCm,radiusCm=500) -> optional<FoliageInstance>: searches resident CPU scatter patches, using an AABB precheck and circle distance. autumn.tintGPermille = 810;

The above values are an example, not a baked climate forecast. Default state retains the existing TWH8 path. No archive version/layout migration occurs. Spring/autumn transitions are immediate material/atlas policy changes rather than continuous blended dual-atlas animations; near impostor cards fade trunk as well as canopy; distant HLOD crown types are procedural/bio-climate approximations, not identities of actual nearby species. Stage 28 — genre-neutral wind presentation for Arbor forest#

Code committed, tests intentionally deferred. The wind motion API is a presentation-only adapter: games or PHYSIS supply wind vectors and simulation ticks; TerraWeave does not run its own weather, physics forces, collision, ECS or platform-time timers.

The new engine/world/TerraWeaveWind.h defines:

struct ForestWindState {
    int32_t xCmPerSec = 0, zCmPerSec = 0;
    uint32_t gustPermille = 350;
    uint32_t cycleTicks = 120;
    uint32_t maxLeanMilliDegrees = 1500;
};
ForestLeanMilliDegrees forestTreeLean(
    const ForestWindState& state, uint64_t tick, uint64_t stableTreeKey);

Both wind components use signed world X/Z centimetres per second. A state is valid when the horizontal magnitude is no more than 5000cm/s (50m/s), gustPermille in 0..1000, cycleTicks in 8..4096 and maxLeanMilliDegrees in 0..3000. The helper computes a bounded integer triangle-wave phase using mix64(stableTreeKey); each tree has a stable offset instead of the entire forest tilting in lockstep. The zero-wind default preserves identical model transforms.

aiverse::terraweave::ForestWindState wind;
wind.xCmPerSec = 900;   // 9 m/s toward +X
wind.zCmPerSec = -300;
worldScene.setVegetationWind(wind);
worldScene.setVegetationPresentationTick(gameplayTick);

WorldScene forwards those values to its optional TerraWeaveForestScene; native projects using the forest independently may call forest.setWind(wind) and forest.setPresentationTick(tick) directly. For an opt-in renderer, the ArborForestAdapter computes a small world-space lean about the base of the model, before the tree's local yaw, then uses existing Renderer3D::drawModel. Stable tree identity, origin-rebased centimetres, per-species LOD, shared meshes and billboard atlas remain unchanged. Per-tree phases and angles are computed on the presentation side; changes to wind/tick do not rescatters, restart workers, or force Horizon atlas uploads.

Important limitations: this is a low-cost root/whole-tree sway approximation, not branch/leaf skinning or vertex-shader wind deformation. Distant Horizon HLOD remains static (moving 12km forest atlases per tick would be excessive); the very far treeline therefore does not individually sway. Billboard impostors lean as one quad. The final float transform is cosmetic and not guaranteed bit-for-bit identical between rendering backends; authoritative physics or harvest logic must never use it. PHYSIS can map its velocity field into this POD from the owning game host without linking the TerraWeave engine to PHYSIS.

Performance and correctness: no new model geometry or draw calls are introduced; however CPU transform math is performed per submitted tree when wind is nonzero, so actual frame cost and visual quality still require the separately scheduled benchmarking and GPU test phase. A future optional vertex deformation shader could preserve stable roots while bending crowns more naturally. Neither compiler nor GPU/CTest has been run during this features-first stage.

Stage 29 — bark/foliage-separated multi-azimuth impostor atlas#

Code committed; no build/CTest/GPU validation yet per the feature-first instruction. This stage replaces the combined all-season RGBA impostor image produced by makeArborImpostorAtlas. A near Arbor tree and its billboard can now lose leaves while retaining an intact bark silhouette.

Atlas and render layout#

engine/render/TerraWeaveImpostorAtlas.h generates one GPU RGBA8 texture per species with two horizontal sets of equal-sized view tiles:

  • The first azimuthViews tiles contain bark/trunk/branch strokes only.
  • The following azimuthViews tiles contain foliage/leaf-cluster strokes only.

Both sets are projected from the same stable TreeSkeleton for each view angle and retain per-tile gutters. The atlas is 2 * tile.width * azimuthViews pixels wide by tile.height high (maximum width 8192, hence previously accepted ultra-wide combinations may now be rejected). Default 8-view, 128x256 atlas becomes 2048x256 RGBA8 instead of 1024x256, doubling raw atlas bytes but still using ONE texture object.

The common render::Model contains one node, one mesh, 8 vertices, 12 indices and two alpha-masked primitives (Primitive.material=0 bark, =1 foliage). The foliage quad is offset +2cm toward its camera-facing model +Z to avoid depth fighting. Both material slots reference the same baseTex=0 with independent per-view UV transforms; ArborImpostorAtlas::viewMaterials is still indexed by azimuth but now contains exactly two materials for each view, in bark/foliage order. No new shader, RHI backend, ECS components, model per instance, or separate atlas upload pass.

Seasonal policy#

ArborForestAdapter::rebuildPhenologyMaterials() copies per-species near and impostor material variants only on policy changes. Material 0 (bark) remains untouched; only material 1 (foliage) gets tint and alpha. canopyCoverPermille chooses evergreen versus broadleaf by the registered profile. At zero canopy cover, existing ModelDraw::primitiveMaterialFilter=0 submits bark primitives only for near BranchLOD and impostors, skipping invisible leaf draws. At partial cover, foliage uses the existing alpha-blend material policy; bark remains alpha-masked and fully opaque. Existing wind lean and root-anchored camera-facing orientation are shared by both impostor layers.

Cost/quality caveats: full-canopy impostors now have two primitives instead of one, so draw submissions/material batching and texture bandwidth can increase. Cutout bark and blended foliage may differ slightly in ordering/coverage from the previous single-layer approximation. Far Horizon still uses its separate aggregated silhouette atlas and is unaffected by this near-impostor format. Partial transparency is a simplified seasonal representation, not deterministic individual leaf shedding; GPU/backend captures are needed to confirm blend order, shadow behavior, LOD transition quality and precise visual parity.

Backward compatibility: makeArborBillboardModel (the standalone single-view utility) retains its original one-quad format. Only the multi-azimuth makeArborImpostorAtlas output changes shape; any native consumer assuming 4 vertices, 6 indices, single material or original atlas width must migrate. Existing tests/terraweave_model_test.cpp has expectations for that old layout and is intentionally not updated or executed in this features-first phase. The later testing agent must revise these assertions to the two-layer contract, then run GCC/Clang CTest, GPU screenshot and benchmark checks. No TWH8 distant-Horizon disk archive version change is needed because its format is unrelated to this near-impostor atlas.

Stage 30 — bounded hierarchical BranchLOD wind motion#

Functional source committed, independent testing deferred. This stage extends Stage 28's PHYSIS-neutral root lean into more organic, articulated wind motion for near Arbor BranchLOD trees, without reskinning meshes or requiring a new render shader.

ForestWindState appends branchFlexPermille (default 600, bounded 0..1000); 0 preserves the exact previous low-cost whole-tree tilt. ArborForestAdapter regenerates the already-deterministic high-detail skeleton ONCE at prototype registration to cache per-branch root pivots (metres relative to original tree root). It then uses the existing branch node hierarchy and Renderer3D's ModelDraw::nodeWorld rigid-model transform path to compute a per-visible-tree vector of cumulative model-space rotations around each branch's own start pivot. The trunk node itself remains at its original pose while global ModelDraw::world supplies the original whole-tree sway. Children inherit parent movement and have a stable per-node phase derived from the tree key, species and branch index.

No tree ECS entities, animation clips, skinned matrices, GPU mesh mutation, shader variants, atlas rebuilds or extra draw passes are added. The original Arbor mesh geometry, TreeProfile, branch LOD simplification and canonical procedural tree seeds remain unchanged. View-distance tiers attenuate additional branch sway (High 100%, Medium 65%, Low 25%, Impostor 0%) to limit near-to-billboard discontinuity. Distant statistical Horizon remains static as previously documented; it is intentionally NOT rebuilt per wind tick.

The private temporary pose arena is a std::deque<std::vector<render::mat4>> so references in ModelDraw::nodeWorld remain stable during a forEachDraw call; the arena is cleared at the next forEachDraw. Renderer3D::drawModel reads node transforms synchronously and copies them into render items. Native callbacks collecting ModelDraws may only use their nodeWorld pointers until the next forEachDraw invocation, and must not use the forest adapter concurrently on multiple threads. ArborForestAdapter::setBranchPoseBudgetBytes(bytes) (forwarded through TerraWeaveForestScene) accepts 0..8MiB and defaults to 4MiB. A draw whose node matrix snapshot would exceed the remaining budget uses root-only sway instead. The budget is for CPU temporary matrices, not new GPU residency.

Example (on the owning host/update thread):

if(auto* forest = worldScene.forestScene()) {
    forest->setBranchPoseBudgetBytes(4u * 1024u * 1024u);
}
aiverse::terraweave::ForestWindState wind;
wind.xCmPerSec=700;
wind.gustPermille=450;
wind.branchFlexPermille=850; // optional, 0 = whole-tree-only
worldScene.setVegetationWind(wind);
worldScene.setVegetationPresentationTick(gameplayTick);

A real PHYSIS solver may supply the world X/Z velocity components; this bridge does not require PHYSIS headers, does not alter collision/navmesh/authoritative physics and does not put wind in an ECS component. WorldScene continues forwarding the same validated wind state and tick, so native code uses the existing public methods.

Limitations/QA debt: Branches are rigidly rotated at their joints rather than continuously bent as a skinned elastic curve. At high winds thin joints can show gaps. The source uses integer hashed wind phases but converts degrees to float matrices in renderer presentation; bitwise cross-GPU determinism is not promised. Very dense near forests can hit the CPU pose budget and switch to root-only motion. Source forEachDraw collectors must respect pose borrowing lifetime. No CMake, CTest, GPU screenshot, per-frame CPU benchmark or cross-platform rendering check has been executed. Dedicated test agent should validate hierarchy/pivot continuity, season + wind, LOD transitions, budget fallback, material/draw pointers and native PHYSIS integration before marking production ready.

Stage 31 — shared GPU crown wind for near Arbor and Horizon#

Source implementation committed in feature/terraweave; independent compilation/CTest/GPU QA NOT RUN. Stage 31 extends Stage 28/30's existing root and rigid-branch sway with an optional GPU vertex-layer. It uses Renderer3D's existing Material Shader Graph vertexOffset hooks for GLSL and MSL, with no compute jobs, new render backend, separate shaders pipeline, GPU vertex buffers, extra atlas or re-bake-per-tick.

First-party vertex graph and instance payload#

The new engine/render/TerraWeaveVertexWind.h provides canopyWindGraph(), one immutable engine-authored render::graph::Program containing both GLSL and Metal vertex code, plus canopyWindVertexParameters(wind,tick,yaw,strength). The graph preserves the fragment's original material/shading (outputs["color"]="sg_input") and emits bounded vertexOffset: wind vector * squared 0..1 height weight * low-frequency, spatially staggered sine wave with bounded higher-frequency gust. Crown roots remain fixed. It uses I.anim, already present in rigid model instance uniform U0, instead of allocating a new uniform buffer. The phase derives from the host's setVegetationPresentationTick (tick modulo ForestWindState::cycleTicks), not uncontrolled wall-clock shader time. X/Z velocities come from the same PHYSIS-neutral ForestWindState as CPU root sway; near instance yaw is inverted before passing the local vector, so wind remains oriented in world space.

This is a trusted engine-generated program, not a user-authored shader source injection API. canopyWindGraph() returns a shared, immutable program to avoid creating a new shader-pipeline identity every tick or every tree. A zero wind vector or zero branch-flex/amplitude leaves the feature disabled and preserves existing materials.

render::ModelDraw appends generic useVertexParameters, vertexParameters (float4) and maxVertexOffsetMetres. Renderer3D::drawModel places those four parameters in U0 Inst.anim only for eligible rigid, non-baked, non-lightmapped instances whose material has a graph. Baked animations and lightmap UV transforms retain priority; no U0 binary layout change was made. Other graph-using native projects may reuse the generic contract, but callers must not request the same U0 payload for baked skin/lightmapped models. Unknown/unbounded shader vertex offsets retain the renderer's conservative no-cull behavior; finite positive explicit bounds allow normal model/node frustum rejection and per-node LOD, with expanded geometry bounds. The TerraWeave graph sets a conservative 0.65m local-space maximum offset.

Near Arbor#

makeArborBranchLodModel encodes each foliage vertex's source height relative to the procedural tree skeleton as a normalized RGBA8 alpha wind weight. Foliage Material::vertexColors=false keeps this auxiliary weight from accidentally tinting/cutting out the leaf texture. Bark geometry/materials remain static under this vertex shader; wind still rotates the tree root and optional rigid branch nodes via the earlier Stage 28–30 paths.

ArborForestAdapter applies the single graph only to foliage material slot 1 in shared per-species and per-azimuth override vectors. The shared program is attached when nonzero validated wind, branchFlexPermille>0 and maxLeanMilliDegrees>0; changing numerical wind/tick values updates per-instance parameters without creating another graph program. GPU flutter amplitude diminishes by LOD (High 100%, Medium 75%, Low 50%, Impostor 35%). If foliage cover is 0 during winter, the old bark-only primitive filter remains active; no hidden leaf vertex pass is submitted. Stage 29's split impostor geometry encodes zero weight at its lower foliage vertices and full weight at the top, so its root is anchored.

Far Horizon#

makeHorizonModel keeps one combined model, the original terrain primitive and shared forest-cluster primitive/atlas. Forest billboard vertex alpha now encodes a weight of 0 at the base and 1 at the canopy top; the forest material ignores vertex alpha in fragment shading so it cannot accidentally erase half the forest. Only its canopy material slot 1 opts into the same graph. TerraWeaveHorizonScene::setWind and setPresentationTick accept the same POD/tick as near Arbor. In submit, current and crossfading forest-region materials receive the shared graph and a restrained 30% GPU wind strength. The terrain material and near/far seam vertices are unchanged. Static TWH8 archives and partial atlas/VB uploads remain untouched; the per-frame motion is a GPU vertex offset, not an atlas redraw. Source snapshot revisions are not advanced merely because the wind changed.

WorldScene::setVegetationWind and setVegetationPresentationTick forward the policy/time to both near ForestScene and far HorizonScene, preserving null opt-in module behavior.

Boundaries/limitations: This is procedural render-only crown flutter, not physical leaf/branch simulation; wind affects shader vertex positions but not collision, navmesh, authoritative tree positions or gameplay ECS. The effect intentionally retains existing root/branch transforms and only adds a small extra vertex displacement. Spatial phases are deterministic functions of the host tick and model-space/rebased world coordinates but GPU sine/floating math is not promised bitwise-identical across devices. Stage 32 — spatial wind grid and near-to-Horizon transition#

Feature source committed, build and tests deferred per the project owner's feature-first priority.

Native games/PHYSIS can publish one bounded, immutable spatial wind snapshot for near Arbor trees and far Horizon, without linking PHYSIS to the forest renderer. The new engine/world/TerraWeaveWindField.h defines ForestWindField as a regular X/Z lattice of ForestWindSample {xCmPerSec,zCmPerSec,gustPermille}, all in signed world centimetres and cm/sec. The caller owns sampling from its actual PHYSIS wind/weather field; TerraWeave performs only the render-side interpolation:

using namespace aiverse::terraweave;
auto mutableField=std::make_shared<ForestWindField>();
mutableField->originXcm=-12800;
mutableField->originZcm=-12800;
mutableField->spacingCm=6400;
mutableField->columns=5;
mutableField->rows=5;
mutableField->samples.assign(25,{800,0,400});
// Optionally fill specific nodes with different PHYSIS velocities.
mutableField->samples[12]={-100,550,750};
mutableField->validate(); // reject invalid geometry/oversized winds
std::shared_ptr<const ForestWindField> published=mutableField;
worldScene.setVegetationWindField(published);
worldScene.setVegetationPresentationTick(gameplayTick);
// Publish a NEW immutable object when the weather field changes:
worldScene.setVegetationWindField({});

Do not mutate a field after publishing it, even if a mutable shared pointer alias still exists. Create and publish a new snapshot for each update. WorldScene::vegetationWindField() returns the active const shared snapshot (or null). Native projects using the forest/Horizon directly can call their setWindField(shared_ptr<const ForestWindField>) methods. The uniform fallback still comes from the existing ForestWindState (setVegetationWind) and supplies the authoritative wind animation period, strength/flex, and limits. The grid overrides only local X/Z wind velocities and gust intensity.

Sampling and transition semantics#

  • Limits: either empty/default field or 2..64 nodes per axis, at most 4096 node samples; spacing 100..10,000,000cm; all node coordinates within +/-kWorldLimitCm. Each node is validated using validateForestWind (horizontal magnitude <=5000cm/s; gust 0..1000). Invalid input fails before replacing the active world snapshot.
  • sampleForestWindField(field,xCm,zCm,fallback) uses Q16 bilinear interpolation in absolute signed world centimetres, including negative positions. Outside the lattice it returns fallback; a half-node-spacing interior feather blends border values back to the fallback to prevent sudden direction/speed jumps at the field edge. No shader texture, RHI buffer, global mutable state or wall-time dependency.
  • blendForestWind(local,macro,macroPermille) is a bounded integer interpolation of velocity and gust. Branch flex, period and lean maximum remain those of the fallback source.
  • The near ArborForestAdapter samples the immutable field at each resident tree's stable world position. Its geometric root lean, hierarchical CPU branch poses, and Stage 31 GPU leaf displacement all use that same effective per-tree wind. For consistency near distant render tiers, wind is blended toward the observer-position macro sample, continuously between FloraView.mediumRangeCm and FloraView.cullRangeCm (using a conservative X/Z Chebyshev distance and bounded permille interpolation). The forest scene configures these boundaries once; an unchanged/no-field setup retains its old execution path.
  • The far TerraWeaveHorizonScene takes one observer-space macro wind sample in submit, shared by active and outgoing region draws during crossfade. This prevents a wind-vector discontinuity when the Horizon region changes and keeps HLOD geometry/atlas batched. It does not yet produce a separate PHYSIS wind vector for every statistical distant forest cluster. A later optional coarse GPU wind field or per-cluster baked vector feature can improve microvariation at kilometre scale if warranted.
  • WorldScene::setVegetationWindField forwards the same shared_ptr<const ForestWindField> to its optional forest and Horizon modules, with no terrain worker invalidation or TWH8 archive changes. Repeated pointer identity is a no-op; passing null clears the field so only uniform wind remains.

Performance/ownership: the spatial field adds a handful of bounded CPU integer interpolations per submitted near-tree, not per ECS entity or terrain scatter candidate. Horizon performs one sample per submission rather than one per billboard cluster. Live weather updates need a new bounded field snapshot but do not allocate new vertex/texture buffers or recompile ShaderGraph programs. The sampler assumes the caller has validated the immutable field on publication; direct native callers MUST invoke field.validate() before sampling, rather than mutating the structure concurrently. Inputs from a high-resolution PHYSIS simulation should be downsampled by the host to this bounded presentation grid.

Not verified: Neither C++20 compiler/CMake/CTest nor GPU/PHYSIS integration, visual transition captures, pathological negative-boundary samples, or performance profiling was run at this feature-only stage. Remaining known test debt includes the Stage 29 two-primitive impostor migration and Stage 31 GLSL/Metal Shader Graph rendering.

Stage 33 — smoothly varying far-Horizon forest-cluster wind#

Source code committed; build/CTest/real GPU checks are deferred. The far Horizon no longer needs to use one visually identical wind vector for every forest card in a multi-kilometre region. Each baked cluster receives a smooth, signed-world-coordinate variation in direction, gust strength and phase without adding draw calls, atlas textures, per-cluster ECS entities, or per-tick GPU uploads.

What is encoded per cluster#

engine/render/TerraWeaveVertexWind.h adds horizonSpatialWindVertexColor(worldXcm,worldZcm,terrainSeed,canopyTop) and horizonSpatialWindGraph(). The former evaluates three deterministic 2.4 km wavelength world-space noise channels at a cluster's fixed X/Z centre and packs them into RGB8 in the already-existing render::ModelVertex::color. Alpha still holds the Stage 31 crown-weight: zero at the bottom edge, 255 at the top. Each pair of crossed silhouette cards for a cluster uses the same RGB wind sample, so the cards cannot diverge. The sampling is independent of observer cell and of how the Horizon region is streamed, including negative world coordinates and transitions between GPU-resident regions. No additional ModelVertex fields or static archive changes.

At runtime, the first-party GLSL + Metal horizonSpatialWindGraph() uses the same inherited I.anim instance data as the Stage 31 crown graph. One shared macro wind vector (from the existing ForestWindField sampled at the observer location, or the fallback uniform wind) is rotated by at most 30 degrees per cluster, scaled between 0.75 and 1.25, and given a coherent but cluster-dependent phase offset. The exact per-cluster coefficients are fixed by the baked vertex RGB metadata and never require new CPU atlas work when the wind tick changes. Roots stay fixed because alpha is still zero at the card bottom. Direction, amplitude and phase vary smoothly across neighbouring clusters in world space rather than jumping between camera tiles.

makeHorizonModel writes this metadata only to the distant forest vertices, not authored/coarse terrain. The far forest material already has vertexColors=false, ensuring these packed RGB8 values do not unexpectedly tint the foliage or modify opacity. No changes were made to near authored terrain, clipping, Q16 height welding, canopy atlas pixels or TWH8 serialized data.

Native API and quality switch#

// Already supported PHYSIS/game wind setup:
worldScene.setVegetationWind(baseWind);
worldScene.setVegetationWindField(immutableSpatialWind);
worldScene.setVegetationPresentationTick(gameplayTick);

// New optional comparison/quality switch. True by default:
worldScene.setVegetationHorizonSpatialWind(true);

// Return to Stage 31's identical macro wind for every far card:
worldScene.setVegetationHorizonSpatialWind(false);

Standalone TerraWeaveHorizonScene::setSpatialWindVariation(bool) and spatialWindVariation() expose the same switch, while WorldScene::vegetationHorizonSpatialWind() returns the current choice. The setting is presentation-only and should be set on the render/update owner thread before calling submit(); toggling changes only the shared ShaderGraph program selection, not the mesh, atlas, CPU bake or source revision. First use of a variant may incur the renderer's existing pipeline warm-up cost, not shader recompilation every simulation tick. The default is enabled; if zero wind is configured, neither the old nor new wind graph is active.

Important scope distinction: The Stage 32 field is sampled exactly at the near individual tree and at the Horizon observer. Stage 33's independent far cluster variation is procedural, applied to that sampled macro vector. It is not a direct sample of the upstream PHYSIS field at every far cluster, and therefore is designed to make a 1–12 km treeline feel alive, not to simulate exact kilometre-scale weather boundaries or tornado trajectories. Exact per-cluster PHYSIS fields would require dynamic vertex metadata updates or an extra bounded GPU wind-grid resource, both outside this no-extra-resources mode.

Bounded visual effect: The base Horizon GPU crown displacement strength remains 30% of the near-tree graph; the per-cluster amplitude is at most 1.25 and the graph's sine/gust multiplier is bounded. The current ModelDraw::maxVertexOffsetMetres = 0.65f remains conservative for the validated host wind bounds. GPU cost is extra vertex shader ALU and shared shader variant, not an additional draw or material per cluster. Real performance, frustum bounds, visual appearance in moving cameras, GLSL/Metal shader compilation and accurate material batching have not been tested yet.

Future work: A dedicated QA agent must test this against Stage 31 default/no-wind parity, near-to-far velocity continuity, camera origin rebasing, negative coordinates, region crossfades, seasonal forest alpha cutout, Vulkan/GL/Metal render captures and batching. The Stage 29 impostor model test still assumes the old single-layer geometry and must be migrated during the separate testing phase.

Stage 34 — exact PHYSIS wind per distant Horizon cluster#

Functionality committed; compiler, CTest and GPU validation intentionally deferred. Stage 32 provides a small immutable ForestWindField sourced by PHYSIS/gameplay. Stage 33 gave distant Horizon clusters smooth procedural subvariation around one macro wind, but could not reproduce opposing winds in separate far areas. Stage 34 adds an opt-in direct per-cluster sample of the current field at the cluster's original world-centimetre centre, encoded into the existing Horizon forest vertex colour stream.

Public native interface#

auto field = std::make_shared<terraweave::ForestWindField>();
// Host fills the validated <=64x64 node field from PHYSIS.
field->validate();
worldScene.setVegetationWindField(field); // shared near + far immutable snapshot
worldScene.setVegetationHorizonExactWindField(true); // default: true
worldScene.setVegetationPresentationTick(gameplayTick);

// Revert to the original procedural 2.4km pattern in distant forests:
worldScene.setVegetationHorizonExactWindField(false);
// Or remove the exact PHYSIS field entirely, keeping the uniform fallback:
worldScene.setVegetationWindField({});

TerraWeaveHorizonScene::setExactSpatialWindField(bool), exactSpatialWindField() and the matching WorldScene getter give native games control of this presentation-only mode. WorldScene::setVegetationHorizonSpatialWind(bool) remains the Stage 33 quality switch for procedural variation when an exact field is not active; exact field mode takes precedence if a non-null field is provided. ForestWindState still determines maximum lean, branch flex and tick period; exact sampled X/Z velocity and gust come from sampleForestWindField at each distant cluster position. No game/PHYSIS headers, ECS entities, physics state or simulated weather are introduced into the renderer.

GPU data flow, format and budgets#

  • On initial Horizon GPU publication, captureHorizonForestWindOverlay copies only the existing contiguous forest-card vertex range (not terrain or the entire model) and stores a compact list of exact cluster world coordinates. Both crossed cards of a cluster share one wind sample; 8 vertices per cluster carry the same wind RGB but retain A=0 for bottom and 255 for top. The capture occurs before uploadModel drops CPU mesh data. This CPU shadow moves with active, outgoing crossfade, and cached GPU models in HorizonGpuRegion::forestWind.
  • horizonFieldWindVertexColor packs X/Z signed velocity (each -5000..+5000 cm/s) into RG8 using centered 8-bit quantization with zero wind encoded exactly as byte 128; B8 stores gust 0..1000 permille; A8 remains root-to-crown bend weight. Values are taken from real PHYSIS/grid samples at each cluster centre, subject to roughly 40 cm/s per-channel resolution. This is spatially sampled field fidelity, not lossless precision.
  • horizonExactFieldWindGraph() is one shared first-party GLSL/MSL vertexOffset program. Unlike Stage 33's pseudo-variation, it reconstructs the velocity vector from RG8 and uses the local B8 gust with caller-tick phase/low-frequency variation; the shader uses the existing rigid U0 Inst.anim strength and phase, without a new uniform buffer, texture, pass, atlas or shader per cluster. Terrain retains material slot 0, untouched; only the single forest material slot 1 uses this program.
  • TerraWeaveHorizonScene::setWindField or a change in fallback wind creates a presentation wind-field revision separate from the Horizon terrain/biome source revision. The next update(device,observer) on the owning RHI thread calls refreshForestWindGpu, creating a candidate colour-only update and committing it via one contiguous gfx::Device::updateBuffer write per visible GPU model if and only if the RGB values actually changed. At most 2 MiB of forest-card vertex bytes per update are sent across active and outgoing regions, and at most 2 MiB CPU forest shadow per region are retained. No atlas CPU regeneration, no terrain vertex edit, no cluster topology change, no TWH8 archive write and no weather-tick-driven upload.
  • The GPU update checks canUpdateSharedBuffers(), requires an unpooled independent model VB/IB, and preserves old colours when updates cannot safely be issued. An incomplete refresh does not switch to an exact-field shader: it uses the existing safe macro wind presentation until a full consistent region update completes. Per-region appliedRevision survives LRU/crossfade ownership changes, and stale cached regions refresh on their next render-owner update after adoption. Disabling exact mode or clearing the spatial field restores Stage 33 procedural RGB through the same bounded GPU patch path.
  • HorizonRuntimeStats appends cumulative windOverlayPatchWrites, windOverlayPatchBytes, and live windOverlayPending / exactWindFieldActive indicators. A skipped update is not reported as successful.

The vertex shader's existing local displacement limit is still kCanopyGpuWindMaxOffsetMetres=0.65f, conservative for validated field wind, 30% distant-forest strength and <=1.25 sine/gust multiplier. The near Flora continues sampling the immutable field at every local tree and smoothly blends toward the observer macro wind before the HLOD handoff, while far Horizon can now sample at each statistical distant cluster centre. That near-to-far blend is approximate rather than mathematically identical at the LOD boundary, because Horizon card centroids are not actual near tree identities. Region transitions may briefly render one region with the old macro graph until its deferred patch is safe.

Limitations: 8-bit packing introduces quantization, and field values are sampled at cluster centres (one sample for the two crossing cards), not at every leaf. Shader phase still uses presentation float math and is not bitwise cross-backend deterministic. The CPU shadow adds up to 2 MiB per resident GPU model and requires an RHI-compatible dynamic VB update; mobile backends that cannot update shared buffers stay in safe fallback. Cached models are only patched after activation, not while dormant. gfx::Device::updateBuffer has a void return and cannot report device loss at the callsite. Changing PHYSIS field data requires publishing a fresh immutable shared_ptr<const ForestWindField>; mutating a published shared field is unsupported. No built-in seasonal weather inference, game-network replication or exact turbulence is included.

Testing explicitly deferred at user request: C++ compilation, GLSL+Metal shader compilation, CTest, GPU screenshots, direct PHYSIS/WorldScene run, frame-time measurements, device-loss handling and near/far switching have NOT been executed. Later QA must also migrate Stage29's old single-primitive impostor test assumptions and validate signed-grid samples at negative coordinates, empty/null field, exact zero velocity, quantization bounds, RHI update budget and cached-region restoration before shipping.

Stage 35 — sparse dirty-cluster GPU wind range updates#

Functional source committed; compilation, CTest and GPU execution deferred by request. Stage 34 introduced exact per-cluster spatial wind samples from the host's immutable PHYSIS/game ForestWindField, but transmitted the entire forest-card vertex range to the RHI whenever even one sampled cluster changed. Stage 35 keeps the same public world and Horizon APIs and GPU format, while replacing that coarse update with a bounded sparse dirty-run planner.

Dirty cluster selection and updates#

engine/render/TerraWeaveHorizonWindPatch.h now provides the pure C++ planner:

std::optional<HorizonForestWindUploadPlan> planHorizonForestWindUpload(
    std::span<const render::ModelVertex> oldVertices,
    std::span<const render::ModelVertex> newVertices,
    size_t maxRanges = 8,
    uint32_t fullFallbackPercent = 70);

It compares only the vertex colour attributes of each eight-vertex forest cluster (two crossed cards), because weather updates never change position, normal, UV, indices, or material assignment. Adjacent dirty clusters are coalesced into one contiguous HorizonForestWindUploadRange{firstVertex,vertexCount}. With at most eight separate dirty runs and under 70% of clusters changed, only those ranges are transferred to the existing render::Model::vb by gfx::Device::updateBuffer; there is no GPU allocation, shader permutation or additional render pass.

If more than eight disjoint runs are dirty, or at least 70% of clusters changed, the planner falls back to one complete forest suffix upload. The maximum resident CPU shadow is still 2 MiB per model and the scene's aggregate render-owner update budget remains 2 MiB per update() across both active and outgoing crossfade regions. If the chosen sparse or full plan would exceed the remaining budget or canUpdateSharedBuffers() is false, all writes for that model are deferred and the old safe rendering mode remains. No RHI write occurs before every selected range has been validated; the CPU copy and field revision are committed only after the planned sequence of writes is issued. Like Stage34, the backend's updateBuffer returns void, so a mid-sequence device failure cannot be detected here; engine-level device-loss recovery is still required.

Important consequence: a small changed area can now be updated even when the full forest suffix is larger than the frame's remaining upload budget. For example, after the active region has consumed some budget, an outgoing region with one modified cluster may still be refreshed through one 8-vertex write instead of being repeatedly deferred. The planner reports an empty plan when the new quantized RGB8 values equal the existing values; this advances the applied weather-field revision with zero GPU traffic. A field snapshot can therefore change with no visual or RHI cost if all cluster samples quantize identically.

HorizonForestWindPatchResult now reports ranges, changedClusters, and fullRangeFallback alongside readiness and uploaded byte count. The existing runtime count windOverlayPatchWrites counts region update batches, not individual RHI calls; windOverlayPatchBytes continues recording actual summed bytes. Added HorizonRuntimeStats::windOverlayPatchRanges, windOverlayChangedClusters, windOverlayFullRangeFallbacks, and windOverlayNoopRevisions to distinguish range traffic, changed cluster groups, dense/fragmented fallback, and no-change field revisions.

Compatibility and boundaries#

The algorithm operates on the same already-uploaded Horizon forest primitive, signed world-centimetre PHYSIS sample centres and quantized RG8/B8+A8 wind metadata as Stage34. No changes to WorldScene::setVegetationWindField, setVegetationHorizonExactWindField, season policy, terrain height/near weld/clip geometry, shared atlas or TWH8 format. HorizonGpuRegion still owns its matching compact vertex shadow through LRU and crossfade. Camera ticks alone do not trigger vertex uploads. CPU work still visits/samples all resident clusters to detect which quantized colours changed; only the GPU transfer is sparse. A pathological checkerboard of changed clusters intentionally uses the full-range fallback rather than issuing hundreds of RHI updates.

Validation intentionally deferred: source commits and source inspection only; the new planner and RHI code have not been compiled, CTest has not run, and no Metal/Vulkan/GL backend or PHYSIS integration screenshots/performance data have been obtained. A later tester must verify one dirty cluster, adjacent clusters, eight vs nine disjoint runs, the 70% threshold, negative world coordinates, identical quantized samples, reduced bandwidth, active/outgoing combined budgets, disabled buffer updates, old cached GPU-region reactivation, and full-fallback correctness before release. Stage29's outdated impostor tests also remain pending.

Stage 36 — configurable far-Horizon wind upload quality policy#

engine/world/TerraWeaveWindUploadPolicy.h exposes a small, genre-neutral HorizonWindUploadPolicy for C++ games. Default values retain Stage35 behavior: maxBytesPerUpdate=2*1024*1024 (one combined RHI bandwidth budget for active + outgoing crossfade GPU regions), maxSparseRanges=8 and fullFallbackPercent=70. Set it from the WorldScene owner/render update thread or directly on the optional TerraWeaveHorizonScene:

aiverse::terraweave::HorizonWindUploadPolicy policy;
policy.maxBytesPerUpdate = 256u * 1024u; // e.g. mobile: 256 KiB/update
policy.maxSparseRanges = 4;              // <= 4 runs per region
policy.fullFallbackPercent = 85;         // full range if >=85% dirty
worldScene.setVegetationHorizonWindUploadPolicy(policy);
auto applied = worldScene.vegetationHorizonWindUploadPolicy();

The Horizon native API is setWindUploadPolicy(policy) / windUploadPolicy(). validateHorizonWindUploadPolicy rejects uploads larger than 2 MiB, ranges outside [1,8] or density outside [1,100] before changing the live policy. Upload bytes may be zero: this explicitly pauses changed GPU wind metadata while allowing zero-byte identical-quantization revisions to advance. Raising it later retries the pending revision; no terrain or forest rebake is required.

applyHorizonForestWindOverlay retains its backward-compatible default policy argument after remainingUploadBytes. It now passes the policy's range/density settings to the existing pure planHorizonForestWindUpload and enforces both the caller's remaining budget and the policy's own maximum before any RHI write. The TerraWeaveHorizonScene::refreshForestWindGpu owner-thread updater starts from the configured budget and consumes it across active and outgoing models, active first. A plan that does not fit is deferred as a complete region revision, with the existing macro wind shader fallback.

This is a GPU traffic / update scheduling policy, not a CPU-cache quality selector: each GPU-resident model may still keep up to 2 MiB of forest vertex CPU shadow, and active/cached model residency remains controlled by the existing Horizon settings. There is no new vertex/index/texture allocation, HLOD topology change, shader, PHYSIS dependency, ECS/gameplay data, atlas format or TWH8 archive version. The host must not set the policy concurrently with update/submit.

Limitations: A too-small budget can permanently defer a dense full-suffix update, leaving the safe macro presentation. Fragmentation thresholds and actual RHI cost must be tuned after GPU measurement; gfx::Device::updateBuffer remains void-returning, so multi-range writes have no device-loss atomicity guarantee. Static source inspection and GitHub writes only — CMake, GCC/Clang, CTest, shader compilation and Metal/Vulkan/GL device validation are NOT RUN at the owner's request. PR #24 stays Draft. The tester must exercise default parity, invalid policies, zero budget, pause/retry, sparse-vs-dense switching, and the shared budget with both crossfade models.

Stage 37 — bounded inactive Horizon wind CPU shadow cache#

A Horizon GPU cache hit normally preserves its matching per-region CPU wind overlay (up to 2 MiB of forest vertex data plus cluster centres). The overlay is necessary for Stage35's sparse wind RGB patch planner: the GPU may already contain exact PHYSIS metadata rather than baked procedural colours. Discarding the overlay alone would make future colour comparisons wrong, and there is no guaranteed cross-backend RHI vertex-buffer readback.

Stage37 adds a separate inactive cache CPU budget via <engine/world/TerraWeaveWindShadowCachePolicy.h>:

aiverse::terraweave::HorizonWindShadowCachePolicy cpuPolicy{};
cpuPolicy.maxCachedShadowBytes=1u*1024u*1024u;
worldScene.setVegetationHorizonWindShadowCachePolicy(cpuPolicy);
auto configured=worldScene.vegetationHorizonWindShadowCachePolicy();

Direct scene use: TerraWeaveHorizonScene::setWindShadowCachePolicy(cpuPolicy) and windShadowCachePolicy(). The default is 16 MiB, above the maximum expected three cached wind overlays so pre-Stage37 default residency is preserved. The setting is bounded to 0..16 MiB and validated before publication. 0 prevents inactive GPU cache entries from retaining any CPU wind overlay; it does not disable the active or outgoing transition wind animation, nor does it change Stage36's per-update GPU transfer budget. This budget measures actual vector capacities of forestWind.vertices and forestWind.centersCm, not merely the current logical vector lengths.

HorizonGpuRegionCache::trimWindShadowBytes(device,budget) runs only on the graphics owner thread. When the cached wind shadow capacity exceeds the budget, it retires the whole least-recently-used shadow-bearing cached GPU region, releasing its matching vertex/index/atlas resources through the normal RHI owner path and the associated CPU wind shadow together. It never removes a shadow from a retained GPU model, never touches the active model or current outgoing fade, and does not evict unrelated zero-shadow entries solely to meet this policy. The CPU budget is enforced immediately on retain() and again at the next update(device) after changes to policy or terrain-source revisions. It does not require a new GPU allocation, RHI readback, shader, asset format or CPU worker.

When a camera returns to a region whose entire GPU cache entry was evicted under this budget, the existing AsyncChunkStream prepare/upload path restores the HLOD model and captures a coherent new wind shadow before uploading. It can reuse a matching CPU Horizon bake/asset archive if enabled; otherwise it re-bakes. The old visible proxy is retained while streaming. No stale GPU colour bytes are ever mistaken for a fresh CPU shadow. If the cache entry was not evicted, it retains both GPU and CPU metadata and remains an ordinary instant cache hit. A tight budget trades GPU cache hit rate/re-upload work for bounded dormant CPU shadow memory.

HorizonRuntimeStats::gpuCachedWindShadowBytes reports the current capacity of inactive cached wind metadata, and gpuWindShadowBudgetEvictions cumulatively counts whole GPU cache entries evicted specifically because of this CPU budget (such evictions also increment the preexisting general GPU cache eviction count). Active and outgoing data, general CPU HorizonBake archives, regular vertex patch references, model upload staging and GPU memory are not included in the reported byte count; the feature is intentionally narrow.

Ownership and compatibility: PHYSIS/game still publishes an immutable ForestWindField; no new field sampling, mesh, terrain seams, extra ECS entities, GPU shaders/passes or TWH8 archive version. No genre dependency. Invoke setters on the owning WorldScene/Horizon update thread; a setter cannot safely release RHI buffers itself and applies trimming during the next update(device). Existing HorizonGpuRegionCache::retain calls remain source-compatible via its defaulted final wind-shadow budget.

Limitations / QA: This is whole-cached-region eviction rather than independent compression/reconstruction of a detached CPU shadow, by design: the latter would require a trustworthy GPU readback or full suffix reconstruction that Stage35 does not provide. A zero budget can force a new model/atlas GPU upload on every revisit, and the general CPU bake cache may still consume memory. Compilation, CTest, shader pipelines, Metal/Vulkan/OpenGL reentry screenshots, upload timing and memory measurements are NOT RUN in this feature-first stage. Test LRU oldest-first, zero/small/max budget, no-forest model, transition completion/reversal, source revision invalidation, cold region reentry, active + outgoing preservation and exact/procedural PHYSIS consistency.

Stage 38 — lossless dormant Horizon GPU wind-shadow compression#

Stage37 had to evict a complete GPU cache entry whenever its inactive CPU wind shadow exceeded the configured budget. Stage38 optionally saves dormant CPU memory without evicting the matching GPU region. The wind field, PHYSIS owner, procedural map, material shader and existing RHI GPU buffers remain unchanged.

Use the public Stage37 policy from a native project:

aiverse::terraweave::HorizonWindShadowCachePolicy policy;
policy.maxCachedShadowBytes=2u*1024u*1024u;
policy.compressCachedShadows=true;  // Stage38 optional; default false
worldScene.setVegetationHorizonWindShadowCachePolicy(policy);

This setter stays on the WorldScene owner thread. The optional TerraWeaveHorizonScene::setWindShadowCachePolicy accepts the same POD. The per-update GPU upload policy is separate (HorizonWindUploadPolicy). All default API values preserve Stage37 behavior (compression disabled unless explicitly enabled). The current 0..16 MiB inactive CPU-shadow budget remains valid and unchanged.

Lossless storage: TerraWeaveHorizonWindCompression.h provides packHorizonWindVertexBytes and unpackHorizonWindVertexBytes with a simple bounded bytewise zero-run/literal codec (1..128 bytes per token). It stores raw ModelVertex bytes, including all 32-bit float fields, RGBA wind metadata and joint/weight fields; it never rescales or recomputes geometry or a PHYSIS wind sample. This is memory-only storage inside the process, not a persistent file format. Before packing, the HorizonForestWindOverlay must be intact and already paired with its GPU-resident model. A compressed overlay keeps its signed world-centimetre centersCm, the exact applied wind revision and first vertex offset, and stores packedVertices plus packedVertexCount instead of a full vertex array. Compression is accepted only when the packed vector's actual capacity is lower than the original vertex vector capacity; otherwise the original raw shadow stays untouched.

Cache lifecycle and budget: HorizonGpuRegionCache::retain packs only inactive entries (not the active or outgoing crossfade model). It compresses already-cached entries when the policy is enabled during a live scene, at the next update(device) before budget trimming. windCompressionAttempted prevents repeatedly scanning incompressible entries every frame. The dormant CPU budget now counts the actual capacities of raw vertices, packed bytes and cluster centres. Only if compressed/raw capacity still exceeds the budget will Stage37's whole-region LRU eviction run. There is no GPU upload, new buffer, atlas rebuild or geometry regeneration when a shadow is packed.

On a camera return, HorizonGpuRegionCache::take decodes compressed data to a fresh std::vector<render::ModelVertex> before transferring the already-uploaded GPU model into active ownership. Decode validates token boundaries, exact output byte count, cluster count and the existing 2 MiB forest-vertex limit, publishes only on full success, and leaves GPU bytes untouched. appliedRevision remains unchanged, so Stage35 can compare the exact last-uploaded RGB values if a newer wind snapshot is pending. A malformed stream is handled by the device-aware cache take overload: release the entire corrupted GPU cache entry and use the normal async re-prepare/re-upload path; never present a bogus exact-field shader. Allocation failures are not suppressed and must follow normal host memory-error handling.

New runtime diagnostics: gpuCachedCompressedWindShadows counts the currently dormant compressed regions; gpuWindShadowCompressions and gpuWindShadowRestores count successful pack/unpack operations; gpuWindShadowDecodeFailures counts corrupt dormant cache entries released for a safe re-stream. The Stage37 gpuCachedWindShadowBytes now includes packed byte vector capacities and resident cluster centres. These are accounting counters, not measured GPU speedups.

Limits: zero-run compression may provide no benefit for high-entropy geometry; such entries remain uncompressed and may still be evicted. Per-entry compression and restoration temporarily allocate an additional CPU buffer. The codec preserves exact bytes only within one running process and is not a disk archive or cross-platform data format. WorldScene/Horizon updates, cache transitions and policy writes must be serialized on the owning render thread. The active/outgoing wind shadows, other CPU terrain patch data and HorizonBake caches remain out of Stage37's dormant CPU policy. No TWH8 archive changes.

Validation not run: native CMake/Clang/GCC, CTest, ShaderGraph GLSL/MSL compilation, Metal/Vulkan/GL GPU rendering, measured memory ratios, PHYSIS field update/crossfade tests, fuzz/corruption fixtures and timing benchmarks are deliberately deferred to the independent QA phase. The QA agent should verify the codec's bitwise roundtrip, no-change fallback, zero budget, toggling compression at runtime, malformed stream eviction, camera return without model reupload when compressed, source revision invalidation and mixed packed/raw LRU accounting.

Stage 39 — composable Horizon runtime quality profiles for native projects and manifests#

Stage39 adds presentation/memory quality independently of the earlier HorizonSettings CPU silhouette/terrain geometry quality. The new engine/world/TerraWeaveHorizonPresentationQuality.h defines:

  • HorizonPresentationQualityPreset: BatterySaver, Mobile, Balanced, Desktop.
  • HorizonPresentationPolicy with exactSpatialWindField, spatialWindVariation, HorizonWindUploadPolicy windUpload, and HorizonWindShadowCachePolicy windShadowCache.
  • horizonPresentationPolicyForQuality(preset) and validateHorizonPresentationPolicy(policy), which validates the whole bundle before any partial update to a live world scene.

This is a convenience composition of the existing Stage33/34 shader mode, Stage36 GPU wind update bandwidth, Stage37 inactive CPU shadow budget and Stage38 optional lossless shadow compression. No change to how PHYSIS computes wind, no per-tree ECS state, no added GPU/CPU resource allocation, no atlas/regeneration for applying a preset, and no TWH8 archive version/fingerprint change. Existing setters still work after a preset and can override individual values.

Native project API#

using namespace aiverse::terraweave;
worldScene.setVegetationHorizonPresentationQualityPreset(
    HorizonPresentationQualityPreset::Mobile);

// Fine-tune after preset (or define a fully custom value policy):
auto quality=worldScene.vegetationHorizonPresentationPolicy();
quality.windUpload.maxBytesPerUpdate=256u*1024u;
quality.windShadowCache.maxCachedShadowBytes=2u*1024u*1024u;
worldScene.setVegetationHorizonPresentationPolicy(quality);

The direct renderer owner API is TerraWeaveHorizonScene::setPresentationQualityPreset, setPresentationPolicy, and presentationPolicy(). These calls are owner-thread-only; no concurrent update(device), submit or mutable PHYSIS field sampling. WorldScene updates its existing individual getters when a whole policy is set, so individual setters and aggregate getters remain coherent. The whole-policy setter validates all fields before altering the live Horizon source; errors cannot leave half a preset applied. No name for a "currently active preset" is retained after manual overrides: query the effective policy values instead.

Stage 40 — opt-in host-fed adaptive Horizon presentation quality#

Stage40 adds a bounded runtime presentation controller in engine/world/TerraWeaveHorizonAdaptiveQuality.h. It composes only the four Stage39 profiles (BatterySaver, Mobile, Balanced, Desktop) and the existing Stage33–38 wind shader/bandwidth/CPU-cache policy. The terrain/forest geometry, near seam, atlas, PHYSIS field, native ECS state, GPU resource topology and TWH8 archive remain untouched. The controller is disabled by default and never starts timing a frame by itself.

Inputs, API and integration#

The game or platform host already responsible for framing/presentation supplies measured CPU and/or completed GPU frame times in microseconds, with a monotonically increasing frame index:

using namespace aiverse::terraweave;
HorizonAdaptiveQualityConfig adaptive;
adaptive.enabled=true;
adaptive.minimum=HorizonPresentationQualityPreset::Mobile;
adaptive.maximum=HorizonPresentationQualityPreset::Desktop;
adaptive.initial=HorizonPresentationQualityPreset::Balanced;
adaptive.targetFrameUs=16667;  // 60 Hz frame budget, not a GPU benchmark
worldScene.setVegetationHorizonAdaptiveQualityConfig(adaptive);

// On the scene owner thread, after the host has a frame measurement:
const HorizonFrameTimingSample timing{
    .frameId=completedFrameId,
    .cpuFrameUs=measuredCpuFrameUs,
    .gpuFrameUs=measuredCompletedGpuFrameUs // 0 when unavailable
};
const bool switched=worldScene.submitVegetationHorizonFrameTiming(timing);
auto state=worldScene.vegetationHorizonAdaptiveQualityState();

Direct scene API: TerraWeaveHorizonScene::setAdaptiveQualityConfig(config), adaptiveQualityConfig(), adaptiveQualityState(), submitAdaptiveFrameTiming(timing). A native WorldScene with no Horizon module returns false for submissions. setVegetationHorizonAdaptiveQualityConfig applies the initial profile immediately only when enabling adaptation. Disabling keeps the current profile. Explicit manual calls to the Stage39 whole-policy setter or any of the four existing individual presentation setters disable adaptation rather than fighting the developer's choice. Wind-field publication, normal simulation ticks and camera updates do not count as manual overrides. Re-enabling starts a fresh history.

The engine's gfx Device::gpuFrameMs() can report a backend's last completed GPU duration, but this is not universally implemented and may be delayed. The host must distinguish real completed timing samples from unavailable/stale values and may submit zero for missing GPU or CPU. Stage40 does not synthesize GPU time or equate its own HorizonRuntimeStats::gpuUploadMs with the whole-frame render duration. At least one nonzero actual CPU/GPU frame duration is required; a frame with no measurements is ignored. An individual sample of more than 10 seconds, an out-of-order/duplicate frame index, or disabled adaptation is ignored. Missing frame IDs break continuous streaks, so occasional metrics must not masquerade as sustained FPS degradation. CPU and GPU together use the worst available duration. This is global frame quality control, not evidence that TerraWeave itself caused all CPU/GPU work.

Hysteresis and hard limits#

HorizonAdaptiveQualityConfig defaults: minimum=Mobile, maximum=Desktop, initial=Balanced, targetFrameUs=16667, downgradePercent=115, upgradePercent=80, downgradeFrames=30, upgradeFrames=240, cooldownFrames=240. Consecutive valid frame IDs more than 15% above the target trigger a one-level downgrade after 30 samples. Consecutive samples at least 20% under the target trigger a one-level upgrade after 240 samples. The neutral band clears both streaks. No further switch occurs until at least 240 frame IDs have elapsed since the previous change; neither direction can pass the configured min/max. No elapsed-wall-clock timers or nondeterministic thread callbacks are involved.

Validation rejects quality ranks outside [0,3], reversed bounds, initial outside bounds, target outside 4–100 ms, downgrade threshold outside 101–200%, upgrade outside 25–99%, downgrade streak outside 2–600 frames, upgrade streak outside 2–3600, and cooldown above 36,000 frames. The controller is purely presentation state driven by host measurements and does not belong in authoritative ECS save/replay. advanceHorizonAdaptiveQuality(config,state,sample) is a backend-free deterministic state step for later unit tests.

A Stage39 low-bandwidth profile can postpone dense wind vertex updates and safely show the macro field until later; automatic quality selection does not bypass Stage36 safety checks. Stage 41 — automatic native RTS/FPS frame timing bridge for Horizon adaptive quality#

Stage40 exposed an opt-in, host-fed adaptive Horizon presentation controller, but it did not connect any real game-frame source. Stage41 connects the two existing native game clients to the AIVERSE graphics measurement APIs while respecting async GPU completion and keeping terrain/PHYSIS/ECS independent.

The new reusable header engine/world/TerraWeaveHorizonFrameTimingBridge.h defines terraweave::HorizonFrameTimingBridge. Its begin(gfx::Device&,world::WorldScene*) and finish(WorldScene*,Clock::time_point) are called once around an actual native client frame. begin is only active when worldScene->vegetationHorizonAdaptiveQualityConfig().enabled is true; otherwise it returns false, drops pending samples, and makes no GPU timing requests. It records a monotonically increasing frame ID, requests gfx::Device::timeGpuFrame(tag) after the backend has begun a frame, and polls takeGpuTimings() on following frame callbacks. The signed GPU completion is associated with its ORIGINAL frame ID using a reserved tag prefix, not misreported as the current frame. The adapter also measures real std::chrono::steady_clock CPU callback elapsed time, not simulation dt, game tick duration, gpuUploadMs or the displayed FPS estimate.

The bridge buffers at most a small bounded number of pending frames (eight GPU-lag frames plus the current submission); frames are delivered to WorldScene::submitVegetationHorizonFrameTiming in increasing frame-ID order, after the matching GPU timestamp arrives or its eight-frame wait expires. Unsupported/non-ready/invalid GPU queries automatically submit the real CPU-only sample, with gpuFrameUs=0. Missing/invalid CPU measurements are likewise zero; never invent a nonzero metric. The controller's existing consecutive-frame and hysteresis policies apply to the delivered samples. No glFinish, waitUntilCompleted, new RHI API, CPU/GPU synchronization stall or new per-frame GPU buffer is introduced. deliveredGpuFrames(), deliveredCpuOnlyFrames(), pendingFrames() and lastFrameId() are lightweight adapter diagnostics. All methods run on the owning game/render thread.

Actual game paths now integrated:

  • RTS / composable strategy client: apps/client/GameClient.h/.cpp owns a bridge beside the streamed worldScene_. During an actual streamed-world game frame, after the platform beginFrame but before Horizon scene update/draw, it requests a tagged GPU interval; immediately after the client's UI/render submission it delivers measured CPU work. It discards pending submissions on map loading, world teardown/new match and planet/no streamed-world paths. No network, RTS simulation, camera or UI data model change.
  • FPS client: apps/fps/client.cpp owns the same bridge beside streamedScene. It calls begin just after its existing device.beginFrame, and finish after its existing endPass/endFrame, measuring its entire native FPS callback from entry. Shutdown discards pending samples. No FPS weapon/network/prediction, server tick, collision, terrain or renderer backend change.
  • These calls are automatically dormant for worlds without Horizon or without an explicit adaptiveQuality.enabled=true in the manifest (or native API setting). No CLI switches or external memory allocations at startup are necessary for the disabled case.

Backend timing ownership: AIVERSE already exposes gfx::Device::timeGpuFrame(tag) and takeGpuTimings(); Metal records a tagged command buffer and returns its asynchronously completed GPUStartTime/GPUEndTime interval, while supported GL may use GL_TIME_ELAPSED around its active interval. These report different GPU scope semantics by backend (Metal whole command buffer, GL from query start until end-frame), NOT isolated TerraWeave render time. Unsupported backends return false and the adapter uses CPU-only data. The takeGpuTimings() API destructively drains all ready device timing tags, so the adapter must be the one timing consumer for these game-client Device instances, or future integrations must introduce a shared device timing router rather than independently polling the API from another benchmark. These game clients currently have no other device-tag timing collector in their runtime paths. The FPS client controls its own beginFrame/endFrame; the RTS client is inside the platform's existing outer frame. Do not add a second begin/end call.

Usage: Existing Stage40 manifest remains enough; no new field required:

{
  "terraweaveHorizon": {
    "presentationQuality": "balanced",
    "adaptiveQuality": {
      "enabled": true,
      "minimum": "mobile",
      "maximum": "desktop",
      "targetFrameUs": 16667
    }
  }
}

Once the relevant native client loads such a streamed world, it supplies actual frame measurements automatically. Other custom native projects can instantiate the same bridge and bracket their own frame once, or continue calling WorldScene::submitVegetationHorizonFrameTiming manually. Do not feed samples a second time from the same frame. Future native hosts with multiple consumers of takeGpuTimings should coordinate timing ownership. The adaptive controller still only adjusts Stage39 presentation policy. No Horizon geometry, per-branch wind physics, PHYSIS data, ECS save/replay, TWH8 archive fingerprint, forest CPU bake or async worker revision is affected by measurement.

Limitations/QA: The bridge measures CPU callback duration, which may exclude platform event pump, swap/present wait, vsync and unrelated work outside the callback; GPU query timing covers backend-defined intervals and can be delayed, invalid or unsupported. For GL a timer started at the streamed world phase is not necessarily a whole-frame GPU cost. A consistently overloaded non-TerraWeave subsystem can still cause a global-quality downgrade. There is no proof that altering Horizon presentation quality improves that bottleneck until native profiling. The bridge intentionally falls back to CPU-only after eight frames rather than blocking the render thread. Device timing tags still belong to the device, not this world, so avoid competing consumers.

Source commits exist, but CMake configure/build, C++ compilers, CTest, real Metal/GL/Vulkan runtime, GPU frame tag timing results, FPS/RTS native smoke tests and measured GPU/CPU frame improvements are NOT RUN (feature-first owner request). Later QA must validate CPU-only fallback, asynchronous paired GPU frames, out-of-order/missing/invalid device timing results, 8-frame timeout, map changes, match shutdown, unsupported GPU backend, 60 FPS threshold behavior, as well as conflicts with any other runtime device timer consumers. Stage 42 — generic per-device GPU timing fan-out#

Stage41's RTS/FPS HorizonFrameTimingBridge previously drained the entire gfx::Device::takeGpuTimings() queue. This was incompatible with an editor benchmark or any future Prisma/SpectraFX/VFX timing consumer using the same graphics Device. Stage42 moves all known non-backend GPU query consumers to a shared, genre-independent RHI service: gfx::Device::gpuTimingRouter(), implemented in engine/gfx/GpuTimingRouter.h and described in docs/render/GPU_TIMING_ROUTER.md.

The router registers an independent subscriber for each subsystem, assigns a private GPU raw query tag, maps it back to the consumer's original frame tag at asynchronous completion, and delivers results into isolated bounded subscriber queues. A subscriber's take(subscriber) cannot remove another subscriber's data. Only the router polls the backend's destructive takeGpuTimings(). Unsupported or busy backends can still reject a query; the Stage41 Horizon bridge retains its measured CPU fallback.

For native games no new manifest key is required. Stage41's bridge now uses device.gpuTimingRouter().subscribe/request/poll/take/cancel and unsubscribes at RTS/FPS shutdown. It cancels its own metadata for a GPU frame that exceeded the Stage41 eight-frame timeout. Stage40's adaptive hysteresis and Stage39 profiles are unchanged; CPU/GPU measurements remain asynchronous and backend scoped. This is not an isolated Horizon GPU render-pass timer.

The shared Device router also serves the editor Scene batching benchmark, RenderBench, GeometryBench and the instancing GPU validation preview. These consumers keep original tag semantics but no longer drain one another's completed GPU results. A subsystem may submit its own custom tag or obtain a new subscriber without creating a new graphics Device, render pass, shader or GPU buffer. Public limits: up to 32 subscribers, 64 pending GPU requests across subscribers, and 64 queued completed samples per subscriber. Rejected GPU requests should degrade gracefully to CPU-only timing or no timing; no synchronous fence waits are added. Every caller uses the graphics Device owner thread.

Important backend limit: GL currently supports only one active GL_TIME_ELAPSED request per frame. Independent routing does not imply simultaneous exclusive GPU time measurements; a second request can fail. Metal may return the same whole command-buffer GPU duration under multiple subscribers' tags. Do not interpret these as the independent GPU costs of two rendering features or promise performance gains. Use actual backend device measurements and diagnostics before drawing conclusions.

Feature-first validation: GitHub source read/writes verified; Clang/GCC, CTest, native editor/RTS/FPS/bench runs, Metal/GL/Vulkan concurrency and GPU timings NOT RUN. The independent testing agent must verify interleaved same-device subscribers, tag ownership, cancel/unsubscribe, queue overflow/rejection, GL busy fallback, Metal completion ordering, device recreation, and teardown. Keep PR #24 Draft. See Stage42 handoff.

Stage 45–46 — bank erosion, excavation, visible roots, plant health and grass patches#

The universal NEREID water framework has been merged from \main\ into \feature/terraweave\ at merge \a56ff765311a8f464a2e180d5dd23e7eacdcb5dd\. NEREID remains the only water ECS/current/renderer owner. TerraWeave adds soil and vegetation reaction, NOT a duplicate water solver. See \docs/nereid/TERRAIN_EROSION.md\ for complete contracts and limitations.

  • \NereidErosion.h\ computes deterministic soil-specific sand/silt/clay/ gravel/rock erosion, suspended sediment, bedrock, root binding and wave energy effects. \NereidShorelineSystems.h\ allows a native ECS game to opt into a persistent per-bank-cell erosion stage AFTER water sampling.
  • \TerraWeaveEarthworks.h\ supports bounded sparse native heightfield excavation/fill with dirty rectangles and replay edits. Flat RTS editor operation \terraweave_excavate\ is undoable and preserves the detailed height/splat layers; other world formats require separate adapters.
  • \TerraWeaveVegetationSoil.h\ provides deterministic \PlantEnvironment\ (age, light, water, nutrients), shrubs with smaller root extent than trees, ground support loss, conditional root geometry, and one stable fall event on loss of support. Grass has no visible roots.
  • \TerraWeaveForestScene\ stores optional sparse per-plant environment overrides/root snapshots. Ordinary generated tree/shrub placements receive stable seeded ages and environments. Natural cliffs can expose roots from the first generation; dynamic excavation/river erosion can expose or undermine them later.
  • \TerraWeaveRootModel.h\ with the existing \ArborForestAdapter\ builds one shared RHI bark root model per species/visibility tier ONLY if roots are exposed. \WorldScene::setVegetationRootStates\ publishes states, and the next regular update uploads any new root tiers on the device owner thread. No per-tree unique GPU model or per-grass-blade ECS entity.
  • \GrassPatch\ represents up to 262144 logical blades as ONE compact cover/age/light/density descriptor. \sampleGrassBlade\ reconstructs age and position from the patch key/seed on demand; erosion changes one coverage value, not thousands of entity states.

Immutable terrain patch LOD#

engine/render/TerraWeaveTerrainLod.h provides appendTerrainPatchLods(model, patch, targetErrorPixels=1.5f) for a CPU model before upload. The native landscape exporter calls it after world-space normal smoothing and tangent generation. The live mutable makeEarthworksTerrainModel path retains its original full-resolution surface and collision by default.

Input must be the complete original patch triangulation on a power-of-two grid (8..128 cells), with matching heights and consistent shared normals/UVs/colors. Skins, animation, morphs, baked-lightmap UVs, uploaded buffers and existing LODs reject. Invalid source input preserves model values. LOD0 vertices/attributes/indices stay exact; three appended alternatives use strides 2, 4 and 8. Each retains all original outer edge segments, so neighbouring tiers join without skirts or edge cracks. For a 129-sample tile the four triangle counts are 32768/8952/2680/1080. Only used vertices are appended for each tier; this adds CPU/GPU asset storage.

Each tier measures maximum vertical deviation against the original piecewise linear surface, including coarse edges crossing fine-grid X, Z and diagonal edges. Its maximum pixel threshold targets the requested error through the shared renderer's conservative projected-size metric, with descending caps 512/256/128. This is a presentation budget, not a collision simplification or a universal guarantee for vertex-displaced geometry. The existing renderer owns camera/shadow selection and opaque spatial crossfade. Both meshes render inside a crossfade band; waiting more frames does not remove that spatial overlap.

Exports retain the existing glTF rtsLods representation and independent shadow LOD policy; catalog tile entries append lods (stride/triangles/errorMetres/ maxPixels). Old readers can ignore these fields. Check terraweave_model, the shared-height export audit, actual per-frame submitted triangles and near/far pixel comparisons. Metal fixture verification does not establish mobile/Vulkan parity or an FPS gain. CPU visual picking/deformed object parity remains a separate editor acceptance task.
