Scripting (Lua)#

Mechanics that the data blocks of rules.json can't express are written as Lua 5.4 scripts in the game folder. Scripts are content: they are read when a match starts, packed into content.rpak like any other file, edited in the editor with hot reload, and the engine never has to be rebuilt.

There are two kinds of scripts:

simulation scriptsview scripts
listed inrules / map "scripts": ["scripts/x.lua"]rules / map "viewScripts": ["scripts/view/x.lua"]
runsinside the deterministic tick, on every machine of a match, in replayson the local machine only, every frame
numbersintegers and fx (fixed point); no floatsnormal Lua numbers
mayread and change the game (game.* actions)read the game, show notices / effects / sounds

A game without "scripts" runs only the engine's standard library (below): no "scripts" system, no budget, identical checksums.

// rules.json
{
  "scripts": ["scripts/rules.lua", "scripts/abilities.lua"],
  "scriptBudget": 1000000,            // optional: VM instructions per tick for all simulation scripts
  "types": {
    "archer": {"abilities": [{"id": "mend", "target": "none", "cooldown": 20, "autocast": true,
                "effects": [{"type": "script", "fn": "chain_heal", "jumps": 3, "amount": 60}]}]}
  }
}

Sample: templates/scripted (Iron and Gold + a war chest, veterans, a scripted chain heal and a custom defeat condition).

A first script#

-- scripts/rules.lua
local util = require("lib.util")            -- scripts/lib/util.lua (only files of the game)

function on_start()                          -- global on_<event> functions are handlers
  state.kills = {}                           -- persistent data lives in `state`
  game.message(0, "Hold the bridge!")        -- 0 = every player
end

-- every 30 seconds the player with the most units gets 50 gold
every(30, function(tick)
  local best, most = nil, -1
  for _, p in ipairs(game.players()) do
    local n = game.count{owner = p, kind = "unit"}
    if game.player_alive(p) and n > most then best, most = p, n end
  end
  if best then game.give(best, "gold", 50) end
end)

on("unit_died", function(e)
  state.kills[e.owner] = (state.kills[e.owner] or 0) + 1
  if state.kills[e.owner] >= 50 then game.defeat(e.owner) end
end)

Determinism rules (simulation scripts)#

Lockstep multiplayer and replays re-run the same scripts on every machine and must get bit-identical results on Windows, macOS, iOS, Android and the web. The engine enforces most of it; the rest is a small contract.

Numbers: integers and fx#

Lua 5.4 has integers and floats. Floats can differ between platforms, so a simulation script never sees one:

  1. Float literals are rejected when a file loads — x * 1.5, 1e3, .5, 0x1p4 give scripts/x.lua:12: float literal 1.5 - use fx("1.5") or an integer.
  2. Float arithmetic raises an error — / and ^ always produce floats in Lua, so 7 / 2, n / 2, 2 ^ 3 fail with "float arithmetic is not allowed in simulation scripts (use fx() numbers, or // for integer division)". Use 7 // 2 (integer division, = 3) or fx(7) / 2 (= 3.5). The guard sits inside the VM (third_party/lua/aiverse_luaconf.h), so it also catches floats made from strings ("1.5" + 1).
  3. Every API function that takes a number accepts only integers or fx; a float gives "got a float - use fx() or integers".

fx is the engine's fixed-point number (Q47.16, engine/core/Fixed.h), the same type all gameplay math uses:

local a = fx(3)              -- 3
local b = fx(3, 4)           -- 0.75  (3 / 4)
local c = fx("1.25")         -- 1.25  (decimal string, parsed with integers only)
local d = a * b + 2          -- fx mixes with integers: + - * / // % unary -
if d >= 4 then ... end       -- < <= > >= work between fx and integers
print(d, tostring(c))        -- "4.25"  (formatted without floats)
fx.sqrt(d) fx.abs(x) fx.min(a, b) fx.max(a, b) fx.lerp(a, b, t)
fx.floor(d) fx.ceil(d) fx.round(d) fx.int(d)   -- -> integers (also d:floor() ...)
fx.is(v)  math.type(v) == "fx"

Pitfall: fx(1) == 1 is false — Lua only calls __eq when both values are tables or userdata. Compare fx with fx (v == fx(1)) or use <, <=, >=.

Values from the game are fx when they can be fractional (positions, hp, resources, time) and integers when they can't (ticks, counts, players, levels, handles). math keeps abs, min, max, floor, ceil, sqrt (→ fx), tointeger, type, maxinteger, mininteger and math.random (simulation RNG: math.random(n), math.random(a, b) integers, math.random() an fx in [0, 1)). tonumber("12") works; tonumber("1.5") is an error (use fx("1.5")).

IEEE floats as bit patterns: f32, f64#

A script that must reproduce another program's floating-point results exactly (a port of a game that simulates in float) keeps each value as its IEEE bit pattern in an integer: binary32 as 0..0xffffffff, binary64 as the signed 64-bit reinterpretation (BitConverter.DoubleToInt64Bits). The f32 and f64 tables do one correctly rounded IEEE operation per call (round to nearest even; NaN results are the canonical quiet NaN 0x7fc00000 / 0x7ff8000000000000), so results are identical on every platform:

f32.add/sub/mul/div(a, b), f32.sqrt(a)binary32 arithmetic
f32.dot2(a, b, c, d)a*b + c*d rounded once (fused two-term dot product)
f32.fromint(i), f32.tof64(a)integer → binary32 (rounded); binary32 → binary64 (exact)
f32.lt/le/eq(a, b)IEEE comparisons (NaN unordered, -0 == +0)
f32.fdot2(a, b, c, d)dot2 of finite operands (a non-finite operand is an error)
f32.sqdist(p, q)fdot2(x, x, y, y) of x = p.x - q.x, y = p.y - q.y (tables with x, y; each difference rounded)
f32.floorint(a)floor as an integer; a finite with |a| < 2^31, otherwise an error
f32.atan2(y, x), f32.sincos(a)binary32 atan2 / sine and cosine: an exact series in 96-bit fixed point rounded once (sticky bit), as an integer-only port computes them; |a| <= 2^33, finite operands, otherwise an error
f32.segment(walkable, burning, owners, w, h, first, second, from, to)four-connected grid walk from point from to to (corner crossings check both cells): true when every cell is inside, walkable[c] == true, not in burning (may be nil) and owned by first or second (may be nil); the crossing parameters are binary32 operations; more than w + h steps is false
f32.cellat(p, w, h)grid cell y*w + x of x = floorint(p.x), y = floorint(p.y), or -1 outside 0..w-1 × 0..h-1
f64.add/sub/mul/div(a, b), f64.sqrt(a), f64.fromint(i), f64.tof32(d), f64.lt/le/eq(a, b)the same for binary64

Arguments must be integers (f32 ones in range), otherwise the call is an error. Both tables exist in simulation and view scripts. (Built on the host's IEEE operations with one operation per call, no FMA contraction and a check of the default floating-point environment: engine/game/ScriptIeee.cpp.)

State: state, game.data(h), not upvalues#

Everything a script remembers between ticks must be in the global table state, in an entity's own table game.data(h), or in trigger variables (game.set_var). The engine writes them into the simulation canonically (sorted keys) when the world is observed — before a checksum, a rollback snapshot or a save — not after every tick: they are hashed into the checksum (desync detection), copied by rollback snapshots, saved, and read back into the VM when the netcode rewinds or a save is loaded. A tick that only changes Lua tables costs nothing until then.

  • game.data(h) returns the entity's own table (created on first use, gone when the entity dies, kept by transform). Only tables handed out since the last write are serialized again, and only changed ones are re-hashed, so per-unit records belong here, not in one big state table: lua local d = game.data(h) -- {} the first time d.morale = (d.morale or 10) - 1 for _, h in ipairs(game.units{has = "morale"}) do ... end -- entities whose table has the key game.has_data(h, "morale") game.clear_data(h) View scripts get a read-only copy of the stored table. The editor shows these tables too (Inspector «Детали» → «Данные скрипта»; Hierarchy search d:); with game.json editor.hierarchy a key can name the row (label) or group the tree (data:<key>), docs/editor-world-tree.md.
  • Allowed in state and game.data: integers, fx, strings, booleans and nested tables whose keys are integers or strings. A value that can't be stored (function, float, table key, cycle) is left out of the saved state and logged; keep such values out of persistent tables.
  • Globals are read-only after loading: assigning a new global in a handler is an error, reading an undefined one too (typos show up immediately). Define functions and constants at the top level.
  • Don't change file-level local variables from handlers (local count = 0 ... count = count + 1 in a handler): such state isn't part of the snapshot, so a rollback can't restore it. Use state. Constants and helper functions as locals are fine.
  • Don't keep references to state sub-tables or game.data tables in locals across ticks (a rollback replaces them); call game.data(h) again.

Order and randomness#

  • pairs() iterates in sorted key order (booleans, integers, then strings), never in hash order, so loops over tables are deterministic. sorted_pairs is the same function. next is not available (iteration order would leak). Keys of other types can't be iterated with pairs. table.count(t) is the number of entries of t (no walk in key order needed just to count).
  • game.units{...} returns handles sorted by entity index.
  • Randomness only from math.random / game.random (the simulation RNG).
  • tostring never shows addresses ("table", "function"), string.format("%p") is refused.
  • String hashing and table.sort pivots use constant seeds (identical on all machines).
  • Not available: os, io, debug, package, load, loadfile, dofile, collectgarbage, string.dump; setmetatable refuses __gc and __mode (they depend on garbage collection).

Budget and errors#

  • All simulation scripts together get scriptBudget VM instructions per tick (default 1,000,000). An endless loop is stopped with "instruction budget exceeded" — even inside pcall — and the game goes on; handlers that didn't get to run in that tick are skipped once.
  • Any error is logged with file:line (headless output, editor Console and Скрипты windows, MCP play_status.scriptErrors, script_check) and disables that handler for the rest of the match (deterministically: the flag is simulation state). Functions called from data ("fn" of effects and trigger hooks) are disabled the same way.
  • Loading errors (syntax, float literals, a missing file) skip that file; the match still starts.
  • Script cost per tick: aiverse_headless --tick-times FILE writes the wall time of every simulation step (tick microseconds per line).

Routes and the screen#

Maps with routes / screen (docs/game-format.md § Routes): game.can_send(a, b) (an open route joins the two garrisons; always true without routes), game.route_length(a, b) (line 0, nil without a route), game.screen() -> x, z, w, h of the current screen (nil without one), game.on_screen(x, z), and in simulation scripts game.set_screen(x, z) (moves the screen centre, clamped to its bounds).

Grid fields: the field table#

Per-cell layers (fire, water, creep, influence...) defined in rules "fields" run as C++ kernels; scripts read and write them: field.get(id, x, z [, player]), field.set / field.add / field.fill_rect / field.fill_circle, field.sum / field.max / field.count / field.find over a rectangle or disc, and on_field_threshold(id, value, fn [, "rise" | "fall"]) hooks. Values are integers (int fields) or fx (fixed). View scripts get the read-only part. Reference: docs/fields.md.

Data hooks: scripts inside rules#

{"type": "script", "fn": "chain_heal", "jumps": 3, "amount": 60}
  • Ability effect (any effect list: abilities, projectiles, areas, statuses...): fn(ctx) with ctx = {caster, owner, target, x, z, scale, source_type, targets, args} — targets are the handles the effect's filter selected (radius, affects...), args is the effect's JSON. It runs in the scripts phase of the same tick.
  • Trigger action {"type": "script", "fn": "f", ...}: fn(ctx), ctx = {player, unit, x, z, tick, trigger, args}.
  • Trigger condition {"type": "script", "fn": "f", ...}: fn(ctx) returns true / false.

Functions named in data that the scripts don't define are reported when the match loads.

Radius must be 0..64, player must exist (0 clears ownership), and rules.territory must be enabled. Off-map centre returns 0. With connected=true, candidate cells must touch ownership present before this brush call. Uses normal territory events, counters, room invalidation and save/hash state.
game.set_position(unit,x,z)Place a living mobile unit on flat-map ground; returns false for stale handles, structures, water or out-of-map destinations. Stops native movement, clears queued orders and preserves prevPos for frame interpolation. Does not pathfind, avoid other units or test intermediate terrain. The game script chooses legal trajectories.

territory_at, frontier, paint_territory and set_position currently reject planet maps with an explicit error. Queries are available in view scripts; the two mutation methods are not. frontier scans the map: cache its result in state and refresh a few times per second, not once per soldier. Read endpoints and distribute slots by length, then match soldiers to nearby free slots in deterministic handle order. Move a bounded distance per tick; paint only after successful placement. User destinations must originate in regular commands, obtainable through order_target.

local x,z = game.pos(unit)
if game.set_position(unit, x + fx(1,20), z) then
  game.paint_territory(game.owner(unit), x + fx(1,20), z, fx("0.8"), true)
end

Use movement.avoidance: "none" to disable both ORCA and body separation for formations; body radii retain their meaning for range queries. Smooth rendering is optional and independent of simulation: game.json → terrain.territory: {smooth:true, transition:0.2, fill:0.4}. Ownership remains deterministic cell data; the view reconstructs a soft contour and animates it. The view never writes ownership or decides victory.

Validation for this API: aiverse_tests script_territory_brush_frontier_and_placement checks brush counts, overwriting ownership, the connected-brush restriction, frontier segment counts, invalid placement, overlapping units with avoidance:none, and snapshot replay equivalence. The full macOS suite passed 4967 checks. A 3600-tick project battle replay matched all checkpoints. The 78 template/fixture checksum runs retained current HEAD behavior: the checked-in baseline contains duplicate obsolete lastcolony entries and stale planets sums; all six relevant seed results were reproduced with an independently built unmodified fd300f2. The baseline was not rewritten. Metal visuals were inspected; GL/Android/web were not exercised in this change.

Script commands (player input with data)#

A game defines its own player commands in rules; each becomes a button (with hotkey) on the command card of the client and of the editor play-test, can be sent from view scripts and through MCP (play_command with command: "script"), and arrives in the simulation as one generic command (kCmdScript) that the engine validates before the game's handler sees it.

"commands": {
  "rally_cry": { "label": "Rally cry", "hotkey": "Y", "tip": "+25% damage for 10 s",
                 "targets": ["footman", "archer", "tag:infantry"], "cost": { "gold": 25 }, "cooldown": 30 },
  "muster":    { "label": "Muster", "hotkey": "U", "targets": ["footman"], "cooldown": 5,
                 "args": [{ "name": "where", "type": "point" },

                          { "name": "count", "type": "int", "min": 1, "max": 20, "default": 5 }] }
}
function on_command(player, id, args)      -- or per command: "fn": "global_function_name"
  if id == "muster" then game.order(args.units, "move", args.where.x, args.where.z) end
  -- return false: refused (cost and cooldown are not taken)
end

Each player's handlers have their own instruction budget per tick (rules "commandBudget", default 200000): a player who sends endless loops only burns their own commands. game.commands() lists the definitions, game.command_cooldown(p, id) gives the remaining seconds; view scripts send with view.send("muster", {where = {x = 10, z = 12}, pace = "walk", units = {h1, h2}}).

Engine standard library (rule-level mechanics in Lua)#

Part of the engine's own mechanics is written in Lua: engine/game/lua/*.lua, compiled into the engine (embed.cmake turns them into a header, so every platform loads them without file access) and run by every game, before the game's own scripts, in the same deterministic VM. The C++ core keeps everything hot (ECS, commands, movement, pathfinding, avoidance, targeting and weapons, projectiles, vision, hashing, data parsing) and offers aggregate queries and primitives in the low-level rts table (engine/game/ScriptStd.cpp); Lua decides the rules.

modulereplaces (C++)called
victory.lua (std.victory)GameCore::sysVictory"victory" system, every 10 ticks (std.period.victory)
waves.lua (std.waves)GameCore::sysWaves (+ wave objective scan, kept as rts.wave_objective)"waves" system, only in games with waves

Every module is bit-identical to the C++ it replaced: same iteration order (ECS order comes from the C++ helpers), the same Fixed operations (fx metamethods call the engine's Fixed), the same RNG calls. tests/checksums/check.sh compares the checksums of every sample game and of the fixtures in tests/checksums/games (seeds 1-3) with baseline.txt, recorded from the C++ implementation; tests/checksums/perf.py compares two builds (wall time, or exact instruction counts with --ir).

  • Modules run without the instruction budget (engine code) and keep their state in the C++ GameState (hashed and rolled back as before), so a game with no scripts of its own has unchanged checksums.
  • A module schedules itself: std.period.<name> = N (every N ticks; 0 = never in this game).
  • Override: a game replaces a module with scripts/std/<name>.lua listed in its rules "scripts" (same contract: define std.<name>). Its changes are then the game's own rules.
  • Kept in C++ after measuring: the per-player economy pass (upkeep, capacity, income) — it runs over all 256 player slots every tick, and the Lua version cost +50% instructions on ironfront.

Script-driven HUD#

Optional game.json.scriptHud panels bind localized text, numeric counters and choice indices to game.set_var values. Buttons send ordinary player-ability commands; the simulation validates their effects. Shared client/editor evaluator and schema: Script HUD bindings. This API is presentation-only.

Local point-target drags#

view.targeting() returns {ability, x, z, active, overWorld} for the local UI's current player-ability target. Coordinates are world X/Z floats. This is presentation state only: it is neither replicated nor written into the simulation. Use it for allowed-area masks and cursor previews; authoritative validation remains in the command's simulation handler. Client and editor clear it when targeting ends. In mapClick games a drag that started on a map-drag HUD element (drag-to-cast discs) reports ability = "map-drag" with the pointer's ground point while the drag lasts (overWorld: over the map, not over the UI, where a release taps the map); client and the editor's Game window when it plays as in the client (the same GameClient; its touch device profiles send the left button as a finger, so touch is true there as on a phone). A map-drag also reports touch (the drag is a touch, not the mouse) and sx, sy (the pointer in window points). view.set_map_drag_offset(dx, dy) (window points, reset when a map-drag starts) moves the point the drag aims at: the ground point (x, z) and the release tap are taken at the pointer + (dx, dy), while overWorld and the release over the UI stay the pointer's own — e.g. aim above a finger so the target is not under it.

The client data-model callback skill_drag(actionId, progress) starts a point-target HUD drag on mousedown for an enabled action with nonnegative progress (the support button convention). Pair it with support_click(actionId, progress) on click for non-target actions such as rearm. Release over the world submits the command; release over UI, Escape, lost focus, and touch cancellation cancel the gesture. The editor's point-target script HUD buttons use the same press/drag/release flow.

paintLayer:set_opacity(value) clamps finite values to 0..1 without clearing its canvas. Two pairs of layers can retain the previous geometry while animating a new network, avoiding destructive clear/repaint flicker. The existing 16-layer budget still applies.

Camera (view scripts)#

view.camera() returns the host camera {x, z, zoom, pitch, yaw, width, height, ortho}: target on the ground, zoom in the units of game.json "camera" (orthographic: visible view-plane height in world units; perspective: distance), angles in degrees, viewport in framebuffer pixels. view.set_camera{x =, z =, zoom =, pitch =, yaw =} changes any subset after the frame's view scripts (pitch 5..90, zoom > 0, finite values). A game ports its own framing with it (OpenWar: scripts/view/openwar/camera.lua, Unity's ArmyMapView). Presentation only; the client applies it, the editor Game view does not yet. Screen canvas (view scripts)#

view.to_screen(x, z [, y]) returns sx, sy, onScreen: the window point (logical points, top-left origin) of a world point (y = height, default 0) through the host camera; onScreen is false behind the camera or outside the window. A view.set_camera earlier in the same frame is already applied, so a script listed after the camera script projects with the frame's final camera. view.draw(verts [, {image = "ui/x.png", layer = 0}]) adds a triangle list in those window points for this frame only: without image each vertex is x, y, rgba, with image it is x, y, u, v, rgba (uv 0..1 over the image, 0, 0 = its top left; atlases work). rgba is an integer 0xRRGGBBAA. Consecutive calls with the same image and layer share one batch; batches are drawn in ascending layer (call order within a layer) after the world, the particles and the overlays, under the UI documents. A call with a partial triangle, a non-finite number or more than 1048576 vertices a frame raises an error and adds nothing. This is how a game ports a 2D vector board drawn over the 3D map (OpenWar: Unity's ArmyBoard VertexHelper meshes, scripts/view/openwar/board.lua). Client only (the editor Game view does not draw it yet); presentation only. Test: view_to_screen_and_draw_canvas. transform = {xx, xy, yx, yy, ox, oy} maps the batch's points on the host side (x' = ox + x*xx + y*yx, y' = oy + x*xy + y*yy, binary64 in that order, then float like any vertex): a script keeps a batch in its own coordinates (e.g. ground coordinates under an orthographic camera, whose ground-to-screen map is affine: three view.to_screen calls give it) and redraws the same table every frame without rebuilding it when only the camera moves — the result equals the same sum written in Lua. OpenWar's nuclear scorch uses it. Test: view_draw_transform.

view.draw_ground(verts [, {image = "ui/x.png", layer = 0}]) is the world-space counterpart for marks lying on the map: each vertex is x, y, z, rgba (with image: x, y, z, u, v, rgba) in world units (y up, absolute height — put it a few hundredths above the ground). The triangles are drawn inside the 3D scene after the opaque and translucent meshes, depth tested without depth writes and with a small bias towards the camera, so units and buildings standing on a mark hide it (the screen canvas above draws over them). Batches are sorted by layer, then call order; same image and layer merge; one frame only; the texture alpha below .02 is cut (vertex alpha is free). Same limits and errors as view.draw (1048576 vertices a frame). Client only; presentation only (modules/rts/view/GameGroundCanvas.*). OpenWar draws its ground ability areas, railways and nuclear target rings with it, as Unity's ground canvases under the units. Test: view_draw_ground_world_triangles.

A unit type's view can carry a flat ground shadow image drawn through the same ground canvas (layer -1, before the view scripts' draw_ground batches of layer >= 0): "groundShadow": {"image": "ui/shadows/Tank.png", "size": [w, d], "offset": [x, z], "color": [r, g, b, a], "lift": .05, "flip": [u, v]} — size and offset in world units in the model's frame (the drawn model's rotation, without its scale), color multiplies the image (default black at alpha .55), the image's u runs along the model's +x and its top lies towards the model's -z unless flipped. It follows the interpolated position and facing and replaces the default blob of air units. OpenWar ports Unity's footprint sprites (ArmyUnitModelLayer.AttachShadow) with it. Client only (drawn by GameView::drawGround). Test: view_ground_shadow_option.

Entity scale and opacity (view scripts)#

view.entity_parent(child, parent, {x=0,y=0,z=0,yaw=0}) attaches an entity's presentation to another entity's final rendered frame. Offsets are in cells: +X forward, +Y up, +Z right; yaw is in degrees. Nested attachments inherit translation, rotation, tilt and scale. Cycles and non-finite offsets are rejected. view.entity_parent(child, nil) detaches. Native hosts may provide GameScene::entityFrames for physics-driven chassis after their visual update. Children use that same frame rather than independently interpolated simulation positions. This is a presentation-only hierarchy: collision, ownership and simulation positions do not change. Links are cleared with the view and when either entity dies; rebuild them from saved simulation state in view.on_frame after loading a game. Tests: view_entity_parent_frames and view_entity_parent_api.

view.entity_fx(h, fields) overrides how one entity (unit, structure, prop: any handle of game.units) is drawn, on the local machine only:

fieldmeaning (default)

A call with a bad field raises an error and changes nothing. The values follow the entity's interpolated position and facing, its attachments, effect anchors, selection outline (faded with it) and, when it dies, its corpse (death clip / fall / fade) for up to 10 s after it left the simulation; then they are dropped. They apply on every backend (GL / GLSL and Metal share the model shaders: ModelDraw::tint.w, teamGlow = instance draw.w), on planets, and to 2D sprites (scale x = width, y = height, opacity). Scripts that run per frame can also set values every frame from their own clock (OpenWar computes Unity's per-tick curves from the match time it publishes in state). Presentation only: the simulation and its checksum never see them; the headless server has no view scripts. Tests: view_entity_fx_script_api, view_entity_fx_renders_scaled_translucent, view_entity_fx_ground_shadow, view_entity_fx_pitch_roll.

View script budget: every handler call (view.on, view.on_frame, ui.on) has its own budget of 5,000,000 VM instructions (the C functions it calls are not counted), so one heavy handler never starves the others in that frame. A call over the budget is aborted and skipped for that frame (logged ... [view handler skipped once], at most 20 times a handler); the handler is disabled only after 10 calls in a row over the budget (an endless loop, not a spike) or on an error ([view handler disabled ...]). An aborted call may leave its own caches half built, so a script that builds incrementally should publish a cache only once it is whole. ViewScripts::profile() gives the instructions per handler (calls, total, most expensive call, last frame, overruns, disabled) and per frame; AIVERSE_VIEW_PROFILE=file makes the client write it every frame (h <index> <file:line> once per handler, then f <tick> <frame total> <per handler ...>, -1 = disabled), and AIVERSE_SIM_SPEED=s (testing) runs the match s times faster than real time (up to 8*s ticks a frame) so long battles fit a profiling run. Test: view_handler_budget_per_call.

View scripts' log (game.log lines and errors, which disable the failing handler) is kept by the host; with AIVERSE_SCRIPT_LOG=1 the client also prints each line on stdout as [view] t=<tick> ... / [view error] ..., next to the simulation scripts' [script] ... lines (screenshot and capture runs). Hook: ViewScripts::onLog; test view_script_log_callback.

Categorical cell layers#

view.paint_layer{bounds = {x, z, w, h}, cells = {width = W, height = H}, density = 1..4, smooth = .75..2, borderWidth = 0..2, borderColor = {r, g, b [, a]}, outside = id, opacity, lift, landOnly} creates a raster of one id byte per cell (row-major, z rows) drawn as smooth categorical regions: every pixel takes the id with the largest smoothstep-weighted coverage of its 5x5 texel neighbourhood (smooth = falloff in texels), and a border of borderWidth texels is drawn where the coverage of an id crosses one half (2x2 bilinear coverage on low material quality). layer:set_cells(bytes) takes a Lua string of W * H bytes, layer:set_palette{[id] = {r, g, b [, a]}} sets colours (0..1); outside is the id used beyond the raster edge. transparent = id draws that id fully transparent (an overlay raster over another layer, e.g. OpenWar's capture flashes: id 0 empty, the flashed cells white, layer:set_opacity(v) animated per frame); palette alpha is not used (the texel alpha holds the id). density repeats each cell as density x density texels (smoothing and border widths are in texels). One quad per layer, texelFetch on an RGBA8 texture (rgb colour, a id); presentation only. OpenWar draws its ownership raster with it (ArmyMapWorld look).

ground = {scale, strength, flipHeight, team = {min, max}, context = {min, max}, linear, coast = {sea, drop, beach, shallow, earthNear, earthFar, foam}} adds a ground surface (a port of ArmyMapWorld's meadow and coast): land ids in team keep their colour under a world-anchored meadow relief (patches, blots, pale spots; scale = patch size in world units, strength = fine variation), other land ids get the neutral meadow (green / olive / pale), ids in context a faint noise; flipHeight > 0 anchors the noise at y = flipHeight - z (north-up source maps); relief = 1 / 2 replaces the meadow of non-context land with the biome surface (the id colour under broad relief and snow / dune ripples of frequency 8 / 12: ArmyMapWorld ApplyMeadow for ice / desert campaigns), 0 (default) keeps the meadow. With coast, the id sea is water: a static signed shoreline distance (texels, chamfer + 3x3 smoothing, rebuilt only when the sea mask changes) gives a beach rim on land and shallows, a shore shadow, a cliff on the shore facing drop (texture-row direction, -1 = towards -z) and an animated foam line on water (colours 0..1). linear = true runs the surface maths on linear colour (sRGB in and out), as a linear-space Unity project. The value noise uses the desktop sine hash, the mobile hash on low material quality (as the source's ARMY_MOBILE variant). Test: view_paint_layer_ground_options.

Scripted air placement#

game.set_position(unit, x, z) keeps its flat-map, living mobile-unit and in-bounds validation. Air-layer units can be placed over water; other units still require a ground cell. Previous render position is preserved for interpolation, native movement/orders are cleared, and presentation applies the configured flight height. The API does not paint territory or find routes. Covered by script_air_position_over_water, including snapshot replay.

Immutable match seed#

game.seed() returns the configured match seed as a Lua integer (the signed two's-complement representation of the full 64-bit seed). It is available in simulation and view scripts, consumes no RNG values, and is unchanged by rollback. Games can use it for deterministic keyed decisions whose result must not depend on unrelated RNG calls. Store accepted decisions and command identities in state as usual.

Custom grid paths#

game.grid_path(width, height, cells, start, goal [, label]) performs a deterministic native A* query over a custom four-neighbour grid in both sim and view scripts. It does not move units or inspect/change the engine map. Cell IDs are zero-based (z*width+x); cells is a sparse Lua table. Without label, only boolean true is passable. With an integer label, only cells containing exactly that Lua integer are passable (including label 0); missing values are blocked. Metatables are not consulted.

The returned one-based array excludes start and includes goal; unreachable or out-of-range endpoints return nil. An in-range start equal to goal returns an empty array. A blocked start is allowed so a unit can escape newly blocked ground; all subsequent cells, including goal, must be passable. Width/height must be integers in 1..4096 and their product at most 262144; malformed dimensions/tables/labels raise a script error. Costs are integer, ties use remaining Manhattan distance then cell ID. No persistent query cache or state is created: changed masks take effect immediately, and scripts store accepted paths in hashed state as usual. Unit radius, diagonals, height and dynamic avoidance remain the caller's responsibility.

game.grid_sample_segment(width,height,cells,x,z,tx,tz[,label[,margin[,density]]]) checks a fixed-point segment against the same masks/labels. It returns false for out-of-grid endpoints or any blocked sample. The start is excluded, the destination included, and a zero-length segment samples its single point. There are floor(length*density)+1 evenly spaced samples; density defaults to 8 and must be an integer in 1..16, with a 65536-sample cap. Coordinates/margin are integer or fx; margin defaults to zero (allowed 0..4096). A nonzero margin adds four probes at ±margin on each axis per sample. This is a sampled cross footprint, not continuous collision detection or a swept circle/rectangle: narrow diagonal obstacles can be missed. Use it for steering shortcuts only where that sampling model is appropriate. Out-of-grid margin probes block; malformed arguments raise a script error. The query reads raw table entries, has no cache/mutation, and uses the same integer/fx arithmetic in sim/view; native query work is outside Lua instruction counting, so callers must bound query frequency too.

Headless snapshot and save-state verification#

aiverse_headless --project <dir> --max-seconds 35 --verify-restore-at 15 --verify-restore-ticks 200 captures both SimSnapshot and Simulation::serialize() at 15 seconds, advances 200 ticks, then repeats the same interval after snapshot and serialized restoration in the same live VM, and after serialized restoration into a newly initialized simulation/VM. Every tick's simulation checksum must match, and script errors fail the verification. External C++ bot objects are copied along with the verification baseline so their input decisions repeat; ordinary save-state files do not serialize those external controllers. A plain --load bot match can therefore receive different commands and is not by itself a deterministic save/load comparison.

The checker retains normal final state and recording behavior. --record can be replayed normally; verification wall time includes the repeated intervals and is not a normal performance benchmark. Restore ticks must be 1..100000 and fit before the requested match limit. A natural match end shortens the checked interval and the actual count is printed. A match ending before the restore point fails rather than reporting success. Verification cannot be combined with replay/setup-only/path/group benchmark modes. Exit 1 reports failed verification; exit 2 reports invalid configuration or failed setup. tests/check_headless_restore.py <binary> exercises all three restoration paths, tick-zero startup, replay consistency, invalid intervals and a deliberately untracked Lua local that must desynchronize.

This checks identical-input continuation, not arbitrary alternate command histories, cross-platform equivalence, UI/visual state, or migration between game versions. Use targeted game tests for those additional requirements.
