# Процедурное лазание и походка через IK

`surfaceLocomotion` — rig-операция AIVERSE для многоногих персонажей. Она ищет зацепы,
удерживает опорные лапы относительно поверхности, переносит остальные по дуге и ведёт
корпус вдоль поверхности. Поддерживаются пол, стены, потолок и автоматические переходы
через внутренние углы. Число лап — 3..16; каждая использует двухкостную IK-цепь.

Это presentation-контроллер движения **модели**. Он не меняет координаты сущности в
RTS simulation, pathfinding, коллизию gameplay или сохранённое игровое состояние.
C++ host получает предлагаемые position/normal в отчёте и должен отдельно связать
авторитетное движение со своим владельцем состояния. View Lua не получает права
писать в simulation. Нельзя выдавать движение root-кости за сетевой climbing motor.

## Быстрый запуск

```sh
python3 examples/animation/spider_showcase.py /tmp/aiverse-spider
# Создаётся новый проект: models/spider.gltf + spider.bin, animations/spider.json.
AIVERSE_CONTENT=/tmp/aiverse-spider AIVERSE_AUDIO=off AIVERSE_SPLASH=off \
  build/<config>/AiverseGame --map 0 --spectate
```

В редакторе откройте проект, окно **Риг анимации**, загрузите `spider`. Нажмите
«Сначала», чтобы начать путь заново. Модель проходит пол, стену и потолок; камера
предпросмотра следует за корпусом. В скелетном превью показаны поверхности, в статусе —
число опор, переносимых лап и ошибка достижения зацепов. Пример использует `world:false`
и локальные плоскости. Эти тестовые поверхности отображаются в скелетном превью;
в игровом клиенте они являются невидимыми демонстрационными коллайдерами.

## Настройка rig

В меню добавления операции выберите `surfaceLocomotion`. Редактор создаёт поля
контроллера и параметр `velocity`. Заполните `legs` реальными именами костей:

```json
{
  "op":"surfaceLocomotion", "bone":"body", "velocity":"velocity",
  "adhesion":"adhesion", "resetParameter":"reset",
  "clearance":0.5, "bodyRadius":0.2, "probe":0.8,
  "stepDistance":0.18, "stepHeight":0.12, "stepDuration":0.2,
  "turnSpeed":4, "maxSpeed":1, "minSupport":5, "maxSwing":2,
  "world":true,
  "legs":[
    {"hip":"hip0","knee":"knee0","foot":"foot0",
     "home":[-0.8,-0.5,-0.54], "pole":[-0.6,0.3,-0.54]}
  ],
  "obstacles":[], "capsules":[], "collisionIterations":24
}
```

Это фрагмент: добавьте остальные лапы (для указанных minSupport/maxSwing нужно ≥7).
Объявите `parameters: {velocity:[0,0,0.4], adhesion:1, reset:0}` в графе.
Hip должен быть потомком body; knee — прямым ребёнком hip, foot — ребёнком knee.
Цепи разных лап не должны совпадать. Кости нулевой длины запрещены.

| Поле | Смысл |
|---|---|
| `velocity` | Имя vector-параметра скорости в текущих осях корпуса: X вбок, Z вперёд; Y игнорируется |
| `adhesion` | Необязательный scalar; ≤0 отпускает опоры и останавливает мотор |
| `resetParameter` | Необязательный scalar-счётчик; изменение сбрасывает путь и зацепы в исходную позу |
| `clearance` | Расстояние корпуса от поверхности (>0..10) |
| `bodyRadius` | Радиус сферы корпуса, не больше clearance |
| `probe` | Дальность поиска поверхности вокруг желаемой позиции лапы (>0..20) |
| `stepDistance` | Ошибка зацепа относительно home, запускающая перестановку (>0..10) |
| `stepHeight`, `stepDuration` | Высота дуги и длительность шага (>0..5) |
| `turnSpeed` | Максимальная скорость выравнивания корпуса, рад/с (>0..20) |
| `maxSpeed` | Ограничение скорости (>0..20) |
| `minSupport`, `maxSwing` | Минимум опор и максимум лап в переносе; сумма ≤числа лап |
| `home`, `pole` | Точки в локальных осях body; default выводится из bind pose |
| `followSurface` | Перенос корпуса движением и вращением опоры; default true |
| `world`, `obstacles` | Запросы окружения и локальные plane/box/sphere, как у contacts full-body IK |
| `capsules`, `collisionIterations` | Необязательная коррекция коллизий лап через FullBodyIK (1..64 итерации) |

Длины и скорости задаются в единицах модели. Host transform поддерживает положительный
равномерный масштаб. Не используйте negative/nonuniform scale костей для этого rig.
Параметры походки редактируются в инспекторе; изменение определения перекомпилирует
rig и сбрасывает его состояние. Сохранение/apply и undo/redo используют обычный asset.

## Как работает движение

1. При инициализации лучи находят поверхности под home каждой лапы.
2. Опорные лапы удерживают мировые зацепы. Исчезновение поверхности или смена ID
   отпускает контакт. Потерянная лапа возвращается через фазу переноса, если остаётся
   достаточно других опор; без достаточной опоры мотор останавливается.
3. Корпус движется в касательной плоскости и поддерживает clearance. Передний луч
   обнаруживает стену/потолок; локальное направление вперёд поворачивается вместе с
   нормалью корпуса. Смена нормали ограничена turnSpeed.
4. Приоритет получает лапа с наибольшим отклонением от home. При равенстве используется
   стабильная циклическая очередь. Новая точка должна быть достижима цепью.
5. Лапа переносится по дуге; при приземлении поверхность и её ID проверяются снова.
   За кадр начинается не более одного шага, одновременно — не больше maxSwing.
6. TwoBoneIK вычисляет суставы. Если заданы capsules, FullBodyIK корректирует коллизии,
   сохраняя цели лап и фиксируя корпус. Остаточные ошибки не скрываются.

`adhesion` означает заданную игрой способность удерживаться на любой ориентации:
это не моделирование силы сцепления, трения или динамики падения. После полного
отрыва используйте reset для повторного захвата либо передайте управление падению.
Мотор не ищет маршрут по уровню. Обход внешних кромок, прыжки через разрывы,
деформируемые поверхности, CCD и self-collision требуют отдельного расширения.

## C++

```cpp
using namespace aiverse::render;
AnimationParameters parameters;
parameters.set("velocity", float3{0,0,0.4f});
parameters.set("adhesion", 1.f);
parameters.set("reset", 0.f);
auto controller = SurfaceLocomotion::compile(model, unitJson, parameters);
SurfaceLocomotionState state; // отдельный на персонажа
parameters.environment = environment; // AnimationEnvironment, world queries
// Каждый кадр сначала восстановить входную pose из bind/клипа:
controller->solve(model, parameters, pose, dt, state);
auto report = state.report;
```

`state.report`: active, attached, supports, stepping, footError, penetration,
position, normal. Position и normal в мировых координатах; ошибки — в model units.
Attached требует достаточно опор, ошибку лап ≤0.05 и проникновение ≤0.01.
Получив неподходящий результат, host выбирает остановку/отрыв/другую позу.

В AnimationGraphInstance вызывайте `update(dt)` один раз за кадр, затем `evaluate()`.
Повторная evaluate не запускает шаги повторно. AnimationRigState хранит pendingTime и
индивидуальные состояния; прямой пользователь AnimationRig задаёт pendingTime перед
execute. Шаг ограничен 0.1 с, лишнее время после паузы отбрасывается. Переход состояния,
смена графа и reset отпускают старые зацепы. Частичный weight может нарушать контакты;
отчёт учитывает вес самой операции, но последующие узлы/общий crossfade могут изменить
позу. Размещайте locomotion последним узлом; Lua post-evaluate после него также меняет
результат. Отчёт нескольких контроллеров возвращает первый активный: обычно нужен один.

`AnimationEnvironment` предоставляет raycast и sphereContact, modelToWorld. Точки и
нормали запросов — мировые, ID поверхности стабилен (младшие 63 бита). Raycast должен
возвращать ближайшее пересечение с нормалью наружу, включая стены/потолок. В RtsView
плоских карт используются terrain и ориентированные bounds отдельных mesh primitives объектов. Для точной геометрии задайте
`RtsView::setAnimationEnvironment`; для прямого C++ — parameters.environment.
Существующий адаптер планет автоматически не подключён. Срок жизни callback-данных
должен включать вычисление позы; запросы не изменяют физический/игровой мир.

## Lua

```lua
view.animation_load("spider", "spider")
view.animation_use(actor, "spider")
view.animation(actor, {velocity={0,0,0.4}, adhesion=1, reset=0})
local s = view.animation_status(actor) -- последний обновлённый кадр позы
-- s.climbing, attached, stanceFeet, steppingFeet, footError, climbPenetration
-- s.bodyPosition = {x,y,z}, s.surfaceNormal = {x,y,z}
view.animation(actor, {velocity={0,0,0}}) -- остановка с сохранением зацепов
view.animation(actor, {adhesion=0})      -- отпустить зацепы
view.animation(actor, {adhesion=1,reset=1}) -- повторный захват из входной позы
```

Для Lua графов включите `type.view.programmableAnimation=true`. Полное определение
можно создать таблицей через `view.animation_define`; формат совпадает с JSON.
Физическое окружение задаёт host C++, а Lua может программировать локальные obstacles
и их positionParameter. Lua callback raycast внутри rig не вызывается.

Проверки: `aiverse_animation_tests` проверяет фиксацию, бюджет опор, движение, повороты,
потолок, потерю опор, reset, изоляцию экземпляров, вложенные графы и коллизии.
`aiverse_tests animation_` включает реальное создание/управление/статус через Lua.
Перед публикацией проверьте сгенерированного паука в редакторе и клиенте.

## Динамические объекты сцены

Зацепы динамической опоры сохраняются в её локальной системе координат. При следующем
кадре позиция и нормаль лапы восстанавливаются через текущий transform этой опоры;
корпус получает её перенос и поворот. Цель переносимой лапы также следует за объектом.
Исчезновение поверхности/ID снимает контакт, а не оставляет лапу висеть в воздухе.

В `AnimationEnvironment` добавлен callback:

```cpp
environment->surfaceTransform = [&](uint64_t surface, mat4& localToWorld) {
    // The ID is exactly the ID returned by raycast / sphereContact (without flag bits).
    return collisionWorld.getSurfaceTransform(surface, localToWorld);
};
```

Он должен возвращать текущую матрицу жёсткой опоры, а false — для удалённой поверхности.
Без callback внешний зацеп считается неподвижным в мировых координатах. `followSurface`
по умолчанию true: переносит корпус вместе с опорой. Если авторитетный host уже переносит
самого персонажа вместе с платформой, задайте false, чтобы не применять перенос дважды;
лапы всё равно сохраняют локальные зацепы. Изменение positionParameter локального
препятствия также перемещает его зацепы. Сброс после телепорта задаётся resetParameter.

Автоматический адаптер RtsView строит отдельные ориентированные bounds для примитивов
rigid-модели. У танка корпус, башня, ствол и колёса имеют отдельные поверхности и ID.
Учитываются текущая позиция, lift/pitch/roll/scale, выбранная модель и node transforms;
матрицы анимированных узлов берутся из последнего вычисленного кадра позы. Для поиска
используются до 64 ближайших примитивов около **текущего корпуса паука**, а не места,
где первоначально стояла его gameplay-сущность. Собственная геометрия исключена.

Это ориентированные коллайдеры частей, не точные triangle/skinned-mesh поверхности.
Для деформируемой геометрии или точных физических коллайдеров подключайте запросы
своего collision world. Удалённые и скрытые объекты не становятся невидимыми опорами.
Карта ID/матриц сохраняется на время кадра; устаревший ID не переиспользуется как
зацеп другого объекта. Стандартный адаптер по-прежнему предназначен для плоских карт.

Проверочный проект с настоящим объектом танка:

```sh
python3 examples/animation/spider_showcase.py /tmp/aiverse-spider-tank --dynamic-tank
```

Здесь `spider_scene.json` использует `world:true` и пустой список obstacles — никаких
демонстрационных плоскостей под лапами. Танк перемещается через simulation Lua API
`game.set_position`, а view script дополнительно поднимает и наклоняет его. Паук
начинает на башне и переставляет лапы на ней. Его gameplay-сущность остаётся отдельной:
пример демонстрирует перенос presentation-root динамической опорой.

Во время editor Play агент может запросить `animation_runtime_status` или
`rig_runtime_status`: возвращаются entity ID, attached, stanceFeet, steppingFeet,
footError, penetration, bodyPosition и surfaceNormal. Это реальные результаты
вычисления сцены, а не состояние отдельного asset-превью.
