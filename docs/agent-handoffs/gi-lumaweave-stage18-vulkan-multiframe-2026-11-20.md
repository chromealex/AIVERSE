## Architecture, public API, GPU correctness boundaries

### Vulkan LumaWeaveDirect owner

- Existing Stage13 explicit receiver path remains single-in-flight. Stage18's concurrency applies to **screen-based direct GGX + spatial/temporal resolve** only; the two paths are mutually exclusive while GPU work remains outstanding.
- `LumaWeaveVulkanDirect::kScreenSlotCount=4`, `kMaxPendingScreens=3`, `screenFramesInFlight()` and `canSubmitScreen()` are new opt-in presentation diagnostics/policy. Each `ScreenSlot` owns an independent 16-bit-float sampled+storage RAW image and an independent filtered image at the accepted low resolution. `submitted` is the exact Vulkan frame serial, `submissionOrdinal` disambiguates multiple view submissions inside the same frame, `historyGeneration` and `stamp` capture source/BVH, view/epoch, size and camera, and `readerUntil` records the **last newer submitted frame** still reading this slot as previous history.
- A slot can be written only if it is not pending, is not the currently promoted history slot, and `readerUntil <= completedFrameSerial()`. Merely promoting a newer completed history does NOT free a previous history image that another in-flight compute still reads. This avoids out-of-order/stale texture overwrites during multiple camera/viewport frames without a device-idle stall.
- `poll()` retires all GPU submissions whose actual Vulkan `completedFrameSerial()` has advanced past the captured submitted serial, in chronological order, and promotes the newest eligible denoised history only if the captured history generation remains current and the view/world/source/BVH stamp is nonzero. `invalidateHistory()` discards reusable history but leaves any pending historical GPU input images protected by `readerUntil`. A failed denoise dispatch presents only the current RAW image, never stale old history.
- Unchanged full `LumaWeaveRegistry` snapshots and byte-identical BVH data with the same revision are read-only no-ops even if previous frames are in flight. Different generations/packets remain rejected while GPU readers exist; no CPU/GPU source-buffer reallocation while pending.
- `encodedOutput(exactFrameSerial)` is valid only for the same active Vulkan command-buffer frame immediately after compute/image barriers. `completedOutput()` remains conservative and invalid while **any** GPU submission is pending. `shutdown()` refuses releasing handles until every raw/filtered and borrowed GPU reader has retired.

### PostProcess receiver ownership and route selection

- `LumaWeaveVulkanPostProcess` maintains exactly four full-resolution `ReceiverSlot` sets. Each set owns the actual opaque material/color, material depth, world normal/roughness, surface depth and HDR compositing depth images. Assignment occurs on `scenePass` before existing Renderer3D material and surface receiver passes. A slot's `retireSerial` is the enclosing device frame; the slot cannot be resized, rewritten or destroyed until its real Vulkan GPU frame fence completes. This protects textures even if a filtered Direct frame is skipped after capture or a different viewport runs.
- `canAcquireFrame(viewW,viewH)` is a **read-only** driver preflight: Vulkan Direct must have a free screen output slot, a free frame receiver slot, a real active GPU frame serial and sufficient worst-case receiver memory budget. `kMaxReceiverRingBytes=512 MiB`; larger simultaneous full-resolution rings select raster fallback before changing the one-writer point-light route. The hard admission cap models 2×RGBA16F + 3×depth per pixel × 4 slots, not measured GPU VRAM or FPS.
- The existing Renderer3D and PostFx paths remain unchanged: the selected Vulkan PostProcess still asks for material/surface captures of actual opaque geometry and depth, dispatches screen-space BVH shadowed GGX from them after the HDR scene is drawn, and composites ONE material-reflected DIRECT term into HDR before the normal downstream tonemap. All source/geometry/receiver coverage opt-in flags remain required. No double direct/indirect/baked accumulation is introduced.
- The VulkanDevice RHI already uses a two-frame-in-flight command-buffer/fence ring; the owner supports at most THREE pending logical output frames (and four history/output slots) but real GPU overlap may be ≤2 on the existing backend due to slot-fence waiting. The bounded API is future-proof for larger RHI queue depths, not a GPU performance promise.
