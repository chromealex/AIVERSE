# AIVERSE PHYSIS

PHYSIS — **независимая от жанра** симуляция природы для AIVERSE. Погода, локальные климатические зоны, мокрая почва, снегопад, огонь, мелкое затопление и интенсивность землетрясений являются авторитетным состоянием ECS. Она **не** связана с FPS/RTS и ни с каким рендерером.

## Быстрая интеграция для любой нативной игры на C++

```cpp
#include "engine/physis/PhysisIntegration.h"
void MyGame::setup(aiverse::Simulation& sim, const aiverse::Json&, const aiverse::Json&) {
    aiverse::physis::InstallOptions options;
    options.climate.seed = sim.config().seed;
    options.climate.width = 32;
    options.climate.height = 32;
    options.enableDisasters = true;
    options.enableStorms = true;        // optional hurricane/tornado update
    options.enableForces = true;        // optional ECS ForceReceiver/ForceOutput pass
    options.enableWindZones = true;     // persist WindZone/WindShelter when used
    options.enableGravityFields = true; // persist GravityField/GravitySettings when used
    // When NEREID owns water: options.floodMode = physis::FloodMode::ExternalAuthority;
    aiverse::physis::install(sim, options);
}

// After committed Simulation::step() (e.g. from renderer/editor):
aiverse::physis::forEachPresentationCell(sim.world(), [](const auto& cell) {
    // cell.environment.wind / wetness / rain / snow / ice
    // cell.hasHazards ? cell.hazards.fire / waterDepth / quake : none
});
```

Все значения, используемые геймплеем, имеют тип `Fixed`; никогда не передавайте float-значения представления обратно в PHYSIS. Мировые координаты PHYSIS — статическая сетка X/Z; `Cell::elevation` назначает проект. Для собственного планирования хоста выбирайте ровно один вариант `advance` на тик. Чтобы зарегистрировать PHYSIS в обобщённой Simulation и постоянной ECS-схеме, выполняйте установку в `GameModule::setup`.

## Текущие границы реализации

- Реализованная эволюция погоды — детерминированная упрощённая локальная модель, а не физически точная модель глобальной циркуляции; сезоны — треугольные волны, у фронтов манхэттенское затухание.
- Огонь, затопление и землетрясения — базовые механики ECS; ураган/торнадо — упрощённые детерминированные поля вихря/воздействия, **а не** полноценные решатели атмосферной CFD, вулканов, лавин, жидкостей, деформации рельефа или разрушений.
- Отклики вроде множителя сцепления и потенциала стока — это коэффициенты/подсказки. **Необязательный, явный** адаптер `engine/physics/PhysisBox3D.h` теперь применяет поправки ветра/гравитации PHYSIS к динамическим телам `physics::Scene`, но автоматическое подключение к Scene/WorldScene не реализовано. С 2026-11-21 включаемый по желанию **хост представления природы** управляет травой TerraWeave (горение/ветер), огнём/дымом SpectraFX, светом и звуком огня, а редактор показывает его вживую без запуска игры (см. «Хост представления природы» ниже); нативный игровой клиент пока не подключён.
- Обновление сетки сейчас последовательное и немедленное; не заявляйте параллельное выполнение заданий, стриминг, распределённую погоду или эффективную пропускную способность на миллионах ячеек.
- В этой сессии коннектора не было выполнено никакой проверки компиляцией/CTest/CI; **наличие кода не означает, что тесты пройдены**.

## Смерчи: огонь, вода и земля (2026-11-22) — `engine/physis/PhysisTornadoNature.h`

Смерч из данных карты (`"physis.tornadoes"`, `engine/physis/PhysisTornado.h`) теперь взаимодействует
с поверхностью под собой. Рядом с `TornadoTrack` у него лежит `TornadoNature` (в C++ — перегрузка
`spawnTornado(world, storm, track, nature)`, значения по умолчанию — `defaultTornadoNature(tickRate)`).
Смерч без `TornadoNature` работает ровно как раньше.

| Что | Как |
|---|---|
| Затягивание огня | Каждый тик вихрь забирает долю `fire.intake` (в секунду) × интенсивность × вес кольца от огня каждой клетки PHYSIS под ядром и кольцом (1 в ядре, до 0 у внешнего радиуса). Забранный огонь (в горящих м²) копится в `heat`, тепло теряет `fire.decay` в секунду. Огненность `fireness = heat / (heat + fire.halfHeat)` от 0 до 1: растёт с количеством и силой огня, маленький огонь даёт слабый эффект, без огня гаснет. |
| Задувание или огненный вихрь | В ядре огонь гасится долей `fire.suppression × (1 − fireness)`: пыльный смерч по-прежнему задувает огонь, огненный — нет. Раздувание в кольце умножается на `1 + fireness`. |
| Поджог | Клетка с топливом под вихрем (не над водой) загорается с вероятностью `fire.ignite × fireness × интенсивность × вес` в секунду, сила `fire.igniteStrength × fireness`. Случайные числа — из собственного состояния RNG смерча, клетки в порядке сетки. |
| Угли | Огненный вихрь выбрасывает `fire.embersPerSecond × fireness` углей в секунду (до `fire.maxEmbers`), их несёт ветер вихря, они сгорают в воздухе за `fire.emberLifeSeconds` или поджигают клетку с топливом, куда упали, с вероятностью `fire.emberIgnite`. |
| Урон от жара | Сущности с `Transform` внутри внешнего радиуса получают `fire.heatDamagePerSecond × fireness × интенсивность` через `GameModule::environmentDamage`, сверх урона от ветра. |
| Вода | Открытая вода — из `GameModule::environmentWaterDepth(sim, x, z)` (новый хук, по умолчанию 0; общее ядро игр отдаёт 2 м для клеток `~` и 0,3 м для бродов `=`) или из локального паводка PHYSIS. Вихрь над водой, если 3 из 5 точек (центр и 4 на кольце ядра) глубже `surface.waterThresholdMeters`. |
| Сухопутный смерч над водой | Теряет `surface.waterDecay` силы в секунду, на суше восстанавливает `surface.recover`; на нуле распадается (интенсивность 0, шторм выключен). Огненность гасится долей `fire.quench` в секунду, поджога и углей нет. |
| Водяной смерч | `surface: "auto"` решает в первый активный тик: родился над водой — водяной (`"water"` / `"land"` задают тип явно). Его ветер — `surface.spoutStrength` от заданного, он поднимает брызги, а на суше теряет `surface.spoutLandDecay` в секунду и распадается за секунды. |
| Размытие земли | На суше ядро (до 1,5 радиуса ядра) снимает `erosion.rate × интенсивность²` метров в секунду в поле `GroundScourField` (клетки `physis.scourCellMeters`, по умолчанию 1 м, разреженно, до 65536 клеток) до глубины `erosion.maxDepthMeters`. Грунт (до `erosion.capacityCubicMeters`) уносится и оседает долей `erosion.deposit` в секунду в полосе 1,5–2,5 радиуса ядра. Над водой унесённый грунт тонет. `groundScourAt(world, x, z)` — изменение в метрах (минус — размыто). |

Данные внутри смерча (всё в секунду, всё необязательно):

```json
"fire": { "suppression": 0.8, "fanning": 0.5,
          "intake": 0.6, "decay": 0.2, "halfHeat": 50, "quench": 1.5,
          "ignite": 0.4, "igniteStrength": 0.6,
          "embersPerSecond": 6, "maxEmbers": 48, "emberLifeSeconds": 8, "emberIgnite": 0.5,
          "heatDamagePerSecond": 3 },              // "whirl": false — только старое задувание
"surface": { "kind": "auto", "waterThresholdMeters": 0.2, "waterDecay": 0.08, "recover": 0.1,
             "spoutStrength": 0.55, "spoutLandDecay": 0.6 },   // или "auto" / "land" / "water"
"erosion": { "rate": 0.04, "maxDepthMeters": 0.6, "deposit": 0.25, "capacityCubicMeters": 40 }  // или false
```

Новые ключи блока `physis` для сцен с огнём: `"ignitions"` (очаги пожара: центр, радиус, сила, время;
нужен `enableDisasters`), `"disasterConfig"` (коэффициенты огня за тик, 0..1), `"noFuelOnWater": true`
(клетки над водой без топлива), `"scourCellMeters"`.

Детерминизм и сохранения: только Fixed, смерчи по номеру сущности, клетки по сетке, угли в порядке
создания, свой RNG. `physis.tornado_nature`, `physis.tornado_embers`, `physis.ground_scour` входят в
сохранение и хэш и регистрируются только при включённых смерчах: карты без смерчей не меняются.

Отображение (`PhysisNatureRuntime`, подключать ничего не нужно): пыльная воронка тускнеет по мере
роста огненности или брызг; `physis_tornado_fire` — вращающийся столб пламени, свечение, свет огня,
искры, дым сверху (прозрачность по огненности, 6 уровней: новый уровень запускает новый эмиттер, старый
догорает); `physis_tornado_spray` — столб водяной взвеси, каскад брызг у основания, кольца на воде;
`physis_tornado_ember` — угли; `physis_tornado_scar` — тёмный след размытой земли. Звук: второй голос
`physis_firestorm_loop` (рёв пламени), громкость по огненности × интенсивности. Пример —
`templates/skirmish/maps/firestorm_valley.json` («Огненная долина»). Тесты: `physis_firestorm`,
`physis_tornado_cues`.

Текстуры огня: встроенные `physis_flame`, `physis_smoke` и `physis_tornado_fire` используют
флипбуки с лицензией CC0 из бесплатных VFX-последовательностей Unity (`engine/assets/fx/physis/`,
источник, лицензия и обработка — в `LICENSE-fx.txt`). Языки пламени на земле — небольшие
вертикальные аддитивные квады, стоящие основанием на земле; в вихре языки вытянуты вдоль спирали;
дым — альфа-блендинг. Проект может заменить любой эффект своим `fx/<имя>.json`.

Ограничения: размытие — данные PHYSIS и след на земле; сетка рельефа, высоты и навигация не
опускаются (адаптера к TerraWeave Earthworks пока нет). Кольца на воде — частицы SpectraFX, не волны
поверхности NEREID. Огонь горит по клеткам PHYSIS (крупная сетка).

## Межсистемное владение (PHYSIS / NEREID / TerraWeave)

PHYSIS владеет **климатом/погодой, полями природных событий и политиками сил/гравитации окружения**, но никогда не самой интеграцией твёрдых тел Box3D. NEREID (агент воды,
черновой PR #23) владеет геометрией водоёмов, течением, контактами и плавучестью; TerraWeave
(агент Terra, черновой PR #24) владеет рельефом, биомами, растительностью и рендерингом суши.
Используйте план включаемой по желанию интеграции хоста и точное преобразование метров/сантиметров из
[`physis-nereid-terraweave-integration.md`](physis-nereid-terraweave-integration.md).
Существующий прототип мелкого затопления PHYSIS **не** является авторитетной
заменой воде NEREID. Когда хост использует NEREID как владельца воды,
задайте `InstallOptions::floodMode = FloodMode::ExternalAuthority`: PHYSIS продолжает
обновлять огонь и землетрясения, но обнуляет/пропускает свою локальную глубину мелкого затопления. Этот
включаемый переключатель написан и покрыт тестами; межмодульная интеграция NEREID/Terra
и реальная проверка сборкой/CTest остаются в ожидании.

Это **только контракт проектирования**. Интеграция Terra/NEREID, рендеринг и
межсистемные тесты остаются НЕ РЕАЛИЗОВАННЫМИ / НЕ ЗАПУЩЕННЫМИ в этой ветке.

## Ветер, гравитация, штормы и необязательное использование Box3D

```cpp
#include "engine/physis/PhysisIntegration.h"
#include "engine/physics/PhysisBox3D.h" // link AIVERSE::physics, if enabled

// During GameModule::setup:
aiverse::physis::InstallOptions options;
options.enableStorms = true;
options.enableForces = true; // only if generic ECS force outputs are required
aiverse::physis::install(sim, options);

aiverse::physis::StormEvent tornado;
tornado.kind = aiverse::physis::StormKind::Tornado;
tornado.center = {10_fx, 0_fx, 10_fx};
tornado.eyeRadiusMeters = 20_fx;
tornado.outerRadiusMeters = 150_fx;
tornado.heightMeters = 500_fx;
sim.world().add<aiverse::physis::StormEvent>(sim.world().create(), tornado);

// Physics owner: after the authoritative PHYSIS tick, just before Box3D Scene::step:
for (aiverse::physics::BodyHandle body : optedInBodies)
    aiverse::physics::applyPhysisToBody(box3dScene, sim.world(), body);
box3dScene.step();
```

Авторитетные типы PHYSIS — это ECS-данные `Fixed`. Внешний мост Box3D
преобразует значения из float Box3D и обратно **только на этой границе**. Box3D уже применяет
гравитацию сцены; адаптер применяет **разность гравитации** и сопротивление ветра через
`Scene::applyForce`, а не вторую силу гравитации. **Не** применяйте дополнительно
`ForceResult::totalForce` к тому же телу Box3D. Включаемым по желанию кинематическим контроллерам
персонажей нужна отдельная интеграция передвижения; здесь не переопределяется ни жёстко заданный скаляр
`CharacterParams::gravity`, ни нативное движение Body.

Физика включается по желанию. Запустите `./run-tests.sh --filter '^physis_'` и, с
`-DAIVERSE_ENABLE_PHYSICS=ON`, CTest `physis_box3d` и существующие
`physics_runtime` / `physics_scene`. Эти тесты **написаны, но НЕ ЗАПУЩЕНЫ**.
В текущей реализации нет физически точных ураганов по Навье–Стоксу, разрушения обломками
от торнадо, решателей орбит N тел, деформации растительности Terra ветром или нагонной волны.

## Комбинированная read-only выборка (для Terra, VFX, Physics и инструментов)

```cpp
#include "engine/physis/PhysisPresentation.h"

aiverse::physis::NatureFieldSample nature;
if (aiverse::physis::sampleNatureField(sim.world(), queryPosition, nature)) {
    const auto wind = nature.windVelocity; // 3D Fixed metres per second
    const auto gravity = nature.gravityAcceleration; // m/s squared
    if (nature.hasAtmosphere) {
        const auto rain = nature.environment.rain; // normalized, not water volume
        const auto snow = nature.environment.snowpack;
    }
    if (nature.hasHazards) {
        const auto fire = nature.hazards.fire;
    }
}
```

`sampleNatureField` не изменяет состояние и возвращает true, когда PHYSIS инициализирован,
в том числе за пределами климатической сетки; `hasAtmosphere`/`hasHazards` показывают,
какие данные сетки присутствуют. Функция не зависит от заголовков TerraWeave/NEREID/Box3D.
Terra должна потреблять её как read-only оверлей окружения и
отдельно выбирать каноническую линию воды NEREID. **Ни производственный адаптер Terra/NEREID,
ни сцена рендеринга пока не подключены.**

**Совместимость сохранений:** `Simulation::PersistentEcsRegistry` хранит строгий
список ID схем. Поэтому PHYSIS **по умолчанию не регистрирует** новые необязательные
типы компонентов ветра/гравитации/штормов/сил. Задайте
`InstallOptions.enableWindZones` для сохранения `WindZone`/`WindShelter`,
`enableGravityFields` для `GravityField`/`GravitySettings`,
`enableStorms` для `StormEvent` и `enableForces` для
`ForceReceiver`/`ForceOutput`. Существующий реестр сохранений этапов 1–5 остаётся
неизменным, когда эти переключатели выключены. **Переключение флагов в существующей сохранённой
игре меняет манифест и не является автоматической миграцией сохранения.** Сохранение и
загрузка должны использовать одинаковые флаги функций. Тесты написаны, но не запущены.

## Диагностический растр для потребителей редактора/отладки

```cpp
#include "engine/physis/PhysisDiagnostics.h"
aiverse::physis::DiagnosticRequest query;
query.originX = -16; query.originZ = -16;
query.width = 32; query.height = 32;
query.stride = 1;
query.layer = aiverse::physis::DiagnosticLayer::WindSpeedMetersPerSecond;
aiverse::physis::DiagnosticRaster raster;
if (aiverse::physis::sampleDiagnosticRaster(sim.world(), query, raster)) {
    // raster.rawValues = Fixed::raw data; raster.valid = inside PHYSIS grid
    // diagnosticNormalized(raster, i) = 0..65535 for view/shader coloring
}
```

Диагностический API работает **только на CPU и только на чтение**: он не рисует
оверлей в Scene, не меняет физику, не изменяет авторитетный World и не выбирает
воду NEREID. Он ограничен 65 536 ячейками на запрос; отсутствующие ячейки климата/опасностей
помечаются как невалидные, а не заменяются вводящими в заблуждение нулями. `LocalFloodMeters`
показывает только автономное мелкое затопление PHYSIS (NEREID остаётся
каноническим владельцем воды). Будущий адаптер редактора может загрузить/использовать возвращённый
растр как тепловую карту, без зависимости PHYSIS от рендерера. Тесты
написаны, но ещё не подтверждены нативным CTest/CI.

## Индексированное чтение для больших сеансов диагностической выборки или выборки редактора

Стандартные `windAt`, `gravityAt`, `stormsAt`, `sampleNatureField`
и `sampleDiagnosticRaster` остаются доступными и не требуют индекса.
Для повторяющихся запросов к **одному зафиксированному снимку ECS** используйте включаемый по желанию
пространственный ускоритель:

```cpp
#include "engine/physis/PhysisSpatialIndex.h"
#include "engine/physis/PhysisDiagnostics.h"
aiverse::physis::FieldSpatialIndex index(sim.world(),
    {.tileSizeMeters = 256, .maxTilesPerVolume = 1024});

// Stable values pinned to the index's original COW world snapshot:
aiverse::physis::NatureFieldSample nature;
if (index.sample(queryPosition, nature)) {
    const auto wind = nature.windVelocity;
    const auto gravity = nature.gravityAcceleration;
}

// Optional accelerated debug raster for vector field layers:
aiverse::physis::DiagnosticRequest request;
request.layer = aiverse::physis::DiagnosticLayer::WindSpeedMetersPerSecond;
aiverse::physis::DiagnosticRaster image;
aiverse::physis::sampleDiagnosticRasterIndexed(index, request, image);
```

Временный индекс группирует ограниченные зоны ветра, укрытия, поля гравитации и
объёмы штормов в **тайлы по мировым метрам X/Z**; окончательные 3D-проверки дальности/времени
остаются в канонической политике PHYSIS. Глобальная гравитация и очень большие объёмы
используют ограниченный резервный список; обход кандидатов сохраняет порядок вставки/пула ECS
для накопления с фиксированной точкой и разрешения равенства по приоритету гравитации.

Стройте индекс один раз после авторитетного зафиксированного тика, используйте для множества запросов и
**перестраивайте после изменения ECS, отката или движения климата/штормов**. Это
не постоянное состояние, не пространственный индекс для симуляции климатических WeatherFront/QuakeEvent
и не планировщик стриминга мира/заданий. Индекс хранит
copy-on-write снимок World; удержание в памяти многих исторических индексов может
сохранять COW-страницы и увеличивать потребление памяти. Нативного бенчмарка или успешной компиляции
пока не наблюдалось; тесты существуют только в исходниках, пока не запущен CTest.

## Этап 17 — отладочное окно PHYSIS в редакторе

Редактор теперь автоматически находит `apps/editor/windows/PhysisWindow.cpp`
через существующий реестр `AIVERSE_EDITOR_WINDOW` и glob в CMake.
Откройте **Мир → PHYSIS · Природа**. Панель **по умолчанию закрыта**.

- Когда в активном `Editor::sim()` инициализирован PHYSIS, панель показывает
  read-only растр живого ECS-состояния PHYSIS: климата, поверхности, ветра, гравитации, огня,
  землетрясения или автономного локального затопления. Панель **не вызывает

  карт или Box3D и не внедряет специфичные для жанра сущности сцены.
- Когда текущая игра не инициализирует PHYSIS, пользователь может явно
  создать в панели отдельный **демо-World PHYSIS** с ветром, торнадо,
  локальной гравитацией, климатическим градиентом и огнём. Элементы управления шагом демо продвигают
  только этот независимый World; они не изменяют текущий проект.
- Можно настраивать слои, палитру, шаг выборки, размер окна (8..64 ячеек PHYSIS) и
  центр по X/Z. Щелчок по ячейке показывает значение с фиксированной точкой,
  координаты климатической ячейки, 3D-ветер и гравитацию. Панель обводит
  активные зоны ветра (W), радиусы штормов (T/H) и объёмы гравитации (G).
- Скалярные слои погоды/опасностей читают ECS напрямую; слои ветра/гравитации используют
  временный `FieldSpatialIndex`. Обновление происходит при смене источника,
  новом тике или явном **Обновить данные**. Правки/откаты, сохраняющие
  тот же тик, требуют ручного обновления, пока в редакторе не появятся токены ревизий.

`PhysisDebugPalette.h` предоставляет `DebugColor`, `DebugPalette`,
`debugGradient` и `diagnosticColor` для нативных CPU-инструментов. Это
относится только к представлению; значения цветов никогда не передаются обратно в симуляцию.

**Ещё не реализовано:** оверлей в мировом пространстве, проецируемый в камеру Scene,
живой Inspector агента PHYSIS для редактирования данных компонентов, общая автоустановка PHYSIS
из `game.json` проекта, GPU-текстуры и интеграция с частицами/VFX.
Окно — настоящая реализация GUI редактора, но **нативная компиляция редактора,
снимок экрана UI и ручные щелчки НЕ проверены**.
Используйте `./run-tests.sh --filter '^physis_'` и соберите/протестируйте редактор на macOS,
прежде чем утверждать, что он работает от начала до конца.


## Этап 18 — настоящий оверлей во вьюпорте Scene и редактирование карты в Inspector

После слияния с main `810feba70f01cdc35003ac80ea8486f39dc16049`
в Scene редактора добавлена включаемая по желанию прозрачная тепловая карта, рисуемая **в настоящем 3D-
виде** и проецируемая через существующий `RTSCamera::worldToScreen`, а также
кольца в мировом пространстве для WindZone, StormEvent и GravityField. Элементы управления на панели инструментов
находятся в **Мир → PHYSIS · Природа**; переключатель **Показать 3D-оверлей
в «Сцене»**. Это оверлей представления ImGui (не затенённая 3D-геометрия и не
коллизия Box3D), и он использует те же read-only `DiagnosticRaster` и ограниченный
`FieldSpatialIndex`. Он только читает живую симуляцию, в которой уже есть PHYSIS;
он не устанавливает и не продвигает тиками активный мир.

Общий Inspector в **Свойства карты** теперь включает раздел PHYSIS:
**Создать PHYSIS**, **Настроить PHYSIS**, **Удалить PHYSIS**. В диалоге редактирования
есть структурированные элементы управления для начала/размеров сетки, сида, температуры,
влажности, включения ветра/гравитации/штормов/бедствий/сил и внешнего владельца воды NEREID,
а также вкладка расширенного JSON. **Применить** проверяет весь
черновик и вызывает `MapDoc::beginEdit` только один раз; существующие Ctrl+Z/Ctrl+Shift+Z
Undo/Redo общие с другими правками карты. Невалидные JSON/настройки отклоняются
без изменения карты. Поддерживаются и обычный формат карт, и формат FPS через
`apps/editor/PhysisAuthoring.h`; специфичная для жанра логика ECS не добавляется.

Редактируемые данные хранятся под ключом JSON уровня карты `"physis"`.
Это **декларация, а не автоматическая запись в живой ECS**. Любой нативный проект
может включить её из своего обобщённого `GameModule::setup`:

```cpp
#include "engine/physis/PhysisProjectConfig.h"

void MyGame::setup(aiverse::Simulation& sim,
                   const aiverse::Json& rules,
                   const aiverse::Json& map) {
    aiverse::physis::installFromMap(sim, map);
}
```

`installFromMap` возвращает false для отсутствующей/отключённой конфигурации; иначе
она строго читает параметры сетки/климата и флаги, регистрирует сохранение и
одну систему PHYSIS с фиксированным тиком и возвращает true. Она не устанавливается
автоматически в модули RTS, FPS или других жанров. Начиная с **этапа 19**, проверенные отдельные массивы `windZones`, `storms` и
`gravityFields` **порождаются** детерминированно, если явно
установлены через `installFromMap`. Каждому ассету нужен стабильный уникальный `id`;
нативный импортёр сортирует ID перед созданием сущностей ECS, в том числе между
типами полей. Неизвестные дополнительные ключи сохраняются редактором, но не
интерпретируются импортёром. Авторитетными во время выполнения являются сущности ECS;
ID из редактируемого JSON сам по себе не является сохраняемым компонентом.

**Проверка:** исходные тесты этапа 18 `physis_scene_geometry`,
`physis_project_config` и `physis_authoring` написаны и зарегистрированы
в CTest. Последнему нужен `aiverse_editor_core`, и он запускается в сборке редактора /
единой сборке; headless CI, сфокусированный на PHYSIS, компилирует два других.
Проверка Studio обновлена, чтобы собирать/запускать все три и компилировать редактор.
На момент этого коммита **сборка C++, CTest, CI PASS, взаимодействие с редактором и
снимок экрана НЕ ЗАПУЩЕНЫ / НЕ ПРОВЕРЕНЫ**. См. отдельный handoff этапа 18.

## Этап 19 — индивидуально редактируемые WindZone, StormEvent и GravityField

Откройте **Мир → PHYSIS · Природа**. Раздел **PHYSIS — объекты и Gizmo**
позволяет создавать, перечислять, выбирать и удалять зоны ветра, торнадо/ураганы и
локальные гравитационные поля, даже когда игра не запущена. Существующий
Inspector MapProps показывает положение, радиус и зависящие от типа
свойства выбранного поля PHYSIS. Расширенный JSON-редактор поля сохраняет неизвестные
дополнительные свойства, но отклоняет невалидные типизированные значения.

Включите **Редактировать маркеры мышью** и щёлкните маркер W/S/G в Scene:
перетаскивайте в плоскости X/Z; удерживайте **Shift**, чтобы менять Y. Первое действительное
перемещение вызывает `MapDoc::beginEdit`, последующие перемещения вызывают
`MapDoc::touched`; **одно перетаскивание целиком равно одной операции Undo/Redo**.
Когда редактор маркеров выключен, обычный независимый от жанра выбор мышью в Scene
работает как прежде. Маркер PHYSIS — ассет документа карты, **а не** фальшивый живой
выбор ECS и не тело Box3D. Активный игровой `World` не изменяется.

Пример карты:

```json
{
  "physis": {
    "enabled": true,
    "grid": {"originX": -4, "originZ": -4, "width": 8,
             "height": 8, "cellSizeMeters": 100, "seed": 8},
    "climate": {"baseTemperature": 15, "baseHumidity": 0.5},
    "enableStorms": true,
    "enableWindZones": true,
    "enableGravityFields": true,
    "floodMode": "ExternalAuthority",
    "windZones": [
      {"id": "wind-1", "center": [0,0,0],
       "radiusMeters": 120, "velocity": [15,0,0], "gustAmplitude": 3}
    ],
    "storms": [
      {"id": "storm-1", "kind": "Tornado", "center": [50,0,25],
       "eyeRadiusMeters": 20, "outerRadiusMeters": 150,
       "heightMeters": 300, "tangentialWind": 45, "updraft": 25}
    ],
    "gravityFields": [
      {"id": "gravity-1", "mode": "Uniform", "center": [0,0,0],
       "radiusMeters": 200, "acceleration": [0,-2,0],
       "overrideBaseline": true}
    ]
  }
}
```

Обобщённая нативная `installFromMap(sim, map)` проверяет все ассеты **до**
изменения состояния World PHYSIS и порождает компоненты в лексикографическом порядке
стабильных ID; для непустых массивов требуются соответствующие флаги `enableWindZones`, `enableStorms`,
`enableGravityFields`, чтобы схемы сохранения
совпадали. Стабильные ID — это ключи редактирования, и они **не добавляются в
схему постоянных компонентов ECS**; для согласованного воспроизведения требуются детерминированный порядок порождения и неизменный
манифест карты/сохранения. Правки редактируемого
JSON карты не перезагружают на лету живой PHYSIS и не перепривязывают существующие сущности ECS.

Ядро библиотеки не зависит от редактора/жанров/Box3D/NEREID/TerraWeave.
Вода остаётся во владении NEREID; задание `ExternalAuthority` отключает
отдельное мелкое затопление PHYSIS. Динамика Box3D по-прежнему остаётся необязательным независимым
потребителем сил PHYSIS.

**Добавлены исходные тесты:** `physis_field_assets` и (только для editor_core)
`physis_field_authoring`, а также расширенная фикстура сохранения `physis_project_config`.
Зарегистрированы в сфокусированном Linux/macOS CI PHYSIS и в CI Studio.
**Нативная компиляция, CTest и графическая проверка перетаскивания НЕ ЗАПУЩЕНЫ / НЕ ПРОВЕРЕНЫ.**

## Этап 20 — гизмо радиуса полей в Scene и привязка к метровой сетке

Общая панель полей PHYSIS теперь предлагает инструменты **Move** и **Radius**. Когда
активен инструмент радиуса, выберите поле карты W/S/G и перетащите спроецированный в мир
маркер радиуса (на периметре +X). Scene рисует внешний
периметр X/Z выбранного поля. Редактирование радиуса шторма меняет `outerRadiusMeters`, но никогда
не радиус глаза; канонический нативный валидатор отклоняет невалидные пары глаз/внешний радиус.
Гизмо использует луч камеры редактора к плоскости земли на текущей высоте Y поля;
оно не меняет 3D-высоту и не выполняет полный объёмный 3D-поворот.

**Привязка к сетке** включается по желанию и имеет настраиваемый шаг 0,25..1000 метров.
Move привязывает X/Y/Z к сетке относительно начала координат мира; привязка радиуса применяется до
проверки границ. Отрицательные координаты используют симметричное округление. При перетаскивании по высоте
сохраняется непривязанный накопитель, чтобы не терять движение мыши меньше шага сетки. Настройки
привязки — предпочтения сеанса редактора, а не дополнительные поля схемы карты/ECS.
Каждое успешное перетаскивание перемещения/изменения размера остаётся **одной транзакцией Undo/Redo в MapDoc**.
Живой World PHYSIS, тело Box3D, вода NEREID или состояние игрового жанра не редактируются.

В существующем `tests/physis_field_authoring_test.cpp` есть новые исходные фикстуры
для Undo/Redo радиуса, невалидных радиусов, пустых правок и привязки отрицательных координат.
**Нативная сборка, CTest и графическая проверка редактора остаются НЕ ЗАПУЩЕННЫМИ.** См.
`docs/agent-handoffs/physis-editor-gizmo-snapping-resize-2026-11-18.md`.


## Этап 21 — множественный выбор, групповые преобразования, дублирование и удаление

Общая панель полей PHYSIS и оверлей маркеров в Scene поддерживают одновременный выбор нескольких
редактируемых полей:
- Ctrl/Shift-щелчок по маркерам W/S/G или строкам переключает принадлежность к выбору.
  Обычный щелчок по строке переключает на одно поле. Также доступны «Выбрать всё» / «Снять
  выбор».
- В режиме Move перетащите уже выбранный маркер, чтобы сдвинуть весь набор
  на ОДНО И ТО ЖЕ смещение по X/Z или Shift+Y. Щёлкнутый элемент становится активной опорной точкой,
  не исключая другие элементы. Относительные смещения сохраняются между
  WindZone, StormEvent и GravityField. Необязательная привязка влияет только на опорную точку,
  а не на каждое поле по отдельности. Завершённые оси сохраняются при смене режима Shift.
- «Дублировать выбранное» копирует полные JSON-объекты полей, включая пользовательские
  свойства, и выделяет детерминированные бесконфликтные ASCII-ID
  (например, wind-1-copy, wind-1-copy-2). Смещение копии по умолчанию +5 м
  и по X, и по Z или выбранный шаг привязки, когда она включена. Новые копии
  становятся выбранными. «Удалить выбранное» атомарно для всех типов полей.
- Групповое дублирование, групповое удаление и перетаскивание всей группы каждое добавляют ОДНО
  действие Undo в MapDoc. Невалидные групповые выборы или позиции вне диапазона
  отклоняются без частичных обновлений. Гизмо Radius редактирует только текущее
  активное поле; редактирование отдельных свойств требует выбора одного поля.

Функции C++ только для редактирования в apps/editor/PhysisAuthoring.h:
  moveFields(MapDoc&, vector<FieldPosition>, bool firstEdit, string* error)
  duplicateFields(MapDoc&, vector<string> ids, dx, dy, dz, vector<string>& newIds, string* error)
  removeFields(MapDoc&, vector<string> ids, string* error)

Обновления при перетаскивании вычисляют абсолютные цели от начальных позиций, и вся
конфигурация редактирования проверяется перед фиксацией тем же нативным
парсером parseFieldAssets, что и в installFromMap. Нет изменения игрового World,
Box3D, NEREID или TerraWeave и нет изменения схемы сохранения ECS.

Исходные фикстуры для группового Undo/Redo, атомарного отклонения, генерации новых ID,
сохранения пользовательских ключей и полного цикла обычных/FPS-карт находятся в
tests/physis_field_authoring_test.cpp. Нативная сборка, CTest и проверка GUI
НЕ ЗАПУЩЕНЫ. См. docs/agent-handoffs/physis-editor-group-authoring-2026-11-18.md.


### Групповой поворот и равномерный геометрический масштаб (расширение этапа 21)

Выбрав любые поля PHYSIS, задайте **Поворот вокруг Y, град** и
**Масштаб геометрии**, затем **Применить к выбранным**. Центр активного элемента
служит опорной точкой. Обе операции выполняются в одной атомарной транзакции
MapDoc функцией physis_authoring::transformFields. Поворот меняет
расположение по X/Z в мировом пространстве вокруг общей оси Y; равномерный масштаб
меняет смещения по XYZ и пространственные размеры источников (радиус ветра/гравитации;
радиус глаза, внешний радиус и высоту шторма). Скорость/направление ветра,
силы шторма, ускорение гравитации, флаги включения и ID НЕ меняются.
Это сделано намеренно: значения полей не зависят от геометрии.

Нативная проверка всей конфигурации отклоняет невалидную преобразованную позицию,
радиус, высоту или комбинацию источников, оставляя весь исходный
выбор без изменений. Поворот ориентации/курса, неравномерное масштабирование по осям,
гизмо объёмного 3D-поворота и запись в живой ECS не
реализованы. Поворот использует double-арифметику редактора и записывает координаты в метрах
с 3 знаками после запятой; авторитетная среда выполнения по-прежнему читает квантованные входные данные карты Fixed.
Новые фикстуры поворота/масштаба/Undo написаны, но нативный CTest НЕ ЗАПУЩЕН.


## Этап 22 — рамочное выделение в Scene, опорная точка и 3D-манипуляция

В Мир → PHYSIS · Природа включите редактирование мышью и, отдельно, выделение
прямоугольником на пустом месте Scene. Прямоугольник выбирает спроецированные центры W/S/G
(в том числе при обратном перетаскивании), а не целые объёмы источников. Ctrl/Shift
добавляет к выбору. Остальной выбор объектов в Scene остаётся активным, когда инструменты
выключены.

Режимы опорной точки: Active, Average, Bounds Center, World Origin, Custom XYZ.
Этот выбор действует только в течение сеанса; схемы редактируемого ECS/карты не меняются.
Режим Move проецирует оси X/Y/Z и использует RTSCamera::screenRay плюс
ближайшую точку луча к оси (а не смещение на экране), чтобы перемещать группу в мировых метрах.
Решения при параллельности или позади глаза отклоняются. Привязка только опорной точки сохраняет
внутреннее расположение выбранных источников.

Rotate Y даёт горизонтальное золотое кольцо для поворота ПОЗИЦИЙ выбранных источников
вокруг опорной точки. Uniform Scale даёт голубое кольцо и масштабирует
расстояния в группе плюс радиусы полей/высоты штормов, но не скорость ветра, силу
шторма, ускорение гравитации или ориентацию. Компоненты источников
не несут полную 3D-ориентацию; поворот кватернионом по X/Z не подразумевается.
Radius по-прежнему редактирует только активное поле.

Интерактивные рыскание/масштаб используют transformFields с необязательным исходным базовым
JSON и firstEdit. Каждое обновление мыши вычисляется от одной и той же начальной карты,
и первое действительное изменение начинает один Undo в MapDoc; последующие обновления
используют touched. Посторонняя ревизия MapDoc отменяет такое перетаскивание. Все кандидаты
проверяются каноническим нативным парсером перед записью; изменения живого World,
NEREID, TerraWeave, Box3D, FPS или RTS не происходит.

Исходные фикстуры покрывают правила опорной точки, обратный прямоугольник, вырожденность луча/оси
и Undo с замороженной базой. Нативный CTest/проверка редактора НЕ ЗАПУЩЕНЫ; задания GitHub Actions
наблюдались только в очереди. См. handoff этапа 22 в
docs/agent-handoffs/physis-editor-marquee-3d-gizmos-2026-11-18.md.


## Этап 23 — включаемая по желанию авторитетная сверка полей и воспроизведение команд

Новый engine/physis/PhysisFieldRuntime.h связывает существующий чистый
PhysisFieldChangePlan с явным реестром идентичности полей ECS, принадлежащим механизму отката.
В отличие от статической installFromMap, работающей только при запуске, этот необязательный путь
поддерживает замену набора редактируемых источников WindZone, StormEvent и GravityField
на границе команд Simulation. Он намеренно обобщённый и
НЕ зависит от FPS, RTS, Box3D, NEREID, TerraWeave или редактора.

Пример интеграции хоста (выберите уникальный ID команды в собственном модуле):

    constexpr uint16_t kPhysisEdit = 53123;

    void MyGame::setup(Simulation& sim, const Json& rules, const Json& map) {
        if (!physis::installEditableFromMap(sim, map))
            return; // PHYSIS absent or disabled
    }

    void MyGame::applyCommand(Simulation& sim, const Command& cmd) {
        if (cmd.type == kPhysisEdit) {
            // The authoritative server MUST authorize system player=0.
            std::string error;
            (void)physis::applyFieldEditCommand(sim, cmd, kPhysisEdit, &error);
            return;
        }
        // Other genre-independent gameplay commands ...
    }

    // Trusted editor/server-side action; NEVER apply World edits in Scene.
    uint32_t scheduledTick = 0;
    std::string error;
    const bool queued = physis::submitEditableFieldsFromMap(
        sim, editedMap, kPhysisEdit, scheduledTick, &error);

Этот результат постановки в очередь означает лишь, что команда принята к отправке;
авторизующий хост может позже отклонить её при несовпадении ожидаемой ревизии.
Simulation::submit и CommandSink обеспечивают существующий транспорт команд.
Хост должен зарезервировать ID команды, отклонять подделанные системные команды на
входе сети и реализовать показанную выше диспетчеризацию applyCommand. Клиент
не может получить полномочия, просто используя Command.player=0.

Реестр времени выполнения — новый включаемый по желанию постоянный ресурс World с именем
physis.field_runtime (версия 1). Он содержит монотонную ревизию правок,
стабильный редактируемый ID -> (Entity, вид, канонический сериализованный отпечаток).
Поэтому снимок и нативное сохранение в файл сохраняют ту же идентичность и
ревизию; откат восстанавливает обе. Неизменённые поля сохраняют динамическое состояние
времени выполнения (в том числе дрейфующий шторм); отредактированные поля того же вида сохраняют
тот же дескриптор Entity; удалённые источники уничтожаются; смена типа вызывает
Remove+Add с новым поколением Entity. Изменения готовятся на копии
World и фиксируются вместе, поэтому сбои проверки/плана оставляют его
нетронутым. Пустая команда всё равно расходует одну ревизию правок.

Новая необязательная установка включает постоянные схемы компонентов для ВСЕХ трёх
видов полей, чтобы их можно было добавлять/менять тип во время работы сеанса.
Это намеренно меняет строгий манифест сохранения; её нужно включать
и при сохранении, и при загрузке. Существующие installFromMap и сохранения остаются неизменными.
Неявная миграция сохранений не реализована.

Полезная нагрузка правки по сети — пополевой двоичный снимок с ID протокола,
ожидаемой ревизией, отсортированными уникальными источниками и ограничением размера. Она упаковывается в
стандартный Command.args Simulation, поэтому полезная нагрузка должна укладываться в
4096 слов int64 всего (до 32760 байт, одно слово зарезервировано под длину).
Более крупные наборы замены отклоняются; атомарное разбиение на несколько команд
НЕ реализовано. Фактическое максимальное число полей зависит от закодированных
свойств источников, а не от ограничения автономного парсера в 2048 полей. Поскольку
передаётся полный набор источников, правки с устаревшими ревизиями отклоняются,
а не перезаписывают параллельные изменения.

На этом этапе редактируемы только коллекции редактируемых полей. Изменения
настроек климатической сетки отклоняются submitEditableFieldsFromMap, а
изменения общей политики затопления/бедствий НЕ перезагружаются на лету.
Пока нет автоматической регистрации команд Inspector карты -> активный GameModule,
слоя сетевой авторизации или подтверждения в GUI; нативный хост
должен явно включить это и использовать свою существующую систему команд.

Цель CTest physis_field_runtime содержит исходные фикстуры для кодирования и
полного цикла сетевой Command, обновлений с сохранением идентичности, добавления/удаления,
замены типа, воспроизведения, отката SimSnapshot, постоянного сохранения/загрузки,
конфликта ревизий, невалидных сетевых полезных нагрузок, отклонения слишком больших команд
и планирования тиков в Simulation::submit. Эти тесты написаны, но
НЕ скомпилированы и НЕ запущены. См. отдельный handoff этапа 23 в
docs/agent-handoffs/physis-field-runtime-reconciliation-2026-11-18.md.


## Этап 24 — живые запросы из редактора, проверка и аутентифицированный допуск на сервере

Окно PHYSIS теперь содержит панель Live Editing. Её кнопка применения к работающей
симуляции включается по желанию и работает только для ЛОКАЛЬНОЙ Simulation с
ресурсом FieldRuntimeState, без CommandSink и с GameModule, который явно
реализует aiverse::editor::physis_live::FieldEditHost. Ни открытие
карты PHYSIS, ни независимый отладочный World не дают полномочий. Обычные
хосты RTS/FPS НЕ включаются автоматически.

Хост проекта предоставляет уникальный ненулевой тип команды, явно разрешает
локальные правки из редактора, вызывает installEditableFromMap из setup и диспетчеризует
applyFieldEditCommand из GameModule::applyCommand. Редактор готовит
полный типизированный набор источников из MapDoc::toJson и отправляет его через
Simulation::submit. Он НИКОГДА не меняет живой World напрямую.

Панель сообщает: Unavailable, Idle, Queued, Applied, Conflict или Rejected.
Queued НЕ означает Applied. Applied требует ожидаемой ревизии реестра ECS
и совпадения стабильных редактируемых отпечатков; статус аннулируется, когда
другая правка заменяет значения или откат восстанавливает более раннее состояние.
Отброшенный обработчик или конфликтующая ревизия сообщаются, а не скрываются.

Для УДАЛЁННЫХ серверов physis::admitAuthorizedFieldEdit — обобщённый
хук допуска только для сервера. Серверный транспорт предоставляет принципала, выведенного из
его аутентифицированного соединения, и обратный вызов ACL, проверяет недоверенный
запрос и заново кодирует новую системную Command от player-0 через Simulation::
submit. Поле player или роль, переданные клиентом, никогда не являются аутентификацией.
Существующий ретранслятор боевого сервера AIVERSE применяет собственный белый список
слотов ввода. Он НЕ подключается автоматически к административным командам PHYSIS.

Реальный проект должен добавить свой аутентифицированный транспорт редактора/администратора, правильную
серверную диспетчеризацию и независимый удалённый протокол ACK/NACK. Сетевая
Simulation с CommandSink намеренно отключена в локальной панели,
вместо того чтобы внедрять команды player-0 через обычный клиентский ввод.
Сервис редактор-сервер между машинами на этом этапе не поставляется.

Файлы: apps/editor/PhysisLiveEdit.h (без ImGui; возможности + статус),
apps/editor/windows/PhysisWindow.cpp (панель),
engine/physis/PhysisFieldRuntime.h (политика доверенного допуска) и
engine/sim/Simulation.h (константный метод доступа к модулю).
Нет новых схем PHYSIS по умолчанию и зависимостей от воды/рельефа/Box3D/жанров.
CTest physis_live_edit написан и зарегистрирован в CMake/workflow PHYSIS/Studio;
нативная компиляция и тесты НЕ ЗАПУЩЕНЫ. См.
docs/agent-handoffs/physis-editor-live-edit-2026-11-18.md.


## Этап 25 — надёжное удалённое редактирование PHYSIS

У PHYSIS есть отдельный версионированный административный протокол поверх существующего net::Conn
(надёжный UDP, WebSocket или loopback). Это НЕ обычный InputFrame игрока
и не обход сетевой авторизации AIVERSE.

Файлы протокола времени выполнения: engine/physis/PhysisRemoteProtocol.h,
PhysisRemoteServer.h и PhysisRemoteClient.h. Клиент использует уникальные
ID экземпляра/запроса, ограниченные повторы, Query перед повторной отправкой при переподключении
и явные квитанции Unknown/Queued/Applied/Rejected/Conflict/Denied.
Сервер хранит ограниченный идемпотентный кэш квитанций по аутентифицированному
принципалу+экземпляру клиента+ID запроса и отклоняет повторное использование ID с изменённой
полезной нагрузкой. Одновременно в очереди может быть только одна новая правка PHYSIS. Applied
сообщается ТОЛЬКО после запланированного тика Simulation и совпадения ревизии ECS
FieldRuntimeState плюс отпечатков источников. Queued != Applied.

Хост сервера должен вызывать ServerGateway::poll на отдельном
АУТЕНТИФИЦИРОВАННОМ net::Conn администратора/редактора, предоставлять доверенного принципала
соединения и обратные вызовы ACL, а затем вызывать ServerGateway::observe после
авторитетных тиков Simulation. Он должен зарезервировать тип команды PHYSIS
и диспетчеризовать applyFieldEditCommand этапа 23 в GameModule::applyCommand.
Никакая управляемая клиентом команда player=0 не считается доверенной.

apps/editor/PhysisRemoteEdit.h::EditorLink принимает только подключённое хостом
уже аутентифицированное соединение. Окно PHYSIS показывает удалённый
статус, подтверждённую ревизию, ID запроса и элементы обновления/отправки/повтора.
Хост должен обеспечить реальную аутентификацию/учётные данные транспорта;
редактор не открывает анонимный привилегированный сокет.
Маршрут локального запуска игры этапа 24 остаётся отдельным.

Ограничения на передачу: кадр протокола 40 KiB и типизированная полезная нагрузка Command.args
этапа 23 в 32760 байт. Крупные многочастные атомарные загрузки пока НЕ
реализованы. Кэш сервера хранится В ПАМЯТИ, поэтому после перезапуска сервера
старая квитанция может стать Unknown, а клиент может увидеть Conflict.
Проверки ревизий предотвращают двойные эффекты, но устойчивое к сбоям
ACK ровно-один-раз требует постоянного журнала. Незавершённые клиентские
запросы можно экспортировать/восстанавливать, включая исходные ID, но
хост должен сохранять счётчики запросов или менять экземпляр клиента.

Отдельный включаемый по желанию реестр PhysisRuntimeFields.h/TrackedFromMap
от другого агента не заменяет эту среду выполнения FieldRuntimeState этапа 23.
Не устанавливайте оба. Нет изменений в устаревшей installFromMap,
полномочиях FPS/RTS, NEREID Water, TerraWeave или Box3D.
CTest physis_remote_edit добавлен в CI PHYSIS и Studio, включая
исходные тесты настоящего loopback net::Conn, переподключения, ACL, дубликатов, джиттера и
отката. НАТИВНАЯ СБОРКА И ТЕСТЫ НЕ ЗАПУЩЕНЫ. Handoff:
docs/agent-handoffs/physis-remote-edit-reliable-2026-11-19.md.


## Этап 26 — устойчивый административный журнал и аутентифицированная loopback-точка

Удалённое редактирование PHYSIS теперь включает файловый журнал квитанций с упреждающей записью
и включаемый по желанию нативный административный WebSocket-слушатель только на loopback. Существующие
FieldRuntimeState / installEditableFromMap / GameModule::applyCommand /
applyFieldEditCommand остаются каноническим источником полномочий редактора. Отдельный путь
RuntimeFieldRegistry / FieldCommandHost, параллельно введённый
другими агентами, НЕ подключён к этому редактору и не должен включаться
одновременно.

Новые обобщённые файлы движка:
- engine/physis/PhysisRemoteJournal.h: FileJournal хранит ограниченный
  снимок с контрольной суммой кэша запросов/квитанций сервера в приватном каталоге,
  принадлежащем оператору. Записи включают доверенного принципала,
  экземпляр клиента и ID запроса, точные исходные байты правки, типизированные редактируемые
  отпечатки, ожидаемую ревизию, запланированный тик и статус.
  Используется непредсказуемое эксклюзивное создание временного файла, flush/
  fsync записи, атомарное переименование/замена и синхронизация каталога POSIX. Неверная
  контрольная сумма или отсутствие прав отклоняют запуск, а не молча
  отбрасывают историю. Путём журнала может владеть только ОДИН серверный процесс.
- engine/physis/PhysisAdminAuth.h: версионированное рукопожатие challenge/proof для администратора
  с новым случайным nonce и ключевым BLAKE2b. Общий секрет не
  передаётся. Строка принципала привязана к доказательству, проверяется через предоставленный хостом
  поиск ключа, затем через серверный ACL и зарезервированный тип команды PHYSIS.
  Переданные клиентом player=0 / токены экземпляра никогда не дают прав.
- engine/physis/PhysisAdminEndpoint.h: LoopbackAdminEndpoint владеет
  настоящим net::WsListener, слушающим ТОЛЬКО 127.0.0.1, и допускает
  аутентифицированные соединения к ServerGateway этапа 25. Он требует
  ненулевого зарезервированного хостом ID команды PHYSIS, обратных вызовов ACL и приватного
  файла журнала. LoopbackAdminConnector может аутентифицировать нативный редактор,
  подключающийся по локальному ws://127.0.0.1. Окно PHYSIS использует его
  мост EditorLink, чтобы опрашивать это соединение и показывать ожидание/статус.
- apps/editor/PhysisRemoteEdit.h: EditorLink::connectLocalAdmin принимает
  предоставленные хостом принципала, секрет из защищённого хранилища, ненулевой
  ID экземпляра, назначенный слот и тип команды. Он не генерирует автоматически
  секреты, не открывает анонимные сетевые соединения и не выдаёт административных прав.

Пример нативной настройки:
    aiverse::physis::remote::admin::LoopbackAdminEndpoint endpoint(
        privateJournalFile);
    endpoint.open(localPort, reservedFieldCommandType,
                  serverKeyLookup, canRead, canWrite, &error);
    // Restore matching Simulation checkpoint BEFORE opening endpoint.
    // In host event loop:
    endpoint.poll(sim, monotonicMs);
    sim.step();
    endpoint.afterTick(sim);

Поиск учётных данных, ротация ключей и ACL принадлежат хосту. Через этот API
административный порт никогда не может быть привязан к публичному адресу. ВАЖНО: текущий нативный
WebSocket-клиент AIVERSE поддерживает ws://, но НЕ wss://; само это рукопожатие
не является шифрованием транспорта. Для административного доступа с других машин используйте
уже зашифрованный аутентифицированный туннель к локальному loopback или реализуйте
настоящий нативный TLS/WSS. Никогда не открывайте наружу обычный ws:// и не называйте это безопасным.

Восстановление после сбоя:
1. Сохраняйте исходное *намерение* правки ДО планирования команды
   Simulation. Неудачная запись в журнал предотвращает любой новый допуск.
2. Сохраняйте квитанции Queued и затем Applied/Rejected/Conflict.
   Восстановленные намерения Unknown можно сверить с сохранёнными в ECS
   ревизией+отпечатками; тот же исходный пакет может быть повторно допущен только
   после проверок ACL и ревизии. Дублированные ID пакетов не могут примениться дважды.
3. При перезапуске сначала восстановите соответствующий World/контрольную точку Simulation и
   состояние ожидающих команд, затем подключите файловый журнал и только
   после этого принимайте аутентифицированные административные соединения.
4. Журнал и контрольная точка Simulation — два отдельных хранилища,
   а не одна атомарная транзакция БД. Отключение питания между их записью
   может оставить неоднозначный результат. Восстановление квитанций должно сообщать
   Unknown/Conflict, а не выдумывать Applied. Это надёжнее,
   чем кэш квитанций этапа 25, существующий только в памяти, но это не всеобъемлющая
   гарантия атомарного при сбое подтверждения ровно один раз.

Нет изменений в манифесте сохранения PHYSIS по умолчанию или в полномочиях NEREID Water,

### Исправление восстановления после сбоя на этапе 26 — сохранённый Queued != ожидающая команда

При усилении этапа 26 ServerGateway::restoreJournal изменён так, чтобы
восстанавливать каждую сохранённую квитанцию Queued как Unknown и очищать старый

могла исчезнуть при перезапуске, даже если сопутствующий журнал
всё ещё говорит Queued. Загруженная квитанция Queued не является доказательством выполнения.

После того как хост восстановит соответствующий World/контрольную точку ECS, observe()
сверяет Unknown с FieldRuntimeState и редактируемыми отпечатками.
Если изменение уже зафиксировано, запрос становится Applied. Если ревизия ушла вперёд
несовместимо, это Conflict. Если не изменилась, сохраняется Unknown; ТОЧНО ТОТ ЖЕ
исходный аутентифицированный Submit может быть повторно допущен с тем же ID
после проверок ACL и ревизии. Это исправление не создаёт новых прав PHYSIS или публичного
слушателя.

Новые исходные фикстуры в physis_admin_journal проверяют и сбой до
выполнения команды из очереди, и сбой после её эффекта в ECS, но до
сброса квитанции Applied в сопутствующий журнал. Эти тесты НАПИСАНЫ, НЕ ЗАПУЩЕНЫ.
Журнал и сохранение Simulation остаются отдельными доменами устойчивости:
это безопасная повторная отправка/сверка, а НЕ полная межфайловая
атомарная при сбое фиксация ровно один раз.

Handoff этого этапа:

### Исправление восстановления после сбоя на этапе 26 для устойчивых квитанций полей
Аутентифицированный запрос редактора PHYSIS может быть сохранён в файловом журнале как Queued до авторитетного шага Simulation. Если процесс аварийно завершается, его очередь ожидающих команд в памяти может пропасть, хотя журнал всё ещё говорит Queued. Это предотвращает преждевременные отчёты Rejected или ошибочные Applied после перезапуска. Тестовые фикстуры в `tests/physis_admin_journal_test.cpp` покрывают и сбой до фиксации, и сбой после фиксации, но до квитанции; нативный CTest НЕ ЗАПУЩЕН. См. `docs/agent-handoffs/physis-stage26-queued-recovery-2026-11-19.md`.

### Этап 64 — игнорирование устаревшего удалённого ACK после Apply

`RemoteClient` обеспечивает монотонную обработку квитанций на активном
соединении: принятую окончательную квитанцию нельзя перезаписать
запоздалыми Queued/Unknown и т. п. Когда операция Applied проверяется после
переподключения, Query для исходного ID должен быть действительно отправлен до
принятия ответа на него; ответ до запроса и устаревший Queued
игнорируются. Unknown во время проверки Applied означает **Uncertain**:
никогда не воспроизводите автоматически ранее подтверждённый Submit.
Ручной `retry()` после тайм-аута проверки — операция только из
Query, а `begin()` отклоняет неопределённую/незавершённую проверку.

Нет изменений в формате передачи, схеме ECS, NEREID Water, TerraWeave или Box3D.
В V1 нет nonce корреляции для каждого Query, поэтому получение после Query
не является криптографическим доказательством того, что задержанный пакет Applied был сформирован
для этого Query. Будущая версия протокола должна добавить корреляцию и
поколение сервера. Исходные фикстуры написаны, но нативный CTest движка
НЕ ЗАПУЩЕН. См.
`docs/agent-handoffs/physis-stage64-monotonic-ack-2026-11-19.md`.
