# PRISMA — универсальная постобработка AIVERSE

PRISMA — название системы полноэкранных эффектов и обработки изображения. Не путать с **SpectraFX** — системой частиц/VFX. Форматы существующих игр не меняются.

## Границы ответственности: PRISMA и SpectraFX

PRISMA владеет **постобработкой итогового изображения**: HDR/тонмаппинг, Bloom, color grading/LUT, DoF, Motion Blur, FXAA/TAA/upscaling, screen-space GI/AO/SSR, объёмы камеры, screen-space Shader Graph (domain `postfx`), render-pass dependencies и performance budgets.

SpectraFX владеет **мировыми визуальными эффектами до постобработки**: эмиттеры/частицы, дым, огонь, взрывы, ribbons, trail-потоки, CPU/GPU particle simulation, авторинг VFX graph и события ECS. SpectraFX генерирует HDR вклад сцены, PRISMA затем может применить Bloom ко всей сцене. Системы не дублируют друг друга, не зависят от жанра и не включаются в deterministic gameplay state.

Канонические исходники теперь `engine/render/Prisma.{h,cpp}`, `PrismaData.{h,cpp}`, `PrismaShaders.h`, `PrismaVolumes.h`. Editor: `apps/editor/core/PrismaOps.{h,cpp}` и `apps/editor/windows/PrismaWindow.cpp`. Устаревшие заголовки PostFx перенаправляют на PRISMA, устаревшие .cpp не содержат реализации. Стабильные JSON `postfx`, MCP `postfx_*` и editor saved id `postfx` **не переименовывать**: это внешние форматы, а не владельцы кода.

## Текущее устройство
- Основной C++ API: `#include "engine/render/Prisma.h"`; класс `aiverse::render::Prisma`.
- Совместимость: `PostFx` и `PostFxData` — исходные alias/forwarding includes; основная компиляция через `Prisma.cpp` и `PrismaData.cpp`. Старые `postfx_*` MCP имена сохранены.
- `Renderer3D` запрашивает `PostProcess::scenePass` и вызывает `resolve()`; `ScreenLighting` при HDR/High выполняет экранное освещение и TAA до финального resolve.
- Параметры: `game.json` / карта, `postfx` с объединением по типу эффекта; панель редактора и MCP-операции уже реализованы.
- GPU/RHI: GLSL/MSL, HDR RGBA16F с ACES и sRGB, fallback RGBA8; текущая цепочка имеет фиксированный порядок. UI отрисовывается **после** PRISMA.

## PrismaRenderGraph — этап 07 (GPU-free planner)

`engine/render/PrismaRenderGraph.h` — первая независимая от RHI реализация **описания проходов и ресурсов**. `PrismaRenderGraph::addResource/addPass/compile` строят стабильный топологический порядок, проверяют один writer на ресурс, ошибки идентификаторов, feedback read/write в одном pass и циклы зависимостей. `PrismaGraphPlan` содержит `order`, `resources` (first/last use), `slots` и число байт выделяемых **внутренних** текстур. Совместимые по формату и размеру временные ресурсы с непересекающимися lifetime используют один slot; history и ресурсы с `allowAlias=false` не разделяют slot. External input/output/history передаются вызывающим кодом и не аллоцируются planner.

**Важно:** это пока только граф зависимостей + lifetime planner, не GPU-executor. Реальный `Prisma::resolve()` пока исполняет текущий фиксированный pipeline. Нельзя заявлять, что RenderGraph уже управляет рендерингом; следующий этап — RHI-resource pool и execution callbacks с реальными pass bindings. Неправильные зависимости намеренно отклоняются, а не исправляются неявным shader blit.

Тестовый код: `tests/render/prisma_graph.cpp`, CTest `prisma_graph`, при `AIVERSE_BUILD_TESTS=ON` включён в стандартную CMake ALL сборку и `./run-tests.sh`. Нативный запуск тестов ещё требуется.

## Целевые интерфейсы
1. GPU-free `PrismaProfile`, `PrismaVolume`, `PrismaVolumeStack` и разрешение параметров по положению камеры.
2. Декларативный `PrismaGraph` с типизированными ресурсами (SceneColor, Depth, Velocity, History, LUT, Output), топологическим порядком и lifetime, без привязки к FPS/RTS.
3. Эффекты DepthOfField, MotionBlur, AutoExposure, GTAO и LensDistortion как отдельные проходы с quality-tier fallback.
4. MotionVectors / reactive masks и temporal upscaling; отдельная политика инвалидирования истории при camera cut/LOD/resize.
5. Профилировщик GPU-проходов, проверка ресурсо-опасных зависимостей, редактор узлов и полная автоматизированная проверка RHI.

## Camera Post Process Volumes — этап 08

`PrismaVolumeStack` теперь используется в игровом клиенте и в редакторских Scene/Game viewport. На этапе старта карты клиент читает `game.json["prismaVolumes"]` и `map["prismaVolumes"]` через `parsePrismaVolumes`; перед `Renderer3D::render(...,&prisma)` вызывает `prisma.applyCameraVolumes(stack,camera.eye())`, после `resolvePrisma()` сбрасывает настройки к базовому профилю. Editor кэширует профиль по JSON-сигнатуре и разрешает его отдельно для каждой камеры; изменение `postfx` не мутируется.

Пример `game.json` (тот же верхнеуровневый блок можно указать на карте):

```json
"prismaVolumes": {
  "volumes": [
    {
      "id": "underwater",
      "shape": "box",
      "center": [12, -5, 20],
      "halfExtents": [15, 6, 12],
      "blendDistance": 3,
      "priority": 10,
      "layerMask": 4294967295,
      "weight": 1,
      "profile": {
        "effects": [
          {"type": "colorGrade", "saturation": 0.5, "temperature": -0.3},
          {"type": "vignette", "intensity": 0.4}
        ]
      }
    }
  ]
}
```

Формы: `global`, `sphere` (`center`, `radius`) и `box` (`center`, **axis-aligned** `halfExtents`). `weight` в [0,1], `blendDistance` — дистанция затухания **за внешней границей**; приоритеты обрабатываются по возрастанию и одинаковые приоритеты сохраняют порядок добавления. `layerMask` фильтрует камеры, `enabled` отключает объём.

Профиль внутри volume использует тот же **existing** `postfx` schema, не новую библиотеку шейдеров. Указание `"hdr"` или `"enabled"` явно включает соответствующий override; отсутствие этих ключей сохраняет значение базового профиля. На карте volume с тем же `id` заменяет игровой; `"replace":true` в блоке карты удаляет все game volumes, прежде чем применить map list. Неверные записи пропускаются с `issues`, authored JSON не меняется.

**Ограничения:** body volume ещё не ориентированный box (rotation нет), нет spatial index/приоритетного GPU culling, маска камеры по умолчанию all bits; обычные GameClient/Editor применяют mask all. Интерполяция изменяет **только явно указанные параметры** эффекта (этап 09), остальные параметры, minQuality и пути LUT сохраняют базовые значения. Для native C++ профиля без masks сохраняется legacy full-profile поведение. Дискретные настройки меняются при весе >= 0.5, числовые параметры blend в float на presentation side. Не хранить такой float стек в authoritative ECS state. Новые данные `prismaVolumes` необязательны и не затрагивают старые проекты. Код: `PrismaVolumeData.{h,cpp}`, `PrismaVolumes.h`; CPU tests: `tests/render/prisma_volume.cpp` / CTest `prisma_volume` (проверка запуском ещё требуется).

## Stage 09 — точечное смешивание параметров

`PrismaVolumeEffectMask` в `PrismaVolumes.h` и `PrismaVolumeData.cpp::authoredEffects` сопоставляют каждому эффекту bitmask явно указанных параметров из JSON, включая компоненты цвета, flags `enabled/minQuality` и текстовый путь LUT. Когда volume задаёт только `colorGrade.exposure`, исходные `colorGrade.saturation`, `contrast`, lift/gamma/gain и minQuality **не перезаписываются**. При отсутствии базового эффекта добавляется нейтральный профиль с плавным входом для ColorGrade/Bloom/эффектов с `intensity` или `amount`; для дискретных эффектов — порог 0.5. Для прямого native C++ создания volume без `effectMasks` сохранено старое full-profile поведение. Тесты `prisma_volume` расширены на сохранение несвязанных параметров, но нативный запуск ещё требуется.

## Stage 10 — визуальное редактирование Camera Volumes

Панель `PRISMA — Постобработка` (`apps/editor/windows/PrismaWindow.cpp`) теперь содержит секцию **PRISMA Volumes** в текущем scope: вся игра (`game.json`) или открытая карта. Она умеет создавать глобальный/сферический/box volume; центрировать объём на камеру Scene, редактировать `id`, enabled, размеры, приоритет, `weight`, `blendDistance`, `layerMask` и вложенные эффекты. Для каждого параметра эффекта рядом есть переключатель **наследовать/переопределить**: снятие override удаляет соответствующий ключ JSON, а не записывает дефолт. Это соответствует `PrismaVolumeEffectMask` и предотвращает сброс глобального контраста/насыщенности.

Авторинг использует общий GPU-free `makePrismaVolumeJson(id, shape, center)` из `PrismaVolumeData.h` — тот же формат, что runtime-парсер и CPU-тест `prisma_volume`. Изменения карты идут через `MapDoc::beginEdit/touched` (undo), изменения игры через сохранение manifest, как в уже существующих PostFX-слайдерах. Scene-камера показывает количество применимых эффектов/объёмов и предупреждения парсера.

**Ограничения:** нет gizmo-контуров объёма в viewport и нет редактора Shader Graph payload внутри volume — для него остаётся отдельный Shader Graph Editor. UI использует существующий ImGui и editor layout. Ни компиляция, ни GUI smoke/undo parity, ни GPU screenshots на этом этапе не проверены; агент должен подтвердить их нативно перед объединением. Старое ID панели `postfx` и MCP-команды `postfx_*` сохранены.


## Stage 11 — типизированный RenderGraph dispatch без GPU

`engine/render/PrismaGraphDispatch.h` добавляет header-only, не зависящий
от жанра контракт `dispatchPrismaGraph<Handle>(graph, plan, bindings, callback)`.
`PrismaGraphBindings<Handle>` содержит по одной записи на каждый ресурс графа
для внешних handle и по одной записи на каждый скомпилированный transient slot
для физических аллокаций. `PrismaGraphDispatchView::resource(id)` разрешает
логический ресурс через скомпилированный план алиасинга; вызывающая сторона
предоставляет типизированные RHI handle, command encoder и переходы текстур.

Проверка завершается **до любого callback**: невалидные планы, несовпадающее
число привязок, непривязанные handle, повторяющиеся ID проходов и неверные
ссылки на ресурсы отклоняются, и кадр не отрисовывается частично. Callback
вызывается в детерминированном топологическом порядке; если он возвращает false,
последующие проходы прерываются с ошибкой и точным числом выполненных проходов.

Это **не RHI executor**: он не выделяет GPU-текстуры, не создаёт барьеры
encoder, не выполняет render pass и не подключается к текущей фиксированной
цепочке PRISMA. Внешняя интеграция должна сначала создать и удерживать
физические слоты, управлять временем жизни внешних ресурсов и history,
обеспечить синхронизацию и подключить существующие вызовы `Prisma::resolve`.
Оставляйте устаревший рендерер включённым по умолчанию, пока не пройдены
нативная проверка Metal/GL и тесты совпадения изображения.

Тесты добавлены в `tests/render/prisma_graph.cpp` / CTest `prisma_graph`.
Нативная сборка, CTest и GPU-тесты **НЕ ЗАПУСКАЛИСЬ** в окружении агента,
работающего только через GitHub; см. `docs/handoffs/prisma-stage-11.md`.


## Stage 12 — пул физических ресурсов (независимый от GPU)

`engine/render/PrismaGraphResourcePool.h` предоставляет принадлежащий хосту
пул физических handle render target для `PrismaGraphPlan::slots`. Хост создаёт
цели через callback `create(format,width,height)` и освобождает их через
`release(handle)`; сам заголовок никогда не вызывает GPU/RHI API.

- `prepare(graph, plan, create, release)` повторно использует аллокации с теми же
  форматом/размерами и совпадающим именем history-ресурса либо создаёт новые цели.
  В пределах одного кадра он никогда не выбирает одну аллокацию дважды. При
  ошибке выделения он освобождает цели, созданные в этом вызове prepare,
  и сохраняет прежние записи пула.
- `markHistoryWritten(name)` помечает успешно полученные temporal-пиксели валидными;
  `invalidateHistory()` отбрасывает temporal *содержимое* при camera cut/телепорте,
  не отбрасывая переиспользуемую GPU-память. Если `prepare` возвращает false
  в бите валидности history, вызывающий код не должен читать старую history и
  должен использовать нетемпоральный fallback. Изменение размера меняет
  дескрипторы ресурсов и всегда выделяет новую history.
- `pruneUnused(release)` освобождает аллокации, не выбранные последним успешным
  prepare; `clear(release)` освобождает все аллокации. **Вызывайте оба только после
  завершения GPU fence**, а не пока предыдущие кадры ещё могут на них ссылаться.
- Используйте отдельный экземпляр пула на каждую независимую камеру/view/temporal
  поток, а не одну глобальную изменяемую history для всех камер. Пул не выделяет
  внешние привязки ресурсов, не вычисляет барьеры, не запускает render pass и не
  встраивается в существующий `Prisma::resolve`. Это opt-in контракт хоста.

Тесты переиспользуемых физических слотов, валидной/невалидной history,
изменения размера/pruning, отката выделения и очистки находятся в `tests/render/prisma_graph.cpp`.
Нативная сборка/CTest/проверка GPU-скриншотов для Stage 12 **НЕ ЗАПУСКАЛИСЬ**.
См. `docs/handoffs/prisma-stage-12.md`.


## Stage 13 — opt-in адаптер графа к RHI (пока не подключён к Prisma::resolve)

`engine/render/PrismaRhiExecutor.h` связывает GPU-free граф Stage 11 и
пул аллокаций Stage 12 с существующим API `gfx::Device`. Он создаёт
цели `TextureDesc{renderTarget=true}`, отображает RGBA8/RGBA16F/Depth32F на
поддерживаемые backend форматы, использует `copyColor` для Copy-проходов
с одним входом/одним выходом и совпадающим RGBA8 и выполняет Raster callback
внутри сбалансированных областей `beginPass/endPass`. Compute callback выполняются
вне render pass и только если `Device::supportsCompute()` сообщает о поддержке.

Нативный хост явно создаёт `PrismaRhiExecutor(device)` на каждую камеру
и вызывает `execute(graph,plan,external,raster,compute,optionalDepth)`
**вне любого существующего прохода**. Сигнатура Raster callback —
`bool(gfx::Device&, PrismaGraphId, const PrismaGraphDispatchView<gfx::TextureHandle>&)`;
он сам привязывает свой pipeline, uniform и входные текстуры. У Compute
та же сигнатура callback, но он сам отвечает за открытие/закрытие нужного ему
compute encoder. `optionalDepth` должен совпадать по размерам с raster target,
если выбранному backend Metal нужен depth attachment. Адаптер никогда не вызывает
`endFrame`, не выполняет present и неявные шейдерные преобразования и не изменяет ECS.

**Ограничения совместимости:** сейчас в `gfx::PixelFormat` нет форматов
целей RG16F/R32F; такие графы не проходят предварительную проверку. Переносимый
интерфейс `copyColor` гарантирует только RGBA8 одинакового размера; для HDR/других
операций копирования нужны явные raster-проходы с шейдером. `gfx::Device` не предоставляет
универсального API барьеров ресурсов. Освобождение GPU-целей и сброс пула
должны выполняться в безопасной точке, которой управляет вызывающий код, после
завершения работы, находящейся в полёте. Temporal history валидна только после того,
как хост успешно получил её пиксели и явно пометил её записанной.

**Это не полная миграция конвейера рендеринга.** `Prisma::resolve()` по-прежнему
по умолчанию использует устаревшую поставляемую фиксированную цепочку проходов,
без автоматического выполнения RHI-графа. Заголовок — это opt-in точка интеграции,
а добавленные тесты сейчас покрывают только отображение RHI-форматов в
`tests/render/prisma_graph.cpp`. Нативная сборка, smoke-проверка драйвера, скриншоты
и численное совпадение остаются **НЕ ЗАПУЩЕННЫМИ**. См.
`docs/handoffs/prisma-stage-13.md`.


## Stage 14 — экспериментальный SDR FXAA через граф

Первая производственная точка вызова `PrismaRhiExecutor` — **opt-in**
SDR FXAA-препроход в `Prisma::resolve()`. Установите
`AIVERSE_PRISMA_GRAPH_FXAA=1`, чтобы создать граф из двух внешних ресурсов
(`scene-fxaa` -> `fxaa-output`) и выполнить существующий FXAA pipeline,
с теми же uniform и привязками текстур, за один raster-проход RHI.

Путь по умолчанию не изменился. Экспериментальный путь используется только тогда,
когда FXAA активен, сцена в RGBA8/SDR, FXAA pipeline валиден,
обе цветовые текстуры существуют и создан соответствующий depth attachment.
Если граф не удаётся скомпилировать/выполнить, вместо него работает исходный путь
прямого `draw()`. Предварительная проверка графа выполняется до отправки любой отрисовки;
шейдер использует ровно одну полноэкранную отрисовку и записывает всё
целевое изображение. Opt-in проход не очищает ни цвет, ни глубину.

У графа нет внутренне выделяемых целей; он использует существующие
ресурсы `Sized` для каждого view. Он **не** включает отрисовку через граф для
HDR, bloom, temporal AA или финального composite. Нет новой
JSON-схемы, переключателя в редакторе или изменений в SpectraFX. Это защищённый
плацдарм в runtime, а не миграция всей цепочки на render graph.

Совпадение на GPU и нативные CMake/CTest остаются **НЕ ЗАПУЩЕННЫМИ**. Исходник теста в
`tests/render/prisma_graph.cpp` проверяет только структуру графа и
логику привязки/диспетчеризации одного прохода, а не корректность пикселей Metal/GL.
Для воспроизведения и оставшейся проверки читайте
`docs/handoffs/prisma-stage-14.md`.


## Stage 15 — opt-in Bloom Prefilter и совпадение очистки с устаревшим путём

`PrismaRhiExecutor::execute` теперь по умолчанию очищает raster-проходы так же,
как `Prisma::draw`: непрозрачным чёрным цветом и очисткой глубины. Дополнительный
аргумент `clearRasterTargets=false` доступен для конвейеров, которые явно только
перезаписывают цель, но экспериментальные точки вызова FXAA и Bloom используют поведение
по умолчанию, совместимое с устаревшим путём. Это устраняет известный риск расхождения Stage 14.

`AIVERSE_PRISMA_GRAPH_BLOOM_PREFILTER=1` переводит в `PrismaRhiExecutor`
только **первый raster-проход Bloom Prefilter**. Он использует существующий
шейдерный pipeline `kPrefilter`, uniform-блок и одну исходную текстуру;
входной/выходной ресурсы — цели `Sized` с внешним управлением (вход в полном разрешении,
выход в пониженном разрешении), и граф не выделяет transient-текстуры.
В режиме HDR оба ресурса объявлены как `RGBA16F`, иначе как
`RGBA8`. Оба формата поддерживаются существующим условным путём RHI.

Остальная цепочка downsample/upsample Bloom остаётся исходным прямым
рендерером; эксперимент с FXAA по-прежнему использует свой независимый
флаг `AIVERSE_PRISMA_GRAPH_FXAA=1`. Путь по умолчанию не изменился, и любая
ошибка предварительной проверки/выделения приводит к fallback на `Prisma::draw`. Экспериментальный
raster callback возвращает true после отправленной отрисовки; ошибку **после** отправки на
GPU откатить нельзя. Совпадение полного кадра не установлено.

`tests/render/prisma_graph.cpp` теперь содержит CPU-only контракты графа для
размеров prefilter в SDR и HDR, привязок, однократной диспетчеризации и предварительной проверки
отсутствующего выхода. Эти исходники **не** компилировались и не запускались в окружении
этого агента; скриншоты Metal/GL и GPU-тайминги также **НЕ ЗАПУСКАЛИСЬ**.
См. `docs/handoffs/prisma-stage-15.md`.


## Stage 16 — opt-in полный RenderGraph Bloom down/up

`AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1` включает экспериментальный полный граф Bloom
**Prefilter → Downsample → Upsample** внутри `Prisma::resolve()`.
По умолчанию флаг выключен. Граф объявляет один внешний вход Scene и
внешние down/up цели для каждого уровня, хранящиеся в существующем кэше текстур
`Prisma::Sized` для каждого view. Каждый downsample читает предыдущий mip; каждый upsample
читает нижний промежуточный результат плюс соответствующий down mip. Все проходы используют
существующие GPU-шейдерные программы `kPrefilter`, `kDown` и `kUp`, в точности
исходные зависящие от размера uniform, нормализацию tint/radius, привязки
источников и форматы текстур (SDR RGBA8; HDR RGBA16F). Хост создаёт
depth attachment для каждого выходного размера перед выполнением.

RHI executor теперь принимает необязательный последний аргумент
`std::function<gfx::TextureHandle(PrismaGraphId)> rasterDepthForPass`.
Если он передан, этот attachment заменяет общий `rasterDepth` для каждого
прохода; это необходимо на Metal для разных размеров mip Bloom.
Существующие пользователи executor из Stage 14/15 по-прежнему используют прежнюю необязательную
общую глубину и совместимые с устаревшим путём параметры очистки по умолчанию.

**Охват/ограничения:** это реальное планирование raster-проходов Bloom через RHI-граф,
но это **ещё не** переход на transient-пул графа из Stage 12:
хост передаёт кэшированные снаружи текстуры целей, которые и так сохраняются
для каждого viewport. Нет автоматической очереди освобождения ресурсов, находящихся в полёте,
и API барьеров ресурсов. Полный граф перестраивается в каждом opt-in кадре,
а `Prisma::resolve()` сохраняет старый путь как fallback, если предварительная проверка
графа не проходит. При любой неожиданной ошибке **после** отправки прохода на GPU
граф не воспроизводится повторно (частичная отрисовка не должна отправляться дважды).
На этом этапе не был перенесён ни один эффект, кроме Bloom. Если установлены и
`AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN`, и флаг Stage 15 только для prefilter,
при успехе приоритет имеет флаг полной цепочки.

Новые GPU-free тесты графа проверяют 1/2/4 уровня downsample для SDR/HDR,
топологический порядок, корректное разрешение привязок и отклонение отсутствующих
mip-целей до выполнения проходов. Эти исходники **НЕ ЗАПУСКАЛИСЬ** нативным
компилятором или на GPU; см. `docs/handoffs/prisma-stage-16.md`.


## Stage 17 — кэш скомпилированной топологии Bloom для каждого view

`engine/render/PrismaBloomGraph.h` предоставляет GPU-free
`PrismaBloomGraphCache`. `configure(sourceWidth,sourceHeight,format,mips)`
компилирует полную топологию Bloom один раз для каждого размера источника, формата HDR/SDR
и списка форм mip. Последующие кадры с той же структурой переиспользуют
`graph()`, `plan()` и `operations()`; изменение качества/размеров mip
запускает компиляцию графа на замену. Неудачная переконфигурация оставляет
прежнюю валидную конфигурацию нетронутой, но рендерер никогда не выполняет
этот устаревший граф для несовместимой текущей раскладки.

Основной кэш viewport `Prisma::Sized` теперь владеет
`PrismaBloomGraphCache`, так что у Scene/Game view раздельные раскладки
графа и нет общей между view history. Opt-in путь Stage 16
`AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1` использует кэшированный неизменяемый граф
и перестраивает только *привязки кадра*: threshold/knee/scatter,
uniform шейдеров, handle исходной и выходной текстур и depth attachment
для каждого mip. Существующий fallback и выключенное по умолчанию поведение
сохранены. Пул transient-целей Stage 12 остаётся отдельной
будущей интеграцией; сама кэшированная топология **не** выделяет GPU-текстуры.

Это работа только над реализацией; CMake, CTest и реальная проверка на GPU
намеренно отложены по просьбе пользователя. См.
`docs/handoffs/prisma-stage-17.md`.


## Stage 18 — освобождение по завершении GPU и постоянный executor для view

`engine/render/PrismaGpuRetirement.h` вводит
`PrismaGpuRetirementQueue<Handle>`: `retire(handle,submissionFence)`
переносит аллокацию в очередь ожидания; `collect(completedGpuFence,
release)` вызывает callback освобождения **только когда GPU сообщил о
завершении** через fence/event, которым управляет вызывающий код. `drainAfterGpuIdle`
допустим только после явной синхронизации простоя GPU. Счётчик кадров CPU
или `gfx::Device::frameSerial()` не является fence завершения.

`PrismaGraphResourcePool::retireUnused/retireAll` теперь передают
аллокации вызывающему коду вместо немедленного уничтожения.
`PrismaRhiExecutor::retireUnused/retireAll/collectCompleted`
связывают эти операции со своей очередью и вызывают RHI `destroyTexture`
после переданного завершённого fence. `resetAfterGpuIdle()` также
освобождает все ожидающие и текущие аллокации, но **только** если
хост убедился, что GPU простаивает.

Каждый viewport `Prisma::Sized` теперь хранит лениво создаваемый постоянный
`std::unique_ptr<PrismaRhiExecutor>`, общий для его opt-in вызовов FXAA,
Bloom prefilter и полного графа Bloom. Он сохраняет состояние пула
ресурсов между кадрами вместо создания нового executor на
каждом проходе. Время жизни привязано к существующему кэшу Sized. Это
пока не заставляет PRISMA использовать цели Bloom, принадлежащие графу; они остаются
внешними RHI-текстурами в Sized, а выполнение графа остаётся opt-in.

**Ограничение интеграции с backend:** Gfx пока не предоставляет
переносимого API завершённого GPU fence. Хосты должны передавать в `collectCompleted`
реальные сигналы завершения. Существующее вытеснение viewport и
завершение работы рендерера по-прежнему уничтожают свои устаревшие текстуры в
текущих точках освобождения; эта opt-in очередь не делает их автоматически
безопасными относительно GPU fence. Реальное подключение fence в backend
и перенос Bloom на transient-пул остаются будущими функциями.
Тестирование/сборка/проверка на GPU намеренно отложены по просьбе пользователя.
См. `docs/handoffs/prisma-stage-18.md`.


## Stage 19 — opt-in выделение mip Bloom, принадлежащих графу

При одновременных `AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1` и
`AIVERSE_PRISMA_GRAPH_BLOOM_POOL=1` полный RenderGraph Bloom
теперь может выделять свои цели downsample/upsample через
`PrismaGraphResourcePool` в постоянном RHI executor каждого viewport.
Внешним остаётся только входной цвет Scene/FXAA. Граф объявляет каждый
mip Bloom **внутренним** ресурсом, что позволяет планировщику алиасить
GPU-текстуры одинакового формата/размера, если их времена жизни не пересекаются.
Без нового флага пула существующий граф Stage 16 по-прежнему использует
`Sized::targets` как внешние ресурсы. Оба экспериментальных флага
по умолчанию выключены.

`PrismaRhiExecution::resources` теперь сопоставляет каждый логический ресурс графа
с его фактическим внешним или пуловым handle RHI-текстуры. Финальный composite Bloom
сэмплирует `resources[cache.outputId()]`, когда пуловый режим
отработал успешно. Depth attachment для каждого прохода по-прежнему берутся из устоявшегося
кэша `Sized::depths`; пороги, scatter, шейдерные pipeline и
соглашения о UV источника не изменились. При ошибке предварительной проверки/выделения
графа до отправки на GPU код выделяет устаревшие mip-цели
и использует существующий fallback Bloom. Ошибка после отправки на GPU
не приводит к попытке повторно воспроизвести частично выполненные проходы.

**Владение:** пуловые RHI-текстуры живут вместе с executor своего viewport,
а не освобождаются после каждого кадра. Переконфигурация сохраняет
невыбранные аллокации до явного безопасного освобождения; их итоговое
освобождение зависит от сообщения о завершении GPU или подтверждённого простоя GPU
при завершении работы. Переносимый backend завершённых fence пока не подключён, поэтому
автоматическое вытеснение во время работы намеренно не используется. Существующее
вытеснение view по-прежнему следует допущениям устаревшего освобождения, а выигрыш
по памяти не измерен. Этот экспериментальный путь требует проверки сборкой/на GPU,
прежде чем включать его по умолчанию.

Этап только реализации: тестирование намеренно отложено по просьбе
пользователя. См. `docs/handoffs/prisma-stage-19.md`.

## Stage 20 — opt-in граф для Tilt Shift

`AIVERSE_PRISMA_GRAPH_TILT_SHIFT=1` направляет существующий трёхпроходный
Tilt Shift (downsample, горизонтальное гауссово размытие, вертикальное гауссово размытие)
через `PrismaRhiExecutor`. Четыре логических SSA-ресурса описывают
источник, первую цель A, цель B и финальную цель A. Две версии
A намеренно отображаются на одну и ту же существующую физическую текстуру: они
никогда не нужны одновременно, а промежуточная B отдельная.
Uniform каждого прохода и исходные pipeline сохранены. Путь по умолчанию
остаётся устаревшими тремя отрисовками. При отсутствии ресурсов или ошибках до
отправки на GPU происходит fallback на него; частично выполненные проходы не воспроизводятся повторно.
Этот этап пока не переносит физические цели Tilt в пул, принадлежащий графу,
и не включает Tilt Shift по умолчанию. Нативные/GPU-тесты намеренно
НЕ ЗАПУСКАЛИСЬ по просьбе пользователя. Handoff: `docs/handoffs/prisma-stage-20.md`.


## Stage 21 — opt-in граф для Sun Shafts

`AIVERSE_PRISMA_GRAPH_SUN_SHAFTS=1` включает двухпроходный граф для
существующей prefilter-маски солнечного света и операции радиального рассеивания.
Положение солнца, fallback по краю за пределами экрана, порог видимости, цвет,
уровень качества, число сэмплов и uniform шейдеров не изменились. Три
текстуры с внешним владением представляют источник, маску и радиальный выход,
с существующим depth attachment для каждого размера. Двухпроходный граф выполняется
через RHI executor каждого viewport. Ошибка до любой отправки приводит к использованию
устаревшего пути из двух отрисовок; частично отправленный граф никогда не воспроизводится повторно.
Путь остаётся выключенным по умолчанию, а HUD по-прежнему рисуется после постобработки.

Новые сериализуемые настройки или варианты шейдеров не вводились.
Этот этап содержит только код и намеренно пока НЕ компилировался и не тестировался на GPU.
См. `docs/handoffs/prisma-stage-21.md`.


## Stage 22 — экспериментальный Depth of Field по глубине

Новая запись `depthOfField` в `postfx.effects` обрабатывается общим
каталогом данных PRISMA (обнаружение параметров в MCP и редакторе управляется данными).
Параметры: `focusDepth` (0..1, **глубина устройства GPU**, а не метры),
`focusRange` (интервал глубины), `maxBlur` (0..16 выходных пикселей) и
`intensity` (0..1). Значения по умолчанию: соответственно 0.5, 0.08, 8, 1.
По умолчанию эта запись требует качества постобработки High и отнесена к Heavy в
модели оценки стоимости.

Opt-in `AIVERSE_PRISMA_DOF=1` активирует один проход размытия по девяти соседям
в полном разрешении **до** SDR FXAA и Bloom; он читает
цвет сцены и глубину render target через существующий путь полноэкранных
программ GLSL/MSL и создаёт новую цветовую текстуру, которую последующие эффекты используют
как источник. Аппаратная глубина намеренно
не представляется как физическое расстояние фокуса, поскольку у PostFrame
сейчас нет переносимого контракта обратной проекции/near-far.
Радиус размытия зависит от разницы между сэмплированной аппаратной
глубиной и `focusDepth`, с центральным резким интервалом. Шейдер —
это ограниченная приближённая расфокусировка, **а не** кинематографическое шестиугольное боке,
разделение слоёв глубины или физически точная симуляция объектива.

Проход сэмплирует исходную глубину сцены, но использует собственный
временный depth attachment совпадающих размеров, избегая обратной связи
чтения/записи на одной и той же текстуре глубины. Он может работать только при наличии
настроенного эффекта, opt-in флага, необходимых GPU-ресурсов и
pipeline. Без флага существующая обработка изображения
продолжает работать без изменений. DoF отключён на качестве low/medium из-за своего
значения по умолчанию `minQuality=high`, если проект явно не переопределяет его.

Пример записи `postfx.effects` в game.json:
```json
{"type":"depthOfField","focusDepth":0.65,"focusRange":0.08,"maxBlur":6,"intensity":0.8}
```

Вся нативная компиляция, CTest и визуальные/GPU smoke-проверки намеренно
**НЕ ЗАПУСКАЛИСЬ** по просьбе пользователя. Реальная совместимость сэмплирования
текстур глубины в Metal/GL, поведение reverse-Z и интерпретация глубины
сцены требуют последующей проверки. Следующая функция —
настоящий автофокус по мировому расстоянию через данные проекции камеры, затем
разделение CoC по нескольким разрешениям и боке, вдохновлённое физикой.
См. `docs/handoffs/prisma-stage-22.md`.


## Stage 23 — HDR Auto Exposure (логарифмическая яркость на GPU + адаптация глаза)

`postfx.effects` теперь может содержать `{"type":"autoExposure"}`. Необязательная
функция остаётся выключенной при рендеринге, если не установлен
`AIVERSE_PRISMA_AUTO_EXPOSURE=1` **и** текущая сцена не
использует линейный HDR RGBA16F. На SDR/RGBA8 эффект не выполняет действий на GPU,
поскольку обрезанные светлые участки нельзя восстановить замером.

GPU-конвейер в `Prisma::resolve()`:
1. Прочитать линейный RGB сцены и сохранить log2 яркости в цель RGBA16F
   половинного разрешения (четыре цветовых выборки с коэффициентами яркости Rec.709).
2. Многократно усреднять логарифмическую яркость через пирамиду 2x2 до 1x1. Это
   оценивает среднее геометрическое яркости, а не полную гистограмму по корзинам.
3. Определить целевую экспозицию `2^(clamp(log2(keyValue)-meanLogL+
   compensation, minEV, maxEV))`. В отдельном ping-pong проходе RGBA16F 1x1
   смешать с предыдущей экспозицией с помощью
   `1-exp(-speed*deltaSeconds)`. `speedUp` управляет увеличением
   экспозиции (тёмный->светлый результат); `speedDown` — уменьшением экспозиции.
   Шаг времени ограничен 0.1 с, чтобы избежать больших скачков после задержек.
4. Сэмплировать полученный множитель экспозиции как `TEX8` в финальном
   composite **до** HDR-тонмаппинга и преобразования в sRGB. UI остаётся
   необработанным. Ручная экспозиция/компенсация ColorGrade по-прежнему умножает
   автоматический результат.

Параметры (обычный каталог `PrismaData` и обнаружение в редакторе/MCP):

| параметр | по умолчанию | диапазон | смысл |
|---|---:|---:|---|
| `keyValue` | 0.18 | 0.01–1 | целевой средний серый сцены |
| `minEV` | -6 | -12–0 | нижний предел автоматического EV |
| `maxEV` | 6 | 0–12 | верхний предел автоматического EV |
| `speedUp` | 3 | 0.01–20 | скорость реакции на осветление, 1/с |
| `speedDown` | 1 | 0.01–20 | скорость реакции на затемнение, 1/с |
| `compensation` | 0 | -5–5 | смещение EV |

Пример:
```json
{"type":"autoExposure","keyValue":0.18,"minEV":-4,
 "maxEV":4,"speedUp":2.5,"speedDown":1.0,"compensation":0.0}
```

Temporal history для каждого `Prisma::Sized` использует две HDR-текстуры 1x1 и
предыдущую метку времени. Явный нативный `Prisma::resetAutoExposure()`
инвалидирует history при camera cut. Переконфигурация проекта,
переключение постобработки и смена качества сбрасывают её; выключенный режим HDR/auto
также очищает валидную history. Первый включённый кадр сразу принимает
текущую измеренную экспозицию, избегая чтения неинициализированной текстуры
history. Чтение яркости обратно на CPU не используется.

**Ограничения:** алгоритм вычисляет среднюю *логарифмическую* яркость, **а не**
процентильную гистограмму; яркие выбросы всё ещё могут влиять на адаптацию,
а измерение не является физически откалиброванным экспонометром. Существующий
кэш `Sized` использует в качестве ключа размеры, а не стабильную идентичность
камеры, поэтому две камеры viewport одинакового размера могут разделять
temporal history. В следующем этапе нужно добавить явные стабильные ID view.
Фиксированный сэмплер экспозиции использует слот 8, который также доступен для
четвёртой пользовательской текстуры ShaderGraph (слоты 5..8); для таких графов автоматическая экспозиция
пропускается, а не затирает пользовательские текстуры. Поддержку HDR
и смешивание 1x1 RGBA16F нужно проверить на реальных Metal/GL.

Это opt-in реализация в исходниках, **нативные/GPU-тесты НЕ ЗАПУСКАЛИСЬ**,
согласно просьбе пользователя сначала реализовать функции. Не включайте её глобально до
проверки. Handoff: `docs/handoffs/prisma-stage-23.md`.


## Stage 24 — независимая history камер и взвешенный замер на GPU

API только для представления `Prisma::setViewId(uint64_t id)` выбирает
**стабильный** идентификатор камеры/view перед рендерингом. `viewId() const`
возвращает его. Две render target истории экспозиции RGBA16F 1x1 одного view,
метка времени адаптации, бит валидности и индекс ping-pong теперь хранятся в
`Prisma::exposureViews_` с ключом по этому ID **вместо размеров рендеринга**.
`resetAutoExposure(id)` инвалидирует один view; перегрузка без аргументов
инвалидирует все view. Прежние кэши целей по-прежнему используют размер как ключ
для совместного использования обычных временных текстур; *history* экспозиции больше не
смешивается между камерами Scene и Game одинакового размера.

Редактор устанавливает ID view `1` для Scene и `2` для Game перед
`applyCameraVolumes`; `GameClient` использует ID `3` в своём
собственном экземпляре PRISMA. Нативный проект, рендерящий несколько камер,
должен сам назначить различные ID. ID по умолчанию остаётся `0` для
устаревших нативных проектов. Истории экспозиции хранятся до
`Prisma::shutdown` (автоматического удаления по камерам/освобождения по fence
пока нет). ID должны быть стабильными, а не увеличиваться каждый кадр.

У `autoExposure` четыре дополнительных настраиваемых параметра:
- `centerWeight` (по умолчанию 0, диапазон 0..1): 0 = равномерный замер,
  1 = сильно центровзвешенный.
- `centerRadius` (по умолчанию 0.35, диапазон 0.05..1):
  нормализованный радиус гауссова центрального взвешивания.
- `minMeterLogL` (по умолчанию -10, диапазон -16..0) и
  `maxMeterLogL` (по умолчанию 10, диапазон 0..16):
  ограничивают log2 яркости отдельных пикселей в начальном проходе HDR-замера,
  уменьшая влияние экстремальной яркости.
  Это не отсечение по процентилям гистограммы.

Первый проход пирамиды теперь выводит два канала: взвешенную сумму
log2 яркости (R) и сумму весов (G); каждый последующий проход 2x2 уменьшает
обе компоненты одинаково. Шейдер адаптации 1x1 делит R/G
перед вычислением целевого EV. По сравнению со Stage 23 не требуется ни чтение на CPU,
ни дополнительная полноэкранная текстура, ни лишний raster-проход.
Формат везде остаётся RGBA16F.

Пример записи `postfx.effects`:
```json
{"type":"autoExposure","keyValue":0.18,
 "centerWeight":0.75,"centerRadius":0.35,
 "minMeterLogL":-8,"maxMeterLogL":6}
```

Весь рендеринг остаётся opt-in через `AIVERSE_PRISMA_AUTO_EXPOSURE=1`,
только HDR уровня High. Существующая схема `postfx` расширена, а не мигрирована.
CMake, CTest и реальная проверка Metal/GL **НЕ ЗАПУСКАЛИСЬ**, как и просили.
См. `docs/handoffs/prisma-stage-24.md`.


## Stage 25 — HDR-векторы движения камеры и Motion Blur (экспериментально)

`postfx.effects` теперь принимает `motionBlur` через общий,
не зависящий от жанра каталог PRISMA. Новый эффект по умолчанию имеет
`minQuality: "high"` и включается в runtime через
`AIVERSE_PRISMA_MOTION_BLUR=1`; дополнительно требуется HDR-сцена
RGBA16F (знаковые RG-векторы движения невозможно представить в
существующем пути RGBA8 без кодирования).

Параметры: `intensity` (0..1, по умолчанию 0.65),
`maxPixels` (0..64, по умолчанию 20), `samples` (2..16, по умолчанию 8),
`shutterScale` (0..2, по умолчанию 1). Пример:
```json
{"type":"motionBlur","intensity":0.6,"maxPixels":20,
 "samples":8,"shutterScale":1.0}
```

Проход векторов движения сэмплирует текущую аппаратную глубину сцены
и восстанавливает мировую позицию через обратную текущую
viewProjection. Он проецирует эту позицию предыдущей
viewProjection и записывает знаковую UV-скорость
`currentScreenUV - previousScreenUV` в текстуру RGBA16F.
Следующий raster-проход собирает цвет сцены текущего кадра вдоль
этой скорости и смешивает его с резким цветом. Motion blur
выполняется **до** depth of field, FXAA, Bloom и финального composite;
HUD/UI остаётся необработанным. Отдельные временные depth attachment не дают
одновременно сэмплировать и записывать глубину сцены.

Предыдущая матрица камеры, флаг валидности и размеры рендеринга
хранятся в `Prisma::motionViews_` для каждого стабильного `setViewId()`, по
тому же контракту идентичности камеры, что и у Auto Exposure. Первый отрисованный
кадр, изменение размера, смена качества, переключение постобработки или явный
`resetMotionHistory(viewId)`/сброс без аргументов инвалидируют
history движения и дают кадр без размытия; затем
матрица запоминается для следующего кадра. `setSettings` также сбрасывает history.

**Необязательный мост скоростей объектов:** нативный рендерер может каждый кадр вызывать
`prisma.setObjectMotionVectors(viewId, velocityTexture)`
с заимствованной текстурой полного разрешения, в которой R/G — знаковые
нормализованные экранные UV «текущее минус предыдущее», а B — маска
пикселей валидных объектов (B > 0.5). Если она есть, для помеченных пикселей эта скорость
заменяет скорость только от камеры. Заимствованный handle очищается после каждого
resolve. PRISMA **пока не** генерирует буферы скоростей отдельных объектов
по трансформациям мешей/скиннингу; адаптер — это контракт интеграции,
а не автоматический рендеринг движения объектов. Эти входные данные — состояние
представления, а не детерминированный ECS.

Ограничения: это motion blur на основе репроекции камеры, а не TAA или
временное накопление изображения; он не хранит предыдущий цвет и
поэтому не синтезирует недостающие сэмплы в открывшихся областях. О camera cut
нужно сообщать явно, чтобы избежать размытия при телепортах; прозрачность
материалов и небо (depth≈1) получают нулевую скорость камеры в
базовом шейдере. Ни сэмплирование глубины в Metal/GL, ни рендеринг знаковой
скорости, ни корректность изображения не тестировались. Вся компиляция,
CTest и проверки на GPU остаются **НЕ ЗАПУЩЕННЫМИ** по просьбе пользователя.
См. `docs/handoffs/prisma-stage-25.md`.


## Stage 26 — автоматические векторы движения жёстких объектов (экспериментально)

Когда HDR `motionBlur` активен с
`AIVERSE_PRISMA_MOTION_BLUR=1`, у Renderer3D теперь есть необязательный GPU-проход
наложения для **непрозрачных жёстких примитивов ModelDraw со стабильным
`persistentId`**. Он выполняется между проходом сцены и
`Prisma::resolve()`, вне любого открытого render pass, а затем передаёт
текстуру скоростей RGBA16F в PRISMA через новый общий мост
`PostProcess`. Он не изменяет gameplay/ECS, а
существующие векторы от камеры остаются fallback для пикселей
без валидной скорости объекта.

Рендерер отслеживает предыдущую мировую трансформацию каждой пары
`(ModelDraw::persistentId, nodeIndex)` в карте для каждого view. В первом
кадре или после camera cut он записывает текущие трансформации, не
рисуя наложение скоростей. Когда history камеры валидна, он
рендерит каждый подходящий жёсткий примитив отдельным шейдером GLSL/MSL
и потоком позиций `ModelVertex`. Текущая и предыдущая
матрицы model-view-projection дают знаковое экранное UV-движение
«текущее минус предыдущее» в RG. B=1 помечает видимые пиксели жёстких объектов. Подключается отдельная
временная текстура глубины; шейдер *сэмплирует* исходную глубину сцены
и отбрасывает фрагменты за видимой поверхностью, так что мировая
окклюзия/рельеф могут скрывать движущиеся объекты, не записывая глубину сцены.

Этот проход работает с существующими ModelItem после обычного батчинга:
трансформации отдельных узлов модели сохраняются, даже если обычный
непрозрачный проход использовал instancing/MDI. Наложение скоростей сейчас использует
одну обычную индексированную отрисовку на примитив (а не indirect/instanced
отправку скоростей); оно переиспользует существующие GPU-буферы
вершин/индексов модели. Render target наложения и depth attachment принадлежат
Renderer3D для каждого ID view `PostProcess` и освобождаются при его завершении.
Ресурсы не разделяются между камерами с разными стабильными ID.

Подходят только *жёсткие*, видимые, непрозрачные, недеформируемые примитивы моделей
со стабильным ID. Отсутствующие ID, прозрачные/masked материалы, skinned или
запечённые анимированные меши, morph target, пользовательская геометрия и временные
немедленные отрисовки пропускаются. Их пиксели продолжают использовать
реконструкцию движения только от камеры. Тест глубины сцены — это
приближённое сравнение с epsilon, а не полное воспроизведение материала/альфы/деформации;
возможны артефакты при быстром открытии областей и на краях.

Существующий `Prisma::setObjectMotionVectors(viewId,texture)` остаётся
доступным для пользовательских нативных рендереров; автоматическая генерация
Renderer3D использует тот же мост заимствованного handle через виртуальный
`PostProcess::acceptObjectMotionVectors`. Нет планирования через ECS
и интеграции под конкретный жанр. Поведение по умолчанию не меняется, когда
MotionBlur не активен.

**НЕ ЗАПУСКАЛИСЬ:** нативная сборка, CTest, компиляция шейдеров Metal/GL,
сравнение экранов и профилирование, согласно просьбе пользователя сначала реализовать функции.
По-прежнему нужен путь освобождения по завершении GPU fence для надёжного
изменения размеров целей и завершения работы, пока работа находится в полёте. См.
`docs/handoffs/prisma-stage-26.md`.


## Stage 27 — векторы движения объектов с учётом деформации и instancing

Необязательный путь HDR `motionBlur` теперь содержит два новых варианта
рендеринга скоростей в `Renderer3D`, оба активны только при
`AIVERSE_PRISMA_MOTION_BLUR=1`:

**Instancing скоростей жёстких объектов.** Геометрически эквивалентные видимые непрозрачные жёсткие
экземпляры `ModelItem` группируются по указателю на исходную модель, первому индексу
и числу индексов. Отдельный pipeline GLSL/MSL на 16 экземпляров принимает
матрицы MVP *текущего и предыдущего* кадров для каждого экземпляра, отправляя один
`drawIndexed(..., instanceCount)` на совместимую группу (до 16
экземпляров в группе). Uniform занимают не более 2064 байт; одиночный
элемент или отсутствующий батч-pipeline по-прежнему используют одиночный шейдер
Stage 26. Совпадающие группы шейдера/геометрии относятся только к представлению;
существующий батчинг цветовых отрисовок не изменяется.

**Скорости skinned и morph.** Объекты со скиннингом через палитру и примитивы с morph target
с ненулевым стабильным `persistentId` могут давать реальные
скорости деформированных вершин. Рендерер запоминает текущую палитру
суставов и восемь весов morph для каждой тройки
`(persistentId, nodeIndex, geometryPrimitive)`, сохраняя значения предыдущего
кадра независимо для каждой камеры. Отдельный шейдер деформирует
каждую вершину меша **и** для текущей, и для предыдущей позы, вычисляет
две позиции в clip space и сохраняет экранное смещение UV. Блоки текущего и
предыдущего U3/U4 вмещают до 80 суставов (по 3 строки); U5 содержит
два массива из 8 весов morph и параметры атласа morph; tex8 переиспользует
существующую текстуру дельт morph. Математика скиннинга/morph на GPU отделена
от детерминированной симуляции и не является загрузкой меша, деформированного на CPU.
Отсутствие предыдущей позы или изменение идентичности исходной модели
приводит к тому, что деформируемый примитив пропускает замену скорости объекта, а не
выдумывает движение.

**Motion blur с учётом краёв глубины.** Motion Blur теперь сэмплирует исходную
глубину сцены в каждой позиции сбора цвета и уменьшает вклад
через большие разрывы глубины. Это защищает контуры переднего плана
от посторонних цветов фона, хотя порог отбрасывания
основан на нелинейной аппаратной глубине, поэтому это консервативное
приближение, а не физически точная реконструкция движения по слоям глубины.
`Prisma::buildProgram` поддерживает `depth2d<float>` для явно помеченных
сэмплеров глубины на Metal, сохраняя соглашения GLSL sampler2D.

Критерии допуска намеренно остаются консервативными: видимые, непрозрачные
примитивы без смещения со стабильными ID. Запечённая анимация (поза которой
берётся из текстур клипов), смещение вершин материала через ShaderGraph,
прозрачные/masked модели и пользовательская геометрия пока не обрабатываются
новым pipeline скоростей деформации. Изменение размера цели скоростей, первый
кадр и camera cut запоминают history, а не экстраполируют невалидное
движение. Renderer3D владеет лениво создаваемыми шейдером/pipeline скоростей и временем жизни
цели.

**Проверка отложена** по просьбе пользователя: нативная компиляция,
проверка шейдеров Metal/GL, визуальное сравнение, CTest и профилирование GPU
НЕ ЗАПУСКАЛИСЬ. Не включайте эти экспериментальные пути по умолчанию до
их проверки. Подробности: `docs/handoffs/prisma-stage-27.md`.


## Stage 28 — движение запечённых клипов, скорости alpha-cutout и пороги глубины

Экспериментальный конвейер `motionBlur` теперь включает вариант шейдера
**скоростей вершин запечённых клипов**. Для `ModelItem` с `baked=true`
рендерер записывает текущие значения `anim` (строка клипа A, строка клипа B,
смешивание) и мировую матрицу по стабильной тройке `(persistentId, nodeIndex,
geometryPrimitive)`. Новый вершинный шейдер GLSL/MSL читает исходный
атлас запечённых костей (`tex7`) и исходную палитру суставов примитива.
Строки текущего и предыдущего клипов и интерполяция сэмплируются отдельно,
чтобы восстановить обе деформированные позиции вершины. Затем фрагментный шейдер скоростей
записывает нормализованное экранное UV-движение «текущее минус предыдущее». Снимок
history относится только к представлению; анимация и авторитетная
симуляция не изменяются. Этот путь намеренно пропускает одновременную деформацию
baked + morph, пока не появится смешанная перестановка.

Необязательный вариант скоростей **жёстких alpha-cutout** объектов теперь воспроизводит
порог отсечения альфы базовой текстуры материала с KHR texture transform
(offset/scale/rotation), базовой альфой и альфой цвета вершин (если
включена). Поскольку на поверхностях с отсечением есть пустые пиксели, отдельный
вариант сэмплирует альфу базовой текстуры и отбрасывает отвергнутые фрагменты
до проверки окклюзии по глубине. Эти материалы исключаются из
обычной instanced отрисовки скоростей непрозрачных объектов и рендерятся отдельно.
Поверхности со смещением через ShaderGraph и деформируемые модели с alpha-cutout
не включены, так как их видимая форма требует совпадения дополнительных
стадий материала. Полностью смешиваемые/прозрачные модели по-прежнему исключены.

History жёстких объектов теперь хранит идентичность исходной Model вместе с её
мировой трансформацией, не позволяя повторно использованному `persistentId` подхватить
предыдущую трансформацию другой модели. Существующие сброс по view, поведение
в первом кадре и при изменении размера сохранены.

`motionBlur` также принимает `depthThreshold` (по умолчанию 0.012, диапазон
0.0005..0.05) для отбрасывания посторонних слоёв глубины при
направленном сборе цвета. Шейдер возвращается к резкому сэмплу, если
все собранные сэмплы отброшены, вместо того чтобы подмешивать в
изображение чёрный цвет. Порог задаётся в **нелинейных единицах глубины устройства**, а не в метрах.
Пример:
```json
{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"shutterScale":1,"depthThreshold":0.012}
```

Все дополнительные пути остаются за уже существующими
`AIVERSE_PRISMA_MOTION_BLUR=1` и проверками HDR/качества. Они используют
тот же мост текстуры скоростей с маской и не изменяют gameplay ECS или
SpectraFX. Поза запечённых клипов и движение жёстких alpha-cutout объектов используют новые
варианты GLSL/MSL; никакое тестирование конкретных backend пока не подтвердило
совпадение их изображения. Сборки CPU/GPU, CTest, компиляция шейдеров,
скриншоты и бенчмарки **НЕ ЗАПУСКАЛИСЬ** по просьбе пользователя.
См. `docs/handoffs/prisma-stage-28.md`.


## Stage 29 — эпохи camera cut, реактивная прозрачность и скорости baked+morph

Экспериментальный путь HDR motionBlur в PRISMA теперь имеет три дополнительные
возможности только для представления, все за существующим runtime-флагом
`AIVERSE_PRISMA_MOTION_BLUR=1` и настроенным качеством.

**Явный жизненный цикл камеры/view.** `Prisma::resetMotionHistory(viewId)`
увеличивает монотонно растущую эпоху camera cut для каждого view, доступную через
`PostProcess::objectMotionEpoch(viewId)`. Renderer3D читает эту эпоху в
каждом opt-in проходе скоростей и отбрасывает прежние снимки трансформаций жёстких
и деформируемых объектов, когда она меняется. Это поддерживает согласованность
репроекции камеры и истории поз отдельных объектов при camera cut, телепортах, смене
качества и переконфигурации карты, не изменяя gameplay ECS. Рендерер
также предоставляет `resetObjectMotionHistory(viewId)` и
`resetAllObjectMotionHistory()` для явного автономного управления.
`releaseObjectMotionViewAfterGpuIdle(viewId)` освобождает GPU-текстуры
скоростей, реактивной маски и глубины для view **только** после того, как хост
подтвердил простой GPU; серийные номера кадров CPU НЕ являются сигналом завершения GPU.
Автоматическое закрытие viewport и GPU fence backend пока не подключены.

Новый read-only `Renderer3D::objectMotionStats()` возвращает ID view последнего
прохода скоростей, состояние отправки и счётчики отрисовок: экземпляры/отрисовки жёстких объектов, cutout,
skinned, baked, reactive и отклонённые. Эти значения —
диагностика отправки на CPU, а не измеренное время GPU или данные о производительности.

**Реактивные маски.** Renderer3D может выдавать отдельную текстуру реактивного
покрытия RGBA8 текущего кадра для видимых **жёстких, полупрозрачных ModelDraw**
примитивов. Она сэмплирует финальную глубину сцены и использует отдельный
временный depth attachment вместо изменения глубины сцены. Красный
канал — сила покрытия, а полностью нулевой фон означает отсутствие
реактивных пикселей. `PostProcess::acceptMotionReactiveMask` передаёт
заимствованный handle в PRISMA. Нативные рендереры могут вместо этого передать
заимствованную текстуру R=0..1 через
`Prisma::setMotionReactiveMask(viewId,texture)` перед resolve.
Шейдер motion blur сэмплирует эту маску в слоте текстуры 3 и уменьшает
локальную силу размытия на `1 - reactive * reactiveStrength`. При отсутствии
маски используется чёрный fallback, так что motion blur остаётся неизменным.

Новый необязательный параметр эффекта `reactiveStrength` по умолчанию равен 0.85
и имеет диапазон 0..1. Реактивный проход рендерера — консервативный
геометрический силуэт полупрозрачных жёстких моделей: он **не**
воспроизводит попиксельную смешанную альфу текстур, материалы с alpha-test,
скиннинг, частицы или воду, рисуемые другими модулями рендерера.
Ложноположительное реактивное покрытие может уменьшать размытие внутри стеклянной геометрии,
что предпочтительнее, чем выдумывать скорости объектов. Это остаётся
экспериментальным приближением.

**Запечённый клип + morph.** Вершинный шейдер запечённых скоростей теперь применяет
и текущие, и предыдущие веса morph к неизменяемым дельтам morph
(tex8) **до** сэмплирования текущей и предыдущей строк запечённого клипа
из tex7, соответствуя порядку деформации существующего цветового шейдера.
Параметры палитры, анимации и morph задаются для каждого примитива и
для каждого view; отсутствие предыдущего кадра или изменение идентичности модели по-прежнему
подавляет замену скорости объекта. Это не добавляет чтение вершин на CPU
и не меняет детерминированное состояние анимации.

Геометрия LOD-перехода, требующая экранного дизеринга, теперь
консервативно исключается из скоростей объектов, пока не реализован соответствующий шейдер
LOD fade; реконструкция движения камеры остаётся там
fallback.

Пример:
```json
{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"shutterScale":1,"depthThreshold":0.012,
 "reactiveStrength":0.85}
```

Нативная компиляция C++, проверка шейдеров, GPU-тесты, скриншоты
и CTest не запускались по просьбе пользователя. Новые GPU-проходы и
API времени жизни остаются opt-in, и их готовность к производству не доказана.
См. `docs/handoffs/prisma-stage-29.md`.


## Stage 30 — анимированное реактивное покрытие, расширяемые маски воды/частиц, fallback для LOD и дилатация скоростей

Существующая экспериментальная цепочка `motionBlur` теперь поддерживает анимированное
реактивное покрытие текущего кадра для полупрозрачной skinned, morph и
baked-clip геометрии `ModelDraw`. Эти **реактивные** проходы не
выдумывают предыдущие позы анимации и не подают скорость движения объектов: они
вычисляют *текущую* деформированную на GPU позицию вершины тем же
вершинным путём, что и шейдеры движения Stage 27/29, сэмплируют read-only
глубину сцены для видимости и помечают покрытые пиксели как реактивные (R=1).
Анимированные шейдеры Metal переиспользуют устоявшийся исходник вершинного шейдера
skinned/baked, подставляя фрагментный шейдер только для покрытия. Это обрабатывает
силуэты текущей позы baked+morph, но **не** воспроизводит
попиксельную альфу прозрачного материала, смещение вершин ShaderGraph,
экранную воду или частицы автоматически. Их точнее может
предоставить рендерер-владелец.

### Расширение реактивного покрытия для всех рендереров

`Renderer3D::addMotionReactiveDraw(fn)` регистрирует callback только для представления
в текущей сцене с сигнатурой

```cpp
void(gfx::Device& device, gfx::TextureHandle sceneDepth,
     int width, int height)
```

Регистрируйте **после** `beginScene()` и до `resolvePrisma()` (обычно
после отправки основного прохода сцены/цвета); регистрация callback
автоматически очищается после resolve текущей сцены. Callback
вызывается **внутри уже открытого реактивного render pass RGBA8**
с отдельной временной целью глубины; он никогда не должен вызывать
`beginPass/endPass`. Провайдер привязывает собственный шейдер, геометрию,
состояние текстур/констант и записывает красный канал R в [0,1] (0 = нет
реакции, 1 = подавить размытие согласно настроенной силе).
Используйте смешивание, совместимое с объединением покрытия, например
`gfx::BlendMode::Screen`, чтобы несколько провайдеров воды/частиц/объектов
объединялись, а не стирали друг друга. Текущий handle sceneDepth
можно только сэмплировать: никогда не привязывайте эту текстуру повторно как записываемый depth
attachment. Провайдер должен держать все заимствованные буферы/текстуры валидными
на протяжении callback и не может изменять состояние gameplay ECS.

Общий callback доступен для движков рендеринга и проектов,
реализующих воду, частицы, погоду или собственное представление. Stage 30
**не** инструментирует автоматически существующие пакеты воды/VFX;
их владельцы должны зарегистрировать свои реактивные callback рендеринга,
чтобы отрисовать правильное покрытие с семантикой своих материалов/геометрии.
Никакие callback не вызываются, если HDR MotionBlur не активен и нет
валидной history камеры; сама по себе регистрация не может заставить
цепочку постобработки запуститься.

Встроенные реактивные pipeline теперь используют смешивание Screen для накопления
нескольких перекрывающихся масок. Fallback для жёстких объектов также воспроизводит
правило покрытия с попиксельным дизерингом из `ModelShaders` для LOD
crossfade с дизерингом: эти пиксели помечают себя реактивными, а не
ошибочно получают обычные скорости жёстких объектов. Это
подавление размытия с учётом покрытия, **а не** полная реконструкция
векторов движения при смене LOD.

### Дилатация скоростей с согласованием по глубине

Новый параметр `motionBlur.velocityDilation` (по умолчанию 1.0,
диапазон 0..2, 0 отключает) сэмплирует четыре соседних значения скорости на
заданном радиусе, выбирая более сильную скорость только когда её
глубина устройства близко совпадает с центральным пикселем. Это помогает сохранить
движение вокруг силуэтов, не перенося движение с явно
другой глубины. Это локальная приближённая проверка глубины (в единицах аппаратной
глубины, а не в метрах), она стоит до четырёх дополнительных чтений скорости и
глубины на каждый размываемый пиксель. Оценщик стоимости учитывает эту
дополнительную работу, когда она включена.

Пример:
```json
{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"depthThreshold":0.012,"reactiveStrength":0.85,
 "velocityDilation":1}
```

Все добавления используют существующий opt-in флаг `AIVERSE_PRISMA_MOTION_BLUR=1`,
HDR RGBA16F и соответствующий уровень качества. Callback реактивных масок —
это расширение представления `Renderer3D`, независимое от владения
FPS, RTS, водой или SpectraFX.

**НЕ ЗАПУСКАЛИСЬ:** CMake/нативная компиляция C++, CTest, компиляция шейдеров Metal/GLES/GL,
скриншоты, профилирование памяти/производительности и CI, согласно
указанию пользователя сначала реализовать функции. Совпадение на оборудовании или готовность
к поставке не заявляются. См. `docs/handoffs/prisma-stage-30.md`.


## Этап 31 — реальная реактивная интеграция воды/частиц RTS и необязательная линейная глубина

Этап 30 ввёл общий интерфейс производителя `Renderer3D::addMotionReactiveDraw()`.
Этап 31 подключает **существующих runtime-производителей**:

- **Вода рельефа RTS и общая полупрозрачность мешей:** `RtsTerrainRender.cpp`
  ставит воду в очередь через `Renderer3D::drawMesh(water_, ..., waterColor)`.
  `Renderer3D::renderObjectMotionVectors` теперь подхватывает реальные
  буферы мешей полупрозрачных `DrawItem` (включая эти водные листы).
  Отдельный конвейер `MeshVertex` рисует ту же геометрию в реактивную
  маску RGBA8 с глубиной сцены только для чтения, без повторной генерации
  игровой геометрии. Сила маски равна альфе элемента отрисовки. Резервный
  шейдер двусторонний для водных листов. Другие полупрозрачные
  непосредственные отрисовки MeshVertex получают выгоду от того же пути.
- **Реальные billboard-частицы, шлейфы, ленты и меш-частицы:**
  `fx::ParticleSystem::render()` записывает не непрозрачные прогоны, которые он
  *действительно отрисовал*, включая исходную альфа-текстуру и диапазоны вершин.
  `hasReactiveGeometry()` сообщает, доступны ли эти прогоны.
  `renderReactive(gfx::Device&,sceneDepth,w,h)` выполняется **внутри уже
  открытого** прохода маски этапа 30, используя ровно тот вершинный/индексный буфер
  частиц текущего кадра, который был загружен, и альфа-текстуру. Он
  сэмплирует глубину сцены, объединяет исходную альфу с альфой вершины
  частицы и использует смешивание Screen, чтобы объединять перекрывающееся покрытие.
  Квады используют существующие 16-битные индексированные диапазоны; меш-частицы используют
  свои неиндексированные диапазоны треугольников. Нет второй симуляции
  частиц, CPU-расширения вершин или дополнительной загрузки вершин.
- **Клиент и редактор:** `GameClient.cpp` и `Editor.cpp` теперь
  регистрируют обратные вызовы сразу после `fx_.render` /
  `gameFx_.render` и до `r3d_.resolvePrisma()`. Обратные вызовы
  синхронно потребляют только что записанную геометрию частиц во время
  реактивного прохода текущей сцены. Они не сохраняются между
  кадрами вида.

Эти пути остаются **за** обычным эффектом `motionBlur`,
`AIVERSE_PRISMA_MOTION_BLUR=1`, требуемым форматом HDR и порогом minQuality.
Вода и частицы — жанронезависимые *производители* покрытия представления
текущего кадра; PRISMA по-прежнему владеет полноэкранной
постобработкой и не зависит от какого-либо конкретного модуля воды/FX.
Специализированные рендереры воды/частиц, не использующие эти два конкретных
пути, могут продолжать использовать существующий общий обратный вызов.

### Необязательная фильтрация по линейной глубине вида

`PostFrame` теперь несёт фактические ближнюю/дальнюю плоскости проекции
камеры и режим перспективы/ортографии. Рендерер заполняет
их из своей `RTSCamera`; ортографические near/far соответствуют её
явной проекции -200..1000.

`motionBlur` добавляет две необязательные настройки:
- `linearDepth` (по умолчанию false): если включено и плоскости проекции
  камеры корректны, для расширения скоростей и сбора размытия сравнивается **линейное расстояние
  вида**, а не нелинейная оконная глубина.
- `depthToleranceMeters` (по умолчанию 0.35; допустимый диапазон 0.01..10):
  допуск отбраковки ближнего/дальнего слоя в мировых единицах сцены (метрах,
  если проект использует метровый масштаб).

Рендерер использует обычную неинвертированную **оконную** глубину 0..1
и на GL, и на Metal; вспомогательная функция обрабатывает перспективную и
ортографическую проекции по отдельности. Если `linearDepth` равно false,
`depthThreshold` сохраняет прежнее значение в единицах аппаратной глубины,
поэтому ранее созданные сцены сохраняют исходное
поведение. Оба пути сэмплируют только текущий кадр и относятся
только к представлению. Пример:

```json
{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"depthThreshold":0.012,
 "linearDepth":true,"depthToleranceMeters":0.35,
 "velocityDilation":1,"reactiveStrength":0.85}
```

**Владение ресурсами:** реальный производитель частиц владеет своим шейдером
и двумя реактивными конвейерами и уничтожает их вместе с `ParticleSystem`.
`Renderer3D` владеет общим реактивным конвейером MeshVertex и
уничтожает его вместе с другими ресурсами движения объектов. Реактивный проход
владеет выходной текстурой; производители не должны начинать/завершать GPU-проходы или
уничтожать её исходную глубину. Сырые внешние реактивные текстуры/текстуры скоростей
по-прежнему не имеют переносимой интроспекции RHI для размеров
и форматов и должны проверяться своим владельцем.

**NOT RUN** (пользователь попросил сначала функции, потом тесты): нативный C++
компилятор, CMake, CTest, компиляция шейдеров Metal/GL/GLES, smoke-тест
редактора, сравнение изображений воды/частиц, замеры времени и GPU-профайлер.
Подтверждённого паритета или ускорения не заявляется. См.
`docs/handoffs/prisma-stage-31.md`.


## Этап 32 — специализированные водные маски SpriteBatch, живые метаданные текстур RHI и контракт освобождения по GPU-fence

Этап 31 подключил реальную воду рельефа RTS через `Renderer3D::drawMesh`.
Для **отдельного** спрайтового/декального пути воды этап 32 добавляет
реактивную отрисовку `SpriteBatch::drawWater` с учётом альфы: исходный
статический `SpriteMesh`, текстура воды и преобразование view-projection
записываются и могут быть зарегистрированы в текущей сцене через
`SpriteBatch::registerWaterReactive(renderer)`. Обратный вызов воспроизводит
только существующие буферы меша в открытом реактивном проходе. Отдельный
шейдер GLSL/MSL сэмплирует альфу водного листа и альфу оттенка каждой вершины
и отбрасывает пиксели, скрытые за исходной глубиной сцены.
Он использует `gfx::BlendMode::Screen`, чтобы вода объединялась с существующими
масками моделей/частиц, а не стирала их. Специализированный
резервный путь `drawWater` на освещённые декали остаётся без изменений.

**Важная область интеграции:** поиск по репозиторию не нашёл текущих
вызовов `SpriteBatch::drawWater` в этой ветке. Поддержка производителя
завершена на уровне API/исходников, но нативная игра, использующая специализированную
спрайтовую воду, должна явно вызывать `registerWaterReactive` после своих
вызовов `drawWater` и до `Renderer3D::resolvePrisma()`.
Обычная вода RTS через `drawMesh` уже регистрирует себя
автоматически. `SpriteBatch::begin` очищает захваченные отрисовки воды
каждый кадр, а регистрация их потребляет; никогда не уничтожайте её текстуры,
буферы мешей или SpriteBatch до завершения синхронного обратного вызова.

### Проверка внешних текстур скоростей и реактивных текстур

`PrismaMotionTextureInput.h` добавляет `MotionTextureInput`, невладеющий
дескриптор с необязательно объявленными шириной, высотой и `gfx::PixelFormat`.
Мост `PostProcess` получает новые типизированные перегрузки
`acceptObjectMotionVectors` и `acceptMotionReactiveMask`; исходные
перегрузки только с дескриптором сохраняются для существующих потребителей.

`Renderer3D` теперь передаёт типизированные входы для своих собственных
целей полного разрешения: скоростей RGBA16F и реактивной RGBA8.
В `Prisma::resolve` оба входа должны соответствовать размерам активного
вьюпорта и требуемым форматам. При обнаружении несоответствия скорость
объектов игнорируется и используется репроекция камеры; несовпадающая
реактивная маска считается отсутствующей (чёрный резервный вариант). Это не даёт
устаревшей текстуре Scene/Game другого размера сэмплироваться как корректный
вход. Владеющий рендерер сохраняет ответственность за время жизни на GPU.

RHI добавляет `gfx::Device::textureInfo(handle,out)` — запрос метаданных
только на CPU, реализованный в GL, Metal и Vulkan по их собственным живым
таблицам ресурсов. PRISMA проверяет **фактические метаданные RHI**
там, где они доступны, даже для устаревшего входа только с дескриптором. Для поставщиков,
чьи бэкенды не предоставляют метаданных, выполняется проверка по любым
объявленным метаданным; в противном случае существующий нетипизированный устаревший путь
по-прежнему считается доверенным ради совместимости. Этот API не выполняет обратного чтения с GPU и
не делает входные текстуры глобально самоописывающимися при передаче
за пределы RHI.

### Безопасная передача при выводе из работы старых целей движения

`Renderer3D` теперь использует `PrismaGpuRetirementQueue<gfx::TextureHandle>`
этапа 18 для текстур движения вида.
`setObjectMotionSubmittedFence(token)` регистрирует **фактически выданный бэкендом**
fence последней отправки для последующих изменений размера.
Старые цели скоростей/глубины/реактивные перемещаются в очередь освобождения,
а не уничтожаются сразу. `collectCompletedObjectMotion(
completedGpuFence)` уничтожает только те дескрипторы, fence отправки которых
был **подтверждён хостом как завершённый на GPU**. Ручной
`retireObjectMotionView(viewId,lastSubmittedFence)` переносит текущие
цели одного вида в эту очередь и отбрасывает его CPU-историю.

Если у рендерера нет корректного fence отправки, старые цели помещаются
в **карантин без fence**, где они удерживаются до вызова
`drainObjectMotionAfterGpuIdle()` при доказанно простаивающем GPU.
Обычное завершение движка сейчас предполагает, что хост достиг своей
существующей безопасной точки освобождения. Автоматической выдачи или опроса fence
бэкендом пока нет, поэтому это консервативное поведение по умолчанию может удерживать
память GPU на протяжении многих изменений размера вьюпорта до простоя. **Счётчики CPU-кадров
и произвольные задержки на N кадров не считаются GPU-fence.**

Более старый `releaseObjectMotionViewAfterGpuIdle` остаётся отдельным
синхронным API и должен вызываться только после простоя GPU.
Эти изменения не исправляют автоматически несвязанные пулы PRISMA `Sized`
или другие точки освобождения ресурсов рендеринга; для них нужны
собственные интеграции с учётом завершения на GPU.

Все добавленные GPU-пути включаются по желанию через
`AIVERSE_PRISMA_MOTION_BLUR=1`; ничего нового не включено по умолчанию.
**NOT RUN:** нативная компиляция, CTest, компиляция шейдеров GLSL/MSL,
изображения Metal/GL/Vulkan, замеры производительности GPU и CI.
Исходники не подтверждены как готовые к продакшену.
См. `docs/handoffs/prisma-stage-32.md`.


## Этап 33 — завершённые на GPU fence для безопасного освобождения ресурсов PRISMA

Рендерер теперь предоставляет отдельную **временную шкалу завершения на GPU** в
жанронезависимом интерфейсе `gfx::Device`:

```cpp
uint64_t submitted = dev.gpuSubmissionFence(); // current GPU frame, 0 if unavailable
uint64_t completed = dev.gpuCompletedFence();  // GPU-confirmed completion only
```

Токен отправки охватывает работу, закодированную в *текущем активном* GPU-кадре,
и не является счётчиком CPU-кадров. Его можно привязать к освобождению цели
до того, как этот кадр действительно отправлен; бэкенд завершит
его только после выполнения на GPU. Ненулевой результат `gpuCompletedFence()`
— это реальный, непрерывный токен завершённой временной шкалы GPU. Неподдерживаемые
устройства возвращают ноль. Все значения относятся к конкретному устройству; никогда не сравнивайте значения
разных устройств, контекстов или очередей GPU.

**Metal:** `GfxMetal.mm` использует токен кадра текущего командного буфера
и обновляет атомарный счётчик завершения в своём
`addCompletedHandler` **только** для
`MTLCommandBufferStatusCompleted`. Он не превращает
`frameSerial()` в fence завершения. Асинхронный обратный вызов
захватывает общее состояние с безопасным временем жизни, а поток-владелец графики
опрашивает его, читая `gpuCompletedFence()`.

**GL33 / GLES3 / WebGL2:** после команд рендеринга кадра бэкенд
вставляет `glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE,0)` и сбрасывает
поток команд без ожидания. При следующем `beginFrame` он
вызывает `glClientWaitSync(..., timeout=0)` для самого старого ожидающего fence,
продвигая токены завершения строго в порядке отправки и удаляя
сработавшие объекты синхронизации GL. Динамический загрузчик GL33 для Windows теперь загружает
`glFenceSync`, `glClientWaitSync`, `glDeleteSync`.
Неудачный fence никогда не считается успешным завершением.
Покадровый `glFinish` не добавлен.

**Vulkan:** использует уже существующие покадровые `VkFence` и
`serial_`. `gpuSubmissionFence` — серийный номер записываемого сейчас GPU-кадра;
`gpuCompletedFence` возвращает только наибольший серийный номер,
fence слота которого успешно подтверждён через
`vkWaitForFences`. Потерянное устройство или неудачное ожидание не
продвигают fence завершения. Это существующий путь ожидания слота, а не
новая реализация опроса, блокирующая лишние кадры.

### Автоматическое освобождение целей движения

`Renderer3D::beginScene` теперь вызывает
`collectCompletedObjectMotion(dev.gpuCompletedFence())` в
потоке-владельце графики. Когда вьюпорт меняет размер,
`queueObjectMotionTexture` берёт текущий
`dev.gpuSubmissionFence()`, если он доступен, и связывает его со
старой целью скоростей объектов, реактивной целью или временной целью глубины. По завершении
старые цели уничтожаются; до этого они удерживаются.
`retireObjectMotionView` и `setObjectMotionSubmittedFence`
остаются доступными для внешне управляемых жизненных циклов отправки.
На устройствах без поддержки fence отправки старые цели остаются в
карантине этапа 32 до явного простоя GPU.

### Отложенные цели PRISMA Sized / RenderGraph

`Prisma::sized` по-прежнему хранит три активные записи размеров для видов Scene/Game,
но при вытеснении давно не использовавшейся записи теперь
перемещает **весь** контекст `Sized` — устаревшие растровые цели, цели глубины,
кэшированный граф Bloom и постоянный пул ресурсов `PrismaRhiExecutor` —
в помеченный fence список освобождения вместо
немедленного освобождения. Когда GPU сообщает, что последняя
ссылающаяся отправка завершена, `collectCompletedSizes` освобождает
выведенные из работы цели и безопасно сбрасывает пул исполнителя графа.
Кроме того, `Prisma::target` теперь освобождает по fence цели, заменённые
из-за смены размера/формата HDR, избегая немедленного уничтожения текстуры,
которая может использоваться более ранним ещё выполняющимся командным буфером GPU.

`Prisma::releaseRetiredSizesAfterGpuIdle()` — запасной выход для
хостов, которые явно дождались простоя GPU; функция также
опустошает отдельные цели без fence / в карантине. Путь `shutdown`
предполагает обычное для платформы условие простоя GPU при уничтожении устройства.

Этот этап посвящён **корректности времени жизни ресурсов**, а не изменению
выходного изображения, топологии bloom, публичного JSON `postfx`, симуляции
частиц или игрового ECS. Существующие экспериментальные флаги по умолчанию
остаются выключенными.

### Ограничения

Новая временная шкала охватывает только команды обычной
очереди графической отправки бэкенда. Внешним очередям или устройствам GPU нужно
собственное отслеживание fence. Дескрипторы Metal освобождаются после обратного вызова
завершения командного буфера; возможности синхронизации GLES/WebGL и фактическое
поведение устройств ещё требуют проверки во время выполнения. Vulkan может
продвигать счётчик завершения только при переходе к слоту кадра, чей
fence был дождан. Без токена завершения на GPU выведенные из работы ресурсы
**не** освобождаются при удобном случае, и карантин может расти.

Покадровая история 1×1 Auto Exposure каждого вида, LUT PRISMA, внешние
буферы Sprite/FX и другие несвязанные кэши ресурсов рендеринга имеют
собственные существующие политики освобождения; не все они перенесены в
эту очередь. Очистка внутреннего пула RenderGraph откладывается вместе
с вытесненным контекстом `Sized`, а не исходя из предположения, что каждый
пиксельный проход завершился в конце CPU-кадра.

Нативная компиляция, CTest, тесты завершения на GPU для Metal/GL/Vulkan,
изображения и профилирование памяти **NOT RUN** согласно указанию пользователя
сначала делать функции. См. `docs/handoffs/prisma-stage-33.md`.


## Этап 34 — жизненный цикл истории каждой камеры по GPU-fence и диагностика редактора

Временная история PRISMA теперь явно **принадлежит стабильным ID видов**,
а не размеру цели рендеринга. Публичные API этапа 34:

```cpp
prisma.retireView(viewId);               // close only this camera's history
prisma.collectGpuRetirements();          // nonblocking, GPU-completed fence
auto post = prisma.retirementStats();    // read-only CPU diagnostics
auto motion = renderer.motionRetirementStats();
```

`retireView(id)` удаляет дескрипторы ping-pong текстур RGBA16F 1×1 Auto Exposure
этого вида из активной карты экспозиции и ставит их в очередь
через существующий механизм `retireTarget()` с учётом GPU-fence. Бэкенд
без fence удерживает их до подтверждённого хостом опустошения при простое GPU;
токен завершения на GPU позволяет собрать их без остановки.
Матрицы MotionBlur каждого вида, признак корректности и заимствованные дескрипторы
скоростей/реактивные текущего кадра отбрасываются без уничтожения этих
**внешних** заимствованных ресурсов. Важно, что `retireView`
**не** удаляет общие цели рендеринга сцены `Prisma::Sized`:
их могут по-прежнему использовать несколько камер Scene/Game одинакового разрешения.

`Renderer3D::retireObjectMotionView(id, fence=0)` теперь можно вызывать
без вручную переданного fence; очередь сначала запрашивает живой
`gpuSubmissionFence()` бэкенда. Его отдельные GPU-цели текущего кадра —
скорости, реактивная и глубины — освобождаются независимо от
экспозиции PRISMA. `Renderer3D::motionRetirementStats()` сообщает
число удерживаемых контекстов видов, число текстур с fence/без fence,
fence завершения GPU бэкенда и известное число ожидающих байт.

`Prisma::retirementStats()` сообщает активные/выведенные из работы контексты размеров,
число видов экспозиции/движения, текстуры с fence/без fence, выведенные из работы записи
пула графа, последний завершённый на GPU fence и **известный минимум**
удерживаемых байт GPU. Оценка байт использует `Device::textureInfo()` для
живых выделений RHI, включая архив целей `Sized` и
вложения глубины; она намеренно не выдумывает память для
внутренних выведенных из работы выделений графа, метаданные дескрипторов которых
уже отброшены. Статистика **не** является полным использованием VRAM.

### Переходы вьюпортов Scene/Game

В редакторе `Editor::frame` отслеживает, какой вид **действительно отрисовал
постобработку** в этом GUI-кадре. Когда вкладка Scene или Game скрыта,
закрыта, переключена в диагностический режим без постобработки или перестаёт
рендерить, редактор **однократно** выводит из работы состояние PRISMA этой камеры и её
цели движения Renderer3D, а затем продолжает собирать
подтверждённые бэкендом завершения на GPU в последующих кадрах редактора, даже
если ни один 3D-вьюпорт не рендерится. Повторное открытие вида начинает новую временную
историю вместо повторного использования устаревшей экспозиции после долгого скрытия.

Вид Scene использует стабильный ID `1`, а Game — `2`. Ранее редактор
использовал ID Game `2`, даже когда вкладка Scene повторно использовала
игровой рендерер во время игры; этап 34 передаёт явный ID `1`
в этом пути, чтобы предотвратить одновременное загрязнение движения и экспозиции
Scene/Game одинакового разрешения. Размещённый автономный игровой клиент
использует собственный экземпляр PRISMA и ID вида `3`.

Нативный `GameClient` аналогично выводит из работы вид `3` при новом матче
до замены камеры и карты и продолжает проверять
ожидающую работу GPU в кадрах меню/загрузки, когда 3D-рендерер не
рендерит.

Вкладка **Statistics** редактора теперь показывает новый раздел
`PRISMA · GPU resource retirement` с завершённым fence GPU,
активными/выведенными из работы контекстами размеров, историями видов, числом текстур с fence и
без fence, незавершёнными выделениями графа и
**минимальным известным объёмом в MiB**, удерживаемым PRISMA и Renderer3D.
Это только наблюдение, оно не создаёт обратного чтения с GPU или синхронизирующего
ожидания GPU.

### Перезагрузка ассетов проекта

`Prisma::setImageLoader` теперь освобождает по GPU-fence заменённые текстуры LUT и
пользовательских ShaderGraph, а не уничтожает их немедленно,
пока на них ещё может ссылаться другой кадр. Общие шейдерные
конвейеры и графы сохраняют существующее владение; меняется только
политика освобождения текстур.

### Ограничения / совместимость

API оставляет без изменений существующий JSON `postfx`, конфигурацию редактора,
поведение игр и ECS. Ни один новый эффект постобработки не включён
по умолчанию. Активные контексты `Prisma::Sized` по-прежнему индексируются выходными
размерами, **а не** ID отдельных камер, потому что содержат
переиспользуемые покадровые цели; по камерам индексируется только приватная история
экспозиции и движения.

`Viewport::color`/`Viewport::depth` (внешние кадровые буферы редактора)
и другие общедвижковые текстурные ресурсы **не**
освобождаются автоматически через `retireView`; время жизни ресурсов собственных кадровых буферов
редактора требует отдельной безопасной миграции на стороне владельца.
Если GPU никогда не предоставляет fence завершения, ожидающие выделения
остаются в карантине до явного простоя GPU. Байты GPU, показанные на
вкладке Statistics, — это нижние границы, а не полный учёт VRAM.

**NOT RUN** по просьбе: CMake/C++, CTest, работа редактора/клиента,
изображения GPU Metal/GL/Vulkan, smoke-тесты fence/пикселей, CI, профайлер и
тесты утечек памяти. Код и интеграции API существуют только на уровне исходников
и не проверены на реальном оборудовании.
См. `docs/handoffs/prisma-stage-34.md`.


## Этап 35 — освобождение кадровых буферов редактора по GPU и явное опустошение при нехватке памяти

Фактические цели рендеринга редактора `Viewport::color` и `Viewport::depth`
теперь используют те же принципы fence завершения на GPU, что PRISMA и
Renderer3D. Ими **не** владеет PRISMA: новый владелец
`apps/editor/ViewportGpuRetirement.h` живёт в экземпляре `Editor`
и переживает объекты его окон Scene/Game/FX. `Viewport`
привязывает этого владельца в `ensure(dev,w,h,owner)`, а `release()` /
изменение размера / уничтожение вьюпорта передают оба GPU-дескриптора
владельцу вместо прямого уничтожения ещё используемых изображений.

Старый дескриптор цвета может ещё находиться в команде отрисовки ImGui даже после
возврата из `Viewport::image()` окна, поэтому он уничтожается только
после того, как `gfx::Device::gpuCompletedFence()` покроет отправку, которая
может на него ссылаться. Ресурсы без fence помещаются в карантин, пока хост
явно не подтвердит простой GPU. Владелец также сбрасывает устаревшее
состояние вьюпорта `drawnFrame` / наведения при освобождении.

Все три производителя редактора (окна Scene, Game и FX) используют этого
общего владельца. Они освобождают скрытые/закрытые внеэкранные цели рендеринга,
не полагаясь на уничтожение окна; владелец удерживает ресурсы
дольше времени жизни окна. Скрытая/закрытая вкладка может позже заново создать
кадровый буфер без устаревших дескрипторов текстур ImGui.

### Политика при нехватке памяти

`ViewportGpuRetirement` сообщает число ожидающих текстур с fence/без fence,
вычисленный по метаданным `knownPendingBytes`, порог и признак
`overBudget`. Общий бюджет известных ожидающих ресурсов по умолчанию составляет
**128 MiB** и настраивается через
`AIVERSE_PRISMA_RETIRE_BUDGET_MB` (32..4096 MiB). Редактор
проверяет сумму *известных* ожидающих байт Viewport, PRISMA и
Renderer3D на **границе перед рендерингом** в `Editor::frame`,
до отправки любой новой отрисовки на GPU. Обычно он собирает уже
завершённые на GPU ресурсы **без ожидания**.

Если эта известная ожидающая память превышает бюджет, он может вызвать
новый явный хук `gfx::Device::waitForSubmittedGpuWork()` ровно
в этой безопасной точке. При успешной синхронизации он опустошает
очереди освобождения GPU Viewport, PRISMA и Renderer3D, включая
карантин без fence. Он никогда не освобождает ещё используемую текстуру исходя
из числа прошедших CPU-кадров.

Это явное ожидание только при нехватке памяти реализовано через `glFinish()`
на GL33/GLES3 (кроме WebGL), ожидание последнего **фактически
закоммиченного** командного буфера Metal (никогда не незакоммиченного буфера
текущего кадра) и `vkQueueWaitIdle` на Vulkan. **Эти ожидания
не выполняются каждый кадр**; они могут вызвать заметную однократную
остановку при нехватке памяти. Бэкенд WebGL2 явно возвращает
false, потому что переносимый синхронный барьер простоя не гарантирован;
ресурсы остаются в карантине до внешнего безопасного завершения.
Положительный результат ожидания охватывает только **ранее отправленные** команды GPU,
поэтому редактор должен вызывать его до того, как закодирует новую работу кадра,
использующую эти ресурсы.

Вкладка Statistics теперь показывает число ресурсов вьюпорта с fence/без fence,
известные ожидающие MiB относительно настроенного бюджета и кнопку
"Запросить безопасную очистку GPU". Эта кнопка лишь
запрашивает **однократную очистку на границе перед рендерингом следующего
кадра**, а не во время активного прохода ImGui окна Statistics.

**Порог — это рекомендательный бюджет нагрузки, а не глобальное
жёсткое ограничение VRAM GPU.** Внутренние выделения RenderGraph, активные ресурсы,
накладные расходы драйвера и неизвестные/неподдерживаемые дескрипторы текстур RHI
могут не входить в оценку нижней границы. Если бэкенд не может
синхронизироваться, редактор намеренно удерживает память, а не
рискует использованием GPU-ресурса после освобождения.

Прежние API RHI `gpuSubmissionFence()` /
`gpuCompletedFence()` не изменились, а новый
`waitForSubmittedGpuWork()` необязателен. Все флаги постобработки
по умолчанию остаются выключенными; владение ECS/игровой логикой не меняется.

**Проверка:** только просмотр исходников и запись в GitHub.
Нативная компиляция, CTest, работа Metal/GL/Vulkan/Android/WebGL,
время жизни текстур ImGui, smoke-тест нагрузки GPU-fence и профилирование VRAM
**NOT RUN**, как и просили. См.
`docs/handoffs/prisma-stage-35.md`.


## Этап 36 — завершение размещённого GameClient, время жизни снимков экрана, освобождение превью ShaderGraph и учёт памяти графа

### Владение GPU размещённого GameClient

`ClientHost::stop()` редактора теперь логически останавливает размещённый клиент
сразу (так что UI больше не направляет ему события или кадры), но перемещает
его инициализированный объект `GameClient`, его прежний HostedView и
текущий токен графической отправки в список отложенного освобождения. Он
**не вызывает `GameClient::shutdown`, пока на его GPU-текстуры ещё могут
ссылаться текущий или предыдущие командные буферы редактора.**

`ClientHost::collectGpuRetirements()` проверяет завершение на том же
`gfx::Device`, который владеет архивированным клиентом. Как только бэкенд
действительно подтвердил его fence отправки, владелец восстанавливает
сохранённый размещённый вид платформы этого клиента и вызывает его завершение в
потоке-владельце графики/UI. Редактор вызывает этот сборщик в начале
каждого GUI-кадра, в том числе после закрытия вкладки Game.
`ClientHost::drainAfterGpuIdle()` доступен в подтверждённой хостом точке
простоя GPU для клиентов, у которых fence отправки не было.
Редактор включает это опустошение в очистку при нехватке памяти и
путь завершения графического устройства. Если в архиве ожидают завершения на GPU
более двух размещённых клиентов, их **количество** (а не возраст в CPU-кадрах)
также запускает попытку настоящего простоя GPU перед рендерингом в
следующем кадре. Если бэкенд не может подтвердить простой, они удерживаются,
а не освобождаются небезопасно.

Если токен отправки GPU недоступен, архивированный клиент
помещается в карантин, а не уничтожается во время обычного кадра; его
GPU-ресурсы могут оставаться выделенными до безопасного завершения хоста.
Вкладка Statistics редактора показывает `ClientHost::pendingRetiredClients()`
в виде количества. Его байты GPU **пока не** включены в числовую
оценку ожидающей памяти, поэтому бюджет 128 MiB остаётся триггером по нижней границе,
а не жёстким ограничением VRAM.

### Безопасность обратного вызова снимков экрана редактора

`Editor::deliverShots` использует существующий API графического бэкенда
`Device::captureNextFrame`, в зону владения которого входят
собственные промежуточные ресурсы/ресурсы захвата бэкенда, а не принадлежащая Editor
внеэкранная текстура. Раньше обратный вызов захватывал незащищённый
`this`; теперь он также захватывает общий атомарный токен времени жизни.
`Editor::shutdown` аннулирует этот токен и очищает очередь
запросов снимков; поздний обратный вызов возвращается, не обращаясь к
уничтоженному Editor, не отправляя ответы MCP через закрытое соединение
и не трогая его указатели на вьюпорты. Новая инициализация Editor
создаёт новый токен для нового времени жизни. Бэкенд по-прежнему
владеет своими промежуточными буферами захвата; эта защита не меняет политику
обратного чтения с GPU и не вызывает синхронизацию GPU.

### Буферы цвета/глубины превью ShaderGraph

`ShaderGraphPreview` теперь привязывает общий `ViewportGpuRetirement`
редактора при инициализации и передаёт свои
две цели рендеринга цвета/глубины 256×256 этому менеджеру при замене
графа или завершении превью. На эти текстуры ещё могут
ссылаться изображение ImGui или предыдущий GPU-проход; менеджер
освобождает их только после подтверждённого fence завершения на GPU или при
явном опустошении хостом в простое. Менеджер переживает все объекты окон
редактора. Другие принадлежащие превью ShaderGraph конвейеры, портреты
материалов, системы частиц и кэши текстур сохраняют существующие
политики жизненного цикла; этот этап **не** утверждает, что каждый подресурс превью
полностью управляется по fence.

### Телеметрия памяти RenderGraph

`PrismaRhiExecutor::gpuMemoryStats()` возвращает:
`liveTextures`, `pendingTextures`,
`liveKnownBytes`, `pendingKnownBytes` и
`unknownFormatsOrDimensions`. Учёт перечисляет
**фактические** живые выделения `PrismaGraphResourcePool` и
ожидающие дескрипторы `PrismaGpuRetirementQueue` с помощью запроса RHI
`Device::textureInfo`. Обратное чтение с GPU или остановки не требуются.

`Prisma::retirementStats()` агрегирует активные и выведенные из работы
пулы графа `Sized` по отдельности. Ресурсы, принадлежащие архивированному
набору размера, считаются ожидающими, даже если были живыми в этом наборе до
вытеснения; текущие активные выделения графа учитываются как *живые*
и не добавляются в бюджет ожидающих. Вкладка Statistics редактора показывает
дополнительные живые/ожидающие MiB графа, число неизвестных выделений и
число отложенных размещённых клиентов.

Это улучшает оценку нехватки памяти по известным ожидающим ресурсам этапа 35,
но сжатые/разреженные текстуры, накладные расходы драйвера и ресурсы за пределами
графа PRISMA или размещённого клиента не дают полного учёта
VRAM.

Вся существующая схема `postfx` и флаги включения экспериментальных эффектов
не изменились. В PRISMA не вводится поведение, специфичное для FPS/RTS;
код размещённого клиента, снимков экрана и превью остаётся у своих
владельцев.

**Статус проверки:** только просмотр исходников и коммиты в GitHub.
CMake, C++/Obj-C++, CTest, работа Metal/GL/Vulkan, обратные вызовы
захвата снимков, smoke-тест докинга/превью графа, профилирование времени
жизни GPU и CI **NOT RUN** по просьбе пользователя. См.
`docs/handoffs/prisma-stage-36.md`.


## Этап 37 — общее освобождение шейдеров, конвейеров, буферов по GPU-fence, горячая перезагрузка FX

Этап 37 распространяет политику времени жизни по завершению на GPU с текстур
и ресурсов вьюпортов на **все категории дескрипторов RHI, используемые
горячей перезагрузкой Shader Graph и VFX**.

`engine/render/GpuResourceRetirement.h` вводит
жанронезависимую службу времени жизни для потока-владельца графики с
перегрузками для `gfx::PipelineHandle`, `ShaderHandle`,
`BufferHandle`, `TextureHandle` и `ComputeHandle`.
Каждый выводимый из работы дескриптор отсоединяется от прежнего владельца и хранится с
токеном отправки GPU из `gfx::Device::gpuSubmissionFence()`.
Нулевой токен отправляется в карантин. Подтверждённый
`gpuCompletedFence()` позволяет неблокирующее освобождение; явный
`drainAfterGpuIdle()` требует реальной гарантии простоя GPU.

Когда несколько GPU-дескрипторов становятся пригодными одновременно,
служба уничтожает конвейеры раньше шейдеров, сохраняя зависимости.
Она также поддерживает `retireOwned(device,cleanup,knownBytes)` для
сложных наборов владельцев рендеринга, у которых внутренний порядок уничтожения
уже инкапсулирован. Обратный вызов вызывается **только после**
завершения на GPU в потоке-владельце графики и никогда — из
потока обработчика завершения Metal. Служба отслеживает число ожидающих
ресурсов по типам, записи с fence/без fence и необязательные
известные байты; это нижние границы, а не полные метрики VRAM.
Она владеет ресурсами исключительно; не передавайте ей заимствованные дескрипторы.

### Превью Shader Graph: освобождение набора целиком

Редактор Shader Graph теперь удерживает **весь предыдущий** объект
`ShaderGraphPreview` при смене ассета графа/проекта/домена.
Архивированный объект включает его Portrait/Renderer3D,
ParticleSystem, PRISMA, TextureCache, шейдеры, конвейеры,
вершинные буферы и цели цвета/глубины превью.
Новое превью создаётся отдельно. `shutdownAfterGpuCompletion()`
старого превью выполняется только тогда, когда его последний fence
отправки GPU действительно завершён (или при явном простое GPU).
Это устраняет прежнее немедленное уничтожение конвейеров/шейдеров, пока
предыдущий GPU-кадр ещё может ссылаться на эти ресурсы.

Изменение только UI-поля `position` узла **не** аннулирует
ресурсы GPU-превью шейдера; и окно, и превью используют
общий `ShaderGraphPreview::resourceKey(graph)`, исключающий экранные
позиции узлов. Фактические изменения шейдерных узлов, связей,
параметров или домена по-прежнему создают новый набор GPU-превью.

### Горячая перезагрузка FX и TextureCache в редакторе

`fx::ParticleSystem` предоставляет необязательный хук
`setGpuResourceRetirement(owner)`. Если он подключён,
`reloadAll()` выводит из работы каждый предыдущий конвейер варианта шейдерного графа
и шейдер, а не вызывает напрямую `destroyPipeline` /
`destroyShader`, пока предыдущие отрисовки могут выполняться. Его
обычный `shutdown()` также выводит из работы собственные буферы частиц, варианты
шейдеров, конвейеры, встроенную текстуру атласа и реактивные GPU-ресурсы.
Старый путь немедленного освобождения владельцем сохраняется для runtime-клиентов без
владельца освобождения.

`render::TextureCache` аналогично получил необязательный хук
`setGpuResourceRetirement(owner)`. При перезагрузке/завершении он
устраняет дубликаты кэшированных дескрипторов текстур и страниц атласа, ставит каждую
собственную текстуру в очередь ровно один раз и сохраняет устаревший путь
очистки по умолчанию, если владелец освобождения не подключён.

Основной производитель FX редактора (`gameFx_` и `fxTextures_`) и
отдельное окно превью FX подключены к этой службе. Существующие
данные рендеринга и ECS не изменяются.

### Жизненный цикл редактора, нехватка памяти и UI

`Editor` владеет `GpuResourceRetirement` независимо от своих
окон; он собирает завершённые на GPU ресурсы в каждом кадре перед рендерингом
и опустошает очередь в подтверждённой точке простоя GPU при нехватке памяти/завершении.
Оценка нехватки ожидающей памяти этапа 35 включает известные
байты этих записей ресурсов. Более восьми ожидающих
наборов превью целиком тоже служит сигналом нехватки для **реальной**
попытки простоя GPU перед рендерингом, а не разрешением предполагать завершение.
В путях без поддержки или с неудавшимся fence ресурсы удерживаются,
а не уничтожаются раньше времени.

Окно Statistics теперь отдельно показывает ожидающие
конвейеры, шейдеры, буферы, текстуры, наборы владельцев и число с fence /
без fence. Нижележащая память GPU наборов известна не полностью,
поэтому бюджет остаётся рекомендательным минимумом.

### Ограничения

Это **не** переносит автоматически каждого производителя в
движке: нативная игра, собственный модуль рендеринга или плагин должны
подключить владельца времени жизни, прежде чем уничтожать шейдеры/конвейеры/буферы
посреди кадра. Интеграции Shader Graph и FX редактора — конкретные
пути. Несколько внешних очередей/устройств GPU требуют собственной
синхронизации и владельцев. Полное уничтожение графического устройства
по-прежнему требует фактической гарантии простоя GPU; ожидающий обратный вызов
не должен разыменовывать уже уничтоженный `gfx::Device`.

Исходный JSON `postfx`, визуальные эффекты PRISMA, игровой ECS,
конфигурации функций воды/VFX и выключенные по умолчанию экспериментальные флаги
остаются без изменений.

**NOT RUN** по указанию пользователя: нативные сборки, CTest,
работа драйверов Metal/GL/Vulkan, снимки экрана, smoke-тест горячей перезагрузки превью FX,
профилирование VRAM и CI. Коммиты на уровне исходников и просмотр символов
не подтверждают корректность во время выполнения. См.
`docs/handoffs/prisma-stage-37.md`.


## Этап 38 — дополнительные владельцы Portrait, метаданные буферов и отказ от ресурсов при потере GPU-устройства

Редактор теперь использует существующий API этапа 37
`render::GpuResourceRetirement::retireOwned()` для дополнительных
**полных владельцев рендерера Portrait** в окнах Model и Materials.
Раньше эти окна хранили встроенный `game::Portrait`
и сразу выполняли его `shutdown()` при уничтожении панели.
Теперь они удерживают весь старый портрет (Renderer3D, сгенерированные
модели, вершинные/индексные буферы, шейдерные конвейеры, текстуры цвета/глубины)
в отложенном наборе владельца графики. Его очистка выполняется только после
фактического fence завершения GPU соответствующего устройства или явного
подтверждённого хостом опустошения при простое GPU. При закрытии окна или потере
выбранной вкладки дока старый портрет выводится из работы; повторное открытие создаёт
новый портрет без повторного использования предыдущих ещё используемых GPU-дескрипторов.
Автономный просмотрщик моделей и другие клиенты с иным
владением не изменены.

### Метаданные выделений буферов RHI

`gfx::BufferInfo` и необязательный
`gfx::Device::bufferInfo(BufferHandle,BufferInfo&)` предоставляют
запрос живых ресурсов только на CPU. Бэкенды GL, Metal и Vulkan читают
собственные таблицы буферов без ожидания GPU или обратного чтения.
Результат содержит `logicalBytes` и `versions` (копии динамических буферов
могут занимать дополнительную память GPU). Они описывают **логический размер
выделения буфера**; динамические снимки Metal/Vulkan и выравнивание
аллокатора GPU могут превышать этот объём.

`GpuResourceRetirement::retire(device,buffer)` теперь автоматически
использует `bufferInfo` для оценки удерживаемых байт, если производитель
не указал их. Выводимые из работы текстуры аналогично используют фактические
ширину, высоту и формат пикселей из `textureInfo`. Это улучшает
оценку известной ожидающей памяти для горячей перезагрузки графов FX редактора,
превью моделей и кэшей текстур. Это по-прежнему не точный счётчик общей
VRAM GPU; выделения драйвера под шейдеры/конвейеры и сложные
наборы владельцев превью могут иметь неизвестный размер.

### Обработка окончательной потери устройства

`GpuResourceRetirement::collect()` проверяет
`Device::gpuHealthy()`; если устройство потеряно, она **не**
вызывает никаких функций `destroyShader`, `destroyPipeline`, `destroyBuffer`,
`destroyTexture` или `destroyCompute`. Новый явный
`abandonDevice(device)` удаляет ожидающие сырые дескрипторы RHI без
вызова API мёртвого GPU. Полные наборы владельцев опаснее:
уничтожение захваченного объекта `ShaderGraphPreview` может транзитивно
вызвать `Device` в его деструкторе. Их обратные вызовы перемещаются в
инертный приёмник-сирот со временем жизни процесса **без деструктора**. Это
намеренно удерживает эту память CPU до выхода из процесса, а не
рискует использованием после освобождения после окончательной потери устройства.

Обычный деструктор `GpuResourceRetirement` также не допускает неявного
выполнения небезопасных обратных вызовов наборов, если хост
предварительно не опустошил очередь в подтверждённой точке простоя GPU. Завершение редактора
вызывает `abandonDevice`, когда `gpuHealthy()` равно false.
`ClientHost::abandonOnDeviceLoss()` предоставляет аналогичный окончательный
путь для отложенных владельцев размещённого GameClient, которые иначе могли бы
уничтожать вложенные рендереры при мёртвом GPU Device. Устройство архивированного
клиента должно совпадать с подтверждённым источником завершения.

Окно Statistics показывает брошенные дескрипторы/наборы для
диагностики. **Отказ от ресурсов — аварийный резервный путь при потере устройства/завершении,
а не обычное освобождение памяти**, и он не заменяет
восстановление устройства, пересоздание целей рендеринга или обработку старых политик
владения других подсистем рендеринга.

### Область действия и ограничения

Общая служба освобождения GPU остаётся относящейся только к представлению,
жанронезависимой и подключаемой по желанию для владельцев, которые могут гарантировать, что
устройство живо во время обычного сбора. Окна Model и Materials —
дополнительные конкретные пользователи; редактор Animation Graph,
внешний просмотрщик моделей и другие независимые владельцы превью
остаются на собственных путях времени жизни и должны быть перенесены
через аналогичный самодостаточный полный набор владельца.

Без изменений ECS, игровой логики FPS/RTS, схемы эффектов postfx,
HDR-вывода шейдеров, воды или выключенного по умолчанию флага Motion Blur.

**NOT RUN:** сборки CMake/C++/Obj-C++, CTest, GPU-fence GL/Metal/Vulkan
во время выполнения, переключение вкладок Model/Materials в редакторе,
симуляции потери устройства, профилирование памяти, снимки экрана и CI
(по указанию пользователя). Статический просмотр исходников не доказывает
корректность во время выполнения. См. `docs/handoffs/prisma-stage-38.md`.


## Этап 39 — наборы превью Animation Graph/Rig и стабильное состояние редактора

Окна Animation Graph и Rig теперь разделяют с редакторами Shader Graph и
Model/Materials **отложенный по GPU-fence жизненный цикл превью**, относящийся
только к представлению. В `apps/editor/animation/AnimationEditor.h`
`AnimationEditorPanel::release()` отсоединяет *полный набор владельца*
старого превью: загруженную `render::Model`, неизменяемое скомпилированное
состояние `AnimationGraphInstance`, которое может ссылаться на эту модель, и
`game::Portrait` с собственным Renderer3D, конвейерами, текстурами
и целями рендеринга цвета/глубины. Прежний владелец остаётся жив
в `GpuResourceRetirement::retireOwned`, пока не завершится его фактический
fence отправки GPU бэкенда или не наступит подтверждённый хостом простой GPU.
Его очистка сбрасывает граф **до** освобождения GPU-буферов модели,
на которую он ссылается, и освобождает GPU-ресурсы Portrait в
той же безопасной точке. Данные ECS редактора или симуляции анимации
менеджеру освобождения не передаются.

И `AnimationGraphWindow`, и `AnimationRigWindow` вызывают
`AnimationEditorPanel::suspendPreview()` для скрытой или закрытой вкладки
дока, освобождая память GPU без стирания документа редактора.
Когда вкладка снова становится видимой, из текущего документа строится новая Model/Portrait.
`release()` намеренно сохраняет
`doc_`, `saved_`, историю undo/redo, текущий выбранный узел, область
графа, заданный пользователем переключатель воспроизведения, высоту земли, рыскание, масштаб,
раскладку камеры/холста и значения элементов управления анимацией.

При повторной компиляции программы числовые и векторные параметры
превью с совпадающими именами восстанавливаются из предыдущих
`AnimationParameters`; новые/удалённые параметры по-прежнему используют
определения текущего графа. *Часы выполнения* скомпилированного графа
и временное состояние каждого узла могут перезапуститься после перезагрузки
модели/освобождения при скрытии вкладки — небезопасной передачи
указателей графа, привязанных к модели, между моделями нет.

Чисто визуальные изменения `position` узлов графа больше не аннулируют
ключ скомпилированной программы превью анимации (включая вложенные
подграфы). Перетаскивание узлов не перезапускает без необходимости текущее
воспроизведение анимации. Тот же этап исправляет ранее написанный
цикл GPU-ключа ShaderGraphPreview, чтобы он использовал изменяемый итератор
узлов JSON (`itemsMut()`) вместо константного представления items; это
исправление корректности типов на уровне исходников, ожидающее фактической компиляции.

Независимая галерея `aiverse_modelview` имеет другой
жизненный цикл: её Portrait и рендереры обычно освобождаются при
завершении всего просмотрщика, а не при горячей перезагрузке отдельной вкладки редактора.
Её завершение теперь пытается выполнить `Device::waitForSubmittedGpuWork()`
до уничтожения Gallery/Portrait и GPU-ресурсов импортированных
моделей. Это ожидание — защита по мере возможности **только при завершении**,
а не замена собственного обязательного для платформы контракта
завершения при простое GPU на неподдерживаемых бэкендах.

Без изменений игрового ECS FPS/RTS, формата JSON графов анимации,
алгоритмов анимации, настроек эффектов PRISMA, рендеринга воды или
выключенного по умолчанию флага функции MotionBlur.

**NOT RUN:** CMake, сборка C++/Objective-C++, CTest, проверка GPU-fence
Metal/GL/Vulkan, скрытие/повторное открытие вкладок, smoke-тест воспроизведения аниматора,
снимки экрана ModelView, профилирование памяти и CI. Просмотр исходников
не может удостоверить фактическую корректность времени жизни на GPU.
См. `docs/handoffs/prisma-stage-39.md`.

## Этап 40 — независимая от GPU контрольная точка часов превью (Animation Graph/Rig)

Когда вкладка редактора Animation Graph или Rig скрывается или загруженная
модель превью перезагружается, освобождение превью по GPU-fence из этапа 39 больше не
всегда перезапускает простое воспроизведение анимации с нуля.

`AnimationGraphInstance::snapshotPreviewClocks()` предоставляет необязательный
`PreviewClockSnapshot` без указателей с ID активного состояния, его прошедшим
временем, именами и часами узлов клипов, идентичностями/длительностями исходных клипов, ID
состояний, порядком видов узлов и именами/родителями скелета загруженной модели.
`restorePreviewClocks(snapshot)` сначала проверяет все эти факты
по заново скомпилированному графу и отклоняет некорректный снимок, не
изменяя частично текущий экземпляр. Редактор *также* требует
того же пути модели и того же ключа авторской программы (исключающего
изменения только визуальной позиции узлов), прежде чем пытаться восстановить.

Это намеренно узко: граф с идущим затуханием перехода,
подграфами, нативными операторами, состоянием рига, motion matching, контроллерами,
трейтами или другими узлами с состоянием перезапустится, а не будет заново привязывать потенциально
зависящее от модели состояние CPU. Простые графы bind/clip/blend/additive/two-bone IK
могут восстанавливать состояние и время клипа при условии, что программа графа и
идентичности скелета/клипов не изменились. Камера, документ, элементы управления,
переключатель воспроизведения и undo/redo остаются как на этапе 39. Явные New/Load/
Discard и Preview Reset очищают сохранённую контрольную точку; изменённая программа
графа или несовместимая загруженная модель не могут её использовать.

Файлы: `engine/render/AnimationGraph.h`,
`engine/render/AnimationGraph.cpp`,
`apps/editor/animation/AnimationEditor.h`.
Это только состояние представления превью; игровой ECS, схема JSON графов
анимации, эффекты GPU-шейдеров Prisma, SpectraFX и политика fence освобождения GPU
не изменены.

**NOT RUN:** нативная компиляция, CTest, воспроизведение в UI редактора, тесты fence
Metal/GL/Vulkan и CI (направление «сначала функции»). См.
`docs/handoffs/prisma-stage-40.md` с SHA закоммиченных исходников и следующим шагом.

## Этап 41 — резидентность памяти по видам, общие пулы графов и вытеснение простаивающего кэша по fence

Этап 41 добавляет в владельца представления Prisma **диагностические вызовы
без GPU, только для чтения**, не меняя вывод шейдеров или состояние игрового ECS:

- `Prisma::memoryStats()`: сообщает активные цели кадрового буфера, привязанные к размеру,
  вложения глубины, живые пулы текстур RenderGraph, приватную для вида историю Auto Exposure,
  постоянные входы LUT/изображений графа и отсутствующие метаданные RHI.
  `MemoryStats::liveKnownBytes` учитывает каждый фактический кэш размера **один раз**,
  даже когда у Scene и Game одинаковые ширина/высота. Повторяющийся для каждого вида
  `ViewMemoryStats::sharedKnownBytes` — поясняющая *ссылка* на
  этот кэш, **а не суммируемое выделение вида**.
- `ViewMemoryStats` записывает последнее успешно выделенное разрешение прохода сцены
  постобработки для каждого стабильного ID вида (Scene=1, Game=2 в редакторе;
  нативные пользователи могут задавать собственные ID). Его `ownedHistoryKnownBytes` для каждого вида
  — это приватная история экспозиции, тогда как пул RenderGraph принадлежит `Sized`
  и может разделяться несколькими ID видов.
- `PrismaRhiExecutor::GpuMemoryStats` теперь различает неизвестные **живые**
  текстуры и неизвестные **ожидающие** текстуры. Мипы, копии с мультисэмплингом,
  сжатие, выравнивание бэкенда и выделения драйвера под шейдеры/конвейеры
  невозможно вывести из текущего интерфейса `TextureInfo`: числа — нижние
  границы, а не бюджет VRAM или сертификат резидентности на GPU.
- `GpuResourceRetirement::Stats` отдельно показывает отложенные наборы владельцев
  (включая наборы превью ShaderGraph/Portrait) **без надёжной оценки
  байт**. Нулевая оценка никогда не означает набор нулевой стоимости.
- `ViewportGpuRetirement` имеет невладеющий реестр живых кадровых буферов для
  окон Scene/Game/FX. `Viewport::ensure()` публикует дескрипторы цвета+глубины
  и размер, а `Viewport::release()` снимает их с регистрации перед освобождением
  текстур по fence. `liveStats()` даёт нижнюю границу использования памяти каждым окном;
  он **не** даёт владения этими дескрипторами RHI.
- `StatsWindow` теперь показывает байты активного общего кэша постобработки,
  приватные байты экспозиции каждой камеры, байты кадровых буферов Scene/Game/FX,
  устаревшие/не используемые кэши, ожидающие байты графа и отсутствующие оценки байт,
  не суммируя повторяющиеся общие значения для каждого вида.

**Время жизни простаивающего кэша размеров:** `Prisma::retireView(id)` удаляет ссылку
стабильного вида, но не уничтожает общие цели сцены. В конце
работы редактора с вьюпортами `Prisma::retireUnreferencedSizeCaches()` просматривает
небольшой кэш размеров и перемещает в `RetiredSized` только размеры, на которые
**не** ссылается ни один живой вид, используя fence графической отправки. Ресурсы
действительно освобождаются только в существующем неблокирующем сборщике с подтверждённым
завершением на GPU или в явном пути с подтверждённым простоем GPU. Когда постобработка
отключена для одной камеры, Editor теперь помечает этот вид неактивным и выводит из работы его
старую ссылку; он больше не удерживает устаревший кэш только потому, что вкладка Game
продолжает рендерить без эффектов. Это может приводить к новым выделениям при
повторном открытии, обменивая «тёплость» кэша на ограниченную память простаивающего редактора.

Эта диагностика и пути освобождения подключаются по желанию и относятся только к представлению; PRISMA
по-прежнему владеет постобработкой. Эмиттеры FX остаются в SpectraFX, а runtime-игры,
не использующие редактор, по-прежнему свободны выбирать собственное удержание кэша.
Компоненты игровой логики/ECS, специфичные для FPS/RTS модули камер и схемы JSON `postfx`
не изменялись.

**Проверка:** только повторное чтение исходников в GitHub и статический просмотр мест вызова.
**NOT RUN** («сначала функции»): нативные сборки, CTest, запуск GPU-fence/драйвера,
smoke-тесты Metal/GL/Vulkan/WebGL, переключение вкладок/изменение размера GUI и профилирование VRAM. Никогда
не интерпретируйте отсутствующий счётчик метаданных как завершённый бенчмарк. Полный перечень путей
и SHA, зависимости и следующие шаги:
`docs/handoffs/prisma-stage-41.md`.

## Этап 42 — подключаемый по желанию HDR temporalResolve (репроекция истории в полном разрешении)

Эта функция расширяет существующий **канонический конвейер Prisma**, а не
историческую обёртку `PrismaScreenLighting`. Обычный каталог `postfx` теперь
поддерживает эффект `temporalResolve` с четырьмя параметрами, настраиваемыми
через редактор/MCP/объёмы. Существующие ID эффектов, корни JSON `postfx`, сохранённый ID панели и
заголовки совместимости PostFx не изменились.

Для активации хост должен использовать **HDR/High** и явно включить функцию через
`AIVERSE_PRISMA_TEMPORAL=1` в дополнение к авторскому эффекту:

```json
{
  "postfx": {
    "effects": [
      {
        "type": "temporalResolve",
        "minQuality": "high",
        "historyWeight": 0.86,
        "depthThreshold": 0.0075,
        "motionScale": 0.04,
        "reactiveStrength": 0.95
      }
    ]
  }
}
```

`Prisma::resolve()` теперь повторно использует **единственный проход знаковых скоростей
в полном разрешении** и для Temporal Resolve, и для Motion Blur, если они запрошены. Скорость —
это разность нормализованных UV текущего и предыдущего кадров, включающая репроекцию камеры и
необязательную скорость объектов/деформаций Renderer3D (RGBA16F, бит присутствия в B);
при некорректных метаданных поставщика используется скорость камеры. Реактивное покрытие RGBA8
текущего кадра заимствуется из обратных вызовов Renderer3D/частиц и
никогда не сохраняется как временная история.

Каждый `viewId` владеет двумя текстурами **линейного HDR RGBA16F** в полном разрешении,
с цветом в RGB и **предыдущей аппаратной глубиной** в альфе. Временной шейдер
выполняет репроекцию по знаковым векторам движения, явно восстанавливает четыре предыдущих
выборки текселей (выборка GPU по ближайшему, отдельные проверки глубины), ограничивает принятую
историю окрестностью 3×3 текущего цвета в сжатой области HDR,
а затем корректирует вес истории по величине движения и реактивному покрытию.
При отсутствующей/некорректной истории записывается текущая неразмытая сцена, которая служит затравкой
для следующего кадра. Пиксели, открывшиеся из-за окклюзии, отбрасывают устаревшую глубину, а не используют
интерполированную альфу истории. Тональная компрессия HDR, Bloom, LUT и HUD выполняются
**после** разрешения. Если подключённый по желанию Motion Blur также активен, он использует
временно разрешённый источник. HDR FXAA пропускается, если выполнялось временное разрешение:
не совмещайте оба подхода к сглаживанию в одном кадре.

Автоматическое аннулирование применяется при смене разрешения и большом перемещении камеры
(>12 мировых единиц представления между кадрами); явный
`Prisma::resetMotionHistory(viewId)` также аннулирует временную историю при
монтажных склейках камеры и переключении профилей. `Prisma::retireView(viewId)` перемещает собственные
дескрипторы истории в существующую очередь освобождения по GPU-fence. Диагностика
ресурсов сообщает число текстур временной истории каждой камеры и
нижнюю границу резидентных байт, не относя их на общий
кэш целей рендеринга, индексируемый по размеру.

**Чем этап 42 не является:** он **не** реализует рендеринг с динамическим разрешением,
суперсэмплинг со смещением на субпиксель, нативное масштабирование TSR/FSR/DLSS,
оценку движения по оптическому потоку, G-буфер доверия/отбраковки истории или
доказательство паритета с исторической необязательной TAA из PrismaScreenLighting.
Это подключаемый по желанию проход временной стабилизации цвета в полном разрешении. Пиксели
неба без восстановленной глубины поверхности не накапливаются, а
движущимся силуэтам всё ещё могут потребоваться более надёжное расширение скоростей/маски
окклюзии. При 1080p две истории RGBA16F плюс одна цель скоростей RGBA16F
занимают не менее ~47 MiB сырой памяти GPU базового уровня на каждое активное разрешение
плюс общие цели глубины/временные цели; физическое выделение может быть больше.
Виды с двумя камерами имеют **отдельные истории**, даже если размеры целей совпадают.

**Проверка:** только повторное чтение исходников в GitHub и статический обзор подключения.
**NOT RUN:** сборка CMake/C++/Metal, CTest, компиляция шейдеров GLES/Vulkan,
снимки экрана GPU, паритет силуэтов/прозрачности, профилирование VRAM, работа при
склейке/изменении размера камеры, бенчмарки мобильных GPU или CI. Готовность к выпуску или
PASS по качеству пикселей не заявляется. Полный handoff:
`docs/handoffs/prisma-stage-42.md`.

## Этап 43 — необязательное субпиксельное смещение и временное сглаживание с учётом доверия

Этап 43 опирается на **канонический temporalResolve PRISMA** этапа 42, не
вводя вторую подсистему TAA и не переписывая стабильные идентификаторы
`postfx`/MCP. История в нативном разрешении остаётся двумя HDR-целями
RGBA16F на камеру; цель рендеринга пониженного разрешения или временной масштабатор
не вводятся.

Эффект добавляет два необязательных параметра с плавающей точкой:

- `jitterPixels`: 0..0.5 (по умолчанию 0.5) задаёт максимальное субпиксельное
  смещение проекции. Смещение дополнительно требует
  `AIVERSE_PRISMA_JITTER=1` и исходного
  `AIVERSE_PRISMA_TEMPORAL=1`, HDR + качество High и авторского
  включённого эффекта `temporalResolve`. Существующие игры не изменяются
  без обоих явных флагов окружения.
- `historyConfidence`: 0..1 (по умолчанию 0.65) задаёт, насколько агрессивно
  отбрасывается предыдущий цвет HDR вблизи резких изменений яркости/глубины, в
  дополнение к правилам этапа 42 по глубине/скорости/реактивности при открытии окклюзии.

**Контракт камеры на C++:** вызовите `setViewId(id)`, затем
`applyCameraVolumes(stack, camera.eye())`, затем
`RTSCamera renderCamera = prisma.jitteredCamera(camera,w,h)` непосредственно
**перед** `renderer.beginScene(renderCamera,w,h)`. `jitteredCamera`
возвращает копию и никогда не изменяет сам `camera`: сохраняйте исходную
`RTSCamera` для выбора мышью, гизмо редактора, UI и сенсорного ввода.
Стандартные пути рендеринга GameClient, Editor Scene и Editor Game
обновлены под эту последовательность. Владельцы превью ShaderGraph, FX и нативные
владельцы превью могут подключиться отдельно. Реальная проекция рендеринга использует
`RTSCamera::jitter`, а теневая камера рендерера уже убирает смещение,
избегая искусственных сдвигов проекции карты теней.

**Поведение шейдера:** каждый ID вида поддерживает собственную 8-шаговую последовательность
Халтона (2,3). Смещение выражается камерой в NDC; временной шейдер
получает текущее/предыдущее смещение в **неперевёрнутых нормализованных UV**.
Каждый стабильный выходной пиксель сэмплирует текущие цвет/глубину/скорость HDR в
`pixel + currentJitter`, а затем сэмплирует предыдущую историю в
`reprojectedInputUV - previousJitter`. Это убирает смещение проекции
из адресации истории и из доверия к физическому движению, сохраняя
различные субпиксельные выборки для накопления. GLSL и Metal
используют одно и то же тело шейдера, а переворот Y цели рендеринга применяется только
существующим макросом `TUV`. Окрестность 3×3 текущего сжатого HDR-цвета
даёт локальное среднее/дисперсию и границы; шейдер использует
независимо проверенные по глубине предыдущие выборки, расхождение цвета и
контраст текущих границ глубины как множители доверия. Поэтому движущиеся
силуэты и реактивные частицы получают меньший вес истории,
чем гладкие статические поверхности.

При явных склейках камеры, разрывах типа проекции/FOV/near/far,
изменениях истории, переключениях режима/амплитуды смещения или изменениях размера
вьюпорта временная история перезапускается, а не смешивает
несовместимые пиксели. Существующее отсечение по положению камеры по-прежнему
действует. `PrismaStats` сообщает, разрешался ли в последнем кадре
временной цвет, было ли активно смещение и применённые смещения
в пикселях; панель **PRISMA — Постобработка** отображает эти значения.

Это **временное сглаживание** в нативном разрешении, а не
временное *масштабирование* со смещением, DLSS/FSR/TSR, оптический поток или
рендеринг с динамическим разрешением. Прозрачные поверхности и экранные
эффекты могут по-прежнему давать алиасинг, если их производители не предоставляют подходящих
реактивных масок или масок движения. `PrismaScreenLighting` содержит более старую
необязательную независимую TAA; не активируйте обе истории одновременно.
История и ресурсы, на которые ссылается GPU, по-прежнему подчиняются
освобождению по GPU-fence из этапов 35–42.

**Проверка:** только просмотр исходников в GitHub и структурное повторное чтение.
Сборка CMake/нативного C++ и компиляция шейдеров GLSL/MSL, CTest,
работа GL/Metal/Vulkan/Android GLES, паритет камеры/UI, несколько
вьюпортов, профилирование памяти и снимки экрана **NOT RUN** в соответствии с
текущим направлением «сначала функции». Измеримое улучшение качества изображения
или готовность к продакшену не заявляются до этих тестов.
Точные коммиты исходников, API и следующие шаги записаны в
`docs/handoffs/prisma-stage-43.md`.

## Stage 44 — явное внутреннее разрешение рендера и временной апскейлинг

Stage 44 расширяет канонический opt-in путь `temporalResolve` / Halton TAA
настоящим **внутренним разрешением 3D-рендера**, которое может отличаться от
**финальной целевой поверхности вывода**. В существующий payload
`postfx.effects[{type:"temporalResolve"}]` добавлены два параметра каталога:

- `renderScale` (0.5..1, по умолчанию **1**): доля ширины и высоты вывода,
  используемая проходами 3D, глубины и векторов движения. Выбранный масштаб
  квантуется шагами 1/16; фактическое число пикселей округляется, ограничено
  минимумом 32px и требует размеров вывода не меньше 64px.
- `reconstructionSharpness` (0..0.5, по умолчанию **0.15**): мягкая
  реконструкция/повышение резкости цвета в окрестности текущего кадра в
  сжатом HDR перед накоплением истории с весами по достоверности.

Функция **выключена, пока явно не заданы все три флага**:
`AIVERSE_PRISMA_TEMPORAL=1`, `AIVERSE_PRISMA_JITTER=1` и
`AIVERSE_PRISMA_UPSCALE=1`. Кроме того, требуются включённый
`temporalResolve`, заданный в обычном каталоге `postfx` игры/карты, поддержка
HDR, качество High, `historyWeight>0`, `jitterPixels>0` и `renderScale<1`.
Существующие проекты и уровни качества low/medium/mobile по умолчанию
сохраняют рендер 1:1.

**Порядок вызовов в host:** после `setViewId(id)` и
`applyCameraVolumes(stack,camera.eye())` вызвать
`auto [renderW,renderH] = prisma.renderSizeForOutput(outputW,outputH)`,
а затем `prisma.jitteredCamera(camera,renderW,renderH)`. Передать эту
камеру и уменьшенные размеры в `Renderer3D::beginScene`, но
в `Renderer3D::render` отдать неизменённый проход назначения
**полного разрешения**. Рисовать 3D, а также reactive/motion-вклады частиц
в уменьшенном размере. `Renderer3D::resolvePrisma` передаёт в Prisma текущую
viewProjection и внутренние размеры, а Prisma читает финальные размеры вывода
из выходной текстуры RHI, из объявленного host размера для конкретного view
или из framebuffer swapchain. HUD, подписи, picking/гизмо и UI рисовать с
исходной камерой и полными размерами вывода. Эти вызовы теперь используют
и Scene/Game редактора, и GameClient.

Основной HDR-путь теперь выполняет размытие затвора, DoF и другие внутренние
эффекты сцены в низком разрешении рендера; буферы Bloom и солнечных лучей
остаются входами низкого разрешения. **Временной проход выполняется
непосредственно перед финальным цветовым композитом** и пишет приватную для
`viewId` историю RGBA16F **в разрешении вывода** (RGB — линейный HDR, A —
предыдущая аппаратная глубина). Временные сэмплеры используют раздельные
обратные размеры texel: `inputPx` для окрестностей цвета/глубины текущей
сцены, `px` для билинейных координат истории вывода. Векторы движения
остаются разностью «текущее минус предыдущее» в нормализованных экранных UV,
поэтому их координаты не требуют специального умножения на отношение
разрешений. Шейдер применяет коррекцию jitter из Stage 43, четыре
индивидуально проверенных по глубине выборки предыдущей истории,
достоверность по яркости/глубине текущего кадра, reactive-покрытие и
ограниченное HDR-повышение резкости. Финальные tonemap/композит и
опциональный UI полного разрешения остаются в размере вывода.
HD/SDR FXAA не накладывается поверх успешного HDR temporal resolve.

История каждого view инвалидируется/выводится из употребления при изменении
размеров вывода **или входа**, при монтажных склейках камеры, изменении
проекции или качества эффекта. Старые цели проходят через существующее
выведение по GPU-fence, а не немедленное уничтожение. `PrismaStats` сообщает
`width,height` (внутренние), `outputWidth,outputHeight` (представление) и
`temporalUpscaled` (успешный шаг пространственно-временного восстановления
разрешения); они отображаются в окне редактора Prisma. `MemoryStats` уже
учитывает байты приватной временной истории отдельно от общих по размеру
буферов сцены; при апскейлинге он учитывает две **более крупные истории
вывода**.

**Fallback:** ошибка выделения истории вывода/глубины на GPU или ошибка
временного пайплайна не стирает исходное изображение: финальный композит
сэмплирует сцену внутреннего размера на весь framebuffer (обычное
билинейное увеличение). Если это происходит после начала кадра с jitter,
нестабильность в течение одного кадра всё ещё может быть видна; этот путь
требует нативной проверки в runtime и, возможно, более раннего предварительного
выделения ресурсов (preflight). Прежняя опциональная временная система
`PrismaScreenLighting` не сливается автоматически и не совместима с
одновременным использованием.

Это экспериментальный **временной апскейлер с фиксированным отношением
разрешений**, а не динамическое разрешение с переменным масштабом, не аналог
FSR/DLSS/TSR, не optical flow, не reactive-маска G-buffer для всего
полупрозрачного контента и не доказательство визуального качества или
производительности. Оценка стоимости на уровне исходников эвристическая;
фактическая стоимость на GPU, пропускная способность, ghosting и экономия
здесь не измерялись.

**Фактически выполненные проверки:** readback исходников с GitHub и 39/39
статических проверок наличия мест вызова, включая порядок temporal после
Bloom, цели истории/scratch в размере вывода и масштабированный beginScene в
Scene/Game/GameClient.
**NOT RUN:** сборка CMake/C++/Metal/GLSL, CTest, исполнение на GPU
Metal/GL/GLES/Vulkan, сравнение скриншотов, память, качество векторов
движения/AA или профилирование производительности и CI. Handoff этого этапа:
`docs/handoffs/prisma-stage-44.md`.

## Stage 45 — адаптивное разрешение по измерениям GPU и стабильный fallback до рендера

Этот этап расширяет **opt-in** путь Stage 44 с масштабом источника/вывода
для temporal. Он не меняет значения по умолчанию, корень JSON `postfx`,
существующие идентификаторы MCP, идентификатор вкладки редактора, шейдеры
сцены или жанровую симуляцию.

**Новые параметры эффекта** в существующем каталоге `temporalResolve`:
`adaptiveResolution` (boolean, по умолчанию false), `targetGpuMs`
(4..50ms, по умолчанию 16.6) и `minRenderScale` (0.5..1, по умолчанию 0.5).
Заданный автором `renderScale` из Stage 44 остаётся *потолком качества*
и не может быть превышен адаптивным контроллером. Чтобы включить функцию,
задайте `AIVERSE_PRISMA_ADAPTIVE=1` **в дополнение** ко всем трём флагам
Stage 44 (`AIVERSE_PRISMA_TEMPORAL=1`, `AIVERSE_PRISMA_JITTER=1`,
`AIVERSE_PRISMA_UPSCALE=1`), выберите HDR/High и добавьте включённый эффект
`temporalResolve` с `adaptiveResolution:true`.

`PrismaAdaptiveResolution` — жанронезависимая политика, работающая только на
CPU, в `engine/render/PrismaAdaptiveResolution.h`. Она использует *только*
конечные положительные асинхронно завершённые показания `Device::gpuFrameMs()`
от **новых, строго возрастающих** токенов `Device::gpuCompletedFence()`.
Backend без надёжных результатов (например, неподдерживаемые GL/Vulkan)
остаётся на заданном автором масштабе; политика никогда не подставляет
время кадра CPU редактора, FPS, серийные номера кадров или прогнозируемое
время GPU. На Metal сигнал измеряет **весь командный кадр GPU**, а не
изолированный проход Prisma или view редактора; адаптация нескольких view
редактора по одному и тому же измерению целого кадра консервативна и может
менять качество в обоих.

Гистерезис: длительность GPU выше 115% от цели в течение 12 различных
завершённых выборок приводит к уменьшению renderScale на 1/16; длительность
GPU ниже 80% от цели в течение 36 выборок приводит к увеличению на 1/16 вплоть
до заданного автором потолка. Изменение масштаба запускает период охлаждения
в 48 завершённых выборок, что снижает частые циклы изменения размера и
перевыделения. Нижняя и верхняя границы ограничиваются и квантуются;
`Prisma::retireView` удаляет состояние контроллера для view, когда viewport
закрывается.

**Предварительная проверка ресурсов до рендера:** `renderSizeForOutput()` в
графическом потоке теперь вызывает `preflightUpscale()`, прежде чем вернуть
любое внутреннее разрешение меньше разрешения вывода. Проверяются
GPU-программы temporal и motion, гарантированный fallback-композит, HDR
RGBA16F текстуры сцены/скоростей с владением по размеру, внутренние
scene/depth/scratch, приватная для камеры пара HDR temporal-историй в размере
вывода и scratch-глубина в размере вывода. Перевыделения истории используют
существующее выведение с GPU-fence. При неудачной предварительной проверке
возвращаются **полные размеры входа/вывода**, а jitter для этого view
запрещается. Повторные попытки выделения ограничены по частоте (60 запросов
размера рендера), чтобы не нагружать каждый кадр неподдерживаемое или
ограниченное по памяти устройство. Ожидание GPU на этом пути не добавляется.

**Безопасный для jitter fallback в runtime:** если temporal-проход неожиданно
не может выполниться после того, как сцена низкого разрешения с jitter уже
закодирована, финальный композитор использует `graphFrame.zw` как смещение
выборки на текущий jitter `s + currentJitter` для исходного цвета и зависимых
экранных эффектов. При успешном temporal resolve или обычном выводе без
jitter смещение равно нулю. Так fallback-изображение остаётся на стабильной
сетке пикселей вывода и при этом допускает линейное билинейное увеличение и
обработку цвета в HDR. Это мера визуальной стабилизации, а не гарантия
качества изображения уровня production и не замена настоящему временному
накоплению. HUD и ввод остаются в полном размере и без jitter.

`PrismaStats` добавляет `adaptiveResolution`,
`requestedRenderScale` и `temporalFallback`; существующая панель редактора
PRISMA показывает их рядом с разрешениями вывода/внутренним разрешением и
опциональными асинхронно завершёнными миллисекундами GPU **целого кадра**.
Если измерение не поддерживается, точное время GPU не показывается.

**Ограничения:** измерения времени backend могут отсутствовать; время целого
кадра включает другие задачи GPU; fallback всё ещё может давать простое
билинейное алиасинг-мерцание и дрожание тонких краёв; потерю устройства
посреди кадра невозможно восстановить сэмплированием текстур; давление
кэшированных выделений может временно расти вокруг переходов масштаба,
пока реальные завершённые на GPU fence не позволят освободить память.
Адаптивное масштабирование не синтезирует настоящее время GPU на viewport
и не обещает прироста частоты кадров. Репроекция по векторам движения,
знак jitter и компиляция GLSL/MSL всё ещё требуют нативной проверки на GPU.

**Выполнено:** прямые правки исходников на GitHub и readback исходников,
включая **38/38 статических проверок наличия** связей adaptive/preflight/
shader-fallback. Эти проверки не являются нативной компиляцией или запуском
на GPU. **NOT RUN:** CMake,
компиляция C++/Obj-C++, CTest, runtime Metal/GL/GLES/Vulkan,
скриншоты/PSNR/ghosting, эксперименты с измерением времени GPU,
профилирование VRAM, тесты потери устройства или CI. Реализация и следующий
этап описаны в `docs/handoffs/prisma-stage-45.md`.

## Stage 46 — реальные измерения времени GPU по viewport на GL33 и защита от давления VRAM

**Различие измерений времени важно:** RHI `gfx::Device` теперь имеет
опциональные неблокирующие `beginGpuScope(tag)`/`endGpuScope()` и отдельную
очередь результатов `takeGpuScopeTimings()`. В отличие от `gpuFrameMs()` и
`timeGpuFrame()`, scope измеряет только команды GPU, отправленные между его
границами. Настольный **OpenGL 3.3** на поддерживаемых путях macOS/Windows
использует настоящий запрос `GL_TIME_ELAPSED`. Backend отказывается начинать
scope, пока выполняется запрос elapsed для целого кадра или другой scope
(OpenGL не допускает вложенных запросов с одной и той же целью).
`takeGpuScopeTimings()` возвращает только завершённые неблокирующие результаты
и не потребляет результаты бенчмарков из `takeGpuTimings()`. Ограниченная
очередь вмещает не более 64 ожидающих записей. Fallback для GL ES/WebGL/Linux,
Metal и Vulkan **не** заявляют измерений по viewport: API по умолчанию
возвращает false/пустой результат. `gpuFrameMs()` у Metal — длительность всего
command buffer, и её всегда нужно обозначать именно так.

Opt-in в редакторе: `AIVERSE_PRISMA_VIEWPORT_GPU_TIMING=1`. Для Scene/Game
редактор начинает scope измерения времени GPU непосредственно перед графическим
`Renderer3D::render` и завершает его после `Renderer3D::resolvePrisma`
и последнего прохода viewport. В этот интервал попадают отрисованные тени,
мир, постэффекты и FX сцены, но **не** предшествующая подготовка сцены на CPU,
предшествующая потоковая загрузка ассетов на GPU или другие окна. При наличии
поддержки редактор опрашивает готовые измерения в своей безопасной границе
перед рендером, передаёт их в `Prisma::acceptViewGpuTiming(viewId,gpuMs)` и
перечисляет выборки по viewport через `Prisma::viewGpuTimings()`. Этот
источник служит только для представления/диагностики, не является
авторитетной симуляцией или компонентом ECS. Он включается явно (opt-in) и
никогда не включает автоматически измерение целого кадра.

**Выбор источника для адаптации:** существующий контроллер
`PrismaAdaptiveResolution` теперь предпочитает последний завершённый scoped
GL-запрос для своего конкретного view. Каждый принятый scoped-запрос
увеличивает последовательность завершённых выборок этого view; повторное
значение не может вызвать повторные обновления гистерезиса. Если scoped-запроса
нет, контроллер сохраняет прежний fallback на время целого кадра GPU,
контролируемый настоящим `Device::gpuCompletedFence()`. Он **не** переводит
FPS CPU в миллисекунды GPU. Длительность scoped-интервала по-прежнему включает
общие проходы GPU для теней/отражений/FX и не является чистой стоимостью
одной постобработки. На неподдерживаемых backend эта scope-диагностика явно
недоступна.

**Ограниченное давление известной памяти:** `temporalResolve` получает
`maxPrismaMemoryMiB` (32..4096, по умолчанию 256 MiB) как opt-in порог
давления для адаптивного разрешения. Только когда активны эффект
`adaptiveResolution` из Stage 45 и `AIVERSE_PRISMA_ADAPTIVE=1`, политика
сравнивает порог с
`Prisma::memoryStats().liveKnownBytes +
Prisma::retirementStats().knownPendingBytes`. Эти оценки учитывают общие
выделения кэша по размеру **один раз**, добавляют активные HDR-истории каждого
view и ожидающие выведения по fence текстуры ровно один раз и **исключают**
неизвестные/ненаблюдаемые байты и физические накладные расходы драйвера.
Превышение известной нижней границы считается выборкой давления только при
**новом подтверждённом завершении на GPU** (фактически завершённый scope-запрос
или GPU fence). После 12 выборок с превышением бюджета политика может снизить
масштаб **на** 1/16. Превышение бюджета блокирует шаги повышения качества;
обычное быстрое/медленное время GPU и существующий период охлаждения в 48
завершённых выборок продолжают действовать. Само по себе давление не
разрешает небезопасное освобождение GPU, безусловное ожидание памяти или
повторный подсчёт кадров CPU. Без подтверждённого завершения на GPU адаптация
не выполняется.

`PrismaStats` и редактор сообщают выбранный источник измерения времени,
последние допустимые миллисекунды GPU, известные байты Prisma live+pending,
настроенный порог и признак его превышения. Окно Stats также показывает
недавние завершённые интервалы GL33 для Scene/Game, вместо того чтобы
ошибочно называть время целого кадра Metal изолированной стоимостью view.

**Оговорки:** `gpuFrameMs` и GL-запросы elapsed — интервалы на временной
шкале GPU, не тождественные времени занятости; scope могут включать дорогие
общие проходы рендерера и не измеряют предшествующие загрузки ресурсов.
Использование одного общего измерения целого кадра GPU для двух одновременно
активных view редактора по своей природе консервативно. Порог памяти — не
общий объём физической VRAM и не жёсткий лимит памяти, а неизмеримые
выделения ShaderGraph/Portrait/драйвера остаются неизвестными. Байты сверх
известного бюджета могут оставаться высокими до фактического завершения fence;
ограниченный по кадрам гистерезис предотвращает «дребезг» на каждом кадре, но
не обещает прироста производительности. Недоступный запрос backend не должен
давать ложный нулевой результат или эскалацию по устаревшему scope.

**Выполненная проверка:** readback исходников с GitHub плюс
**42/42 структурные проверки**, включая порядок begin/end scope для каждого
viewport, взаимоисключение запросов GL33, раздельные очереди бенчмарков, ввод
выборок по view, безопасный учёт бюджета памяти и отчётность редактора.
Это ТОЛЬКО проверки наличия исходников и порядка; см.
`docs/handoffs/prisma-stage-46.md`.
**NOT RUN:** нативная компиляция C++/Metal/GLSL, CTest, реальные scope-запросы
GPU на GL33, smoke-тесты Metal/GLES/Vulkan/WebGL, бюджет кадра/
профилирование VRAM, потеря GPU/насыщение очереди и CI. Никаких заявлений о
готовности к production до выполнения этих проверок не делается.

## Stage 47 — аппаратные scope-измерения времени на Metal, память под владением рендерера и надёжное переключение источников

**Реализация GPU scope на Metal:** `gfx::Device::beginGpuScope`,
`endGpuScope` и `takeGpuScopeTimings` теперь имеют настоящий опциональный
backend `engine/gfx/metal/GfxMetal.mm` для совместимых устройств. Он
проверяет доступные `MTLDevice.counterSets` на наличие счётчиков timestamp и
требует поддержки сэмплирования счётчиков на границах blit или стадий.
Он использует **две** выборки на scope viewport в
`MTLCounterSampleBuffer`, кодируемые в лёгкие blit-энкодеры
*внутри того же command buffer Metal, что и фактическая работа Scene/Game*.
Отправка/представление command buffer, семафоры кадров и GPU fence
не изменились.

Счётчики Metal не обязательно идут в наносекундах CPU. Выборка времени
принимается только после того, как фактический command buffer достигает
`MTLCommandBufferStatusCompleted`, а
`resolveCounterRange(NSMakeRange(0,2))` возвращает оба допустимых значения
timestamp. Backend получает согласованные пары часов CPU/GPU с помощью
`[device sampleTimestamps:&cpuTimestamp gpuTimestamp:&gpuTimestamp]`
до кодирования и после завершения. Он переводит интервал timestamp GPU в
наносекунды часов CPU интерполяцией по этим парам часов.
Нулевые, сигнальные значения ошибки, немонотонные, неконечные и выходящие
за диапазон результаты **не** публикуются как допустимое время. Результаты
опрашиваются без блокировки; число ожидающих scope ограничено 64. Оборудование
без поддерживаемого сэмплирования счётчиков или допустимого sample buffer
сообщает об отсутствии поддержки, без выдуманного scoped-времени GPU. На
настольном GL33 сохраняется прежний настоящий путь scoped GPU-запросов
elapsed. Vulkan/GLES/WebGL scoped-таймеров не получили; `Device::gpuFrameMs()`
остаётся метрикой **целого кадра** везде, где используется как адаптивный
fallback, и никогда не обозначается как измерение на viewport.

Scene/Game редактора по-прежнему используют существующий opt-in
`AIVERSE_PRISMA_VIEWPORT_GPU_TIMING=1` с ограниченными scope вокруг
рендеринга на GPU и postresolve Prisma; опрос редактора перед рендером
читает только завершённые результаты scope. Это исключает работу GPU,
отправленную вне scope (например, предшествующие загрузки текстур), и может
включать общие проходы освещения/отражений. Сумма длительностей scope не
равна общему времени занятости GPU.

**Новая нижняя граница памяти GPU:**
`Renderer3D::residentMemoryStats()` использует read-only RHI
`TextureInfo` и `BufferInfo`, чтобы подсчитать *уникальные* хэндлы текстур/
буферов в прямом владении. Включены: карта теней солнца, собственная текстура
выделения рендерера, кэши захвата цвета сцены (включая глубину), текстуры-
заглушки trace, собственные текстуры-заглушки моделей, текстуры object-motion/
depth/reactive для каждой камеры и буферы line/selection/blit/indirect в прямом
владении. Псевдонимы кэша сцены `sceneColor_/sceneDepth_` **не** учитываются
дважды. Отложенные текстуры движения объектов сообщаются отдельно как
`pendingMotionKnownBytes`. Динамические `versions` буферов отмечаются,
но их физические копии в аллокаторе определить невозможно. Сжатые форматы
текстур без достаточных метаданных сообщаются как неизвестные, а не
угадываются. Внешние ресурсы `Model/Material`, цели отражений/прожекторов
`LightSystem`, общие постоянные пулы сцены/геометрии, выделения драйвера под
шейдеры/пайплайны и ресурсы Prisma этот отчёт **не** присваивает себе.

**Интеграция:** `Prisma::setExternalRendererGpuMemory(live,pending)` —
опциональный вход host, относящийся только к представлению. Scene/Game
редактора и GameClient теперь вызывают `Renderer3D::residentMemoryStats()` и
передают его известные байты живых текстур+буферов и отдельно байты ожидающего
движения тому же экземпляру Prisma **до**
`renderSizeForOutput`. Существующий сериализуемый ключ
`temporalResolve.maxPrismaMemoryMiB` для совместимости не изменился, но его
сравнение давления теперь включает непересекающиеся **известные нижние границы
Prisma и этого подмножества Renderer3D в прямом владении**, активные и
ожидающие. Это по-прежнему не охватывает общую VRAM GPU, физические выделения
устройства, mip-уровни, временный backbuffer или неизвестных владельцев. Это
**не** принуждает GPU к idle и не приводит к преждевременному уничтожению
текстур; правила выведения по GPU-fence из Stage 35–46 остаются в силе.

**Корректность переключения источников времени:** завершённую
последовательность scope-запросов Metal/GL нельзя сравнивать с завершённым
токеном fence кадра GPU. Stage 47 отслеживает их как разные домены выборок,
сохраняя качество рендера и период охлаждения, но сбрасывая предыдущий токен
и краткосрочные счётчики при каждой смене источника. Scoped-выборка старше
восьми вновь завершённых кадров GPU игнорируется, чтобы бесконечно скрытый или
неподдерживаемый view не мешал вернуться к допустимому источнику времени
целого кадра. Ни одна устаревшая scope-выборка не засчитывается повторно как
новое завершение на GPU. Ни время кадра CPU, ни оценочный FPS в качестве
замены не используются.

**UI:** окно Prisma обозначает адаптивное время как завершённые счётчики
viewport Metal/GL33 или как fallback на время целого кадра GPU и показывает
объединённый порог известной памяти Prisma + Renderer3D в прямом владении.
Окно Stats перечисляет нижние границы живых текстур/буферов Renderer3D,
промежуточные итоги захвата сцены/движения, ожидающее движение объектов и
неизвестные выделения отдельно от Prisma, чтобы владелец не учитывался дважды.

**Проверка:** инспекция исходников и **53/53 структурные
проверки наличия в исходниках**, включая ограниченные GPU scope на Metal,
раздельные очереди измерений, калибровку часов GPU, телеметрию памяти
владельца-рендерера, дедуплицированную обработку ресурсов, свежесть источника/
переключение доменов и подключение API host. Это не результат компилятора и
не проверка на GPU.
**NOT RUN:** нативная компиляция Obj-C++/Metal, CTest, калибровка счётчиков
Metal на Apple Silicon/Intel Mac/iOS, захват измерений GL33,
давление памяти GPU и тесты скриншотов. Детали API счётчиков Apple сверены
с актуальной документацией Metal, но это не доказательство поддержки этого
backend в runtime. См.
`docs/handoffs/prisma-stage-47.md` — коммиты исходников, неизвестные моменты
и точные следующие шаги. PR #26 остаётся Draft; main не изменён.

## Stage 48 — отчёт о выделениях GPU для LightSystem, постоянной GPU-сцены и общих страниц геометрии

Stage 48 расширяет экспериментальный вход давления памяти для адаптивного
разрешения: от `Prisma` и ресурсов в прямом владении `Renderer3D`
(Stage 47) — к **независимо владеемым подмодулям освещения и рендеринга**
и **глобальным пулам страниц геометрии**, не меняя существующий корень JSON
`postfx` и поведение ECS/симуляции.

Новый заголовок `engine/render/GpuOwnedMemory.h` предоставляет повторно
используемый read-only `GpuOwnedMemoryCounter` на основе RHI
`Device::textureInfo` / `Device::bufferInfo`. Он дедуплицирует хэндлы
текстур и буферов по их типизированному ID *внутри одного владельца*, сообщает
известные нижние границы байтов текстур/буферов, число известных выделений,
число неизвестных форматов/метаданных и предупреждения о динамических буферах
с несколькими версиями. В отличие от GPU-аллокатора, он никогда не вызывает
create/destroy, map, ожидание GPU, readback или запросы. Он использует
насыщающее суммирование байтов и никогда не приравнивает отсутствующие байты
текстуры к реальному нулю физической VRAM. Сжатые форматы без точных
метаданных выделения остаются неизвестными.

Новые или расширенные контракты отчётности прямых владельцев:

- `LightSystem::ownedGpuMemoryStats()` включает собственную карту света,
  depth-attachment, статический атлас света (RGBA32F), тень прожектора,
  цвет/глубину планарного отражения, крошечную текстуру-заглушку и
  динамические буферы light/halo/beam/decal, не трогая независимо
  владеемую `Renderer3D` карту теней солнца
- `PersistentGpuSceneUpload::ownedGpuMemoryStats()` сообщает о staging-буферах
  GPU из всех трёх слотов загрузки в полёте, а не о содержимом зеркала на CPU
- `GpuSceneCulling::ownedGpuMemoryStats(device)` сообщает обо всех
  собственных выходах видимости/compute для трёх кадров
- `GpuSceneDrawCommands::ownedGpuMemoryStats(device)` перечисляет
  буферы input/output/compacted/visible-count, сформированные GPU, для всех
  удерживаемых отправок и всех трёх слотов GPU в полёте
- `Renderer3D::residentMemoryStats()` теперь объединяет эти взаимно
  исключающие группы со своими из Stage 47: карта теней солнца в прямом
  владении, заглушки selection/trace, захват сцены и основные буферы
  object-motion/собственные. Он сохраняет категории
  `lightSystemKnownBytes`, `persistentUploadKnownBytes`,
  `persistentCullKnownBytes` и `gpuAuthoredKnownBytes`. Старые
  подкатегории capture/motion и итоги ожидающего движения остаются
  доступными; ожидающие ресурсы не добавляются как живые резидентные
  байты GPU

Общий `GlobalGeometryPool` находится **вне** дерева владения Renderer3D:
`geometryPoolStats(device).allocatedBytes` учитывает каждую выделенную общую
страницу геометрии один раз на `gfx::Device`, независимо от того, сколько
Models или примитивов ссылаются на эту страницу. Эти страницы намеренно не
входят в прямое перечисление буферов Renderer3D и не должны добавляться для
каждой Model. Выделенные буферы моделей вне пула и внешне владеемые текстуры
материалов по-прежнему опущены: чтобы избежать дублей, живые выделения должен
перечислять их фактический владелец.

**Интеграция с host:** перед вызовом
`Prisma::renderSizeForOutput(outputW,outputH)` и Scene/Game редактора, и
нативный GameClient передают два независимых источника памяти:
`Prisma::setExternalRendererGpuMemory(rendererOwned.liveTextureKnownBytes
+ rendererOwned.liveBufferKnownBytes,
rendererOwned.pendingMotionKnownBytes)` и
`Prisma::setExternalGeometryPoolGpuMemory(geometryPoolStats(device).allocatedBytes)`.
Исходные имя и API `temporalResolve.maxPrismaMemoryMiB` обратно совместимы,
но расчёт давления известной памяти теперь использует насыщающую сумму
**Prisma live+pending**, **Renderer3D в прямом владении + LightSystem +
буферы постоянной загрузки/culling/отрисовки live + ожидающее движение** и
**живые выделенные страницы GlobalGeometryPool**.
Это остаётся нижней границей и никогда не вызывает небезопасного уничтожения
ресурсов GPU; фактическое освобождение всегда ждёт ранее спроектированной
политики владения с GPU-fence.

Панель Stats редактора разделяет итог владельца Renderer3D на категории
освещения, загрузки, culling и сформированной отрисовки и показывает общий
пул геометрии только один раз. Окно PRISMA явно обозначает отображаемое
значение адаптивной памяти как объединённый известный минимум, а не полную
VRAM. Подготовка на CPU и планирование пакетов draw-call не изменились.

**Известные ограничения / чего не утверждается:** физическая VRAM устройства,
выравнивание/mip-уровни драйвера, версии динамических буферов Metal,
шейдеры/пайплайны, ресурсы моделей/материалов вне пула, внешние модули
рендера сцены, наборы offscreen-захвата и использование GPU другими
приложениями не учитываются. Владельцы Renderer/LightSystem/Persistent
раздельны и не учитывают общие буферы геометрии дважды. Эта работа не
добавляет глобальный аллокатор кучи GPU, запрос физического бюджета или
автоматическое вытеснение памяти GPU; параметр `maxPrismaMemoryMiB` —
консервативный опциональный порог контроллера качества, а не строгий
лимит памяти.

**Последовательность работ:** дальнейшая интеграция владельцев и
функциональная полнота — до нативной компиляции/CTest/проверки на GPU, по
требованию пользователя. Этот этап включал код и документацию, а также
инспекцию исходников только на уровне структуры; нативные тесты по-прежнему
отложены. См. `docs/handoffs/prisma-stage-48.md` — SHA,
затронутые файлы, фактические проверки и следующая функциональность.

## Stage 49 — владение выделенными моделями/материалами и допуск качества камер с учётом приоритета

Этот функциональный этап продолжает политику **сначала функции, нативные
тесты — после функционального завершения**. Он добавляет отчётность о памяти
GPU для выделенных (вне пула) GPU-выделений Model и их фактических
владельцев-кэшей текстур. Также вводится допуск HDR-истории для каждого view
и разрешение давления памяти с учётом приоритета.

**Владение GPU у Model:** новая read-only функция
`appendModelOwnedGpuMemory(const Model&,GpuOwnedMemoryCounter&)`
перечисляет собственные `vb`, `ib` Model только если
`Model.geometryPoolPage==nullptr`, а также `morphTex`,
`Model::Baked.tex` и каждый `Image.tex`, у которого
`borrowedTexture==false`. Это повторяет `releaseModel()`, который
уничтожает отдельные буферы и не заимствованные изображения, оставляя
общий пул и заимствованные изображения их владельцам. Каждый отдельный
типизированный хэндл RHI учитывается один раз через `GpuOwnedMemoryCounter`.
`ModelTextureCache::appendOwnedGpuMemory(counter)` добавляет свои
кэшированные хэндлы PBR/материальных текстур **как фактический владелец**,
никогда — через заимствованную ссылку `Model::Image`.
`RtsView::ownedModelGpuMemoryStats(device)` перечисляет каждую уникальную
кэшированную `Model` и общий кэш текстур моделей, не умножая выделения на
число видимых сущностей или ссылок на материалы. Общие страницы
`GlobalGeometryPool` по-прежнему учитываются ТОЛЬКО через
`geometryPoolStats(device).allocatedBytes`.

Общий `TextureCache::ownedGpuMemoryStats()` сообщает о собственных
GPU-текстурах страниц атласа, сгенерированных и отдельных спрайтов,
дедуплицируя любую страницу, на которую также ссылается запись кэша текстур.
Выведенные из употребления текстуры остаются у владельца выведения с
GPU-fence и не называются живыми. Другие модули могут так же предоставлять
host непересекающиеся `GpuOwnedMemoryStats`. Сжатые форматы без достаточных
метаданных размера в RHI и физические копии буферов/mip-уровней Metal
по-прежнему дают неизвестные/заниженные байты; это не физическая VRAM.

**API памяти host в Prisma:** `setExternalPresentationAssetsGpuMemory`
принимает единый итог нижней границы для **уникальных** внешних владельцев
моделей/материалов/FX-спрайтов представления. Scene/Game редактора
объединяют `view_.ownedModelGpuMemoryStats` с независимым
`fxTextures_.ownedGpuMemoryStats()` насыщающей арифметикой.
Нативный GameClient передаёт инвентарь моделей/материалов своего RtsView.
`setExternalRendererGpuMemory` и
`setExternalGeometryPoolGpuMemory` остаются раздельными. Авторский ключ
`temporalResolve.maxPrismaMemoryMiB` не изменился,
но его консервативный порог памяти теперь включает саму Prisma,
подвладельцев Renderer3D/освещения/постоянных данных, глобальные страницы
геометрии и непересекающийся инвентарь ассетов представления. Это
по-прежнему **известные байты нижней границы**, а не строгий бюджет кучи GPU
и не запрос ёмкости всего устройства.

**API политики для каждой камеры** в `Prisma.h`:

```cpp
prisma.setViewQualityPolicy(viewId, {priority, maxTemporalHistoryMiB});
prisma.clearViewQualityPolicy(viewId);
```

Политика не зависит от геймплея FPS/RTS, ввода UI и владения ресурсами GPU.
Priority — целое число от 0 (уступает первым) до 255 (уступает последним),
по умолчанию 128. При **одном лишь давлении известной памяти GPU**
контроллеру гистерезиса требуется 6 завершённых выборок для низкого
приоритета (0..84), 12 для обычного (85..169)
и 30 для высокого (170..255), прежде чем сделать шаг масштаба вниз на 1/16.
Действительно превышающее бюджет время кадра GPU по-прежнему вызывает
понижение после существующих 12 завершённых выборок для **любого** приоритета,
а быстрому восстановлению нужно 36 допустимых выборок. У каждого изменения
размера остаётся существующий период охлаждения в 48 завершений, что
предотвращает колебания.

`maxTemporalHistoryMiB==0` означает отсутствие лимита допуска для конкретной
камеры. Положительное значение ограничивает ТОЛЬКО две истории RGBA16F
полного вывода каждого view: `2*outputWidth*outputHeight*8` байт.
До того как к сцене будет применён jitter, `renderSizeForOutput` отклоняет
апскейл, если требуемый размер истории вывода превышает квоту этого view,
возвращает полные нативные размеры рендера и выводит по fence предыдущие
выделения истории. Отказ распространяется через
`jitteredCamera` И `Prisma::resolve`; последний не должен выделять истории,
от которых отказались при допуске. Таким образом, отклонённый view выводит
обычное изображение полного разрешения со стабильной проекцией камеры, а не
сцену с jitter без допустимого temporal-прохода. `PrismaStats` сообщает
приоритет и состояние допуска. `retireView` стирает политику и флаг отказа,
не давая устаревшим настройкам скрытой камеры перейти к view, который её
заменит.

**Выбор host по умолчанию** на этом этапе: Scene редактора — приоритет 64
и 128 MiB на пару HDR-историй; Game редактора и
GameClient используют приоритет 224 и лимит истории 256 MiB.
Другие нативные host проектов могут задавать свои политики. Глобальный
бюджет давления памяти, лимит допуска истории для каждого view и scoped-
измерения времени GPU в runtime управляют разными решениями, и их нельзя
смешивать.

**Реализовано, не проверено:** код, интеграция, skill для агентов и
readback с GitHub. **NOT RUN:** CMake/нативный компилятор, компиляция
Obj-C++ Metal, проверка шейдеров, CTest, измерения времени GPU, снимки VRAM,
эксперименты с производительностью приоритетов view/«дребезга» или CI.
`docs/handoffs/prisma-stage-49.md` описывает изменённые коммиты, реальную
структурную инспекцию и оставшееся функциональное покрытие перед отдельным
этапом тестов.

## Stage 50 — интеграция памяти внешних GPU-владельцев и безопасный допуск TAA в нативном разрешении

Проект остаётся на этапе **реализации «сначала функции»**: нативная компиляция
и тестирование на GPU намеренно отложены до закрытия всего функционального
бэклога. Stage 50 добавляет к существующему бюджету качества/известной памяти
Prisma телеметрию GPU независимо владеемых SpectraFX, ландшафта/планет и
потокового WorldScene. Он также исправляет асимметрию выделения/fallback для
temporal из Stage 49.

**SpectraFX:** `ParticleSystem::ownedGpuMemoryStats()` учитывает только
собственные вершинные и индексные буферы частиц и встроенный RGBA-атлас,
используя `GpuOwnedMemoryCounter` поверх существующих метаданных RHI.
Текстуры графов частиц, импортированные спрайты эффектов и пользовательские
меши являются **заимствованными**, так как поставляются через callback
загрузчика и могут разделяться отдельным владельцем текстур/мешей. Нативный
`ClientFx::ownedGpuMemoryStats()` объединяет инвентарь своего приватного
`ParticleSystem` со страницами спрайтов/атласа своего независимо резидентного
`TextureCache`. В редакторе эквивалентные буферы и кэш текстур перечисляются
независимо через `gameFx_` и `fxTextures_` и добавляются один раз; Prisma
не принимает их во владение и не выводит из употребления.

**Ландшафт и планеты:** `TerrainRenderer::ownedGpuMemoryStats()`
сообщает обо всех резидентных VBO/IBO чанков/LOD, геометрии фартуков и воды,
render-текстурах по ячейкам, динамических, splat, видимости, карты высот и
детальных нормалей/splat, а также о приватном для владельца `TextureCache`
материалов ландшафта/обрывов. Объекты `TextureRef`, привязываемые шейдерами
ландшафта, — псевдонимы этих хэндлов, принадлежащих кэшу, и отдельно не
учитываются. `PlanetRenderer::ownedGpuMemoryStats()` аналогично учитывает
чанки планет, атласы видимости и деталей для каждого тела, меши глобуса/
атмосферы, заглушки и свой отдельный кэш текстур материалов.
`RtsView::ownedPresentationGpuMemoryStats` объединяет уникальный инвентарь
Model/ModelTextureCache из Stage 49 с ландшафтом и планетами, **включая
выделения, которые остаются живыми, пока представление временно скрыто**.
Это отчёт владельца, а не триггер вытеснения на GPU.

**Потоковый мир:** `WorldScene::ownedGpuMemoryStats(device)`
обходит текущие резидентные чанки и пропускает каждую общую/необщую модель
через `appendModelOwnedGpuMemory` с одним дедуплицирующим счётчиком.
Несколько чанков, ссылающихся на одну и ту же общую Model или хэндл GPU,
учитывают её только один раз; страницы GeometryPool исключены и по-прежнему
учитываются через `GlobalGeometryPool`. Внешний `ModelTextureCache` может
предоставлять другой владелец, например GameClient передаёт
`view_.textureCache()` своему потоковому миру. Поэтому `WorldScene`
намеренно не перечисляет этот заимствованный кэш повторно.

**Интеграция в каждом host:** Scene/Game редактора теперь объединяют
`view_.ownedPresentationGpuMemoryStats(*dev_)`,
`gameFx_.ownedGpuMemoryStats()` и отдельный
`fxTextures_.ownedGpuMemoryStats()` насыщающим сложением известных байтов.
Нативный GameClient добавляет view представления,
`fx_.ownedGpuMemoryStats()` и опциональный резидентный
`worldScene_->ownedGpuMemoryStats(dev)`. Оба передают результат через
существующий общий `setExternalPresentationAssetsGpuMemory` перед
`renderSizeForOutput`. Буферы GPU Renderer3D/LightSystem/постоянных данных и
байты глобально общих страниц геометрии по-прежнему передаются собственными
непересекающимися вызовами host. Отображаемое значение
`temporalResolve.maxPrismaMemoryMiB` остаётся **оценочным порогом качества
по нижней границе, а не общей физической VRAM устройства, бюджетом аллокатора
или гарантированным пиком**.

**Безопасность нативного TAA:** Stage 49 ввёл для каждой камеры лимит
`maxTemporalHistoryMiB` для двух HDR-историй RGBA16F,
но проверял его только после принятия флагов временного апскейлинга.
Stage 50 переносит эту проверку допуска сразу после подтверждения активного
авторского HDR-эффекта `temporalResolve`, *до* решения об апскейле или jitter.
Тем самым камера со стабилизацией в нативном разрешении из Stage 42
получает ту же защиту квотой. Отклонённая история выводится из употребления
только через существующую политику владения с GPU-fence; камера остаётся в
нативном/полном разрешении и без jitter.

Для `AIVERSE_PRISMA_JITTER=1` TAA в полном нативном разрешении теперь также
заранее выделяет и проверяет две текстуры HDR-истории, нативные цвет/глубину
сцены, скорости движения, внутреннюю и выходную scratch-глубину и свои
fallback/composite пайплайны через существующий `preflightUpscale(w,h,w,h)`
из Stage 45. Предварительная проверка выполняется **до**
`Renderer3D::beginScene`. Неудачная проверка на GPU помечает view как
отклонённый и возвращает стабильную камеру без jitter; `Prisma::resolve`
проверяет тот же флаг `preflightRejected` и не может позже в кадре обойти
отклонённое выделение. Повторы неудачной проверки остаются ограниченными по
частоте. Нативная временная стабилизация без флага jitter по-прежнему может
использовать унаследованный путь Stage 42 без jitter.

**Ограничения:** метаданные RHI не могут сообщить обо всех выделениях
драйвера, поколениях динамических буферов Metal, mip-уровнях текстур, байтах
сжатых ресурсов, внешних владельцах сцены или выделениях GPU в отдельных
процессах. Новые отчёты мира/ландшафта/планет/FX содержат только хэндлы,
которые создают и поддерживают их владельцы. Они никогда не подразумевают
разрешения уничтожить заимствованный ресурс или ресурс в полёте.
Проекция/начало координат на Metal/GL/GLES/Vulkan, временная репроекция и
поведение при отказах ресурсов на реальном оборудовании не проверены.

**Фактическая проверка:** инспекция исходников через подключённый GitHub,
readback исходников и 51/51 структурная проверка наличия API и порядка.
**NOT RUN:** нативная сборка C++/Objective-C++, компиляция шейдеров, CTest,
реальная работа на GPU, профилирование VRAM, сравнение скриншотов, CI. См.
`docs/handoffs/prisma-stage-50.md`; следующий этап должен продолжить
функциональное закрытие и НЕ начинать финальные тесты, пока пользователь не
разрешит эту фазу.

## Stage 51 — оставшиеся GPU-владельцы представления, отчёт о возможностях runtime и разрешение конфликта temporal

Stage 51 завершает ещё один функциональный слой реализации RHI и адаптивного
качества PRISMA по принципу «сначала функции». В `Prisma`, её корень JSON
`postfx` и идентификаторы MCP редактора не добавлено зависимостей от
геймплея/ECS. Изменения исходников ограничены владельцами представления,
запросами метаданных ресурсов GPU и опциональной интеграцией унаследованной
обёртки temporal.

**Дополнительные непересекающиеся владельцы памяти GPU:**
`SpriteBatch::ownedGpuMemoryStats` сообщает о собственных буферах VB/IB/caster,
*а не* о статическом SpriteMesh вызывающей стороны или заимствованных хэндлах
текстур. `FogOfWar` сообщает о своей приватной геометрии листа и текстуре.
`RtsFieldView` учитывает геометрию полей и выходные текстуры каждого поля;
`RtsOverlays` учитывает буфер оверлеев, собственный белый fallback и
приватный для оверлеев TextureCache; `RtsGroundFx` учитывает живые меши
слоёв земли/меш дорожек, белый fallback и свой приватный кэш текстур.
`Rts2DView` учитывает свой меш тайлов, собственные буферы SpriteBatch и
кэш текстур спрайтов. Владельцы Road и Shore перечисляют уникальные VBO/IBO
моделей и GPU-изображения, принадлежащие их китам, но никогда — заимствованные
ссылки на изображения, продублированные между моделями. Roads также учитывают
буферы мешей декалей разметки, мокрой плёнки и луж, свой SpriteBatch и текстуры
разметки. `RtsPlanetGroundFx` перечисляет геометрию тайлов территории/
раскапываемых участков/дорог/дорожек на планетах, `RtsGroundCanvas` владеет
буферами sprite batch для земли и своим кэшем текстур, а `RtsPaintLayers`
сообщает о своих холстах RenderTexture для раскраски, текстурах береговой
линии и буферах мешей.

`RtsView::ownedPresentationGpuMemoryStats(device)` теперь объединяет
этих владельцев с моделями, ландшафтом, планетами и ModelTextureCache из
Stage 49–50. Ассеты, которые остаются резидентными, но не рисуются именно в
этом кадре, по-прежнему учитываются, пока владеющая подсистема их не
освободит. Заимствованные текстуры, псевдонимы статических буферов мешей с
другим владельцем, общие страницы GlobalGeometryPool и выделения
Renderer3D/Prisma/LightSystem никогда не должны учитываться повторно из записи
отрисовки. Результаты остаются метаданными RHI нижней границы, а НЕ общей
физической резидентностью GPU или точной VRAM.

**Запрошено, поддерживается и фактически выполнено:**
`Prisma::runtimeCapabilities() const` — read-only диагностика без обращения к
GPU: доступность/исправность устройства, поддержка RGBA16F, запрошенный и
фактический HDR в последнем кадре, авторский temporal-эффект с флагом runtime,
подготовленные хэндлы GPU-пайплайнов temporal/velocity, запросы субпиксельного
jitter/апскейла/адаптации и флаги их фактического выполнения в последнем кадре.
Также сообщается, использовала ли последняя сцена допустимый reactive-вход,
была ли принята scoped-выборка времени, и `fallbackReason` для отключённого
устройства, неподдерживаемого HDR, недостаточного уровня качества,
отсутствующих пайплайнов, отказа по квоте истории камеры, отказа
предварительной проверки temporal или ошибок backend.
`runtimeCapabilities` никогда не компилирует шейдеры и не выделяет
текстуры; подготовленный GPU-пайплайн не гарантирует успешного выполнения
на GPU. Панель Prisma редактора явно показывает каждое из этих измерений.
Поля последнего кадра — статистика последнего resolve Prisma, а не
одновременные снимки по каждой камере.

**Конфликт с унаследованным temporal resolver:** старая опциональная обёртка
`PrismaScreenLighting` владеет отдельным resolver истории цвета и
последовательностью Halton. Одновременный запуск с каноническим
temporal-проходом `Prisma::resolve` смешивал бы две разные истории и
последовательности jitter. Новый
`Prisma::canonicalTemporalRequested() const` назначает единственного
канонического temporal-владельца для запрошенного HDR-качества High и
включённого авторского Temporal Resolve, *не завися от ленивой готовности
шейдеров*. В этом случае `PrismaScreenLighting::jittered`
делегирует каноническому `Prisma::jitteredCamera` и сбрасывает
собственную историю; его `scenePass` подавляет унаследованный
temporal-пайплайн. Stage 52 теперь отделяет опциональные проходы диффузного
переотражения и объёмного освещения от этого унаследованного temporal
resolver: когда выбран канонический Temporal Resolve, перед каноническим
resolve выполняется только линейное HDR-освещение. Вторая история TAA или
jitter не используются.

**Явный жизненный цикл камер:** `Prisma::retireUnregisteredViews(
const std::vector<uint64_t>& liveViewIds)` может вызываться host после
записи всех живых проходов Scene/Game/пользовательских камер для
графического кадра. Он объединяет отслеживаемые ID для экспозиции, temporal,
качества/допуска, scoped GPU-запросов, матриц движения и ссылок на размеры
каждого view и вызывает существующий `retireView(id)` с GPU-fence только для
ID, отсутствующих в переданном списке живых. Текстуры в полёте остаются до
фактических fence завершения на GPU; процедура не уничтожает их немедленно и
не выводит из употребления размер, разделяемый другой камерой. Host отдельно
выводит view object-motion, принадлежащие Renderer3D, через существующий API.
Редактор сохраняет явное выведение RHI-движения для Scene/Game и добавляет
общую очистку Prisma для каждого view в конце окна отправки viewport; общие
буферы по размеру по-прежнему обрабатываются через
`retireUnreferencedSizeCaches`.

структурных проверок наличия/порядка. Нативная компиляция, CTest,

`docs/handoffs/prisma-stage-51.md`.

## Stage 52 — опциональное HDR-освещение, независимое от унаследованного временного накопления

`PrismaScreenLighting` — опциональный адаптер `PostProcess` вокруг
`Prisma`; не копируйте его реализацию в SpectraFX и не запускайте второго
владельца TAA. Этот этап отделяет его проходы HDR-освещения сцены от
исторической временной реконструкции.

- Когда `canonicalTemporalRequested()` истинно на HDR/High, адаптер
  делегирует `jittered()` в `Prisma::jitteredCamera` и сбрасывает
  унаследованную историю. Его шейдер переотражения (приближённое непрямое
  диффузное освещение в экранном пространстве) и опциональное объёмное
  рассеяние солнца с тенями по-прежнему выполняются над **линейным
  HDR SceneColor до `Prisma::resolve`**. Последняя вспомогательная текстура
  копируется обратно в цвет сцены отдельным шейдером, который не трогает
  альфу. Затем Prisma остаётся единственным temporal-владельцем.
- Если канонический temporal не выбран, а адаптер включён на HDR/High,
  сохраняется его старый TAA с двумя историями / jitter камеры по Halton,
  включая старый контракт копирования с непрозрачной альфой.
  `temporalShadowResolve()` адаптера истинно **только** в этом
  унаследованном режиме, поэтому опциональное PCSS-сэмплирование теней не
  рандомизируется случайно без соответствующей унаследованной истории.
- Вспомогательные текстуры переотражения, рассеяния, истории и глубины
  создаются лениво по запросу. Режим только с каноническим temporal **не**
  создаёт два унаследованных изображения истории и унаследованный
  depth-attachment; существующие выделения из предыдущего режима остаются в
  кэше, а не уничтожаются при переключении режима, пока GPU ещё может их
  использовать. Полное освобождение ресурсов при resize/shutdown унаследовано
  от старого адаптера и всё ещё требует проверки жизненного цикла с GPU-fence.
- Отсутствие тени солнца подавляет объёмное рассеяние в этом кадре,
  даже если оно настроено. Без унаследованной temporal-истории
  последовательность выборок рассеяния имеет стабильную фазу, чтобы
  избежать анимированного шума, когда каноническая предварительная проверка
  temporal не проходит. Из этих изменений исходников не выводится ни
  возможность GPU, ни визуальное соответствие.

Публичный API: `PrismaScreenLighting::lightingOnly()` описывает текущий путь
адаптера; `running()`, `passCount()`,
`temporalShadowResolve()`, `setDiffuseBounceEnabled()` и
`setVolumetricLight()` сохраняют совместимую семантику, за исключением того,
что флаг temporal-теней больше не считает нетемпоральный проход только
освещения temporal resolver. Два прямых шейдера освещения и отдельная
копия с сохранением альфы входят в набор пайплайнов MSL/GLSL адаптера.
Существующий JSON `postfx`, имена редактора/MCP и порядок «UI после
tone-map» не изменились.

Проверка: 15/15 **проверок наличия и порядка в исходниках** после
readback с GitHub. **NOT RUN:** clang/нативный CMake, unit/CTest, выполнение
на Metal/GL/Vulkan/GLES, GPU fence, пиксельное соответствие HDR-цвета/альфы,
скриншот-тесты экранного переотражения/объёмного света и CI. Код Stage 52
и точное продолжение — в `docs/handoffs/prisma-stage-52.md`.


## Stage 53 — камера-специфичная диагностика эффекта (CPU read-only)

`Prisma::effectReport(viewId) const` возвращает указатель на
`Prisma::ViewEffectReport`, снятый **после последнего `resolve()` именно
этой камеры**. Идентификаторы `viewId` назначает host; значение 0 —
унаследованный default. `effectReportViewIds()` возвращает отсортированные
ключи сохранённых отчётов. Результат не создаёт RHI shader/texture,
не вызывает `program()/composite()`, не ждёт GPU и не меняет ECS.

`ViewEffectReport`: `viewId`, счётчик `sequence` (только вызовы resolve
для данного ID), размеры входа, качество, HDR-путь, готовность сцены и
список `EffectExecution` для всех элементов текущего camera-profile,
**включая authored-disabled/low-tier эффекты**. Каждая запись содержит:

- `type` — `PrismaType` из стандартного каталога; `authored` означает
  присутствие в текущем профиле.
- `requested` — effect enabled на текущем tier и его opt-in + числовые
  условия (при наличии) выполнены; низкий tier / выключенная переменная
  окружения даёт конкретный reason и `requested=false`.
- `pipelinePrepared` — локальные кэшированные RHI handles
  доступны. Это **не** доказательство GPU execution; для composite
  проверяется реально выбранный variant, а для многопроходных
  Bloom/TiltShift/SunShafts конкретные подготовленные pipelines.
- `encoded` — соответствующий эффект реально вошёл в последний
  рендер (draw для MotionBlur/DoF/FXAA/Temporal, подключённый к
  отправленному composite ресурс для Bloom, LUT, Bloom/etc). Частичный
  ошибочный GPU graph без использования результата не считается
  успешным эффектом. Готовность шейдера без draw не даёт `encoded`.
- `reason` — причина пропуска (camera cut/first frame, history quota,
  temporal preflight, HDR/tier/opt-in, отсутствие LUT/pipeline,
  shadergraph/exposure texture-slot конфликт, отсутствие target и др.).
  Пусто у успешно закодированного эффекта.

Отчёт per-view не смешивает Scene/Game с одинаковым размером. При
`retireView` / `retireUnregisteredViews` снимок удаляется вместе с
камерным состоянием, при `shutdown()` и `setSettings()` старые отчёты
очищаются. Обновление `applyCameraVolumes()` отражается при следующем
`resolve`; до него снимок является историей *последнего рендера*, не
планом текущей настройки. Указатели report инвалидируются при очистке
или обновлении карты; не кэшировать их между кадрами.

Редактор `PRISMA — Постобработка` отображает collapsible матрицу
`View ID / effect / requested / pipeline / encoded / reason`, не создавая
ресурсы во время просмотра. Существующий глобальный `runtimeCapabilities()`
по-прежнему описывает последние данные из `PrismaStats`, а не все
камеры; для per-view эффекта использовать новый API.

Особенно важно: `encoded` означает **GPU draw command issued**, а
не выполненный GPU fence, корректные пиксели, изображение в кадре или
соответствие эффектов на разных RHI. Последние четыре утверждения
допускаются только после реальных GPU-тестов.

Источник Stage 53: `engine/render/Prisma.{h,cpp}`,
`apps/editor/windows/PrismaWindow.cpp`; точные коммиты,
структурные проверки и следующий этап — `docs/handoffs/prisma-stage-53.md`.
**Фактическая проверка:** 18/18 проверок наличия в исходниках и жизненного цикла после
readback с GitHub. **NOT RUN:** локальный CMake/clang/CTest, редактор,
Metal/GL/GLES/Vulkan, shader compile, screenshots, GPU passes, CI.
Проверку производительности/пикселей не заявлять до отдельной test phase.

## Stage 54 — безопасное закрытие камер и deferred GPU retirement

В PRISMA camera `viewId` обозначает устойчивую идентичность
presentation-камеры, **не** её размер, поэтому две камеры 1920×1080
имеют независимые temporal/velocity histories.

`Renderer3D::retireUnregisteredObjectMotionViews(liveViewIds)`
(новый публичный genre-independent API) принимает полный набор
активных stable view IDs **после** отправки всех camera passes текущего
кадра. Для каждого отсутствующего ID вызывается уже существующий
`retireObjectMotionView(id,device.gpuSubmissionFence())`;
в очередь помещаются только Renderer3D-owned `target/depth/reactive`
текстуры. Их высвобождение происходит через
`collectCompletedObjectMotion(device.gpuCompletedFence())`.
Нулевой submission token сохраняет ресурсы в `motionUnfenced_` до
явно подтверждённого GPU idle. **CPU frameSerial и время не могут
заменить GPU fence**. Активные камеры и size-shared targets не
освобождаются.

Editor после Scene/Game render использует один
`activePrismaViews` для
`Prisma::retireUnregisteredViews(...)` и
`Renderer3D::retireUnregisteredObjectMotionViews(...)`, затем
`Prisma::retireUnreferencedSizeCaches()`. Старые переходы закрытия
Scene/Game сохранены и являются no-op, если generic cleanup уже
удалил ID; custom-camera cleanup больше не пропускает независимые
Renderer3D velocity textures. GameClient оставляет 3D view 3 живым,
когда рендерит `sim_`; если кадр содержит только меню или загрузку,
он удаляет частные Prisma/Renderer3D состояния и невостребованные
size caches. `startMatch` по-прежнему явно завершает предыдущую
камеру. При следующем рендере камера создаёт чистую историю.

`PrismaScreenLighting` сохраняет исключительное владение своими
`bounce_`, `scatter_`, `history_[2]` и `depth_`.
`releaseTargets()` при resize или в `scenePass()` после
`setEnabled(false)` теперь перемещает их в
`PrismaGpuRetirementQueue<gfx::TextureHandle>`, привязанную к
`Device::gpuSubmissionFence()`. Пока устройство не сообщило
`gpuCompletedFence()`, фактического `destroyTexture` нет.
Если backend не дал submission token, ресурс сохраняется в
`unfencedTargets_` и освобождается только через
`drainRetiredAfterGpuIdle()` после явного ожидания GPU idle
владельцем устройства.

Публичный API адаптера:
`collectGpuRetirements()` — неблокирующий сбор по
подтверждённому completion fence;
`retirementStats()` — CPU/GPU-free статистика количества
fenced/unfenced текстур и последнего GPU completion token;
`drainRetiredAfterGpuIdle()` — **только при известном GPU idle**;
`shutdown()` также **требует GPU idle** для безопасного удаления
пайплайнов/шейдеров/vertex buffer, как и исторический адаптер.

Общий `Prisma` и `Renderer3D` владеют собственными GPU queues;
ScreenLighting **никогда** не удаляет чужие targets, depth или
history. Отключение адаптера удаляет его текущие auxiliary resources
на *следующем вызове* `scenePass`, а не немедленно при
`setEnabled(false)`. Если adapter больше никогда не вызывается,
его GPU owner должен продолжать `collectGpuRetirements()` и
в конце жизненного цикла завершить `shutdown()` после idle.

**Ограничения/проверки:** только readback исходников с GitHub и
30/30 структурных проверок целевых переходов/методов. **NOT RUN:**
CMake/clang, CTest, Metal/GL/GLES/Vulkan/WebGL, GPU fence overlap,
интеграционный Editor/GameClient runtime, memory stress и image
parity. Корректность сигнальных backend tokens в реальных RHI и
наличие у всех custom camera hosts полного live-ID roster должны
быть подтверждены отдельно. Exact source commits и следующий
этап — `docs/handoffs/prisma-stage-54.md`.



## Stage 55 — Auto Exposure совместно с четырьмя Shader Graph текстурами

До этого этапа PRISMA отводила для GPU HDR Auto Exposure
фиксированный sampler `TEX8`, а postfx Shader Graph использовал
привязки `TEX5..TEX8` для максимум четырёх независимых текстур.
При четырёх текстурах включённая автором Auto Exposure
**молча отключалась**, хотя все остальные её условия были выполнены.
Это было функциональным ограничением, а не физическим запретом RHI.

Новый GPU-независимый `PrismaCompositeTextureLayout.h` определяет
общую, constexpr-вычислимую карту ресурсов. Фиксированный композит
занимает слоты 0..4, Shader Graph — 5..8, а HDR Auto Exposure —
слот 8, пока граф использует 0..3 текстуры, и слот 9 при
четырёх текстурах. Неподдерживаемое количество текстур (более 4)
явно отклоняется. Пять `static_assert` подтверждают ожидаемые
вычисления при компиляции библиотеки; **нативная компиляция ещё НЕ
проводилась**. Схема не меняет сериализацию, JSON или MCP API.

В `Prisma.cpp` план используется одновременно при создании
`ShaderDesc.textureSlots`, формировании masks для GLSL/MSL
`TEX0..TEX9` и фактическом `Device::setTexture`.
`PrismaShaders.h` выбирает `TEX9` только с
`PF_AUTO_EXPOSURE_SLOT9`, иначе сохраняет `TEX8`.
Ключ кэша composite остаётся `effectMask + ShaderGraph JSON`:
этого достаточно, поскольку layout однозначно определяется самим
графом. При ошибке построения expanded pipeline PRISMA сохраняет
старый fallback: тот же composite без Auto Exposure, а если он
тоже недоступен, базовый composite без эффектов. Не подменять
неуспешный pass на «эффект выполнен».

`Prisma::ViewEffectReport` теперь содержит
`shaderGraphTextures` и `autoExposureTextureSlot`.
Последнее равно `-1`, когда **финальная выбранная composite pipeline**
не содержит Auto Exposure; запись обновляется только после
разрешения fallback. Editor `PRISMA — Постобработка` показывает
фактический slot по каждому `viewId`, не инициируя GPU
shader compile для отображения диагностики.

Проверка RHI исходников: GL настраивает `texN` по
`ShaderDesc.textureSlots`, Metal backend содержит sampler
bindings, включающие 9, Vulkan допускает до 32 descriptor
texture slots; Shader Graph компилятор ограничивает число
самостоятельных текстур четырьмя. Это **структурная оценка
исходников**, не доказательство работоспособности на всех
адаптерах GLES/WebGL/Metal/Vulkan.

**Фактическая проверка:** после readback с GitHub выполнено 25/25
структурных проверок source/layout/логики; **NOT RUN:**
CMake/clang, shader compilation, редактор, CTest, GPU-resolve,
readback HDR пикселей, backend stress/CI/benchmarks. См.
`docs/handoffs/prisma-stage-55.md` для точных коммитов,
ограничений и следующего шага. PR #26 остаётся Draft;
никаких изменений в `main` не вносилось.


## Stage 56 — Depth of Field: фокус по расстоянию и защита силуэтов

Экспериментальный `depthOfField` остаётся частью PRISMA и
по-прежнему требует `AIVERSE_PRISMA_DOF=1` и подходящий quality tier.
Старые карты/JSON автоматически используют **прежний режим**:
`focusDepth` и `focusRange` в аппаратной глубине [0,1];
`maxBlur` и `intensity` остаются без изменений. В shader этот
режим сохранён в отдельной ветви с оригинальной формулой и
10-весовой схемой размытия, чтобы старое изображение не
переинтерпретировалось как физическое расстояние.

Новые необязательные параметры того же эффекта:

| Параметр | По умолчанию | Назначение |
|---|---:|---|
| `metricFocus` | false | Явно включить линейную глубину по данным камеры |
| `focusDistance` | 12 | Плоскость фокуса вдоль направления взгляда (единицы мира) |
| `focusRangeMeters` | 4 | Интервал резкости вокруг плоскости фокуса |
| `occlusionToleranceMeters` | 0.35 | Допустимый перепад глубины между центром и tap до подавления смешивания |

*Обозначение «метры» относится к проектам, где одна единица
мира равна метру.* Это линейная глубина вдоль направления
камеры (view-space Z), **не** сферическая дистанция
от глаза до произвольной точки. Для perspective:
`z = near * far / (far - depth * (far - near))`;
для orthographic: `z = mix(near, far, depth)`.
`Renderer3D::resolvePrisma()` уже передаёт
`PostFrame.depthNear`, `depthFar` и `orthographic`;
ортографические границы текущего renderer могут быть
отрицательными `-200..1000`, что корректно поддерживается.

Код `Prisma.cpp` проверяет finite near/far и
`far > near`; perspective также требует `near > 0`.
Если `metricFocus` запрошен, но входная проекция невалидна,
RHI draw выполняет **старую аппаратную глубину**, а
`Prisma::EffectExecution` для этой камеры выставляет
`encoded=true`, `degraded=true` и конкретный `reason`.
Это предотвращает NaN и пустой кадр. Указатель на report остаётся
read-only; `degraded` не означает проверенную визуальную
корректность эффекта на GPU.

Metric-шейдер считает CoC из линейной глубины и в
восьми соседних цветовых tap выбирает вес по
**разнице линейной глубины**. Точки, отделённые силуэтом
или принадлежащие sky/background (device depth >= 0.99999),
не смешиваются, переход между согласованными и
несогласованными слоями сглажен `smoothstep`.
GPU sampling оставлен в linear HDR; output alpha в metric-ветви
наследуется от исходного SceneColor. Legacy-ветвь оставляет
прежний output alpha=1 по совместимости.
Самплируемый scene depth никогда не привязывается как
writable depth attachment; для DoF используется отдельный
`scratchDepth`. Pass работает с `src.tex`, который может
содержать результат предыдущего Motion Blur, и теперь проверяет
наличие именно `src.tex` перед draw.

`PrismaData.cpp` автоматически открывает новые поля в общей
схеме JSON/editor/MCP/volume-mask; отдельную реализацию для FPS,
RTS или SpectraFX не создавать. В `PrismaWindow.cpp` добавлена
подсказка о выборе режима и видимое `degraded fallback`
в матрице эффектов по `viewId`. Любой старый `postfx`
без `metricFocus` продолжит использовать старый путь.

**Ограничения:** это 8-tap screen-space defocus, а не
физически правильный bokeh, Gather/Scatter DoF или
полноценное separated foreground/background scattering.
На пересечениях полупрозрачных поверхностей ограничение
глубиной может подавлять размывание, но не может
восстановить закрытые за объектами цвета.
Семантика depth [0,1], камера и Metal/GL parity требуют
проверки на реальном устройстве.

**Фактические проверки:** после коммитов исходники
прочитаны из GitHub и выполнено **32/32 source-only
структурных проверки**. **NOT RUN:** CMake/clang,
GLSL/MSL/Vulkan shader compiler, CTest, Editor/GameClient,
Metal/GL/GLES/WebGL/Vulkan GPU pixel/readback,
скриншоты, profiling и CI. Следующему агенту читать

## Stage 57 — устойчивый HDR Auto Exposure и согласованный camera-cut reset

`autoExposure` по-прежнему требует эффекта в postfx-профиле,
эффективного HDR и переменной `AIVERSE_PRISMA_AUTO_EXPOSURE=1`.
Измерение яркости остаётся в линейном scene-referred HDR до
тонмаппинга и UI, а его отдельная 1×1 ping-pong history принадлежит
**стабильному `viewId`**, независимо от размеров Scene/Game viewport.

Новые необязательные параметры общего PrismaData-каталога:

| Поле | Default | Диапазон | Значение |
|---|---:|---:|---|
| `highlightRejection` | 0 | 0..0.95 | Насколько уменьшать влияние очень ярких пикселей при измерении |
| `highlightStartEV` | 3 | -10..16 | Порог начала снижения веса в log2(luminance), а НЕ camera exposure EV |
| `highlightSoftnessEV` | 2 | 0.1..8 | Плавность перехода до максимального снижения веса в ступенях log2 |

`highlightRejection=0` **по умолчанию** сохраняет прежний
weighted log-luminance estimator и уже существующие
`centerWeight`, `centerRadius`, `minMeterLogL`,
`maxMeterLogL`, EV clamps и скорости адаптации. Это опциональный
**soft highlight weighting**, не histogram/percentile metering.

GPU shader `kExposureLog` вычисляет luminance каждого из четырёх
семплов, ограничивает logL текущими `minMeterLogL/maxMeterLogL`,
затем уменьшает базовый пространственный вес:
`weight *= 1 - rejection * smoothstep(startEV, startEV+softnessEV, logL)`.
Граница `rejection <= 0.95` гарантирует не менее 5% исходного
веса даже для полностью яркого кадра и исключает нулевой
знаменатель измерения. Пирамидальное уменьшение `kExposureReduce`
по-прежнему отдельно переносит взвешенную сумму log2 luminance
и сумму весов, а `kExposureAdapt` делит первое на второе
перед вычислением EV. Нет скрытого GPU readback или CPU luminance pass.

**Camera cut:** до Stage 57 обнаружение автоматического скачка
камеры происходило после GPU-метеринга, поэтому первый кадр после
телепорта мог смешиваться с прежней экспозицией. Теперь проверка
`motionView.previousCameraPos`, finite и скачка свыше
12 единиц мира выполняется в начале `Prisma::resolve`
**до** Auto Exposure. Сброс одновременно инвалидирует
velocity/temporal history и `resetAutoExposure(viewId_)`.
Явные `resetMotionHistory(id)` / `resetMotionHistory()` также
инвалидируют per-view/all-view exposure history без удаления GPU
текстур. Первый адаптационный pass новой камеры использует
`historyValid=false` и заново инициализируется от текущего
измерения. Сброс не требует ожидания GPU и не путает
две камеры одного разрешения.

Цветовой порядок сохранён: weighted HDR metering измеряет
`scene.tex`, 1×1 экспозиция применяется к HDR RGB в
`PF_AUTO_EXPOSURE` внутри final composite, далее
ColorGrade-authored `exposure` в HDR входит в pre-tonemap
множитель `filt.z`, затем ACES/sRGB, пользовательские
display-space grade/LUT и postfx Shader Graph.
Это **два независимых авторских множителя**, а не два
экземпляра алгоритма автоадаптации; GPU history исключительно
одна per-view. Ресурсы Shader Graph (слоты 5..8) и
Auto Exposure (8 или 9) продолжают соблюдать Stage 55 layout
и fallback без Auto Exposure на неподдерживаемом pipeline.

`Prisma::ViewEffectReport` теперь записывает
`autoExposureHighlightRejection` **только** когда финально
закодированный composite реально содержит Auto Exposure.
Иначе поле остаётся нулевым, `autoExposureTextureSlot=-1`
и Stage 53 per-effect status указывает отсутствие эффекта.
Editor показывает величину и подсказки непосредственно в
`PRISMA — Постобработка`; список эффектов и volume editor
получают новые параметры автоматически через общий каталог.
Старый `postfx` JSON, MCP, saved editor panel id и SpectraFX
не затрагиваются. Параметры не влияют на authoritative ECS.

**Ограничения:** не реализованы histogram percentile metering,
тональная сегментация кожи/неба, AE metering masks и локальная
экспозиция. Глобальный яркий фон всё ещё может влиять на общий
результат (не меньше 5%). Настраивать `highlightStartEV` с учётом
scene-referred **log2 яркости**, а не EV управления камерой.
Качество цветовой динамики и GPU shader parity пока не проверены.

**Проверка:** GitHub readback пяти исходников и **31/31
source-only structural checks**. **NOT RUN:** CMake/clang,
GLSL/MSL/Vulkan compiler, CTest, editor/client, Metal/GL/GLES/
Vulkan/WebGL execution, pixel/temporal parity, perf, CI.
См. `docs/handoffs/prisma-stage-57.md` для точных коммитов
и следующего функционального этапа.

## Stage 58 — cinematic Exposure Freeze и круговая область HDR metering

PRISMA по-прежнему использует **один** глобальный алгоритм
Auto Exposure: HDR scene luminance → `kExposureLog` →
`kExposureReduce` → `kExposureAdapt` → 1×1 per-view
exposure history → final HDR composite до tonemapping/UI.
Stage 58 добавляет управление его уже существующими
GPU-проходами, без новой ECS-системы, второго шейдерного
Exposure owner или обязательных параметров JSON.

### Новые необязательные поля `postfx.effects[].type=autoExposure`

| Поле | Default | Семантика |
|---|---|---|
| `freezeExposure` | false | Удержать последнее валидное значение 1×1 Auto Exposure этой камеры |
| `meterRegionEnabled` | false | Включить локальное взвешивание яркости круговой области кадра |
| `meterCenterX`, `meterCenterY` | 0.5, 0.5 | Нормализованный центр области, X слева направо, Y снизу вверх |
| `meterRadius` | 0.25 | Радиус круга относительно **высоты** кадра, с поправкой на aspect |
| `meterFeather` | 0.10 | Плавная ширина края круга, в долях высоты кадра |
| `meterOutsideWeight` | 0.05 | Вес пикселей вне круга; гарантированно больше 0 (минимум 0.02) |

Все поля добавлены в конец прежнего каталога Auto Exposure:
старые offsets и значения не сдвигаются. Generic
`PrismaData` parser/serialization, editor, MCP и
`PrismaVolumeStack` автоматически получают новые поля.
Для игр без новых ключей прежняя обработка остаётся
функционально неизменной; оба режима выключены по умолчанию.
Существующий эффект всё ещё требует HDR, соответствующий tier
и `AIVERSE_PRISMA_AUTO_EXPOSURE=1`.

**Freeze:** при валидной истории `ExposureView.history[current]`
предыдущая 1×1 GPU-текстура просто подключается к final
composite. На этом кадре не создаются дополнительные mip
targets, не запускаются `kExposureLog`, `kExposureReduce`
или `kExposureAdapt`; GPU history не читается и не
записывается одновременно. Внутреннее время адаптации
обновляется, чтобы разморозка не давала большой delta-time.
На первой активной камере, после завершения camera view,
сброса настроек или Camera Cut история невалидна; freeze
делает **один новый метеринг / адаптацию** текущей сцены,
после чего снова удерживает результат. Явные camera cuts
сохраняют контракт Stage 57 — заново захватывать экспозицию,
а не навсегда держать прежний кадр. Само выключение эффекта
инвалидирует его историю, не уничтожая ресурсы немедленно.

**Region:** `kExposureLog` получил дополнительный
`vec4 region` только в собственной UBO (`ExposureMeterU`).
`SimpleU` и интерфейсы других проходов не изменились.
`region.z < 0` отключает область без влияния на старую
формулу. При включении каждый из четырёх исходных sample UV
переводится обратно из backend texture orientation в
bottom-up экранные координаты `TUV(q)`; X масштабируется
отношением width/height. Веса вычисляются по
`smoothstep(radius,radius+feather,physicalDistance)`,
после чего перемножаются со старым `centerWeight` и
Stage 57 `highlightRejection`. Outside weight никогда не
равен нулю. Редукция пирамиды сохраняет
`(weightedLogL, totalWeight)` и не зависит от маски;
все прочие шейдеры/UBO остаются прежними.
Это **дешёвое area-weighted metering**, не GPU histogram,
segmentation, текстурная пользовательская маска или
локальная экспозиция по разным частям экрана.

### Отдельные настройки для native-камер

`Prisma.h` предоставляет GPU-free presentation API,
ключованный **stable view ID**, а не координатами камеры
или размером viewport:

```cpp
prisma.setViewExposureFreeze(viewId, true);
prisma.setViewExposureMeterRegion(viewId, {
    true, 0.5f, 0.5f, 0.25f, 0.10f, 0.05f
});
// Чтобы вернуться к наследованию postfx/PrismaVolumeStack:
prisma.clearViewExposureFreeze(viewId);
prisma.clearViewExposureMeterRegion(viewId);
```

Также `setViewExposureFreeze(id,false)` явно
переопределяет `freezeExposure=true` из профиля.
`setViewExposureMeterRegion` проверяет finite и clamping
координат, radius, feather и outsideWeight при поступлении.
Таким образом две камеры в одной географической точке
могут иметь независимые freeze и region параметры.
После окончания всех camera passes host передаёт полный
набор живых идентификаторов в
`Prisma::retireUnregisteredViews`; новые overrides
включены в unionTracked и удаляются `retireView`/
`shutdown` вместе с пер-камерным state. Это
presentation-only, не authoritative ECS и не изменение
глобального базового профиля.

`ViewEffectReport.autoExposureFrozen` и
`autoExposureRegionMetered` обновляются только если
**конечный encoded composite** реально применяет
Auto Exposure. Frozen означает «в этом кадре повторно
взята валидная история, meter не запущен»; RegionMetered
означает «в этом кадре выполнен замер с областью».
При отсутствии exposure в финальном fallback оба false.
Окно редактора показывает их по каждому viewId и даёт
подсказки по новым generic-полям; GUI-чтение не вызывает
GPU-созданий.

CPU-плану, native API, lifecycle, UI и final fallback.
**NOT RUN:** CMake/clang, CTest, GLSL/MSL/SPIR-V shader
compiler, Metal/OpenGL/GLES/Vulkan/WebGL GPU, редактор

## Stage 59 — Manual EV, прямоугольная ROI и отказоустойчивый HDR metering

Ручной EV реализован **внутри существующего** `AutoExposure`
postfx effect; он не запускает второй HDR owner, GPU-историю,
новый fullscreen pass или дополнительный sampler. Каталог
`PrismaData.cpp` дополняет Stage 58 полями:

| Поле | По умолчанию | Назначение |
|---|---|---|
| `manualExposure` | false | Режим фиксированной экспозиции вместо автоматического замера |
| `manualEV` | 0 | −12…+12 stops, `2^manualEV` в линейном HDR |
| `meterBox` | false | Вместо круга использовать прямоугольную ROI |
| `meterHalfWidth` | 0.25 | Полуширина прямоугольника в долях **ширины** кадра |
| `meterHalfHeight` | 0.25 | Полувысота прямоугольника в долях **высоты** кадра |

Все новые настройки opt-in и добавлены в конец каталога.
Старые `postfx`, editor IDs и MCP операции сохраняются;
у существующих проектов `manualExposure=false` и
`meterBox=false` означают отсутствие изменений. Обычная
автоматическая экспозиция всё так же требует
`AIVERSE_PRISMA_AUTO_EXPOSURE=1`, а **явно включённый**
manualExposure работает без этого флага (но требует
authored `autoExposure`, enabled postFX, разрешённый tier
и линейный HDR).

### Fixed EV и camera state

В `Prisma::resolve` ручной режим выбирается по профилю камеры
и native override. При активном manualExposure GPU metering,
`kExposureLog/Reduce/Adapt`, 1×1 exposure history и texture
sampler `TEX8/TEX9` **не используются**. Вместо этого
уже существующий `CompositeU.filt[2]` умножается на
`exp2(manualEV)` **после** вычисления author ColorGrade
exposure, но **до** final HDR composite / ACES / sRGB / LUT /
Shader Graph и UI. Это означает, что фиксированный EV и
художественная ColorGrade exposure композиционно
перемножаются, но автоматической адаптации в manual-режиме нет.

Manual EV из нативных вызовов и C++ профиля проверяется на
finite и ограничивается [-12,+12] перед HDR; NaN/Inf
не пропускаются в shader. При переходе в/из ручного
режима camera-local exposure history инвалидируется; при
возврате к автоматике выполняется новый замер текущей
сцены вместо смешивания со старой яркостью. Ручной режим
может работать сразу при первом кадре — в отличие от
`freezeExposure`, требующего валидную предшествующую 1×1
адаптацию. При ошибке пользовательского Shader Graph
fallback к `composite(0)` сохраняет fixed EV, поскольку
`filt[2]` применяется вне `PF_GRADE` и `PF_AUTO_EXPOSURE`.
При невалидном final pipeline отчёт не объявляет manual EV
выполненным.

Native API:
```cpp
prisma.setViewManualExposure(stableViewId, true, 1.5f);
prisma.setViewManualExposure(stableViewId, false, 0.0f); // explicit disable
prisma.clearViewManualExposure(stableViewId); // restore profile inheritance
```
Выбор `setViewManualExposure(id,false,...)` явно
переопределяет авторский `manualExposure=true`; clear
возвращает управление профилю и инвалидацией AE history.
Overrides принадлежат stable presentation `viewId`, а не
разрешению/позиции камеры. `retireView`,
`retireUnregisteredViews` и `shutdown` удаляют их
вместе с остальным per-camera state, не освобождая
общие GPU texture caches.

### Мягкий прямоугольник для HDR Metering

Stage 58 круговая область остаётся default; Stage 59
добавляет `meterBox=true` с параметрами
`meterHalfWidth` и `meterHalfHeight` в нормализованных
координатах viewport. Радиус и feather прежней области
сохранены. В `ExposureMeterU` добавлен `regionBox`
(пятый vec4); `kExposureLog` через
`regionBox.z > 0.5` выбирает signed-distance box вместо
circle. Разность X приводится к масштабу **высоты**
кадра множителем aspect; у мягкой границы есть
`smoothstep(0,feather,signedDistance)`.
`TUV(q)` обеспечивает одинаковое направление Y в
GL/Metal, а прежний `meterOutsideWeight >= 0.02`
сохраняет ненулевые вклады вне области. Глобальная
редукция (weighted log sum и weight sum) не изменена.

Native `ExposureMeterRegion` дополняет существующие поля
`bool box=false; float halfWidth=0.25, halfHeight=0.25`
**в конце** структуры, сохраняя старые aggregate initializers.
Сеттеры клэмпят finite размеры к [0.01,0.5], а ROI
не входит в authoritative ECS. Отчёт camera view
дополнен `autoExposureBoxMetered` (только для
**фактически закодированной** экспозиции). В режиме
manualEV никакой meterRegion на кадре не выполняется.

### Fallback при сбое GPU metering

Если HDR luminance pyramid не закончилась полноценной
1×1 текстурой (`valid=false` или `pw/ph != 1`),
Prisma теперь **не выделяет и не пишет**
`ExposureView.history` для этого замера. Старый
per-camera sample инвалидируется, final composite
продолжает работать без sampled Auto Exposure;
в будущих кадрах может быть сделана новая попытка.
Частично закодированные mip passes не выдаются за
успешное адаптированное освещение, отдельного
GPU sync ожидания не добавлено.

`ViewEffectReport.manualExposureEncoded` и
`manualExposureEV` сообщают только об истинно выбранном
и закодированном fixed EV на последнем `resolve`.
`autoExposureTextureSlot` остаётся -1 для manual.
Существующая матрица эффектов отмечает manual как
выполненный через base/fallback HDR composite, без
ложной необходимости ExposureLog pipelines.
`autoExposureBoxMetered` показывается вместе с
`autoExposureRegionMetered` только после реального
GPU meter pass и последующего успешного composite.
В редакторе эти параметры доступны из общего
каталога с пояснениями и статусом по viewId.

Это **не** полноценный произвольный metering texture
mask, GPU histogram, local exposure, физическая
имитация камеры, TSR или решение всех Shader Graph
ошибок. Дополнительные рендер-ветви остаются
экспериментальными до настоящих GPU-тестов.

**Фактическая проверка:** GitHub readback пяти
изменённых исходников и **49/49 source-only
структурных проверок**. **NOT RUN:** CMake, clang,
CTest, GLSL/MSL/SPIR-V компиляция, Metal/GL/GLES/
Vulkan/WebGL GPU smoke/pixel capture, сохранение editor
undo, замер HDR parity и производительности, CI.
Для точных коммитов и следующего шага см.
`docs/handoffs/prisma-stage-59.md`.



## Stage 60 — graceful Shader Graph / LUT fallback с сохранением обычных эффектов

Ранее `Prisma::resolve()` при ошибке пользовательского postfx
Shader Graph (GLSL/MSL компиляция, неподдерживаемый sampler layout
или невалидные input texture) мог в конечном итоге перейти сразу
на `composite(0)`, теряя исправные фиксированные Bloom,
ColorGrade, LUT, Vignette и другие эффекты. Теперь PRISMA
использует следующую **упорядоченную систему fallback**:

1. Запрошенный вариант со Shader Graph и, при наличии,
   GPU Auto Exposure.
2. Тот же Shader Graph, но без Auto Exposure, если
   первая попытка не создала pipeline.
3. **Без Shader Graph**: полный fixed-effect mask с Auto Exposure
   (если подготовленная HDR 1×1 текстура ещё доступна).
4. Тот же fixed-effect mask без Auto Exposure, если
   предыдущая pipeline не поддерживается.
5. Только как последняя возможность — `composite(0)`
   без фиксированных эффектов. Если даже он недоступен,
   диагностика не заявляет успешный draw.

Набор фиксированных эффектов сохраняется отдельной копией
`fixedMask` **до** попыток Shader Graph. Если пользовательская
текстура Shader Graph отсутствует или не была загружена в GPU,
весь Shader Graph исключается из текущего composite, а
исправные fixed effects продолжают работать. Успешное создание
Shader Graph pipeline само по себе не означает, что input
textures загрузились: `graphInputsReady` проверяет
`graphTextures_[path].valid()` для всех используемых путей
после попытки upload. Отсутствующий input больше не
представляется молча валидной «чёрной» текстурой внутри
выполненного Shader Graph.

**Особенно важно после Stage 55:** в graph-варианте с четырьмя
изображениями Auto Exposure использует `TEX9`.
Если graph не прошёл и используется fixed-only fallback,
последняя реально выбранная pipeline требует `TEX8`.
`PrismaCompositeTextureLayout::plan(...)` теперь
вычисляется повторно на основании **фактически выбранного**
Shader Graph, а не исходного авторского списка текстур.
Точно этот же `exposureSlot` используется в GPU binding,
`ViewEffectReport` и shader variation. При
graphless fallback текстуры в slots 5..8 не привязываются
без необходимости. Сохранены HDR manual EV Stage 59,
ColorGrade и настройки Auto Exposure, если итоговый
variant поддерживается. Кэш `composite(mask,graphData)`
и отложенная GPU-retirement ownership неизменны.

### Диагностика и кэширование ошибок

`ViewEffectReport.shaderGraphFallback` указывает, что
авторский Shader Graph был пропущен, а остальная цепочка
смогла быть использована **там, где валидны её pipelines**.
`EffectExecution` для `ShaderGraph` получает
`encoded=false` и конкретную причину: отсутствие/upload
текстуры либо shader compile/composite failure. У
исправных fixed effects `encoded` определяется итоговым
GPU mask, а не фактами исходного запроса. В редакторе
`PRISMA — Постобработка` появилось соответствующее
предупреждение по стабильному `viewId`.

У `Prisma::lut()` ошибка чтения, некорректная LUT strip
`N²×N` и ошибка GPU upload теперь устанавливают
`lastError()` с описанием и project-relative path.
LUT по-прежнему negative-cached, поэтому остальные
эффекты могут продолжать работать без него.
`graphTexture()` теперь negative-caches также ошибки
**GPU upload**: повторная декодировка и неудачное
`createTexture` в каждом кадре не нужны. Сброс
кэша через существующий `setImageLoader()`
retire-ит успешные texture handles за реальным GPU
fence и позволяет повторить загрузку; изменение файла
на диске **без вызова** этой процедуры само по себе
не является live-reload и не обещается в данном этапе.

Не изменились format `postfx` в `game.json`,
`PrismaData` каталог, MCP API, ECS gameplay, настройки
эффектов по умолчанию, SpectraFX, per-view exposure ownership
или пользовательские Shader Graph форматы.

## Stage 61 — reactive прозрачные края для Motion Blur и безопасный FXAA

В Stage 61 исправлены два конкретных presentation-пути PRISMA:
SDR FXAA больше не подменяет input невалидной текстурой при
неудачном создании промежуточного render target, а optional
Motion Blur умеет подавлять смешивание цветовых проб по
разнице **reactive coverage** на краях полупрозрачных
объектов/частиц. Работа остаётся независимой от жанра и
не затрагивает authoritative ECS или отдельную SpectraFX.

### Motion Blur + reactive input

Новый необязательный параметр существующего `motionBlur`:
`reactiveTapRejection`, диапазон 0..1, **default 0**.
Он добавлен **в конце** каталога эффектов
`PrismaData.cpp`, поэтому все предыдущие numeric offsets,
старые `postfx` JSON, пресеты и native/volume profiles
остаются совместимыми. При нуле действует прежний
шейдерный вес и прежний фильтр.

`MotionBlurU` получил пятый vec4 `tapInfo`. Только
`kMotionBlur` использует расширенную UBO; остальные
pass-ы (Temporal, DoF, Bloom, FXAA, ExposureLog) и
формат reactive texture не менялись.
`tapInfo.x` получает `reactiveTapRejection`
**только при валидном входном** `MotionTextureInput`
(RGBA8, размер текущего scene render target, проверка
declared metadata и доступного RHI `textureInfo`).
Когда reactive mask отсутствует/отвергнута, значение
нулевое, шейдер сохраняет прежнее поведение.

Если фильтр активен, текущий pixel и его соседние
цветовые пробы читают `TEX3` reactive R. Пробы
с существенно другим coverage получают уменьшенный
вес:
`keep *= 1 - strength * smoothstep(0.1,0.8,abs(tapReactive-centerReactive))`.
Это **дополнение** к уже существующей глубинной
фильтрации (hardware или линейная depth), а не её
замена. Если сумма весов нулевая, применяется
исходный резкий RGB. При новых HDR прогонах
Motion Blur возвращает **исходную alpha**
`centerColor.a`, не `1.0`, поскольку постэффект
изменяет radiance RGB, не прозрачность сцены.
Canonical `TemporalResolve` по-прежнему сам
записывает глубину в собственную history alpha —
этот контракт не изменён.

Зависимость от реальной reactive geometry: mask
строится отдельно Renderer3D и дополнительными
провайдерами (например, particles/water),
а временное изображение mask НЕ сохраняется
между кадрами. Данный этап не пытается исправлять
отсутствующее покрытие у конкретного материала
или считывать GPU пиксели на CPU.

`ViewEffectReport` по каждому stable `viewId`
теперь хранит `reactiveInputSupplied`,
`reactiveInputAccepted` и
`motionBlurReactiveEdgesEnabled`. Это
**CPU metadata/RHI acceptance**, а не GPU pixel
validation: legacy borrowed handle без metadata
может считаться допустимым, когда backend
не предоставляет introspection. Последнее поле
становится true только когда MotionBlur
фактически закодирован, нужный вход проверен
и strength больше нуля. Editor PRISMA показывает
доступность mask и status фильтра.

### Безопасная деградация FXAA

Ранее SDR prepass делал `src=target(kAa)`
**до** проверки, валиден ли результат создания.
При failed `RGBA8` target или depth attachment
composite мог сэмплировать невалидный src.
Теперь `fxaaInput` сохраняет оригинальную
scene/post-chain текстуру, `fxaaOutput`
создаётся отдельно, и prepass исполняется
только если input/output и depth валидны.
Graph FXAA (opt-in) и обычный direct draw
используют те же два проверенных handles,
а `src=fxaaOutput` назначается **только после
encoded draw**. Если выделение не удалось,
остальная цепочка продолжает с прежним src,
без ложного `fxaaEncoded=true`.

Для HDR fallback FXAA, который применяется
после финального Composite и только если
TemporalResolve не сработал, добавлена проверка
`pipe.valid()` **до** начала промежуточного
AA target/pass. Это исключает чтение пустого
composite target, если pipeline вообще не
удалось получить. Проверка output target/depth
сохранена. TAA и FXAA остаются взаимоисключающими
на едином HDR presentation output.

Никаких новых GPU history или shared texture
owners не введено. Рендер поддерживает текущие
fence-retirement контракты Stage 54.

`Prisma.cpp`, `Prisma.h`,
`PrismaWindow.cpp` и
`PrismaMotionTextureInput.h`,
**40/40 source-only structural checks** (проверка
логики и вызовов в исходниках). **NOT RUN:**
CMake/clang, GLSL/MSL/SPIR-V compilation,
CTest, Editor/GameClient, Metal/GL/GLES/
Vulkan/WebGL, screenshot/alpha/historical
parity, temporal ghosting и performance.

`docs/handoffs/prisma-stage-61.md`.


## Stage 62 — reactive mask на первом кадре, Camera Cut и resize

С этого этапа `Renderer3D` разделяет два **независимых**
presentation-производителя: (a) объектные velocity vectors,
требующие предыдущей камеры и истории текущих/прошлых
transform-ов, и (b) current-frame RGBA8 reactive coverage,
которой **не нужна** предшествующая поза. Ранее весь reactive
pass находился внутри `if (history.target.valid() &&
history.depth.valid())`, а функция выходила с `return`
на первом кадре, при camera cut и resize. Поэтому
прозрачность воды, частиц, morph/skinned translucent объектов
могла не покрываться reactive mask именно там,
где temporal history недействительна.

### Новая структура Renderer3D

`renderObjectMotionVectors(PostProcess&)` продолжает вызываться
на завершающем scene frame, до `Prisma::resolve`.
В нём `velocityHistoryReady` определяется только по
`previousCameraValid && history.valid && !resize`.
При отсутствии предыдущих данных никакие ложные/нулевые
object-motion velocity кадры **не отправляются** в Prisma.
Текущие rigid/animated transform-позы собираются как прежде;
после reactive-прохода они сохраняются для следующего
кадра. Если viewport поменял размер, `target/depth/reactive`
текстуры *все* помещаются в существующую GPU-fenced очередь
через `queueObjectMotionTexture(...)`, а не уничтожаются
синхронно. Это сохраняет Stage 54 ownership contract.

Новый приватный метод
`Renderer3D::renderCurrentFrameReactiveMask(PostProcess&,
ObjectMotionHistory&, gfx::TextureHandle sceneDepth,int w,int h)`
использует только **текущий** `viewProj_`, model poses,
scene depth и готовые framebuffer размеры. Этот helper
вызывается **после** условного object velocity прохода
и не вложен в него. Он сам обеспечивает private depth
attachment для reactive-only кадров (`Depth`) и
при наличии нужной геометрии создаёт RGBA8 reactive target.
Scene depth от `Prisma` передаётся как borrowed sampler
и никогда не становится writable depth attachment.
Отсутствие RGBA16F velocity не блокирует **helper на уровне
Renderer3D**, если native post hook запросил такую
reactive работу и предоставил scene depth; обычная
Prisma HDR-политика по-прежнему сама решает, нужен
ли ей MotionBlur/Temporal Resolve вообще.

Рендер current coverage сохраняет прежние источники:
rigid прозрачные модели и fading LOD, morph/skinned/baked
translucent модели с current pose для обеих motion
матриц, immediate water MeshVertex-геометрию,
`motionReactiveDraws_` от частиц и custom native
providers. Маска по-прежнему создаётся/clear-ится
только на текущем кадре, blending объединяет coverage,
передаётся в Prisma как
`MotionTextureInput::declared(reactive,w,h,RGBA8)`.
Варианты, где нет reactive geometry/callback или
нет доступного depth/target/pipeline, не объявляются
успешным reactive pass.

### Раздельная статистика и диагностика

`Renderer3D::ObjectMotionStats` теперь имеет:
`velocitySeedOnly` — первый кадр / invalid/cut/resize,
чтобы не выдавать pose initialization за GPU object
velocity; и `reactiveSubmitted` — отдельный флаг
**фактически закодированного** current-frame mask.
Историческое `submitted` остаётся показателем
object-velocity прохода, не reactive-only.

Камера PRISMA хранит
`ViewEffectReport.objectVelocityInputAccepted`
и `reactiveWithoutObjectVelocity` с учётом отдельной
`MotionTextureInput` проверки: сначала проверяются
declared width/height/format, затем RHI `textureInfo`,
если backend поддерживает introspection. Эти поля
не доказывают содержимое пикселей GPU. Editor показывает
`mask-only pass` для reactive coverage без валидной
object velocity texture; отдельный статус MotionBlur
reactive edge rejection продолжает зависеть от
реально encoded blur и настроенного параметра.

**Сохраняются без изменений:** стабильная идентичность
per-view независимо от одинакового разрешения двух
камер; `resetObjectMotionHistory(viewId)` и camera-cut
epoch; GPU-fenced retirement; отсутствие ECS mutation;
`Prisma::resolve` и HDR temporal history как
единственного color history owner; HUD вне
постобработки. Reactive mask не становится
долгоживущим temporal input.

**Фактически выполненные проверки:** readback 6
исходников из подключённого GitHub,
42/42 структурных source checks, статический
баланс C++ brace scopes 2/2.
**NOT RUN:** CMake/clang/Obj-C++, CTest, shader
compilation, тесты first frame/cut/resize на реальных
Metal/GL/GLES/Vulkan/WebGL, pixel capture,
скриншоты reactive coverage, GPU fences,
профилирование и CI. Реальные backend outcomes
должны быть получены в общей фазе валидации,
а не объявлены PASS по исходникам.

`docs/handoffs/prisma-stage-62.md`.

## Stage 63 — точная rigid alpha-cutout / dissolve reactive coverage и lifecycle callbacks

Этот этап расширяет текущий `Renderer3D::renderCurrentFrameReactiveMask`
(Stage 62), не меняя архитектуру, формат `Prisma`/MCP,
HDR color history или ownership Reactives. Reactive mask остаётся
**RGBA8 current-frame** входом от `Renderer3D` в PRISMA;
пер-камерная история движения является независимым компонентом.

### Rigid-модели: точный AlphaMask, dissolve и LOD

Для rigid-моделей с `AlphaMode::Mask` или `dissolve > 0`
добавлен отдельный шейдерный вариант
`reactive_shaders::kCutoutVS/kCutoutFS/kCutoutMSL`
и `objectMotionReactiveCutoutPipeline_`.
Основной water/transparent/mesh pipeline оставлен без изменений.

Шейдер повторяет фрагментные условия обычного
`ModelShaders`: `baseTex` alpha, `baseColor.a`,
опциональную vertex alpha (с исключением
vertex-occlusion/AO), `alphaCutoff`, KHR base-UV
offset/scale/rotation, screen-space 4×4 LOD dither
и **тот же object-space noise**
`modelNoise3(opos*7)*0.7 + modelNoise3(opos*19)*0.3`
для dissolve. `TeamMode::BaseAlpha` использует
baseColor alpha без baseTexture alpha; для
`TeamMode::VertexAlpha` не умножает alpha vertex
дважды, следуя материалу. Сцена по-прежнему
сэмплирует чужой `sceneDepth` только на чтение;
реактивный pass имеет собственный writable
`history.depth`. Используется `BlendMode::Screen`
для объединения coverage. Shader source предоставляет
одинаковую логику отсечения GLSL и Metal, но **GPU
parity требует настоящих shader tests**.

Новый uniforms layout только для этого pipeline:
`ReactiveCutoutUniforms {mvp,params,lod,uv0,uv1,maskInfo}`,
144 bytes. Vertex attributes — настоящие
`ModelVertex` `position[0]`, `uv[2]`,
`color[4]`. AlphaCutout texture bind slot 1,
scene depth в slot 0. Поскольку шейдер точно
отбрасывает alpha holes, реактивность больше не
закрашивает целый треугольник у foliage/grilles.
Shader Graph vertex displacement и geometry-driven
models по-прежнему требуют отдельных производителей
coverage; не заявлять их как поддержанные данным
rigid-путём.

### Анимированные переходы и callbacks

Для skinned/morph/baked translucent моделей
`kAnimatedFS` и его MSL-генератор получили
необязательный `U1.reactiveLod` (fragment
`buffer(2)`) с точным 4×4 LOD dithering на
текущем кадре. Анимированные LOD и
`dissolve` теперь подают coverage и при
отсутствии previous pose. **Dissolve у
анимированных объектов консервативный** —
маска может покрывать фрагменты, которые
основной ModelShaders отбрасывает по
object-space noise. Точный анимированный
alpha-cutout/actor aperture требует нового
current-object-space varying или отдельного
material-specific shader, не реализован здесь.

В `Renderer3D` readiness маски проверяется
**по необходимому источнику**: отдельно
simple rigid, cutout/dissolve rigid,
skinned, baked, MeshVertex или
`motionReactiveDraws_`. Наличие
неподходящего заранее созданного shader
(например, skin pipeline при отсутствии
baked pipeline) больше не является основанием
публиковать пустую reactive mask. Когда
callback был зарегистрирован на текущий
scene frame, но активный postprocess, scene
depth или mask pipeline недоступны,
`ObjectMotionStats.reactiveCallbacksDropped`
учитывает невыполненные вызовы; callback
не переносится на следующий кадр.

Registration contract прежний: `addMotionReactiveDraw`
**после** `beginScene`, но **до**
`resolvePrisma`. Рендерер вызывает
callbacks только с открытым масочным pass:
поставщик должен лишь записывать draws,
не вызывать `beginPass/endPass`, сохранять
свои GPU ресурсы до завершения submission и
комбинировать coverage без уничтожения
предыдущих пикселей. Список очищается
после resolve, при неактивном postprocess
или в начале нового scene frame.
Промежуточная маска не кэшируется
между camera cuts и не переносится между
`viewId`.

`Renderer3D::ObjectMotionStats` дополнен
`cutoutReactiveDraws`,
`dissolveReactiveDraws`,
`reactiveCallbacksDropped`; прежние
`reactiveDraws/reactiveAnimatedDraws/
reactiveCallbacks/reactiveSubmitted` сохранены.
Счётчики означают CPU-encoded submissions /
callback invocations, а **не GPU completion**
или доказанное содержимое пикселей.
Общий per-view `Prisma::ViewEffectReport`
из Stage 62 и GPU-fenced retirement
Stage 54 не изменялись.

ownership checks**, статический баланс

**NOT RUN:** CMake/clang, Metal/GLSL/MSL

## Stage 64 — precise animated reactive alpha/dissolve и Actor Reveal

Stage 64 завершает bounded functionality пробела, найденного в
Stage 63: animated skin/morph/baked reactive coverage раньше
создавалась только как консервативный силуэт, без применения
материального `AlphaMode::Mask`, object-space dissolve и
локального `kDrawActorReveal` aperture. В новой реализации
обычная velocity pipeline остаётся **без изменений**,
а reactive path получает отдельный **GPU shader variant**.

### Reactive-only vertex stage

`Renderer3DReactiveShaders.h` теперь предоставляет две
проверяемые функции генерации:
`reactive_shaders::animatedVertexGlsl(source,baked)` и
`reactive_shaders::animatedMsl(source,baked)`.
Они принимают существующие `kDeformedVS/kDeformedMSL`
или `kBakedVS/kBakedMSL`, подставляют UV
(`ModelVertex` атрибут 2), vertex color/alpha
(атрибут 4) и **current deformed object-space pose**,
сохраняя прежние skin/morph/baked источники
(атрибуты 5/6, U0/U3/U4/U5 и texture 7/8).
Результирующие локальные текстовые варианты
передаются в `createShader`; оригинальные
motion shaders и velocity output остаются прежними.
Если ожидаемый source anchor отсутствует, генератор
возвращает пустую строку, а Renderer3D не
создаёт невалидную реактивную pipeline.

`kAnimatedFS` (GLSL) и создаваемый MSL fragment
используют новый `ReactiveAnimatedU1`, 160 bytes:
`lod[4],uv0[4],uv1[4],maskInfo[4],world[16],
reveal[4],revealAxis[4]`. Он занимает
обычный uniform slot 1 (Metal buffer 2), не
мешает skin/baked deformation слоту U3/U4/U5.
Шейдер по-прежнему рендерит только
**current-frame RGBA8 reactive coverage**,
не записывает скорость и не использует
предыдущую кадровую историю. Depth
сэмплируется из чужого `sceneDepth`, а
writable attachment — renderer-private
`history.depth`.

Для animated объектов теперь точно воспроизводятся
те же условия отсечения текущего кадра:
4×4 LOD dither, UV offset/scale/rotation,
материальный cutoff `baseTex alpha *
baseColor alpha` (+ vertex alpha, если допустимо),
и `modelNoise3(currentDeformedLocalPos * 7) * 0.7 +
modelNoise3(currentDeformedLocalPos * 19) * 0.3`
для dissolve. Настройки `TeamMode::BaseAlpha` и
`TeamMode::VertexAlpha` не перемножают
вершинную/текстурную alpha дважды; vertex
occlusion/AO не трактуется как opacity.

### Actor Reveal для rigid и animated

`kDrawActorReveal` с активным
`Renderer3D::actorReveal` теперь делает
модель источником reactive coverage, даже
если она полностью opaque и не имеет LOD
fade/dissolve. Только главный camera pass
(`geometryMainView_`) передаёт
world-space actor center/radius, camera axis
и view-dependent attenuation из той же
`Renderer3DModels.cpp` формулы. Fragment
shader повторяет aperture:
`radial=length(delta-axis*depth)`,
`radius=actorRadius*max(0.01,1-depth*axisScale)`,
`coverage=(1-smoothstep(radius*.48,radius,radial))*
smoothstep(.04,.24,depth)` и 4×4
dither discard. В неактивном режиме
`reveal.w=0` и этот путь не влияет
на маску.

Для rigid alpha/dissolve shader был расширен
`ReactiveCutoutUniforms` с 144 до
**240 bytes**, за счёт world matrix и
reveal/axis в U0. GLSL и Metal получают
current world position вершины. Для animated
используется current deformed local position,
преобразуемая через переданную `world`
матрицу во fragment. Это не отдельный
draw pass и не ECS-система: источником остаётся
тот же current-frame reactive pass из Stage 62.

В `Renderer3D::renderCurrentFrameReactiveMask`
replay анимированных материалов теперь
настраивает `ReactiveAnimatedU1`, отдельный
baseTexture sampler slot 1 и вершинные
атрибуты UV/color/skin. Параметры actor reveal,
dissolve, alpha cutoff и LOD задаются
по каждой `ModelItem`. Статистика
`ObjectMotionStats.actorRevealReactiveDraws`
дополняет существующие `cutoutReactiveDraws`,
`dissolveReactiveDraws`, `lodReactiveDraws`.
Это CPU-encoded draw counts, не подтверждение
GPU-видимости. Ресурсы остаются за
`Renderer3D`; existing GPU-fenced target
retirement и stable per-`viewId` ownership
не изменены.

### Ограничения и проверка

### Новое исправление: native и JSON numeric safety

`parsePrismaEffect` теперь не принимает

рендера эти гарантии не добавляют GPU
пасс, шейдер или новые ресурсы.

## Необязательная физическая атмосфера и локальный объёмный туман (2026-11-20)

PRISMA владеет HDR-проходами `PhysicalSky` и `LocalFog`. Они выполняются до замера
экспозиции и обработки motion/temporal, затем идут обычные bloom/tonemap. Новые роли
целей 200/201 не пересекаются с DoF (50), metering и буферами движения. Глубину сцены
сэмплировать с существующим отдельным scratch depth attachment; ресурсы, зависящие от размера,
используют обычный путь fence-retirement PRISMA. Pipelines уничтожаются после её барьера
GPU-idle. Никакой второй реализации PostFx и никакого владения эмиттерами SpectraFX.

См. [физическое небо/облака/god rays](physical-sky.md) и
[локальный туман в сферах/OBB с runtime reveal](local-volumetric-fog.md).
Read-only мост PHYSIS нацелен на `Prisma&`; legacy-псевдоним `PostFx` остаётся
совместимым. По умолчанию эти возможности выключены. Нативные API регионов/настроек
действуют на весь владелец: хост с несколькими камерами должен задавать косметические данные
каждого вида до его resolve или использовать отдельного владельца Prisma. Смешивание профилей
camera-volume пока не задаёт и не интерполирует эти настройки атмосферы. Геймплей не меняется.

### Продолжение: структурированный туман

`FogVolume::structure` при необходимости формирует локальный туман периодическим 3D-шумом,
масштабом мира по каждой оси, затуханием по высоте и ветром; `Prisma::setLocalFogTime`
даёт воспроизводимые презентационные часы. Однородный туман по умолчанию сохраняется.
Этим владеет существующий проход локального тумана, без дополнительной истории и render targets.
См. раздел о структурированных полосах в `docs/local-volumetric-fog.md`. Сэмплирование
рельефа, игровая видимость и изменение состояния PHYSIS не вводятся.

Локальный туман теперь также поддерживает `heightVariation`, трёхмерный `warp`, размытие
границ `edgeErosion` и необязательные `selfShadow`/`shadowDistance`. Самозатенение делает
ray-march через все активные объёмы и отверстия reveal в сторону солнца, независимо от
существующей shadow map геометрии. Это ограниченное однократное рассеяние; никаких новых
temporal-буферов, владения shadow map, зависимости от рельефа или авторитетного состояния симуляции.

## Расфокусировка физического объектива по виду (LENS P2, stage 96)

`Prisma::setViewDepthOfField(viewId, DepthOfFieldOverride{enabled, focusDistance,
focusRangeMeters, maxBlur})` заменяет метрическую плоскость фокуса, интервал резкости и
максимальное размытие **авторского** эффекта `depthOfField` для одного стабильного вида
так же, как `setViewManualExposure` переопределяет авторскую экспозицию. Переопределение
принудительно включает метрическую (линейную по камере) ветвь и сохраняет `intensity` и
`occlusionToleranceMeters` эффекта. `enabled=false` выключает расфокусировку для этого вида.
Значения при поступлении ограничиваются границами каталога; `clearViewDepthOfField` и
`retireView` удаляют переопределение. По-прежнему требуются авторский эффект и
`AIVERSE_PRISMA_DOF=1`; в профиль ничего неявно не добавляется.

LENS управляет им из `CameraLensComponent::driveDepthOfField` через
`CameraPostFxPool`: интервал резкости тонкой линзы `[near, far]` превращается в
`focusDistance = (near+far)/2`, `focusRangeMeters = far-near` (бесконечная дальняя граница
ограничивается 500 м), а `maxBlur` = радиус диска фона на бесконечности в пикселях
рендера (ограничен 16). Это та же 8-tap screen-space расфокусировка, а не физический
bokeh. См. `docs/handoffs/prisma-stage-96-lens-physical-dof.md`.


## Пользовательский композитор кадра

Граф хранится в `postfx.compositor` игры или карты. В Studio откройте Post effects → Frame compositor, загрузите пример свечения и соедините выход прохода со входом следующего. В Targets and passes задаются имена текстур, масштаб, операции и параметры. Save graph проверяет весь документ перед сохранением. Карта наследует граф игры, пока не заменит блок postfx, не задаст свой граф или не отключит граф через `compositor:null`.

Вход `scene` содержит цвет сцены. Чтобы обработать выбранные объекты, задайте текстурной камере LENS маску видимости и добавьте ключ её выходной текстуры в список reads камеры-получателя. Источник `{"id":"selected","cameraInput":0}` указывает на первую зависимость. Управляемый камерный конвейер привязывает текстуры на один кадр и камеру. Нативный хост может вызвать `Prisma::setCompositorCameraInputs` до resolve. Пример находится в `examples/prisma/camera-glow.json`.

Граф содержит от 1 до 12 именованных текстур. Для каждой задаётся один записывающий проход. Делитель разрешения — 1, 2, 4 или 8. Итоговая текстура имеет полное разрешение. Проход задаёт id, op, inputs и target. Доступны downsample, bright (amount задаёт порог), blurX и blurY (множитель радиуса), add (взвешенный первый вход плюс второй) и shaderGraph (вложенный граф домена postfx в поле graph с основным входом и текстурами из проекта). PRISMA упорядочивает проходы по зависимостям; временные текстуры совместимого размера с непересекающимся временем жизни используют одну память. Граф выполняется после вкладов сцены до экранного освещения, замера экспозиции и тонмаппинга. При отсутствии источника или шейдера кадр сохраняет исходную сцену. Число выполненных проходов показывает `effectReport(viewId)->compositorPasses`. MCP сохраняет граф через `postfx_compositor_set`, читает через `postfx_get`.

## Аддитивные частицы в пространстве отображения

Эмиттеры и следы SpectraFX принимают `blendSpace:"display"`; по умолчанию используется `linear`. Renderer3D повторно использует подготовленную геометрию после тонального отображения PRISMA и перед HUD, с исходной глубиной сцены. PRISMA остаётся единственным владельцем тонального отображения. Альфа, туман и перекрытие непрозрачной геометрией сохраняются; такой вклад не участвует в HDR bloom, экспозиции и временных эффектах. Другие режимы смешивания отклоняют display-space. Обязательный GPU-режим отклоняет эту настройку; обычный граф использует CPU-путь представления.

Реальные пиксельные проверки Metal и три сцены Metal/WebGL сохранены в `docs/evidence/issues-additive-metal-20261127` и `docs/evidence/issues-material-effects-{metal,web}-20261127`. Windows/Vulkan и мобильные устройства не проверены. Интеграция и публикация выполняются отдельно после итоговой проверки. Пример: `demos/material-effects`; формат: `docs/particles.md`.
