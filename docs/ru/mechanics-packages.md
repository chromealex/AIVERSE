# Межжанровые игровые пакеты C++: первый набор

Это переиспользуемые детерминированные политики для кода проекта (native) и хоста. Они сочетаются с механиками
движка и не подменяют незаметно существующее перемещение FPS, способности и урон RTS или правила матча.

## Виды записей сохранения (genre::save/load)

Один реестр для всех пакетов, которые хранят состояние через `genre/Persistence.h`; новый пакет резервирует здесь
следующий свободный блок из восьми номеров, прежде чем его использовать.

| Виды | Владелец |
|---|---|

| 16..18 | weapon-policies (feed, charge, loadout) |
| 20..23 | character-locomotion (20 — режимы 0.2.0, по-прежнему загружаются; 21 — 0.3.0 с новыми движениями) |
| 32..36 | combat-actions |
| 40..47 | цели match-rules |
| 48..55 | stealth-senses |
| 56..63 | action-bots |
| 64..71 | сцены narrative-graphs |
| 72..79 | cinematic-gameplay (76 = мост NarrativeCueQueue) |
| 80..87 | physical-interactions |
| 88..95 | vehicle-controllers, sports-rules и их боты |
| 96..103 | card-games, tactics-grid, cards-turns-bots |
| 104..111 | settlement-production, survival-ecology |

| 128..135 | сессии гонок vehicle-controllers (128 `RaceSessionState`) |

## Интеграция с native-кодом и хостом

Подключите `<aiverselib/mechanics/Configured.h>`, нужный заголовок политики и `genre/Persistence.h`.
Исполняемые хосты линкуют `AIVERSE::genre`; зарегистрированные OBJECT-модули вызывают
`aiverse_native_use_genre(aiverse_native_<id>)` после `aiverse_native_module(...)`. Эта функция вешает зависимости
бэкенда коллизий на владеющую цель aiverse_game, избегая циклов линковки объектных библиотек.
Для политик только из заголовков без коллизий снарядов достаточно `AIVERSE::gameplay_native`.

Проверенные настройки и хранение в NativeState см. в `examples/native/libraries/GenreConsumer.cpp`.
Native-модуль library_demo теперь инициализирует эти записи в setup (модуль VERSION 7: добавлены жанровые записи этапов 1–4, включая головоломки, карты/тактику, транспорт/спорт и поселение/выживание).
`tests/libraries/genre_tests.cpp` проверяет траектории, комбо, столкновения с миром, переходы раундов,
транзакции выбора и восстановление. В проекте-потребителе правки исходников движка не нужны.

Внешний ввод должен приходить в виде проверенных Command. Используйте эти функции внутри владеющей авторитетной
системы или обработчика, а не из подачи. Храните неизменяемые определения отдельно от динамического состояния.
Используйте целочисленные тики и Fixed dt. Сохраняйте всё состояние, влияющее на исход, и не обновляйте один контроллер
дважды за тик. Политики motion, melee и match отвергают повторные и идущие назад тики. Шаговые функции recoil/projectile
— это примитивы одного шага; их владелец отвечает за ровно одно обновление на тик симуляции.

## Конфигурация

Скалярные значения по умолчанию находятся в `libraries/spec/gameplay.json` (пакет конфигурации 0.3.3): разделы
`locomotion`, `melee`, `projectile`, `matchRules`. После изменения спецификации запустите generate_gameplay.py.
Загружайте через `readGameplaySettings`, затем `motionConfig`, `locomotionModeConfig`, `attackConfig`, `projectileConfig`,
`matchConfig`. Ключи режимов перемещения необязательны (`maxSlopeMilliDegrees`, `ledge*`, `ladder*`, `swim*`,
`buoyancyMilli`, `climb*`, `mantle*`, `vault*`); нарушения соотношений вроде swimExit <= swimEnter <= swimFloat <= swimDive
и mantleMin <= vaultMax <= mantleMax отвергаются с понятными ошибками. Метры и секунды в JSON задаются целыми милли-единицами; C++ напрямую переводит их в Fixed.
Длительности в тиках — это буквальное число тиков при частоте тиков проекта. Существующие настройки остаются необязательными.

`examples/libraries/genre/settings.json` настраивает контроллер с двойным прыжком, тайминг атак,
рикошетящий снаряд и раунды best-of. Определения атак — типизированные записи AttackSet:
явно задавайте стабильные положительные ID, разрешённые ID комбо и cancelFrom. Проверка графа отвергает
неизвестные рёбра комбо. `attackConfig(settings,id)` по умолчанию разрешает отмену в комбо с начала восстановления.
RecoilConfig — типизированная публичная структура настроек; углы задаются в оборотах, восстановление — за шаг симуляции.

Сюжетный JSON читается через `readStory`, пример — `examples/libraries/genre/story.json`. У каждого узла и
выбора есть ключ локализации. Выбор `next:0` завершает граф; условия ссылаются на целочисленные ID фактов.
Отсутствующие факты делают условия ложными. Задавайте явный выбор-концовку даже для последнего узла диалога.
Неизвестные поля, повторяющиеся ID, битые рёбра и недопустимые целые значения отвергаются при загрузке.

## Режимы перемещения

`genre/LocomotionModes.h` добавляет `LocomotionModeConfig/State/Input/Result` и `stepLocomotion`. Он оборачивает
`stepMotion` для Ground/Air (на ровной земле поведение совпадает побитово) и добавляет режимы, управляемые только
`LocomotionEnvironment` — отчётом владельца коллизий на каждом тике:

- **Склоны:** земля с нормалью `normal.y >= cos(maxSlope)` проходима, и скорость следует плоскости;
  более крутая земля вызывает скольжение вдоль касательной под уклон (slideAcceleration, с ограничением slideSpeed),
  без прыжка. События SlideStart/SlideEnd.
- **Уступ:** при падении (или при захвате) рядом с сообщённым уступом, верх которого на ledgeMin..ledgeMax выше
  ног: вис, перемещение вдоль уступа по wish.x вдоль cross(up, normal), прыжок/вверх — подъём (фаза LedgeClimb по таймеру),
  отпустить/вниз — отпускание. Отпущенный уступ игнорируется в течение ledgeRegrabTicks.
- **Лестница:** захват прикрепляет, вертикальная скорость vertical*ladderSpeed; ladderTop + вверх запускает фазу выхода по таймеру наверх,
  ladderBottom/контакт с землёй + вниз — выход в Ground; прыжок отталкивает вдоль нормали лестницы.
- **Плавание:** погружение >= swimEnterDepth включает режим (но не при подъёме), < swimExitDepth выводит из него. Плавучесть
  тянет тело к floatDepth; вертикальный ввод погружает/всплывает (Dived/Surfaced на diveDepth); прыжок
  с головой над водой выводит из воды со скоростью waterJumpSpeed.
- **Лазание:** захват на стене, по которой можно лезть (climbEnabled); перемещение вдоль стены, расход выносливости за тик
  (встроенный счётчик или запас владельца через `stepLocomotionWithStamina`), прыжки от стены, выход на сообщённый
  уступ наверху или падение со StaminaDepleted.
- **Перелезание/перепрыгивание (mantle/vault):** прыжок рядом с препятствием высотой mantleMin..mantleMax запускает фазу по таймеру: подъём
  в первой половине, движение над obstacleDepth в остальное время. На земле препятствия высотой до vaultMaxHeight,
  взятые со скоростью >= vaultMinSpeed, перепрыгиваются за vaultTicks с сохранением импульса. Потолок во время подъёма прерывает фазу.

- **Рывок (0.3.0):** `dashPressed` — рывок вдоль wish (или `facing`, если wish нет) со скоростью dashSpeed
  на dashTicks без гравитации, выход со скоростью dashEndSpeed. На земле рывок бесплатный, в воздухе тратит
  один из `airDashes`; запас восстанавливается при приземлении и на стенных движениях. После рывка —
  dashCooldownTicks; стена впереди (`wallContact` с нормалью против рывка) останавливает его без импульса.
- **Скольжение по стене (0.3.0):** в воздухе, при падении, с сообщённым `wallContact` и wish в стену скорость
  падения ограничена wallSlideSpeed; прыжок — отталкивание от стены (contactNormal*wallJumpPush + jumpSpeed).
- **Бег по стене (0.3.0):** в воздухе с `wallContact` и скоростью вдоль стены >= wallRunMinSpeed — бег по
  касательной со скоростью wallRunSpeed в прежнем направлении; вертикальная скорость начинается с max(vy,0)
  и убывает с gravity*wallRunGravityScale, не дольше wallRunTicks. Конец — земля, потеря контакта, drop или
  таймер, затем wallRunCooldownTicks; прыжок — толчок от стены + скорость бега + jumpSpeed.
- **Крюк-кошка (0.3.0):** владелец прицеливается (raycast) и каждый тик сообщает `grappleAnchor` и
  `grappleOffset` (точка минус тело); `grapplePressed` цепляется на расстоянии grappleArrive..grappleMaxLength.
  Pull (по умолчанию) летит к точке со скоростью grappleSpeed и отцепляется ближе grappleArrive. Swing
  (`grappleSwing`) — гравитация и слабое управление в воздухе, верёвка только тянет (наружная радиальная
  скорость убирается, растяжение исправляется со скоростью до grappleSpeed), `vertical` сматывает со
  скоростью grappleReelSpeed. Прыжок, `grappleReleased`, потеря точки или grappleTicks отцепляют.
- **Односторонние платформы (0.3.0):** владелец ставит `groundOneWay`, стоя на такой платформе; drop
  спрыгивает (DropThrough), а `LocomotionResult::ignoreOneWay` держится oneWayDropTicks, чтобы проверка
  коллизий пропустила тело вниз. `oneWaySupports(top, previousFeet, feet, vy, ignoreOneWay)` — проверка
  приземления у владельца: только сверху, не при подъёме и не во время спрыгивания.

- **Планирование (0.3.0):** в воздухе, при падении, без стены и с `jumpHeld` (удержание, а не нажатие прыжка):
  скорость падения ограничена glideFallSpeed, тело летит со скоростью glideForwardSpeed по wish (или `facing`).
  Конец — отпускание, земля или стена.
- **Та же стена (0.3.0):** `env.wallId` (0 — неизвестно) запрещает стену, от которой только что оттолкнулись, на
  wallReattachTicks, а стену с истёкшим бегом — до приземления; по стенам с `env.wallRunnable=false` можно только скользить.
- **Хост акторов:** правила `locomotion` переводят персонажей engine/actor на этот автомат с предсказанием на клиенте
  (docs/fps.md § Режимы перемещения). Отдельный пакет traversal-moves влит сюда (один владелец).

Каждому движению нужен свой ввод или отчёт окружения, поэтому вызовы 0.2.0 ведут себя побитово так же;
хеш конфигурации и хеш состояния 0.2.0 не меняются, пока новые поля по умолчанию (тест фиксирует хеш конфигурации 0.2.0).

Владелец держит dt постоянным (скорости фаз вычисляются при входе), вызывает функцию один раз за тик и двигает
тело с протяжённой проверкой коллизий. Недопустимые config/state/input, dt вне (0,1] и повторные или идущие назад тики
возвращают nullopt, не меняя состояние. Всё состояние (включая вложенный MotionState и фазу mantle)
сохраняется через `genre::save/load` (вид состояния 21; записи 0.2.0 вида 20 по-прежнему загружаются) и хешируется `locomotionHash`; привязывайте
`locomotionConfigHash` в конверте сохранения. Лазание и IK в подаче (surface-locomotion.md) читают
режим и события, но не решают их. Сетевое предсказание и откат — забота владельца: восстановите
сохранённую запись и повторите те же вводы.

## Контракты выполнения

**Motion:** `jumpPressed` — это фронт ввода, а не удерживаемая кнопка. Владелец физики должен давать фактический
результат коллизий на следующем тике. Сход с уступа расходует наземный прыжок, когда окно coyote
истекает. Буферизованное нажатие может сработать при приземлении до истечения. Политика ограничивает предельную скорость падения
1000 единиц в секунду и принимает dt в (0,1]. Она не добавляет дополнительные прыжки мотору FPS автоматически.

**Melee:** одна активная атака владеет отсортированным списком ID уже поражённых целей. Используйте стабильные упакованные ID сущностей,
помещающиеся в положительный int64 (или ID, принадлежащие проекту). `recordMeleeHit` записывает только контакты в активном окне;
вызывайте его после авторитетной пространственной проверки и проверки команды. `stepMelee` вызывает авторизацию, только когда атака
может начаться; делайте расход атомарным в этом колбэке и выдавайте результирующие эффекты через существующего владельца.
`resolveMeleeContact` отдаёт приоритет неуязвимости, затем парированию, затем блоку, затем обычному попаданию. Он не
вычисляет отдельную формулу урона. Буфер ввода истекает; ни одно попадание не может быть выдано дважды за один взмах.

**Оружие:** используйте `sim.rng()` с `sampleSpread`; недопустимый разброс не расходует RNG. Выборка использует равномерные
целочисленные смещения yaw/pitch, а не равномерный по телесному углу конус. Сохраняйте отдачу, если она меняет авторитетное прицеливание.
Движение снаряда использует настоящую протяжённую проверку AABB мира (радиус как равные половинные размеры), избегая
пролёта быстрых снарядов сквозь боксы. За тик обрабатывается одно столкновение; оставшийся после отскока путь
отбрасывается. Каждое столкновение возвращается владельцу урона и эффектов для обработки. Время жизни считает завершённые
шаги, поэтому при lifetime=1 снаряд сдвигается один раз. Снаряды, выходящие за границы мира +/-100000, ограничиваются и уничтожаются.
Никакие физические позиция, скорость, боезапас или урон не копируются незаметно в существующее состояние актора FPS.

**Матчи:** инициализируйте уникальные положительные ID команд через makeMatch. `awardScore` принимает неотрицательные очки
только во время игры/овертайма, со строго возрастающими ID событий для каждой команды. Сохраняйте эти ID между раундами;
никогда не используйте их повторно, пока могут прийти отложенные команды. Step вычисляет переходы по счёту и часам. Овертайм
заканчивается при единоличном лидере или по своему пределу; раунды с равным счётом могут завершиться ничьей. Победа в матче определяется по выигранным раундам. Точки захвата
замораживаются, пока оспариваются, теряют прогресс на единицу за каждый пустой тик и закрепляют владение при достижении порога.
Вызывающая сторона проверяет присутствие и начисляет связанные очки и награды. Количество присутствующих не считается доверенным вводом.

**Сюжет:** доступные выборы стабильны по ID. `chooseStory` повторно проверяет условия, применяет все изменения
фактов к копии, отвергает переполнение целых, фиксирует следующий узел и атомарно записывает ID команды.
Один явный выбор даёт один переход; циклы разрешены без рекурсивного автовыполнения.
Изменяются только принадлежащие проекту сюжетные факты. Для наград и инвентаря используйте существующего транзакционного владельца
и идемпотентное событие из зафиксированного сюжетного перехода; не считайте приращение факта кошельком.

## Состояние и проверка

Запустите catalog.py check, generate_gameplay.py --check, tests/libraries/run.py и native_consumer.py.

настоящие приёмочные проверки геймплея, а также проверки реплея и сохранений. Текущие тесты проверяют политики C++ и настоящие
коллизии; это не заявление о том, что поставляется законченный UI платформера, файтинга или сюжетной игры. В этом наборе нет изменений
рендеринга. Пути выполнения Windows, подачи на Metal, мобильных платформ и веба остаются непроверенными.

## Боевые действия (combat-actions 0.1.0)

Заголовок `genre/CombatActions.h` (+ адаптеры настроек `CombatConfigured.h`, JSON хитбоксов `CombatData.h`).
Цель `AIVERSE::lib_combat_actions` (зависит от `lib_melee_combat`, `aiverse_engine`); native OBJECT-модули
вызывают `aiverse_native_use_libraries(target combat-actions)`. Навык: `skills/gameplay/aiverse-combat-actions`.

**Формы и попадания:** метры в Fixed; yaw в оборотах вокруг +Y (yaw 0 смотрит на +Z, +X — вправо). `CombatShape` — это
сфера (центр a), капсула (отрезок a..b) или бокс (центр a, половинные размеры, вращение только по yaw, радиус 0).
`overlaps` точен для сферы/бокса/бокс-бокс (SAT) и использует детерминированный целочисленный тернарный поиск по
параметру отрезка для капсул; касание считается пересечением. `HitboxDef{id,from,to,shape}` активен для возрастов атаки
`[from,to)`, которые должны лежать внутри активного окна атаки. `collectMeleeHits` преобразует хитбоксы позой
атакующего, а хёртбоксы — позой каждой цели, пропускает себя, ту же ненулевую команду (если нет friendlyFire) и
цели, уже поражённые этим взмахом, и записывает попадания через `recordMeleeHit`. Контакты сортируются по ID цели
и называют первый пересекающийся хитбокс/хёртбокс по возрастанию ID. Недопустимые данные или повторяющиеся ID целей возвращают
nullopt, не трогая состояние. Пересечения проверяются по тикам (без sweep между тиками).

**Защита:** `stepDodge` (колбэк авторизации, перезарядка отсчитывается от конца уклонения) и `dodgeInvulnerable`
(`[invulnFrom,invulnTo)` от начала). `stepGuard` поднимает/опускает защиту; подъём открывает окно `parryTicks`,
если предыдущий подъём был не менее `rearmTicks` назад. `insideGuardArc` сравнивает направление на атакующего с
yaw защищающегося (`halfArc` оборотов в каждую сторону). `resolveCombatContact` передаёт данные в `resolveMeleeContact` из Melee.h
(invulnerable > parry > block > hit); `unblockable` обходит защиту.

**Стойкость (poise):** целые милли-единицы. `stepPoise` один раз за тик (инициализирует максимумом, восполняет
`recoveryPerTick` спустя `recoveryDelay` после последнего урона по стойкости, сбрасывает в полную после оглушения от слома).
`applyPoiseHit` в том же тике: Hit снимает полный урон + оглушение от попадания, Blocked снимает `blockScaleMilli/1000`
+ оглушение от блока, Parried/Evaded ничего не снимают. Достижение 0 ломает стойкость (`breakStunTicks`); пока она сломана, следующие
попадания ничего не добавляют. `applyParryStagger` оглушает парированного атакующего; `interruptMelee` отменяет взмах.

**Захват цели (lock-on):** `lockScore = distance/range*distanceWeight + |angle|/halfAngle*angleWeight`; побеждает меньшее значение,
при равенстве — меньший ID. `stepLockOn`: сброс, если цель пропала, недоступна или дальше `breakRange`; переключатель отпускает или
захватывает; смена выбирает ближайшего по углу соседа с этой стороны среди оцениваемых кандидатов (без перехода через край),
затем по расстоянию, затем по ID. Видимость кандидатов (`targetable`) берётся из авторизованных органов чувств владельца.

**Настройки:** необязательный раздел `combat` в `libraries/spec/gameplay.json` (конфигурация 0.3.2):
dodgeTicks/dodgeInvulnFrom/dodgeInvulnTo/dodgeCooldown, blockHalfArcMilli (милли-обороты), parryTicks,
parryRearmTicks, poiseMilli, poiseRecoveryMilli, poiseDelayTicks, blockPoiseMilli, тики оглушения hit/block/break/parry,
lockRangeMilli/lockBreakMilli (миллиметры), lockHalfAngleMilli (милли-обороты), веса захвата.
Загрузчик отвергает `dodgeInvulnFrom > dodgeInvulnTo`, `dodgeInvulnTo > dodgeTicks` и
`lockRangeMilli > lockBreakMilli`. Хитбоксы: `readHitboxes(json, attacks)`, см.
`examples/libraries/genre/hitboxes.json`; неизвестные ключи/атаки, кадры вне активного окна, неверные формы
и невозрастающие ID дают ошибки с указанием пути.

**Состояние:** `CombatActorState{dodge,guard,poise,lock}` и каждый его член — записи `genre::save/load`
(виды 32..36 зарезервированы за этим пакетом), канонические и проверяемые при загрузке. `combatHash` / `hashCombatState`
хешируют канонические байты для контрольной суммы симуляции. Все шаговые функции отвергают повторные и идущие назад тики.
`GenreConsumer.cpp` проводит один взмах по защищающемуся, разрешает контакт, применяет стойкость и сохраняет
`genre.combat`, `genre.combat_swing` и `genre.combat_hash` в NativeState. Проверено только с g++ 11
(Linux VM): проверки синтаксиса заголовков, исходники `aiverse_library_genre_tests`, собранные вручную (также ASan/UBSan), и
функция-потребитель в автономном драйвере. Полная сборка движка, aiverse_tests, тесты изоляции CMake,
экспорт native-модуля и headless-матчи с восстановлением для этого пакета не запускались.

## Оружие и баллистика (weapon-policies 0.2.0)

Новые заголовки строятся поверх `Weapons.h`, не меняя его: `genre/Ballistics.h` (пробитие, взрывы,
прицеливание), `genre/WeaponMods.h` (системы питания, заряд, обвесы), `genre/WeaponData.h` (адаптеры
настроек, JSON оружия) и `genre/WeaponPersistence.h` (сохранение/загрузка, хеширование). Вся математика на Fixed/целых;
недопустимый ввод возвращает `std::nullopt` (или `false`), не вызывая колбэков владельца и не меняя состояние.

**Пробитие.** `traceLayers(world, start, delta, materialOf)` возвращает каждый коллайдер, пересечённый
отрезком, в порядке (вход, id коллайдера) с геометрической толщиной (вход/выход для бокса по двум протяжённым проверкам;
треугольники — листы нулевой толщины). Пересекающиеся коллайдеры — отдельные слои. `resolvePenetration`
проходит слои с `MaterialTable`: каждый слой стоит `resistance * thickness` мощности
(толщина не меньше `minThickness`), урон и скорость умножаются на `1 - falloff * thickness`
(с нижней границей 0). Он останавливается на неизвестном/непробиваемом материале, исчерпанной мощности, `minDamage`, `minSpeed`
или `maxLayers`, сообщая `PenetrationStop` и для каждого слоя `damageIn` (урон для находящегося в этом слое)
и значения на выходе. Нанесение урона находящимся в слоях остаётся работой владельца боя.

**Взрывы.** `resolveExplosion(config, center, targets, exposure)`: полный эффект внутри `innerRadius`,
линейное затухание до `edgeScale` на `outerRadius`, дальше — ничего. Расстояние берётся до ограничивающей
сферы цели (radius). Целям нужны уникальные положительные ID. Задаваемая владельцем `exposure(target)` (видимость/укрытие, 1 —
видна, 0 — перекрыта, с ограничением) вызывается один раз для каждой цели в радиусе в порядке (расстояние, id), никогда для
целей вне радиуса, и останавливается на `maxTargets` открытых попаданиях. Перекрытые цели пропускаются. Результаты содержат
урон, величину и направление импульса (вверх для совпадающей с центром цели) в одном и том же порядке независимо от
порядка входа.

**Системы питания.** `stepFeed(config, state, tick, {fire, reload, cancel}, draw)` — автомат состояний на каждый тик
(один вызов на оружие за тик, строго возрастающие тики). Виды: Magazine (перезарядка целиком, необязательная более долгая
перезарядка пустого), Belt (каждый выстрел берёт из запаса владельца), PerShell (по одному патрону за `shellTicks` после
`reloadStartTicks`), Energy (без боеприпасов). Необязательный нагрев для любого вида: перегрев при `heatCapacity`,
блокировка не менее `overheatTicks` и пока не будет `heat <= recoverHeat`; охлаждение `coolPerTick` за каждый прошедший тик.
`intervalTicks` и `spinupTicks` (тики удержания спуска до первого выстрела) — необязательные правила темпа.
`draw(n)` должна атомарно забрать до n патронов из запаса владельца (инвентарь, мета-кошелёк, ...)
и вернуть выданное количество; она вызывается только после проверки, поэтому шаг всегда фиксируется. Порядок за
тик: охлаждение/восстановление, отмена/прерывание перезарядки, начало перезарядки (явное или автоматическое при выстреле вхолостую), ход
перезарядки, выстрел. Выстрел при оставшихся патронах прерывает прерываемую перезарядку: прогресс магазина теряется,
вставленные патроны остаются. Эти записи отделены от боезапаса акторов `modules/fps`: никогда не отражайте один магазин
у обоих владельцев.

**Режимы заряда.** `stepCharge(config, state, tick, {held, cancel})` (ввод уровнем, один вызов за тик).
Отпускание до `minTicks` отменяет (или стреляет уровнем 0 при `fireBelowMin`); тики удержания ограничены
`maxTicks`; `tier` считает достигнутые пороги, `fraction` — прогресс от минимума к максимуму, `scale` — масштаб
уровня (или `baseScale`). `autoReleaseTicks` стреляет автоматически и защёлкивается до отпускания спуска.

**Обвесы.** `WeaponFrame` (характеристики с base/min/max, разрешённые слоты) + `AttachmentSet` (по одному в слоте,
модификаторы add/mul). `equipAttachment` проверяет слот/ID и возвращает заменённый обвес;
`resolveStats` применяет base, затем все Add, затем все Mul (по возрастанию id слота, в авторском порядке,
последовательное округление Fixed), затем ограничивает. Порядок установки никогда не меняет результат. Промежуточные значения ограничиваются
+/-1e10, поэтому никакие данные не переполняются.

**Прицеливание.** `solveLaunch(delta, speed, gravity)` возвращает 0, 1 или 2 решения запуска (низкая/высокая дуга,
гравитация вдоль -Y, как в `ProjectileConfig`). Он решает относительно времени полёта, поэтому аналитическая траектория проходит
через цель с точностью до округления Fixed, а |velocity| приближает `speed`; масштабированный степенью двойки
дискриминант удерживает большие дальности в пределах Q47.16. `solveIntercept(config, origin, target, velocity, ...)`
берёт упреждение по цели с постоянной скоростью не более чем за `maxIterations` решений; `converged` сообщает, что последовательные
времена полёта отличаются не более чем на `tolerance` секунд. `found=false`, когда предсказанная точка становится недостижимой.

**Конфигурация.** Генерируемые разделы `penetration`, `explosion`, `ammoFeed` (`kind`: 0 magazine, 1 belt,
2 perShell, 3 energy), `charge` (`tiers` равномерно распределены от minTicks до maxTicks, масштабы от minScale
до maxScale) и `aimSolver`, все в милли-единицах/тиках и необязательные. Адаптеры: `penetrationConfig`,
`explosionConfig`, `feedConfig`, `chargeConfig`, `aimConfig`; `weaponSettingsErrors` сообщает понятные
проблемы между полями (ammoPerShot против capacity, shellTicks, recoverHeat, autoRelease, расстановка уровней).
Таблицы используют `readWeaponDefinitions` (`examples/libraries/genre/weapons.json`): `materials`, `frame`,
`attachments`; неизвестные ключи, дубликаты, неизвестные слоты/характеристики, неверные операции и диапазоны выбрасывают
`JsonError("weapons.<path>: ...")`. Пример настроек: `examples/libraries/genre/weapon-settings.json`.

**Состояние.** `FeedState`, `ChargeState` и `LoadoutState` используют `genre::save/load` (версия 1, виды 16-18;
каноническая кодировка, недопустимые записи отвергаются). Храните каждое под своим ключом NativeState и привязывайте
неизменяемые конфигурации/определения в конверте сохранения проекта. `hashWeapon(hasher, value)` / `weaponHash`
сворачивают каноническую кодировку состояний и исходов каждого вызова (пробитие, попадания взрыва, запуск,
шаги feed/charge) в контрольную сумму владельца. `GenreConsumer.cpp` проверяет настройки и определения,
запускает каждую политику один раз и сохраняет начальные записи feed/charge/loadout.

Проверено: проверки синтаксиса заголовков (g++ 11, `-Wall -Wextra -Werror -pedantic`), `genre_tests.cpp` с g++
(также под ASan/UBSan), покрывающий цепочки пробития, порядок/затухание/перекрытие взрывов, последовательности питания/перезарядки/
перегрева, уровни заряда, сложение обвесов, точность прицеливания, сохранение/восстановление и недопустимые данные, а также
автономный запуск функции GenreConsumer. В том изменении не проверено: CMake/полная сборка движка,
`aiverse_tests`, headless-матчи, MSVC/clang, выполнение на платформах.

## Цели матча (match-rules 0.2.0)

Новые заголовки строятся поверх `Match.h`, не меняя его: `genre/MatchObjectives.h` (политики, мост к счёту,
сохранение), `genre/MatchObjectivesConfigured.h` (адаптеры настроек) и `genre/MatchObjectivesData.h`
(JSON раскладки). Каждая шаговая функция принимает целочисленные тики, отвергает повторные/идущие назад тики и недопустимые config/state/
input, возвращая `std::nullopt` без изменения состояния, и возвращает `ObjectiveEvents` (`kind`, `team`, `subject`,
`value`; команда 0 — информационная, например ничья). Расстояния — метры в Fixed. Владелец даёт только
проверенные факты: `Occupants` (команда -> присутствующие тела, например подсчитанные через `insideZone`), толкающих/защищающих тележку,
смерти, тела внутри зоны эвакуации, носителя бомбы/обезвреживающих/подборы и прохождения ворот (`crossesGate`).

- **Зоны / царь горы.** `stepZone`: единственная присутствующая команда захватывает со скоростью `min(bodies, maxCapturers)` за тик; другая
  команда сначала сливает существующий прогресс; пустые зоны затухают на `decayPerTick`; присутствие владельца откатывает прогресс
  противника со своей скоростью. `ContestRule::Freeze` замораживает при любой второй команде, `Majority` продвигает строгое
  большинство на разницу в числе тел (при равенстве — заморозка). `neutralizeFirst` делает зону с владельцем нейтральной на пороге,
  прежде чем её можно захватить. `ZoneContested` срабатывает при начале оспаривания; `state.contested` — текущий флаг.
  Очки за удержание: `ZoneHoldTick` каждые `holdScoreInterval` тиков, пока владелец контролирует зону (или просто владеет
  ею при `holdRequiresPresence=false`); тик захвата учитывается. `kingOfTheHill(captureTicks, interval)` —
  пресет; `activeHill(HillRotation, start, tick)` даёт индекс сменяющегося холма (при смене сбрасывайте зону).
  `stepCapture` из Match.h не изменён (простой вариант: сбрасывает, а не сливает).
- **Груз (payload).** `makePayloadTrack(points, checkpoints)` (ломаная, строго возрастающие контрольные точки внутри
  длины), `payloadPoint` переводит прогресс в позицию. `stepPayload(config, track, state, attackers, defenders,
  tick)`: толкающие двигают тележку со скоростью `pushSpeed * (1 + extraPusher * (n - 1))`, n ограничено `maxPushers`;
  защищающие блокируют при `contestBlocks`; после `reverseDelayTicks` без атакующих она откатывается со скоростью
  `reverseSpeed`, но никогда не за достигнутую контрольную точку при `checkpointLock`. `PayloadCheckpoint` несёт
  `checkpointBonusTicks` для `extendClock`; `PayloadDelivered` — конечное событие.
- **Выбывание.** `makeElimination(config, roster)`; `stepElimination(config, state, tick, deaths)` (только уникальные
  живые игроки). `lives` учитывает первую жизнь (0 = без ограничений). Возрождение в первую волну
  (`start + k * respawnWaveTicks`) не раньше смерти + `respawnDelayTicks` (волна 0: индивидуальный таймер).
  Команда без оставшихся жизней (или со всеми членами, погибшими одновременно, при `wipeEliminates`) выдаёт `TeamEliminated`; когда
  остаётся не более одной команды — `LastTeamStanding` (команда 0 и `lastStanding = -1` при взаимном уничтожении).
- **Эвакуация.** `stepExtraction(config, state, tick, inside)`: начиная с `opensAtTicks` после первого шага
  каждое тело, несущее `requiredItems`, продвигается на один тик; прогресс заморожен, пока внутри другая команда
  (`contestBlocks`); выход сбрасывает (`resetOnLeave`) или замораживает прогресс. `Extracted` — один раз на игрока.
- **Бомба / обезвреживание.** `makeBomb(attackers, defenders, carrier)`; `stepBomb` с `BombInput{plantSite,
  defusers, pickups, carrierDown}`. Устанавливает только носитель (смена точки начинает заново); отпускание прерывает
  (`plantResets`); сбитый носитель роняет бомбу; её берёт атакующий с наименьшим ID среди подбирающих. После
  установки (`BombPlanted.value` = тик взрыва) приоритет сохраняет текущий обезвреживающий, иначе защитник с наименьшим
  ID; набор сапёра использует `kitDefuseTicks`; смена/отпускание прерывает (`defuseResets`). Запал проверяется первым,
  поэтому обезвреживание, завершающееся в тик взрыва, проигрывает. `bombPending` сообщает об установленной бомбе для овертайма.
- **Ворота маршрута.** `makeRoute(racers)`; `stepRoute(config{gates, laps}, state, tick, crossings)` применяет
  прохождения для каждого участника в заданном порядке и игнорирует ворота не по порядку: `GatePassed`, `LapCompleted`,
  `RouteFinished` (value = место). `routeStandings`: место, затем прогресс по кругам/воротам, более ранние последние ворота, ID.
- **Часы и овертайм.** `startClock(config, tick)` (предел = `matchRules.roundTicks` через
  `objectiveClockConfig`), `extendClock` (ограничено `maxDeadlineTicks` от начала; выходит из овертайма),
  `stepClock(config, state, tick, contested)`: к сроку оспариваемая цель (определяется владельцем:
  `zone.contested`, атакующие у тележки, `bombPending`, ...) запускает овертайм, который заканчивается через `graceTicks` после
  последнего оспариваемого тика или по `maxOvertimeTicks` (0 = без ограничения) с `OvertimeEnded` + `TimeExpired`.
- **Наблюдатели.** `spectatorDied(config, state, killer, tick)`, затем `stepSpectator(config, state, tick,
  candidates, cycle)`: камера убийцы на живом убийце в течение `killCamTicks` (переключение её завершает), затем слежение: держать
  текущую цель, пока она подходит, иначе первая подходящая после неё в порядке «союзники по возрастанию ID, затем
  противники по возрастанию ID» (`allowEnemies`), с переходом по кругу; никто не подходит -> `Free`. `cycle` +1/-1 проходит этот порядок.
- **Очки.** `awardObjectiveEvents(match, scoring, events, nextEvent)` начисляет очки за каждый вид события через
  `awardScore` со строго возрастающим счётчиком событий владельца; фиксируются либо все начисления, либо ни одного. 
  `awardObjectiveWin(config, match, team, nextEvent)` делает команду единоличным лидером не менее чем с
  `scoreToWin`, так что следующий `stepMatch` закрывает раунд. Встроенные режимы победы сохраняют своих владельцев.

**Конфигурация.** Необязательный генерируемый раздел `objectives` (спецификация пакета конфигурации 0.3.2): zone*,
holdScoreInterval/holdRequiresPresence, hillRotateTicks/hillCount, payload* (миллиметры за тик),
eliminationLives/respawnDelayTicks/respawnWaveTicks/wipeEliminates, extraction*, bomb*, overtimeEnabled/
overtimeGraceTicks/overtimeMaxTicks/clockMaxTicks, spectator*, routeLaps. Загрузчик отвергает
`zoneDecayPerTick > zoneCaptureTicks` и `bombKitDefuseTicks > bombDefuseTicks`; `objectiveSettingsErrors`
сообщает о смене холмов без периода, clockMaxTicks меньше roundTicks, волнах при единственной жизни, отсрочке
больше предела овертайма и обезвреживании с набором, которое не успевает раньше запала. Адаптеры: `zoneConfig`, `hillRotation`,
`payloadConfig`, `eliminationConfig`, `extractionConfig`, `bombConfig`, `objectiveClockConfig`,
`spectatorConfig`, `routeConfig(settings, gates)`. Раскладки: `readObjectiveLayout` (зоны с видом
capture/hill/extraction/bombSite, путь груза + контрольные точки, ворота маршрута); неизвестные ключи, повторяющиеся ID, неверные
виды, короткие/повторяющиеся пути, контрольные точки вне пути, невозрастающие ID ворот и короткие нормали выбрасывают
`JsonError("objectives.<path>: ...")`. Примеры: `examples/libraries/genre/objectives.json`,
`examples/libraries/genre/objective-settings.json`.

## Скрытность и органы чувств (stealth-senses 0.1.0)

Заголовки `genre/Senses.h` (политика), `genre/SensesConfigured.h` (адаптеры настроек), `genre/SensesData.h`
(JSON маскировок/укрытий) и `genre/SensesPersistence.h` (сохранение/загрузка, хеширование). Цель `AIVERSE::lib_stealth_senses`
(зависит от `aiverse_engine`); native OBJECT-модули вызывают `aiverse_native_use_libraries(target stealth-senses)`.
Навык: `skills/gameplay/aiverse-stealth-senses`. Это общая политика восприятия для каждого агента — стражников, монстров и
ботов; туман войны RTS остаётся в `modules/rts` (RtsVision). Долговременная память и ранжирование угроз могут строиться на `ai-perception`.

**Тик.** `stepSenses(config, defs, state, tick, input, los, occlusion)` один раз за авторитетный тик, строго
возрастающие тики; недопустимые config/definitions/state/input (повторяющиеся или неположительные ID, множители вне
диапазона 0..4000, неизвестные ID маскировок/укрытий, неверный радиус шума) или повторный/идущий назад тик возвращают nullopt и
оставляют состояние нетронутым. Списки ввода могут приходить в любом порядке; они обрабатываются по возрастанию ID. Порядок внутри
тика: истечение меток, доставка наступивших тревог, надевание/раскрытие маскировки, выходы из укрытий, зрение, входы в укрытия, слух,
обнаружение следов, оставление меток, подозрение, рассылка тревог, поиск, записи. Наблюдатели, отсутствующие во вводе,
заморожены (нет затухания и прогресса поиска); адресованные им тревоги отбрасываются (`AlertDropped`).
`stepSensesOpen` использует колбэки «всегда видно» / «без перекрытия» (тесты, открытые пространства).

**Зрение.** Метры в Fixed; yaw в оборотах вокруг +Y (yaw 0 смотрит на +Z). Глаз = позиция + eyeHeight. Зоны: Focus
(|bearing| <= halfAngle, расстояние <= range; сила nearMilli внутри nearRange, линейно падающая до farMilli на
range), Near (любое направление в пределах nearRange, nearMilli) и Peripheral (|bearing| <= peripheralHalfAngle,
расстояние <= peripheralRange, peripheralMilli); применяется самая сильная. Затем сила умножается на
освещённость/укрытие/стойку/заметность цели и sightMilli наблюдателя (milli, с ограничением 1000). Только выборки
>= `sight.minMilli` доходят до `los(agent, target)`, который вызывается в порядке (id наблюдателя, id цели), не более
`sight.maxQueries` за тик (`losSkipped` считает остальные). Себя и ту же ненулевую команду наблюдатель никогда не воспринимает.

**Слух.** `NoiseEvent{id, source, team, position, radius, loudnessMilli}`; source 0 = анонимное возмущение
(ограничено уровнем Searching). Сила = loudness * (radius - distance)/radius * occlusion/1000 * hearingMilli/1000.
За тик обрабатывается не более `hearing.maxNoises` событий, сначала самые громкие, затем с меньшим ID (для остальных — события `NoiseDropped`).
`occlusion(agent, noise)` (milli 0..1000, с ограничением) выполняется в этом порядке шумов, затем по ID слушателя,
только для слушателей, у которых сила без перекрытия достигает `thresholdMilli`, не более `hearing.maxQueries` за тик.
Шумы своей команды игнорируются; спрятавшиеся цели всё равно шумят.

**Следы.** `SenseTarget::leaveTrail` оставляет метку (сила trailMilli) после обнаружения в этом тике.
Метки линейно затухают до нуля за `trail.lifetime` и затем удаляются; сверх `maxMarkers` удаляется самая старая.
Наблюдатели воспринимают самую сильную метку каждого владельца в пределах `trail.range` (масштабируется расстоянием и trailMilli,
>= minMilli; при равенстве — меньший ID метки) без проверки линии видимости.

**Подозрение.** Одна `AwarenessRecord` на (наблюдатель, цель): прирост за тик = (sight*sightGain + hearing*hearingGain
+ trail*trailGain)/1000, масштабируется активной маскировкой. Уровни: >= alertAt — Alert, >= searchingAt — Searching,
>= suspiciousAt — Suspicious (1 <= suspiciousAt < searchingAt < alertAt <= maximum). Без раздражителя счётчик
затухает на decayPerTick за тик, начиная через decayDelay тиков после последнего раздражителя (точно и через пропущенные тики),
никогда не ниже searchingAt для активной цели поиска; записи с 0 удаляются. Последняя известная позиция берётся по приоритету
зрение > слух > след; тревоги обновляют её, если они новее.

**Тревоги.** Воспринятый переход в Alert (или любой переход при `alert.relay`) планирует `PendingAlert` для
союзников той же ненулевой команды в пределах `alert.radius` от отправителя, которые ещё не находятся в Alert по этой
цели; доставка происходит через `alert.delay` тиков (ограничено `maxPending`). Получение поднимает счётчик получателя до
`receivedMilli` и передаёт последнюю известную отправителю позицию и её тик.

**Поиск.** Когда самая сильная запись Searching/Alert в этом тике не воспринимается, наблюдатель начинает один поиск:
точки = последняя известная позиция, затем `SearchCandidate` владельца в пределах `candidateRadius` по (расстояние, ID), до
`maxPoints`. `searchGoal(state, observer)` — текущая точка; её достижение (горизонтальное расстояние <=
pointRadius, одна точка за тик) выдаёт `SearchPointReached`. Новый раздражитель (или более новая переданная позиция)
перепланирует поиск и продлевает срок; если цель увидена на уровне Alert, поиск заканчивается `SearchFound`. Посещение всех точек или
`giveUpTicks` без контакта завершает поиск событием `SearchGaveUp` и опускает счётчик до `suspiciousAt`.

**Маскировка.** `DisguiseDef{id, factions, zones, blownBy, scaleMilli, trespassScaleMilli}`: наблюдатели из
перечисленных команд масштабируют прирост от носителя на scaleMilli внутри зон (пусто = везде) и на
trespassScaleMilli в других местах. Любое действие из blownBy раскрывает маскировку (`DisguiseBlown`) для всех, пока владелец
не наденет её снова (`equipDisguise` > 0; 0 снимает).

**Укрытия.** `enterHiding` удаётся в пределах `hiding.enterRange` от укрытия и пока не превышена его вместимость, иначе
`HidingRefused`. Наблюдатели, у которых проверка линии видимости удалась в тик входа, продолжают видеть цель (`revealedTo`); все остальные
наблюдатели не могут её увидеть (вызова LOS нет), пока их поиск не дойдёт до кандидата с этим укрытием
(`HidingRevealed`). `exitHiding` или отход дальше enterRange выводит из укрытия (`HidingExited`, extra 1 при автоматическом выходе).

**Выходные данные для ботов.** `PerceivedTarget{observer, target, level, suspicion, lastKnown, lastKnownTick, lastSense,
sensedNow, visibleNow, strengthNow, searching}`, отсортированные по (observer, target), по одной на запись присутствующих
наблюдателей. Это контракт для жанровых политик ботов: преследовать/вступать в бой при `visibleNow && level==Alert`, исследовать
`lastKnown` или `searchGoal` в состоянии Searching, иначе бездействовать. `SenseEvent{kind, observer, target, value, extra}`
перечисляет переходы в порядке тика. Вызывающие стороны преобразуют записи в наблюдения `ai-perception`, если им нужна память с TTL.

**Настройки.** Необязательный раздел `senses` (конфигурация 0.3.3): sight* / peripheral* (миллиметры, милли-обороты,
силы в milli, sightQueryBudget), hearingThresholdMilli, noiseBudget, occlusionBudget, noiseMaxRadiusMilli,
trail*, пороги/приросты/затухание подозрения, alert*, alertRelay, search*, hideEnterRangeMilli. Генерируемый загрузчик
отвергает нарушения соотношений (`senses.sightNearMilli: must not exceed sightRangeMilli`, ...);
`sensesSettingsErrors` добавляет строгий порядок порогов. Пример: `examples/libraries/genre/senses-settings.json`.
Определения: `readSenseDefinitions` (`examples/libraries/genre/senses.json`); неизвестные ключи, повторяющиеся ID,
пустые фракции, неверные позиции/вместимости/масштабы выбрасывают `JsonError("senses.<path>: ...")`.

**Состояние.** `SensesState` (вид 48) хранит наблюдателей (записи + поиск), метки, ожидающие тревоги, маскировки и
укрытия; `ObserverState` 49, `SearchState` 50, `DisguiseState` 51, `HidingState` 52 — тоже записи. Виды 48..55
зарезервированы за этим пакетом. Записи канонические и проверяются при загрузке. `sensesHash` хеширует состояния и
отчёты; `sensesConfigHash` привязывает конфигурацию. `removeSenseAgent` удаляет уничтоженную сущность отовсюду.
`GenreConsumer.cpp` (`librarySensesConsumerExample`) выполняет один тик для пары стражников и нарушителя и сохраняет
`genre.senses`, `genre.senses_hash` и `genre.senses.config`.

Проверено только с g++ 11 (Linux VM): проверки синтаксиса заголовков (`-Wall -Wextra -Werror -pedantic`),
`genre_tests.cpp`, собранный вручную (также под ASan/UBSan), покрывающий конусы/дальности, порядок и бюджет LOS, перекрытие и бюджет
шума, пороги и затухание подозрения, задержку и ретрансляцию тревог, планирование/прекращение/перепланирование поиска, маскировки,

## Жанровые боты (action-bots 0.1.0)

Заголовки в `bots/`: `GenreCommon.h` (сложность, запись восприятия, выбор цели), `MeleeBot.h`, `ShooterBot.h`,
`ObjectivePolicy.h`, `SquadRoles.h`, `GenreBotPersistence.h`, общий `GenreBots.h`, адаптеры настроек
`GenreBotConfig.h`. Цель `AIVERSE::lib_action_bots` (зависит от `combat-actions`, `weapon-policies`,
`configuration`); native OBJECT-модули вызывают `aiverse_native_use_libraries(target action-bots)`. Навык:
`skills/ai/aiverse-action-bots`. Пространство имён `aiverse::lib::bots`; политики не зависят от жанровых меток.

**Контракт.** Каждая политика — чистый шаг принятия решения: один вызов на бота (или отряд) за строго возрастающий тик
(повторные/идущие назад тики и недопустимый ввод возвращают nullopt, не меняя состояние). Она читает снимок,
переданный владельцем, и возвращает тот же ввод, что выдаёт игрок; владелец применяет его через свою обычную авторизацию
(`stepMelee`/`stepDodge`/`stepGuard`/`stepLockOn`, `stepFeed`/`stepRecoil`, навигация, `Command`). Боты никогда
не пишут здоровье, позы, боезапас, перезарядки или состояние матча, а сложность никогда не меняет характеристики. Запускайте их
только на авторитетном хосте; реплеи записывают получившиеся команды. Случайность — только через переданный `Random&`
(`sim.rng()` или RNG, сохраняемый вместе с симуляцией); выборки делаются только для шансов строго внутри (0,1000) и для
ошибки прицела > 0, поэтому поток воспроизводим.

**Восприятие.** `PerceivedTarget{id,team,position,velocity,yaw,visible,guarding,vulnerable,healthMilli,threat}` —
минимальная передача от органов чувств владельца (LOS/FOV/слух). В бой вступают только с видимыми враждебными целями (та же ненулевая
команда и сам бот пропускаются); текущий захват/цель сохраняется, пока видна, иначе выбирается ближайшая по расстоянию, затем по id.
`meleeThreat(attacks,meleeState,tick,reach)` выводит телеграф (id атаки, начало, замах, активная фаза, досягаемость) из
видимой фазы атаки. Пакет органов чувств может адаптировать свой вывод к этой структуре, не меняя политики.

**Сложность.** `BotDifficulty{reactionTicks,decisionTicks,aimError,misreadMilli}`; пресеты `difficultyPreset(0..2)`
(easy 20/8/1/40 turn/600, normal 5/4/1/200/150, hard 2/2/1/2000/0). Реакция задерживает действие по новой воспринятой
цели и чтение телеграфа (отсчитывается от начала взмаха); интервал решений перепланирует движение и
заново выбирает ошибку прицела; ошибочное прочтение игнорирует прочитанный взмах.

**Бот ближнего боя.** `stepMeleeBot(config, attacks, dodge, guard, state, tick, self, seen, rng) -> MeleeInput`.
Полоса дистанции `[minRange,maxRange]`: дальше — сближение, ближе — отход, внутри — стрейф (сторона меняется каждые strafeTicks;
вне `attackRange` стрейф также сближает). Открытия: в покое и в пределах `attackRange` бот запрашивает `opener`
с шансом `openMilli` за тик (избегая зеркальных размен), никогда не бьёт в поднятую защиту при `respectGuard`, если только
цель не `vulnerable` (восстановление/оглушение: наказывается всегда). Комбо: только после подтверждения попадания этим взмахом, запрос
при `age + bufferTicks >= cancelFrom`, чтобы stepMelee начал продолжение на кадре отмены. Защита: взмах в пределах
досягаемости читается один раз после задержки реакции; ответ — Dodge (начало в `activeStart - invulnFrom`, чтобы
кадры неуязвимости покрыли первые активные кадры), Guard (подъём в `activeStart - parryTicks/2`, окно идеального парирования охватывает
первый активный кадр; удержание до конца взмаха), Ignore (ошибочное прочтение) или Retreat (уклонение не готово и удар неблокируемый).
`dodgeMilli` смещает выбор между уклонением и защитой. Lock-on: переключается на захват после реакции. При оглушении/начатом взмахе бот держит позицию.

**Бот-стрелок.** `stepShooterBot(config, feed, state, tick, self, seen, cover, rng) -> ShooterInput`. Взгляд поворачивается
не более чем на `turnPerTick` по каждой оси к решению плюс ошибка прицела с сидом, минус `recoilCompensationMilli` от текущей
отдачи. Hitscan целится в сообщённую позицию; оружие со снарядами (`projectileSpeed > 0`) берёт упреждение через
`genre::solveIntercept` с `aim` (AimConfig) и не стреляет, если решения нет. Стрельба (уровень удержания спуска) только
при выравнивании в пределах `fireTolerance`, успокоившейся отдаче ниже `recoilTolerance` (контроль очереди), в пределах `maxRange`, при наличии патрона
и состоянии питания Ready. Перезарядка, когда магазин не может стрелять, а запас остался, или без цели ниже
`reloadIdleMilli`; никогда во время боя с оставшимися патронами. Гистерезис нагрева: остановка на `heatStopMilli`, продолжение на
`heatResumeMilli` от ёмкости (или пока Overheated). Укрытие: при ранении (`retreatHealthMilli`), перезарядке или охлаждении
при наличии цели выбирается достижимый кандидат с лучшим `protectionMilli - distance*coverDistanceWeight` (при равенстве —
по id), он удерживается до следующего решения, бот движется к нему (по возможности продолжая стрелять). Полоса: сближение дальше
`preferredRange`, отход ближе `minRange`, стрейф между ними. Решения Idle/Engage/Reload/Cool/Cover — диагностические.

**Роли в отряде.** `stepSquad(config, state, tick, objective, stance, members) -> SquadPlan`. Число членов на роль берётся из
смеси стойки (веса `offense`/`defense`, наибольший остаток, при равенстве — по индексу роли). Переназначение при первом вызове,
при изменении состава живых (id, маски возможностей, стойка) или каждые `intervalTicks`; в остальное время сохранённые роли
и направление удерживают цели стабильными. Порядок заполнения Support, Flanker, Defender, Attacker; для каждого места — неназначенный член с
наименьшим ключом (не может взять роль; сохранить: та же прежняя роль < новой или избыточная роль < другой; квадрат расстояния до
якоря роли; id), поэтому выжившие сохраняют роли после гибели, если позволяет численность. Цели: атакующие в построении `attackShape` у
цели, защитники на кольце радиуса `defendRadius`, поддержка в линию на `supportDistance` позади, фланговые в
колонну на `flankDistance` справа от направления. Приказы — это цели для собственного контроллера/навигации каждого члена.

**Хук выбора цели.** `chooseObjective(weights, team, from, objectives, current) -> ObjectiveChoice{id,score,stance}`
по переданным владельцем `ObjectiveInfo{id,kind(Capture/Hold/Escort/Attack/Defend),position,owner,valueMilli,progressMilli,
allies,enemies,active}`. Целочисленная оценка: ценность, минус стоимость расстояния, плюс бонус за нейтральную/вражескую точку и прогресс этой команды
для точек, которые она не удерживает, threatened/ownedIdle для своих точек и целей Defend, сопровождение + прогресс
для своего груза, бонус за оспаривание, «липкость» для текущего выбора; при равенстве — меньший id. Стойка Defense для своих
точек/грузов и целей Defend. Заполняйте `ObjectiveInfo` из владельца матча/целей (состояние захвата, прогресс
груза); политика сама никаких правил не вычисляет.

**Настройки.** Необязательный раздел `genreBots` (конфигурация 0.3.3): тики реакции/решений, `aimErrorMicro` (микро-
обороты), ошибочное прочтение, полоса ближнего боя/дальность атаки/открытие/стрейф/предпочтение уклонения/флаги использования, полоса стрелка, скорость снаряда и
гравитация (milli), допуски поворота/стрельбы/отдачи (микро-обороты), компенсация отдачи, пороги перезарядки/нагрева/отхода,
вес расстояния до укрытия, интервал отряда, веса ролей offense/defense, интервалы построения/радиусы support/flank/defend,
`attackShape` (0 линия, 1 клин, 2 колонна, 3 кольцо) и веса целей. Загрузчик проверяет соотношения
`meleeMin <= meleeMax`, `shooterMin <= shooterPreferred <= shooterMax`, `heatResume <= heatStop`;
`genreBotSettingsErrors` добавляет понятные ошибки между полями (дальность атаки ниже полосы, скорость снаряда вне
0 или 63..1000000, гравитация без скорости, все веса ролей нулевые). Пример: `examples/libraries/genre/bot-settings.json`.

**Состояние.** `MeleeBotState`, `ShooterBotState` и `SquadState` — записи `genre::save/load` (версия 1, виды 56,
57, 58; 59..63 зарезервированы для будущих адаптеров ботов), канонические и проверяемые при загрузке; `genreBotHash` /
`hashGenreBot` сворачивают их в контрольную сумму симуляции. Храните каждое под своим ключом NativeState и привязывайте конфигурации,
наборы атак и определения оружия в конверте сохранения. `GenreConsumer.cpp` (`genreBotConsumerExample`) выполняет один
тик каждой политики и сохраняет `bots.genre.melee`, `bots.genre.shooter`, `bots.genre.squad` и `bots.genre.hash`.

**Проверка.** `tests/libraries/genre_tests.cpp` (`genreBots`) проводит дуэль ботов ближнего боя поверх combat-actions
(хитбоксы, уклонение, защита/парирование, стойкость, lock-on) и дуэль hitscan поверх питания/отдачи/разброса оружия с небольшой симуляцией владельца
внутри теста: повторные запуски дают одинаковые хеши, сохранение/восстановление посреди боя продолжается побитово идентично, а hard
побеждает easy на разных сидах с перестановкой сторон. Модульные проверки покрывают дистанцию, задержку реакции, тайминг уклонения/парирования, комбо после подтверждённого попадания,
упреждение, перезарядку, гистерезис нагрева, контроль очереди, укрытия, стабильность ролей, построения, оценку целей,
сохранение и недопустимые настройки/данные. Проверено только с g++ 11 (Linux VM): проверки синтаксиса заголовков, тесты genre,
собранные вручную (также ASan/UBSan), и автономный запуск функции GenreConsumer. Не проверено: CMake/полная сборка
движка, `aiverse_tests`, изоляция CMake, экспорт native-модуля, headless-матчи с восстановлением, MSVC/clang, выполнение на платформах.

**Восприятие из stealth-senses.** `bots/SensesPerception.h` `perceivedFromSenses(records, observer, facts,
filter)` преобразует `genre::PerceivedTarget` (stealth-senses) в `PerceivedTarget` бота. Цель, которая
`visibleNow` на уровне `engageFrom` (по умолчанию Alert), доступна для боя и получает `TargetFacts` владельца (команда, поза,
скорость, защита, телеграфируемая атака); цель на уровне `rememberFrom` (по умолчанию Searching) или выше сохраняется в своей
позиции `lastKnown` с `visible=false`, поэтому боты приближаются, но никогда не стреляют по ней и не захватывают её. Анонимные возмущения
(target 0) пропускаются; направляйте поиск через `genre::searchGoal`. Результаты сортируются по id цели. Если `facts` возвращает
nullopt, цель отбрасывается. Это делает `stealth-senses` зависимостью пакета `action-bots`.

## Прогрессия в матче (match-progression 0.1.0)

Прогрессия внутри матча для шутеров с героем и отрядом, забегов в жанре survivors/bullet-heaven и рогаликов (эталонный порт: Drone
Fall — опыт на каждого игрока, карточки найма и перков при повышении уровня, пакеты модификаторов на слот колоды или игрока, круги
призыва, возвращающие павших роботов, флаги разблокировки боевой колоды из стартовых данных матча). Заголовки:
`genre/Perks.h` (определения, конвейер характеристик, опыт, предложения), `genre/XpPickups.h`, `genre/Summons.h`,
`genre/BattleDeck.h`, `genre/PerksData.h` (JSON), `genre/PerksConfigured.h` (настройки), `genre/PerksPersistence.h`.

**Конвейер модификаторов.** Перк — это один пакет `ModEffect{stat, op, value, stage, bearer}`; известные характеристики —
`perk_stat::IncomingDamage, OutgoingDamage, MoveSpeed, FireInterval, FireCount, AttackRange, MaxHealth,
SplashRadius, PickupRadius, PickupXp, CritChance, CritDamage, SummonCharges, SummonCooldown, HealthRegen`; игры добавляют
собственные идентификаторы в `stats` (с ограничениями min/max). `evaluateStat(defs, progress, stat, base, slot, bearer, &steps)`
упорядочивает эффекты по стадии (по умолчанию Set 0, Add 1, Multiply 2; явно 0..15), затем пакеты уровня слота идут раньше пакетов
уровня игрока, затем по идентификатору вхождения и индексу эффекта; Multiply задаётся в тысячных и усекается на каждом шаге (пакеты
применяются последовательно, а не как свёрнутое произведение); результат ограничивается; `steps` перечисляет каждый применённый эффект
со значением после него (объяснимые билды). Перки уровня слота действуют только на запросы для этого слота колоды, перки уровня
игрока — на все слоты; носитель (вид владельца: robot/weapon/bullet/hero...) фильтрует эффекты. `scaleAmount` применяет множители
урона с насыщением; `rescaleHealth` сохраняет долю здоровья при росте максимального здоровья и ограничивает его при уменьшении.
Встроенные характеристики RtsModule сохраняют своего владельца: этот конвейер предназначен для нативных/хостовых игр и собственных
характеристик.

**Наложение и выбор.** `maxSelections` (0 = без ограничений) считается на игрока или на слот; `requires` /
`excludes` проверяют тот же слот и область игрока; `units` ограничивает перки слота юнитами колоды; `minLevel` задаёт порог
по выбираемому уровню; `upgrades` создаёт цепочки уровней (выбор заменяет одно вхождение предыдущего уровня;
циклы отклоняются). Перки с `offerable=false` только выдаются (начальные способности). `grantPerk` применяет перк по тем же
правилам без опыта (консоль, скриптовые награды); `clearPerks` удаляет выбранные перки (по желанию сохраняя начальные);
идентификаторы вхождений остаются монотонными.

**Опыт и предложения.** `xpToNext` читает поуровневую таблицу (`xp.toNext`, по текущему уровню); за её концом добавляет
`xpGrowthPerLevel` или упирается в предел; без таблицы используется линейная `xp.curve` (progression-curves `systems::curve`);
`maxLevel` ограничивает оба варианта. `grantXp` начисляет опыт за убийства и цели; с `pickupBonus` характеристика игрока
`PickupXp` масштабирует его, а дробный остаток сохраняется. Уровни накапливаются: `availableLevels`, `levelProgressMilli` (кольцо HUD).
`openOffer` строит предложение следующего уровня из `offers.levels[level]` или `offers.default` (типы вариантов recruit,
slotPerk, playerPerk, anyPerk; явные выборы `perk` резервируются первыми), количество берётся из боевой колоды
(`choiceCount`, иначе `deck.choices` по уровню технологий, иначе число вариантов / `offerChoices`). Кандидаты
перечисляются по возрастанию слота/перка, фильтруются правилами и необязательным хуком `PerkHooks::weight`, затем вытягиваются
собственным потоком PCG32 состояния (`seedPerks`); недоступные позиции пропускаются без замен; пустое
предложение закрывается без траты опыта. `preferNewRecruitAtLevel` сужает выбор найма до ещё не нанятых слотов.
`rerollOffer` тратит один из `offerRerolls`, сохраняет явные выборы и избегает повторов, если есть альтернативы.
Каждое изменение увеличивает `offer.revision`; `selectOffer(revision, index)` заново проверяет, тратит опыт уровня, применяет
перк (события PerkSelected / PerkReplaced со строкой `hook` перка, например именем функции Lua) или сообщает о
Recruit, чтобы владелец создал юнита, и открывает следующее накопленное предложение. `closeOffer` отменяет (станции). `botOfferChoice`
выбирает наименьший `aiPriority` (для найма — `recruitAiPriority`; `aiPriorityLowHealth`, когда у бота мало здоровья).

**Боевая колода.** `readBattleDeck` разбирает стартовые данные матча (player, techLevel, choiceCount, enforceUnlocks,
slots с unit, level, opened, inTeam, perks). `battleDeckError` проверяет нумерацию слотов, известные юниты/перки,
`maxSlots`, `maxSameUnit`, `budget` стоимости и героя в слоте 0. Слот доступен для найма, когда `opened && inTeam`
(если не `enforceUnlocks=false`, например в песочнице/для ИИ); заблокированные слоты сохраняют свой индекс. `addPlayer` один раз выдаёт
начальные перки юнита и слота (перки уровня игрока без дублирования) и отмечает слот героя активным. `maxSquad` и
`maxRecruitsPerSlot` ограничивают найм.

**Подбор опыта.** `stepPickups(config, state, tick, {spawns, collectors})`: сферы приземляются через `pickupLandingTicks`,
исчезают через `pickupLifetimeTicks` (0 = никогда), принадлежат любому или одному игроку; сборщик подбирает сферы в пределах
своего радиуса (владелец передаёт характеристику `PickupRadius`, 0 = `pickupRadiusMilli`) на плоскости земли или в пределах
`pickupMagnetRadiusMilli` на тике магнита. При `pickupAttractSpeedMilli` 0 сбор мгновенный (Drone Fall);
иначе сферы летят к цели с ускорением до `pickupMaxSpeedMilli` и собираются на `pickupGrabRadiusMilli`;
исчезнувший сборщик отпускает свои сферы. `pickupMaxOrbs` ограничивает поле: лишнее появление сливается с ближайшей свободной
сферой того же владельца, иначе вытесняет самую старую. При равенстве выигрывает ближайший сборщик, затем меньший идентификатор игрока.

**Призыв.** `stepSummons(config, points, state, tick, {presences, died, removed})`: игрок с наименьшим идентификатором внутри
радиуса точки, которому там можно призывать (фильтр команды, проверка владельца `canSummon`, точка не использована/не ожидает/не на
перезарядке, отряд меньше `summonMaxAllies`, есть мёртвый приобретённый союзник для восстановления или действие найма, есть заряд при
`summonCharges` > 0), заполняет прогресс по одному за тик (`progressTicks`, иначе `summonProgressTicks`); выход сбрасывает его
(`summonResetOnExit`). По завершении выдаётся `SummonRequest` (восстановление: мёртвый союзник с наименьшим слотом; найм:
слот выбирает владелец), а точка помечается ожидающей; `confirmSummon` регистрирует нового союзника (восстановление заменяет
запись мёртвого) и расходует (`singleUse`) точку или ставит её на перезарядку; `cancelSummon` освобождает её и возвращает
заряд. Союзники хранят владельца, юнита, слот, тик появления и необязательное время жизни; истёкшие союзники перечисляются в `despawn`;
неприобретённые союзники забываются при смерти; `removeSummoner` возвращает живых союзников уходящего игрока.
`summonPointView` выдаёт Ready / Progress (с прогрессом в тысячных) / Pending / Used / Cooldown / SquadFull / Blocked для
визуализации кругов и подсказок. `useSummonCharge` тратит заряд для способностей призыва без точки; заряды восстанавливаются каждые
`summonChargeRechargeTicks`.

**Данные и хуки.** `examples/libraries/genre/perks.json` (юниты, перки, таблица опыта, предложения и точки призыва в духе Drone Fall),
`perks-deck.json` (данные с заблокированным слотом и слотом вне команды), `perks-settings.json`. Имена `hook` перков
и `PerkHooks::weight` — точки стыковки со скриптами: мост Lua сопоставляет события функциям и может запрещать кандидатов или
менять их вес; хуки должны быть детерминированными и не должны читать системное время или состояние отдельного клиента.

**Состояние.** `PerkState` (игроки: колода, опыт, остаток, уровень, предложение, вхождения, нанятые; поток PCG32),
`PickupState`, `SummonState` — записи `genre::save/load` (версия 1, виды 104, 105, 106; 107..111 зарезервированы),
канонические и проверяемые при загрузке; `progressionHash` включает их в контрольные суммы; привяжите `perkDefinitionsHash` и
`progressionConfigHash` в конверте сохранения. `examples/native/libraries/ProgressionConsumer.cpp` прогоняет цепочку убийство ->
сфера -> подбор -> предложение -> выбор и сохраняет `genre.perks`, `genre.pickups`, `genre.summons`.

**Проверка.** `tests/libraries/perks_tests.cpp` (`aiverse_library_progression_tests <repo>`) покрывает ошибки
JSON, ограничения колоды и количество вариантов выбора, порядок конвейера/ограничения/носителей/улучшения/пересчёт здоровья, таблицу/кривую/
рост опыта/остаток подбора, предложения (уровни только с наймом при заблокированных слотах, предпочтение новых наймов, явные выборы,
перебросы, устаревшие ревизии, хуки, исчерпанные пулы, выбор бота), подбор (приземление, владение, магнит, лимит слияния,
истечение, наведение/освобождение), призыв (прогресс/сброс, восстановление/подтверждение, одноразовость, перезарядка, полный отряд, отмена,
истечение, заряды, удаление владельца), сохранение и настройки. `aiverse_progression --root <repo> --verify` проигрывает
скриптовый забег бота на 5400 тиков (убийства, сферы, предложения, найм, смерти, восстановление призывом) и требует одинаковых
контрольных сумм для повтора и для сохранения/восстановления посреди матча. Проверено только с g++ 11 на Linux VM (заголовки с
-Wall -Wextra -Werror -pedantic, тесты и безголовый прогон собраны вручную). Не проверено: MSVC/clang, изоляция CMake,
экспорт нативного модуля, платформенные среды выполнения, производительность при плотностях bullet-heaven, интеграция UI/VFX.

**Интеграция с движком.** RTS-игры используют пакет без нативного кода через блок правил `progression`
([progression.md](progression.md), `modules/rts/RtsProgression*`): убийства реальных юнитов роняют сферы, предложения выбираются через
`kCmdProgression` (UI / бот / Lua), характеристики перков поступают в `RtsModule::stat`, `dealDamage` и хуки выстрела, перки пуль
расширяют программы снарядов, круги призыва создают реальных союзников, а боевая колода берётся из
`players[i].deck` карты (стартовые данные матча). Заголовки библиотеки не изменились.

## Повествовательные сцены (narrative-graphs 0.2.0)

Заголовки `genre/NarrativeScenes.h` (политика), `genre/NarrativeCues.h` (запись `CueRequest`, общая с владельцами кинематографии),
`genre/NarrativeSceneData.h` (JSON), `genre/NarrativeScenePersistence.h` (сохранение/загрузка, хеширование) и `genre/NarrativeConfigured.h`
(настройки). Цель `AIVERSE::lib_narrative_graphs` (теперь объявляет `aiverse_engine`). Старый API `Story` / `readStory` /
`chooseStory` / `StoryState` и вид записи 7 не изменились; `readNarrativeWorld` также загружает старый
`examples/libraries/genre/story.json` (без `facts` упомянутые ключи становятся постоянными целочисленными фактами на всём диапазоне int64
с начальным значением 0; без `scenes` сцена 1 входит в первый узел; старые изменения add ограничиваются, а не отклоняют переполнение).
Пример: `examples/libraries/genre/story-social.json`.

**Определения.** Все идентификаторы — положительные целые числа, весь текст — ключи локализации. `facts`: `int` (min/max/initial), `bool`
или `enum` (имена `values`; JSON использует имена, C++ — индекс), `persistent` (состояние мира, сохраняемое между сценами; остальные сбрасываются
в `initial` при каждом StartScene). `characters`: `nameKey` и шкалы `meters` `affinity`/`trust`/`fear` с min/max/initial
(значения по умолчанию из `narrative.meter*`). Персонаж 0 — игрок/рассказчик (только говорящий и знающий). `flags`: однократные флаги
(устанавливаются один раз, эффекты их никогда не сбрасывают; флаги с `persistent:false` сбрасываются при StartScene). `chapters`: `act`, `titleKey`;
`initialChapter`; в `chapter` сцены происходит вход при StartScene. `scenes`: узел `entry`. `nodes`: `textKey`, `speaker`,
`participants`, `cues`, эффекты `onEnter` и либо `choices`, либо `next` (линейная реплика; `next:0` завершает сцену), плюс
необязательный `autoTicks`. `choices`: `textKey`, `next` (0 завершает сцену), `once`, `conditions`, `effects`, `cues`.
`consequences`: `conditions` (проверяются в момент срабатывания), `effects`, `cues`. `barks`: `trigger`, `speaker`, `textKey`, `priority`,
`cooldown` (по умолчанию `narrative.barkCooldownTicks`), `once`, `conditions`, `cues`.

**Условия** (список означает И): `{"all":[...]}`, `{"any":[...]}`, `{"not":{...}}`; `{"fact":id,"op":..,"value":..}` (int:
eq/ne/lt/le/gt/ge/between с min/max; bool/enum: eq/ne; bool-факт без значения означает true);
`{"meter":"trust","character":id,"op":"ge","value":n}` (op по умолчанию ge: пороги отношений); `{"knows":fact,"character":id}`
(по умолчанию 0 = игрок); `{"flag":id}`; `{"visited":node}` (по умолчанию ge 1); `{"chapter":id}` / `{"act":n}` (с op);
`{"chose":choice,"node":node}`; старый `{"key","minimum","maximum"}`. Глубина <= 16, <= 256 термов в списке.
**Эффекты:** `{"set":fact,"value":v}`, `{"add":fact,"value":d}` (целочисленные факты, с ограничением), `{"meter":m,"character":id,"add"|"set":n}`
(ограничивается границами), `{"reveal":fact,"to":[ids]}`, `{"forget":fact,"from":[ids]}`, `{"flag":id}`, `{"chapter":id}`,
`{"schedule":consequence,"afterTicks":n | "afterScenes":n}` (n >= 1), `{"cancel":consequence}`; старый `{"key","value","add"}`.
**Проверка:** неизвестные ключи, неверные типы, повторяющиеся идентификаторы, неизвестные персонажи/факты/флаги/главы/узлы/последствия, значения
вне области определения, оборванные связи и любая реплика, из которой нельзя дойти до концовки (циклы без выхода, по графу без учёта условий), вызывают
`JsonError("narrative.<path>: reason")`. Ошибки разбора используют индексы массивов JSON (`narrative.nodes[0].choices[1]: unknown key 'nxt'`),
проверки определений используют идентификаторы (`narrative.nodes[id=4].choices[id=2].next: unknown node 99`); `narrativeWorldError` возвращает те же
пути по идентификаторам для миров, построенных в C++.

**Тик.** `beginNarrative(world, config, overrides)` инициализирует каждый факт и шкалу. `stepNarrative(world, config, state,
tick, input)` вызывается один раз за авторитетный тик со строго возрастающими тиками (повторные/обратные тики, неверная конфигурация, повторяющиеся
или нулевые идентификаторы команд/запросов возвращают nullopt и не трогают состояние). Порядок: последствия с задержкой по тикам, наступающие в этот тик
(по тику срабатывания, затем в порядке планирования), команды по возрастанию идентификатора, пропуск прочитанного / автопродвижение, запросы реплик по возрастанию идентификатора.
Команды: `StartScene(scene)` (сбрасывает локальные факты/флаги сцены, входит в главу сцены, запускает последствия с задержкой по сценам,
входит во входную реплику), `Advance` (линейная реплика), `Choose(choice)` (заново проверяет условия и `once`), `SetAuto(0/1)`,
`SetSkip(0/1)`. Каждая команда — транзакция над копией; идентификатор <= последнего принятого или неверная команда выдаёт
`CommandRejected` (extra 1 для повторов) и ничего не меняет. Эффекты выбора применяются до onEnter его следующей реплики.

**Сигналы.** `CueRequest{sequence, cueId, nodeId, choiceId, sceneId, speaker, barkId, consequenceId, tick, delayTicks, source}`
с `source` NodeEnter / Choice / Consequence / Bark. Порядок внутри тика: сигналы последствий, затем для каждой команды сигналы
выбора перед сигналами входа в следующую реплику, затем сигналы реплик-барков. `sequence` постоянен и строго возрастает; владелец кинематографии
(воспроизведение, тайминг, пропуск, QTE) устраняет дубликаты по нему. Этот пакет никогда не воспроизводит сигнал и не ждёт его.

**Реплики-барки.** Для каждого `BarkRequest{id, trigger, speakers}` кандидатами являются барки этого триггера, чей говорящий указан в списке
(пусто = любой) и ещё не использован более ранним запросом в этом тике, не исчерпанные по `once`, прошедшие собственную перезарядку и
перезарядку говорящего (`speakerCooldownTicks`), с выполненными условиями. Побеждает наивысший приоритет, затем ни разу не звучавший, затем
давнее всех звучавший, затем меньший идентификатор. Результат — `BarkLine{request, bark, speaker, textKey}` + `BarkSpoken` либо `BarkNone`.

**Визуальная новелла.** Каждая показанная реплика добавляется в `state.backlog` (`node, speaker, choice taken, tick, scene`, хранятся
последние `backlogLimit`). `state.read` считает прочтения между сценами; `lineWasRead` / `canSkipLine` / `lineRead` дают определение
прочитанного для пропуска. Режим пропуска продвигает до `skipLinesPerTick` прочитанных линейных реплик за тик и останавливается (и выключается) на непрочитанной
реплике или выборе (`SkipStopped`, extra 1 для выбора). Автоматический режим продвигает линейную реплику через `autoTicks` (или
`autoAdvanceTicks`) после её показа; `autoAdvanceTick` сообщает, когда это произойдёт.

**Настройки.** Необязательный раздел `narrative` (configuration 0.3.4): `autoAdvanceTicks`, `skipLinesPerTick`, `backlogLimit`,
`barkCooldownTicks`, `speakerCooldownTicks`, `maxPendingConsequences` (сверх него `ConsequenceDropped`), `maxBarkRequests`,
`meterMinimum <= meterInitial <= meterMaximum`. Пример: `examples/libraries/genre/narrative-settings.json`.

**Состояние.** `NarrativeState` — запись вида 64 (`BarkMemory` 65); виды 64..71 зарезервированы за этим пакетом. Тело записи
начинается с формата 1 для будущих миграций. `genre::load` проверяет структуру и канонические байты; затем вызовите
`narrativeStateError(world, config, state)`, чтобы привязать его к определениям. `narrativeHash` хеширует состояния и отчёты;
привяжите `narrativeWorldHash` и `narrativeConfigHash` в конверте сохранения. `GenreConsumer.cpp`
(`narrativeSceneConsumerExample`) выполняет один тик крошечной социальной сцены и сохраняет `genre.narrative`, `genre.narrative.legacy`,
`genre.narrative.world`, `genre.narrative.config` и `genre.narrative.cue`.

Проверено только с g++ 11 (Linux VM): синтаксические проверки заголовков (`-Wall -Wextra -Werror -pedantic`), собранный
вручную `genre_tests.cpp` (тесты повествовательных сцен также отдельно под ASan/UBSan), покрывающий загрузку старого формата, пороги отношений и ограничение, выборы с проверкой знания и однократные выборы, последствия с задержкой
по сценам и тикам, сброс локального состояния сцены против постоянного состояния мира, главы/акты, порядок и последовательности сигналов, приоритет
барков/перезарядки/once/разрешение равенства, ограничения журнала, пропуск прочитанного и автопродвижение, сохранение/восстановление посреди сцены с идентичным
продолжением, отклонённые тики/команды и пути неверных данных, а также цепочку GenreConsumer в отдельном драйвере.
Не запускалось: CMake/изоляция, `aiverse_tests`, экспорт нативного модуля, безголовые матчи с восстановлением, clang/MSVC.

## Физические взаимодействия (physical-interactions 0.1.0)

Заголовки в `genre/`: `PhysicalInteractions.h` (общий заголовок + `InteractionDefinitions`), `Carry.h`, `Push.h`, `Ropes.h`,
`Doors.h`, `Platforms.h`, `Breakables.h`, общий `PhysicalCommon.h` (события, `WorldCollision`, перемещение с заметанием) и
`InteractionConfig.h`, адаптер настроек `InteractionConfigured.h`, JSON `InteractionData.h`, записи
`InteractionPersistence.h`. Цель `AIVERSE::lib_physical_interactions` (зависит от `configuration`, `aiverse_engine`,
`aiverse_world`); нативные OBJECT-модули вызывают `aiverse_native_use_libraries(target physical-interactions)`. Навык:
`skills/gameplay/aiverse-physical-interactions`. Отделён от `object-interactions` (меню действий и встроенные команды
взаимодействия движка): предпросмотр там никогда не разрешает эти изменения.

**Детерминизм и сетевая модель.** Эти политики — авторитетное игровое состояние взаимодействий. Они используют
математику Fixed, целочисленные тики и порядок по возрастанию идентификаторов, вызывают только чистые запросы коллизий, предоставленные владельцем, и хранят каждое
влияющее на исход значение в версионированных записях. Запускайте их на авторитетной стороне (сервер или участники lockstep) по проверенным
Command, каждую по одному разу за тик; клиенты предсказывают, выполняя те же шаги, и откатываются, восстанавливая записи и
повторно проигрывая ввод. Необязательный модуль Box3D (`docs/physics.md`) не детерминирован между сборками/процессорами и здесь
**не авторитетен**: он может симулировать обломки по `DebrisRequest` (с зерном) или косметическое движение, но из него ничего не
считывается обратно. Если игра вместо этого делает Box3D авторитетным, ей нужна собственная интеграция команд/сохранений/сети.

**Коллизии.** Подходит любой объект с `sweep(start,delta,half,ignore) -> InteractionHit` и
`overlapping(box,ignore) -> ascending ids`; `WorldCollision(spatialWorld)` адаптирует `engine/world::SpatialWorld`
(отсортированные кандидаты, при равенстве — меньший id). Перемещения используют `physSweep`: коробка, уменьшенная на `skin`, заметается по перемещению, удлинённому
на `skin`, и останавливается так, чтобы настоящая коробка касалась контакта. Соприкасающиеся тела могут скользить или расходиться; давление в
поверхность сообщает о столкновении без ползучести; старт внутри блокирует. Проверки пересечения строгие (касающиеся грани не блокируют).

**Общий контракт.** Каждый шаг сначала проверяет конфигурацию, определения, состояние и ввод; неверные данные, dt вне (0,1]
или повторный/обратный тик возвращают nullopt без изменения состояния. Ввод может приходить в любом порядке; он
обрабатывается по возрастанию идентификаторов. Результат — обновлённое состояние плюс `InteractionEvent{kind, object, actor, value, collider,
position}` (value = код причины, импульс/натяжение в тысячных долях единиц, id стадии, ...) и списки статусов по механикам. Никакого
рендеринга, звука или анимации. Единицы: метры, килограммы, секунды, ньютоны; рыскание/тангаж в оборотах (рыскание 0 смотрит в +Z).

**Перенос/бросок.** `stepCarry` сначала обрабатывает полёты (по возрастанию объекта), затем носильщиков (по возрастанию id): бросить на месте, метнуть,
когда уровень `charge` падает, подобрать, обновить удержание. Подбор отклоняется (`PickupRefused`: TooHeavy выше `maxMass`,
OutOfReach дальше `reach` от точки удержания = ступни + `holdHeight`, Busy, когда объект удерживается/летит). Удерживаемый объект следует к
`carryHoldPoint` (точка + вперёд*`holdDistance`) не быстрее `followSpeed` в секунду перемещением с заметанием, игнорируя себя
и носильщика; заблокированный и находящийся дальше `breakDistance` от точки удержания -> `DroppedBlocked` (с заданным коллайдером).
`CarrierStatus::speedMilli = max(minSpeedMilli, 1000 - mass*speedPenaltyMilli)` — множитель скорости носильщика для
владельца перемещения. Броски: импульс растёт линейно от `throwMinImpulse` до `throwMaxImpulse` за `chargeTicks`;
скорость = вперёд*импульс/масса + скорость носильщика. `stepFlight` (v.y -= g*dt, перемещение с заметанием на v*dt) выполняется раз за тик
начиная с тика после броска; `previewThrow` выполняет идентичный шаг, поэтому `points[k]` равен позиции полёта через k+1
тиков после броска, а приземление (`Landed`, коллайдер/нормаль) совпадает точно. `maxFlightTicks` завершается
`FlightExpired`. Свободные объекты принадлежат владельцу (он сообщает их позы для подбора); `releaseCarried` забывает предмет.

**Толкание/тяга.** `addPushable` регистрирует тело. Для каждого объекта силы всех команд складываются (только горизонтальная составляющая);
движение требует |F| > friction*mass*g (`PushResisted` TooWeak по переднему фронту; тяга нетягаемого объекта ->
NotPullable). Свободный режим: a = (|F| - сопротивление)/m вдоль F, с ограничением `pushMaxSpeed`; при недостаточной силе кинетическое
трение (friction*g) замедляет его; перемещение с заметанием скользит вдоль стен (`PushBlocked` по переднему фронту, `PushStarted` /
`PushStopped`). Режим сетки: одна клетка вдоль доминирующей оси после проверки свободного пространства с заметанием, линейно за `gridMoveTicks`,
`PushArrived` ровно на клетке; команды во время перемещения игнорируются. Толкаемые объекты никогда не падают: владелец держит их на
земле. Тяга = актёр задаёт направление к себе; его собственный коллайдер не игнорируется, поэтому сначала отступите им назад.

**Верёвки.** `makeRope(def, a, b)` создаёт `segments+1` частиц. Концы: Free, Point (точка мира), Body (следует позе
владельца в `RopeInput::bodies`, при отсутствии сохраняет последнюю позу) и Load (подвешенная масса, симулируемая верёвкой).
Каждый тик: команды присоединения/отсоединения (`RopeAttached`/`RopeDetached`), предсказание с гравитацией и демпфированием, затем
`ropeIterations` проходов Гаусса–Зейделя XPBD по ограничениям расстояния (только растяжение, `compliance` в м/Н, 0 = жёстко).
Натяжение = максимальная сила сегмента (lambda/dt^2); при фиксированном числе итераций более тяжёлый груз растягивает верёвку чуть
сильнее, а больше итераций сходятся ближе к длине покоя. Выше `breakForce` (0 = неразрываемая) верёвка рвётся
(`RopeBroken`, value = натяжение в миллиньютонах) и перестаёт симулироваться. `RopeStatus::pullA/pullB` — сила на конце Body
для его собственного контроллера. dt должен быть >= 1/1000 с. Нет коллизий верёвки с миром или с собой.

**Двери.** `addDoor` из `DoorDef` (коробка закрытой створки, Hinged: вертикальная ось + `openAngle` в оборотах, Sliding:
смещение `slide`). Открытие занимает `openTicks`, закрытие `closeTicks` (точный целочисленный прогресс), через `autoCloseTicks` после
`DoorOpened` начинается закрытие. Каждый тик следующая поза (консервативный AABB для распашных дверей) проверяется через `overlapping`,
игнорируя коллайдер двери: заблокированная закрывающаяся дверь разворачивается (`DoorReversed`, autoReverse) или стоит (`DoorBlocked`),
заблокированная открывающаяся дверь стоит. Запертые двери отказывают в открытии (`DoorRefused` Locked), если только `keys` актёра не содержат
`key` (тогда `DoorUnlocked` + открытие); Lock/Unlock требуют ключа (NoKey); односторонние двери открываются только со стороны `oneWay`
по более тонкой оси створки (WrongSide); команды `scripted` обходят ключи и стороны. Обновляйте коллайдер двери по
`DoorStatus::bounds` после каждого тика; передавайте в запрос двери тела (персонажей, предметы), а не её статическую раму.

**Движущиеся платформы.** `addPlatform`; постоянная `speed` вдоль `waypoints` (Loop, PingPong, Once), неподвижна ровно
`waits[i]` тиков после прибытия в точку маршрута i (`PlatformArrived`/`PlatformDeparted`, value = индекс точки маршрута); остаток
пути в тике прибытия отбрасывается; `PlatformCommand` запускает/останавливает. Только перенос. Владелец коллизий
сообщает `RiderContact{rider, platform}` из своей проверки земли (тот же контакт, что устанавливает `LocomotionEnvironment::
grounded`); отчёт перечисляет `RiderCarry{rider, platform, delta, velocity}` по возрастанию id пассажира
(`RiderBoarded`/`RiderLeft`). Порядок владельца за тик: контакты -> `stepPlatforms` -> добавить `delta` пассажиру (с заметанием) ->
`stepLocomotion` с `env.grounded` -> переместить на скорость передвижения -> обновить коллайдер платформы.
Скорость передвижения остаётся относительной платформы; добавьте `velocity` один раз при сходе, чтобы унаследовать импульс.
Платформы никогда не останавливаются из-за препятствий; раздавливание — правило владельца.

**Разрушаемые объекты.** `addBreakable`; `DamageInput{id, object, type, amount, source, position}` по возрастанию (object, id).
Масштабированный урон = amount * scaleMilli/1000 для типа (иначе `defaultScaleMilli`; 0 = иммунитет), игнорируется ниже
`threshold` типа, повторные/более старые id и разрушенные объекты (`DamageIgnored` с причиной). Стадии (по возрастанию id,
убыванию здоровья) один раз вызывают `StageReached`, когда здоровье опускается до них; здоровье 0 -> `Broken`. Каждая стадия / разрушение
выдаёт `DebrisRequest{object, stage (0 = break), kind, count, position, seed}`; зёрна — хеш (object, stage, damage id).

**Настройки.** Необязательный раздел `interaction` (configuration 0.3.3): гравитация, skin, carry* (масса, досягаемость, расстояние/высота
удержания, скорость следования, расстояние срыва, штраф/минимум скорости), импульсы/заряд броска, тики полёта, скорость
толкания / тики сетки, итерации/демпфирование верёвки (в тысячных долях). Загрузчик требует throwMin <= throwMax;
`interactionSettingsErrors` добавляет `interactionConfigError`. Пример `examples/libraries/genre/interaction-settings.json`.
Определения: `readInteractionDefinitions` (`examples/libraries/genre/interactables.json`), ошибки вроде
`interaction.platforms[0].waitTicks: expected one value or one per waypoint`.

**Состояние.** Записи (версия 1): `CarryState` 80, `PushState` 81, `RopeState` 82, `DoorState` 83, `PlatformState` 84,
`BreakableState` 85; виды 80..87 зарезервированы за этим пакетом (повествование занимает 64..71, кинематография 72..79). Загрузка проверяет
структуру; каждый шаг заново сверяет записи с определениями. `interactionHash` включает канонические байты в
контрольную сумму, `interactionConfigHash` / `interactionDefinitionsHash` привязывают неизменяемые данные в конверте сохранения.
`GenreConsumer.cpp` (`physicalInteractionConsumerExample`) выполняет один тик шагов переноса, двери, платформы и разрушаемого объекта
и сохраняет `genre.interaction.{carry,doors,platforms,breakables}` вместе с хешами.

**Проверка.** `tests/libraries/genre_tests.cpp` (`physicalInteractions`): точки предпросмотра броска/приземление совпадают с
симулированным полётом тик за тиком, восстановление посреди полёта продолжается побитово идентично, отказы по массе/досягаемости и штраф скорости
переноса, сброс при заносе в стену; совместное толкание, отказ из-за трения, заблокированное свободное толкание без ползучести, перемещение
по сетке/прибытие/блокировка и восстановление; натяжение подвешенной верёвки в пределах 10% от веса, меньше растяжения при большем числе итераций,
разрыв, отсоединение/присоединение к телу с выводом тяги, восстановление; правила ключа/замка/скриптов для двери, автоматический разворот на теле,
остановка без автоматического разворота, односторонняя сторона, границы распашной двери, восстановление; смещения пассажиров платформы, пропущенные через `stepLocomotion`
в течение 90 тиков (точное смещение в покое, относительная ходьба), порядок пассажиров по возрастанию, ожидания, восстановление; пороги разрушаемых объектов,
иммунитет, повторы, стадии, зёрна обломков; неверные JSON/настройки/ввод. Проверено только с g++ 11 (Linux VM): синтаксические
проверки заголовков, жанровые тесты, собранные вручную, физические тесты также под ASan/UBSan и полная цепочка GenreConsumer
в отдельном драйвере. Не проверено: CMake/изоляция, `aiverse_tests`, экспорт нативного модуля, безголовые матчи
с восстановлением, MSVC/clang, платформенные среды выполнения, любое отображение обломков Box3D.

## Кинематографичный геймплей (cinematic-gameplay 0.1.0)

Заголовки `genre/CinematicTime.h` (домены масштаба времени), `genre/CinematicQte.h` (оценка QTE),
`genre/CinematicScene.h` (определения, состояние, проверка), `genre/CinematicRunner.h` (`stepScene`), общий заголовок
`genre/Cinematic.h`, `genre/CinematicData.h` (JSON сцен), `genre/CinematicConfigured.h` (адаптеры настроек) и
`genre/CinematicPersistence.h` (сохранение/загрузка, хеширование). Цель `AIVERSE::lib_cinematic_gameplay` (зависит от
`aiverse_engine`); нативные OBJECT-модули вызывают `aiverse_native_use_libraries(target cinematic-gameplay)`. Навык:
`skills/gameplay/aiverse-cinematic-gameplay`. Сочетается с системой анимации (клипы/маркеры указываются по ID, а их состояние
сообщается обратно; `docs/animation-graphs.md` остаётся владельцем воспроизведения) и с `narrative-graphs` (триггеры по сигналам).

**Модель детерминизма.** Авторитетны, сохраняются и хешируются: запросы масштаба времени и накопители по доменам
(`TimeState`), позиция на таймлайне, учёт выдачи сигналов, исходы ожиданий и QTE, статус расстановки, блокировки ввода,
поставленные в очередь триггеры и параметры QTE (`SceneState`). Принадлежат хосту/отображению и никогда не авторитетны: прогресс воспроизведения
звука и анимации, камера, навигация, выполнение телепортации. Факты хоста поступают только как `SceneInput` с отметкой
авторитетного тика (`LineReport`, `MarkerReport`, `ParticipantPose`/`arrived`, `QteInput`) и проверяются по тику выдачи
сигнала и текущему тику, поэтому повторы и участники видят одинаковый ввод и исходы. У каждой точки синхронизации
и перемещения расстановки есть тайм-аут в авторитетных тиках (никогда не в шагах домена), поэтому медленное устройство, отсутствующий отчёт или
замороженный домен не могут остановить симуляцию. Только целочисленная математика (Fixed для позиций меток), строго возрастающие
тики; неверный ввод или повторные/обратные тики возвращают nullopt без изменения состояния; устаревшие порядковые номера команд
игнорируются (`CommandIgnored`). Отображение читает `SceneEvent`; оно никогда не пишет ни в одно из состояний.

**Домены масштаба времени.** `TimeConfig` перечисляет домены (по умолчанию world 1, player 2 с родителем world, ui 3,
cinematic 4; допускаются собственные id, id родителя < id потомка). Масштабы — `TimeRatio{num,den}` с 0 <= num/den <= 16
и den, делящим 720720 (все знаменатели 1..16 точны); значения хранятся в единицах 1/720720 шага, и каждый домен
держит целочисленный накопитель, поэтому за N тиков домен продвигается ровно на floor(N*num/den) целых шагов (проверено на
300000 тиков). Запросы (`TimeRequest{tag, domain, scale, priority, duration, blend}`) применяются по доменам в
порядке (priority, id): `Override` заменяет текущее значение, `Multiply` масштабирует его (с округлением вниз в единицах шага, если
результат неточен); дочерний домен умножается на родительский. `duration` — авторитетные тики от стартового тика
(0 = до отмены), поэтому хит-стоп (масштаб 0) всегда заканчивается. Порядок `stepTime` в тике: отмена по id, отмена по тегам,
истечение, добавление (id назначаются в порядке ввода), вычисление, накопление; пропуски тиков интегрируются точно с истечениями
внутри пропуска. `DomainTick{steps, units, local}` для каждого домена; не более 256 активных запросов (сверх этого `Rejected`).
Пресеты: `hitStop(domain, ticks)`, `slowMotion(domain, ratio, ticks)`, библиотечные `timePresets`, используемые сигналами `timeScale`
(помечаются id сцены и отменяются при пропуске/перемотке/возобновлении/завершении).

**Таймлайны сцен.** Сцена продвигается шагами своего домена времени (`domain` 0 = один шаг за тик). Сигналы
(`dialogue`, `animation`, `camera`, `sound`, `event`, `timeScale`, `move`, `inputLock`, `inputRelease`) сортируются
по (at, track, id) и выдаются в этом порядке, когда позиция достигает `at`. Существенные сигналы (по умолчанию события,
всегда move/input) срабатывают ровно один раз за прогон сцены, в том числе при пропуске (`flags` 1); сигналы отображения срабатывают один раз
за проход и при пропуске записываются как пропущенные. Точки синхронизации и QTE («остановки») удерживают таймлайн на своей
позиции перед сигналами этой позиции; время удержания не накапливается. Команды (`SceneCommand{seq, kind, value,
bindings}`): `TriggerScene`, `TriggerCue`, `Pause`/`Unpause` (все сроки сдвигаются на тики паузы), `Skip` (до
следующей точки синхронизации или до конца), `SkipScene`, `Seek` (вперёд = семантика пропуска и требует `skippable`; назад
заново взводит остановки и сигналы отображения), `Abort`, `ResumeCheckpoint`. Пропуск телепортирует перемещаемых и разрешает QTE
по пути как `Skipped` без ветвления. Порядок в тике: параметры, команды по seq, отчёты, затем, если нет паузы:
запуск сцены, вызванной в более раннем тике, расстановка, оценка QTE, ожидания синхронизации, продвижение таймлайна. Вызывайте каждый тик:
при пропусках тиков снятое удержание поглощает шаги всего пропуска.

**Ожидания синхронизации.** `SyncDef{id, at, timeout, checkpoint, waits}`; ожидания: `lineFinished{cue}` (сообщено о завершении
сигнала dialogue/animation), `marker{cue, marker}` (сообщено о маркере анимации или клип завершился), `inPosition{participants}`
(пусто = все; InPosition или Teleported). Ожидаемые сигналы должны начаться до точки синхронизации. Ожидание пропущенного сигнала
считается выполненным. Снятие происходит, когда все выполнены, или через `timeout` тиков (`SyncReleased` value 1 = по тайм-ауту; воспроизведение продолжается).

**QTE.** Виды `QteDef`: `press` (окно [open, close] тиков после подсказки, необязательное подокно `perfect`, раннее
нажатие проваливает), `mash` (`count` нажатий до закрытия), `hold` (нажать до закрытия, удерживать `hold` тиков, раннее
отпускание проваливает), `sequence` (упорядоченные `steps`, каждое окно от предыдущего успеха). Неверные кнопки игнорируются,
если нет `strict`. Оценивается по `QteInput.tick` в (тик подсказки, текущий тик]. `QteOptions{windowScaleMilli
(сложность), accessibleWindowMilli (расширенные окна, 1000 = выкл.), mashScaleMilli, holdScaleMilli, autoSucceed}`
масштабируют окна симметрично относительно их центра (>= 1 тика, открытие при >= 1) и применяются в момент подсказки;
`autoSucceed` разрешает `AutoSuccess` в момент подсказки. Исходы (Success, Perfect, Fail, AutoSuccess, Skipped)
хранятся в `SceneState::results` и выдаются как `QteResolved`. Ветвления: `onSuccess` должен переходить вперёд к точке
синхронизации (семантика пропуска), `onFail` может переходить назад для повтора; `failAborts` прерывает сцену.

**Расстановка.** `MarkDef{id, position (миллиметры в JSON), toleranceMilli}`, `ParticipantDef{id, mark, lockInput,
timeout, fallback teleport|proceed|abort}`. При старте заблокированные участники получают `InputLocked`, участники с
меткой получают `MoveToMark` и остаются `Moving` до позы в пределах допуска или отчёта `arrived` (`InPosition`) либо
до своего тайм-аута: `TeleportRequested` (хост телепортирует; считается занявшим позицию), `StagingLate` или прерывание. Сигналы `move`
перестраивают расстановку посреди сцены. Воспроизведение начинается, когда никто не движется. `inputLocked(state, participant)` /
`lockedEntities(state)` пропускают или блокируют команды игрока; каждый путь завершения (окончание, пропуск, прерывание) снимает все блокировки. Привязки
триггера сопоставляют участников с сущностями (события несут и то и другое).

**Контрольные точки и повествование.** `checkpointBefore` выдаёт `SnapshotRequested` value 0 в тике триггера, пока
сцена в состоянии `Pending` (она начинается в следующем тике), точки синхронизации с контрольной точкой выдают value 1 при достижении, `checkpointAfter` —
value 2 по завершении. После загрузки любого сохранения отправьте `ResumeCheckpoint`: таймлайн перематывается к последней достигнутой точке
синхронизации (или к началу), заново взводит её ожидание и повторно проигрывает оттуда сигналы отображения; существенные сигналы никогда не повторяются.
Повествовательный `CueRequest{cueId,...}` отображается в `cueTrigger(seq, cueId, bindings)`; id сигнала `trigger` сцены
индексируется в `SceneLibrary::triggers` (`indexTriggers`, `sceneForCue`), неизвестные сигналы дают `TriggerIgnored`, триггеры
во время сцены ставятся в очередь (8). Этот пакет не подключает повествовательный заголовок; тип события связывает MAIN.

**Данные и настройки.** `readSceneLibrary(json)` (`examples/libraries/genre/scene.json`): неизвестные ключи, неверные типы,
целые числа вне диапазона, неотсортированные/повторяющиеся ID, неизвестные метки/участники/пресеты/домены/сигналы, ожидания более поздних сигналов,
`onSuccess` назад, тайм-ауты 0 и повторяющиеся триггеры вызывают `JsonError("cinematic.<path>: ...")` с путями по индексам
для синтаксиса (`cinematic.scenes[0].cues[2].kind: unknown value 'x' ...`) и путями по id для ссылок
(`cinematic.scene 10.sync 1.wait[0].cue: unknown dialogue/animation cue 9`). Необязательный раздел настроек `cinematic`
(configuration 0.3.4): `hitStopTicks` (>= 1), `hitStopPriority`, `slowMotionNumerator`/`Denominator` (<= 1),
`slowMotionTicks`, `slowMotionPriority`, `qteWindowScaleMilli`, `qteAccessibleWindowMilli`, `qteMashScaleMilli`,
`qteHoldScaleMilli`, `qteAutoSucceed`; адаптеры `qteOptions`, `hitStopRequest`, `slowMotionRequest`,
`cinematicSettingsErrors`. Пример `examples/libraries/genre/cinematic-settings.json`.

**Состояние.** `TimeState` вид 72, `SceneState` 73, `QteProgress` 74, `ParticipantState` 75; виды 72..79 зарезервированы
за этим пакетом (повествование использует 64..71). Записи канонические и проверяются при загрузке; `stepScene` отклоняет состояние,
у которого id/версия сцены, курсор или индексы остановок не совпадают с библиотекой. `cinematicHash` хеширует состояния, отчёты и
определения; привяжите `sceneLibraryHash(lib)` в конверте сохранения. `GenreConsumer.cpp`
(`libraryCinematicConsumerExample`) запускает сцену по повествовательному сигналу 42 через два тика доменов времени и сохраняет
`genre.cinematic.time`, `genre.cinematic.scene`, `genre.cinematic_hash` и `genre.cinematic.library`.

Проверено только с g++ 11 (Linux VM): синтаксические проверки заголовков (`-Wall -Wextra -Werror -pedantic`), собранный
вручную `genre_tests.cpp`, покрывающий точность масштаба времени на 300000 тиков, пропуски, вложенность, наложенные/отменённые/истекающие запросы,
порядок сигналов при пропуске/перемотке, тайм-ауты синхронизации/паузу/замороженные домены, оценку QTE каждого вида со сложностью и
доступностью, ветвления внутри сцены, запасные варианты расстановки и блокировки ввода, возобновление с контрольной точки, очередь повествовательных триггеров,
сохранение/восстановление посреди сцены на примере библиотеки и неверные данные; кинематографические тесты также под ASan/UBSan, а
функция GenreConsumer — в отдельном драйвере. Не запускалось: CMake/изоляция, `aiverse_tests`, экспорт нативного модуля,
безголовые матчи с восстановлением, clang/MSVC.

**Повествовательные сигналы.** `genre/NarrativeCinematicBridge.h` соединяет narrative-graphs со сценами. Каждый тик владелец передаёт
`CueRequest` из отчёта повествования в `queueNarrativeCues(queue, cues)` и один раз перед `stepScene` вызывает `releaseNarrativeCues(queue, tick,
nextCommandSeq, bindings)`. Сигналы наступают в `tick + delayTicks` и выпускаются как
команды `TriggerCue`, упорядоченные по (тик наступления, повествовательная последовательность), с использованием монотонного счётчика `SceneCommand` владельца.
Последовательности не больше последней принятой игнорируются, поэтому повторная подача отчёта после восстановления никогда не запустит сцену
дважды. Неизвестные ID сигналов доходят до исполнителя и порождают `TriggerIgnored`. `NarrativeCueQueue` сохраняется как запись вида 76
(в пределах диапазона этого пакета 72..79).

## Решатели головоломок (puzzle-solvers 0.1.0)

`genre/PuzzleSolvers.h` (заголовки `Puzzle{Common,Match3,Flood,Sliding,Constraints,Sokoban,Data,Persistence}.h`) и
политика бота `bots/PuzzleBot.h`; цель `AIVERSE::lib_puzzle_solvers` (зависит от `grid-puzzles`, чей
`strategy/Puzzles.h` 0.2.0 добавляет `pushDeadCells`, `pushDeadlocked`, `solvePushAStar` и `pushHint`). Исполняемый
пример: `examples/libraries/genre/puzzles` (CTest `library_genre_puzzles_example`).

**Модель детерминизма.** Только целые числа; клетки идут построчно; соседи обходятся влево, вправо, вверх, вниз; ходы-кандидаты,
цвета, фигуры и значения перебираются по возрастанию; при равенстве всегда выигрывает более ранний кандидат. Случайность —
только через `aiverse::Random&` вызывающей стороны (генерация/дозаполнение/перемешивание match-3, `puzzleTilesShuffle`, ошибки
бота). Каждая головоломка с состоянием принимает одну структуру команды с номером `move`, строго большим
`state.lastMove`; `*Apply` заново проверяет команду по уровню и при отклонении не трогает состояние,
поэтому ввод игрока и вывод бота идут одним авторитетным путём.

**Бюджеты.** Каждый решатель и подсказка принимают `PuzzleBudget{nodes}` (не более 2,000,000) и возвращают `PuzzleSearch`:
`Solved`, `Unsolvable` (исчерпывающий перебор: доказательство), `Unknown` (бюджет исчерпан: никаких утверждений) или `Invalid`.
Поиск итеративный там, где глубина не ограничена; ничто не зацикливается без расхода бюджета.

Распространение идёт до неподвижной точки в порядке ограничений (один узел бюджета на ревизию); поиск выбирает наименьший домен, наименьшую клетку, значения по возрастанию. Подсказки исправляют первую неверную клетку, иначе заполняют самую ограниченную пустую клетку. |

**Данные.** `genre/PuzzleData.h`: `readMatch3Level`, `readSokobanLevel`, `readSudoku`, `readNonogram`, `readCsp`,
`readFloodLevel`, `readPipeLevel`, `readTilesLevel`, `readBlocksLevel`, `readPackLevel` (форматы описаны в заголовке;
пример `examples/libraries/genre/puzzles/levels.json`). Ошибки — `JsonError` с путём, например
`puzzle.match3.rows[2][4]: expected '#', '.' or a color digit` или `puzzle.csp.constraints[0].cells[1]: must be in 0..8`.
Генерируемого раздела настроек нет: всё настраиваемое — данные уровня.

**Бот.** `bots::puzzleBotMatch3 / Flood / Pipes / Tiles / Blocks / Pack / Csp / Sokoban(level, state, skill, rng)`
возвращают следующую команду игрока (`lastMove + 1`). `PuzzleBotSkill{budget, mistakeMilli, match3}`; пресеты 0..2.
С вероятностью `mistakeMilli` бот вместо этого делает случайный допустимый ход (CSP: подсказанная клетка с угаданным значением,
исправляемым позже; Сокобан: случайный шаг, отменяемый, как только доказан тупик или решение не найдено). Идеальный бот
никогда не обращается к ГСЧ. Бот не имеет состояния.

**Состояние.** Виды записей 112..119 (все заняты): `Match3State` 112, `PuzzleFloodState` 113, `PuzzlePipeState` 114,
`PuzzleTilesState` 115, `PuzzleBlocksState` 116, `PuzzlePackState` 117, `PuzzleCspState` 118,

не зависящие от формы; после загрузки перепроверьте по уровню (`match3Compatible`, `puzzleFloodCompatible`,

## Карты и пошаговая стратегия (card-games 0.1.0, tactics-grid 0.1.0, cards-turns-bots 0.1.0)

Заголовки `genre/CardGame.h` (определения, варианты правил, состояние, представления, допустимые действия), `genre/CardGameRunner.h`
(`cardGameSetup`, `stepCardGame`), `genre/CardGameData.h`, `genre/CardGameConfigured.h`, `genre/CardGamePersistence.h`;
`genre/TacticsGrid.h` (сетки, передвижение, укрытия, линия огня), `genre/TacticsTurns.h` (ходы с ОД/инициативой, представления),
`genre/TacticsWeGo.h`, `genre/TacticsData.h`, `genre/TacticsConfigured.h`, `genre/TacticsPersistence.h`; боты
`bots/CardBot.h`, `bots/TacticsBot.h`. Цели `AIVERSE::lib_card_games` (зависит от `lib_card_runtime`),
`AIVERSE::lib_tactics_grid`, `AIVERSE::lib_cards_turns_bots` (зависит от обеих); навыки `aiverse-card-games`,
`aiverse-tactics-grid`, `aiverse-cards-turns-bots`.

**Связь со стратегическими средами выполнения.** `card-runtime` (`strategy/Cards.h`) и `turn-scheduler` (`strategy/Turns.h`)
не изменились, включая их записи `strategy/Persistence.h` (виды 3 и 4). card-games переиспользует словарь зон card-runtime
(Deck, Hand, Board, Discard, Exile; `cardRuntimeZone`) и добавляет Stack, эффекты, заданные данными, цели,
варианты правил и скрытую информацию, которые ограниченная дуэль намеренно опускает. turn-scheduler сохраняет фиксированный
порядок инициативы с вложенными реакциями, применяемыми хостом; tactics-grid владеет динамическим порядком на каждый раунд (модификаторы скорости,
задержка) и сам разрешает передвижение, укрытия и выстрелы, поэтому расширение планировщика на месте изменило бы его
сохраняемый формат и контракт.

**Модель детерминизма.** Всё состояние целочисленное; случайность — только из переданного `aiverse::Random` (перемешивание карт при
подготовке и муллигане, одно вытягивание на выстрел). Каждое изменение проходит через одну функцию, принимающую команду со
строго возрастающим порядковым номером (`CardCommand`, `TacticsCommand`, `seq` в WeGo), и проверяется по
списку допустимых действий; неверная, повторная или сделанная вне своего хода команда возвращает nullopt без изменения состояния и ГСЧ.
Перебор идёт по стабильным id (id экземпляров карт, id юнитов, id элементов стека); равенство разрешается по id. Ввод игрока и бота идёт
одним путём.

**Карты.** Виды `CardDef` unit/spell/instant, `cost`, у юнитов `power`/`health`/`guard`/`rush`, `target`
(none/player/unit/character/stackItem) с `side` (any/enemy/friendly), упорядоченные `effects` (damage, heal, draw, energy,
buff, counter, reveal, mill), применяемые к выбранной цели, контролирующему игроку, противникам, вражеским или дружественным юнитам.
Варианты `CardRules`: места 2..4, стартовая рука, максимальная рука (лишний добор сжигается), стартовое здоровье, энергия на старте/прирост/максимум,
добор за ход, первый игрок пропускает добор, усталость (растущий урон от пустой колоды), лимит поля, лимит ходов (затем
побеждает наибольшее здоровье, при равенстве ничья), размер колоды, муллиган none/partial (выбор карт по позиции в руке, замешать обратно,
добрать заново)/full (со штрафом), отдельная фаза боя, юниты атакуют сразу. Ход: начало (энергия, разворот,
добор) -> Main -> (Combat) -> следующее живое место. Розыгрыш карты или объявление атаки кладёт элемент на стек и
передаёт приоритет; мгновенные карты могут отвечать, удерживая приоритет; если все живые места подряд пасуют, разрешается верхний
элемент (LIFO), а приоритет возвращается активному месту. При разрешении элемент, чья цель исчезла (юнит пропал, игрок
выбыл, элемент стека отменён), не срабатывает; атака, чей атакующий погиб, не срабатывает. Юнитов-защитников нужно атаковать
раньше их игрока. Мёртвые юниты, выбывания и победитель проверяются после каждого изменения.

**Скрытая информация.** `CardGameCard::known` — маска по местам: колоды не известны никому (только количество), руки — их
владельцу и местам, которым их показало раскрытие (сбрасывается, когда карта возвращается в колоду), открытые зоны и стек —
всем. `cardViewFor(lib, state, seat)` (seat -1 = зритель) никогда не содержит скрытых карт, а допустимые действия
вычисляются по этому представлению (`cardLegalActions(lib, view)`), поэтому ни то ни другое не может зависеть от скрытых карт (проверено
изменением скрытых карт противника: представление и выбор бота не меняются). `cardEventsFor(events, seat)`
убирает личности карт из доборов и раскрытий, которые месту видеть нельзя. RTS lockstep реплицирует полное состояние; только
авторитетный сервер, отправляющий проекции, сохраняет руки в тайне.

**Тактические сетки.** На квадратных полях движение в 8 направлениях (ортогонально 2 полуединицы x стоимость клетки, по диагонали 3, без срезания
углов); шестиугольные поля используют осевые координаты в параллелограмме (2 за шаг). `tacticsReachable` — Дейкстра, фиксирующая клетки
в порядке (cost, cell) и заменяющая родителя только при строго более дешёвом пути, поэтому пути везде одинаковы.
Занятость: союзники проходят насквозь, враги блокируют, никто не останавливается на занятой клетке. Линии огня берут по одной клетке на
шаг сетки с фиксированным сдвигом; промежуточные клетки `blocksSight` блокируют (юниты — никогда). Укрытие: соседняя клетка укрытия
защищает от атакующих в пределах `coverCosMilli` (косинус половинного угла, по умолчанию 707 = 45 градусов, включительно) от
её направления; цель рядом с укрытием, но вне всех дуг, обойдена с фланга (+`flankBonusMilli`, +`flankDamage`), без
соседнего укрытия она открыта. Шанс попадания `tacticsPreviewShot` = меткость - половинное/полное укрытие - штраф за дальность сверх оптимальной
- штраф дозора (+ фланг), ограниченный [min, max]; 0 при блокировке или вне дальности.

**Ходы.** Порядок раунда: эффективная инициатива (база + активные приращения `tacticsSetSpeedModifier`, применяемые со следующего
раунда) по убыванию, при равенстве по возрастанию id юнита. Активный юнит получает полные ОД; Move стоит ceil(стоимость пути / (mobility x 2))
ОД; Attack делает одно вытягивание ГСЧ и завершает ход (`attackEndsTurn`); Overwatch завершает ход и взводит резервирование,
срабатывающее один раз по первому врагу, вошедшему в видимую клетку в пределах дальности (резервирования в порядке id юнитов; убитый
движущийся останавливается); Delay (с полными ОД, раз за раунд) переставляет юнита в конец раунда; EndTurn. Дозор
истекает в следующий ход зарезервировавшего юнита. Победа: последняя оставшаяся команда; при лимите раундов — команда с большим суммарным
здоровьем (при равенстве ничья, winner 0).

**WeGo.** `tacticsSubmitOrders` (раз на команду за раунд; свои живые юниты; движение в пределах 1 ОД; атака цели, которую команда
видит сейчас; дозор отдельно), затем `tacticsResolveWeGo`, когда все живые команды подали приказы: (1) взводится дозор;
(2) синхронное движение, спорная клетка достаётся большей эффективной инициативе, затем меньшему id, встречные обмены и
движения в клетку, чей обитатель её не покидает, останавливаются (`Bumped`), ответный огонь после каждого шага в порядке id движущихся;
(3) выстрелы бросаются в порядке id юнитов с позиций после движения, весь урон применяется вместе (взаимные убийства),
выстрелы без линии/дальности `Fizzled`; (4) смерти, победитель, следующий раунд. Ожидающие `TacticsOrders` сохраняются (вид 99).

**Видимость.** `tacticsViewFor(scenario, state, team)`: свои юниты (мёртвые с hp 0) и враги, которых видит какой-нибудь живой свой
юнит (дальность обзора + свободная линия); порядок и активный юнит — только когда видны. `tacticsEventsFor(view, events)` отбрасывает
движение невидимых юнитов и стирает клетки невидимых целей.

**Боты.** `cardBotChoose(lib, view, config)`: допустимые действия из представления, каждое симулируется по реальным правилам на
`cardStateFromView` (остальные пасуют, пока стек не опустеет; усталость выключена, так как неизвестные колоды пусты), оценивается по
весам здоровья/поля/руки, затем ограниченный ответный полуход, равномерно распределённый по кандидатам (`nodeBudget`, `depth`);
муллиган заменяет карты дороже порога. `tacticsBotChoose(scenario, view, objectiveCell, config)`: точки назначения из
достижимого множества, где блокируют только видимые юниты, в порядке (cost, cell), оцениваемые по ожидаемому урону и шансу убийства выстрелов,
которые они открывают, видимым угрозам на клетке, укрытию, расстоянию до ближайшего видимого врага или до клетки цели (данные карты,
никогда не позиция невидимого врага); дозор — только если видимый враг может войти в дальность; `searchBudget` ограничивает
число оценок. Оба не расходуют ГСЧ и при равенстве сохраняют более раннего кандидата. Движение в клетку, занятую невидимым юнитом,
отклоняется `stepTactics`; тогда владелец завершает ход.

**Данные и настройки.** `readCardLibrary(json, defaults)` / `readCardDecks` и `readTacticsScenario(json, defaults)`
строго проверяют данные с `JsonError` с путями (`cards.cards[0]: unknown key 'foo'`,
`cards.card 1.effects[0]: counter needs a stackItem target`, `tactics.grid.rows[1][0]: unknown cell 'x'`,
`tactics.units[0].at: cell is impassable`). Необязательные генерируемые разделы настроек (configuration 0.3.5): `cardGame`
(`startingHand` <= `maxHand`, `startingHealth`, `turnLimit`, `botNodeBudget`, `botDepth`) и `tactics`
(`roundLimit`, `halfCoverMilli` <= `fullCoverMilli`, `flankBonusMilli`, `rangePenaltyMilli`, `overwatchPenaltyMilli`,
`minHitMilli` <= `maxHitMilli`, `coverCosMilli`, `botSearchBudget`); адаптеры `cardRulesFromSettings`,
`tacticsRulesFromSettings`, `cardBotConfig`, `tacticsBotConfig`.

**Состояние.** Виды записей 96..103 зарезервированы за этим набором: `CardGameState` 96, `TacticsState` 98, `TacticsOrders` 99
(97 и 100..103 зарезервированы). Хешируйте через `cardGameHash` / `tacticsHash` (состояния, события, представления, определения) и привяжите
`cardLibraryHash` / `tacticsScenarioHash` в конверте сохранения. Боты не имеют состояния.

**Пример и тесты.** `examples/libraries/genre/cards-turns/` (`duel.json`, `skirmish.json`, `main.cpp`): дуэль на два места

## Транспорт (vehicle-controllers 0.2.0)

Заголовки `genre/VehicleControllers.h` (контроллеры), `genre/VehicleDamage.h` (зоны повреждений), `genre/VehicleSeats.h`
(места), `genre/RaceCourse.h` (чекпоинты, круги, позиции), `bots/RaceBot.h` (гоночный бот), `genre/RaceSession.h` (от стартовой решётки до результатов), общий заголовок `genre/Vehicles.h`,
`genre/VehicleData.h` (JSON), `genre/VehicleConfigured.h` (адаптеры настроек), `genre/VehiclePersistence.h` (записи,
хеширование). Цель `AIVERSE::lib_vehicle_controllers` (зависит от `match-rules`, `configuration`, `aiverse_engine`); нативные
OBJECT-модули вызывают `aiverse_native_use_libraries(target vehicle-controllers)`. Скилл: `skills/gameplay/aiverse-vehicle-controllers`.

**Детерминизм и сетевая модель.** Контроллеры кинематические и являются авторитетным игровым состоянием: математика Fixed, целые
тики, порядок по возрастанию id, никакой плавающей точки и физического бэкенда в цикле. Владелец коллизий сообщает контакты
(`VehicleContacts{grounded, groundHeight, groundNormal, grip, wheels[]}`) до шага и разрешает столкновения после него
(`vehicleResolveCollision(state, position, normal, restitution)` убирает скорость сближения и возвращает
импульс на единицу массы — входные данные для правил повреждений). `VehicleState` хранит и позу, поэтому предсказание — это прогон того же
шага с теми же входами; откат восстанавливает запись и проигрывает заново. Мир Box3D (docs/physics.md) не детерминирован
между сборками и может лишь зеркалировать позы для отображения; из него ничего не читается обратно. Каждый шаговый метод сначала проверяет конфиг,
состояние и вход; при некорректных данных, dt вне (0,1] или повторном/обратном тике возвращается nullopt, а состояние не меняется.

**Колёсный (аркадный симулятор).** Оси X/Z — земля, Y — вверх, рыскание в оборотах (0 смотрит на +Z, положительное рыскание поворачивает вправо). Руление
стремится к `steer * maxSteer` со скоростью `steerRate` и уменьшается с ростом скорости (`steerFalloffSpeed`). Обороты двигателя следуют за ведущими
колёсами (`speed / radius * gear * finalDrive`) и ограничены диапазоном холостой ход..красная зона; крутящий момент берётся из кусочно-линейной кривой `torque`
(rpm -> Nm), на ограничителе он равен нулю. Коробка передач: автомат переключается вверх на `shiftUpRpm`, вниз на `shiftDownRpm`, торможение
на месте включает заднюю передачу (тормоз ведёт назад, газ тормозит); ручная использует фронты `shiftUp`/`shiftDown` вплоть до
нейтрали (0) и задней (-1). Переключение отключает тягу на `shiftTicks`. Шины: статическая нагрузка плюс продольный перенос веса
(`cgHeight`, ускорение прошлого тика); запрос тяги/торможения выше `friction * load * grip` переходит в скольжение по
кривой `longitudinalGrip` (отношение запроса -> сцепление), боковая сила следует кривой `lateralGrip` по углу увода
(в оборотах), обе обрезаются кругом трения; тормоза и боковые силы никогда не разворачивают скорость колеса в пределах одного тика.
Ручник блокирует соответствующие колёса и масштабирует их боковое сцепление на `handbrakeGrip`: скольжение задней оси выше `driftEnter`
при `driftMinSpeed` начинает занос (`DriftStarted` / `DriftEnded` ниже `driftExit`). Рыскание использует суммарный момент шин
и инерцию, вычисленную по расположению колёс. Уклоны добавляют гравитацию вдоль нормали земли; без земли корпус падает
(`Airborne` / `Landed` с вертикальной скоростью в милли-м/с).

**Гусеничный, ховер, полёт.** Гусеничный: каждая гусеница стремится к `throttle*maxSpeed +- steer*pivotSpeed` (разворот на месте при нулевом
газе), скорость рыскания = разность гусениц / trackWidth, боковое скольжение гасится `lateralGrip`. Ховер: удержание высоты
`(groundHeight + height - y) * stiffness - vy * damping`, пока владелец сообщает о земле внизу (иначе гравитация), тяга
вдоль курса, квадратичное сопротивление, боковой дрейф гасится `lateralDamping`, скорость рыскания сглаживается `yawResponse`. Полёт:
воздушная скорость из тяги, квадратичного сопротивления и составляющей гравитации по тангажу; скорости тангажа/крена/рыскания с ограничениями крена и
автовыравниванием, виражи с креном масштабируются подъёмной силой; подъёмная сила = min(1, (airspeed/stallSpeed)^2), а её недостаток накапливает
снижение; ниже `stallSpeed` самолёт сваливается (`Stalled`, ослабленное управление, нос опускается) до `recoverSpeed`. На земле
он катится с торможением `groundFriction` и взлетает, как только набор высоты выводит его за пределы сообщённой земли.

**Зоны повреждений.** `VehicleZoneDef{id, local box, health, armor, critical, penalties{stat, atZero}}`. Входные повреждения
применяются по возрастанию id (id <= последнего принятого — `DamageIgnored`) с учётом брони; зона 0 находит зону по
локальной точке (`vehicleZoneAt`: содержащий её бокс, иначе ближайший). Каждый штраф линейно масштабирует свой показатель (двигатель, сцепление, руление,
тормоза, подъёмная сила) от 1 при полном здоровье до `atZero`; несколько зон перемножаются. Критическая зона на 0 выводит
машину из строя (двигатель 0) до ремонта (отрицательные значения). `vehiclePerformance(def, state)` передаётся в `stepVehicle`.

**Места.** Роли водитель/пассажир/стрелок; запросы по возрастанию id: Enter (скорость <= maxEnterSpeed, актёр в пределах
`enterRadius` от входа на место, место свободно, та же команда, что у сидящих, или не заперто; место 0 = первое свободное место
предпочитаемой роли, затем любое), Exit (скорость <= maxExitSpeed, первая точка выхода, которую принимает `clear(point, actor)` владельца:
выходы этого места, затем выходы других мест по id; если нет — `ExitBlocked`), Eject (игнорирует скорость), Switch, Lock/Unlock
(сидящие). `vehicleDriver` называет сидящего, чей ввод управляет машиной; выходы возвращают мировые позиции.

**Гонки.** `RaceCourse{checkpoints (RouteGate + respawn pose), laps, grid}` переиспользует ворота маршрута из match-rules: отрезок гонщика
от последней сообщённой позиции, пересекающий плоскость его следующих ворот по направлению нормали (`crossesGate`), передаётся в
`stepRoute` (ворота не по порядку игнорируются). Последний чекпоинт — линия финиша; стартовая решётка расположена сразу за ней.
Положение в гонке: финишировавшие по месту, затем круг, чекпоинт, расстояние на плоскости до следующего чекпоинта, более раннее прохождение последнего чекпоинта,
id. Езда в обратную сторону: скорость вдоль (предыдущий -> следующий чекпоинт) ниже `-wrongWaySpeed` в течение `wrongWayTicks`; автоматический респаун
после `respawnWrongWayTicks` тиков в обратную сторону или `stuckTicks` ниже `stuckSpeed`, плюс запросы владельца. Респаун происходит на
последнем пройденном чекпоинте (линия финиша после круга, место на решётке до первого) и сбрасывает отслеживаемую позицию, чтобы
телепорт никогда не засчитывался как пересечение.

**Гоночный бот.** `makeRaceLine(points)` (замкнутая петля; кривизна в каждой точке), `stepRaceBot(config, line, state, tick, view)`
возвращает `VehicleInput`: руление pure pursuit к точке упреждения (`lookahead + speed * lookaheadTime`) со смещением на
текущую полосу; целевая скорость = минимум по поворотам в пределах `brakeHorizon` от sqrt(vCorner^2 + 2 * brakeDecel * distance)
при vCorner = sqrt(cornerAccel / curvature) (точки торможения); трафик: соперник сбоку вытесняет на другую полосу,
ближайший более медленный соперник впереди в пределах `overtakeDistance` обгоняется со стороны, противоположной ему, машина прямо впереди
в пределах `followDistance` ограничивает скорость. Сложность: `skillMilli` масштабирует темп; `rubberBandMilli` добавляет темп последнему
месту и отнимает у лидера, только на прямых (в поворотах никогда не превышается заданное сцепление). Никакой случайности.

**Гоночная сессия.** `genre/RaceSession.h` проводит одну гонку от стартовой решётки до результатов для любого хоста. `makeRaceSession(course,
config, racers{id, bot}, line, startTick)`; на каждом тике `raceSessionInputs(config, line, state, tick, drivers)` до шага
машин (в Countdown, у финишировавшего гонщика и в завершённой гонке зажаты тормоза; компьютерные гонщики получают `stepRaceBot` со
своим местом и всеми остальными гонщиками как соперниками; игроки сохраняют собственные педали), затем `stepRaceSession(course, config,
state, tick, samples, respawnRequests)` после коллизий хоста (stepRace, респауны, фаза). Фазы: Countdown на
`countdownTicks` (счётчики застревания / обратного хода начинаются вместе с гонкой) -> Running -> Finished, когда финишировали все,
через `finishGraceTicks` после первого финишировавшего или через `timeoutTicks` после старта; `raceSessionWinner` = место 1. Вид записи
128. Данные для любого проекта: rules / map `"race"` (`genre/RaceSessionData.h`: `readRaceRules`, `readRaceTrack`), см. docs/races.md.

**Конфигурация.** Необязательная генерируемая секция `vehicles` (configuration 0.3.5): ограничения скорости для мест, `raceLaps`,
правила обратного хода/застревания/респауна и параметры гоночного бота (`bot*`). `vehicleSettingsErrors` отклоняет задержку респауна короче
задержки обратного хода и тики застревания без скорости застревания. Данные: `readVehicleDefinitions`; ошибки вида
`vehicles.vehicles[0].wheeled.gearsMilli[1]: ratios must be strictly descending`.

**Состояние.** Виды записей 88..95 зарезервированы за vehicle-controllers и sports-rules: `VehicleState` 88,
`VehicleDamageState` 89, `VehicleSeatState` 90, `RaceState` 91 (включает `RouteState` из match-rules), `SportsState` 92,
93 зарезервирован, `bots::RaceBotState` 94, `bots::SportsBotState` 95; `RaceSessionState` 128. Канонические, проверяются при загрузке. `vehicleHash` хеширует
состояния и потиковые отчёты; привязывайте `vehicleDefinitionHash`, `raceCourseHash` и `bots::raceLineHash`.

## Спорт (sports-rules 0.1.0)

Заголовки `genre/SportsRules.h` (правила), `genre/SportsFormation.h` (построения), `bots/SportsBot.h` (бот позиционирования),
общий заголовок `genre/Sports.h`, `genre/SportsData.h`, `genre/SportsConfigured.h`, `genre/SportsPersistence.h`. Цель
`AIVERSE::lib_sports_rules` (зависит от `configuration`, `aiverse_engine`). Скилл: `skills/genres/aiverse-sports-rules`.

**Контракт.** `stepSports(rules, field, state, tick, dt, players, actions, rng)` один раз на строго возрастающий тик.
Владелец двигает тела и сообщает каждого `SportsPlayer{id, team, position, velocity, tackle/control/accuracy skills,
active}`; действия (`Pass` с целевой точкой или получателем, `Shoot` в точку, `Tackle`) приходят из команд игрока или
от бота через ту же структуру, не более одного на игрока. Случайность — только из переданного движкового `Random` (броски на отбор,
фол, перехват и вбрасывание, ошибка удара); некорректный вход не трогает состояние и RNG. Порядок за тик:
выполнение возобновления игры, действия по id игрока, движение мяча (ведение со смещением вдоль скорости владеющего, или свободное качение с
трением), подборы и перехваты, голы и границы, часы.

**Владение и единоборства.** Свободный мяч забирает игрок, чьё наибольшее сближение с траекторией мяча на этом тике лежит
в пределах `pickupRadius` (самое раннее вдоль траектории, затем ближайший, затем id); ударивший не может снова забрать его в течение
`kickLockTicks`; выше `controlSpeed` для контроля нужен бросок `interceptMilli` с поправкой на навык контроля. Нового
владельца нельзя отобрать в течение `possessionLockTicks`. Для отбора нужны `tackleRange` и отсутствие оглушения; шанс равен
`tackleBase + (tackle - control)/2` (5..95%); неудачный отбор оглушает на `tackleCooldownTicks`. Фолы: отбор из-за
спины относительно направления бега владельца бросает `behindFoulMilli`, неудачный — `failFoulMilli` -> штрафной с места нарушения,
или пенальти с точки, если место нарушения в штрафной площади нарушившей команды.

**Удары.** Скорость паса `passSpeedMin..Max` и скорость удара `shotSpeedMin..Max` по `powerMilli`; пасы получателю даются на
опережение (две итерации расстояние/скорость); направление поворачивается на сидированную ошибку до `passError`/`shotError` оборотов,
масштабированную на `(1000 - accuracy)/1000`. `sportsInterceptPoint` предсказывает самую раннюю достижимую позицию мяча для бегущего.

**Поле и возобновления игры.** Ворота на x = +-halfLength в пределах `goalHalfWidth`; команда с индексом 0 атакует +x в нечётных периодах.
`Lines`: боковые линии -> вбрасывание другой командой, линии ворот -> угловой (последнее касание защитников) или удар от ворот;
`Walls`: мяч отскакивает с `restitution` (ведомый мяч зажимается); `FaceOff`: любой выход -> вбрасывание на
ближайшей точке, которое разыгрывают ближайшие игроки каждой команды (`faceoffBiasMilli`). После гола игра возобновляется с центра поля
пропустившей командой. Возобновления ждут `restartDelayTicks`, затем их выполняет ближайший доступный игрок команды, которой они назначены.

**Часы.** `periods` по `periodTicks`; `clockMode` Running (мёртвый мяч засчитывается), Stopped (засчитываются только тики живого мяча) или Added
(мёртвые тики добавляют компенсированное время, ограниченное `maxStoppageTicks`). Стороны меняются каждый период (`swapEnds`), каждый период начинается
с начального удара, команды чередуются. Ничья после основного времени ведёт к овертайму при `overtimeTicks > 0` или `goldenGoal`
(`goldenGoal` с `overtimeTicks == 0` играется до следующего гола); первый гол в овертайме завершает матч с золотым голом.
`MatchEnded` несёт победителя (-1 при ничьей).

**Построения и бот.** Слоты `SportsFormation`: роль, базовая/атакующая/оборонительная доли половины поля в системе отсчёта
атаки, `ballPull`. `sportsSlotTarget` отражает по направлению атаки; `sportsAssignSlots` сохраняет прежние назначения и
заполняет свободные слоты по роли, затем по расстоянию, затем по id. `bots::stepSportsBot` для каждой команды на каждом тике: фаза по воспринимаемому
владельцу (после `reactionTicks`), целевые слоты для всех, вратарь на линии мяч—ворота, владелец бьёт в пределах
`shootRange` при открытой линии (`laneWidth`, сидированный выбор стороны), пасует лучшему по формуле «продвижение минус давление» партнёру
по открытой линии или уводит мяч от давления (решение пересматривается каждые `decisionTicks`); в обороне: ближайший игрок прессингует
и отбирает (бросок `tackleMilli`), следующий не-вратарь опекает соперника, ближайшего к своим воротам; за свободным мячом бежит
игрок с самым ранним перехватом. Выход: целевая точка движения, флаг рывка и `SportsAction` для каждого игрока.

**Конфигурация и состояние.** Необязательная генерируемая секция `sports` (configuration 0.3.5) с соотношениями
`passSpeedMin <= passSpeedMax`, `shotSpeedMin <= shotSpeedMax`; `sportsSettingsErrors` добавляет перекрёстные проверки полей.
Данные: `readSportsDefinitions` (`sports.field.goalHalfWidthMilli: must not exceed halfWidthMilli`, ...). Записи:
`SportsState` 92, `bots::SportsBotState` 95 (93 зарезервирован); сохраняйте вместе с ними состояние RNG. `sportsHash` хеширует состояния и
отчёты; привязывайте `sportsDefinitionsHash(field, rules, formations)`.

**Исполняемый пример и проверка.** `examples/libraries/genre/vehicles-sports/VehiclesSportsExample.cpp` загружает
`vehicles.json`, `sports.json` и `settings.json`, проводит гонку на 3 круга из четырёх машин под управлением ботов (места, повреждения от
контактов машин, позиции, респауны) и футбольный матч 3 на 3 с золотым голом между двумя командами ботов, сохраняет и перезагружает
каждую запись посреди прогона и печатает результаты и итоговый хеш. CTest `library_vehicles_sports_example` запускает его дважды
(`tests/libraries/vehicles_sports_example.cmake`) и требует победителя гонки, победителя матча и равенства хешей;
`library_vehicles_sports` запускает `tests/libraries/genre_vehicles_sports_tests.cpp`. `VehiclesSportsConsumer.cpp` —
нативный потребитель library_demo. Проверено только с g++ (Linux): проверки синтаксиса заголовков, все заголовки genre/bots в одной единице трансляции,
тесты и пример, собранные вручную (также ASan/UBSan). Не проверено: CMake/изоляция, `aiverse_tests`, экспорт нативного
модуля, headless-матчи с восстановлением, MSVC/clang, рантаймы платформ.

## Поселение и производство (settlement-production 0.1.0)

Заголовки `genre/ColonyTypes.h` (определения, состояние, команды, проверка), `genre/ColonyRunner.h` (`stepColony`, вспомогательные функции настройки
`colonyAddColonist/Stockpile/Workstation`, `colonySchedule`), `genre/ColonyPower.h` (`stepPower`, `powerAddNode`,
`powerLink`, `powerComponents`), `genre/ColonyData.h` (JSON), `genre/ColonyConfigured.h` (настройки `colony`),
`genre/ColonyPersistence.h`, общий заголовок `genre/Colony.h`; бот `bots/ColonyPlanner.h` + `bots/ColonyPlannerData.h`.
Цель `AIVERSE::lib_settlement_production` (tasks, reservations, graphs, configuration, `aiverse_engine`); нативные OBJECT-модули
вызывают `aiverse_native_use_libraries(target settlement-production)`. Скилл: `skills/genres/aiverse-settlement-production`.

**Разделение ответственности.** Авторитетны, сохраняются и хешируются: колонисты (потребности, настроение, уровень настроения, занятие, работа, расписание, приоритеты,
навыки), склады с их книгами резервирования, рабочие места и заказы, работы (lib::Task + прогресс), тревоги, счётчики id
и номер последней команды (`ColonyState`); граф энергии/жидкостей с зарядом накопителей, флагами питания и
тиками переподключения (`PowerGridState`); перезарядки планировщика и счётчик команд (`ColonyPlannerState`). Владелец/хост: позиции,
навигация и время ходьбы (объёмы работ его включают), размещение построек, отрисовка, симуляция бедствий (пожар в сеточных
полях, наводнения, налётчики), инвентарь отдельных предметов. Только целые числа: потребности и настроение 0..100000 (настроение ±100000), работа в
«тиках при скорости 1000», скорости в милли. Строго возрастающие тики; некорректный ввод владельца возвращает nullopt, а состояние
не меняется; некорректные или устаревшие команды игрока/бота игнорируются и сообщаются (`CommandIgnored`), никогда не через assert.

**Порядок тика (`stepColony`).** 1 команды по возрастанию seq (`SetPriority`, `SetSchedule`, `SetBill`, `ClearBill`,
`OrderBuild`, `OrderGather`, `CancelJob`); 2 факты владельца (недееспособность, тревоги: сначала снятые, затем поднятые; поднятие создаёт
min(severity, maxResponseJobs) работ реагирования); 3 потребности убывают и восстанавливаются по текущему занятию (`restores`: сон,
отдых, работа), события NeedLow/NeedCritical/NeedRecovered; настроение = база + первая подходящая ступень настроения по каждой потребности + настроения активных
тревог + модификаторы владельца, уровни Breaking/Low/Content/High (события MoodBand); 4 занятие каждого колониста в порядке id: есть, когда
потребность в еде на уровне `lowAt` или ниже (одна единица со склада с наименьшим id, где есть незарезервированная единица, занятость `ticks`; реагирующие — только
при критическом уровне), нервный срыв (Breaking, не раньше `calmUntil`), критическая усталость -> сон где угодно, продолжать спать до
`recoveredAt` вне рабочих блоков, блоки Sleep/Leisure, если к колонисту не применяется тревога `ignoreSchedule`, иначе
работа; 5 генерация работ: одна открытая работа по рецепту на каждое рабочее место с заказом, пока первый выход ниже цели (0 = повторять),
одна открытая работа по переноске на каждое правило переноски, пока в `to` меньше `keep`; 6 назначение: вытеснение тревогами `preempt` (только работы
реагирования), затем `lib::claim` по уровням предпочтений 1..4 среди ожидающих работ с эффективным приоритетом = база + сумма приоритетов
активных тревог для типа работы, при равенстве — наименьший id работы; входы рецептов/строительства резервируются при захвате (`systems::reserve`, ticket =
id работы, owner = колонист), работы по переноске сокращаются до незарезервированного запаса; 7 работа: прогресс += навык * скорость уровня / 1000, работы по рецептам
на обесточенных рабочих местах (`input.unpowered`) и выходы, не помещающиеся в ёмкость склада, блокируются (`JobBlocked`);
завершение фиксирует резервирование и порождает Produced / Hauled / Built (новый id постройки; рабочее место создаётся, если у
чертежа есть тип рабочего места) / Gathered (ограничено значением `gatherAvailable[node]` за вычетом уже взятого на этом тике) /
AlertWorked; тревога, все работы реагирования которой выполнены, снимается (AlertResolved).

**Энергия и жидкости (`stepPower`).** У узлов есть среда (1 энергия, 2 вода, ...); связи соединяют только одинаковые среды; каждая связная
компонента (обход в ширину по `lib::Graph`, компоненты упорядочены по наименьшему id узла) балансируется отдельно. Предложение = выработка
производителей, масштабированная `PowerInput::outputMilli` (погода: `SurvivalWeatherEffects::windPowerMilli/solarMilli`, топливо); накопители добавляют
до `min(charge, rate)`; потребители удерживаются в порядке (приоритет по убыванию, id по возрастанию), пока помещаются, более поздние меньшие потребители всё ещё
могут поместиться (skip-fit); потребитель, потерявший питание, остаётся выключенным на `restoreDelayTicks` (гистерезис; события Shed/Restored). Дефицит
покрывается из накопителей в порядке id, излишек заряжает их в порядке id (StorageEmpty/StorageFull). `PowerReport::unpowered` передаётся в
`ColonyInput::unpowered`; связь между средами (насос, потребляющий энергию, чтобы производить воду) — это проводка владельца через
`outputMilli`, как показывает пример.

**Бот-планировщик.** `bots::planColony(config, defs, colony, facts, state, tick)` запускается раз в `intervalTicks`, оценивает правила
в порядке (приоритет по убыванию, id по возрастанию), у каждого — условия через AND над метриками (`stockPerColonist`, `stock`, `powerDeficit`,
`coldColonists`, `needLow`, `structures`, `openJobs`, `alerts`, `colonists`, `custom`) и действие: `build` (по средствам,
не более `maxOpen` открытых), `bill` (простаивающее рабочее место нужного рецепту типа с наименьшим id), `gather` (вариант сбора владельца с наибольшим
доступным количеством, наименьший id узла), `priority` (все колонисты, у которых он отличается). Не более `maxCommands` команд, перезарядки по правилам, без RNG.
Выход — `ColonyCommand` с собственным возрастающим seq бота, передаются в `stepColony` точно так же, как ввод игрока.

**Данные и настройки.** `readColonyDefinitions(json, colonyConfig(settings))`, `readPowerGrid(json)`,
`bots::readColonyPlanner(json, defs)`: неизвестные ключи, дроби, целые вне диапазона, повторяющиеся id и неизвестные ссылки
выбрасывают `JsonError` с путями по индексам (`colony.recipes[0].outputs[1][0]: duplicate id 1`) или по id
(`colony.recipe 5.workType: unknown work type 9`, `planner.rule 1: unknown blueprint or missing stockpile`). Необязательная секция настроек `colony`
(configuration 0.3.5): `ticksPerHour`, `moodBase`, `moodBreakAt` < `moodLowAt` < `moodHighAt`
(`colonySettingsErrors`), `breakTicks`, `lowSpeedMilli`, `contentSpeedMilli`, `highSpeedMilli`, `maxResponseJobs`.

**Состояние.** Виды записей 104..111 зарезервированы за settlement-production + survival-ecology: `ColonyState` 104,
`PowerGridState` 105, `bots::ColonyPlannerState` 110 (survival-ecology использует 106..109, 111 свободен). Записи канонические и
проверяются при загрузке (включая ссылки между работами, колонистами, резервированиями и складами). Хешируйте через `colonyHash`,
`powerHash`, `bots::colonyPlannerHash`; привязывайте `colonyDefsHash(defs)` в обёртке сохранения.

## Выживание и экология (survival-ecology 0.1.0)

Заголовки `genre/Survival.h` (модель тела, `survivalWeatherEffects`, `survivalMood`), `genre/Ecology.h` (популяции),
`genre/EcologyAnimals.h` (поведение), `genre/EcologyResources.h` (возобновление), `genre/EcologyData.h` (JSON),
`genre/SurvivalConfigured.h` (настройки `survival`), `genre/SurvivalPersistence.h`, общий заголовок `genre/SurvivalEcology.h`.
Цель `AIVERSE::lib_survival_ecology` (stealth-senses для `PerceivedTarget`, configuration, `aiverse_engine`); нативные OBJECT-модули
вызывают `aiverse_native_use_libraries(target survival-ecology)`. Скилл: `skills/genres/aiverse-survival-ecology`.

**Модель тела (`stepSurvival`).** Для каждого тела и тика: влажность (вода выставляет её на максимум; осадки на открытые тела, умноженные на
(1 - waterproof); высыхание на `dryPerTick` плюс тепло выше комфорта); ощущаемая температура = воздух, укрытие подтягивает её к
`shelterMilli` на `shelterInsulationMilli` (внутри нет ветра/дождя), снаружи ветро-холодовой эффект, умноженный на (1 - windproof), охлаждение от влажности,
плюс источники тепла; ядро (микроградусы) остывает на `coolingMicro` за каждый миллиградус ниже зоны комфорта, умноженное на
(1 - insulation), нагревается выше неё (утепление усугубляет перегрев) и внутри неё возвращается к норме (вдвое медленнее без еды);
нагрузка добавляет тепло. Голод убывает быстрее при нагрузке и дрожи, жажда — при жаре; выносливость тратится при нагрузке,
восстанавливается в покое (вдвое быстрее при отдыхе, вдвое медленнее при голоде/жажде, ноль при истощении от голода) и ограничена голодом. Состояние здоровья получает
урон от голода/обезвоживания/сильного холода/жары и восстанавливается, когда всё в порядке; 0 -> Died (тело замораживается). Биты статуса Cold,
Freezing, Hot, Overheating, Hungry, Starving, Thirsty, Dehydrated, Exhausted, Wet, Soaked порождают StatusOn/StatusOff.
`survivalMood(body)` превращает дискомфорт в модификатор настроения колонии. Проекты, где голодом владеет колония/инвентарь, задают
`survival.hungerPerTick` 0 (так делает пример). Реально съеденная еда/выпитое приходит от владельца инвентаря как `eatHunger` /
`eatThirst`; владелец здоровья/урона может зеркалировать состояние здоровья вместо прямого использования.

**Погода.** `survivalWeatherEffects(config, SurvivalWeather{temperature, wind, precipitation, sun})` возвращает окружающую температуру, ветро-холодовой
эффект, скорость намокания, `solarMilli`/`windPowerMilli` (коэффициенты производителей энергии), `growthMilli` (0 вне зоны роста,
максимум на `growBestMilli`, бонус от дождя) и `activityMilli` (бури/дождь замедляют животных). Само состояние погоды принадлежит владельцу.

**Экосистемы (`stepEcology`).** Популяции для каждой пары (регион, вид). Добыча применяется по поступлении (с ограничением). На тиках, кратных
`periodTicks`: рождения/смерти по логистическому росту r*N*(K-N)/K (отношение ограничено ±1, рост травоядных масштабируется
`growthMilli`, K масштабируется по региону `capacityMilli`), базовая смертность, хищничество attack*Npred*Nprey/(Nprey+half) с добычей,
делимой в порядке id хищников, рождения хищников = съеденное * конверсия, голодная смерть при съеденном < потребности, затем миграция
доли `migrateMilli` от избытка над K к соседям (поровну, остаток — меньшим id, события Arrived). Дробные части переносятся
в аккумуляторах милли каждой популяции; необязательный шум рождений `noiseMilli` берётся из переданного `Random`. События Extinct.

**Животные (`stepEcologyAnimals`).** Для каждого животного (в порядке id) по записям `PerceivedTarget` этого тика (наблюдатель = животное) и
фактам владельца (`species` 0 = люди): бежать от ближайшей пугающей цели в пределах `fleeDistance` (продолжать бег `fleeCalmTicks`), спать
в часовом окне или при истощении, охотиться на ближайшую видимую добычу, когда голодно (сдаётся через `huntGiveUpTicks`, перезарядка),
пастись, пока голодно и в регионе есть растительность, иначе бродить к целям из RNG вокруг дома. Кинематическое движение по XZ, ограниченное
границами; `poses` позволяют владельцу коллизий корректировать позиции. События Behavior, Killed (добыча удаляется, если это животное этого
состояния), Grazed, Starved; владелец направляет убийства/выпас в `EcologyInput::harvests` / узлы возобновления.

**Возобновление (`stepEcologyResources`).** Добыча сортируется по (узел, запросивший) и ограничивается; истощение запускает `regrowDelayTicks`;
восстановление каждые `periodTicks` на `regrowPerPeriod`, умноженное на рост от погоды/региона (перенос в милли). События Harvested, Depleted,
Regrowing, Full.

**Данные и настройки.** `readEcologyDefinitions`, `readEcologyAnimals` (скорости/расстояния в миллиметрах),
`readEcologyResources`; ошибки `ecology.species 1.diet: ...`, `ecology.species[0]: unknown key 'speed'`,
`resources[0].amount: must be in 0..5`. Необязательная секция настроек `survival` (configuration 0.3.5): пороги ядра/комфорта/холода/жары
(перекрёстно проверяются `survivalSettingsErrors`), скорости охлаждения/нагрева/восстановления, скорости голода/жажды/выносливости,
`lowAt`, охлаждение от влажности/высыхание, урон/восстановление, `windChillMilli`, `wetPerTick`.

**Состояние.** `SurvivalState` 106, `EcologyState` 107, `EcologyAnimalState` 108, `EcologyResourceState` 109 через
`genre::save/load`; `survivalHash`; привязывайте `survivalConfigHash`, `ecologyDefsHash`, `ecologyAnimalDefsHash`. Сохраняйте RNG
(`Random::state/inc`) вместе с симуляцией.

**Исполняемый пример.** `examples/libraries/genre/production-survival` (`colony.json`, `power.json`, `ecology.json`,
`planner.json`, `settings.json`, `production_survival.cpp`, CTest `library_production_survival_example`): 10 колонистов с двумя
сменами сна и индивидуальными рабочими предпочтениями выживают 20 дней (24000 тиков при 50 тиках/час) холодеющей осенней погоды с
дождём и ветром; планировщик выставляет заказы на готовку, собирает ягоды и дерево, включает охоту, когда кончается сырая еда, строит два

его не потушат; насос связывает энергосеть с графом воды, из которого пьют колонисты; олени и волки живут в двух регионах

## Схватки с боссами (boss-encounters 0.1.0)

Заголовки в `genre/`: `Telegraphs.h` (наземные области + телеграфируемые атаки), `StatusEffects.h`, `BossEncounter.h`,
`BossSchedule.h`, `MobBehaviour.h`, `EncounterData.h` (JSON), `EncounterPersistence.h`, `TelegraphDecals.h`
(отображение), `EncounterScenario.h` (эталонный бой без графики). Цель `AIVERSE::lib_boss_encounters` (зависит от
`combat-actions` ради соглашения о рыскании и `AttackPhase`); нативные OBJECT-модули вызывают
`aiverse_native_use_libraries(target boss-encounters)`. Скилл: `skills/gameplay/aiverse-boss-encounters`. Инструмент:
`aiverse_encounter validate|simulate <file>`. Сделано для порта Drone Fall (ME.BECS `DelayedAttackSystem`,
`TelegraphSystem`, `BossAttackUtils`, `MobsHuntSystem`, `MobAvoidanceJob`, `BossRotationUtils`, запросы персонального
босса); универсально для любой экшен-игры с видом сверху.

**Контракт.** Каждый шаг — чистое решение на математике Fixed и целых тиках: один вызов на объект на строго
возрастающий тик (повторный/обратный тик и некорректный вход возвращают nullopt, состояние не меняется), цели и
соседи обрабатываются по возрастанию id, RNG — только через переданный `Random&`. Владелец применяет урон через
своего владельца здоровья, применяет статусы (`StatusActorState` этого пакета или движковые), двигает тела, порождает
боссов/подкрепления и рисует отображение. Отображение читает `TelegraphView` / `StatusViewEvent` и никогда не пишет обратно.

**Области** (`AreaDef` на плоскости XZ, `Vec2{x,z}`, рыскание в оборотах, 0 смотрит на +Z, +X — вправо). `areaHits(area, pose, p, r,
reach)` проверяет круг цели; касание засчитывается. Круг: `|p-o| <= R+r`. Кольцо: пересекает `inner..R` (тело внутри
отверстия в безопасности, если не достаёт до внутреннего края). Конус: вершина внутри тела, либо в пределах `R+r` и внутри половинного
угла, либо касание граничного отрезка (как `AttackAreaGeometry.IntersectsCone` в Drone Fall). Линия: прямоугольник
`0..length` вперёд и `±halfWidth`; `reach` укорачивает его для рывков. `areaFalloffMilli` равен 0 в центре / вершине /
начале линии и 1000 на краю (у кольца 0).

**Телеграфы.** `TelegraphDef`: область, привязка (`Source`: у кастующего плюс локальный для него `offset` [вправо, вперёд],
например удар кулаком о землю; `Aim`: в точке прицеливания, ограниченной `[minRange, maxRange]`, например брошенный камень на 7..15 м),
тики `windup/active/recovery`, `interval` (0: один удар при срабатывании; >0: горящая земля бьёт каждый интервал),
`sweep` (линейные рывки: досягаемость растёт за активное окно, одно попадание на цель, `sweepReach` говорит владельцу, насколько
сдвинуть кастующего), `trackAim` (перенацеливание во время замаха; фиксируется при срабатывании), `falloff` от `damage` до `damageMin`,
`oncePerTarget`, `friendlyFire` (команда 0 = без принадлежности), `cancelOnSourceDeath` (только замах / рывок: сработавшая область
всё равно разрешается, как круги в Drone Fall), `cooldown` (читает мозг босса) и `statuses`. `beginTelegraph` фиксирует
начало и рыскание; `stepTelegraph` возвращает события `Started, Released, Strike, Ended, Cancelled`, попадания этого тика
(цель, урон, затухание, id статусов) и `TelegraphView` (`progressMilli` = заполнение замаха, затем 1000;
`activeMilli`). Удар приходится на первый активный тик; шаг, перепрыгнувший активное окно, всё равно бьёт
один раз. `telegraphLocksMovement` удерживает позу атаки на время замаха и восстановления (не во время рывка).

**Статусы.** `StatusEffectDef{kind Slow|Root|Stun|Burn, duration, tickInterval, speedMilli, damagePerTick,
stacking Independent|Refresh|Reject, maxStacks, anchor Ground|ModelTop}`. Значения по умолчанию как в Drone Fall: горение
независимое (несколько пожаров сразу), оглушение отклоняется (нельзя повторно оглушить оглушённого) с визуалом ModelTop, замедление обновляется.
Горение бьёт `ceil(duration/interval)` раз, первый раз через интервал после наложения, последний — при истечении. Сводка
за тик: наименьшее замедление, 0 при оглушении или обездвиживании, `stunned` блокирует атаки. `setStatusImmunity` по маске видов или по id
(боссы: иммунитет к оглушению/толчку, горение разрешено). `applyStatus` возвращает Applied / Refreshed / Rejected / Immune / Invalid
и событие отображения; `clearStatuses` завершает все (смерть). `gameStatusRules` записывает то же определение как статус `rules.json`
(+ длительность эффекта) для игр на RTS-симуляции, где авторитетными остаются движковые статусы.

**Мозг босса.** `BossDef{phases, enrage, archetype}`. Фаза 0 начинает бой; фаза i>0 начинается, когда
`hp <= hpBelowMilli/1000 * maxHp` или при возрасте схватки `afterTicks`, входы идут по порядку, даже если HP перескакивает несколько.
Паттерны: `ByRange` (первая запись, чья полоса `[minRange,maxRange]` содержит расстояние до цели — перечисляйте ближние полосы
первыми, например конус <= 3 м / удар о землю <= 7 м / камень <= 15 м), `Sequence` (курсор, ждёт свою запись), `Weighted` (одна выборка rng,
когда готовы две или более записей). `alternate` чередует каждое второе применение (левый/правый кулак) и использует общий
ключ перезарядки. Владелец сообщает `busy`, пока атака идёт; собственная перезарядка атаки и общая для фазы
`globalCooldown` начинаются, когда она заканчивается (Drone Fall: полная анимация, затем 1 с). `transitionTicks` приостанавливают атаки после
смены фазы. Множители (`damageMilli`, `speedMilli`, `cooldownMilli`) складываются с яростью (`afterTicks` или
`hpBelowMilli`); `bossDamage(step, damage)` масштабирует попадание. Волны подкреплений (`unit, count, maxAlive, every, radii`) порождают
`SpawnAdds` при входе в фазу и каждые `every` тиков, ограничиваясь числом живых подкреплений, о котором сообщает владелец.

**Расписание.** `ScheduleDef{windows, personal, rotation, archetypes}`; окно `{start, end, breather, variants,
excludePrevious, pauseWaves}`. Когда окно открывается, выбирается один вариант на всю карту (взвешенно; ротация показывает
каждый архетип по разу перед повтором и никогда не повторяет последний дважды, как `BossRotationUtils`; сохраняйте `BossRotation`
в профиле). Персональный режим создаёт по одному запросу на участника (по одному успеху на каждого, без повторного появления после раннего
убийства), общий режим — один запрос. События `Pending` повторяются до `markBossSpawned`; запросы, не размещённые до `end`, истекают.
`markBossDefeated` (только убийства) начинает передышку; `cancelBossRequests` (вышел / удалён) никогда не считается победой.
`ordinaryWavesAllowed` равен false, пока собственный босс ожидает или жив (pauseWaves), и во время передышки;
`bossesDefeated` считает персональные победы (трофеи).

**Поведение мобов.** `stepMob(config, state, tick, self, candidates, neighbours, rng, walkable)`. Порядок: возврат на привязи
домой (цели игнорируются до возвращения), бегство при `hpMilli <= fleeBelowMilli` от ближайшего врага в пределах `fleeRange`
до `fleeRecoverMilli`, истечения таймера или отсутствия угрозы; охота на закреплённую цель (атака идёт) > цель `priority`
(персональный босс -> его герой) > текущая цель в пределах `loseRange`, если другая не ближе на `switchMargin` >
ближайшая в пределах `aggroRange` (при равенстве по id); остановка на `stopDistance`; `movementLocked` сохраняет цель с нулевым
направлением. Иначе блуждание: точка в кольце `[wanderMin, wanderMax]` вокруг `anchor`, которую принимает `walkable`
(до `wanderAttempts` попыток, по две выборки `rng.unit()` на каждую), отрезок заканчивается по прибытии, при перелёте или по `wanderLegTicks`, затем
`wanderDelay`. Давление роя (`swarmCorrection`) — это разведение толпы и шаг в сторону с упреждением из Drone Fall: ближайшие
`maxNeighbours`, интервал `(r1+r2)*spacingMilli`, совпадающие пары разводятся по id без RNG, коррекция ограничена
`correctionMilli` от желаемой скорости, итоговая длина направления <= 1. `MobDecision{mode, target, desired, goal,
approach}`: рулить по `desired` или отдать команду движения по flow field / navmesh к `goal`.

**Данные.** `readEncounterData` читает `{"ticksPerSecond", "statuses", "attacks", "bosses", "schedule", "mob"}` с
целыми единицами милли (`radiusMilli`, `halfAngleMilli` в миллиоборотах, `offsetMilli: [right, forward]`) и временем
в тиках; неизвестные ключи, ключи неподходящей формы, неизвестные id статусов/атак/боссов и перевёрнутые диапазоны дают ошибку с путём
(`attack 1.halfAngleMilli: required for this shape`). Пример: `examples/libraries/genre/boss-encounter.json` —
трёхфазный великан (конус + оглушение, чередующиеся удары кулаками о землю + замедление с затуханием, отслеживаемый камень + горение, рывок с проходом,
кольцевая ударная волна, волны подкреплений, ярость на 150 с), взвешенный босс с горящей землёй и босс-последовательность с фазой по
времени, три окна персональных боссов на 3:00 / 6:00 / 9:00 с ротацией. Привязывайте `encounterDataHash` в сохранениях.

**Отображение.** `telegraphDecal(view, groundY, own, colors)` возвращает треугольники x, y, z, rgba: фоновая фигура плюс заливка,
растущая вместе с `progressMilli` (круг / кольцо наружу, конус от вершины, линия от начала), цвета своих и врагов
как `TelegraphColorConfig` в Drone Fall. Передавайте их в `RtsGroundCanvas` (`ViewGroundBatch`) или в Lua-список
`view.draw_ground`. Визуалы статусов: одно отображение на каждый серийный номер `StatusViewEvent` (Started / Refreshed / Ended) у привязки
Ground или ModelTop.

**Состояние и проверки.** Виды записей 112..119 (112 TelegraphInstance, 113 StatusActorState, 114 BossState,
115 ScheduleState, 116 MobState, 117 BossRotation); `encounterHash` сворачивает канонические байты в контрольные суммы.
`tests/libraries/encounter_tests.cpp` (`library_encounters`) покрывает граничные проверки попаданий для каждой фигуры, тики ударов,
позднее срабатывание, отмену, ограничение/отслеживание прицела, периодические удары и удары рывком, наложение/иммунитет/тайминг горения, вход в фазу по
HP и по времени, чередование, перезарядки от окончания атаки, переходы, ярость, ограничения подкреплений, детерминизм взвешенного выбора, порядок
ротации, персональные запросы / передышки / истечение, каждый режим мобов и разведение роя, ошибки данных, сохранение/загрузку каждого
состояния и эталонный бой. `aiverse_encounter simulate examples/libraries/genre/boss-encounter.json` запускает
его: с реакцией по умолчанию в 4 тика герой побеждает великана во всех трёх фазах (тик 1897, 15 увернутых
телеграфов); с `--reaction 100000` (без уклонений) герой погибает — исход боя решают телеграфы.

**Не покрыто.** Снаряды в полёте (weapon-policies), физика отбрасывания/толчков, навигация, добыча и награды,
HUD-баннеры и сетевая авторитетность (подключение к юнитам RtsModule: ниже).

**RTS-игры** используют пакет через rules `encounters` (`modules/rts/RtsEncounters.*`): боссы, мобы, телеграфы
и расписание на настоящих юнитах со статусами rules, приказами, flow fields, событиями, сохранениями и контрольными суммами; см.
[encounters.md](encounters.md) и `templates/boss_arena`.

## Королевская битва (battle-royale 0.1.0)

Заголовки в `libraries/include/aiverselib/genre/royale/` (первый пакет в собственной папке, без агрегирующих
включений): `SafeZone.h`, `Bombardment.h`, `SupplyDrops.h`, `Insertion.h`, `Standings.h`, `Lobby.h`, `Data.h`
(JSON), `Persistence.h` (записи), `BattleRoyale.h` (всё). Цель `AIVERSE::lib_battle_royale` (только aiverse_engine).
Рецепт: `skills/gameplay/aiverse-battle-royale/SKILL.md`; пример данных: `examples/libraries/genre/royale/royale.json`.

**Безопасная зона.** `SafeZoneDef` = игровые границы, начальный круг, стартовый тик, `centerPull` (0 — концентрически .. 1 — где угодно,
где помещается) и до 32 фаз (`wait`, `shrink`, целевой `radius`, `damage` каждые `interval` тиков, необязательный заданный
`center`). Каждая фаза объявляется, ждёт, затем линейно сужается; следующий центр — сидированная точка в диске
радиуса `(current - next) * centerPull` вокруг текущего центра, ограниченная границами, поэтому круги вложены, если только заданный
центр или ограничение не говорят иначе. `stepSafeZone` проходит любое количество границ стадий за один вызов
(нулевые ожидания / сужения, вызовы с крупным шагом); `safeZoneCircle(tick)` интерполирует, `safeZoneTarget` — объявленный
круг, `safeZoneTicksLeft` управляет таймерами HUD, `safeZoneDamage(tick)` — урон по актёру вне зоны на этом тике.

**Обстрел и сброс припасов.** `stepBombardment` предупреждает за `warningTicks`, выбирает область равномерно внутри
текущего безопасного круга, затем выпускает залпы кругов `Shell` с уроном до окончания `duration`; повторяется каждые
`interval` до `maxStrikes`. `stepSupplyDrops` объявляет ящики в сидированных точках внутри круга (обычно
объявленного целевого, за вычетом `edgeMargin`) каждые `interval` и приземляет их через `fall` тиков; `supplyDropPosition` даёт
спуск для отображения и проверок попаданий.

**Высадка с воздуха.** `planInsertionFlight` выбирает курс по полному обороту и точку пересечения в
диске `crossRadius` вокруг центра границ; путь начинается и заканчивается на `margin` за границами на высоте `altitude`.
`stepSkydiver` двигает одного актёра: Aboard следует за транспортом, прыгает, когда дверь открыта (через `doorOpen` тиков после
взлёта), или выбрасывается в конце; Freefall стремится к `fallSpeed` (или `diveFallSpeed` при пикировании) и рулит
к `move * glideSpeed`; парашют раскрывается по запросу выше `minDeployHeight` (после `chuteDelay`) или сам на
`autoDeployHeight` над сообщённой землёй; Parachute планирует со скоростями `chuteSpeed` / `chuteFallSpeed`; Landed прижимает к
земле. Единицы — метры за тик.

**Таблица результатов.** Участники вступают в команды до `startRoyaleStandings`. `reportDown` сбивает жертву, пока стоит товарищ по команде
(при `knockdowns`), иначе она выбывает; сбитая жертва, о которой сообщили повторно, выбывает. Когда в команде не остаётся
стоящих, её сбитые участники добиваются (засчитываются сбившему при `finishKnocked`), команда получает место
`оставшиеся команды + 1`, более ранние выбывания на том же тике делят лучшее место, а когда остаётся одна команда, матч завершается
победителем. `reportOutTogether` разрешает несколько выбываний сразу: если там выбывают все последние команды, это ничья
(`winner = -1`). `reportRevive`, `reportDamage` (только урон от врагов) и `royaleRanking` дополняют таблицу; каждый
вызов возвращает события ленты убийств (Knocked, Eliminated, Revived, TeamOut, Winner, Draw).

**Лобби.** `stepRoyaleLobby` запускает обратный отсчёт, когда присоединились `fillPlayers` или прошло `maxWait` при наличии `minPlayers`,
отменяет его, когда число падает ниже `minPlayers`, и сообщает места `botFill` в Started.

**Состояние и проверки.** Виды записей 120..126 (120 SafeZoneState, 121 BombardmentState, 122 SupplyDropState,
123 InsertionFlight, 124 SkydiverState, 125 RoyaleStandings, 126 RoyaleLobbyState); `hashRoyale` сворачивает канонические байты
в контрольные суммы; привязывайте `royaleDataHash` JSON-файла. `tests/libraries/royale_tests.cpp` (`library_royale`) покрывает
вложенность и интерполяцию кругов, многостадийные шаги, интервалы урона, заданные и концентрические центры,
расписания обстрелов и сбросов, геометрию полёта, прыжок / пикирование / ручное и автоматическое раскрытие парашюта / принудительный выброс / приземление,
сбивание / поднятие / уничтожение команды / зачёт / равенство / ничью, обратный отсчёт и отмену лобби, ошибки JSON, сохранение/загрузку каждого состояния и
эталонные хеши сидированного круга и траектории полёта (одинаковые с переносимым 64-битным умножением и на gcc / clang).

**Не покрыто.** HUD, мини-карта и модели; таблицы добычи (порождение через владельца добычи / инвентаря); поведение ботов
с учётом зоны; транспорт; репликация (снапшоты владельца переносят круги и фазы).
