# AIVERSE MotionWeave

## Импорт записи ходьбы BVH

`render::parseBvhMotion(text)` читает иерархию и кадры BVH, а
`render::retargetBvhMotion(motion, model, rootNode, jointMap)` переносит
повороты выбранных суставов и перемещение персонажа на другой скелет.
Масштаб перемещения определяется длиной ноги целевой модели. Высота таза
подстраивается под нижнюю стопу на ровной плоскости; ориентация опорной
стопы выравнивается по исходной позе. Исходный BVH передаётся извне и не
встроен в движок. Для просмотра в VIVID Creator используйте
`--preview-bvh <path>` вместе с `--asset <manifest>` и
`--preview-sequence <frames>`.

Для Ada взята запись CMU Graphics Lab `02_01` (344 кадра, 120 кадров/с),
доступная по адресу
`https://github.com/una-dinosauria/cmu-mocap/blob/master/data/002/02_01.bvh`.
Условия CMU на `https://mocap.cs.cmu.edu/` разрешают использование в
продуктах, но запрещают прямую продажу данных, включая преобразованные
форматы. Исходный BVH хранится вне репозитория. Ноги и корпус Ada следуют
записи; для рук используются процедурные каналы, адаптированные к её
А-позе. Пока это предпросмотр, а не готовый бесшовный цикл или решение для
неровного рельефа.

## Генерация цикла ходьбы (прототип)

`render::generateWalkCycle(model, rig, settings)` создаёт зацикленный `AnimClip`
по указанным суставам обеих ног, плеч, корня и, при наличии, локтей, корпуса,
шеи и головы. Исходная модель не меняется. Направление движения рига — локальная
ось +Z; оси сгиба выводятся из исходной позы. `rootSpeed` задаёт перемещение
персонажа за цикл, а `rootBob` — вертикальное движение таза как долю длины
ноги, поэтому результат сохраняет амплитуду при разных масштабах импорта.

В опорной фазе цель голеностопа компенсирует движение корня, а двухзвенная IK
рассчитывает положение ноги. Таз слегка смещается к опорной ноге и
поворачивается; руки качаются с задержкой и немного сгибаются в локтях,
корпус слегка наклоняется. Свободная стопа проходит по низкой плавной дуге.
По направлению плеча и локтя генератор распознаёт расслабленную, A- и T-позу
и опускает руки перед шагом. Голова получает небольшое движение относительно
корпуса. Пока опора рассчитана для ровной плоскости на высоте стопы в исходной
позе; точного переката подошвы, адаптации к рельефу, автоматического поиска
суставов и записи клипа в каталог ещё нет.

Диагностический просмотр VIVID Creator с параметрами `--smoke --preview-walk
--preview-sequence 48 --asset <human-manifest>` показывает этот клип в 3D.
Адаптер модульного персонажа передаёт движение таза, корпуса и головы
отдельным скелетам кожи и волос; сам генератор не зависит от VIVID.

**MotionWeave** — каноническое название модульной, не зависящей от жанра
подсистемы анимации AIVERSE: AnimationGraph, клипы, деревья смешивания, IK, Motion Matching,
Montage, root motion, позы ragdoll, инерциализация и LOD анимации/GPU-толпы.

## Публичный API

В нативных проектах используйте новую цель CMake и брендированный публичный заголовок:

```cmake
target_link_libraries(my_game PRIVATE AIVERSE::MotionWeave)
```

```cpp
#include <aiverselib/motionweave/MotionWeave.h>

// Separate client presentation ECS World; never Simulation::world().
aiverse::World presentation;
// Configure animation asset, player and output pose components first.
aiverse::motionweave::MotionWeave::update(presentation, frameDt);
```

Это *та же самая* реализация, что и у существующей библиотеки, а не второй движок:

| Рекомендуемый новый символ | Совместимый существующий символ |
| --- | --- |
| `AIVERSE::MotionWeave` | `AIVERSE::animation_ecs` |
| `AIVERSE::motionweave` | `AIVERSE::animation_ecs` |
| `aiverse::motionweave` | `aiverse::lib::animation` |
| `MotionWeave::update(world,dt)` | `stepAnimationPresentation(world,dt)` |
| `<aiverselib/motionweave/MotionWeave.h>` | `<aiverselib/animation/EcsAnimationSystems.h>` |

Все специализированные библиотеки по-прежнему доступны по историческим путям
`<aiverselib/animation/...>`. Существующие имена `render::AnimationGraph`,
`render::Animator` и `Pose` намеренно оставлены без изменений.

## Устройство среды выполнения

**Представление:** числа с плавающей точкой, экземпляры AnimationGraph, IK и скиннинг живут
в отдельном визуальном ECS World. FPS подключает `fps.visual.model`, настраиваемый
Graph или запечённую анимацию толпы, сохраняя запасной вариант с кубом. Существующий RTS view
продолжает использовать свой исходный путь анимации, пока его не перенесут осознанно.

**Геймплей:** авторский root motion с фиксированной точкой попадает в авторитетную
симуляцию только через мотор, учитывающий столкновения. Косметические уведомления AnimationGraph
и Montage не могут запускать авторитетный урон, перезарядку или попадания.

**Авторинг:** визуальные окна редактора, профили Humanoid Avatar, дескрипторы Ragdoll,
операции Montage и запекания root motion используют общий Workspace/MCP.
Схемы сохраняемых ассетов и идентификаторы редактора не меняются из-за смены бренда.

## Многопоточная среда выполнения представления

Для игры с множеством анимированных персонажей один раз создайте **постоянный, принадлежащий хосту**
планировщик и передавайте его в трёхаргументный вызов обновления MotionWeave:

```cpp
#include <aiverselib/motionweave/MotionWeave.h>

aiverse::motionweave::MotionWeaveScheduler scheduler;
auto stats = aiverse::motionweave::MotionWeave::update(
    presentationWorld, frameDt, scheduler);
```

Существующий двухаргументный `MotionWeave::update(world,dt)` по-прежнему
**последовательный** ради совместимости. Планировщик владеет постоянным ограниченным
пулом потоков с перехватом работы (до семи фоновых потоков плюс поток
кадра). Каждый кадр он классифицирует модели и скомпилированные графы, разделяет
независимую работу клипов, смешивания, контроллеров, motion matching и совместимого IK
на порции, взвешенные по стоимости, а затем выполняет их параллельно.
Нативные/Lua-колбэки, traits анимации, контакты с окружением и
операции рига, чувствительные к колбэкам, **всегда выполняются в потоке кадра
после завершения рабочих потоков**. Компонент `AnimationWorkHintComponent` с `mainThread=true`
явно направляет работу в эту очередь.

`MotionWeaveScheduleOptions` задаёт минимальное число сущностей, минимальную
оценку работы и размеры порций. `AnimationWorkHintComponent` также
поддерживает множитель стоимости для отдельного персонажа. Планы безопасности и стоимости графов
мемоизируются в пределах кадра, а ёмкость плотных списков работы переиспользуется.
Невидимые персонажи с уже действительной позой получают уменьшенную оценку
работы. Вызывающий код не должен менять структуру World или делать её снимок, пока
`MotionWeave::update` не вернёт управление.

`MotionWeaveScheduleStats` сообщает число подходящих, параллельных и последовательных актёров,
пакеты, число рабочих потоков, оценку работы, число уникальных графов, число актёров вне экрана
и время безопасной и последовательной фаз. Эти измерения — неавторитетная
диагностика представления; они никогда не влияют на lockstep геймплея и контрольные суммы.

### Автоматический выбор бэкенда для FPS

FPS поддерживает `fps.visual.animationMode: "auto" | "cpu" | "gpu"`
и устаревший `bakedCrowd: true`. Для подходящей простой импортированной
скиннинговой модели режим auto переходит на запечённый GPU-инстансинг при 24 видимых
удалённых персонажах и выходит из него при 12, избегая частых переключений.
Сложные пользовательские графы, требования к IK/контроллерам и `graphFile`
остаются на CPU; клиент FPS лениво создаёт постоянный планировщик,
когда присутствует 16+ персонажей с палитрой.
`fps.visual.animationStats: true` включает необязательную диагностику в HUD.

Отрисовка сцены и загрузки на GPU остаются в графическом потоке.
Быстрый путь для толпы переиспользует существующий в AIVERSE запечённый скиннинг и
инстансинг Renderer3D; MotionWeave не заявляет нового бэкенда GPU compute
скиннинга.

**Статус тестов:** все новые CTest-фикстуры для рабочих потоков, планировщика и бэкендов
закоммичены, но **NOT RUN** (отложено по просьбе пользователя). Проверьте компиляцию,
TSAN, скриншоты FPS на macOS, паритет сохранений и сети FPS, а также реальные бенчмарки FPS/RTS,
прежде чем объявлять готовность к продакшену.

### Фикстура производительности CPU (отложена)

Соберите отдельный (без GPU и файлов моделей) бенчмарк после настройки
`AIVERSE_BUILD_TOOLS=ON`:

```sh
cmake --build build/ecs-test --target aiverse_motionweave_bench
./build/ecs-test/aiverse_motionweave_bench --actors 1000 --frames 120
./build/ecs-test/aiverse_motionweave_bench --actors 5000 --frames 120 --ik
```

Он создаёт одинаковые World для последовательного режима и для постоянных рабочих потоков, прогревает оба,
измеряет среднее время кадра на CPU и проверяет одну выходную позу на паритет.
Бенчмарк намеренно **не зарегистрирован в CTest**, потому что время
зависит от машины. Его нужно запускать вместе с ThreadSanitizer,
скриншотами Metal на реальных моделях и показательной трассировкой кадра RTS/FPS,
прежде чем менять пороги рабочих потоков в продакшене. **NOT RUN**.

## Строгий контракт независимости от жанра

MotionWeave НИКОГДА не должен зависеть от модулей FPS/RTS/RPG или заглядывать в них.
Зависимость направлена в одну сторону:

```text
Any game module / game simulation / editor
      ↓ generic animation model and named parameters
MotionWeave reusable presentation ECS
      ↓ generic Pose / Notifies / Root delta
Host rendering, audio/VFX and host-owned gameplay motor
```

Ядро не знает, что означает «fire», «attack», «move», «cast»,
«reload» или другое действие. Авторы выбирают имена параметров и событий
в собственных графах; клиенты проецируют своё состояние в
один и тот же переиспользуемый API.

Универсальный `<aiverselib/animation/MotionWeaveSourceBridge.h>` предоставляет
`AnimationSourceFrame {sourceId,generation,model,graph,inputs}` и
`MotionWeaveSourceBridge::sync(presentationWorld, sources)`.
Мост поддерживает идентичность визуальных ECS-сущностей, сбрасывает визуальные плееры
при замене источника, копирует определённые графом скалярные и векторные параметры
и удаляет пропавшие источники. Он не вычисляет анимацию и не
фиксирует состояние геймплея. Вызывайте обычный планировщик MotionWeave
после проецирования всех входов и необязательной настройки бюджета view.

Исходный адаптер событий FPS вынесен из библиотеки анимации
в `modules/fps/view/FpsAnimationEvents.h`.
Общий `<aiverselib/animation/AnimationActionEdges.h>` теперь
обрабатывает только непрозрачные именованные счётчики и переходы булевых состояний, без
семантики FPS/RTS или типов действий. `playAnimationSlot` находится рядом с
определением универсального ECS-компонента `AnimationMontageSlotsComponent`.

## Миграция на View движка

Канонический тип сцены/вида — `aiverse::View` (также
`aiverse::view::View`) в `engine/view/View.h`, подключаемый через
`AIVERSE::view`. Код хоста передаёт записи `aiverse::view::Object`,
содержащие стабильные ID, универсальные пакеты `render::ModelDraw`,
необязательный AnimationGraph и именованные параметры. Универсальный View
управляет независимыми ECS-состояниями представления, бюджетами LOD анимации,
планированием рабочих потоков и отправкой сцены на основе поз.

Используйте `View::update(span,dt)` перед `View::submit(renderer,span)`
или `View::submitOne(renderer,object)`. Пакет может содержать модель
без графа анимации. View не зависит от модулей RTS, FPS, контроллера камеры,
правил игры, сети, боя, карты или ландшафта.

Переходный адаптер всё ещё существует в
`modules/rts/view/RtsView.cpp` и `RtsViewDraw.cpp`: он проецирует
в универсальный View только простые подходящие скомпилированные графы анимации и
делегирует их **финальную отправку ModelDraw** в
`View::submitOne`. Сложная процедурная анимация RTS, контактный IK,
жанровые вложения/FX/туман/ландшафт остаются в игровом
хосте, пока для каждого из них не появится универсальный контракт рендеринга. Класс совместимости
`game::RtsView` остаётся для старого игрового кода; это не
канонический View движка, и в новых проектах его использовать не следует.

### Статус миграции хостов

Оба существующих игровых фронтенда теперь отправляют как минимум поддерживаемые
ими отрисовки анимированных моделей через универсальный движковый
`aiverse::View::submitOne`:

- Устаревший игровой `game::RtsView` делегирует строго
  подходящее подмножество вычисления поз чистого AnimationGraph и
  финальную стилизованную отрисовку модели.
- Эталонный клиент FPS проецирует свой существующий `render::ModelDraw`
  (CPU Graph / GPU Baked) через `View::submitOne`, сохраняя
  предвычисленную позу. Его реплицируемое состояние геймплея никогда не попадает
  в View движка.

Общее имя CMake `AIVERSE::View` (устаревшее имя в нижнем регистре
`AIVERSE::view` тоже работает) и публичный
`<engine/view/View.h>` описывают предпочтительный API движка.
Старое представление `aiverse_game_view`/RTS-специфичное остаётся
кодом совместимости на время миграции; оно **пока не** идентично
новому универсальному View. Общая композиция камеры/отсечения/ландшафта/освещения
и полное удаление устаревшего игрового адаптера требуют дальнейшего
рефакторинга. Внутри `engine/view` не допускается никакая зависимость
от жанра на уровне исходного кода.

### Владелец ресурсов рендеринга (Stage 99)

Состояние графа и позы MotionWeave **не** владеет GPU-выделениями Model.
Универсальные нативные хосты могут использовать `aiverse::render::ModelResourceCache`
(`engine/render/ModelResourceCache.h`) с отдельным `World`/`aiverse::View`
представления. Кэш владеет картой моделей и общими
арендами текстур. При замене модели/графа хосты должны отсоединить затронутые
`AnimationSourceFrame` и плееры поз/графов **до** перемещения
старой модели в очередь отложенного вывода из эксплуатации в кэше. На следующей безопасной
границе кадра хоста `collectRetired(device)` вызывает явный
барьер `gfx::Device::waitForResourceIdle` и освобождает только ресурсы,
чьи предыдущие отправки на GPU завершены. Никогда не выводите завершение
из `frameSerial()` или фиксированного числа кадров в полёте.

Устаревшие `game::view_adapter::RtsModelResourceCache` и
`RtsModelPreparationService` — псевдонимы универсальных классов
рендеринга. Ресурсы сферы/куба для предпросмотра материалов в `game::Portrait`
— первый реальный потребитель редактора с независимым владением. Полный
адаптер совместимости сцены RTS ещё не выведен из эксплуатации. Отложенные
тесты GPU/бэкендов и паритета анимации — **NOT RUN**.

### Неблокирующий вывод GPU-моделей из эксплуатации (Stage 100)

Время жизни моделей и текстур на GPU не зависит от состояния плееров MotionWeave.
Нативный хост может владеть `render::ModelAssetProvider` (из
`engine/render/ModelAssetProvider.h`) без подключения заголовков RTS/FPS,
а затем отправлять заимствованную модель через `aiverse::View::submitModel` или
универсальный упорядоченный `ScenePacketBatch`. После инвалидации графа/источника
отсоедините владеющие ECS-источники представления, прежде чем перемещать модели в
очередь вывода из эксплуатации `render::ModelResourceCache`. Каждый граф вычисляет
только один владелец анимации; отправка пакета не должна продвигать граф второй
раз.

Stage 100 добавляет асинхронные маркеры вывода из эксплуатации для каждого пакета через
`gfx::Device::beginResourceRetirement`,
`resourceRetirementComplete` и `endResourceRetirement`.
`ModelResourceCache::collectRetired` на поддерживаемых бэкендах опрашивает состояние, а не ждёт
весь GPU. Старое синхронное ожидание — лишь запасной вариант или явный
барьер при завершении работы. Никогда не используйте счётчик кадров,
фиксированную задержку или время с последнего использования как условие завершения работы GPU.
Новый `game::Portrait::renderStaticModel` — прямой потребитель предпросмотра
нативных моделей, использующий канонический View; для этого пути кода
не нужен владелец на стороне игры. Динамические модели RTS по-прежнему используют
представление и рендеринг совместимости.

**NOT RUN:** отложенные нативные проверки сборки, выполнения,
времени жизни на GPU, санитайзеров и визуального паритета для Metal/Vulkan/GL/WebGL2.

### Stage 101 — асинхронная подготовка исходников моделей и давление вывода GPU-ресурсов из эксплуатации

Графы анимации остаются отделены от загрузки ресурсов рендеринга. Нативные
хосты проектов могут использовать `render::ModelAssetProvider::requestAsync(path)`
для ограниченного однопоточного импорта моделей на CPU, а затем вызывать
`publishReady(device, maxCount)` в владеющем потоке рендеринга перед
построением пакетов `aiverse::View`. Очередь CPU записывает ревизии
исходников: инвалидация исходника модели делает любой более старый результат рабочего потока
непубликуемым, даже если задача CPU завершится позже. Идентичность/поколение
источника MotionWeave и любые живые плееры поз/графов по-прежнему нужно
отсоединить перед заменой резидентной Model.

`render::ModelResourceCache` теперь предоставляет телеметрию давления вывода из эксплуатации
на основе числа моделей и мягкий лимит допуска для НОВЫХ загрузок
универсальных моделей. Существующие источники графов продолжают отрисовываться; переполненная очередь
никогда не должна вызывать преждевременного уничтожения на GPU. По умолчанию — 128 выведенных
объектов Model, а НЕ точный по байтам бюджет памяти GPU. Панель Statistics редактора
показывает ожидающие вывода GPU-модели и срабатывания запасного пути с fence.

Окно Model редактора даёт подключаемый по желанию предпросмотр нативного исходника для
статических моделей без скиннинга, используя `render::ModelAssetProvider`
с независимым владением и
`game::Portrait::renderStaticModel`. Полностью авторские портреты
RTS/персонажей по умолчанию по-прежнему используют прежний путь представления,
сохраняя переопределения материалов, вложения и воспроизведение анимации.
Путь просмотра сырой модели не является заменой с паритетом.

**NOT RUN:** CMake/компилятор, CTest, GPU-тесты Metal/Vulkan/GL/WebGL2,
нативный предпросмотр/предпросмотр редактора, санитайзеры и визуальные регрессии
симуляции/анимации. Держите этапы независимыми и не утверждайте, что старый RtsView
удалён.

### Stage 102: приоритеты исходников моделей и оценка памяти при выводе GPU-ресурсов из эксплуатации

Хост владеет одним `render::ModelAssetProvider` или отдельным провайдером
на каждую область представления, а не одним на каждого анимированного актёра. Для импорта нативных моделей
`requestAsync(source, ModelLoadPriority)` выбирает
`Background`, `Visible` или `Interactive` для поставленных в очередь задач CPU;
активный рабочий поток никогда не вытесняется. Вызывайте
`publishReady(device,maxCount,budgetMs)` на границе кадра потока рендеринга
с жёстким ограничением числа моделей и рекомендательным ограничением по времени.
Первая загрузка на GPU может превысить `budgetMs`; изнутри рабочего потока ничего
не публикуется. Сохраняйте ревизии исходников и отсоединяйте любые старые
`AnimationSourceFrame`, граф, позу и заимствованный `Model*` перед
инвалидацией. Второго вычисления MotionWeave не появляется.

`ModelResourceCache` теперь может оценивать *известный, принадлежащий модели*
объём выводимых ресурсов и применять необязательный лимит допуска,
выведенный из байтов. `ModelResidentEstimate` намеренно не учитывает заимствованные
аренды текстур и общие страницы геометрии и НЕ является точным показанием
VRAM. Никогда не освобождайте объект из-за достижения лимита; уничтожение
разрешает только его собственный завершённый GPU fence.

Отдельный `aiverse_modelview --provider --no-merge` — второй
реальный потребитель универсального `aiverse::View` для статических сырых ассетов, наряду
с подключаемым независимым сырым предпросмотром в редакторе. Предвычисленные позы на
устаревшем пути анимированного modelview по-прежнему формирует существующий хост;
View лишь отправляет их один раз. Жанровый адаптер `RtsView`
всё ещё используется в других местах и не выведен из эксплуатации.

**NOT RUN:** все проверки CMake, CTest, нативного modelview/редактора, GPU-бэкендов,
санитайзеров, снимков и визуального паритета остаются отложенными.

### Stage 103 — подготовка исходников в нескольких рабочих потоках и отображение View с единым владельцем

Общий владелец ресурсов моделей теперь может готовить несколько независимых
файлов моделей в рабочих потоках CPU, не затрагивая ECS World и GPU:
`render::ModelAssetProvider::setCpuWorkerCount(1..8)`,
`setCpuMaxQueued` и `requestAsync(source,priority)` передаются в
`AsyncModelCpuQueue`. По умолчанию остаётся один рабочий поток; редактор или
нативный хост может включить больше. Рабочие потоки ничего не знают о жанре,
типах игроков FPS/RTS, пакетах сцены или вычислении графов MotionWeave.
`ModelAssetProvider::publishReady(device,...)` загружает подготовленные Model
в потоке-владельце рендеринга/устройства. Хосты авторинга, которым нужна проверка
перед публикацией на GPU, могут вместо этого вызвать `takePrepared(result)`, скомпилировать
свой риг на основе `result.model`, а затем вызвать `publishPrepared(device,
freshGenerationKey,std::move(result.model))`. Этот путь использует ту же
транзакцию стейджинга и отклоняет публикацию, пока активна аренда чтения Model.
`cancelAsync(source)` инвалидирует ожидающие результаты CPU, не
вытесняя последнюю исправную резидентную Model; `stopAsync()` дожидается читателя
до уничтожения его проекта. Выводите старое поколение из эксплуатации только после
успешной публикации, предварительно отсоединив кэши поз и рендерера.

Нативный предпросмотр лица в Studio использует этот раздельный путь. Одна `ModelReadLease`
охватывает вычисление позы вплоть до синхронной отправки в Renderer3D.
Смена проекта опустошает старого владельца и его кэш текстур, поэтому одинаковые
относительные пути не могут переиспользовать текстуры другого проекта. Подготовка на CPU
идёт в рабочем потоке; загрузка/вывод из эксплуатации на GPU и единственный Animator остаются
в потоке рендеринга. Неудачные импорты сохраняют владение последней исправной версией и сообщают
об отклонённом поколении, а не рисуют устаревший ассет.

Приоритеты — `Interactive`, `Visible`, `Background`. Ожидающие
задачи одинакового приоритета обслуживаются по FIFO; после длительной череды
высокоприоритетных отправок планируется самый старый запрос в очереди, чтобы уменьшить
голодание фоновых задач. Выполняющаяся задача не вытесняется. Каждый результат CPU
содержит ревизию своего исходника; при инвалидации ассета он
отбрасывается, а не публикует устаревшую Model, а при завершении работы
дожидаются все futures рабочих потоков до освобождения читателя и кэша текстур.
Передаваемые вызывающим кодом колбэки `FileReader` должны быть реентерабельными, если
настроено больше одного рабочего потока.

Общее владение текстурами на GPU измеряется один раз через
`ModelTextureCache::gpuOwnerEstimate()`, никогда — на каждого заёмщика.
Глобальный для устройства пул геометрии остаётся отдельным владельцем ресурсов; эти
цифры — диагностика в эквиваленте RGBA8, выведенная из исходников, а не точное
использование VRAM драйвером.

Исходный код `SceneRenderable` редактора теперь использует канонические
`aiverse::View::submitModel` и `submitMesh` для обычных отправок моделей
и мешей. Специализированные силуэты мешей при выделении/наведении
сохраняют прежний путь, специфичный для рендерера. Владелец по-прежнему
строит преобразование, оттенок и контур ModelDraw; View
не запускает анимации графа второй раз. Устаревший слой совместимости
портретов/внешнего вида типов RTS остаётся активным.

**Проверка NOT RUN:** нативный компилятор CMake, CTest, санитайзер,
реальные GPU/Metal/Vulkan/GL/WebGL, скриншоты FPS/RTS/редактора,
конкуренция многопоточного загрузчика и визуальный паритет не
проверены. Точный SHA и следующее действие — в handoff Stage 103.

### Stage 104 — постоянный многопоточный импорт и стили выделения во View

Нативный `render::AsyncModelCpuQueue` теперь переиспользует 1–8 постоянных
рабочих потоков `std::thread` вместо запуска новой асинхронной задачи
для каждого файла модели. Он использует диспетчеризацию через condition variable, ограниченные
очереди ожидания/готовых результатов, инвалидацию по ревизии исходника и существующие
приоритеты Visual/Interactive/Background. Конфигурацией владеет хост:
читатель и кэш изображений на CPU должны быть реентерабельными; вся загрузка на GPU,
публикация исходников и состояние поз MotionWeave остаются в потоке-владельце
рендеринга. Изменение числа рабочих потоков дожидается выполняющихся задач;
не меняйте конфигурацию во время интерактивного кадра рендеринга.

Общая геометрия на GPU учитывается по идентичности страницы, а не по
числу анимаций или импортированных Model. API
`geometryPoolReferencedStats(device,modelPointers)` может принимать
модели от нескольких владельцев-хостов рендеринга в ОДНОЙ коллекции, избегая
двойного учёта страницы, на которую ссылается множество моделей или видов.
`ModelResourceCache::geometryPoolModelReferences` включает
текущие резидентные и выведенные на GPU модели. Глобальный для устройства
пул геометрии остаётся авторитетным владельцем ёмкости страниц, а
общие текстуры по-прежнему учитываются их владельцем — кэшем текстур.

У `aiverse::view::MeshObject` теперь есть не зависящие от жанра стили
`selectionOutline` / `selectionColor`. Отправки мешей при выделении/наведении
в `SceneRenderable` редактора и линии рёбер выделения
идут через `aiverse::View::submitMesh/submitLine`,
а устаревшая специфичная для рендерера реализация силуэта
сохранена внутри. Это не продвигает граф анимации и не добавляет
в MotionWeave игровые компоненты выделения.
Полный вывод `game::RtsView` из эксплуатации всё ещё не завершён.

**NOT RUN:** нативная сборка, CTest, GPU-тесты на настольных и мобильных устройствах, визуальный
паритет выделения в редакторе, санитайзер потоков CPU и проверки времени жизни
пула геометрии на GPU. См. handoff агента Stage 104.

### Stage 105 — GPU-ресурсы между хостами и универсальные пакеты авторских портретов

`render::RenderResourceOwnerGroup` — невладеющий агрегирующий
фасад над несколькими независимыми нативными хостами `ModelResourceCache`.
Группа вычисляет уникальное владение моделями и общими текстурами, включает
выведенные модели, ожидающие GPU fence, и устраняет дубликаты общих страниц
геометрии по их глобальной для устройства идентичности. Её статусы `Ready`,
`PendingGpuRetirement` и `DeviceUnhealthy` —
диагностика/политика допуска, а не разрешение досрочно освобождать ресурсы.
Ожидающая работа GPU — норма, а не ошибка. Оценки используют известную
исходную геометрию и метаданные текстур в эквиваленте RGBA8; никогда не называйте
их точной занятостью VRAM драйвером.

Нативный предпросмотр сырых моделей в редакторе теперь объединяет в группу основную сцену,
предпросмотр портрета и провайдер сырых исходников, с необязательным
оценочным бюджетом допуска для всей группы. Нарушение работоспособности GPU приостанавливает
публикацию новых моделей, сохраняя все выведенные на GPU модели живыми,
пока не удастся установить корректное завершение fence.

`game::Portrait::renderAppearance(const render::ModelDraw&,
RTSCamera,background)` — универсальный синхронный
внеэкранный потребитель, сохраняющий выбранное хостом переопределение материала,
сопоставление узлов и материалов, политику геометрии, командный оттенок, вариант
и любую предвычисленную позу. Портреты сырых моделей, с предвычисленной позой и
**статические** портреты, разрешённые RTS, делегируют ему. Сложные
анимированные портреты сохраняют существующий запасной путь совместимости RTS
и его единственный вычислитель графа MotionWeave; второго
плеера или продвижения анимации на стороне рендеринга не появляется.

**Проверка NOT RUN:** новые контракты CTest, нативный компилятор,
восстановление GPU fence/потери устройства, паритет скриншотов рендерера/портретов,
тесты FPS/RTS и санитайзеры потоков отложены
пользователем. Следуйте Stage 105 в handoff анимации.

### Stage 106 — истекающие ссылки на владельцев GPU и проверенные состояния отказа

Несколько нативных владельцев моделей/ресурсов можно наблюдать через
`render::RenderResourceOwnerGroup`. Её регистрации теперь несут
токены времени жизни кэшей `weak_ptr`, поэтому уничтоженный кэш
пропускается, а не используется. Группа по-прежнему
работает только в потоке-владельце устройства; слабая ссылка не делает
одновременное уничтожение GPU-ресурсов и снимок потокобезопасными.
Группа не владеет ресурсами рендеринга и не завершает их работу.

Вывод из эксплуатации на GPU теперь отличает обычный ожидающий fence
от реально неудавшегося токена завершения через
`gfx::Device::resourceRetirementStatus`. Неудачный пакет вывода Model
остаётся живым, даже если более новые токены сигнализируют
об успехе. Только успешный барьер полного простоя GPU всего устройства
разрешает очистку и `abandonRetirementTokenAfterIdle`.
`RenderResourceGroupStats::health` сообщает
`RetirementFenceFailed` отдельно от
`PendingGpuRetirement` и `DeviceUnhealthy`.
Эти статусы влияют только на допуск НОВЫХ ресурсов, но никогда
на авторитетный геймплей или существующие часы графов MotionWeave.

Фигура предпросмотра материала модели теперь делегирует внеэкранную отрисовку
тому же универсальному пути `Portrait::renderAppearance` +
`aiverse::View::submitModel`, что и нативные статические модели
и предвычисленные позы. Авторинг материалов по-прежнему идёт через
старый RTS-совместимый хост; запасной путь для динамической/сложной анимации
не удалён и сохраняет ровно один источник записи анимации.

**NOT RUN:** компиляция, CTest, тесты GPU/потери устройства,
скриншоты редактора, паритет FPS/RTS, санитайзер потоков и CI.
В handoff Stage 106 перечислены точные ссылки на исходники и следующий шаг.

### Stage 107 — владельцы устройства с областью действия, детерминированная трасса вывода из эксплуатации и независимый пакет авторского внешнего вида

Универсальный `render::ModelResourceCache` теперь явно привязывается к
одному `gfx::Device` и одному потоку-владельцу через
`bindResourceDevice(device)`. Изменение GPU-моделей с другого устройства или
из другого потока отклоняется. `RenderResourceOwnerGroup` поддерживает
`registerScoped(device,cache)`, возвращающий перемещаемую (move-only) регистрацию
с областью действия. Предпросмотр редактора использует такие регистрации,
а не оставляет указатели-наблюдатели на владельцев ресурсов в
неограниченном реестре. Владельцы ресурсов не переживают устройство,
а ModelResourceCache можно перепривязать только после успешного
GPU-безопасного завершения работы. Старый `add(cache)`, работающий только на CPU, сохранён для
существующих инструментов, но не является рекомендуемым путём с привязкой к устройству.

Новые подключаемые по желанию колбэки `RetirementDiagnosticEvent` в
очереди вывода ресурсов из эксплуатации и `RetirementStatusReplay`
с `script/issue/advance/status/events` позволяют детерминированно
синтезировать время токенов GPU и трассы ожидания/отказа/восстановления после простоя.
Синтетические результаты никогда не заменяют реальный GPU fence завершения и
не могут разрешать уничтожение GPU-ресурсов на оборудовании. Неудачные
маркеры удерживаются, пока реальный бэкенд не предоставит успешный
барьер полного простоя.

`engine/view/AppearancePacket.h` теперь отвечает за универсальную
композицию визуального пакета: переопределения материалов, назначение
материалов узлам, вариант, команда/оттенок, политика геометрии и необязательные
входы графа/параметров. Адаптер статического предпросмотра RTS отображает
свой типизированный выбор и авторское размещение в тот же
`view::AppearanceSpec`, а затем отправляет получившийся канонический
`view::Object`. Хост RTS по-прежнему выбирает тип, размещение,
библиотеку материалов и игровую политику; ни один заголовок RTS/FPS не попадает
в универсальный код View. Статический/предвычисленный внешний вид использует
`submitPrecomputedAppearance` и НЕ ДОЛЖЕН иметь прикреплённого графа.
Для внешнего вида с графом владеющий View должен вызвать
`update` ровно один раз, затем `submitOne`; не создавайте
второго источника записи MotionWeave.

**Проверка NOT RUN:** нативные сборки C++, все фикстуры CTest,
GPU Metal/Vulkan/GL, визуальный паритет редактора/портретов FPS/RTS,
санитайзеры и CI. Новые отложенные фикстуры и точный следующий
этап записаны в handoff Stage 107.

### Stage 108 — эпохи GPU-устройства, ограниченная диагностика и общий авторинг материалов/графов

Кэши моделей нативных хостов теперь поддерживают
`RenderDeviceLifetime::Lease` и
`ModelResourceCache::bindResourceDevice(device,lease)`, чтобы
различать пересозданные GPU, даже когда платформа переиспользует
тот же адрес `gfx::Device*`. `RenderResourceOwnerGroup`
поддерживает `registerScoped(lease,cache)` и отклоняет истёкшие
поколения. Хост должен выводить из эксплуатации эпоху устройства только
после безопасного завершения работы кэша GPU-моделей. Это НЕ восстановление после
потери устройства и не способ освободить ресурсы, выведенные по fence без
подтверждения.

`RetirementDiagnosticRing` хранит ограниченную невладеющую
историю событий вывода ресурсов из эксплуатации; редактор хранит
128 событий и сообщает об отброшенных/переполненных записях, не
удерживая никаких GPU-ресурсов. Диагностические колбэки не
меняют время жизни ресурсов или семантику завершения работы GPU.

Новый `engine/view/AppearanceAuthoringService.h` отделяет
наследование библиотек материалов и компиляцию неизменяемых графов
анимации от политики RTS. Он принимает JSON библиотеки,
колбэки загрузчика текстур и предупреждений, FileReader, модель,
операции/traits и необязательные именованные графы. И компиляция
внешнего вида типов в RtsLook, и компиляция управляющих
графов среды выполнения в RtsAnimate теперь используют этот универсальный
сервис. У существующих плееров поз/графов MotionWeave по-прежнему
один владелец; этот сервис лишь создаёт неизменяемые
программы и не вычисляет и не продвигает их.
Изменения авторинга не влияют на авторитетный игровой
тик, движение, сеть или сериализацию.

Оставшийся устаревший RtsView по-прежнему выбирает тип/оружие,

внешнего вида и реальный визуальный паритет остаются открытыми.
**NOT RUN**: нативный компилятор, CTest, проверка рендерера/GPU,
скриншоты FPS/RTS, санитайзер и CI.



## Повторный импорт исходной модели без потери совместимого воспроизведения (Stage 146)

`MotionWeaveSourceBridge::forgetForReimport(World&, sourceIds)`, доступный как `View::forgetSourcesForReimport(ids)`, — синхронное необязательное рукопожатие перед выводом из эксплуатации. Вызывайте его **до** уничтожения старой CPU Model/скомпилированного Graph; мост сначала захватывает именованное состояние графа и фазы клипов из действительного плеера представления, а затем забывает его ECS-сущность. Следующий `sync` может однократно использовать это зерно, если совпадают логический ID/поколение источника, точно скопированные имена/родители рига, явные **различные ненулевые** старая/новая эпохи публикации и отличающийся адрес Model. Старый указатель не сохраняется и не разыменовывается; старый адрес — лишь консервативная защита отклонения по значению. Запись ограничена 8192 источниками и истекает через 120 вызовов sync источников. Существующие API `forget` и `clear` намеренно отбрасывают непрерывность, что подходит для деспавна или сброса сессии.

Адаптер **не** владеет арендами CPU/GPU, не может восстановить уже уничтоженный Graph, не переносит root motion, авторские потоки событий, состояние IK/ragdoll/нативных решателей или игровой ECS и не должен выполняться во время диспетчеризации рабочих потоков анимации. Пути инвалидации Model и графов RTS подключены к нему; паритет FPS и редактора требует отдельного аудита. Нативный компилятор/CTest/проверка GPU **NOT RUN** для этого этапа, затрагивающего только исходники; см. [handoff Stage 146](agent-handoffs/animation-stage146-pre-retirement-playback-rebind-2026-11-19.md).



## Эпохи хоста и публикация только графа в Stage 147

Исходный устаревший путь RTS не заполнял `View::Object::animationModelGeneration`, хотя `ModelChoice` уже отслеживал ненулевую `view::ModelPublicationEpoch`. Теперь он передаёт настоящую опубликованную эпоху и использует для ускоренной универсальной анимации только стабильные упакованные ECS ID; в противном случае сохраняется устаревший путь. Зерно именованного воспроизведения перед выводом из эксплуатации дополнительно принимает перекомпиляцию **только графа** с той же неизменяемой Model и той же ненулевой эпохой, а не только публикацию новой Model с новой эпохой. Все варианты требуют точно неизменного логического поколения и скопированной иерархии рига; неоднозначные смешанные случаи адреса/эпохи перезапускаются, и старые Model/Graph никогда не переживают отсоединение. Нативные тесты и сквозной рендеринг по-прежнему **NOT RUN**; см. [Stage 147](agent-handoffs/animation-stage147-rts-publication-epoch-and-graph-rebind-2026-11-19.md).



## Stage 148 — универсальная замена только Graph в ECS и единственный владелец источника

Для любого хоста с существующим ECS-плеером Graph представления используйте `aiverse::motionweave::rebindAnimationPresentationGraph(world, entity, *immutableModel, nextGraph)` в потоке представления после завершения рабочих потоков, пока предыдущие CPU Model/Graph ещё доступны для чтения. Возвращает `AnimationGraphRebindResult {replaced, playbackCaptured}`. Новый скомпилированный Graph должен быть нацелен на ту же неизменяемую Model, что и текущий ассет. Помощник пытается сохранить совместимое именованное состояние/фазы клипов, при отказе безопасно откатывается к авторским значениям по умолчанию, немедленно инвалидирует старую позу скина и очищает устаревшие очереди montage и уведомлений графа; он никогда не затрагивает ECS симуляции и не вызывает второй вычислитель. Заменённый граф вычисляет только следующее обычное обновление MotionWeave.

Замена источника остаётся за `MotionWeaveSourceBridge::forgetForReimport`, а не за помощником для замены только графа. Отсоединённая замена графа с той же Model и той же ненулевой эпохой должна иметь отличную идентичность скомпилированного Graph (защита по целочисленному значению старого указателя, который никогда не разыменовывается); для другой Model требуется действительно продвинутая ненулевая эпоха публикации и другой адрес Model. Ядро всегда инвалидирует устаревшие позы при смене ассета источника, даже если следующий тик анимации пропускается.

Эталонные клиенты могут либо владеть независимым ECS-миром представления MotionWeave, либо использовать представление, которым владеет универсальный View; они никогда не должны вычислять ОДИН И ТОТ ЖЕ визуальный источник дважды. Физика, геймплей, сеть или жанровые действия, принадлежащие только хосту, адаптируются вне анимации. Панели предпросмотра редактора с собственным отдельным универсальным `render::AnimationGraphInstance` — это отдельные владельцы представления, а не кандидаты на дополнительный ECS-плеер. Подробности и фактические коммиты кода: [Stage 148](agent-handoffs/animation-stage148-genre-neutral-graph-rebind-native-owners-2026-11-19.md). **NOT RUN** нативная сборка/CTest/Metal/GL/Vulkan, текущий зелёный CI, санитайзер, бенчмарки.



## Stage 149 — безопасные ID источников, эпохи Model и инвалидация LOD рендеринга

Источник `MotionWeaveSourceBridge::sync(world,sources)` должен иметь **стабильный ненулевой** `sourceId`. Object в `View::update(objects,dt)`, которым владеет граф, с действительными Graph+Model также должен иметь долговечный `id!=0`; недопустимые входы отклоняются до шага анимации представления. Статическая геометрия и **безграфовые** пакеты с предвычисленной/запечённой позой могут оставаться анонимными, потому что View их не вычисляет. Хост не должен переиспользовать произвольные позиции в массиве отрисовки как идентичность между кадрами, повторными импортами или респавнами сущностей.

Чтобы перенести переносимое именованное воспроизведение при горячей перезагрузке, новой опубликованной `Model*` требуется `modelPublicationGeneration`, отличная от старой и ненулевая; та же Model с той же эпохой может сохранить совместимую фазу, когда меняется только скомпилированный Graph. В противном случае новый плеер безопасно перезапускается. `forgetForReimport` идемпотентен для повторяющихся ID в ОДНОМ диапазоне отсоединения, тогда как обычный `forget` отменяет любую сохранённую фазу. Оба API forget во View стирают гистерезис визуального LOD для отсоединённых ID источников. Кэшированное состояние выбранного LOD включает публикацию источника, адрес/эпоху визуальной Model, выбранный порог и число уровней и сбрасывается при изменении этих отслеживаемых ревизий (весь список LOD НЕ снимается полностью как отпечаток). Постоянные ID вложений по умолчанию включают эпоху Model источника; явные ID не меняются.

Никаких зависимостей от жанра/геймплея/сети не добавлено; на каждый источник по-прежнему приходится единственный вычислитель графа. Полная компиляция, CTest и проверки Metal/GLES/Vulkan во время выполнения **NOT RUN** в рамках согласованного процесса «сначала функциональность». См. [handoff Stage 149](agent-handoffs/animation-stage149-source-identity-lod-attachment-reimport-2026-11-19.md).



## Stage 150 — ревизии авторских визуальных LOD и неизменяемые привязки сокетов

Каждый `View::Object` по-прежнему использует ровно один источник записи графа/позы MotionWeave независимо от выбранного визуального LOD Model или вложений. Теперь View инвалидирует гистерезис, относящийся только к рендерингу, на основе ревизий полной авторской конфигурации LOD (адрес/эпоха Model всех уровней, порог и необязательная идентичность ретаргета/скомпилированного плана), а не только ранее выбранного уровня. Снимки для сравнения перестраиваются только при изменении раскладки и не содержат живого владения Model.

Универсальный нативный хост может скомпилировать именованное или индексированное вложение с помощью `aiverse::view::compileModelSocket(rig, epoch, socketName, socketIndex)` во время публикации ассета, а затем разделять этот неизменяемый `CompiledModelSocket` через добавленный `ModelAttachment::compiledSocket`. Учитывающий ревизии `composeAttachment` во View проверяет точный риг/эпоху/авторский селектор; истёкшие скомпилированные сокеты безопасно отклоняются и требуют перекомпиляции. Устаревшие нескомпилированные сокеты и вложения к корню остаются доступными. Хост владеет CPU Model/выводом GPU из эксплуатации и не должен изменять опубликованную Model на месте без новой эпохи. Ядро анимации не имеет зависимостей от FPS/RTS/RPG.

См. [handoff Stage 150](agent-handoffs/animation-stage150-complete-lod-signatures-compiled-sockets-2026-11-19.md). **NOT RUN:** компилятор, нативный CTest, текущий проходящий CI, реальная визуальная проверка Metal/Vulkan/GLES, санитайзеры или бенчмарки — в ожидании единого прохода проверки после завершения функциональности, о котором просил пользователь.



## Stage 151 — транзакция авторских привязок представления

Универсальный нативный проект теперь может использовать `AppearanceAssetRegistry::Asset::compilePresentationBindings`, чтобы скомпилировать целый набор планов ретаргета визуальных LOD Model и привязок сокетов относительно неизменяемых опубликованных снимков источника/визуала. Успешный `CompiledPresentationBindings::apply(View::Object&)` атомарно устанавливает конфигурацию после проверки эпохи Model источника и авторских селекторов сокетов. Недопустимый ввод сохраняет последний исправный кандидат; старые скомпилированные сокеты удаляются при полной замене, а не переносят незаметно неверные индексы костей через повторный импорт.

Это **только публикация/авторинг**, а не ещё один вычислитель анимации, система игровых действий, выделение RHI или правило конкретного хоста. Единственный владелец представления MotionWeave продолжает обновлять Graph источника, а универсальный View использует предкомпилированные LOD и сокеты для рендеринга. Ответственность за время жизни CPU Model/Graph/GPU-ресурсов остаётся за вызывающим кодом. Подробные API, точные коммиты кода и итоговые случаи проверки — в [handoff Stage 151](agent-handoffs/animation-stage151-transactional-presentation-authoring-2026-11-19.md). ## Stage 152 — владение опубликованным пакетом внешнего вида в нативных проектах

Опубликованный `AppearanceAssetRegistry::Asset` теперь может транзакционно построить целый `View::Object` с необязательными предкомпилированными привязками LOD/сокетов с помощью `packetWithBindings`. Сопоставление LOD по именам импортёра включается явно через `VisualLodRequest::matchByName` и проверяется обычным универсальным компилятором ретаргета; он никогда не угадывает индекс кости или карту морфов. Недопустимая привязка или эпоха Model оставляет предыдущий результат без изменений.

Эталонное нативное представление FPS использует этот общий путь опубликованных пакетов для реального рендеринга удалённых персонажей, но по-прежнему само владеет единственным графом анимации и вычисляет его в собственном ECS представления. Его пакет с предвычисленной/запечённой позой **очищает граф** перед передачей через `View::beginPreparedFrame`/submit, поэтому универсальный View не может вычислить его дважды. Жанровые решения остаются исключительно в клиенте. Предпросмотр редактора, специализированные ассеты хоста и полный реальный импорт дочерних моделей/наборов остаются частичными. См. [handoff Stage 152 и таблицу статуса](agent-handoffs/animation-stage152-native-appearance-packet-integration-2026-11-19.md). ## Stage 153 — импортированные вложения безопасно разделяют одного универсального владельца анимации

Не зависящий от жанра помощник `ImportedAttachmentAuthoring` в `engine/view/ImportedAttachmentAuthoring.h` делает доступными любому нативному проекту реальный импорт дочерних Model через `ModelAssetProvider`, публикацию статических `AppearanceAssetRegistry` и композицию скомпилированных сокетов. Его перемещаемый (move-only) `Prepared` удерживает опубликованные снимки внешнего вида источника/дочерних моделей и кратковременные аренды `ModelResourceCache::acquireModelRead` для источника, визуального LOD и дочерних Model до синхронной отправки рендеринга. Хост по-прежнему владеет барьерами GPU, выводом старых моделей из эксплуатации и сменой поколений источника.

Выбирайте `ViewEvaluates`, когда `View::update` — ЕДИНСТВЕННЫЙ владелец графа анимации, или `HostPrecomputed`, когда другой World представления уже вычислил Pose (граф его пакета рендеринга сбрасывается, чтобы не появился второй вычислитель). Ассеты анимированных дочерних Graph намеренно отклоняются *статическим* путём вложений и, если они анимированы, требуют независимых ID источников/обновлений. Текущие редакторы и эталонные клиенты ещё не подключены к импорту авторского набора дочерних моделей с помощью этого помощника; Stage 154 займётся этим отдельно. [Handoff Stage 153](agent-handoffs/animation-stage153-imported-child-attachments-read-leases-2026-11-19.md) содержит API, SHA исходников, матрицу готовности и список отложенных тестов. **NOT RUN:** нативная сборка C++/CTest/текущий зелёный CI, GPU Metal/Vulkan/GLES, санитайзеры и производительность.



## Stage 154 — реальный процесс работы с импортированными дочерними вложениями в ModelView

Переиспользуемый `ImportedAttachmentAuthoring` теперь вызывается нативным предпросмотром ассетов `aiverse_modelview`. Реальные файлы дочерних Model и родительская модель разделяют одного владельца `ModelAssetProvider`, опубликованные снимки Appearance дают материалы/эпохи, а скомпилированные именованные сокеты — размещение по костям. CLI `--attach child.glb@SocketName` и `--attachments-file config.json` подкреплены окном ImGui Attachments с добавлением, переключением, Detach, Rebuild и Save. Поток-владелец применяет правки между завершёнными кадрами, а кратковременные аренды чтения источника/дочерних моделей удерживаются до синхронного `View::submitOne`.

Существующий Animator в ModelView — единственный источник записи анимации; его уже вычисленная Pose передаётся универсальному View с `HostPrecomputed`, поэтому View не планирует лишний Graph MotionWeave. Это ещё не полный авторинг в AIVERSE Studio, и он не выполняет горячий повторный импорт изменённых на диске байтов дочерних моделей; GPU-кэш провайдера и отложенный вывод из эксплуатации остаются за хостом. ## Stage 155 — авторинг вложений в Studio, повторный импорт с изоляцией ресурсов

AIVERSE Studio теперь открывает отдельное окно авторинга `MotionWeave — Attachments` из панелей инструментов Modeling и Animation Graph/Rig. Оно использует тот же не зависящий от жанра компилятор Model и именованных сокетов `ImportedAttachmentAuthoring`, что и нативный ModelView, но имеет СОБСТВЕННЫЙ кэш, принадлежащий провайдеру, для реальных импортированных родительских/дочерних моделей. Оно никогда не импортирует игровые действия и не заимствует Model, которой напрямую владеет другая панель предпросмотра редактора; существующий GraphInstance редактора остаётся единственным источником записи анимации предпросмотра.

`Reimport & Publish` повторно читает исходники Model с диска в полностью отдельного подготовленного владельца GPU-ресурсов, прежде чем зафиксировать новый снимок. При ошибках сохраняется предыдущая опубликованная сессия ассетов; уничтожение старого провайдера ограничено полным барьером простоя GPU редактора. Это намеренно блокирующая, а не бесшовная/неблокирующая операция, и сейчас это **редактор раскладки файлов и проверки сокетов**, а не второй 3D-предпросмотр или живая операция со сценой/префабом. Дальнейшая визуальная интеграция, повторный импорт исходников в ModelView, авторинг ретаргета/морфов и проверка на бэкендах остаются в ожидании. ## Stage 156: реальный 3D-предпросмотр в Studio, отложенные поколения владельцев вложений

Окно авторинга вложений в AIVERSE Studio теперь владеет настоящим внеэкранным
вьюпортом родительской и дочерних моделей, используя не зависящий от жанра конвейер
`ImportedAttachmentAuthoring` и `View`, предназначенный только для рендеринга. Оно сэмплирует первый импортированный клип во
временную позу предпросмотра, компонует именованные сокеты костей из той же опубликованной
исходной Model и рисует, не создавая ещё одного владельца графа MotionWeave.

Новые поколения провайдеров источника/дочерних моделей могут публиковаться сразу после успешного
авторинга; предыдущие и неудачные черновые провайдеры удерживаются до безопасной
очистки при полном простое GPU по достижении порога ограниченной очереди/при завершении работы. Такие отложенные
владельцы уменьшают задержки при каждом повторном импорте, но по-прежнему требуют полного простоя для фактического
завершения работы провайдера и могут увеличить пиковое потребление памяти; не называйте это настоящим
выводом из эксплуатации на основе fence или без задержек. См.
[handoff Stage 156](agent-handoffs/animation-stage156-studio-attachment-preview-deferred-retirement-2026-11-20.md).
Реальная проверка C++/CTest/GPU/визуальная/санитайзеры/бенчмарки остаётся **NOT RUN**.



## Stage 157 — нативная горячая перезагрузка всего исходника без второго владельца анимации

Stage 157 добавляет пример в ModelView с **полной заменой поколения исходника на диске**, оставляя общий не зависящий от жанра код MotionWeave/AnimationGraph/ECS/View без изменений. Подготовленный нативный ModelAssetProvider владеет всеми заново импортированными родительскими и дочерними Model; хост создаёт новые Animator, привязанные к этим Model, и свежие скомпилированные сокеты относительно заново опубликованных снимков внешнего вида источника/дочерних моделей. Допустимые совместимые именованные клипы сохраняют нормализованную фазу через существующий API `Animator::seek`. Только после успешного завершения всех импортов/компиляций ModelView публикует новую сцену. Неудачные кандидаты удерживаются в GPU-безопасной очереди старых владельцев до окончательного завершения. Просмотрщик выдаёт предвычисленные позы через тот же универсальный конвейер View с единственным источником записи.

Элементы управления для пользователя: **Reload model files** в ModelView (полное новое поколение ассетов GPU/CPU), **Rebuild** только по кэшу, включаемый по желанию опрос `--watch-model-files` / **Watch source files**. Выведенные владельцы Animator/Model/вложений удерживаются до проверки полного простоя GPU при рекомендательном ограничении очереди в восемь элементов или при завершении работы; это не API асинхронного вывода из эксплуатации на основе GPU-токенов, и пиковое использование ресурсов может возрасти. 3D-предпросмотр Studio из Stage 156 остаётся отдельным. См. [handoff Stage 157](agent-handoffs/animation-stage157-modelview-atomic-model-file-reimport-2026-11-20.md). Нативный компилятор/CMake/CTest/GPU Metal-Vulkan-GLES/ASan-TSan/бенчмарки **NOT RUN** согласно запрошенному процессу «сначала функциональность».



## Stage 158 — универсальная авторская раскладка вложений, общая для Studio и ModelView

`view::AttachmentLayoutCodec` теперь предоставляет единый не зависящий от жанра формат документа вложений: путь к родителю, реальная импортированная статическая дочерняя Model/сокет/видимость и оба полных аффинных преобразования. Устаревший JSON (без матриц) использует единичное преобразование; недопустимые или неаффинные преобразования отклоняются транзакционно. И Studio, и нативный ModelView используют общий парсер/писатель и `ImportedAttachmentAuthoring::childFromLayout` для идентичного размещения во время выполнения. Studio поддерживает редактирование базисных осей 3x3 и смещений дочерних моделей; ModelView поддерживает позицию для каждого сокета и может открывать родителя прямо из сохранённого JSON. Для статических вложений родительский Animator остаётся единственным источником записи графа/позы.
 
Эти документы **готовы для будущей сериализации сцен/префабов**, но пока не связаны с созданием/уничтожением живых ECS-сущностей или игровыми сценами. Аудит GPU в Stage 158 также подтверждает, что настоящий вывод провайдеров из эксплуатации по завершению токенов не доделан: завершение работы существующего ModelResourceCache и отката изображений зависит от полного простоя GPU устройства; никакой произвольный токен не является достаточным доказательством, чтобы этого избежать. См. [handoff Stage 158](agent-handoffs/animation-stage158-universal-attachment-layout-transform-2026-11-20.md). Нативный компилятор/CTest, реальные Studio/ModelView/Metal-Vulkan-GLES, санитайзер и бенчмарки **NOT RUN**.


## Stage 159 — реальный мост между ECS представления и сценой/префабом вложений

`view::EcsAttachmentScene` даёт не зависящий от жанра мост от авторинга к среде выполнения: из JSON `AttachmentLayout` без указателей в реальные дочерние Entity **изолированного** `aiverse::World` **представления**. Родителем по-прежнему владеют извне; компоненты Root и Child записывают уникальную ревизию экземпляра, родительскую Entity с учётом поколения, опубликованную эпоху Model источника, порядок слотов, путь к Model, сокет и полные локальные/дочерние преобразования. `publish` компилирует сокеты всех опубликованных дочерних Model и проверяет аренды CPU ДО изменения структуры мира; замена удаляет только старые принадлежащие ему дочерние хэндлы. `restore` заново создаёт свежие дочерние Entity, `save` сохраняет только авторские данные, `forget` освобождает именно принадлежащих ему потомков, а `valid/prepare` безопасно отказывают на устаревших ECS-хэндлах. Рендерер по-прежнему использует ОДНУ вычисленную хостом позу родителя плюс существующую композицию статических вложений; дублирующего источника записи графа нет.

Studio теперь использует этот ECS World/мост напрямую в своём нативном 3D-предпросмотре вложений и подготовленном повторном импорте, а не только хранит простой скомпилированный вектор. Полная интеграция с SceneLoadCoordinator/игровыми сценами/активацией префабов всё ещё отсутствует, потому что `engine/scene` нет в этой разошедшейся ветке функциональности; изучите API агента соседней ветки сцен до интеграции. Анимированные дочерние графы, настоящее завершение работы ModelAssetProvider по GPU-токенам и продвинутый ретаргет морфов остаются открытыми. См. [handoff Stage 159](agent-handoffs/animation-stage159-presentation-ecs-attachment-prefab-restore-2026-11-20.md). Нативные C++/CTest/Metal-Vulkan-GLES/санитайзер/внедрение отказов **NOT RUN**.



## Stage 160 — стабильные ID потомков, не зависящие от источника, и владение сценой представления

Вложения AIVERSE теперь поддерживают необязательные явные стабильные ID дочерних элементов префаба в общем JSON-документе `AttachmentLayout` (<=128 символов, уникальные в пределах родителя); старые документы только с порядковыми номерами остаются допустимыми. Компонент ECS среды выполнения `SceneAttachmentChildComponent` записывает авторский ID, а `EcsAttachmentScene::resolveChild` при каждом поиске перепроверяет поколение/ревизию родителя и потомка вместо того, чтобы выдавать устаревший сохранённый индекс Entity.

`SceneAttachmentHost` отображает нативные `sceneId + prefabObjectKey` на независимые косметические экземпляры вложений в ECS представления. Он обрабатывает активацию, замену, удаление именно принадлежащих ему потомков, выгрузку целой сцены и экспорт по сценам без указателей; `prepare` по-прежнему возвращает безграфовый пакет позы HostPrecomputed и ModelReadLeases. Studio переиспользует этот адаптер для своего 3D-предпросмотра, а ModelView сохраняет стабильные ID при Save/Load JSON. Жанровый симулируемый ECS, урон и сеть остаются вне MotionWeave.

Проверенная интеграция с загрузчиком сцен соседней ветки `SceneLoadCoordinator::SpawnPrefab` (ветки `feature/scene-runtime-multiworld` / `feature/ecs-static-prefab-scene-integration`) по-прежнему требуется и НЕ реализована в этой ветке анимации. Независимые анимированные дочерние источники, настоящее завершение работы ModelAssetProvider по GPU-токенам и продвинутый ретаргет морфов остаются в ожидании. [Handoff Stage 160](agent-handoffs/animation-stage160-scene-attachment-host-stable-identity-2026-11-20.md) / [руководство по API хоста](scene-attachment-host.md). Нативный компилятор/CTest/Metal-Vulkan-GLES/ASan-TSan/производительность **NOT RUN**.



## Stage 161 — независимые графы MotionWeave дочерних элементов, один плеер на источник

Этот этап реализует не зависящий от жанра сервис `AnimatedSceneAttachmentSources` поверх существующих `MotionWeaveSourceBridge` и `stepAnimationPresentation`. Его собственный World представления владеет одним GraphInstance для КАЖДОЙ стабильной идентичности `scene/object/childId` анимированного потомка. Статические потомки остаются отрисовками скомпилированных сокетов с использованием уже вычисленной позы родителя; авторский потомок с `animated=true` исключается из этого статического пакета и требует опубликованного внешнего `animationGraph` и стабильного непустого `id` потомка. Все проверки Model/Graph/эпохи источника потомка и компиляция именованного сокета родителя выполняются до продвижения независимого вычислителя потомка.
 
Поза и матрицы костей родителя задают мировое преобразование независимого потомка; потомок даёт собственную вычисленную локальную Pose, а `View::Object.graph` в результате сбрасывается, чтобы универсальный View никогда не вычислил его второй раз. Реальный предпросмотр вложений в Studio импортирует/компилирует ассеты дочерних Graph и продвигает их один раз в предотрисовочном обновлении владельца перед безграфовой отправкой рендеринга. ModelView сохраняет поля авторинга, но пока не поддерживает независимый плеер потомка; он безопасно отказывает. Полная интеграция с нативным загрузчиком сцен, завершение работы провайдеров по токенам, продвинутый паритет морфов/LOD и реальное тестирование Metal/Vulkan/GLES/CMake/CTest/ASan-TSan остаются невыполненными. [Handoff Stage 161](agent-handoffs/animation-stage161-independent-animated-child-graph-sources-2026-11-20.md).
