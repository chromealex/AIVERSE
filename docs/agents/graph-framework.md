# Shared Studio graph authoring foundation

The framework is presentation infrastructure, not a graph runtime or a new persisted format. Native owners remain authoritative: Shader Graph compiler, SpectraFX, MotionWeave, modeling, navigation and gameplay graph systems. No graph evaluation in the WebView.

Stage 1 API:
- src/graphs/graphFramework.ts: GraphView, NodeView, Port, Link, GraphPolicy, GraphAdapter<T>, GraphRegistry<T>, validateTopology, DraftHistory<T>. Adapters project native documents and return immutable drafts. Use explicit cycle policy (state graphs may loop); native domain validation always decides whether a graph can be saved.
- src/graphs/GraphCanvas.tsx: shared layout canvas with pointer capture, inverse SVG coordinates, keyboard selection and movement, semantic Studio tokens. Canvas only emits select/move callbacks. No file writes.
- src/graphs/shaderAdapter.ts: material, postfx and particle domain registry, existing shader projection and movement. Shader panel uses the shared canvas; existing typed bridge and native compiler remain unchanged.

DraftHistory is a local immutable-reference utility, not yet wired into the shader panel or native Undo/Redo. Topology checks are advisory, not a substitute for native arity, schema or compiler checks. No claim of complete node wiring, graph inspector, debugger, profiler or migration. No new runtime library or CMake target.

Next: coordinate with Studio owner before migrating more panels; extract typed node catalog and port interaction, integrate draft history and inspector, then adapter-based native validation/save/preview for SpectraFX, MotionWeave and modeling. For other graph families use the actual owner schema; graph algorithms alone do not imply a node editor.

Tests: apps/studio-web npm run test:graphs, npm run typecheck, npm run build, native Mac visual verification. Existing graph operations are unchanged. See the stage handoff for real results.

## Stage 2 — shader authoring interactions

Shared canvas supports click output/input wiring callbacks, keyboard activation, zoom 50–200%, scroll navigation, and a single committed movement per pointer gesture. Shader-specific authoring operations filter the native catalog, preserve input slots, reject cycles and invalid arity, disconnect inputs, edit finite float4 constant/parameter values, duplicate nodes and maintain local draft history. The shader panel connects these operations and retains the native compiler/save bridge. Local Undo/Redo is reset on graph load, discard or save; it is not global project Undo. Workspace refresh updates catalog without deliberately resetting the loaded draft. Native external-writer conflict handling, shared inspector generalization, multi-selection, drag-to-pan, graph templates and other domain adapters remain pending. No runtime or visual verification claimed.

## Stage 3 — group editing

GraphCanvas supports modifier selection, marquee selection, rigid group movement, middle-button/Alt panning via scroll and zoom. Shader clipboard is local to the mounted panel, supports compatible same-domain graph drafts, remaps internal node links and leaves external links disconnected. The auto layout orders acyclic dependencies and rejects layouts outside existing bounds. Group edits enter draft history as one operation. No OS clipboard, cross-domain paste, generalized multi-output port model or native revision conflict handling yet. No execution or visual verification claim.

## Stage 4 — stable ports and commands

GraphCanvas now consumes GraphView directly. Independent input/output port IDs support multiple outputs, type labels, and preview wire geometry derived from current temporary node positions. Domain adapters still implement all connection mutations. Shader projection derives arity from native catalog and maps the native single output to value; incomplete links stay disconnected. Canvas-scoped commands support right-click Actions and Ctrl/Cmd C/V/D/A/Z/Shift-Z, Escape cancels pending connections. Existing shader output keys can be reassigned and a catalog-validated tint node group inserted without replacing existing outputs. Context actions use a toolbar strip rather than a floating pointer-position menu. Native graph templates, OS clipboard, external-writer revision safety and remaining adapters are still pending. No native API or format change; verification NOT RUN.

## Stage 5 — native graph adapters

The existing fx_graph and anim_graph ToolPanel instances offer a shared visual Graph view and retain a Native operations tab. SpectraFX uses its actual native list/get/catalog/edit/validate/set operations for existing v1/v2 assets, separate execution and named data ports, adding/deleting nodes, native property edits and disconnects. Save validates, checks a read-back baseline, then writes through native set; the baseline check is not atomic and concurrent writers remain a limitation. MotionWeave projects the pose DAG and state machine separately, allows earlier-node pose rewiring and explicit JSON editing of an existing node/state, validates and saves with the existing expected document CAS. State loops remain valid. Animation layout is local, not persisted. Draft history is local. No invented GPU preview, full animation inspector or graph execution; native owner remains authoritative. Use native operation tab for other operations. Actual Studio interaction and builds NOT RUN.

## Stage 6 — model source and state transitions

Modeling now has a shared visual graph view in its existing panel (native operations remain accessible). The adapter projects actual model part parent relationships and the existing embedded AnimationGraph pose/state definitions; it is not a new procedural geometry evaluator. Parent changes preserve local transform values and reject cycles. Entry JSON editing preserves IDs. Native modeling_validate is allowlisted; save uses the existing modeling_edit replace transaction with expectedRevision and native full build. Layout is local. MotionWeave adds visual state port connection with explicit unconditional default, initial-state choice, transition removal and fade/after editing; existing order and native compiler validation remain authoritative. Conditions remain editable through JSON. No new format, runtime, GPU preview or general geometry dataflow authoring. Tests and build NOT RUN.

## Stage 7 — geometry dependencies and typed animation inspector

ModelGraphPanel separates native CSG geometry dependencies from transform parenting. Geometry view projects actual preceding-node boolean operands a/b and the ordered native modifier stack. Users can reconnect mesh operands, select union/subtract/intersect, reorder existing modifiers, and edit the native JSON entry. Save remains a revision-checked full native model build through modeling_edit. No separate mesh evaluator, new file format, modifier graph runtime, or GPU preview. AnimationConditions and AnimationParameters are shared by standalone and embedded animation graphs: declared finite scalar/boolean defaults, AND conditions, comparison operators, thresholds, add/remove and native limits. Vector defaults remain JSON-only. The compiler remains authoritative for all domain constraints. Generator investigation: the inspected branch contains BuildingGen.h generateBuilding and GenOps map_generate/gen_presets; standalone cave/building graph docs at the probed paths were absent, not evidence that generators are absent elsewhere. Do not invent their graph interfaces; consult current owner branches. Tests NOT RUN.

## Stage 8 — owner recipe projections and model materials

Added geometry modifier creation/removal using documented native modifier schemas, and assignment of existing model-source materials by stable ID. All edits stay in the model draft and use the existing revision-checked native modeling transaction. These are model-local material definitions, not project PBR library texture embedding. Existing texture_patterns/texture_generate remain accessible in Modeling Native operations; no new texture runtime or automatic binding is claimed.

Added generatorProjections.ts for read-only owner-data views. TerraWeave's existing generator panel displays a recipe dependency diagram and retains its native preview/generate/forest controls. Building and Caverns projection functions are preparatory only and not connected to their native panels: owner branches are not merged in this feature branch. Building projection consumes persisted style/features/materialBindings; Caverns consumes native v1 snapshot, with a bounded display (64 stamps, 32 entrances) and no modification of the authoritative snapshot. Neither is a node-based generator/evaluator. No fabricated engine calls.
