AIVERSE SpectraFX#

SpectraFX — официальное название универсальной, не зависящей от жанра системы визуальных эффектов в AIVERSE. Её устройство вдохновлено процессом авторинга и событийной моделью Unreal Niagara, но это не копия кода, форматов ассетов или редактора Unreal. aiverse::spectra — пространство имён публичного C++ API.

Текущий объём (2026-11-18): фронтенд Graph v1, переиспользуемый CPU-бэкенд частиц, варианты графовых ассетов и горячая перезагрузка, а также необязательный адаптер ECS-представления только для чтения закоммичены. Базовый редактор графа v1 на холсте узлов и предпросмотр на CPU в памяти закоммичены, но не проверены; ограниченный прототип GPU-частиц на Metal закоммичен, но не проверен; полная интеграция GPU/CPU, поток данных в духе Niagara и автоматическая продакшн-интеграция в RTS/FPS не завершены. Тесты добавлены, но в среде разработки ещё не запускались. Точные SHA и статус проверки см. в docs/agent-handoffs/universal-niagara-vfx-2026-11-18.md.

Граница интеграции с PRISMA#

SpectraFX — НЕ движок постобработки. Ей принадлежат эмиттеры, симуляция частиц, FX-графы (VFX fx/graphs/*.vfx.json), FX-источники в ECS и кратковременные визуальные события. PRISMA в engine/render/Prisma.{h,cpp} отвечает за HDR-композит и тональную компрессию, bloom, глубину резкости, motion blur, временное сглаживание, экранное освещение и объёмы постобработки для камеры. FX-спрайты и меши записывают HDR сцены до PRISMA; полноэкранный домен Shader Graph postfx принадлежит PRISMA. Общий компилятор Shader Graph и RHI — разделяемая инфраструктура, а не вторая реализация VFX или постобработки.

Никогда не добавляйте полноэкранные эффекты кадра в engine/fx и никогда не добавляйте эмиттеры или жизненный цикл частиц в PRISMA. Сохраняемый блок postfx и MCP-команды postfx_* в PRISMA остаются стабильными для существующих проектов. См. таблицу владения в AGENTS.md и docs/prisma.md. Никакой автоматической живой привязки не подразумевается.

Архитектура#

Gameplay ECS (authoritative, deterministic)
  ├─ typed gameplay events ────────────────┐
  └─ data-only SpectraSourceComponent ──┐  │
                                       ▼  ▼
                               SpectraFX presentation
                               (read-only World + events)
                                       │
                          exposed graph parameters
                                       │
                graph assets fx/graphs/*.vfx.json
                                       │
                     compileGraph (versioned IR)
                                       │
                   existing fx::EffectDef schema
                                       │
                    CPU fx::ParticleSystem/RHI
                                       │
                         renderer + quality tiers

Future opt-in path: GPU simulation/backend + advanced Niagara dataflow nodes

Никаких жанрово-зависимых FX-движков. Турель в RTS, оружие в FPS, двигатель космического корабля или гоночный автомобиль используют один и тот же компонент источника и презентер событий. Игра-хост предоставляет только резолвер позы и сопоставляет свои ID событий с ассетами эффектов. Графическое состояние и хэндлы частиц никогда не попадают в детерминированное игровое состояние и контрольные суммы.

Публичные точки входа C++#

  • engine/fx/SpectraFX.h: aiverse::spectra::Runtime, Effect, Handle, GraphAssets, GraphLoadResult, compileGraph.
  • libraries/include/aiverselib/mechanics/SpectraFX.h: aiverse::spectra::SourceComponent, EventBinding, PresentationSystem.
  • AIVERSE::spectrafx: цель линковки CMake, псевдоним существующей aiverse_fx; старая цель остаётся рабочей для других агентов и проектов.

Создание графа#

Поместите этот файл в fx/graphs/engine_fire.vfx.json внутри проекта:

{
  "version": 1,
  "parameters": {
    "color": [[0, "#ffe8a0ff"], [1, "#ff330000"]]
  },
  "nodes": [
    {"id": "spawn", "type": "Spawn", "properties": {"rate": 24, "duration": 1, "loop": true}},
    {"id": "initialize", "type": "Initialize", "properties": {"life": 0.6, "speed": 1.0, "size": 0.4}},
    {"id": "update", "type": "Update", "properties": {"color": {"$param": "color"}}},
    {"id": "output", "type": "SpriteOutput", "properties": {"texture": "builtin:smoke"}}
  ],
  "links": [
    {"from": "spawn", "to": "initialize"},
    {"from": "initialize", "to": "update"},
    {"from": "update", "to": "output"}
  ],
  "outputs": ["output"]
}

Компилятор v1 принимает цепочки Spawn → Initialize → Update* → SpriteOutput|MeshOutput|RibbonOutput с разветвлением на выходы, но без слияния нескольких входов в одном узле. У каждого узла есть объект properties, ключи которого проверяются по engine/fx/FxEffect.h. Цепочка модулей компилируется в существующий fx::EffectDef — она не исполняет произвольные графовые инструкции для каждой частицы.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::Runtime particles;
particles.init(device); // The native host owns gfx::Device.
particles.setFileReader(readGameContent);
aiverse::spectra::GraphAssets assets(particles, readGameContent);

// Converts a versioned graph asset into a CPU particle effect.
auto flame = assets.load("engine_fire");
if (flame.effect >= 0)
    particles.play(flame.effect, {0.0f, 1.0f, 0.0f});

// Overrides produce independent graph variants:
auto cold = assets.load("engine_fire",
    aiverse::Json::parse(R"({"color":[[0,"#aaddffff"],[1,"#0044ff00"]]})"));

Цикл выполнения: вызывайте setView(camera, viewProj, width, height), update(dt), затем render(fog) после отрисовки сцены, пока её проход ещё открыт, как описано в engine/fx/ParticleSystem.h.

Необязательное нативное ECS-представление#

#include <aiverselib/mechanics/SpectraFX.h>
using namespace aiverse;

auto entity = world.create();
spectra::SourceComponent source;
source.effect = "graph:engine_fire:<hash>"; // Better: use GraphLoadResult::runtimeName.
source.killOnDetach = false;
world.add<spectra::SourceComponent>(entity, source);

spectra::PresentationSystem presenter(particles);
presenter.sync(world, [](const World& w, Entity e,
                         fx::float3& position, fx::float3& direction) {
    // Resolve the render transform using YOUR game's component types.
    // Do not hardcode FPS/RTS into SpectraFX.
    return gameResolveEffectPose(w, e, position, direction);
});

presenter.consumeTickEvents(tick, sim.events(),
    {{hitEventId, spectra::EventBinding{"impact_flash", 1_fx}}});

Для непрерывных графовых ассетов после GraphAssets::load используйте фактическое значение GraphLoadResult.runtimeName; реестр fx/graphs не инициализирует все графы автоматически при запуске игры. После отката или начала нового матча вызовите presenter.reset(), чтобы отбросить оставшиеся хэндлы представления и сбросить курсор показанного тика; состояние GPU/CPU-симуляции по-прежнему принадлежит хосту.

Совместимость#

Новые брендированные типы Spectra* введены без изменения идентичности старых псевдонимов Vfx*. Существующие fx/<effect>.json, fx/fx.json, aiverse_fx и compileVfxGraph остаются доступными. Файлы рантайма движка на время миграции остаются в engine/fx. Не удаляйте псевдонимы совместимости и не меняйте постоянные двоичные идентификаторы сохранений, пока нативные проекты не перейдут на новый API и не пройдут регрессионные тесты.

Авторинг графовых ассетов через MCP (этап 7)#

registerFxOps в editor-core также регистрирует универсальные операции fx_graph_* через apps/editor/core/SpectraGraphOps.cpp. Они доступны из GUI Workspace и из отдельного MCP-сервера независимо от игрового жанра проекта. Для проверки графов GPU-контекст редактора не нужен.

ОперацияВходные данныеРезультат
fx_graph_listнетВсе fx/graphs/*.vfx.json, диагностика компиляции для каждого файла
fx_graph_getnameJSON графа, исходный текст и результат проверки
fx_graph_validategraph, или text, или name, необязательно overridesСтрогие ошибки компилятора, число эмиттеров и текстуры; только чтение
fx_graph_setname, graph или textСоздание/обновление проверенного файла, уведомление Change::Fx
fx_graph_deletenameУдаляет только исходный ассет графа
fx_graph_bakename, effect, необязательно overrides, overwriteКомпилирует граф в fx/<effect>.json для существующего fx_preview и старого рантайма

Имена графов для совместимости с редактором ограничены строчными буквами, цифрами и подчёркиваниями (1–48 символов). Документ графа ограничен размером 1 МиБ. Неудачная компиляция возвращает ok:false и не перезаписывает предыдущий корректный граф; fx_graph_bake отказывается заменять существующий старый эффект, если явно не передан overwrite:true.

Пример последовательности действий через MCP:

fx_graph_set {"name":"engine_fire","graph":<graph v1 object>}
fx_graph_validate {"name":"engine_fire","overrides":{"color":[[0,"#ffffffff"],[1,"#ffffff00"]]}}
fx_graph_bake {"name":"engine_fire","effect":"engine_fire_cpu"}
fx_preview {"effect":"engine_fire_cpu","advance":1,"freeze":true}
view_screenshot {"window":"scene"}

Объём: запекание — это шаг материализации, совместимый с CPU, а не исполнение графа на GPU и не живая ссылка: повторное редактирование графа не обновляет уже запечённый эффект, пока его не запечь заново. У графов пока нет отдельного холста узлов в редакторе; это следующий этап авторинга. Старые fx/<name>.json, fx/fx.json и привязки событий RTS не затронуты. Новый тест vfx_graph_ops требует сборки aiverse_editor_core; тест закоммичен, но в среде, работающей только через коннектор, НЕ ЗАПУСКАЛСЯ.

Визуальный редактор графов SpectraFX (этап 8)#

В стандартном редакторе AIVERSE есть необязательное окно SpectraFX в группе Графика / Look, определённое в apps/editor/windows/SpectraGraphWindow.cpp. Его исходник автоматически попадает в сборку через CMake GLOB редактора apps/editor/windows/*.cpp.

  • Открывайте и создавайте fx/graphs/<name>.vfx.json прямо из проекта.
  • Добавляйте узлы типов Spawn, Initialize, Update, SpriteOutput, MeshOutput, RibbonOutput; перетаскивайте узлы и сдвигайте холст средней кнопкой мыши.
  • Чтобы создать связь, щёлкните по выходному пину исходного узла, затем по входному пину целевого; у входа может быть только одно входящее ребро. Циклы и недопустимые типы концов блокируются; незавершённые графы показывают ошибки компилятора, пока не будут соединены.
  • Выберите узел, чтобы редактировать его JSON properties. Редактируйте открытые parameters как JSON-объект; правки графа можно отменять и повторять.
  • Сохранение идёт через fx_graph_set; диагностика компиляции поступает от той же реализации spectra::compileGraph, что используется в рантайме.
  • Предпросмотр вызывает новую команду fx_graph_preview, доступную только в GUI: она компилирует graph в памяти, определяет временный эффект в Editor::gameFx_ и проигрывает его в Scene/Game. Временные FX-файлы не пишутся; снимки экрана по-прежнему работают через view_screenshot.

Узлы графа могут дополнительно содержать метаданные авторинга "position":[x,y] (две конечные ограниченные числовые координаты), которые проверяются компилятором v1, но игнорируются при построении эффекта на CPU. Существующие графовые ассеты без координат остаются корректными; редактор раскладывает их слева направо по умолчанию. Эти метаданные не попадают ни в состояние игровой ECS, ни в ресурсы шейдеров рантайма.

Это лишь базовый редактор v1, а не полное соответствие Niagara: нет произвольного типизированного потока данных, графов функций, исполнения на GPU compute, столкновений по глубине, связанного предпросмотра графов в поставляемых клиентах и полноценного UI модулей в стиле UE. В tests/vfx_graph_compiler_test.cpp добавлена проверка на уровне исходников для метаданных раскладки узлов; запуск GUI, взаимодействия перетаскивания и связывания, а также GPU-скриншоты в среде разработки через коннектор НЕ ЗАПУСКАЛИСЬ. Требуется ручная проверка.

Типизированные свойства модулей (этап 9 — исходники закоммичены, сборка ещё не проверена)#

engine/fx/SpectraModuleSchema.h предоставляет безголовый, не зависящий от жанра каталог распространённых полей графа v1. Канонический публичный заголовок engine/fx/SpectraFX.h подключает его, чтобы нативные проекты и редактор использовали одни и те же типы и границы значений.

#include "engine/fx/SpectraFX.h"

aiverse::Json node = aiverse::Json::parse(
    R"({"id":"emitter","type":"Spawn","properties":{"burst":8}})");
std::string error;
bool changed = aiverse::spectra::applyTypedField(
    node, "burst", aiverse::Json::number(int64_t(24)), error);
// Also available: fieldsForNode("Spawn"), fieldForNode(...),
// validateTypedField(...), removeTypedField(...).

В визуальном окне SpectraFX теперь есть раздел Типизированные модули над Расширенные свойства (JSON). Типизированный инспектор поддерживает свойства типов число, целое, логическое значение, строка, выбор из списка и трёхкомпонентный вектор. Сейчас его каталог включает:

СтадияРаспространённые поля
Spawnburst, rate, perMeter, delay, duration, loop
Initializelife, speed, size, direction, spread, shape, radius, gravity
Updatedrag, spin, rotation, speedLimit, stretch, velocity, hidden
SpriteOutputtexture, blend, align, fps

Все операции с типизированными полями — необязательные правки. Проверка отклоняет неверные типы, недопустимые значения перечислений и значения вне объявленных диапазонов, не изменяя исходный узел. Инспектор не приводит к скаляру MinMaxCurve, массив-диапазон, цветовой градиент, список мешей или вложенный модуль эффекта: такие поля остаются нетронутыми, и их нужно редактировать через расширенный JSON или существующие инструменты модулей частиц. Неизвестные свойства всегда сохраняются при обновлении одного типизированного поля. Последним авторитетом при проверке остаётся компилятор графа (parseEffect).

Это только метаданные авторинга, а не исполняемая программа узлов на GPU. Эти изменения требуют проверки нативной сборки и GUI; коммиты исходников и добавленные тесты не доказывают успешную сборку редактора. tests/vfx_graph_compiler_test.cpp содержит проверки схемы и контракта компиляции поверх уже существующей цели CTest SpectraFX.

Прототип GPU-частиц на Metal (этап 10 — исходники закоммичены, не проверено)#

Новый необязательный класс aiverse::spectra::ComputeParticles в engine/fx/SpectraGpuParticles.{h,cpp} исполняет ограниченное подмножество частиц-билбордов на compute-пути Metal RHI. Он не подключён к существующим клиентам RTS/FPS и не заменяет старый aiverse::fx::ParticleSystem. Это подмножество намеренно содержит единственный аддитивный эмиттер с мягкой текстурой и настраиваемыми числом частиц во вспышке, временем жизни, начальной скоростью, размером, гравитацией, линейным сопротивлением и альфой по времени жизни. Сложные атрибуты, шум, шлейфы, меш-частицы, столкновения, GPU-субэмиттеры, поток данных Niagara и пользовательские шейдерные графы остаются на существующем CPU-бэкенде эмиттеров, пока не будут реализованы отдельно.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::ComputeParticles particles;
aiverse::spectra::ComputeEmitterDesc params;
params.capacity = 1024;
params.burst = 16;
params.backend = aiverse::spectra::ComputePreference::Automatic;
params.quality = aiverse::fx::FxQuality::High;

// Initialization can occur outside a frame. Device may be nullptr for
// pure CPU/headless tests; RequireGpu fails if compute is unavailable.
if (!particles.init(device, params)) {
    // inspect particles.reason()
}

// Presentation frame, AFTER Device::beginFrame, BEFORE scene render pass:
particles.setView(camera, viewProjection, width, height);
particles.burstAt({0,2,0}, {0,1,0}, {1,0.5f,0.1f,1});
if (!particles.step(1.f/60)) {
    // RHI timing/encoder order error; inspect particles.reason()
}

// During the scene's existing still-open depth-tested render pass:
particles.draw();
// After the render pass: Device::endPass, Device::endFrame.
// Before destroying gfx::Device: particles.shutdown().

Чистая безголовая политика chooseComputeBackend(backend, supportsCompute, preference) выбирает GPU-путь только для Metal с поддержкой compute. CpuOnly принудительно выбирает CPU; Automatic и PreferGpu откатываются на CPU при неподдерживаемом RHI или неудачном создании конвейера; RequireGpu отклоняет неподдерживаемые устройства, а не молча работает на CPU. Конфигурации GPU с низким качеством намеренно выбирают CPU, соблюдая существующее поведение качества частиц. Вызовы compute в RHI должны выполняться вне проходов отрисовки и внутри GPU-кадра. Вызывающая сторона отвечает за единственного владельца представления/поток устройства и за очистку до уничтожения устройства; этот модуль не содержит игровой ECS или состояния детерминированного симулятора.

Реализация на Metal: три compute-прохода за кадр представления (очередь принятых рождений → интегрирование возраста/скорости/позиции → разворачивание вершин квадов, обращённых к камере). GPU-буферы постоянные: 64 байта на частицу для состояний и сидов, 4-байтовый индекс слота и 40 байт на вершину билборда. Compute-шейдер пишет вершинный буфер, который напрямую читается обычным вершинным шейдером частиц RHI; в обычных кадрах позиции с GPU обратно на CPU не читаются. Пул рисуется одним аддитивным вызовом с тестом глубины. Текущий прототип рисует весь ограниченный массив индексов слотов (мёртвые слоты дают вырожденные квады); это не уплотнённый и не GPU-indirect рендерер. Максимальный пул — 4096 слотов, не более 64 рождений за вызов.

Исходник на GLSL приложен для будущего compute на Vulkan, но gfx::Device::supportsCompute для Vulkan в текущем RHI не реализован. GLES3/GL33/WebGL2 не запускают compute-ядро, поэтому вместо него используется существующий CPU-рендерер частиц. Не заявляйте эти платформы как поддерживающие GPU. Отдельный тест tests/vfx_gpu_backend_test.cpp проверяет политику выбора, границы, выпуск частиц при безголовом откате на CPU и время жизни. Он также содержит записывающий мок Metal RHI, который проверяет порядок диспетчеризации spawn→integrate→expand и последовательность команд прохода отрисовки без компиляции и запуска настоящих GPU-шейдеров. Это не интеграционный тест Metal GPU. По-прежнему нужны CI и проверка на нативном GPU.

Известные ограничения: нет уплотнения на GPU, нет отсечения по камере и LOD для отрисовки отдельных частиц, нет мягкого пересечения GPU-частиц, нет отрисовки мешей и лент на GPU, нет продвинутых графов эмиттеров, нет планировщика эффектов между CPU и GPU, нет автоматической миграции рантайма FPS/RTS и нет замеров производительности GPU. Автоматическая маршрутизация графа на бэкенд (этап 11 — исходники закоммичены, не проверено)#

engine/fx/SpectraGraphRuntime.{h,cpp} вводит новый необязательный, не зависящий от жанра aiverse::spectra::GraphRuntime. Он компилирует графовый ассет v1 или принимает заранее скомпилированный fx::EffectDef и решает, может ли тот без потери смысла исполняться на существующем compute-прототипе Metal. Каждый неподдерживаемый граф исполняется с точно тем же полным EffectDef в fx::ParticleSystem; сложные модули никогда не урезаются, чтобы уместиться на GPU.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::GraphRuntime runner;
aiverse::spectra::GraphRuntimeOptions options;
options.preference = aiverse::spectra::ComputePreference::Automatic;
options.quality = aiverse::fx::FxQuality::High;
options.capacity = 1024;

if (!runner.initGraph(device, graphJson, aiverse::Json::object(), options)) {
    // runner.reason() and runner.errors() describe the rejection
}

// After Device::beginFrame, before the scene render pass:
runner.setView(camera, viewProj, width, height);
runner.burstAt({0, 1, 0}, {0, 1, 0});
runner.step(1.f / 60.f);

// While the scene pass is open:
runner.draw(fog);
// On match change/rollback: runner.clear() outside an active encoder.
// Before device shutdown: runner.shutdown().

Валидатор схемы inspectGraphGpuEligibility(effect, options) не требует GPU и безопасен для нативных модулей, безголовых тестов и инструментов редактора. Он возвращает GraphGpuEligibility { eligible, gpu, reason }. GPU v1 разрешён только для одного аддитивного точечного эмиттера builtin:soft, выровненного по камере, с одной вспышкой из 1–64 частиц, постоянными скоростью/временем жизни/размером/сопротивлением, нулевым разбросом, гравитацией по мировой оси Y и цветовой шкалой по умолчанию от белого к прозрачному. Текущий прототип поддерживает только такую нагрузку. Пользовательские цвета и градиенты, несколько эмиттеров, случайные диапазоны и кривые, пользовательские шейдерные графы, шлейфы и ленты, шум, силовые поля, субэмиттеры, источники света, столкновения, анимация текстур или любой другой неподдерживаемый модуль принудительно переводят эффект целиком на CPU. Валидатор сравнивает нормализованные полные определения эффектов с известным поддерживаемым шаблоном и дополнительно явно проверяет чувствительные неподдерживаемые модули и цветовые ключи.

ComputePreference::RequireGpu завершается неудачей, если граф не подходит, реальное устройство не предоставляет Metal compute, уровень качества слишком низок или шейдер/конвейер не удаётся инициализировать. Automatic и PreferGpu вместо этого используют неизменённый CPU-ассет. CpuOnly никогда не пытается использовать GPU. Сбой работоспособности GPU внутри ComputeParticles может затем откатиться на его ограниченный CPU-эквивалент; GraphRuntime продолжает владеть этим экземпляром и сообщает фактический бэкенд.

Ответы редактора и MCP fx_graph_validate, fx_graph_get, fx_graph_list после успешной компиляции теперь содержат metalGpuEligible и metalGpuReason. Это лишь диагностика возможностей ассета, а не доказательство наличия Metal или успешного исполнения на GPU. Визуальный редактор SpectraFX показывает тот же вердикт под инспектором свойств; его предпросмотр графа в памяти по-прежнему использует проверенный CPU-рендерер.

Важные границы: это необязательный нативный API. Он не подключается автоматически ни к существующим FPS, RTS, игровому режиму редактора, авторитетному состоянию ECS, файловым ассетам, ни к текущим протоколам сохранения. Существующий продакшн-рендерер клиента остаётся на CPU. Реальная отрисовка на GPU Apple Silicon, компиляция MSL, несколько кадров в полёте и все регрессионные тесты остаются непроверенными, пока не будут запущены в реальном чекауте.

Тесты в исходниках: tests/vfx_graph_runtime_test.cpp проверяет поддерживаемый граф, строгие отказы и откат на CPU; tests/vfx_graph_ops_test.cpp проверяет MCP-диагностику пригодности. Имя в CTest: vfx_graph_runtime (метка SpectraFX).

Укрепление жизненного цикла Metal и разреженного диапазона отрисовки (этап 12 — исходники закоммичены, не проверено)#

Необязательный бэкенд Metal в ComputeParticles теперь отслеживает занятый префикс слотов, а не всегда обновляет и рисует все выделенные слоты. Учёт возраста слотов, принадлежащий CPU, определяет наибольший индекс живого в данный момент слота; compute-интегрирование и разворачивание квадов выполняются по этому префиксу, а индексированная отрисовка ограничена submittedSlots * 6. Пул без живых частиц и без ожидающих рождений не выполняет ни compute-диспетчеризации, ни отрисовки.

Это не уплотнение на GPU: промежутки между активными слотами по-прежнему дают вырожденные квады. Настоящее уплотнение потока на GPU, префиксные суммы, счётчики indirect-отрисовки и тысячи материалов — последующие этапы. Жёсткий предел в 4096 слотов и исходный формат буферов RHI сохраняются.

ComputeStats теперь предоставляет:

  • submittedSlots: длина префикса, фактически отправленного в последней GPU-отрисовке (может превышать alive при наличии дыр).
  • gpuFallbacks: автоматические переходы на CPU во время работы.
  • lostOnFallback: число частиц, находившихся на GPU и отброшенных, когда GPU-устройство стало неработоспособным. Существующая статистика сохраняется.

Событие потери устройства во время работы — не бесшовный шаг анимации: ComputeParticles::step сообщает о сбое. Для RequireGpu эмиттер становится недоступным, сохраняет идентичность бэкенда Metal до завершения работы и не переключается на CPU. Для Automatic и PreferGpu класс пытается инициализировать CPU-эмиттер, записывает число отброшенных GPU-частиц и возвращает false для кадра перехода. CPU-отрисовка на устройстве, помеченном как неработоспособное, не гарантируется; может потребоваться реальное пересоздание графического устройства. Ошибки порядка кодировщиков RHI по-прежнему возвращают сбой без молчаливой смены бэкенда.

GraphRuntime::step теперь передаёт наружу фактическую готовность, бэкенд и сообщение об ошибке вложенного GPU/CPU-рантайма. GraphRuntime::gpuActive также проверяет внутренний compute-эмиттер, исключая ложноположительные отчёты об успехе после потери устройства при RequireGpu. При очистке сбрасываются разреженный диапазон и счётчики GPU-слотов; попытка вызвать clear внутри активного GPU-кодировщика оставляет состояние нетронутым и выдаёт диагностику.

Записывающий тест RHI tests/vfx_gpu_backend_test.cpp содержит сценарии защиты clear от активного кодировщика, разреженного диапазона отрисовки, нулевой диспетчеризации для пустого пула, потери GPU при RequireGpu, перехода GPU→CPU с явной телеметрией потерянных частиц и поочерёдного истечения жизни частиц на протяжении нескольких кадров. Это тесты команд хоста на моках, а не реальное исполнение MSL.

Отдельный workflow .github/workflows/spectrafx-validation.yml даёт проверки для pull request и ручного запуска: сборку на Linux/macOS и безголовый CTest для SpectraFX; на Linux дополнительно собирается редактор и тестируются MCP-операции с графами. Этот workflow не проверяет реальный compute-шейдер Metal и корректность изображения на GPU. Фактическая компиляция, результаты CI, отрисовка на Apple Silicon, скриншоты и замеры производительности остаются НЕ ПРОВЕРЕНЫ, пока не будут выполнены.

Плотный сбор билбордов (этап 13 — исходники закоммичены, проверка на GPU ожидается)#

Необязательный бэкенд Metal spectra::ComputeParticles теперь собирает только живые физические слоты частиц в непрерывные вершины билбордов на GPU. Постоянный пул состояний частиц по-прежнему использует стабильные индексы для рождения и повторного использования; один дополнительный буфер хранения по 4 байта на слот отображает плотный порядковый номер отрисовки → физический слот состояния. CPU уже владеет учётом времени жизни и слотов и публикует список живых индексов на GPU до запуска compute-кодировщика. GPU читает позицию, скорость и оттенок каждой выбранной частицы из её собственного резидентного буфера состояний и пишет непрерывный блок из четырёх вершин. Состояние движения никогда не читается обратно на CPU.

Порядок кадра такой: загрузить новые состояния частиц и индексы слотов → загрузить текущую карту живых слотов → compute-рождения → интегрировать диапазон физических слотов, живых до шага → на GPU собрать и развернуть ровно те частицы, что остались живы после шага → обычная индексированная отрисовка RHI на alive * 6 индексов. Compute-ядро использует слот 4 для буфера живых индексов и Uniforms.meta.w для числа живых; исходники MSL и будущего GLSL используют одну и ту же раскладку. Обновления на GPU остаются между beginFrame и beginPass; отрисовка остаётся внутри прохода отрисовки сцены.

ComputeStats::submittedSlots теперь равно плотно выпущенному числу живых частиц (а не максимальному индексу физического слота). Например, после того как слоты 0–2 истекли, а слоты 3–5 выжили, GPU получает [3,4,5] и отправляет 18 индексов, а не 36. Регрессия на записывающем RHI проверяет эту карту и число отрисовываемых индексов на протяжении кадров с поочерёдными рождениями и смертями. Новая загрузка живых слотов занимает 4 * alive байт в каждом активном кадре и учитывается в ComputeStats::uploadedBytes. Простаивающий пул частиц по-прежнему пропускает compute и отрисовку.

Объём и ограничения: это сбор вершин на GPU по списку живых слотов, поддерживаемому CPU. Он исключает отрисовку разреженных мёртвых слотов, но это не полностью резидентное на GPU уплотнение через атомики и префиксные суммы и не indirect-отрисовка, сформированная на GPU. CPU по-прежнему просматривает до 4096 записей возраста за кадр, а загрузка живых индексов расходует пропускную способность. Фиксированный 16-битный индексный буфер по-прежнему ограничивает пул 4096 билбордами. Бэкенд ограничен аддитивными мягкими спрайтами, допустимыми для GraphRuntime, и по умолчанию не включён в существующих клиентах RTS/FPS. Компиляция шейдеров Metal, вывод изображения и производительность на Apple Silicon остаются НЕ ПРОВЕРЕНЫ, пока не завершатся нативные CI- и аппаратные тесты. Пути RHI, отличные от Metal, продолжают использовать исходный CPU ParticleSystem.

Экспериментальная отрисовка частиц, сформированная на GPU (этап 14)#

Подмножество Metal теперь имеет явно включаемый режим уплотнения и отрисовки на стороне GPU, использующий существующие необязательные методы RHI. Это не меняет бэкенд по умолчанию и не затрагивает существующие рантаймы FPS/RTS:

Контракт RHI и compute-проходы#

Переносимый gfx::Device получает запрос возможности supportsGpuAuthoredIndirectDraw(), по умолчанию возвращающий false. Metal сообщает о поддержке через свой существующий простой путь drawIndexedGpuIndirect, независимо от экспериментальных возможностей ICB. Vulkan/GL/GLES/WebGL по-прежнему возвращают false. Устройства, объявляющего только supportsCompute(), недостаточно.

Compute на Metal использует два дополнительных постоянных буфера хранения: aliveCounter (4-байтовый атомарный uint, compute-слот 5) и gpuDrawArgs (20-байтовый gfx::DrawIndexedIndirectCommand, слот 6). Существующие форматы ParticleState и 40-байтовой развёрнутой вершины не изменились.

Mode 3  reset GPU alive counter
Mode 0  spawn into persistent physical GPU particle slots
Mode 1  integrate physical state / kill expired particles
Mode 4  atomic-fetch-add surviving particle -> dense vertex ordinal
Mode 5  write GPU indexed draw args (indexCount = alive * 6)
Render  gfx::Device::drawIndexedGpuIndirect(gpuDrawArgs, 0)

RHI Metal вставляет барьер памяти буфера после каждой compute-диспетчеризации, а графическая отправка происходит в следующем кодировщике отрисовки. Порядок выживших частиц недетерминирован (атомарное выделение), что допустимо только для текущего подмножества аддитивных билбордов. Счётчик GPU и аргументы отрисовки при обычном рендеринге не читаются обратно на CPU.

Если gpuIndirect=true, но у устройства нет supportsGpuAuthoredIndirectDraw(), SpectraFX сохраняет плотный сбор слотов этапа 13, публикуемый CPU, с обычным drawIndexed. Если уже включённая indirect-команда отклоняется во время отрисовки, сообщается ошибка и отрисовка пропускается, вместо того чтобы рисовать, возможно, неинициализированные или устаревшие вершины с приблизительным числом от CPU.

ComputeParticles::gpuIndirectActive() сообщает фактический выбор; ComputeStats::gpuCompactDispatches и gpuIndirectDraws отслеживают отправленные GPU-операции. Когда indirect активен, stats().submittedSlots и stats().alive — это оценки времени жизни на стороне хоста, а не измерения, прочитанные с GPU. Фактическое число индексов берётся из 20-байтовой команды, сформированной на GPU.

Что остаётся на CPU#

GPU indirect устраняет ежекадровую загрузку карты живых слотов, а уплотнение на GPU и вычисление числа отрисовываемых элементов больше не зависят от этой карты. CPU по-прежнему владеет выделением слотов и учётом времени жизни и списка свободных слотов и просматривает не более 4096 записей возраста. Движение и генерация плотных квадов остаются на стороне GPU. Это не аллокатор только на GPU, не планировщик нескольких эмиттеров, не система сортировки и не полная симуляция Niagara.

Пакетирование материалов между экземплярами (этап 14B — исходники закоммичены, не проверено)#

Раньше несколько экземпляров GraphRuntime владели отдельными объектами fx::ParticleSystem и каждый мог отправлять один и тот же спрайтовый материал отдельным вызовом отрисовки на GPU. Необязательный spectra::BatchWorld (engine/fx/SpectraBatchWorld.{h,cpp}) помещает произвольные определения графов и эффектов в одну общую ParticleSystem представления. Это повторно использует существующий глобальный ParticleSystem::Impl::batchFor и очередь рендеринга FxRender.cpp, которая уже группирует частицы независимо от ID эффектов и экземпляров.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::BatchWorld shared;
shared.init(device, aiverse::fx::FxQuality::High);

aiverse::spectra::GraphRuntime smoke, fire;
// smokeJson and fireJson may represent different effects/parameters.
smoke.initGraph(shared, smokeJson);
fire.initGraph(shared, fireJson);

// Each GraphRuntime keeps its OWN handles; no CPU renderer per source.
smoke.burstAt({0,1,0});
fire.burstAt({2,1,0});

// ONCE PER FRAME (not once per GraphRuntime):
shared.setView(camera, viewProjection, width, height);
shared.update(dt);
// INSIDE the existing scene render pass, ONCE:
shared.draw(fog);

// Kill smoke's particles without affecting fire:
smoke.clear();
// Full scene/match reset: shared.clear().
smoke.shutdown();
fire.shutdown();
shared.shutdown(); // MUST outlive all attached GraphRuntime instances.

BatchWorld::defineEffect кэширует эквивалентные полностью сериализованные определения эффектов, сохраняя различающиеся данные эмиттеров. defineGraph компилирует JSON v1 каноническим компилятором и регистрирует его эффект в том же мире. play, move, stop, kill и playing — операции над хэндлами нижележащей ParticleSystem. Вызывающая сторона может задать загрузчики текстур и мешей в общем мире до регистрации эффектов, получать stats(), вызывать collectLights и пользоваться его существующим глобальным бюджетом качества. Эти API не зависят от FPS, RTS или какого-либо конкретного игрового модуля и живут вне авторитетного состояния ECS и отката.

Ключ пакетирования отрисовки: фактический нижележащий хэндл текстуры или атласа RHI, режим смешивания, идентичность скомпилированного шейдерного графа и вид примитива (меш или квад). Эффекты с разными анимациями, размерами, экземплярами или параметрами рождения могут использовать один вызов отрисовки, если эти требования к состоянию рендеринга совпадают. Даже разные спрайты в одном атласе могут пакетироваться, поскольку их UV независимо закодированы в вершинных данных. Одна и та же текстура с разным альфа/аддитивным смешиванием или шейдерным графом НЕ должна пакетироваться. Вызов отрисовки разбивается на пределе 16-битных индексов в 16 384 квада. Сортировка альфы по-прежнему следует существующим правилам упорядочивания текущего рендерера; единая глобально отсортированная очередь прозрачной отрисовки по разным текстурам — отдельная архитектурная задача.

GraphRuntime::initGraph(BatchWorld&, ...) и initEffect(BatchWorld&, ...) явно подключают экземпляр к этому общему рендереру. Его burstAt запоминает хэндлы, а clear()/shutdown() уничтожают только эти хэндлы, а не все частицы мира. Список хэндлов источника ограничен 65 536 элементами: самый старый хэндл уничтожается до переполнения предела. В общем режиме step, setView и draw отдельных источников ничего не делают, чтобы предотвратить двойные обновления и дублирующие вызовы отрисовки. Хост должен вызывать методы общего мира один раз за кадр. RequireGpu отклоняется при регистрации в общем мире, а не молча понижается; текущее объединение рассчитано на зрелый путь эмиттеров с симуляцией на CPU и отрисовкой через RHI.

Существующие игровые приложения: клиенты RTS/FPS уже используют одну центральную ParticleSystem и получают выгоду от её встроенного пакетирования. Эта возможность предназначена для новых нативных и графовых контекстов экземпляров, которые раньше создавали отдельные рендереры. Она не переопределяет отдельные экземпляры GPU ComputeParticles. Общие пулы GPU-частиц Metal для нескольких независимых эффектов по-прежнему требуют отдельного GPU-планировщика нескольких эмиттеров и реальной проверки на устройстве.

Регрессионный исходник: tests/vfx_shared_batch_world_test.cpp записывает индексированные вызовы отрисовки RHI и проверяет, что 5 + 7 частиц из разных определений эффектов, использующих одну текстуру атласа, дают один вызов отрисовки. Разные режимы смешивания дают два вызова. Также проверяются независимая очистка источников, регистрация графов, дедупликация и отсутствие случайных обновлений отдельных источников. CTest: vfx_shared_batch_world, цель aiverse_vfx_shared_batch_tests, метка SpectraFX. Профильный CI workflow собирает этот тест на Linux и macOS; фактические результаты CI/CTest в этой сессии остаются непроверенными.

Планирование сигналов без привязки к жанру и мост ECS-источников (этап 15)#

Необязательный spectra::CueScheduler в engine/fx/SpectraCueScheduler.{h,cpp} координирует множество независимых источников событий и прикреплённых эффектов поверх уже существующего BatchWorld. Он не создаёт ещё одну ParticleSystem и сам не вызывает update/draw; хост представления, которому он принадлежит, по-прежнему вызывает BatchWorld один раз за кадр. Всё планирование и хэндлы частиц остаются вне игровой ECS, детерминированных хэшей и состояния отката.

Используйте канонический заголовок engine/fx/SpectraFX.h для чистого API представления или <aiverselib/mechanics/SpectraFX.h> в нативных ECS-проектах, чтобы также получить доступ к syncEcsCueSources и acceptSimCueTick. ECS-адаптер переиспользует SpectraSourceComponent (без нового типа или ID ECS-компонента). Хост предоставляет тот же универсальный резолвер позы для рендеринга, что и существующий SpectraPresentationSystem. Ключи источников используют Entity::packed(), поэтому переиспользованные индексы с новыми поколениями не могут переиспользовать старый хэндл эффекта.

#include <aiverselib/mechanics/SpectraFX.h>

// BatchWorld and CueScheduler must outlive each other's handles in this
// order: shared BatchWorld initialized first, CueScheduler destroyed first.
aiverse::spectra::BatchWorld shared;
shared.init(device, aiverse::fx::FxQuality::High);
aiverse::spectra::CueBudgets limits;
limits.maxQueued = 512;
limits.maxPerTick = 64;
limits.maxPerFrame = 128;
limits.maxAttachments = 1024;
limits.maxTrackedOneShots = 2048;
aiverse::spectra::CueScheduler cues(shared, limits);

cues.registerEffect("impact", impactEffectDef); // or registerGraph(...)
cues.registerEffect("engine_fire", loopingEffectDef);
cues.bindCue(72, "impact"); // game-defined event type, not an FPS/RTS enum

// On the presentation thread, after a committed gameplay tick:
aiverse::spectra::acceptSimCueTick(cues, tick, simEvents);

// ONCE per presentation frame, with graphics Device in a valid frame:
shared.setView(camera, viewProj, width, height);
aiverse::spectra::syncEcsCueSources(world, cues, resolvePose);
cues.flush();          // deferred one-shots, bounded per frame
shared.update(dt);     // exactly once for ALL sources
// With the scene render pass open:
shared.draw(fog);      // exactly once, batches compatible materials

// Before replaying restored ticks after rollback/new match:
cues.resetForRollback();  // kills only this scheduler's cues/sources
// Do not call shared.clear() unless resetting ALL other presentation owners.
// Destroy cues BEFORE shared.shutdown()/gfx::Device destruction.

Бюджеты и правила владения#

CueBudgets ограничивает число ожидающих событий, допуски за тик, запуски одноразовых эффектов за кадр, одновременные ECS-прикрепления и кольцо хэндлов одноразовых эффектов, отслеживаемых для отката. Входные значения ограничиваются безопасными жёсткими потолками; ёмкость отслеживаемых одноразовых эффектов не может быть нулевой. CueScheduler::acceptTick(tick, events) игнорирует повторяющиеся или убывающие тики до вызова resetForRollback(), но не продвигает нижележащий рендерер частиц. flush() запускает эффекты в пределах бюджета кадра и оставляет остаток ограниченной очереди на последующие кадры. Очередь хранит ID эффектов, разрешённые в момент принятия, чтобы избежать молчаливых изменений поведения при горячей перезагрузке ассетов.

Когда кольцо отслеживаемых хэндлов одноразовых эффектов заполняется, самый старый эффект уничтожается до повторного использования его слота, поэтому его частицы не могут выйти из-под владения отката. syncAttachments принимает полный набор активных источников текущего кадра, перемещает существующие хэндлы, перезапускает их при изменении эффекта, ревизии или масштаба и снимает отсутствующие источники до применения лимита прикреплений к новым. Обычное открепление следует политике stop или kill каждого компонента; откат всегда уничтожает собственные хэндлы планировщика и очищает его очередь ожидания, позволяя заново проиграть более ранние восстановленные зафиксированные тики. Другие производители, использующие тот же BatchWorld, не затрагиваются.

CueSchedulerStats сообщает о принятых и дублирующихся тиках, принятых и выпущенных сигналах, числе ожидающих и прикреплённых, отбрасываниях по бюджету, непривязанных эффектах, неудачных рождениях, вытесненных хэндлах одноразовых эффектов и перезапусках источников. Вызывайте registerGraph/ registerEffect один раз при настройке или перезагрузке ассетов, а не каждый тик; bindCue сопоставляет универсальные беззнаковые типы событий с зарегистрированными именами эффектов. Для собственного цвета, масштаба или направления у отдельного события вызывайте acceptTick напрямую с CueEvent; acceptSimCueTick использует направление вверх, масштаб и оттенок по умолчанию и преобразует позиции SimEvent с фиксированной точкой в числа с плавающей точкой для представления.

Сейчас этот планировщик использует зрелый общий CPU-бэкенд частиц плюс отрисовку и пакетирование через RHI. Он намеренно не является планировщиком нескольких эмиттеров на Metal compute и не включает gpuIndirect для обычных графовых ассетов. Собственное планирование экземпляров на GPU, автоматическая миграция нативных клиентов RTS/FPS, полное визуальное совпадение при откате и реальная производительность на платформах остаются будущими задачами проверки и работы.

Тесты: tests/vfx_cue_scheduler_test.cpp, цель aiverse_vfx_cue_scheduler_tests, CTest vfx_cue_scheduler с меткой SpectraFX. Сценарии охватывают два не связанных между собой ECS-жанра, безопасную по поколениям замену прикреплений, дедупликацию зафиксированных тиков, лимиты очереди, кадра и прикреплений, вытеснение одноразовых эффектов, очистку при откате без влияния на посторонний эффект BatchWorld и диагностику регистрации графов. Тесты закоммичены в исходниках, но их выполнение не подтверждено, пока не будут доступны результаты нативного CI.

Типизированный граф потока данных v2 (этап 16)#

SpectraFX теперь принимает графовые ассеты "version":2 через тот же API fx::compileSpectraGraph / spectra::compileGraph, который используют редактор, MCP, GraphAssets, GraphRuntime и общий BatchWorld. Все существующие ассеты "version":1 сохраняют свой исходный путь компиляции; публичная константа spectra::kGraphVersion теперь сообщает новейшую версию авторинга (2), а kLegacyGraphVersion=1.

V2 добавляет два различных типа связей: связи исполнения {"from":"spawn","to":"init"} упорядочивают модули Spawn→Initialize→Update →Output; связи типизированных портов значений {"from":"math","to":"init","toPort":"speed"} привязывают значение узла данных к одному свойству (поддерживаются пути свойств через точку, например noise.frequency). Эквивалентные встроенные ссылки — {"$node":"math"} и {"$param":"wind"}. Связи данных могут соединять математические узлы с другими математическими узлами, причём проверка на циклы выполняется даже для несвязанных ветвей данных.

Новый engine/fx/SpectraValueGraph.h реализует ограниченный DAG константных выражений из литеральных значений, типизированных открытых параметров, скалярной и векторной математики, сравнений и операций Select. Характерные узлы: Float, Integer, Bool, Vec2/Vec3/Vec4, Color, String, Curve, Gradient, Parameter, Add, Subtract, Multiply, Divide, Min/Max, Clamp, Lerp, Sin/Cos, Pow/Sqrt, Floor/Ceil, Normalize/Length, Dot/Cross, ComposeVec2/3/4, Select, Greater/Less/Equal. Недопустимые типы, неконечные результаты, деление на ноль, чрезмерная глубина графа, повторяющиеся ID узлов и циклические ссылки отклоняются. Переопределения параметров должны соответствовать объявленному JSON-типу.

AgeNormalized имеет смысл только внутри явно дискретизируемой ссылки {"$curve":"expression_id","samples":33}. Она компилирует скалярное выражение от нормализованного возраста в 2–64 ключа, понятных существующей CPU-системе FxRange/кривых. Это не скрипт для каждой частицы и не универсальное программируемое GPU-ядро. Математические выражения без зависимости от возраста вычисляются во время компиляции графа; дискретизированные кривые вычисляются при уже существующем обновлении LUT времени жизни частиц.

Новый компилятор engine/fx/SpectraGraphV2.h понижает узлы стадий модулей до существующих строгих свойств модуля Update: NoiseModule, CollisionModule, TrailModule, LightModule, ForceModule, VelocityModule, SubEmitterModule, TriggerModule, InheritVelocityModule, SpeedLimitModule, ColorBySpeedModule, SizeBySpeedModule, SpinBySpeedModule, LifeBySpeedModule. Плоские ShapeModule, FlipbookModule, MaterialModule, SortModule, CustomModule переиспользуют полную существующую грамматику FxEffect; неподдерживаемые ключи эмиттера по-прежнему отклоняются fx::parseEffect. SubEmitterModule.properties.items содержит массив субэмиттеров. Существующие выходы спрайтов, мешей и лент остаются доступными.

Результат — обычный fx::EffectDef, скомпилированный тем же авторитетным парсером v1, что сохраняет совместимость с нативным C++ и жанрами и зрелый путь отрисовки на CPU. Любой эффект с модулями вне ограниченного подмножества Metal по-прежнему использует полный откат на CPU. У графов нет специфических зависимостей от FPS, RTS или других игровых модулей.

Пример ассета: examples/spectrafx/typed_noise_trail_v2.vfx.json. Он сочетает открытые параметры, узлы умножения, явные связи значений, зависящее от возраста затухание, дискретизированное в ключи, а также модули шума и шлейфа.

Явные ограничения: V2 — типизированный фронтенд авторинга и потока данных для существующих CPU-модулей эффектов, а не произвольный байткод для каждой частицы во время работы и не компиляция GPU-ядер. Полноценные пользовательские функции, буферы атрибутов частиц переменной длины и исполнение графов событий для каждой частицы остаются отдельными шагами реализации. Код закоммичен, но на этом этапе ещё не выполнялись ни сборка CMake, ни запуск тестов, ни скриншоты, ни проверка на Metal.

Визуальный авторинг и безопасные черновики для графа v2 (этап 17)#

Необязательный редактор SpectraFX на ImGui теперь по умолчанию создаёт графы версии 2. Ассеты графов версии 1 по-прежнему можно открывать и редактировать, а кнопка v1 → v2 обновляет черновик в памяти, не перезаписывая сразу его исходный файл.

Общая чистая модель на C++ engine/fx/SpectraAuthoring.h предоставляет spectra::authoring::nodeCatalog, newGraphV2, addNode, connectExec, connectData, disconnect, inputPorts, node, isData, isOutput и reaches. Она живёт вне редактора и может переиспользоваться нативными инструментами на C++ или агентами через engine/fx/SpectraFX.h. Определения узлов содержат категории, свойства по умолчанию и имена типизированных входных портов. Редактор показывает сгруппированный каталог узлов значений, математики, векторов, логики, симуляции, сил, событий и рендереров. Связи исполнения и типизированные связи данных отображаются на холсте разными цветами; правый инспектор позволяет автору выбирать входные свойства (включая вложенные пути) и подключать их к выбранному узлу значения. Защита от циклов действует для обоих видов связей.

Правый инспектор предлагает быстрые редакторы для узлов-литералов чисел, целых, логических значений, векторов и цветов, специализированные элементы управления полями модулей шума, столкновений, сил, шлейфов, света, рендеринга, сортировки и формы, а также редактирование ключевых кадров для узлов значений Curve и Gradient. В кривой можно добавлять и удалять ключи и редактировать время и значение; в градиенте — редактировать RGBA-ключи. Неизвестные модули, выражения $node и сложные вложенные поля остаются доступны через существующий инспектор сырого JSON, без приведения с потерями.

Безопасная работа с незавершёнными графами#

Графу не обязательно успешно компилироваться на каждом промежуточном шаге авторинга. Ассеты-черновики хранятся в fx/graphs/_drafts/<name>.vfx.json и не перечисляются и не загружаются продакшн-реестром графов. В редакторе есть отдельные действия Черновик / Опубликовать и список черновиков. Черновик сохраняется, даже если связи или модули не завершены; публикация компилирует ровно сохранённый черновик и отказывается заменять опубликованный граф, если компилятор возвращает ошибки. Существующие fx/graphs/<name>.vfx.json и старые fx/*.json не меняются при сохранении незавершённого черновика.

Дополнительные MCP-действия:

  • fx_graph_node_catalog: типы узлов, категории, JSON свойств по умолчанию, имена входных портов данных и новый граф по умолчанию.
  • fx_graph_edit: чисто в памяти выполняет операции new, upgrade, add, connect/disconnect, deleteNode, setProperty. Возвращает отредактированный граф и диагностику компилятора; файлы не пишутся.
  • fx_graph_draft_set, fx_graph_draft_get, fx_graph_draft_list, fx_graph_draft_publish: неразрушающий авторинг, проверка и явная публикация.
  • Существующие fx_graph_get/set/list/validate/bake продолжают работать для обеих версий графов; опубликованные графы всегда проходят строгую компиляцию.

Код закоммичен; запуск GUI, сборка CMake и CTest намеренно отложены, пока не будет завершена функциональная работа. Текущее расширенное редактирование — это по-прежнему базовый холст ImGui и запасной вариант через сырой JSON, а не полноценный коммерческий редактор уровня Niagara; подграфы функций, отладка пользовательских атрибутов частиц, временные шкалы профайлера и кодогенерация шейдерных узлов остаются задачами на будущее.

Переиспользуемые типизированные подграфы функций (этап 18)#

Граф SpectraFX v2 теперь поддерживает переиспользуемые чистые функции значений. Тела функций — это вложенные типизированные графы значений, не зависящие от рендеринга, игровых жанров и состояния ECS:

{
  "version": 2,
  "functions": {
    "scale_speed": {
      "parameters": { "base": 1, "gain": 1 },
      "returns": "number",
      "nodes": [
        { "id": "a", "type": "Parameter",
          "properties": { "name": "base" } },
        { "id": "b", "type": "Parameter",
          "properties": { "name": "gain" } },
        { "id": "out", "type": "Multiply",
          "properties": {
            "a": { "$node": "a" },
            "b": { "$node": "b" }
          } }
      ],
      "output": "out"
    }
  }
}

Вызывающий граф ссылается на функцию через узел значения FunctionCall:

{"id":"scale","type":"FunctionCall","properties":{
  "function":"scale_speed",
  "arguments":{"base":{"$param":"speed"},"gain":1.5}
}}

Сигнатуры функций объявляют типизированные parameters со значениями по умолчанию, ID выходного узла и необязательный строгий тип returns: number, bool, string, vec2, vec3, vec4. Вызовы наследуют контекст вызывающего — время компиляции или дискретизацию по нормализованному возрасту, — что позволяет создавать переиспользуемые функции затухания, ветра и отклика, компилирующиеся в существующие CPU-кривые FxRange. Определения функций содержат только узлы DAG значений и никогда — стадии Spawn/Update/Output. Компилятор графа отклоняет неизвестные функции, аргументы неверных типов, рекурсию (включая несвязанные определения), более 32 объявленных функций или более восьми вложенных вызовов. Никакие нативные скрипты, рефлексия или произвольный исполняемый код не вычисляются.

Общие библиотеки функций-ассетов#

engine/fx/SpectraFunctionAssets.h предоставляет validateFunctionLibrary, mergeFunctionLibrary и FunctionLibraryAssets с внедряемым читателем файлов и откатом к последней корректной версии при перезагрузке. Файлы библиотек используют fx/functions/<name>.vfxfn.json:

{"version":1,"functions":{"my_function":{
  "parameters":{"x":1},
  "returns":"number",
  "nodes":[{"id":"result","type":"Parameter",
            "properties":{"name":"x"}}],
  "output":"result"
}}}

Импорт библиотеки в граф v2 явно копирует её проверенные определения функций; если уже существуют функции с теми же именами, но другими телами, импорт отклоняется, если замена не запрошена явно. Импорт работает с незавершёнными черновиками редактора, а чистый компилятор графа по-прежнему не выполняет файлового ввода-вывода. Нативный API доступен из engine/fx/SpectraFX.h.

MCP поддерживает fx_function_list, fx_function_get, fx_function_set, fx_function_import и fx_function_export. Импорт возвращает отредактированный граф в памяти; пользователь явно публикует его или сохраняет черновик. В редакторе SpectraFX есть селектор FunctionCall, встроенный JSON-редактор функций, а также элементы импорта и экспорта для имён переиспользуемых библиотек функций. Примеры ассетов: examples/spectrafx/common_math.vfxfn.json и examples/spectrafx/function_calls_v2.vfx.json.

Статус: весь код закоммичен, тестирование намеренно отложено. Функции компилируют чистые значения и дискретизированные по возрасту кривые в существующие определения CPU-эмиттеров; они пока не определяют байткод изменяемых атрибутов для каждой частицы и программируемые GPU-ядра симуляции.

Скомпилированные CPU-программы для каждой частицы (этап 19)#

Существующая fx::ParticleSystem теперь может исполнять необязательную EmitterDef::particleProgram: небольшую скомпилированную ограниченную программу-выражение, выполняемую на стадиях жизненного цикла отдельной частицы. Она НЕ интерпретирует JSON заново для каждой частицы и не запускает никаких скриптов C++/Lua из файла эффекта. Компилятор проверяет опкоды, цели, вложенность, конечность констант и бюджеты и преобразует JSON в предкомпилированные инструкции в engine/fx/SpectraParticleProgram.h. На каждом шаге частицы VM использует стек фиксированного размера без динамического выделения памяти. Состояние игровой ECS не читается и не записывается.

Используйте узел конвейера ParticleProgramModule в графе v2 перед выходом или задайте particleProgram в обычном старом определении эмиттера. Поддерживаемые именованные стадии программы — spawn, update, death, collision, trigger. Каждая стадия содержит не более 32 присваиваний/обновлений и 256 постфиксных инструкций VM. Выражение — это конечное число, {"var":"field"} или дерево встроенных операций арифметики, clamp, lerp, сравнения и тригонометрии. Глубина рекурсии ограничена 16. Не допускаются произвольный исполняемый исходный код, сеть, доступ к файлам или вызов плагинов.

{
  "version":1,
  "spawn":[
    {"target":"attribute0","value":0.75}
  ],
  "update":[
    {"op":"addRate","target":"velocity.y",
     "value":{"op":"multiply",
       "a":2.2,
       "b":{"op":"subtract","a":1,
            "b":{"var":"ageNormalized"}}}},
    {"op":"set","target":"tint.a",
     "value":{"op":"saturate","a":{
       "op":"subtract","a":1,"b":{"var":"ageNormalized"}}}}
  ]
}

Поддерживаемые скалярные чтения включают age, ageNormalized, dt, uid, мировые position.x/y/z, velocity.x/y/z, size, rotation, tint.r/g/b/a и восемь независимых пользовательских значений attribute0..7 с плавающей точкой, хранящихся у каждой визуальной частицы. Поля жизненного цикла только для чтения программа записывать не может. Действия set, add, multiply, addRate (value * dt в секунду) применяются к записываемым полям. Выходные значения конечны и ограничены, каналы оттенка ограничиваются диапазоном 0..1, а размер — неотрицательными значениями.

spawn вызывается после встроенной инициализации частицы и до шлейфов и обработчиков рождения; update выполняется после существующих гравитации, сил и интегрирования и до проверки столкновений и триггеров; стадии событий выполняются на соответствующих границах столкновения, срабатывания триггера и смерти. Старые механики скорости, размера, света, шума и шлейфов по-прежнему работают для любого эффекта без программы, без нового вычисления скриптов. Динамические атрибуты могут управлять размером, поворотом, оттенком и движением через последующие инструкции VM. Графы функций v2 остаются отдельной возможностью подграфов времени компиляции; произвольная кодогенерация GPU-ядер из графов не подразумевается.

Пример: examples/spectrafx/runtime_particle_program_v2.vfx.json использует пользовательский атрибут, зависящую от возраста подъёмную силу, затухание альфы, переменный размер и обработчик смерти. Продвинутые эффекты, использующие эту VM только на CPU, автоматически исключаются из ограниченного экспериментального подмножества Metal GPU: GraphRuntime должен сохранять полный исходный эффект на CPU, а не молча отбрасывать программу. Пользователь попросил отложить сборки и тесты; исходники закоммичены, но не компилировались и не проверялись во время работы.

Именованные живые параметры экземпляров графа v2 (этап 20 — функциональные исходники закоммичены, тесты отложены)#

Графы могут объявлять до восьми именованных скалярных входов CPU VM частиц отдельно от parameters времени компиляции. Значения экземпляров во время работы можно менять без пересборки эффекта, перекомпиляции графа или изменения данных другого экземпляра. Это только представление, не зависящее от жанра, и значения не записываются в игровую ECS.

Корневой элемент графа v2 instanceParameters сопоставляет безопасное имя с {slot,default,min,max} (уникальные слоты 0..7, конечные ограниченные числа). Узел данных типа InstanceParameter ссылается на properties.name, а выражение ParticleProgramModule, использующее {"$runtime":"node_id"}, во время компиляции понижается до чтения CPU VM param0 … param7. Значения остаются динамическими во время работы частиц, в отличие от обычных литералов графа $param.

{
  "version": 2,
  "instanceParameters": {
    "lift": {"slot": 0, "default": 2.2, "min": 0, "max": 25},
    "intensity": {"slot": 1, "default": 1, "min": 0, "max": 10}
  }
}

Размещайте это объявление рядом с обычными полями nodes, links, outputs и parameters. См. examples/spectrafx/per_instance_parameters_v2.vfx.json — полный граф, в котором ускорение каждой частицы вверх использует именованное значение lift. engine/fx/SpectraInstanceParameters.h содержит общие метаданные проверки.

#include "engine/fx/SpectraFX.h"

// Same graph asset can be compiled by multiple independent runtimes:
aiverse::spectra::GraphRuntime fireA, fireB;
fireA.initGraph(device, graphJson);
fireB.initGraph(device, graphJson);

fireA.setNamedProgramParameter("lift", 2.5f);
fireB.setNamedProgramParameter("lift", 10.0f);

// For already-live particles, propagate the new value explicitly:
fireA.setNamedProgramParameter("lift", 5.0f, true);

// Or without a graph schema, use raw CPU VM slot 0..7:
fireA.setProgramParameter(0, 5.0f, true);

Вызов setProgramParameter(slot,value,affectExisting=false) у GraphRuntime меняет будущие рождения только для этого источника; affectExisting=true дополнительно обновляет текущие частицы, принадлежащие его отслеживаемым хэндлам. Публичная fx::ParticleSystem также предлагает setProgramParameter(handle,slot,value,affectExisting) и атомарный playWithProgramParameters(effect,pos,dir,scale,tint,params), который задаёт все восемь скаляров до предварительного прогрева и колбэков Spawn. spectra::BatchWorld предоставляет такое же атомарное воспроизведение и сеттер для отдельного хэндла. Стандартный play остаётся совместимым на уровне исходников и передаёт нули.

spectra::CueEvent и AttachedCue могут дополнительно нести programParams[8] и programParamMask. Планировщик сигналов применяет включённые значения до запуска нового одноразового или прикреплённого эффекта. Изменения параметров у существующего непрерывного источника обновляют текущие частицы без перезапуска эффекта. Выключенные слоты остаются нулевыми; удаление переопределения очищает старое значение слота. Планировщик по-прежнему владеет хэндлами исключительно на стороне представления.

В редакторе SpectraFX (версия 2) на правой панели есть Параметры экземпляра (runtime). Там редактируется проверяемая JSON-схема, показываются именованные значения ползунков для текущего экземпляра предпросмотра, и instanceValues передаются в операцию fx_graph_preview, работающую в памяти. Предпросмотр запускает существующую CPU ParticleSystem со значениями, применёнными до первого Spawn, и сохраняет их при перезапусках цикла. Новые файлы fx/*.json при этом не создаются.

Контракт бэкенда: произвольная CPU VM частиц и графы с именованными InstanceParameter не исполняются на экспериментальном ядре простых билбордов Metal. GraphRuntime::initGraph выбирает для таких графов полный CPU-рантайм; RequireGpu отклоняет запрос, а не молча отбрасывает параметры экземпляра. Никакой трансляции GPU VM/JIT, кодогенерации HLSL/MSL или произвольного буфера параметров экземпляров на стороне GPU не подразумевается.

Пользовательские атрибуты частиц CPU VM в шейдерных материалах (Stage 21 — исходники закоммичены, тесты отложены)#

Эмиттеры теперь могут по желанию включить четырёхканальную карту входов shader graph через graphInputs. Рендерер использует уже существующий 40-байтный формат вершины и его поле float4 graphData, поэтому совместимое батчирование отрисовки и прежние форматы вершин спрайтов/мешей не меняются. Карта источников проверяется в fx::parseEffect, сериализуется в fx::effectToJson и один раз предвычисляется в ParticleSystem::Impl::build в четыре небольших целочисленных селектора. В цикл отрисовки каждой частицы не добавляется никакого разбора JSON.

Пример внутри любого эмиттера в fx/<name>.json или в плоских свойствах MaterialModule / выходного узла graph-v2:

{
  "graphInputs": ["attribute0", "attribute1", "param0", "age"]
}

Требуется ровно четыре имени источника. Допустимые имена: age, lifetime, random, zero, от attribute0 до attribute7 и от param0 до param7. Скалярные пользовательские атрибуты записывает CPU particleProgram на этапах Spawn/Update/событий. Параметры экземпляра захватываются при испускании или обновляются посредством сеттеров на экземпляр из Stage 20. И то и другое относится только к представлению.

shaderGraph уже получает четыре вершинных канала как sg_particle во встроенном компиляторе графов материалов. Этот Stage 21 отображает выбранные значения VM в эти каналы; авторы могут комбинировать их с математическими/цветовыми/текстурными узлами графа. Он не меняет язык графов материалов, число вершинных каналов или бюджеты слотов шейдеров/текстур.

Совместимость исходников: если graphInputs отсутствует, генерируемые вершинные данные равны в точности [particle age, particle lifetime, stable random, zero], что соответствует исходному контракту shader graph. Это отображение включается по желанию для частиц на CPU и не меняет вывод обычного материала частиц без шейдера. Новая заданная карта входит в полностью сериализованную идентичность эффекта для дедупликации BatchWorld; эффекты с разными вершинными входами всё равно делят вызовы отрисовки, если их фактическое состояние материала/рендера совпадает, поскольку каждая вершина несёт собственные данные.

Экспериментальный бэкенд простых билбордов на Metal не выполняет CPU VM частиц и произвольные shader graph. Изменённые эффекты, использующие нестандартные graphInputs, отклоняются строгим шлюзом допуска к GPU и сохраняют существующий полный рендерер на CPU. Автоматический компилятор шейдерной VM для GPU, привязка параметров графа на GPU, полный регистровый файл пользовательских атрибутов или гарантированное визуальное соответствие не заявляются.

Экспериментальное выполнение скалярной VM частиц на Metal (Stage 22 — исходники закоммичены, не проверено)#

engine/fx/SpectraGpuProgram.h предоставляет фиксированный двоичный payload для строгого подмножества программ частиц CPU. Вычислительное ядро Metal из Stage 22 теперь интерпретирует этот проверенный payload напрямую во время Spawn и Update частиц. Это не динамическая генерация шейдеров MSL; шейдер компилируется один раз, а payload — обычный постоянный storage-буфер RHI. Более ранняя подготовка компилятора/ABI существовала до реализации выполнения на GPU; фактическое вычислительное выполнение и буферы параметров были добавлены в Stage 22.

Явное включение обязательно и по умолчанию выключено:

#include "engine/fx/SpectraFX.h"

aiverse::spectra::GraphRuntimeOptions options;
options.preference=aiverse::spectra::ComputePreference::Automatic;
options.gpuProgram=true;  // EXPERIMENTAL; defaults to false
options.gpuIndirect=false; // independent option from Stage 14

aiverse::spectra::GraphRuntime emitter;
if(!emitter.initGraph(device,graphJson,aiverse::Json::object(),options)) {
    // emitter.reason(), emitter.errors()
}
emitter.setNamedProgramParameter("lift",3.5f);
emitter.burstAt({0,1,0}); // parameters snapshotted before Spawn
// Per-frame device sequence: beginFrame -> emitter.step -> beginPass ->
// emitter.draw -> endPass -> endFrame.
emitter.setNamedProgramParameter("lift",5.0f,true);
// affectExisting = true queues a GPU parameter-buffer upload for next step.

Опциональный шлюз допуска к GPU сначала сравнивает каждое скомпилированное поле эмиттера с единственным контрактом аддитивного точечного всплеска builtin:soft; он допускает particleProgram, только если вся программа проходит gpu_program::prepareForMetal. Любой другой модуль, произвольный материальный shaderGraph, graphInputs, события, столкновения, следы, несколько эмиттеров, частицы-меши, принудительные поля, сортировка, случайные диапазоны или этапы графа вне поддерживаемого подмножества по-прежнему используют точно исходный полный эффект на CPU. RequireGpu завершается ошибкой вместо того, чтобы молча отбрасывать поведение.

Поддерживаемые этапы VM: Spawn и Update. Читаемые скалярные поля: age, ageNormalized, dt, position.x/y/z, velocity.x/y/z, size, tint.r/g/b/a и доступные только для чтения параметры экземпляра param0..param7. Записываемые поля: компоненты позиции/скорости, размер и оттенок. Действия: set, add, addRate, multiply. Поддерживаемые операции выражений: конечные константы и чтения полей, сложение/вычитание/умножение, min/max, abs/negate/saturate, clamp и lerp. Числовые результаты конечны/ограничены; размер ограничивается снизу нулём, каналы оттенка — диапазоном [0,1]. Ядро отклоняет некорректные инструкции и пропускает неудачные операторы, не изменяя состояние частицы.

Не поддерживаются: пользовательские регистры attribute0..7, uid, вращение, деление/pow/тригонометрия/sqrt/floor/ceil, сравнения, условный Select, программы столкновения/триггера/смерти, циклы/рекурсия, пользовательские скрипты во время выполнения и все вычислительные бэкенды, кроме Metal. GPU-интерпретатор ограничен 24 операторами всего, 192 инструкциями и 48 инструкциями на оператор. Номера ABI/опкодов/полей проверяются на этапе компиляции по перечислениям CPU VM; эти проверки всё ещё требуют фактической нативной сборки для подтверждения.

Исходное 64-байтное состояние частицы на GPU и 40-байтная вершина билборда не изменились. Вычислительный конвейер Metal дополнительно привязывает:

  • слот 7: снимки параметров на момент посева (32 байта на поставленное в очередь рождение);
  • слот 9: постоянные снимки параметров (32 байта на физический слот);
  • слот 10: проверенный payload GPU VM (10 256 байт, версия ABI 1);
  • слот 8 остаётся существующим константным буфером Uniforms.

И старый режим сбора на хосте, и опциональный режим indirect вызывают одно и то же ядро Spawn/Update и используют состояние частиц, находящееся на GPU. Изменения параметров во время выполнения без affectExisting применяются только к последующим рождениям; его включение обновляет уже отслеживаемые частицы через ограниченную карту слотов CPU на хосте и планирует одно обновление буфера по 32 байта на слот вне прохода рендера. Позиции частиц на GPU никогда не считываются обратно на CPU. Поведение при потере устройства GPU по-прежнему сообщает о не бесшовном откате на CPU.

Используйте examples/spectrafx/gpu_vm_lift_v2.vfx.json как готовый пример одиночного всплеска с зависящими от возраста подъёмом/затуханием, у которого именованное значение lift передаётся в VM. Редактор и fx_graph_validate/get/list сообщают metalVmEligible и metalVmReason отдельно от исходного вердикта для GPU только по билбордам. Это лишь диагностика возможностей по исходникам; предпросмотры в редакторе продолжают использовать зрелую среду выполнения на CPU.

Пользовательские скалярные атрибуты GPU VM (Stage 26 — функциональные исходники, тесты отложены)#

Опциональная GPU VM ComputeParticles на Metal теперь поддерживает восемь постоянных пользовательских float на частицу (от attribute0 до attribute7) и как входы выражений, и как записываемые цели Spawn/Update, что соответствует аналогичному подмножеству зрелой CPU SpectraParticleProgram. Это расширяет прежний интерпретатор Stage 22; это не новый рендерер, не аллокатор free-list только на GPU и не автоматическое переключение в продакшн для нативных клиентов FPS/RTS.

  • Фиксированный ParticleState остаётся 64 байта; Vertex билборда остаётся 40 байт. Атрибуты на GPU хранятся в отдельном storage-буфере по 32 байта на физическую частицу, привязанном к вычислительному слоту Metal 11, с двумя значениями float4.
  • При диспетчеризации Spawn на GPU каждый повторно используемый физический слот получает свежую запись атрибутов, инициализированную нулями; VM Spawn может записать свои регистры до сохранения результата. Каждая последующая диспетчеризация Update читает значения того же слота, последовательно выполняет свои ограниченные операторы выражений и записывает их обратно.
  • Существующий ABI перечислений payload GPU из Stage 22 остаётся версии 1. Поля 16–23 — это attribute0..7; поля 24–31 остаются param0..7. Шлюз возможностей на CPU разрешает эти поля для интегрированного ядра Metal. Все прочие неподдерживаемые поля, инструкции и этапы, отличные от Spawn/Update, сохраняют исходный откат полного эффекта на CPU.
  • Инициализация, clear() и shutdown() выделяют/сбрасывают/освобождают этот дополнительный буфер. ComputeStats::gpuBytes теперь учитывает его полную ёмкость. Покадровое обратное считывание атрибутов с GPU на CPU не требуется.

Пример для авторинга: examples/spectrafx/gpu_vm_custom_attributes_v2.vfx.json. Он захватывает именованный параметр экземпляра intensity в attribute0 на Spawn, затем читает сохранённый атрибут на Update, чтобы управлять tint.a и size. При GraphRuntimeOptions::gpuProgram=true эта программа укладывается в схему ограниченной GPU VM аддитивных билбордов с учётом фактических возможностей устройства и шейдеров. Тот же граф также выполняется на устоявшейся CPU VM. Фактическое числовое/визуальное соответствие не проверялось.

Важное разделение: самостоятельный gpu_program::MetalVmPass — это отдельная экспериментальная вычислительная утилита с другим шейдером. У неё пока нет буфера пользовательских атрибутов. Её инициализатор явно отклоняет payload, читающий или записывающий поля 16–23, вместо того чтобы молча выдавать неверные значения. Новое хранилище регистров есть только у интегрированного ядра ComputeParticles.

Отображение материалов шейдера graphInputs из Stage 21, работающее только на CPU, ещё не реализовано в рендерере спрайтов на GPU. Пользовательские атрибуты на GPU сейчас могут косвенно влиять на видимый вывод GPU через поддерживаемые записи VM в tint, size, позицию или скорость; произвольный shaderGraph остаётся только на CPU. Программы VM событийных этапов (столкновение, триггер, смерть), пользовательские вращения, субэмиттеры, выводы мешей/лент, сложные графы материалов, альфа-сортировка и выполнение на GPU в Vulkan/GLES/WebGL остаются за пределами этого GPU-подмножества.

Проверка: по явному указанию пользователя функциональность реализуется до тестирования. На этом этапе НЕ ЗАПУСКАЛИСЬ CMake, CTest, компиляция MSL, реальный рендеринг на GPU Apple и проверки соответствия производительности. Коммиты фиксируют изменения исходников, а не подтверждённое поведение в продакшне.

Ограниченные материалы shader graph на GPU Metal (Stage 27 — исходники закоммичены, тесты отложены)#

Опциональный бэкенд билбордов на GPU Metal теперь поддерживает ограниченное подмножество существующего языка shaderGraph домена частиц, включая пользовательские входы VM на частицу attribute0..7 и входы param0..7 на источник. Это тот же компилятор render::graph::compile(graph,"particle"), который уже используется полным CPU ParticleSystem, а не дублирующий язык узлов материалов. Сложные эффекты продолжают использовать свои полные определения эффектов для CPU.

Нативное включение (оба переключателя по умолчанию false):

aiverse::spectra::GraphRuntimeOptions options;
options.preference = aiverse::spectra::ComputePreference::Automatic;
options.gpuProgram = true; // if ParticleProgramModule is present
options.gpuMaterial = true; // enables the restricted particle shaderGraph
options.gpuIndirect = false; // optional, independent, experimental

Используйте узел SpriteOutput (или устаревший эмиттер) с такими полными полями авторинга:

{
  "texture": "builtin:soft",
  "blend": "additive",
  "graphInputs": ["attribute0", "param0", "age", "lifetime"],
  "shaderGraph": {
    "version": 1,
    "domain": "particle",
    "nodes": [
      {"id":"input","op":"input"},
      {"id":"gain","op":"particleAge"},
      {"id":"tint","op":"multiply","inputs":["input","gain"]}
    ],
    "outputs":{"color":"tint"}
  }
}

Полный пример графа: examples/spectrafx/gpu_vm_material_inputs_v2.vfx.json. Он захватывает именованный intensity в attribute0 частицы на Spawn, затем использует sg_particle.x в узле particleAge материала, чтобы модулировать базовый оттенок спрайта.

Контракт возможностей и рендеринга#

  • GraphRuntimeOptions::gpuMaterial (и низкоуровневый ComputeEmitterDesc::gpuMaterial) должен быть явно true, иначе эмиттер с shaderGraph остаётся на CPU. Граф с graphInputs, но без совместимого shaderGraph также отклоняется для Metal, чтобы его заданные данные не игнорировались.
  • gpu_material::compile допускает не более 32 чистых фрагментных узлов, один выход color, никакого вершинного графа, никаких дополнительных сэмплеров текстур, никаких зависящих от времени/недоступных операций и ограниченный белый список: input, UV, выборка встроенного спрайта, константы/параметры/vertexColor, четыре канала графа частиц и элементарная цветовая арифметика/комбинирование. Авторитетный render::graph::compile также должен принять граф.
  • Схема graphInputs эмиттера CPU используется повторно. Вычислительное ядро GPU публикует ровно четыре исходных float из возраста частицы, времени жизни, attribute0..7, param0..7 или нуля в существующий 40-байтный Vertex::graphData. Отображение компилируется при инициализации эмиттера в буфер из четырёх uint (16 байт) в вычислительном слоте Metal 13; оно никогда не разбирается как JSON каждый кадр. Стабильный random, выводимый из UID на CPU, отклоняется в материале на GPU, поскольку фиксированное состояние частицы на GPU не может его воспроизвести. Графы материалов, ссылающиеся на стандартный вход particleRandom без явного отображения, отклоняются, а не молча меняют визуал.
  • Совместимый материал на GPU использует отдельный сгенерированный шейдерный конвейер с вершинным атрибутом 3, привязанным как Float4 со смещением 24. Все остальные эмиттеры частиц сохраняют старый конвейер билбордов с тремя атрибутами. Существующее состояние частицы остаётся 64 байта, а вершины GPU — 40 байт; существующие параметры VM на экземпляр, пользовательские регистры, пути сбора на хосте и опциональной indirect-отрисовки сохранены.
  • Графический шейдер строится из доверенного шаблона MSL/GLSL и исходника, сгенерированного существующим компилятором (никакой произвольный авторский исходник шейдера не подставляется). Фрагмент получает те же параметры sg_input, sg_color, sg_particle, UV/позиции/вида, что и реализация материала на CPU, и выводит выражение color компилятора. Привязывается только одна встроенная текстура мягкого спрайта; никаких новых загрузчиков текстур материалов или зависимостей от конкретного проекта не вводится.
  • Полный откат на CPU для самостоятельного ComputeParticles сохраняет заданные particleProgram, shaderGraph и graphInputs. Для GraphRuntime существующее строгое полное сравнение EffectDef теперь сохраняет эти поля только после того, как подмножество материалов GPU прошло проверку. RequireGpu сообщает об ошибке вместо отбрасывания любого неподдерживаемого поведения материала.

Граница: это не общее соответствие авторингу материалов Niagara/HLSL, не рендеринг мешей/лент на GPU, не выборка внешних текстур, не произвольные шейдерные этапы графа, не модули света/столкновений, не альфа-сортировка, не материалы с мультисмешиванием и не общий пул отрисовки нескольких эмиттеров на GPU. Vulkan/GL/ES/WebGL продолжают использовать VFX на CPU, когда вычисления недоступны.

Исходники C++/MSL/GLSL и файлы примеров Stage 27 закоммичены, но CMake, CTest, компиляция шейдеров, реальный рендеринг на Metal, скриншоты, производительность и визуальное соответствие CPU/GPU остаются НЕ ЗАПУЩЕНЫ. Общий мир ресурсов эмиттеров CPU/GPU (Stage 28 — исходники закоммичены, тесты отложены)#

Опциональный, не зависящий от жанра spectra::GpuPoolWorld создаёт одну постоянную группу ресурсов эмиттера на GPU для каждого уникального полного эффекта и повторно использует этот ресурс для нескольких логических имён источников. Два транспортных средства, оружия или эффекта заклинаний, ссылающиеся на точно тот же граф и GPU-политику, делят один буфер симуляции ComputeParticles, payload VM и графический конвейер. Неподдерживаемые модули графа попадают в один существующий CPU spectra::BatchWorld, который может батчировать совместимые материалы/типы примитивов независимо от жанра геймплея.

Публичный API экспортируется из engine/fx/SpectraFX.h и линкуется с AIVERSE::spectrafx:

#include "engine/fx/SpectraFX.h"

aiverse::spectra::GpuPoolWorld pool;
aiverse::spectra::PoolWorldBudgets budgets;
budgets.maxGpuGroups = 16;
budgets.maxGroupCapacity = 1024;
budgets.maxBurstsPerFrame = 256;
pool.init(device, budgets);

aiverse::spectra::GraphRuntimeOptions gpu;
gpu.gpuProgram = true;
gpu.gpuMaterial = true;
gpu.capacity = 1024;
pool.defineGraph("ship_left", graphJson, aiverse::Json::object(), gpu);
pool.defineGraph("ship_right", graphJson, aiverse::Json::object(), gpu);
// Identical full graph + matching options => ONE GPU resource group.
// Runtime instance values remain independent for each source name.
pool.setNamedParameter("ship_left", "intensity", 0.3f);
pool.setNamedParameter("ship_right", "intensity", 0.9f);

// After gfx::Device::beginFrame(), BEFORE scene beginPass():
pool.beginPresentationFrame(camera, viewProj, width, height);
pool.burst("ship_left", {0, 1, 0});
pool.burst("ship_right", {3, 1, 0});
pool.step(1.f/60.f); // ONE CPU BatchWorld update + ONE update per GPU group

// DURING the already open scene render pass:
pool.draw(fog);      // one CPU batching pass + one draw per live GPU group
// After ending the render pass:
pool.endPresentationFrame();

// Between frames (no active render/compute encoder):
pool.resetForRollback(); // clears this pool's entire visual scene
pool.shutdown();         // BEFORE destroying the graphics Device

Идентичность ресурсов, бюджеты и семантика параметров#

  • Идентичность группы ресурсов на GPU включает полный канонический fx::effectToJson(effect), ёмкость, эффективный уровень качества и флаги gpuProgram, gpuMaterial, gpuIndirect. Сериализованный ключ с префиксом длины предотвращает коллизии с заданными строками shader graph. Совпадающие определения делят ровно одну группу ComputeParticles; разные определения эффектов или GPU-политики не делят состояние ошибочно.
  • PoolWorldBudgets ограничивает число групп GPU (0..64), физическую ёмкость частиц на группу (1..4096), запуски одноразовых всплесков за кадр (0..4096) и общее качество CPU. Запрошенные качество/ёмкость для определения не могут превышать бюджет мира. Когда группа GPU не поддерживается, недоступна или бюджет исчерпан, Automatic/PreferGpu сохраняют полный EffectDef в общем мире CPU. RequireGpu явно завершается ошибкой.
  • GpuPoolWorld::defineGraph хранит независимые значения по умолчанию instanceParameters для каждого логического имени, даже если его граф делит группу GPU. Используйте setNamedParameter(name,parameter,value), чтобы менять значения по умолчанию для будущего испускания, с ограниченными проверками типа/диапазона. burst(...,const std::array<float,8>* sourceParams) опционально переопределяет все восемь значений на один вызов. Перед рождением на GPU мир обновляет будущий набор параметров группы, а ComputeParticles захватывает этот набор на Spawn. Более старые частицы из других источников сохраняют свои собственные снимки; рождения на CPU используют BatchWorld::playWithProgramParameters.
  • Stage 28 также допускает именованные входы param0..7 в графе GPU только с материалом, когда ParticleProgramModule отсутствует. Это не включает неподдерживаемые операции GPU VM: сам материал должен пройти строгий шлюз возможностей shaderGraph из Stage 27.
  • beginPresentationFrame / step / draw / endPresentationFrame обеспечивают одно обновление и одну отрисовку на каждый собственный мир за кадр представления. Хост по-прежнему отвечает за фактический порядок RHI beginFrame/beginPass/endPass/endFrame. Сцена не должна отрисовывать батч CPU повторно через другого владельца.
  • PoolWorldStats сообщает число уникальных групп ресурсов GPU и определений эффектов CPU, число отправленных и отброшенных всплесков, память GPU, оценки частиц CPU/GPU и число отрисовок. Бюджеты CPU и GPU остаются на стороне рендерера и никогда не изменяют детерминированную симуляцию ECS.

Текущие границы#

Это повторное использование ресурсов GPU по полному определению эффекта, а не единый глобальный аллокатор частиц на GPU для всех материалов. У каждого уникального эффекта на GPU по-прежнему свой физический пул, атомарный счётчик живых частиц и индексированная отрисовка. Совместимые источники с идентичными эффектами делят эти буферы и отправки отрисовки; несвязанные определения шейдеров/материалов не объединяются только потому, что используют одну текстуру. Сейчас хост отправляет в эти пулированные группы только одноразовые рождения. Пока нет ни дескриптора остановки/уничтожения на GPU для каждого источника, ни индивидуального времени жизни непрерывного эмиттера на GPU, ни прозрачной сортировки между группами, ни глобального free list только на GPU. Откат очищает ВСЕ эффекты GPU/CPU, принадлежащие этому GpuPoolWorld (не внешним мирам частиц), и должен выполняться между кадрами, пока RHI исправен.

Ни один существующий клиент RTS/FPS не мигрирует молча. CueScheduler остаётся отдельным устоявшимся общим путём событий/привязок на CPU. Адаптируйте постоянные источники ECS и отмену на GPU для каждого источника только тогда, когда можно сохранить семантику, идентификаторы поколений и соответствие при откате.

Stage 24 — безопасные к поколениям снимки параметров частиц GPU VM (экспериментально; тесты отложены)#

Публичный engine/fx/SpectraGpuSourceParameters.h предоставляет реестр gpu_program::SourceParameters только для рендерера. create(initial[8]) возвращает SourceId {slot,generation}; spawn(physicalParticleSlot,id) делает снимок всех восьми значений при рождении. set(id,param,value,affectExisting) по умолчанию меняет только будущие рождения или также изменяет уже рождённые частицы, несущие в точности это поколение источника. retire(id) делает источник недействительным и сохраняет существующие значения снимков частиц до явного kill(physicalSlot). Поколения никогда не переполняются до нуля; исчерпанные слоты не могут случайно признать действительными устаревшие дескрипторы. Таблица относится только к представлению и не сериализуется в игровой ECS.

gpu_program::MetalVmPass::dispatchSources(states,count,stage,dt,registry) теперь загружает массив ParticleParams по 48 байт на слот и читает его отдельные значения float8 в экспериментальном интерпретаторе Metal; устаревший dispatch(...,values) по-прежнему передаёт один единый набор параметров. Частицы на GPU сохраняют существующий 64-байтный ABI состояния. Все физические слоты должны соответствовать реестру источников хоста, а размеры буферов GPU на одну диспетчеризацию ограничены. Отдельный хост отвечает за порождение/уничтожение физических слотов GPU синхронно с зеркалом на CPU и за правильное планирование Spawn/Update.

Не интегрировано в продакшн: GraphRuntime и ComputeParticles остаются без изменений; ни один пользовательский граф не выполняется автоматически через Metal VM. Этот проход не имеет асинхронного диагностического обратного считывания с GPU или миграции живых частиц при отказе устройства и сейчас загружает активный префикс снимков при каждой диспетчеризации. Stage 25 — жизненный цикл физических слотов GPU VM и инкрементальная загрузка снимков (экспериментально)#

Публичный gpu_program::ParticleSlots связывает физический слот, принадлежащий рендереру, с безопасным к поколениям ParticleId и снимком SourceParameters. Хост вызывает acquire(sourceId) перед загрузкой семени порождения на GPU, markSpawnSubmitted(particleId) только после успешной отправки Spawn VM и release(particleId) только после завершения работы GPU, использующей старый физический слот. needsSpawn, alive, physicalPrefix и activeCount помогают общим нативным хостам без привязки к FPS/RTS. Адаптер не планирует рендеринг и не продвигает игровую симуляцию.

Stage 25 также помечает снимки новорождённых флагом reserved=1; экспериментальное ядро Metal выполняет Spawn VM только на этих ожидающих снимках и пропускает более старые частицы на этом этапе. Хост подтверждает отправку, чтобы снять флаг ожидания. Update по-прежнему применяется ко всем активным частицам. Это устраняет прежний риск повторного выполнения Spawn для всех живых частиц.

MetalVmPass::dispatchSources кэширует собственные предыдущие значения для каждой частицы и загружает только изменённые непрерывные диапазоны, вместо загрузки всего активного префикса при каждом вызове. На Metal RHI ставит в очередь блиты storage-буферов в порядке команд перед вычислительным энкодером. readErrors(uint32_t&) предоставляет строго опциональное диагностическое обратное считывание RHI; неудачное чтение не равнозначно нулю ошибок VM. Обратные считывания должны выполняться между завершёнными кадрами, а не в активном вычислительном/рендер-энкодере. Обработка ошибок GPU/откат пока не автоматические.

Граница: по-прежнему нет автоматической интеграции VM с GraphRuntime / ComputeParticles, нет полностью принадлежащего GPU аллокатора для нескольких источников, нет доказанной компиляции шейдеров, нет числового соответствия GPU/CPU и нет миграции без потерь при отказе устройства. Тесты и нативные сборки остаются отложенными по указанию пользователя.

Stage 27 — диагностика ошибок интегрированной GPU VM на Metal и честный учёт отката#

Интегрированное ядро частиц на Metal (SpectraGpuShaders.h, не самостоятельное экспериментальное ядро Stage 23) теперь подсчитывает неудачные операторы VM, недопустимую арифметику и неконечные результаты присваиваний в выделенном атомарном счётчике storage-буфера. Счётчик сбрасывается перед непустым вычислительным кадром и привязывается как вычислительный буфер Metal в слоте 12. Неудачный оператор VM по-прежнему пропускается, как того требует существующая семантика CPU VM; диагностика не включает неподдерживаемые операции графов на GPU.

ComputeParticles::readGpuVmErrors(uint32_t&) и GraphRuntime::readGpuVmErrors(uint32_t&) предоставляют опциональную, блокирующую диагностику, выполняемую между завершёнными кадрами. Результат false означает неподдерживаемое/недоступное обратное считывание и никогда — нулевое количество. ComputeStats::gpuVmErrorsKnown равно false до успешного чтения и сбрасывается при каждом новом кадре GPU или откате на CPU. Не вызывайте это из активного рендер-/вычислительного энкодера. readBuffer в RHI Metal явно отказывается работать с активным буфером команд и ждёт отдельной отправки обратного считывания; используйте только для диагностики, а не в каждом игровом кадре.

При неисправном GPU RequireGpu по-прежнему отвергает откат. В разрешающих режимах существующий switchToCpu создаёт новый эмиттер на CPU, а не миграцию живого состояния. Счётчик lostOnFallback теперь включает ожидающие выделения слотов GPU, а не только частицы, отрисованные в последнем кадре. Это изменение улучшает учёт, но позиции, атрибуты, возраст каждой частицы и оставшееся время жизни, хранящиеся на GPU, по-прежнему теряются. Политика восстановления, требующая миграции без потерь, должна сохранять или считывать полную контрольную точку и восстанавливать состояние на CPU. Такой миграции пока нет.

Статус: исходный код закоммичен; нативная сборка C++, компиляция шейдеров Metal, CTest, UI редактора и тесты внедрения отказов GPU НЕ ЗАПУСКАЛИСЬ. Не заявляйте, что это реализация восстановления уровня продакшна.

Stage 28 — диагностические контрольные точки GPU Metal + асинхронные запросы ошибок VM#

ComputeParticles::captureGpuCheckpoint(GpuCheckpoint&) (и обёртка graph-runtime) считывает все физические слоты GPU, включая 64-байтное состояние позиции/возраста, скорости/времени жизни, оттенка и размера, восемь 32-битных параметров экземпляра VM и восемь пользовательских атрибутов VM. Она также захватывает зеркало оставшегося времени жизни на стороне CPU и серийный номер завершённого кадра. Каждая экспортированная GpuCheckpointParticle занимает 128 байт. Контрольная точка помечается как complete только после успешного выполнения всех трёх чтений storage-буферов; недействительное, недоступное состояние, состояние активного кадра или ожидающего рождения отклоняется. Вызовы блокирующие, строго между завершёнными кадрами Metal: никогда не запускайте их в каждом интерактивном кадре. Синхронный readBuffer в RHI Metal использует отдельную команду копирования и ждёт её завершения.

ComputeParticles::requestGpuVmErrors(callback) использует RHI readBufferAsync, чтобы вернуть callback(bool success,uint32_t count) в последующем кадре. Одновременно принимается только один ожидающий диагностический запрос. Токен времени жизни отменяет обратные вызовы, если ресурсы GPU были уничтожены; проверка ревизии кадра не даёт старым результатам ошибок перезаписать статистику более нового кадра. Обратный вызов не гарантируется, если среда выполнения VM уничтожена до возврата её обратного считывания. GraphRuntime пробрасывает оба API.

Важно: это экспорт состояния GPU и основа для будущего восстановления, а не откат GPU→CPU без потерь. Существующий CPU ParticleSystem не предоставляет API импорта живых частиц с их пользовательскими атрибутами и состоянием экземпляра. Если GPU становится неисправным, нельзя рассчитывать на возможность прочитать уже потерянные буферы. Stage 29 должен реализовать транзакционный импорт на CPU и периодически захватываемые контрольные точки с безопасной политикой ресурсов/fence до включения автоматического восстановления. lostOnFallback продолжает честно сообщать о потерянных частицах. RequireGpu по-прежнему запрещает молчаливый откат на CPU.

Ни компилятор, ни CMake, ни CTest, ни выполнение на Metal, ни тест внедрения отказов, ни тест соответствия CPU/GPU для Stage 28 не выполнялись; исходный код не проверен.

Stage 29 — транзакционный импорт контрольной точки на CPU и защищённое восстановление после отказа GPU#

fx::ParticleSystem::importLiveParticles(effect, particles) добавляет уже живые частицы в совместимый эффект с одним эмиттером без повторного проигрывания Spawn и без создания испускающего экземпляра. Он проверяет весь пакет (конечные позиция, скорость, цвет, возраст, время жизни, размер, восемь параметров/атрибутов VM), существующую ёмкость CPU и поддерживаемые ограничения эмиттера до изменения пула CPU. Каждая импортированная частица сохраняет позицию, скорость, возраст, оставшееся время жизни, закодированное как возраст/полное время жизни, размер, оттенок и пользовательские регистры. Она помечается как не имеющая испускающего владельца, участвует в обычном Update на CPU и батчировании рендерера и не может запускать новые всплески эмиттера. Неподдерживаемые сложные ленты, столкновения, триггеры, меши и эффекты в локальном пространстве отклоняются, а не восстанавливаются частично.

После успешного блокирующего ComputeParticles::captureGpuCheckpoint среда выполнения сохраняет полный экспорт вместе с его ревизией кадра представления. Когда switchToCpu происходит после отказа устройства, она пытается восстановиться только если контрольная точка соответствует последнему отправленному кадру GPU, содержит полное число физических слотов и нет неотправленных рождений. Импортированные частицы учитываются в ComputeStats::recoveredOnFallback; оставшиеся отброшенные выделения отражаются в lostOnFallback. При устаревших/отсутствующих/недействительных снимках существующий откат на CPU по-прежнему начинается с чистого листа и сообщает о потерях. RequireGpu продолжает запрещать неявное переключение на CPU.

Восстановление включается выбором момента захвата: контрольные точки не собираются автоматически, поскольку доступное синхронное обратное считывание RHI Metal блокирует выполнение до завершения работы GPU. Вызывайте захват контрольной точки только между завершёнными кадрами с осознанно выбранными безопасными интервалами. На неисправный GPU нельзя полагаться в создании новых снимков. Точное числовое продолжение CPU/GPU не доказано: алгоритмы рендерера и симуляции различаются, у импортированных частиц нет исходного экземпляра источника, а ранее живой эффект может перестать испускать. Термин без потерь не оправдан, пока не проверены соответствие, все категории эмиттеров и внедрение отказов. Ни нативный компилятор, ни CTest, ни тест Metal, ни GUI smoke не запускались для этого этапа; код остаётся непроверенным.

Stage 30 — опциональный поблочный асинхронный захват контрольных точек на Metal (исходники закоммичены, не проверено)#

GraphRuntimeOptions::checkpointEveryFrames (или напрямую ComputeEmitterDesc::checkpointEveryFrames) управляет выключенным по умолчанию периодическим запросом контрольной точки. Каждые N успешных вычислительных отправок Metal среда выполнения может поставить в очередь снимок после Spawn/Integration/Update/Compaction, не дожидаясь завершения. GraphRuntime::requestGpuCheckpoint(callback) и ComputeParticles::requestGpuCheckpoint(callback) позволяют делать явные ручные запросы. Обратный вызов сообщает bool complete, а не указатель на изменяемый буфер GPU. Неудачная попытка планирования возвращает false и не должна давать пригодной к использованию частичной контрольной точки.

Для каждого физического слота GPU снимок включает 64 байта состояния частицы, 32 байта входов VM на частицу и 32 байта пользовательских регистров — максимум 512 KiB при текущих 4096 слотах GPU. RHI Metal теперь реализует readBufferRangeAsync(handle,offset,size,callback) для чтений размером до 64 KiB каждое. Контрольная точка разбивает три буфера не более чем на восемь небольших запросов, собирает их только после успеха всех ответов и использует токен времени жизни рендерера для отмены обратных вызовов после завершения работы. Для каждого экземпляра ComputeParticles может ожидать не более одного захвата контрольной точки. Частично поставленный в очередь пакет отклоняется и никогда не публикуется.

Ревизия кадра GPU увеличивается при успешной вычислительной отправке, что исправляет прежний неувеличивающийся токен свежести. Асинхронный результат хранит свою исходную ревизию; switchToCpu может восстановить её, только если она всё ещё соответствует последнему кадру GPU и нет ожидающих неотправленных частиц. Периодический снимок более раннего кадра может оставаться для диагностики, но непригоден для якобы восстановления без потерь. Отсутствующие, неполные или устаревшие снимки сохраняют явный откат на CPU с подсчётом потерь.

ComputeStats предоставляет накопительные checkpointRequests, checkpointCompleted и checkpointFailed. Автоматический запрос никогда не блокирует отправку рендера синхронным чтением, но ставит в очередь копирования на устройстве; обратный вызов и сборка на CPU всё равно потребляют ресурсы. Полный захват 512 KiB включается по желанию и может быть затратным на мобильных устройствах. Захваты сложных эффектов не гарантируют воспроизведение точной траектории на CPU, поскольку числовое соответствие VM GPU/CPU и рендерера не было продемонстрировано.

НЕ ЗАПУСКАЛОСЬ: Clang/CMake, CTest, компиляция шейдеров Metal, реальные контрольная точка/восстановление на GPU, внедрение отказов и анализ производительности. Этот API экспериментальный и не является гарантией восстановления, безопасной для продакшна.

Stage 29 — общий мост сигналов зафиксированных тиков для пула GPU (функциональные исходники, тесты отложены)#

spectra::GpuCueBridge адаптирует ограниченные одноразовые события представления к существующему spectra::GpuPoolWorld. Он не создаёт собственный симулятор частиц, группу GPU, ресурсы RHI или игровые компоненты ECS. Пул продолжает объединять совместимые политики графа/материала/VM в общие группы ComputeParticles и использует исходный общий CPU BatchWorld для неподдерживаемых эффектов.

#include <aiverselib/mechanics/SpectraFX.h>
aiverse::spectra::GpuPoolWorld pool;
pool.init(device);
pool.defineGraph("impact", graphJson, aiverse::Json::object(), options);

aiverse::spectra::GpuCueBridge cues(pool);
cues.bind(42, "impact");

// Once AFTER a committed gameplay simulation tick:
aiverse::spectra::acceptSimGpuCueTick(cues, tick, simEvents);

// Per render frame, after Device::beginFrame and before its scene pass:
pool.beginPresentationFrame(camera, viewProjection, width, height);
cues.flush(); // queues are bounded; effects route to GPU/CPU via pool
pool.step(dt);
// Within the open render pass:
pool.draw(fog);
// After the render pass:
pool.endPresentationFrame();

// On a gameplay rollback: outside GPU render/compute passes,
// before replaying any restored committed tick:
if (!cues.resetForRollback()) { /* handle cues.reason() */ }

GpuCueBudgets управляет queued, acceptedPerTick и dispatchedPerFrame независимо от глобального maxBurstsPerFrame пула. accept(tick, span<GpuCueEvent>) отклоняет дублирующиеся или убывающие тики. Принятые сигналы захватывают имя эффекта в момент допуска, так что последующая перепривязка типа события не меняет события в очереди. Мост отслеживает допуски, отбрасывания, успешные запуски и отказы на уровне мира. Сбои во время flush не считаются испущенными и отбрасываются, а не блокируют будущие кадры. GpuCueEvent опционально предоставляет ключ поколения источника, направление, оттенок и снимок восьми значений param0..7.

resetForRollback() вызывает GpuPoolWorld::resetForRollback() до очистки событий в очереди и своего курсора тиков. Отклонённый сброс оставляет состояние моста нетронутым, так что возможна безопасная повторная попытка. Этот сброс очищает весь пул, а не только частицы моста: хост должен выделить пул под ту же область отката представления.

Нативные проекты ECS используют libraries/include/aiverselib/mechanics/SpectraGpuCueEcsAdapter.h и acceptSimGpuCueTick для существующего типа SimEvent. Адаптер работает только на чтение и не делает никаких предположений о FPS/RTS/жанре.

Важная функциональная граница: этот мост обрабатывает только одноразовые эффекты. Пул сейчас не предоставляет дескриптор частиц GPU на источник, которым можно было бы выборочно останавливать/уничтожать частицы или перенаправлять непрерывный эмиттер. Непрерывные эффекты, привязанные к ECS, остаются в существующем общем CueScheduler на CPU до появления безопасного к поколениям API жизненного цикла GPU для каждого источника. Не заявляйте выборочное удаление источников на GPU, полную постоянную привязку ECS или самостоятельную миграцию в продакшн.

Проверка: тесты явно отложены пользователем. CMake/CTest, выполнение на Metal Apple Silicon, соответствие скриншотов/визуала, интеграция с нативными хостами FPS/RTS и производительность НЕ ЗАПУСКАЛИСЬ. Это закоммиченный исходный код, а не подтверждённая готовность к релизу.

Stage 32 — допуск обратного считывания контрольных точек в пуле и живая телеметрия#

Контрольные точки GPU опциональны и относятся только к визуалу. Stage 32 добавляет SpectraCheckpointReadbackBudget.h — ограничитель, работающий в потоке-владельце графики, который резервирует байты и количество блоков обратного считывания на кадр GPU и для запросов в полёте. Запрос, превышающий любую из границ, возвращает false; частичная контрольная точка не публикуется. ComputeStats каждого эмиттера сообщает checkpointBudgetDenied и checkpointBytesReturned в дополнение к существующим счётчикам завершённых/неудачных/запросов. Счётчик байтов измеряет корректную полезную нагрузку обратного вызова, полученную на CPU; это не профиль пропускной способности оборудования. Резервирование удерживается до завершения обратных вызовов или уничтожения их замыканий, включая отклонённые частичные постановки в очередь.

using namespace aiverse::spectra;
auto limiter=std::make_shared<CheckpointReadbackBudget>(
    CheckpointReadbackLimits{});
GraphRuntimeOptions options;
options.checkpointEveryFrames=15; // 0 disables automatic snapshots
options.checkpointBudget=limiter;  // share across standalone GraphRuntime objects

PoolWorldBudgets poolOptions;
poolOptions.sharedCheckpointBudget=limiter;
GpuPoolWorld pool;
pool.init(device,poolOptions); // now every GPU group uses this same limiter

// After any presentation frame / callback deliveries:
const PoolCheckpointStats info=pool.checkpointStats();
// info.pendingGroups / staleGroups / freshGroups / missingGroups
// info.restoreEligibleGroups / budgetDenied / bytesReturned
// info.budget.bytesInFlight / chunksInFlight / frameBytesReserved

Если sharedCheckpointBudget не задан, GpuPoolWorld создаёт один ограничитель для всех своих групп GPU, используя PoolWorldBudgets::checkpointReadback. Потолок по умолчанию — 512 KiB и 16 блоков на кадр; 1536 KiB и 24 блока в полёте. RHI Metal поддерживает всего 32 одновременных диапазонных чтения в полёте; потолок в 24 блока оставляет запас для диагностики VM, но не гарантирует допуск, когда активны другие клиенты обратного считывания. Несколько миров на одном и том же графическом устройстве должны передавать один и тот же общий ограничитель, чтобы соблюдать единый бюджет на устройство; иначе независимые миры соблюдают только свои локальные границы. Самостоятельный GraphRuntime сохраняет прежнее независимое поведение, если не задан GraphRuntimeOptions::checkpointBudget.

Идентичные эффекты в пуле группируются по полному сериализованному эффекту, GPU-политике и теперь также по периодичности контрольных точек. Пул поворачивает начальную группу GPU в покадровой отправке, чтобы одна постоянно первая группа не расходовала весь общий бюджет контрольных точек. Это меняет порядок диспетчеризации только для представления, а не симуляцию ECS или авторитетный геймплей.

PoolCheckpointStats вычисляется по запросу без обратного считывания с GPU и включает счётчики полезной нагрузки успешных обратных вызовов плюс классификацию свежести из checkpointStatus(). Метрики бюджета отражают весь ограничитель, если он намеренно разделён с другими мирами. Свежая контрольная точка лишь актуальна на последней отправленной ревизии симуляции GPU и не является доказательством завершённого числового соответствия GPU/CPU, непрерывности источников или восстановления без потерь. Ни один устаревший снимок не импортируется автоматически.

Stage 33 — адаптивное планирование контрольных точек и безопасный к источникам VFX в пуле#

Обратные считывания контрольных точек теперь могут адаптировать свою частоту, когда отправка GPU скапливается. Опциональная AdaptiveCheckpointPolicy определена в engine/fx/SpectraAdaptiveCheckpoint.h и передаётся через GraphRuntimeOptions в ComputeParticles. Планирование считает успешные отправки симуляции на GPU, а не кадры реального времени или тики ECS.

// runtime.gpuStats().checkpointAdaptiveBackoffs / Recoveries

Состояние планирования опционально и не блокирует рендеринг. Оно не может сделать старый снимок актуальным или гарантировать откат на CPU без потерь. Завершение захвата считается успешной передачей, даже если симуляция продвинулась и снимок поэтому устарел.

GpuPoolWorld теперь поддерживает безопасные к поколениям дескрипторы источников представления. Источник владеет привязанной к имени ревизией эффекта и отдельным снимком из 8 скалярных параметров. Он может приостанавливаться, возобновляться, выводиться из эксплуатации и испускать несколько всплесков через общие пулированные ресурсы GPU/CPU:

PoolSourceId source=pool.createSource("impact");
pool.setSourceNamedParameter(source,"speed",2.5f); // if "speed" is declared
pool.emitSource(source,position);
pool.pauseSource(source);        // prevents future emission
pool.resumeSource(source);
pool.emitSource(source,newPosition);
pool.retireSource(source);       // invalidates this handle

Дескрипторы источников несут worldEpoch, slot и generation. Выведенный из эксплуатации, повторно использованный, полученный до отката или до повторной инициализации дескриптор не может законно испускать. Переопределение именованного эффекта делает недействительными ревизии привязки старых дескрипторов вместо того, чтобы молча менять граф, используемый для будущих всплесков. maxSources ограничивает активные/повторно используемые слоты (по умолчанию 4096, максимум 65536). Это остаётся не зависящим от жанра состоянием представления, доступным ECS только на чтение.

Важное ограничение: pauseSource и retireSource предотвращают будущие испускания. Уже рождённые частицы GPU продолжают своё естественное время жизни и пока не могут быть выборочно уничтожены или перенесены в другую группу источников. Владение слотами GPU на уровне частиц и безопасное по fence выборочное уничтожение — отдельная функция. Откат сбрасывает общий пул и делает недействительными дескрипторы источников. PoolWorldStats::activeSources считает активные дескрипторы, включая приостановленные.

В окне графов SpectraFX в редакторе есть опциональная панель телеметрии Metal GPU checkpoint — live, использующая PoolCheckpointStats. Хост может подключить невладеющий пул через Editor::setSpectraGpuTelemetry(&pool) и обязан отключить его до уничтожения пула. Существующий предпросмотр VFX в Scene работает только на CPU и не создаёт автоматически пул GPU Metal; без подключённого пула окно показывает явное сообщение о недоступности. Диагностика включает fresh/stale/missing/pending, давление на бюджет обратного считывания, возвращённые байты, адаптивные отступления/восстановления, текущий максимальный интервал и число активных источников. Это не означает завершённой проверки на GPU.

Проверка: только коммиты исходников на GitHub; НЕ ЗАПУСКАЛИСЬ CMake/Clang, компиляция шейдеров Metal, CTest, нативный запуск редактора, внедрение отказов, предпросмотр рендера, пользовательская проверка захвата GPU или бенчмарк производительности.

Stage 34 — частицы во владении источников, непрерывное испускание и предпросмотр Metal в редакторе#

Stage 34 снимает ограничение Stage 33, согласно которому частицы GPU в пуле нельзя выборочно уничтожать. Группа ресурсов по-прежнему владеет одним общим экземпляром ComputeParticles на уникальный эффект/политику: это не отдельный вычислительный эмиттер для каждого игрового объекта и не жанрово-специфичная система VFX.

API источников, относящийся только к представлению, теперь поддерживает упорядоченное выборочное уничтожение, ограниченный планировщик непрерывного испускания и трансформ рендера, обновляемый хостом:

using namespace aiverse::spectra;
PoolSourceId flame=pool.createSource("flame");
pool.setSourceTransform(flame,{10,1,20},{0,1,0},{1,0.5f,0.2f,1});
pool.configureContinuous(flame,PoolContinuousEmission{
    .burstsPerSecond=12, .metresPerBurst=0.5f,
    .lifetimeSeconds=0, .maxBurstsPerFrame=8
});

// Once after gfx::Device::beginFrame and before the scene pass:
pool.beginPresentationFrame(camera,viewProj,width,height);
// Native scene updates the current transform once or more before pool.step().
pool.setSourceTransform(flame,updatedPosition,forward,tint);
pool.step(dt);   // emits at configured time/distance gates, then simulates
// During depth-tested scene pass: pool.draw(fog);
// After render pass: pool.endPresentationFrame();

pool.pauseSource(flame);         // future emissions only
pool.resumeSource(flame);        // resumes bounded scheduler
pool.stopSource(flame,true);     // also selectively kill current particles
pool.retireSource(flame);        // invalidate handle/release source slot

PoolContinuousEmission задаёт шлюз по частоте в всплесках в секунду, шлюз по расстоянию в метрах на всплеск, опциональное прошедшее время жизни (0 означает отсутствие истечения) и дополнительный максимум всплесков/кадр на источник. Оба шлюза дают рождения, ограниченные глобальным PoolWorldBudgets::maxBurstsPerFrame. Избыток отбрасывается, а не ставится в очередь для неограниченного догоняния. PoolWorldStats::continuousBursts и continuousSkipped отслеживают и то, и другое. Привязанные трансформы — значения, подаваемые рендерером; движок не вносит графическое состояние в авторитетный ECS. Нативный адаптер ECS может вызывать setSourceTransform из неизменяемого/зафиксированного снимка позы рендера.

Для групп GPU ComputeParticles::burstAt(...,sourceToken) помечает каждый физический слот токеном владения источника. Токен уникален в течение времени жизни пула и не совпадает с дескриптором заново переиспользованного источника. killSourceParticles(token) удаляет соответствующие источнику рождения, которые так и не были отправлены, и ставит отправленные физические слоты в очередь на инвалидацию на GPU. На следующем step смежные уничтоженные слоты объединяются в обновления буфера мёртвого состояния до вычислительного энкодера; лишь после упорядоченной отправки на GPU эти физические слоты возвращаются в free list. Компактизация GPU indirect затем пропускает инвалидированные частицы. Это ограниченное по области уничтожение, а не глобальная очистка буфера. CPU-путь источника сохраняет ограниченное владение FxHandle и по требованию вызывает существующий общий kill на CPU. Счётчик selectivelyKilled — это частицы GPU, помеченные/отменённые, а не количество, наблюдаемое на стороне GPU. Ожидающие уничтожения делают контрольные точки непригодными для восстановления на CPU, а очистка делает недействительными данные ревизии предыдущей контрольной точки.

Предпросмотр на GPU в редакторе (опционально): окно графов SpectraFX предлагает Metal GPU наряду с исходным CPU Предпросмотр. Эквивалентная операция MCP — fx_graph_preview {graph:..., gpu:true, loop?:true, instanceValues?:{...}}. Графы проверяются с помощью inspectGraphGpuEligibility и реальной проверки возможностей вычислений Metal: RequireGpu отклоняет неподдерживаемые эффекты, а не молча отбрасывает функции или рисует приближение на CPU. Редактор ставит в очередь скомпилированный эффект, создаёт пул GPU из одной группы на следующей фазе перед проходом, отправляет вычисления до r3d_.render, рисует в открытом проходе сцены и освобождает предпросмотр после прохода. Этот живой пул автоматически подключается к панели телеметрии контрольных точек SpectraFX. Путь предпросмотра на CPU по умолчанию остаётся доступным, и семантика его вывода не изменилась. Предпросмотр на GPU пока не повторяет функцию advance/freeze предпросмотра на CPU и лишь показывает строгое подмножество одноразовых билбордов Metal.

Важные границы корректности: уничтожение источников и привязка трансформов остаются только для представления и требуют исправного графического устройства. Завершение уничтожения упорядочено на границе отправки команд, а не защищено fence GPU до фактического завершения; корректность зависит от единственной очереди команд RHI Metal и порядка блитов буферов. Нативные ID источников и токены GPU не должны сериализоваться в авторитетные игровые сохранения. Привязки источников — это снимки, обновляемые вызывающими сторонами, а не встроенная система привязки трансформов к иерархии/анимации. Подмножество эффектов GPU по-прежнему не реализует произвольные графы частиц Niagara, столкновения на GPU, вывод света/событий, эффекты с несколькими рендерерами, соответствие лент или материалов. Предпросмотр на GPU в редакторе требует нативного Metal и открытого вьюпорта Scene или Game.

Проверка: только коммиты исходников/чтения ветки. НЕ ЗАПУСКАЛИСЬ: нативная компиляция CMake, запуск редактора, компиляция шейдеров Metal, CTest, проверка выборочного уничтожения/fence на GPU, компактизация нескольких источников, скриншоты редактора, соответствие отката или профилирование производительности.

API gfx::Device, доступный только на Metal, теперь опционально предоставляет updateStorageBufferChecked(handle,data,size,offset) и completedFrameSerial(). Он возвращает их в free list порождения только после того, как completedFrameSerial() >= submittedFrame. Если проверяемая загрузка не удалась, ожидающие слоты удерживаются, а не используются повторно. Пока какие-либо уничтожения источников ожидают завершения, свежие контрольные точки непригодны для отката, а блокирующие или асинхронные захваты отклоняются.

Общий мост привязок для нативного ECS#

<aiverselib/mechanics/SpectraFX.h> теперь экспортирует заголовочный spectra::GpuEcsAttachmentPresenter, реализованный в libraries/include/aiverselib/mechanics/SpectraGpuAttachmentEcsAdapter.h. Он читает существующий lib::genre::SpectraSourceComponent из const World& с помощью eachExistingConst. Каждый источник адресуется ключом Entity::packed(), поэтому переиспользованные ID ECS не могут унаследовать дескриптор VFX другой сущности. Вызывающая сторона предоставляет тот же не зависящий от жанра SpectraPresentationSystem::ResolvePose, что используется путём на CPU.

using namespace aiverse::spectra;
GpuPoolWorld pool;
pool.init(device);
pool.defineEffect("engine_flame",compiledEffect,gpuOptions);
GpuEcsAttachmentPresenter ecsFx(pool);
PoolContinuousEmission rate{};
rate.burstsPerSecond=15;
rate.maxBurstsPerFrame=6;
ecsFx.bindEffect("engine_flame",rate);

// Once per presentation frame, after Device::beginFrame:
pool.beginPresentationFrame(cam,viewProj,width,height);
// Only the committed (or immutable copied) authoritative ECS snapshot
// is read; renderer pose resolver may interpolate visual positions.
if(!ecsFx.syncCommitted(committedTick,world,resolveRenderPose)) {
    // Handle ecsFx.reason(); never pretend that emission succeeded.
}
pool.step(dt); // GPU/CPU group simulation once BEFORE render pass.
// pool.draw(fog) once INSIDE open render pass.
// pool.endPresentationFrame() after render pass.

// When a rollback is observed: at a safe point outside active encoders,
// before replaying committed ticks or new presentation frames:
bool cleared=ecsFx.resetForRollback();

syncCommitted(tick,...) идемпотентен в отношении создания источников при повторном тике, но может обновлять позу рендера несколько раз; убывающие тики отклоняются до явного resetForRollback(). Отсутствующие/отключённые компоненты выводятся из эксплуатации; если задан killOnDetach, их существующие частицы уничтожаются выборочно. Временно неразрешённая поза приостанавливает новые рождения и возобновляет их без пересоздания дескриптора, когда снова становится корректной. Изменения эффекта/ревизии/политики отсоединяют устаревшие источники и создают новые. Политики явно регистрируются через bindEffect; правил по умолчанию для жанров нет. Адаптер предоставляет detachAll(killLiving) для явного завершения работы.

Никакого молчаливого несоответствия масштаба: исходный SpectraSourceComponent::scale имеет семантику, которую текущее подмножество пулированных билбордов на GPU не может полностью сохранить. Этот мост сейчас требует единичного масштаба и сообщает об ошибке для любого неединичного значения. Он никогда не изменяет компоненты ECS, не вставляет PoolSourceId в компонент симуляции, не записывает игровое состояние и не использует частицы GPU для авторитетных столкновений. Для каждой области отката требуется отдельный пул, поскольку GpuPoolWorld::resetForRollback() сбрасывает все его эффекты.

Управление предпросмотром на GPU Metal#

Этап 37 — поэтапный допуск ECS-источников, проверяемый сброс при откате и прямой GPU-таймлайн#

Поэтапный допуск ECS-привязок#

GpuEcsAttachmentPresenter::syncCommitted(tick,world,resolve) теперь использует поэтапное создание источников. Он проверяет каждую запрошенную политику эффекта, ограничение единичного масштаба и конечность разрешённой позы до изменения существующих привязок. Он создаёт/настраивает заменяющие дескрипторы PoolSourceId во временной карте и использует GpuPoolWorld::canStopSource(handle,killLiving) как предварительную проверку отсоединения только для чтения. Любая ошибка выделения/настройки/предварительной проверки освобождает временные источники и не трогает уже отслеживаемые эффекты.

Если старый источник ещё жив, но определение его именованного эффекта было заменено в GPU-пуле, sourceBindingCurrent обнаруживает устаревшую привязку даже тогда, когда источник приостановлен. Презентер готовит свежий источник вместо попытки испускать частицы с неверным определением.

Для замены пулу нужен достаточный свободный запас maxSources, чтобы временно вместить и старый источник, и подготовленную замену. Если его нет, синхронизация завершается неудачей без молчаливого удаления существующих источников; нативный хост может увеличить PoolWorldBudgets::maxSources или явно вывести из работы часть эффектов на безопасной границе презентации. Фазу фиксации, которая выводит из работы устаревшие GPU-источники, нельзя сделать полностью транзакционной относительно аппаратного сбоя во время последующей операции выборочного уничтожения: частичное отсоединение всё ещё возможно. Адаптер сохраняет оставшиеся отслеживаемые дескрипторы и явно возвращает false, чтобы хост мог повторить попытку. Это не обещание атомарных переходов состояния на аппаратном уровне.

Категоризированная GPU-диагностика#

ComputeStats теперь отдельно записывает gpuDeviceUnhealthy, gpuKillUploadFailures, gpuComputeBeginFailures, gpuPassOrderRejections и gpuResetFailures. PoolCheckpointStats агрегирует эти счётчики и сообщает, действительно ли известно состояние устройства Metal (gpuDeviceHealthKnown) и исправно ли оно (gpuDeviceHealthy). Неподдерживаемые бэкенды показывают неизвестное состояние, а не выдуманное исправное. Представление телеметрии SpectraFX в редакторе выводит все эти статусы и счётчики барьеров уничтожения источников. Группа GpuPoolWorld, у которой не прошёл step, больше не рисует устаревшие вершины предыдущего кадра; автономный ComputeParticles также сбрасывает свои флаги отправки при важных ранних ошибках шага GPU.

Проверяемый сброс GPU при откате#

ComputeParticles::tryClear() — новый явный API с результатом успех/неудача, а clear() остаётся обёрткой совместимости. Сброс в Metal требует активного кадра gfx Device вне энкодеров рендера/вычислений, а не просто завершённого предыдущего кадра. Он использует updateStorageBufferChecked для записей сброса состояния частиц, параметров VM и пользовательских атрибутов. Он не фиксирует CPU-зеркало свободных слотов/возраста, пока не будут приняты все три упорядоченные передачи. При частичной неудаче gpuResetDirty_ блокирует последующие рождения на GPU, симуляцию и захват контрольных точек до успешного повторного сброса; он никогда не выдаёт устаревшее состояние за точное восстановление. Эти проверяемые загрузки по-прежнему подтверждают кодирование команд, а не успешное завершение на оборудовании. Последующие сбои GPU нужно обрабатывать с помощью состояния устройства и телеметрии завершённых кадров.

GpuPoolWorld::resetForRollback() вызывает tryClear() для всех GPU-групп перед очисткой общего CPU-мира эффектов или освобождением ECS-источников презентации. Если какая-то группа не справилась, он возвращает false и сохраняет отслеживание CPU/источников для повторной попытки. Более ранняя GPU-группа к этому моменту уже могла успешно очиститься; поэтому операция является операцией по принципу «наилучшего усилия» для нескольких GPU-групп, а не атомарной транзакцией по нескольким группам. Клиенты-источники не должны заново проигрывать тики презентации, пока сброс не пройдёт успешно.

// At a rollback boundary: finish the old scene/graphics frame first.
device.beginFrame(width,height); // active RHI command buffer required
bool resetOk=attachmentPresenter.resetForRollback();
device.endFrame();
if(!resetOk) {
    // Do not claim visual reset. Retry at a subsequent safe frame.
}

Пример нативной интеграции из этапа 36 обновлён и показывает этот обязательный порядок кадра.

Таймлайн GPU-превью (только вперёд)#

Включаемое вручную превью графа Metal GPU в редакторе теперь отображает Visual simulation time (накапливается только из успешных шагов презентации). Этап 38 — повторяемый сброс GPU-групп, восстановление Device и интерполированная ECS-презентация#

Явное состояние восстановления для пулированных VFX на Metal#

У SpectraFX GpuPoolWorld теперь есть доступный только для чтения PoolResetReport resetReport() и шлюз presentationBlocked(). Попытка отката запоминает маску принятых сбросов для каждой GPU-группы, а не сбрасывает уже подготовленные группы повторно. Если группа номер N отклоняет свои проверяемые загрузки сброса, resetForRollback() возвращает false, записывает groupsAccepted, groupCount и failedGroup и блокирует создание новых источников, всплески, отправку GPU-кадров и рисование. Последующая повторная попытка в безопасном кадре презентации пропускает группы, чьи загрузки уже приняты. CPU-мир эффектов и дескрипторы источников рендерера не становятся недействительными, пока ВСЕ GPU-группы не примут свои упорядоченные команды сброса.

Это перезапускаемая подготовка, а не аппаратно-атомарный сброс. groupsAccepted означает, что RHI закодировал загрузки сброса; GPU мог их ещё не завершить. Если последующий командный буфер Metal завершится сбоем, хост должен обработать состояние/потерю устройства и заново инициализировать графический стек. Потерянный Device фиксирует resetReport().deviceLost; пул не возобновляет работу ложно лишь потому, что флаг состояния позже стал true.

Новый каталог определений только для CPU, PoolRecoveryManifest, позволяет нативному хосту воссоздать эффекты на новом, исправном графическом Device. Он сохраняет имена эффектов, исходный скомпилированный EffectDef, параметры графа, объявленную схему параметров времени выполнения и действующие значения по умолчанию. Он НЕ содержит идентификаторов источников рендерера, графических дескрипторов, буферов частиц, тайминга эмиттеров или GPU-контрольных точек.

using namespace aiverse::spectra;
PoolRecoveryManifest snapshot=oldPool.exportRecoveryManifest();
// Keep OLD graphics Device alive until oldPool.shutdown() finishes.
oldPool.shutdown();
GpuPoolWorld recovered;
bool ok=recovered.importRecoveryManifest(&newHealthyDevice,snapshot);
// Recreate the ECS attachment presenter against recovered and re-sync
// the latest committed ECS World only if ok == true.

Импорт завершается неудачей без публикации пригодного частичного пула, если эффект RequireGpu не поддерживается новым бэкендом. Старый ограничитель чтения обратно не переиспользуется через границу Device: создаётся новый бюджет контрольных точек. GPU-частицы намеренно теряются; цель — безопасное воссоздание определений эффектов и нативных привязок презентации.

Интерполяция позы рендера для ECS-источников#

Публичный нативный заголовок <aiverselib/mechanics/SpectraFX.h> экспортирует GpuEcsPoseInterpolator из libraries/include/aiverselib/mechanics/SpectraEcsRenderPose.h. Этап 39 — события хоста восстановления, ограниченный экспорт свежих GPU-данных и справедливое ограничение нагрузки VFX#

    // Host/platform explicitly creates a healthy replacement Device.
    // OLD Device remains alive through old-pool shutdown.
    bool restored=recovery.replaceDevice(newHealthyDevice);
    // Compiled effect definitions survive; live GPU particles do not.
}

poll() сообщает своему обратному вызову только переходы фазы/прогресса/состояния и никогда не выдумывает успешное восстановление. Фактическое пересоздание устройства платформы выполняет хост. replaceDevice() экспортирует манифест восстановления только для CPU, освобождает старые графические ресурсы, делает недействительными принадлежащие презентации дескрипторы источников и историю интерполированных поз, а затем импортирует определения эффектов в заново инициализированный пул. Никакие находящиеся на GPU буферы частиц, авторитетные данные ECS, сетевое состояние или прежние поколения источников рендерера не воскрешаются. Автономный пример нативной интеграции в examples/spectrafx/native_ecs_attachments.h теперь использует этот контроллер для отката и пересоздания нового Device.

Строгая и ограниченная бинарная диагностика GPU-контрольных точек#

engine/fx/SpectraCheckpointExport.h определяет 40-байтный GpuCheckpointExportHeader с сигнатурой SPFX, версией формата, числом слотов, захваченной ревизией GPU, серийным номером графического кадра и длиной сырых данных. Тело захвата состоит из существующего 128-байтного состояния GpuCheckpointParticle на слот и 4-байтного на слот CPU-зеркала времени жизни. При существующем пределе в 4096 физических слотов максимум составляет 512 КиБ состояния GPU + 16 КиБ зеркала + 40-байтный заголовок. Кодировка представляет собой диагностический блоб с нативным ABI, а не переносимое сохранение игры, стабильную межверсионную сериализацию, снимок экрана или восстанавливаемый GPU-таймлайн.

ComputeParticles::exportFreshCheckpoint(bytes,maxBytes) и GpuPoolWorld::exportFreshCheckpoint(groupIndex,bytes,maxBytes) копируют уже существующие завершённые данные GPU-контрольной точки, только когда выполнены все условия: GPU Metal активен и исправен, захваченная ревизия сохранённой контрольной точки в точности равна текущей ревизии GPU, снимок полон и имеет правильное число слотов, нет неотправленных рождений частиц или слотов уничтожения, ожидающих GPU-барьера, нет незавершённого сброса GPU и нет параллельного ожидающего чтения контрольной точки. Закодированный буфер подставляется в выходные данные только после всех предварительных проверок и проверок размера; при неудаче прежние выходные данные вызывающего остаются нетронутыми. Эти методы никогда не инициируют чтение с GPU.

PoolCheckpointStats::exportReadyGroups подсчитывает группы, которые в данный момент удовлетворяют этим условиям. Редактор SpectraFX теперь показывает это число и предлагает Save fresh GPU checkpoint, только когда какая-либо группа подходит. Он сохраняет один ограниченный файл .spfx в platform::userDataDir()/spectrafx-diagnostics/, используя временный файл с последующим переименованием. Если асинхронное чтение на момент работы интерфейса устарело, кнопка отключена или возвращается понятная ошибка; нет ни поддельного снимка, ни блокирующего синхронного чтения. Эта функция требует, чтобы хост включил реальную периодичность контрольных точек или завершил ручную контрольную точку; по умолчанию никакие контрольные точки автоматически не захватываются.

Справедливое автоматическое ограничение нагрузки VFX (включается вручную)#

PoolLoadSheddingPolicy доступна внутри PoolWorldBudgets::loadShedding и через GpuPoolWorld::setLoadShedding(policy) между кадрами презентации:

PoolLoadSheddingPolicy policy{};
policy.enabled=true;
policy.maxContinuousBurstsPerFrame=64;
policy.reserveManualBursts=16;
policy.estimatedParticleSoftLimit=8000; // previous frame's estimate
policy.maxReadbackBytesInFlight=1024u*1024u;

Планировщик каждый кадр сдвигает начальный слот источника, поэтому постоянно занятый эмиттер с малым индексом не может навсегда лишить ресурсов эмиттеры с бо́льшими индексами. Включённая политика ограничивает автоматические рождения, сохраняя существующий глобальный предел и явное выделение ёмкости под ручные одноразовые всплески. Давление по частицам основывается на оценочном числе CPU + GPU частиц предыдущего отрисованного шага; давление по чтению использует зарезервированные байты «в полёте» существующего планировщика из этапа 32. Это не измерение производительности GPU и не жёсткая гарантия резидентности памяти. Лишние автоматические всплески отбрасываются, а не ставятся в неограниченную очередь догоняющей обработки. Отключение политики сохраняет прежнее общее поведение испускания (за исключением справедливой ротации). PoolWorldStats сообщает continuousFrameBudget, pressureActive, pressureSkipped и sourceCapacity; редактор отображает эти значения, когда подключён GPU-пул.

Этап 40 — GPU-снимки замороженной ревизии, проверяемая подготовка входных данных и гистерезис VFX#

GPU Freeze сохраняет ревизию частиц, не замораживая камеру#

Асинхронные захваты контрольных точек из этапа 39 часто оказывались устаревшими к моменту, когда Metal доставлял обратный вызов чтения, поскольку ComputeParticles::step(0) всё равно запускал Update VM, хотя эмиттер был заморожен. Этап 40 добавляет gpu_pipeline::plan(...,bool integrate=true). Когда dt==0 и нет ожидающих рождений, уничтожений источников или правок параметров VM в реальном времени, шаг GPU пропускает Update VM режима 1, но по-прежнему выполняет сбор вершин, ориентированных на камеру, атомарное уплотнение и публикацию аргументов косвенного рисования. Ревизия состояния частиц не увеличивается во время такой чисто графической перерисовки. Поэтому существующая полная контрольная точка может оставаться свежей на протяжении нескольких замороженных отрисованных кадров, даже пока камера редактора движется.

Новый GpuPoolWorld::requestGpuCheckpoint(groupIndex,callback) передаёт ограниченный асинхронный захват допустимой GPU-группе. Он никогда не выполняет блокирующее чтение с GPU. Кнопка редактора Freeze & capture GPU state включает Freeze, отменяет поставленные в очередь шаги визуального времени, а затем запрашивает GPU-захват на следующей безопасной фазе перед рендером. Она отслеживает Queued / InFlight / Ready / Failed; ожидающий или устаревший захват не разрешает бинарный экспорт. Только после поступления полного снимка текущей сохранённой ревизии частиц редактор может сохранить диагностику контрольной точки. Если ранее запланированный захват уже выполняется, редактор ждёт его, а не ставит в очередь пересекающееся чтение с GPU.

Проверяемая подготовка входных данных Metal с безопасным повтором#

Вычислительный эмиттер Metal теперь использует gfx::Device::updateStorageBufferChecked() для покадрового сброса диагностики VM, параметров VM на слот, состояний порождения, идентификаторов слотов порождения, параметров VM порождения и созданной на CPU карты сбора живых слотов. Отклонённая проверяемая загрузка или отправка вычислительного энкодера сохраняет ожидающие рождения и владение слотами, устанавливает gpuStagingDirty_, делает недействительными ранее захваченные данные/ревизию контрольной точки и подавляет рисование устаревшего GPU-состояния. Следующий принятый ComputeParticles::step повторяет полный набор входных передач; только после успешной отправки вычислений расходуются флаги грязной загрузки и очереди рождений на CPU.

Это намеренно консервативная стратегия против частично принятых blit-операций Metal. Все уже принятые графические команды остаются упорядоченными в командном буфере устройства; это не атомарный откат более ранних GPU DMA-операций, и завершение на оборудовании по-прежнему требует соблюдения контракта RHI о состоянии/барьерах командных буферов Metal. GpuCheckpointStatus::stagingRecoveryPending, ComputeStats::gpuStagingUploadFailures и PoolCheckpointStats::stagingRecoveryGroups / gpuStagingUploadFailures показывают это состояние в редакторе. Игровые данные ECS не затрагиваются.

Диагностический формат контрольных точек V2 (заменяет V1 из этапа 39)#

engine/fx/SpectraCheckpointExport.h теперь записывает явный 48-байтный заголовок V2, содержащий CRC32 по данным. Ограниченный размер сырого тела остаётся 512 КиБ состояния GPU-частиц/VM плюс 16 КиБ CPU-зеркал времени жизни при 4096 слотах. Функция validateGpuCheckpointDiagnostic() проверяет сигнатуру заголовка, версию, точное число байтов, число слотов и CRC32, не обращаясь к графическому оборудованию. Редактор использует этот валидатор перед записью файла .spfx.

Прежний 40-байтный экспорт V1 является историческим и заменён форматом V2; validateGpuCheckpointDiagnostic намеренно проверяет только текущий формат V2. Ни V1, ни V2 не являются переносимым сохранением игры, стабильным при произвольных ABI компиляторов, воспроизводимой GPU-историей или авторитетной сериализацией ECS. Бинарный файл можно проверить на целостность, но он не обеспечивает импорт GPU-состояния.

Повтор восстановления и гистерезис ограничения нагрузки#

Нативный GpuPoolRecoveryHost сохраняет свой манифест только для CPU PoolRecoveryManifest, если импорт эффектов на заново созданный графический Device не удался. Хост может передать другой исправный заменяющий Device и повторить попытку, не требуя, чтобы исходный GPU-пул оставался живым. Неудачные импорты явно остаются в состоянии DeviceRecreationRequired; живые GPU-частицы и принадлежащие рендереру дескрипторы источников никогда не воскрешаются.

Необязательный PoolLoadSheddingPolicy::recoverBelowPercent (по умолчанию 85, диапазон 1..100) вводит гистерезис для давления по оценочному числу частиц и давления по байтам чтения «в полёте» из этапа 32. Как только автоматические всплески ограничиваются, они остаются ограниченными, пока соответствующая оценка не опустится до нижнего порога восстановления. Это предотвращает покадровые колебания вкл/выкл около мягкого предела. Обновление политики между кадрами сбрасывает обе защёлки гистерезиса. Метрики включают particlePressureLatched, readbackPressureLatched и pressureHeldFrames. Политика по-прежнему не применяется к ручным одноразовым VFX, никогда не ставит пропущенные всплески в очередь и по умолчанию отключена.

Инспектор контрольных точек V2: графический Device не требуется#

Новый чистый заголовок engine/fx/SpectraCheckpointInspector.h предоставляет inspectGpuCheckpointDiagnostic(bytes) и gpuDiagnosticErrorString(error). Он проверяет один ограниченный диагностический захват .spfx V2 той же сборки, не обращаясь ни к каким ресурсам Metal, коду рендеринга, состоянию ECS или API чтения с GPU.

Инспектор различает неверную сигнатуру, неподдерживаемые версии V1/другие версии, усечённые заголовки/данные, неверные числа слотов в заголовке/физических слотов, несовпадающие объявленные размеры, неожиданные хвостовые байты и несовпадение CRC32. Только после того как полная ограниченная структура и контрольная сумма прошли проверку, он читает отдельные 128-байтные записи частиц и 4-байтные CPU-зеркала времени жизни. Структурно корректный файл всё равно может нести семантические предупреждения: NaN/неконечные значения частиц, неверный возраст, несогласованные CPU-зеркала оставшегося времени жизни или необычные времена жизни. Он сообщает оценочное число живых/мёртвых физических слотов и ограничивающие координаты для конечных позиций живых частиц. Структурный успех НЕ подтверждает численный паритет CPU/Metal или корректное игровое состояние.

Переиспользуемый офлайн-CLI tools/spectrafx/inspect_spfx.cpp требует лишь нативного компилятора C++20 и заголовков репозитория:

c++ -std=c++20 -O2 -I. tools/spectrafx/inspect_spfx.cpp -o inspect_spfx
./inspect_spfx path/to/checkpoint.spfx
./inspect_spfx --json path/to/checkpoint.spfx

CLI проверяет размер файла на диске до выделения памяти и чтения, ограничивает память значением kGpuCheckpointExportMaxBytes (540,720 байт при текущем максимуме в 4096 слотов), обнаруживает файлы, которые меняются во время чтения, и выводит диагностику обычным текстом или в JSON. Он возвращает код выхода 0 для структурно корректного файла V2 (даже если тот содержит семантические предупреждения), код 1 для неверного формата/целостности V2 и код 2 для неверного вызова или ошибок ввода-вывода. Полное описание использования и ограничения «той же сборки» приведены в tools/spectrafx/README.md.

Контрольная сумма V2 охватывает данные контрольной точки. Заголовок и раскладка пакетов по-прежнему зависят от ABI нативной сборки и порядка байтов; преобразование V1, миграции между произвольными версиями, переносимость сериализации, импорт GPU-буферов и обратная перемотка GPU намеренно не поддерживаются. Диагностика может включать мировые позиции и параметры графа, и с ней следует обращаться как с данными проекта.

Нативный захват в потоке-владельце и время жизни обратных вызовов#

Новая публичная интеграция <aiverselib/mechanics/SpectraFX.h> spectra::GpuPoolCaptureHost (реализована в libraries/include/aiverselib/mechanics/SpectraGpuCaptureHost.h) предоставляет ограниченный API запросов по одному за раз:

GpuPoolCaptureHost captures(pool);
// Between frames: one requested GPU group with an explicit byte cap.
captures.request(0);
// Each frame, AFTER Device.beginFrame delivers earlier readbacks and
// BEFORE any new pool.step(dt) can invalidate the captured revision:
auto status=captures.pollBeforeStep();
// Between pool.step(0) and the scene render pass, on the same owner thread:
if(captures.status().phase==GpuCapturePhase::Queued)
    captures.submitAfterStepBeforePass();
// Once Ready, bytes are already copied and validated (no new GPU read).
std::vector<uint8_t> bytes;
if(captures.takeReady(bytes)) { /* offline diagnosis only */ }
// Always cancel before pool rollback, shutdown or graphics-Device recreation.
captures.cancel();

Контроллер хранит точный GpuPoolWorld::lifecycleEpoch() и идентификатор запроса, отбрасывает результаты от переиспользованного/пересозданного пула, хранит не более одного ограниченного вектора байтов и допускает до 600 опросов в графических кадрах потока-владельца, прежде чем вернуть тайм-аут. Асинхронные обратные вызовы RHI держат только слабые ссылки на общее состояние завершения запроса; они не захватывают висячий объект хоста и не навязывают второго владельца графики. Отмена делает публикацию недействительной, но не может принудительно отменить уже отправленную работу Metal; общий бюджет контрольных точек из этапа 32 и урегулирование обратных вызовов RHI по-прежнему действуют. Статус различает Idle, Queued, InFlight, Ready и Failed, с конкретной ошибкой, если полное чтение с GPU устарело до экспорта.

Пример examples/spectrafx/native_ecs_attachments.h теперь встраивает контроллер захвата в единый жизненный цикл нативного кадра рендера. Он замораживает развитие VFX и откладывает синхронизацию ECS-источников/поз только для чтения, пока захват находится в состоянии Queued/InFlight/Ready. Каждый кадр продолжает рисовать текущие частицы через pool.step(0); хост забирает или отменяет результат до возобновления обычной презентации. При откате или потере устройства захват отменяется до процесса восстановления этапов 38/39, и никакое потерянное/старое GPU-состояние частиц не публикуется как авторитетные данные ECS. Восстановление корректного GPU-состояния по-прежнему требует существующего явного пересоздания нового Device хостом; захваченные байты V2 не импортируются.

Этап 42 — диагностика с редактированием приватных данных, захват по группам и явные запросы восстановления#

Безопасная с точки зрения приватности диагностика — по умолчанию#

Инспектор только для чтения из этапа 41 раскрывал мировые границы и идентификаторы GPU-кадров в выводе JSON/консоли. Этап 42 вводит engine/fx/SpectraDiagnosticReport.h и GpuDiagnosticReportPrivacy. Новый gpuDiagnosticReportJson(inspection,privacy) возвращает фиксированную схему только с агрегатами, без исходных путей файлов, позиций отдельных частиц, скалярных значений VM или сырых бинарных данных GPU. По умолчанию он также скрывает границы в координатах сцены, серийный номер/ревизию GPU и отпечатки содержимого на основе CRC. Каждая чувствительная категория требует отдельного намеренного включения:

auto inspected=inspectGpuCheckpointDiagnostic(checkpointBytes);
GpuDiagnosticReportPrivacy privacy{}; // all sensitive categories OFF
std::string redacted=gpuDiagnosticReportJson(inspected,privacy);

// Only when a developer specifically requires bounds:
privacy.includeWorldBounds=true;
// Similarly, frame serial/revision/CRC fingerprints are opt-in:
privacy.includeGpuIdentifiers=true;

tools/spectrafx/inspect_spfx.cpp теперь по умолчанию выводит отредактированный текст и --json. Явный аргумент --report <safe.json> создаёт один локальный JSON-отчёт, никогда не выгружается автоматически и не включает автоматически сырую контрольную точку. Необязательные флаги CLI --include-coordinates и --include-identifiers включают только соответствующие агрегированные поля. Никакой параметр CLI никогда не выводит исходные массивы параметров VM отдельных частиц.

Редактор добавляет Save safe JSON report и намеренно отдельный Save RAW GPU checkpoint (sensitive). Безопасный отчёт содержит агрегированные счётчики проверки и не более 180 отфильтрованных по приватности выборок GPU-превью (порядковый номер выборки, оценочное число частиц, результат шага, число свежих/устаревших/ожидающих и число ожидающих уничтожений). Он исключает точные серийные номера кадров RHI, авторские имена графов, имена файлов, а также позиции и входы VM отдельных частиц. Флажки разрешают необязательные ГРАНИЦЫ в мировых координатах и GPU-идентификаторы, но никогда не сырое состояние внутри безопасного отчёта. Сохранение — это прямое локальное действие пользователя в platform::userDataDir()/spectrafx-diagnostics; система НЕ выгружает диагностику и не создаёт повторяющихся заданий.

Выбор группы в пулированном GPU-мире#

GpuPoolWorld::gpuGroupCount() и gpuGroupSummary(index,out) предоставляют доступную только для чтения PoolGpuGroupSummary: активное состояние, оценочное число частиц, байты GPU-буферов, статус ревизии ожидающей/свежей контрольной точки, принятие последнего шага/сброса и то, может ли быть экспортирована полная, текущая контрольная точка. Эти API не раскрывают сериализованные ключи графа эффекта или исходный код эффекта. Неверный индекс группы оставляет выходные данные без изменений.

Редактор показывает ограниченный селектор индекса для существующего максимума в 64 GPU-группы и привязывает как бинарный saveFreshSpectraGpuCheckpoint(out,index), так и saveSafeSpectraGpuReport(out,index,...) к выбранной группе. Старый API бинарного сохранения с одним аргументом по-прежнему автоматически выбирает первую подходящую группу для совместимости. Только принадлежащая редактору группа 0 превью Metal может захватываться редактором напрямую; отдельно подключённый внешний пул рендерера остаётся телеметрией без владения и должен выполнять собственный GPU-захват между безопасными проходами RHI. Диагностический интерфейс никогда не выводит его из порядка рендеринга.

Нативный GpuPoolCaptureHost::requestNext(policy) выбирает одну активную в данный момент группу через GpuCaptureTargetPolicy::{RoundRobin,LargestEstimatedGroup, MissingOrStalestCheckpoint}. RoundRobin сдвигает начальную группу; остальные режимы используют предыдущее оценённое на CPU число активных частиц или отсутствующую/устаревшую ревизию контрольной точки. Группы, уже выполняющие чтение, пропускаются. На каждый нативный хост в очереди/в работе остаётся ровно один захват, а общий бюджет байтов/чанков этапа 32 по-прежнему является определяющим. Запросы — это операции потока-владельца, без фонового опроса, дополнительных GPU-контекстов или прямого синхронного чтения буферов.

Нативные события сброса и пересоздания графики#

GpuPoolRecoveryHost::requestPresentationReset(purpose) теперь явно планирует визуальный сброс без отправки GPU-команд. В следующем безопасном графическом кадре, вне активных энкодеров, хост вызывает retryPresentationReset(). PoolRecoveryPhase::ResetRequested отличается от ResetRetryRequired (неудачный/незавершённый сброс GPU-группы) и DeviceRecreationRequired (потерянный GPU или неудачный импорт на новое устройство).

PoolRecoveryEvent теперь включает стабильный монотонный transitionSequence, который меняется только при изменении наблюдаемой фазы, прогресса, состояния или деталей ошибки. Он также сообщает счётчики запросов сброса и попыток замены Device хостом, был ли сброс явно поставлен в очередь и сохраняется ли манифест восстановления только для CPU для повторной попытки. Ни один обработчик событий не пересоздаёт Device сам. Настоящий платформенный хост должен создать отдельный исправный gfx::Device и держать старый Device живым, пока не будут освобождены старые пулированные GPU-ресурсы.

Обновлённый examples/spectrafx/native_ecs_attachments.h показывает как явный захват по группам, так и автоматический захват на основе политики, безопасное получение сводки и процесс сброса/статуса через очередь. Байты захвата VFX и идентификаторы физических GPU-слотов остаются вне авторитетного ECS, а потерянные GPU-частицы никогда ложно не восстанавливаются.

Проверка: только изменения исходного кода этапа 42 и чтение содержимого через GitHub. НЕ ЗАПУСКАЛОСЬ: компиляция CMake/C++/ObjC++/MSL, CTest, офлайн-CLI отредактированных отчётов, реальный экспорт отчётов из редактора, захват нескольких групп на Metal, сброс устройства с внедрением сбоев, снимки интерфейса, паритет CPU/GPU или бенчмарки производительности. Это экспериментальные API в исходном коде, ожидающие проверки исполнением.

Этап 43 — явные локальные безопасные ZIP-пакеты, нативный почтовый ящик захвата и ограниченные повторы восстановления GPU#

Безопасный локальный ZIP-пакет поддержки (без сырого GPU-состояния)#

Новый заголовок engine/fx/SpectraDiagnosticBundle.h предоставляет makeSafeGpuDiagnosticZip(inspection,frames,output). Он создаёт один ограниченный детерминированный архив ZIP STORE, содержащий лишь три записи с фиксированными именами файлов:

manifest.json
checkpoint_summary.json
preview_timeline.json

Никакой zlib или другой библиотеки сжатия не требуется: каждый член ZIP содержит строго сгенерированный JSON и CRC32. Принимаются только структурно корректная проверка V2 и до 180 агрегированных значений GpuSafeTimelineFrame на стороне рендерера. Общий размер ZIP ограничен 128 КиБ, а неверные/слишком большие запросы возвращают false, не изменяя выходные данные вызывающего.

Манифест явно объявляет ограничения приватности: redacted=true, containsRawCheckpoint=false, containsWorldCoordinates=false, containsVmScalars=false, containsGpuIdentifiers=false и uploadedAutomatically=false. У сборщика ZIP намеренно нет входного аргумента для сырых байтов SPFX, путей авторских графов или произвольных имён записей ZIP. Вызов сборщика не может случайно упаковать сырой GPU-снимок. Даже если разработчик включает мировые границы или GPU-идентификаторы для отдельного JSON-отчёта этапа 42, ZIP остаётся полностью отредактированным. Это локальный артефакт поддержки, а не сохранение ECS, GPU-воспроизведение или импортёр SPFX между сборками.

Действие редактора Save SAFE ZIP bundle создаёт один .zip в platform::userDataDir()/spectrafx-diagnostics/ только после того, как пользователь нажал кнопку и подходящая контрольная точка V2 текущей ревизии готова. Оно использует локальное имя файла safe-bundle-group-N-M.zip, а не серийный номер GPU-кадра, и отказывается перезаписывать существующий безопасный пакет. Связанный безопасный JSON-отчёт также использует нумерацию имён файлов без серийных номеров. Только когда отчёт относится к собственному GPU-превью редактора, в него включаются последние 180 очищенных счётчиков выборок; внешние GPU-пулы не наследуют не относящуюся к ним историю превью редактора.

Офлайн-утилита tools/spectrafx/inspect_spfx.cpp теперь также поддерживает:

./inspect_spfx --bundle /path/to/support.safe.zip /path/to/checkpoint.spfx

У офлайн-ZIP пустой таймлайн превью. Бинарный исходный SPFX никогда не добавляется как запись архива. Нет никакой неявной выгрузки, электронной почты, создания задач или внешнего обмена. Существующая кнопка Save RAW GPU checkpoint (sensitive) намеренно является отдельным действием пользователя.

Нативный почтовый ящик захвата без владения#

Публичный <aiverselib/mechanics/SpectraFX.h> включает GpuCaptureRequestMailbox из libraries/include/aiverselib/mechanics/SpectraGpuCaptureMailbox.h. Почтовый ящик — это хранилище намерения/статуса для того же потока-владельца с состояниями Idle / Requested / Claimed / InFlight / Ready / Failed / ReleaseRequested. Он хранит один запрошенный индекс группы, монотонно возрастающую последовательность и ограниченную информацию о сбоях; он не выполняет никаких GPU-команд и не несёт ни данных частиц, ни графических дескрипторов, ни изменений ECS, ни фонового планирования.

Нативный хост рендера может передать редактору указатель на почтовый ящик без владения через Editor::setSpectraGpuCaptureMailbox(mailbox). Интерфейс может вызывать Editor::queueSpectraExternalGpuCapture(groupIndex) или Editor::releaseSpectraExternalGpuCapture() для этого почтового ящика, но не может обращаться к gfx::Device или сам запускать readBufferAsync. Нативный владелец презентации забирает запрос на своей следующей безопасной фазе перед рендером, использует существующий GpuPoolCaptureHost «по одному за раз», держит состояние VFX замороженным, пока асинхронная контрольная точка ожидается, и публикует состояние того же запроса обратно в интерфейс. Освобождение обрабатывается нативным хостом в следующем кадре презентации, а не во время рисования ImGui.

examples/spectrafx/native_ecs_attachments.h теперь демонстрирует эту интеграцию и предоставляет captureMailbox(), poolTelemetry() и recoveryHost(). Приложение должно отсоединить все указатели без владения от редактора до уничтожения нативного хоста/графического Device. Если пул сбрасывается, восстанавливается или завершает работу, нативный хост очищает почтовый ящик и отменяет захват; поздние обратные вызовы Metal не могут повторно присоединиться к устаревшему поколению источника.

Статус восстановления и ограниченные повторы#

GpuPoolRecoveryHost::serviceQueuedResetAtSafeFrame(ownerFrameOrdinal) добавляет необязательный механизм повтора сброса в потоке-владельце. Хост вызывает его только после gfx::Device::beginFrame, вне энкодеров рендера/вычислений. При восстановимом неудачном сбросе следующая попытка отстоит на ограниченное экспоненциально растущее число кадров хоста (максимум 32); это избавляет от постоянных записей сброса каждый кадр. Возвращаемый PoolRecoveryServiceResult различает NoWork, Deferred, ResetSucceeded, ResetFailed и NeedsNewDevice. Потерянный Device должен пересоздаваться нативным платформенным хостом; его не повторяют как обычный сброс.

Существующий PoolRecoveryEvent добавляет consecutiveResetFailures и retryNotBeforeOwnerFrame, делая статус повтора/паузы видимым без таймеров. Его счётчик переходов меняется при наблюдаемых изменениях состояния восстановления, а не порождает дублирующиеся обратные вызовы в рамках одного и того же вызова сервиса восстановления. Обновлённый нативный пример вызывает этот ограниченный сервис в своём безопасном кадре перед началом обычной презентации и отменяет любой ожидающий захват перед GPU-откатом. Необязательное присоединение без владения Editor::setSpectraGpuRecoveryHost() позволяет редактору показывать этот статус и ставить в очередь намерение сброса только для VFX. Редактор никогда не выполняет сам GPU-сброс.

Ограничения приватности и исполнения#

Редактор сбрасывает оба включения чувствительных данных в отчётах, когда меняется выбранная GPU-группа или пул GPU-телеметрии, что не даёт согласию переноситься на другой рендерер. Безопасный ZIP никогда не включает сырое состояние частиц или точные серийные номера GPU-устройства. Сырой SPFX по-прежнему содержит позиции в сцене/значения VM и остаётся намеренно чувствительным экспортом.

Выполненная проверка: коммиты исходного кода через GitHub с защитой по SHA и чтение исходников. НЕ ЗАПУСКАЛОСЬ: нативная компиляция C++/ObjC++/MSL, проверка корректности ZIP распаковкой, тесты вывода/приватности/повреждений CLI, CTest, запуск интерфейса редактора/снимки экрана, реальный захват на Metal и тесты обратных вызовов в потоке-владельце/потери устройства. Этот этап реализован в исходном коде, но не проверен для продакшена.

Этап 44 — исполняемая проверка офлайн-диагностики и регрессионные шлюзы CI#

Этап 44 проверяет существующую диагностику V2, ограниченный ZIP-пакет поддержки, отредактированные отчёты и автономный CLI с помощью реального нативного исполнения C++20, а не только коммитов исходного кода в GitHub.

Новая регрессия и интеграция в сборку#

  • tests/vfx_spfx_diagnostics_test.cpp проверяет корректное кодирование/проверку контрольной точки V2, повреждённый CRC, неподдерживаемую версию, усечённые/хвостовые байты, неверную сигнатуру и число физических слотов. Он подтверждает, что чувствительные GPU-идентификаторы и мировые границы по умолчанию исключаются из отредактированного JSON, что явные включения работают независимо и что безопасный ZIP содержит только три фиксированных JSON-члена с корректными STORE, центральным каталогом и CRC32. Неверные/слишком большие запросы к сборщику должны оставлять существующие выходные данные без изменений.
  • CMakeLists.txt теперь регистрирует автономный тест как aiverse_vfx_spfx_diagnostics_test с CTest vfx_spfx_diagnostics, помеченным SpectraFX.
  • .github/workflows/spectrafx-diagnostics.yml — это автономный конвейер проверки C++20 для Linux/macOS, запускаемый изменениями соответствующих исходников/PR. Он компилирует CLI и регрессию с -Wall -Wextra -Werror, генерирует явные файлы фикстур и использует zipfile из Python для проверки реальной распаковки ZIP, CRC и редактирования. Он также проверяет, что повреждённый бинарный SPFX отклоняется, а явно включённые чувствительные поля становятся видимыми только по запросу.
  • Существующий .github/workflows/spectrafx-validation.yml включает новый исполняемый файл в свою целевую сборку CMake, чтобы помеченный CTest не оказался случайно зарегистрированным без сборки.

  • Успешность кроссплатформенного процесса GitHub Actions: последние экземпляры процесса на момент проверки были в ожидании или в очереди, а не завершены/пройдены.

Эти различия обязательны: изолированный PASS диагностики на Linux не является ни успешным полным набором CTest, ни доказательством того, что вычисления на GPU Apple уже работают.

Интеграция graph-v2 из Inspector с текущим main (2026-11-20)#

Средства авторинга/компилятор graph-v2, VM выражений, общий spectra::BatchWorld и необязательный spectra::GpuPoolWorld из ветки Inspector сосуществуют с fx::SpectraFxSceneHost из main. Это альтернативные владельцы презентации: нативный хост должен отправлять эффект ровно через одного владельца и продвигать этого владельца один раз за кадр презентации. Эта интеграция не переключает существующие хосты FPS/RTS и не включает экспериментальные флаги GPU/ICB.

Все четыре точки входа представления среды выполнения графов (BatchWorld, GpuPoolWorld, ComputeParticles, GraphRuntime) принимают существующий fx::SpectraFxView. Вызовы источников в форме камеры остаются совместимыми через шаблонные адаптеры. Device::updateStorageBufferChecked отклоняет неподдерживаемые бэкенды и небезопасные состояния энкодеров; Metal записывает загрузку в текущий кадр. readBufferRangeAsync возвращает ограниченные байты по смещению в потоке-владельце после завершения на GPU. Установленный в main таймлайн завершения GPU остаётся каноническим.

Замена GPU-превью редактора, неудачная инициализация кандидата и Stop сохраняют старых владельцев пулов, пока gpuCompletedFence не покроет их gpuSubmissionFence. При неизвестном завершении ресурсы сохраняются, пока явное завершение работы не докажет простой; ограниченная очередь из восьми владельцев откладывает дальнейшие запросы на замену. Рендеринг Scene/Game в одном и том же кадре устройства продвигает рождения/время превью один раз. Рисование SpectraFX по-прежнему выполняется до разрешения PRISMA и сохраняет реактивное покрытие, объёмы и тайминг вьюпорта из main. Публичные ассеты graph-v1 по-прежнему поддерживаются.

Проверка нативной интеграции записана в docs/agent-handoffs/inspector-spectrafx-main-2026-11-20.md.
