AIVERSE SpectraFX#

SpectraFX is the official name of the universal, genre-independent visual-effects system in AIVERSE. Its design is inspired by the authoring and event-driven workflow of Unreal Niagara, but it is not a copy of Unreal code, asset formats, or editor. aiverse::spectra is the public C++ API namespace.

Current scope (2026-11-18): Graph v1 frontend, reusable CPU particle backend, graph-asset variants/hot reload and optional read-only ECS presentation adapter have been committed. A basic graph-v1 node-canvas editor and in-memory CPU preview are committed but unverified; a limited Metal GPU particle prototype is committed but unverified; full GPU/CPU integration, Niagara dataflow and automatic RTS/FPS production integration are not finished. Tests were added but have not yet been run in the authoring environment. Refer to docs/agent-handoffs/universal-niagara-vfx-2026-11-18.md for exact SHA and verification status.

2026-11-22: effects declared in data (rules/map/type/weapon/ability "spectraFx") for every host, and one asset running on the GPU kernel or its CPU twin with Metal parity tests: see spectrafx-entity-effects.md.

Integration boundary with PRISMA#

SpectraFX is NOT the post-processing engine. It owns emitters, particle simulation, FX graphs (VFX fx/graphs/*.vfx.json), ECS FX sources and transient visual events. PRISMA in engine/render/Prisma.{h,cpp} owns HDR composite/tone mapping, bloom, depth of field, motion blur, temporal AA, screen-space lighting and post-process camera volumes. FX sprites/meshes write scene HDR before PRISMA; the full-screen postfx Shader Graph domain belongs to PRISMA. The common Shader Graph compiler/RHI is shared infrastructure, not a second VFX or postprocess implementation.

Never add full-screen frame effects to engine/fx, and never add emitters/particle lifecycle to PRISMA. PRISMA's persisted postfx block and postfx_* MCP commands stay stable for existing projects. See AGENTS.md ownership table and docs/prisma.md. No automatic live binding is implied.

No genre-dependent FX engines. An RTS turret, FPS gun, spaceship engine or racing car all use the same source component and event presenter. The host game supplies only the pose resolver and maps its event IDs to effect assets. Graphics state and particle handles never enter deterministic gameplay state/checksums.

Author a graph#

Put this file at fx/graphs/engine_fire.vfx.json inside a project:

{
  "version": 1,
  "parameters": {
    "color": [[0, "#ffe8a0ff"], [1, "#ff330000"]]
  },
  "nodes": [
    {"id": "spawn", "type": "Spawn", "properties": {"rate": 24, "duration": 1, "loop": true}},
    {"id": "initialize", "type": "Initialize", "properties": {"life": 0.6, "speed": 1.0, "size": 0.4}},
    {"id": "update", "type": "Update", "properties": {"color": {"$param": "color"}}},
    {"id": "output", "type": "SpriteOutput", "properties": {"texture": "builtin:smoke"}}
  ],
  "links": [
    {"from": "spawn", "to": "initialize"},
    {"from": "initialize", "to": "update"},
    {"from": "update", "to": "output"}
  ],
  "outputs": ["output"]
}

The v1 compiler accepts Spawn → Initialize → Update* → SpriteOutput|MeshOutput|RibbonOutput chains, with output fan-out but no multiple-input node merges. Every node has a properties object whose keys are validated against engine/fx/FxEffect.h. The module chain compiles to the existing fx::EffectDef — it does not execute arbitrary per-particle graph instructions.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::Runtime particles;
particles.init(device); // The native host owns gfx::Device.
particles.setFileReader(readGameContent);
aiverse::spectra::GraphAssets assets(particles, readGameContent);

// Converts a versioned graph asset into a CPU particle effect.
auto flame = assets.load("engine_fire");
if (flame.effect >= 0)
    particles.play(flame.effect, {0.0f, 1.0f, 0.0f});

// Overrides produce independent graph variants:
auto cold = assets.load("engine_fire",
    aiverse::Json::parse(R"({"color":[[0,"#aaddffff"],[1,"#0044ff00"]]})"));

Runtime loop: call setView(camera, viewProj, width, height), update(dt), then render(fog) after scene rendering while its pass remains open, as described in engine/fx/ParticleSystem.h.

Opt-in native ECS presentation#

#include <aiverselib/mechanics/SpectraFX.h>
using namespace aiverse;

auto entity = world.create();
spectra::SourceComponent source;
source.effect = "graph:engine_fire:<hash>"; // Better: use GraphLoadResult::runtimeName.
source.killOnDetach = false;
world.add<spectra::SourceComponent>(entity, source);

spectra::PresentationSystem presenter(particles);
presenter.sync(world, [](const World& w, Entity e,
                         fx::float3& position, fx::float3& direction) {
    // Resolve the render transform using YOUR game's component types.
    // Do not hardcode FPS/RTS into SpectraFX.
    return gameResolveEffectPose(w, e, position, direction);
});

presenter.consumeTickEvents(tick, sim.events(),

Use the actual GraphLoadResult.runtimeName for continuous graph assets after GraphAssets::load; the fx/graphs registry does not automatically initialize all graphs when the game starts. After rollback/new match, call presenter.reset() to discard outstanding presentation handles and reset the presented-tick cursor; GPU/CPU simulation state still belongs to the host.

Compatibility#

The new branded Spectra* types were introduced without changing the identity of the old Vfx* aliases. Existing fx/<effect>.json, fx/fx.json, aiverse_fx and compileVfxGraph remain available. Engine runtime files stay under engine/fx during migration. Do not remove compatibility aliases or change persistent binary save identifiers until native project adoption and regression tests pass.

The editor-core registerFxOps also registers universal fx_graph_* operations through apps/editor/core/SpectraGraphOps.cpp. They are available from the GUI Workspace and the standalone MCP server, independent of the project's gameplay genre. No editor GPU context is required to validate graphs.

Example MCP workflow:

fx_graph_set {"name":"engine_fire","graph":<graph v1 object>}
fx_graph_validate {"name":"engine_fire","overrides":{"color":[[0,"#ffffffff"],[1,"#ffffff00"]]}}
fx_graph_bake {"name":"engine_fire","effect":"engine_fire_cpu"}
fx_preview {"effect":"engine_fire_cpu","advance":1,"freeze":true}
view_screenshot {"window":"scene"}

Scope: baking is a CPU-compatible materialization step, not GPU graph execution and not a live reference: editing the graph again does not update an already baked effect until re-baked. Graphs still have no dedicated node canvas in the editor; that is the next authoring stage. The old fx/<name>.json, fx/fx.json and RTS event bindings are unaffected. The new vfx_graph_ops test requires aiverse_editor_core to be built; the test is committed but was NOT RUN in the connector-only environment.

Visual SpectraFX graph editor (stage 8)#

The standard AIVERSE Editor has an optional SpectraFX window in the Графика / Look group, defined in apps/editor/windows/SpectraGraphWindow.cpp. Its source is automatically included by the editor's apps/editor/windows/*.cpp CMake GLOB.

  • Open/create fx/graphs/<name>.vfx.json directly from the project.
  • Add nodes of types Spawn, Initialize, Update, SpriteOutput, MeshOutput, RibbonOutput; drag nodes and pan the canvas with the middle mouse button.
  • Click the source node's output pin, then the target's input pin to link; an input may have one incoming edge. Cycles and invalid endpoint types are blocked; unfinished graphs show compiler errors until connected.
  • Select a node to edit its properties JSON. Edit exposed parameters as a JSON object; undo and redo graph edits.
  • Save through fx_graph_set; compile diagnostics come from the exact spectra::compileGraph implementation used at runtime.
  • Предпросмотр calls the new GUI-only fx_graph_preview command, which compiles graph in memory, defines an ephemeral effect on Editor::gameFx_, and plays it in Scene/Game. No temp FX files are written; screenshots still work via view_screenshot.

Graph nodes may optionally include authoring metadata "position":[x,y] (two finite bounded numeric coordinates), validated by the v1 compiler but ignored during CPU effect construction. Existing graph assets without coordinates remain valid; the editor places them in a default left-to-right layout. This metadata does not enter gameplay ECS state or shader runtime resources.

This is only a basic v1 editor, not full Niagara parity: there is no arbitrary typed dataflow, function graph, GPU compute execution, depth collision, linked graph preview in shipped clients or complete UE-style module UI. Source-level smoke coverage was added to tests/vfx_graph_compiler_test.cpp for node layout metadata; GUI launch, drag/link interactions and GPU screenshots are NOT RUN in the connector-backed development environment. Manual QA is required.

Metal GPU particle prototype (stage 10 — source committed, unverified)#

A new opt-in aiverse::spectra::ComputeParticles class in engine/fx/SpectraGpuParticles.{h,cpp} executes a limited billboard particle subset on the Metal RHI compute path. It is not wired into existing RTS/FPS clients and does not replace the legacy aiverse::fx::ParticleSystem. This subset intentionally contains a single additive soft-textured emitter with configurable burst count, lifetime, initial speed, size, gravity, linear drag and alpha-over-life. Complex attributes, noise, trails, mesh particles, collision, GPU subemitters, Niagara dataflow and user-authored shader graphs remain on the existing CPU emitter backend until separately implemented.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::ComputeParticles particles;
aiverse::spectra::ComputeEmitterDesc params;
params.capacity = 1024;
params.burst = 16;
params.backend = aiverse::spectra::ComputePreference::Automatic;
params.quality = aiverse::fx::FxQuality::High;

// Initialization can occur outside a frame. Device may be nullptr for
// pure CPU/headless tests; RequireGpu fails if compute is unavailable.
if (!particles.init(device, params)) {
    // inspect particles.reason()
}

// Presentation frame, AFTER Device::beginFrame, BEFORE scene render pass:
particles.setView(camera, viewProjection, width, height);
particles.burstAt({0,2,0}, {0,1,0}, {1,0.5f,0.1f,1});
if (!particles.step(1.f/60)) {
    // RHI timing/encoder order error; inspect particles.reason()
}

// During the scene's existing still-open depth-tested render pass:
particles.draw();
// After the render pass: Device::endPass, Device::endFrame.
// Before destroying gfx::Device: particles.shutdown().

The headless pure policy chooseComputeBackend(backend, supportsCompute, preference) selects the GPU path only for Metal with compute support. CpuOnly forces CPU; Automatic and PreferGpu fall back on unsupported RHI or failed pipeline allocation; RequireGpu rejects unsupported devices rather than silently running on CPU. Low-quality GPU configurations intentionally choose CPU, respecting the existing particle quality behavior. RHI compute calls must run outside render passes and inside a GPU frame. The caller is responsible for a single presentation owner/device thread and cleanup before device destruction; this module contains no ECS gameplay or deterministic simulator state.

Metal implementation: three compute passes per presentation frame (queue accepted births → integrate age/velocity/position → expand camera-facing quad vertices). GPU buffers are persistent: 64 bytes/particle for states and seeds, a 4-byte slot index and 40 bytes per billboard vertex. The compute shader writes a vertex buffer directly sampled by the regular RHI particle vertex shader; normal frames do not read the GPU positions back to CPU. One depth-tested additive draw renders the pool. The current prototype draws the entire capped slot index array (dead slots emit degenerate quads); this is not a compacted or GPU-indirect renderer. Maximum pool is 4096 slots, with a maximum of 64 spawned per call.

GLSL source is supplied for future Vulkan compute, but Vulkan gfx::Device::supportsCompute is not implemented in the current RHI. GLES3/GL33/WebGL2 do not run the compute kernel, so the existing CPU particle renderer is used instead. Do not report those platforms as GPU-supported. The dedicated test tests/vfx_gpu_backend_test.cpp checks the selection policy, bounds, headless CPU-fallback emissions and lifetime. It also contains a recording Metal RHI mock that verifies spawn→integrate→expand dispatch ordering and render-pass command sequencing without compiling/launching real GPU shaders. It is not a Metal GPU integration test. CI and native GPU validation are still required.

Known limitations: no GPU compaction, no camera culling/LOD for per-particle draws, no GPU-particle soft intersection, no mesh/ribbon GPU rendering, no advanced emitter graphs, no cross-CPU/GPU effect scheduler, no automatic FPS/RTS runtime migration, and no GPU performance measurements. Runtime Metal shader compilation, GPU resource hazards, multi-frame correctness and framebuffer output remain NOT VERIFIED.

Automatic graph-to-backend routing (Stage 11 — source committed, not verified)#

engine/fx/SpectraGraphRuntime.{h,cpp} introduces a new optional, genre-independent aiverse::spectra::GraphRuntime. It compiles a graph-v1 asset or accepts a precompiled fx::EffectDef and decides whether it can run without semantic loss on the existing Metal compute prototype. Every unsupported graph is executed with the exact same full EffectDef on fx::ParticleSystem; complex modules are never stripped to fit the GPU.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::GraphRuntime runner;
aiverse::spectra::GraphRuntimeOptions options;
options.preference = aiverse::spectra::ComputePreference::Automatic;
options.quality = aiverse::fx::FxQuality::High;
options.capacity = 1024;

if (!runner.initGraph(device, graphJson, aiverse::Json::object(), options)) {
    // runner.reason() and runner.errors() describe the rejection
}

// After Device::beginFrame, before the scene render pass:
runner.setView(camera, viewProj, width, height);
runner.burstAt({0, 1, 0}, {0, 1, 0});
runner.step(1.f / 60.f);

// While the scene pass is open:
runner.draw(fog);
// On match change/rollback: runner.clear() outside an active encoder.
// Before device shutdown: runner.shutdown().

The schema validator inspectGraphGpuEligibility(effect, options) does not require a GPU and is safe for native modules, headless tests and editor tools. It returns GraphGpuEligibility { eligible, gpu, reason }. GPU v1 is allowed only for one additive builtin:soft camera-aligned point emitter containing one burst of 1–64 particles, constant speed/life/size/drag, zero spread, world-Y gravity, and the default white-to-transparent colour ramp. The current prototype supports only this limited payload. Custom colours/gradients, multiple emitters, random ranges/curves, custom shader graphs, trails/ribbons, noise, force fields, sub-emitters, lights, collisions, texture animation, or any other unsupported module force a full CPU fallback. The validator compares normalized complete effect definitions against a known-supported template and also explicitly checks sensitive unsupported modules and colour keys.

ComputePreference::RequireGpu fails if the graph is not eligible, the real device does not expose Metal compute, the quality tier is too low or the shader/pipeline cannot initialize. Automatic and PreferGpu instead use the unchanged CPU asset. CpuOnly never attempts GPU. A GPU health failure inside ComputeParticles can subsequently fall back to its restricted CPU equivalent; GraphRuntime continues to own that instance and reports the actual backend.

The editor and MCP fx_graph_validate, fx_graph_get, fx_graph_list responses now add metalGpuEligible and metalGpuReason after successful compilation. These are only asset capability diagnostics, not proof that Metal is present or that GPU execution succeeded. The SpectraFX visual editor shows the same capability verdict under the properties inspector; its in-memory graph preview still uses the established CPU renderer.

Important boundaries: This is an opt-in native API. It is not automatically wired into existing FPS, RTS, editor gameplay, ECS authoritative state, file assets or current save protocols. The existing production client renderer stays on CPU. Actual Apple Silicon GPU rendering, MSL compilation, multiple frames in flight and all regression tests remain unverified until run in a real checkout.

Source tests: tests/vfx_graph_runtime_test.cpp exercises a supported graph, strict rejections and CPU fallback; tests/vfx_graph_ops_test.cpp checks MCP eligibility diagnostics. CTest name: vfx_graph_runtime (label SpectraFX).

Metal lifecycle and sparse draw-range hardening (Stage 12 — source committed, unverified)#

The opt-in ComputeParticles Metal backend now tracks its occupied slot prefix rather than always updating and drawing all allocated slots. The CPU-owned slot-age bookkeeping determines the greatest currently live slot index; compute integration and quad expansion run through that prefix and the indexed draw is limited to submittedSlots * 6. A pool containing no live particles and no pending births performs no compute dispatch or draw.

This is not GPU compaction: gaps between active slots still produce degenerate quads. True GPU stream compaction, prefix sums, indirect draw counts, and thousands of materials are subsequent phases. The hard 4096-slot capacity and original RHI buffer format remain.

ComputeStats now exposes:

  • submittedSlots: prefix length actually submitted in the latest GPU draw (may exceed alive when holes exist).
  • gpuFallbacks: automatic runtime transitions to CPU.
  • lostOnFallback: number of GPU-resident particles discarded when the GPU device became unhealthy. Existing stats remain.

A runtime device-loss event is not a seamless animation step: ComputeParticles::step reports failure. For RequireGpu, the emitter becomes unavailable, retains its Metal backend identity until shutdown and does not switch to CPU. For Automatic and PreferGpu, the class attempts to initialize a CPU emitter, records the discarded GPU particles and reports false for the transition frame. CPU rendering on a device reported unhealthy is not guaranteed; a real graphics-device recreation may be required. RHI encoder timing errors continue to return failure without silently switching backend.

GraphRuntime::step now forwards the actual readiness, backend and error message of its contained GPU/CPU runtime. GraphRuntime::gpuActive also checks the underlying compute emitter, preventing false-positive success reports after RequireGpu device loss. On clear, the sparse range and GPU slot counters reset; attempting clear inside an active GPU encoder leaves state intact and emits a diagnostic.

The RHI recording test tests/vfx_gpu_backend_test.cpp has scenarios for active encoder clear protection, sparse draw range, empty-pool zero dispatch, GPU loss with RequireGpu, GPU→CPU transition with explicit lost-particle telemetry and staggered particle expiry over multiple frames. These are mocked host-command tests, not actual MSL execution.

A focused workflow, .github/workflows/spectrafx-validation.yml, provides pull-request and manual gates: Linux/macOS build and headless CTest for SpectraFX; Linux additionally builds the editor and tests MCP graph operations. The focused workflow does not validate a real Metal compute shader or GPU image correctness. Actual compilation, CI results, Apple Silicon rendering, screenshots and performance measurements remain NOT VERIFIED until they run.

Dense billboard gathering (Stage 13 — source committed, GPU validation pending)#

The optional Metal spectra::ComputeParticles backend now gathers only live physical particle slots into contiguous GPU billboard vertices. The persistent particle-state pool still uses stable indices for spawn/recycle; one additional 4-byte-per-slot storage buffer maps dense draw ordinal → physical state slot. The CPU already owns lifetime/slot bookkeeping and publishes the live-index list to GPU before the compute encoder starts. The GPU reads each selected particle's position/velocity/tint from its own resident state buffer and writes a contiguous block of four vertices. Motion state is never read back to CPU.

The frame order is: upload any new particle states and slot indices → upload the current live slot map → compute births → integrate the physical-slot range that was live before the step → GPU gather and expand exactly the particles still alive after the step → regular RHI indexed draw of alive * 6 indices. The compute kernel uses slot 4 for the live-index buffer and Uniforms.meta.w for the alive count; both MSL and future GLSL sources use the same layout. GPU updates stay between beginFrame and beginPass; draw remains inside the scene render pass.

ComputeStats::submittedSlots now equals the densely emitted live count (not the high-water physical slot index). For example, after slots 0–2 expire while slots 3–5 survive, the GPU receives [3,4,5] and submits 18 indices, not 36. The recording-RHI regression verifies this map and the draw count across staggered birth/death frames. The new live-slot upload is 4 * alive bytes each active frame and is tracked under ComputeStats::uploadedBytes. An idle particle pool continues to skip compute and draw.

Scope and limitations: This is GPU vertex gathering from a CPU-maintained live-slot list. It eliminates sparse-dead-slot rendering, but it is not a fully GPU-resident atomic/prefix-sum compaction or GPU-authored indirect draw. CPU still scans at most 4096 age records per frame, and live-index uploads incur bandwidth. The fixed 16-bit index buffer still limits the pool to 4096 billboards. The backend is restricted to additive soft sprites eligible under GraphRuntime and is not enabled by default in existing RTS/FPS clients. Metal shader compilation, image output and performance on Apple Silicon remain NOT VERIFIED until native CI/device tests complete. Non-Metal RHI paths continue using the original CPU ParticleSystem.

RHI contract and compute passes#

The portable gfx::Device adds the default-false capability query supportsGpuAuthoredIndirectDraw(). Metal reports support through its existing plain drawIndexedGpuIndirect path, independently of experimental ICB features. Vulkan/GL/GLES/WebGL continue to return false. A device advertising only supportsCompute() is not enough.

Metal compute uses two additional persistent storage buffers: aliveCounter (4-byte atomic uint, compute slot 5) and gpuDrawArgs (20-byte gfx::DrawIndexedIndirectCommand, slot 6). The existing ParticleState and 40-byte expanded vertex formats are unchanged.

Mode 3  reset GPU alive counter
Mode 0  spawn into persistent physical GPU particle slots
Mode 1  integrate physical state / kill expired particles
Mode 4  atomic-fetch-add surviving particle -> dense vertex ordinal
Mode 5  write GPU indexed draw args (indexCount = alive * 6)
Render  gfx::Device::drawIndexedGpuIndirect(gpuDrawArgs, 0)

Metal's RHI inserts a buffer memory barrier after each compute dispatch, and graphics submission occurs in the following render encoder. Surviving particle order is nondeterministic (atomic allocation), which is acceptable only for the current additive billboard subset. The GPU counter and draw arguments are not read back to CPU during normal rendering.

If gpuIndirect=true but the device lacks supportsGpuAuthoredIndirectDraw(), SpectraFX retains Stage 13's CPU-published dense slot gather with regular drawIndexed. If an already-enabled indirect command is rejected during drawing, it reports an error and skips the draw instead of drawing potentially uninitialized/stale vertices with an approximate CPU count.

ComputeParticles::gpuIndirectActive() reports actual selection; ComputeStats::gpuCompactDispatches and gpuIndirectDraws track submitted GPU operations. When indirect is active, stats().submittedSlots and stats().alive are host-side lifespan estimates, not GPU-readback measurements. The actual indexed count comes from the GPU-authored 20-byte command.

What remains on CPU#

GPU indirect removes the per-frame upload of the live slot map, and GPU compaction/draw-count calculation no longer relies on that map. The CPU still owns slot allocation and lifetime/free-list bookkeeping, and scans a bounded maximum of 4096 age records. GPU motion and dense quad generation remain GPU-side. This is not a GPU-only allocator, multi-emitter scheduler, sorting system, or complete Niagara simulation.

Cross-instance material batching (Stage 14B — source committed, unverified)#

Multiple GraphRuntime instances previously owned separate fx::ParticleSystem objects and could each submit the same sprite material as a separate GPU draw call. The opt-in spectra::BatchWorld (engine/fx/SpectraBatchWorld.{h,cpp}) puts arbitrary graph/effect definitions into one shared presentation ParticleSystem. This reuses the existing global ParticleSystem::Impl::batchFor and FxRender.cpp render queue, which already groups particles independent of effect and instance IDs.

#include "engine/fx/SpectraFX.h"

aiverse::spectra::BatchWorld shared;
shared.init(device, aiverse::fx::FxQuality::High);

aiverse::spectra::GraphRuntime smoke, fire;
// smokeJson and fireJson may represent different effects/parameters.
smoke.initGraph(shared, smokeJson);
fire.initGraph(shared, fireJson);

// Each GraphRuntime keeps its OWN handles; no CPU renderer per source.
smoke.burstAt({0,1,0});
fire.burstAt({2,1,0});

// ONCE PER FRAME (not once per GraphRuntime):
shared.setView(camera, viewProjection, width, height);
shared.update(dt);
// INSIDE the existing scene render pass, ONCE:
shared.draw(fog);

// Kill smoke's particles without affecting fire:
smoke.clear();
// Full scene/match reset: shared.clear().
smoke.shutdown();
fire.shutdown();
shared.shutdown(); // MUST outlive all attached GraphRuntime instances.

BatchWorld::defineEffect caches equivalent fully serialized effect definitions while preserving distinct emitter data. defineGraph compiles v1 JSON through the canonical compiler and registers its effect in the same world. play, move, stop, kill and playing are the underlying ParticleSystem handle operations. The caller can set texture/mesh loaders on the shared world before registering effects, retrieve stats(), call collectLights, and use its existing global quality budget. These APIs are independent of FPS, RTS or any particular game module and live outside authoritative ECS/rollback state.

Draw batching key: the actual underlying RHI texture/atlas handle, blend mode, compiled shader-graph identity and primitive kind (mesh vs quad). Effects with distinct animations, sizes, instances or spawn parameters can use the same draw call when these render-state requirements match. Even different sprites in the same atlas can batch because their UVs are encoded independently in vertex data. The same texture with different alpha/additive blending or shader graph must NOT batch. A draw is split at the 16-bit-index limit of 16,384 quads. Alpha sorting still follows the current renderer's existing ordering rules; a single cross-texture globally sorted transparent render queue is a different architectural task.

GraphRuntime::initGraph(BatchWorld&, ...) and initEffect(BatchWorld&, ...) explicitly opt the instance into this shared renderer. Its burstAt captures handles and clear()/shutdown() kills only those handles, not all the world's particles. The source handle list is bounded at 65,536: the oldest handle is killed before overflowing the bound. In shared mode, per-source step, setView and draw are no-ops to prevent double updates and duplicate draw calls. The host must call the shared world's methods once per frame. RequireGpu is rejected for shared-world registration, not silently downgraded; current pooling is for the mature CPU-simulated/RHI-rendered emitter path.

Existing game apps: RTS/FPS clients already use one central ParticleSystem and benefit from its built-in batching. This feature addresses new native/graph instance contexts that formerly created separate renderers. It does not override individual GPU ComputeParticles instances. Shared Metal GPU-particle pools across multiple independent effects still need a dedicated multi-emitter GPU scheduler and actual device QA.

Budgets and ownership rules#

CueBudgets bounds outstanding events, per-tick admissions, per-frame one-shot starts, simultaneous ECS attachments and the rollback-tracked one-shot handle ring. Inputs are clamped to safe hard ceilings; tracked one-shot capacity cannot be zero. CueScheduler::acceptTick(tick, events) ignores duplicate or decreasing ticks until resetForRollback(), but does not advance the underlying particle renderer. flush() starts up to the frame budget and leaves the remaining bounded queue for later frames. The queue stores resolved effect IDs at acceptance time to avoid silent behavior changes during an asset hot-reload.

When the tracked one-shot handle ring fills, the oldest effect is killed before its slot is reused, so its particles cannot escape rollback ownership. syncAttachments consumes the complete set of active sources for the current frame, moves existing handles, restarts on effect/revision/scale change and retires absent sources before applying the attachment cap to newcomers. Normal detach uses each component's stop-vs-kill policy; rollback always kills the scheduler's own handles and clears its pending queue, allowing older restored committed ticks to play again. Other producers using the same BatchWorld are untouched.

CueSchedulerStats reports accepted/duplicate ticks, accepted and emitted cues, queued/attached counts, budget drops, unbound effects, failed spawns, evicted one-shot handles and source restarts. Call registerGraph/ registerEffect once during setup or asset reload, not every tick; bindCue maps generic unsigned event types to registered effect names. For custom colour, scale or direction per event, call acceptTick directly with CueEvent; acceptSimCueTick uses the default up-direction, scale and tint and converts SimEvent fixed-point positions into presentation floats.

This scheduler currently uses the mature shared CPU particle backend plus RHI rendering/batching. It is deliberately not a multi-emitter Metal compute scheduler and does not enable gpuIndirect for ordinary graph assets. Custom GPU per-instance scheduling, automatic native RTS/FPS client migration, full rollback visual parity and actual platform performance remain future verification/work items.

Typed dataflow graph v2 (Stage 16)#

SpectraFX now accepts "version":2 graph assets through the same fx::compileSpectraGraph / spectra::compileGraph API used by the editor, MCP, GraphAssets, GraphRuntime and shared BatchWorld. All existing "version":1 assets retain their original compilation path; the public spectra::kGraphVersion now reports the newest authoring version (2), with kLegacyGraphVersion=1.

V2 adds two distinct types of connections: execution links {"from":"spawn","to":"init"} order Spawn→Initialize→Update modules→Output; typed value-port links {"from":"math","to":"init","toPort":"speed"} bind the value of a data node into one property (dotted property paths are supported, e.g. noise.frequency). Equivalent inline references are {"$node":"math"} and {"$param":"wind"}. Data links can connect math nodes to other math nodes, with cycle validation even for disconnected data branches.

The new engine/fx/SpectraValueGraph.h implements a bounded constant-expression DAG of literal values, typed exposed parameters, scalar/vector math, comparisons and Select operations. Representative nodes: Float, Integer, Bool, Vec2/Vec3/Vec4, Color, String, Curve, Gradient, Parameter, Add, Subtract, Multiply, Divide, Min/Max, Clamp, Lerp, Sin/Cos, Pow/Sqrt, Floor/Ceil, Normalize/Length, Dot/Cross, ComposeVec2/3/4, Select, Greater/Less/Equal. Invalid types, nonfinite results, division by zero, excessive graph depth, duplicate node IDs and cyclic references are rejected. Parameter overrides must match their declared JSON type.

AgeNormalized is meaningful only inside an explicitly sampled {"$curve":"expression_id","samples":33} reference. It compiles a scalar expression over normalized age to 2–64 keys understood by the existing CPU FxRange/curve system. It is not a per-particle script or general programmable GPU kernel. Math expressions without an age dependency are resolved at graph compile time; sampled curves are evaluated during the already-existing particle lifetime LUT update.

The new engine/fx/SpectraGraphV2.h compiler lowers module-stage nodes to existing strict Update module properties: NoiseModule, CollisionModule, TrailModule, LightModule, ForceModule, VelocityModule, SubEmitterModule, TriggerModule, InheritVelocityModule, SpeedLimitModule, ColorBySpeedModule, SizeBySpeedModule, SpinBySpeedModule, LifeBySpeedModule. Flat ShapeModule, FlipbookModule, MaterialModule, SortModule, CustomModule reuse the complete existing FxEffect grammar; unsupported emitter keys are still rejected by fx::parseEffect. SubEmitterModule.properties.items contains the sub-emitter array. Existing sprite/mesh/ribbon outputs remain available.

The output is an ordinary fx::EffectDef compiled by the same authoritative v1 parser, preserving native C++/genre compatibility and the mature CPU render path. Any effect with modules outside the limited Metal subset continues to use the full CPU fallback. There is no graph-specific dependency on FPS, RTS or other gameplay modules.

Example asset: examples/spectrafx/typed_noise_trail_v2.vfx.json. It combines exposed parameters, multiply nodes, explicit value connections, an age-dependent fade sampled into keys, and noise and trail modules.

Explicit limits: V2 is a typed authoring/dataflow frontend for existing CPU effect modules, not arbitrary runtime per-particle bytecode or GPU kernel compilation. Full user-defined functions, variable-length particle attribute buffers and per-particle event graph execution remain separate implementation steps. The code is committed, but no CMake build, test run, screenshot or Metal validation has yet been executed in this stage.

Compiled per-particle CPU programs (Stage 19)#

The existing fx::ParticleSystem can now execute an optional EmitterDef::particleProgram: a small compiled, bounded expression program running at individual particle lifecycle stages. It does NOT reinterpret JSON for every particle or run any C++/Lua script from the effect file. The compiler validates opcodes, targets, nesting, finite constants and budgets, and converts the JSON into precompiled instructions in engine/fx/SpectraParticleProgram.h. On every particle step, the VM uses a fixed-size stack with no dynamic allocation. No gameplay ECS state is read or written.

Use the ParticleProgramModule pipeline node in a v2 graph before an output, or provide particleProgram in an ordinary legacy emitter definition. Supported named program stages are spawn, update, death, collision, trigger. Each stage contains at most 32 assignments/updates and 256 postfix VM instructions. An expression is a finite number, {"var":"field"}, or a tree of built-in arithmetic, clamp, lerp, comparison and trigonometric operations. Recursion depth is bounded by 16. No arbitrary executable source, network, file access or plugin invocation is allowed.

{
  "version":1,
  "spawn":[
    {"target":"attribute0","value":0.75}
  ],
  "update":[
    {"op":"addRate","target":"velocity.y",
     "value":{"op":"multiply",
       "a":2.2,
       "b":{"op":"subtract","a":1,
            "b":{"var":"ageNormalized"}}}},
    {"op":"set","target":"tint.a",
     "value":{"op":"saturate","a":{
       "op":"subtract","a":1,"b":{"var":"ageNormalized"}}}}
  ]
}

Supported scalar reads include age, ageNormalized, dt, uid, world-space position.x/y/z, velocity.x/y/z, size, rotation, tint.r/g/b/a, and eight independent user-defined attribute0..7 floats stored with each visual particle. Read-only lifecycle fields cannot be written by a program. Actions set, add, multiply, addRate (value * dt per second) apply to writable fields. Output values are finite/bounded, tint channels clamp to 0..1 and size clamps to nonnegative.

spawn is invoked after built-in particle initialization and before trails/birth handlers; update runs after existing gravity/forces/integration and before collision and trigger testing; event stages run at the corresponding collision, trigger and death boundaries. The legacy velocity/size/light/noise/trail mechanics still run for any effect lacking a program with no new script evaluation. Dynamic attributes can drive size, rotation, tint and motion through subsequent VM statements. Function graphs v2 remain a separate compile-time subgraph feature; arbitrary graph-to-GPU kernel codegen is not implied.

Example: examples/spectrafx/runtime_particle_program_v2.vfx.json uses a custom attribute, age-dependent rising force, alpha fade, variable size and a death handler. Advanced effects using this CPU-only VM are automatically excluded from the restricted experimental Metal GPU subset: GraphRuntime must preserve the full source effect on CPU, not silently drop the program. User requested postponing builds/tests; source is committed but not compiled or runtime verified.

Experimental Metal scalar particle VM execution (Stage 22 — source committed, unverified)#

engine/fx/SpectraGpuProgram.h provides a fixed binary payload for a strict CPU particle-program subset. The Stage-22 Metal compute kernel now interprets that validated payload directly during particle Spawn and Update. This is not dynamic MSL shader generation; the shader compiles once, while the payload is an ordinary persistent RHI storage buffer. The older compiler/ABI preparation existed before the GPU execution implementation; actual compute execution and parameter buffers were added in Stage 22.

Opt-in is mandatory and false by default:

#include "engine/fx/SpectraFX.h"

aiverse::spectra::GraphRuntimeOptions options;
options.preference=aiverse::spectra::ComputePreference::Automatic;
options.gpuProgram=true;  // EXPERIMENTAL; defaults to false
options.gpuIndirect=false; // independent option from Stage 14

aiverse::spectra::GraphRuntime emitter;
if(!emitter.initGraph(device,graphJson,aiverse::Json::object(),options)) {
    // emitter.reason(), emitter.errors()
}

// Per-frame device sequence: beginFrame -> emitter.step -> beginPass ->
// emitter.draw -> endPass -> endFrame.
emitter.setNamedProgramParameter("lift",5.0f,true);
// affectExisting = true queues a GPU parameter-buffer upload for next step.

The opt-in GPU eligibility gate first compares every compiled emitter field against the single additive builtin:soft point-burst contract; it only permits a particleProgram when its entire program passes gpu_program::prepareForMetal. Any other module, arbitrary material shaderGraph, graphInputs, events, collision, trails, multiple emitters, mesh particles, forced fields, sorting, random ranges or graph stages outside the supported subset still use the exact original full CPU effect. RequireGpu fails instead of silently dropping behavior.

Supported VM stages: Spawn and Update. Readable scalar fields: age, ageNormalized, dt, position.x/y/z, velocity.x/y/z, size, tint.r/g/b/a, and read-only per-instance param0..param7. Writable fields: position/velocity components, size and tint. Actions: set, add, addRate, multiply. Supported expression ops: finite constants and field reads, add/subtract/multiply, min/max, abs/negate/saturate, clamp and lerp. Numeric results are finite/bounded; size clamps at zero, tint channels at [0,1]. The kernel rejects malformed instructions and skips failed statements rather than modifying particle state.

Unsupported: user attribute0..7 registers, uid, rotation, division/pow/trig/sqrt/floor/ceil, comparisons, conditional Select, collision/trigger/death programs, loops/recursion, runtime user scripts and all non-Metal compute backends. The GPU interpreter is bounded at 24 total statements, 192 instructions and 48 instructions per statement. ABI/opcode/field numbers are compile-time asserted against the CPU VM enums; these checks still require an actual native build to confirm.

The original 64-byte GPU particle state and 40-byte billboard vertex are unchanged. The Metal compute pipeline additionally binds:

  • slot 7: seed-time parameter snapshots (32 bytes per queued birth);
  • slot 9: persistent parameter snapshots (32 bytes per physical slot);
  • slot 10: validated GPU VM payload (10,256 bytes, ABI version 1);
  • slot 8 remains the existing Uniforms constant buffer.

Both old host-gather and opt-in indirect modes call the same Spawn/Update kernel and use GPU-resident particle state. Runtime parameter changes without affectExisting apply only to later births; enabling it updates already tracked particles through the host's bounded CPU slot map and schedules one 32-byte-per-slot buffer refresh outside the render pass. GPU particle positions are never read back to the CPU. GPU device-loss behavior continues to report non-seamless CPU fallback.

These are source capability diagnostics only; editor previews continue to use the mature CPU runtime.

GPU VM custom scalar attributes (Stage 26 — functional source, tests deferred)#

The optional Metal ComputeParticles GPU VM now supports eight persistent per-particle custom floats (attribute0 through attribute7) as both expression inputs and writable Spawn/Update targets, matching the corresponding subset of the mature CPU SpectraParticleProgram. This extends the prior Stage-22 interpreter; it is not a new renderer, GPU-only free-list allocator or an automatic production switch for native FPS/RTS clients.

  • The fixed ParticleState stays 64 bytes; the billboard Vertex stays 40 bytes. GPU attributes live in a separate, 32-byte-per-physical-particle storage buffer, bound at Metal compute slot 11, with two float4 values.
  • On the GPU Spawn dispatch, each reused physical slot receives a fresh zero-initialized attribute record; the Spawn VM may write its registers before the result is stored. Every later Update dispatch reads the same slot's values, executes its bounded expression statements sequentially, and writes them back.
  • The existing Stage-22 GPU payload enum ABI remains version 1. Fields 16–23 are attribute0..7; fields 24–31 remain param0..7. The CPU capability gate permits these fields for the integrated Metal kernel. All other unsupported fields, instructions and non-Spawn/Update stages keep the original full-effect CPU fallback.
  • Initialization, clear() and shutdown() allocate/reset/release this additional buffer. ComputeStats::gpuBytes now accounts for its full capacity. No per-frame GPU-to-CPU attribute readback is required.

Authoring example: examples/spectrafx/gpu_vm_custom_attributes_v2.vfx.json. It captures a named instance intensity into attribute0 on Spawn, then reads the stored attribute on Update to drive tint.a and size. With GraphRuntimeOptions::gpuProgram=true, this program fits the restricted additive billboard GPU VM schema, subject to actual device and shader capability. The same graph also executes under the established CPU VM. Actual numerical/image parity has not been verified.

Important separation: standalone gpu_program::MetalVmPass is a distinct experimental compute utility with a different shader. It does not yet have a custom attribute buffer. Its initializer explicitly rejects payloads reading or writing fields 16–23, rather than silently producing incorrect values. Only the integrated ComputeParticles kernel has the new register storage.

The Stage-21 CPU-only graphInputs shader material mapping is not yet implemented in the GPU sprite renderer. GPU custom attributes can currently influence visible GPU output indirectly through supported VM writes to tint, size, position or velocity; arbitrary shaderGraph remains CPU-only. Event-stage VM programs (collision, trigger, death), custom rotations, subemitters, mesh/ribbon outputs, complex material graphs, alpha sorting and Vulkan/GLES/WebGL GPU execution remain outside this GPU subset.

Shared CPU/GPU emitter resource world (Stage 28 — source committed, tests deferred)#

The opt-in, genre-independent spectra::GpuPoolWorld creates one persistent GPU emitter resource group for each unique full effect and reuses that resource across multiple logical source names. Unsupported graph modules go into one existing CPU spectra::BatchWorld, which can batch compatible materials/primitive types regardless of gameplay genre.

The public API is exported from engine/fx/SpectraFX.h and linked with AIVERSE::spectrafx:

  • GPU resource-group identity includes the full canonical fx::effectToJson(effect), the capacity, effective quality tier and gpuProgram, gpuMaterial, gpuIndirect flags. Matching definitions share exactly one ComputeParticles group; different effect definitions or GPU policies do not falsely share state.
  • PoolWorldBudgets limits GPU groups (0..64), per-group physical particle capacity (1..4096), one-shot burst starts per frame (0..4096) and shared CPU quality. Requested per-definition quality/capacity cannot exceed the world budget.   • GpuPoolWorld::defineGraph stores independent instanceParameters defaults for each logical name, even when its graph shares a GPU group. Use setNamedParameter(name,parameter,value) to change future emission defaults, with bounded type/range checks. burst(...,const std::array<float,8>* sourceParams) optionally overrides all eight values per call. Stage 28 — diagnostic Metal GPU checkpoints + asynchronous VM error requests#

ComputeParticles::captureGpuCheckpoint(GpuCheckpoint&) (and the graph-runtime wrapper) reads all physical GPU slots, including the 64-byte position/age, velocity/lifetime, tint and size state, the eight 32-bit VM instance parameters and eight VM custom attributes. A checkpoint is marked complete only after all three storage-buffer reads succeed; invalid, unavailable, active-frame or pending birth state is rejected. Stage 29 — transactional CPU checkpoint import and guarded GPU-failure recovery#

fx::ParticleSystem::importLiveParticles(effect, particles) appends already-live particles to a compatible single-emitter effect without replaying Spawn or creating an emitting instance. It validates the entire batch (finite position, velocity, color, age, lifetime, size, eight VM params/attributes), existing CPU capacity and supported emitter restrictions before altering the CPU pool. Each imported particle keeps the position, velocity, age, remaining lifetime encoded as age/total lifetime, size, tint and custom registers. It is tagged with no emitting owner, participates in normal CPU Update and renderer batching, and cannot start new emitter bursts. Unsupported complex ribbons, collision, trigger, mesh and local-space effects are rejected rather than partly restored.

After a successful blocking ComputeParticles::captureGpuCheckpoint, the runtime retains the complete export plus its presentation-frame revision. When switchToCpu occurs after device failure, it attempts recovery only when the checkpoint matches the last submitted GPU frame, has the full physical slot count, and there are no unsent births. Imported particles are counted in ComputeStats::recoveredOnFallback; remaining discarded allocations are reported in lostOnFallback. On stale/missing/invalid snapshots the existing CPU fallback still starts clean and reports losses. RequireGpu continues forbidding an implicit CPU switch.

Recovery is opt-in by capture timing: checkpoints are not collected automatically because the available synchronous Metal RHI readback blocks until the GPU finishes. Exact CPU/GPU numerical continuation is not proven: renderer and simulation algorithms differ, imported particles have no original source instance, and a formerly live effect may stop emitting. Stage 30 — opt-in chunked asynchronous Metal checkpoint capture (source committed, not validated)#

GraphRuntimeOptions::checkpointEveryFrames (or the direct ComputeEmitterDesc::checkpointEveryFrames) controls a disabled-by-default periodic checkpoint request. Every N successful Metal compute submissions the runtime may enqueue a snapshot after Spawn/Integration/Update/Compaction, without waiting for completion. GraphRuntime::requestGpuCheckpoint(callback) and ComputeParticles::requestGpuCheckpoint(callback) allow explicit manual requests. The callback reports bool complete, not a mutable GPU buffer pointer. A failed scheduling attempt returns false and must not yield a usable partial checkpoint.

For each physical GPU slot the snapshot includes 64 bytes particle state, 32 bytes per-particle VM inputs and 32 bytes custom registers — maximum 512 KiB at the current 4096 GPU slots. The Metal RHI now implements readBufferRangeAsync(handle,offset,size,callback) for reads of up to 64 KiB each. The checkpoint splits the three buffers into at most eight small requests, assembles them only after all replies have succeeded, and uses a renderer-lifetime token to cancel callbacks after teardown. At most one checkpoint capture per ComputeParticles instance is pending. A partially queued batch is rejected and never published.

The GPU frame revision is incremented on successful compute submission, fixing the earlier non-incrementing freshness token. The async result stores its originating revision; switchToCpu may restore it only if it still matches the latest GPU frame and there are no pending unsent particles. A periodic snapshot from an earlier frame can remain for diagnostics but is not eligible for a supposedly lossless restoration. Missing, incomplete or stale snapshots retain the explicit loss-counting CPU fallback.

ComputeStats exposes cumulative checkpointRequests, checkpointCompleted and checkpointFailed. An automatic request never blocks render submission with a synchronous read, but enqueues device copies; the callback and CPU assembly still consume resources. The full 512 KiB capture is opt-in and can be costly on mobile. Captures from complex effects are not guaranteed to reproduce an exact CPU trajectory, since GPU/CPU VM and renderer numerical parity has not been demonstrated.

Stage 32 — pooled checkpoint readback admission and live telemetry#

GPU checkpoints are optional and visual-only. Stage 32 adds SpectraCheckpointReadbackBudget.h, a graphics-owner-thread limiter that reserves readback bytes and chunk counts per GPU frame and across in-flight requests. A request exceeding either bound returns false; no partial checkpoint is published. Per-emitter ComputeStats reports checkpointBudgetDenied and checkpointBytesReturned in addition to the existing completed/failed/request counters. The byte counter measures valid callback payload received on CPU; it is not a hardware bandwidth profile. The reservation remains held until callbacks complete or their closures are destroyed, including rejected partial enqueues.

using namespace aiverse::spectra;
auto limiter=std::make_shared<CheckpointReadbackBudget>(
    CheckpointReadbackLimits{});
GraphRuntimeOptions options;
options.checkpointEveryFrames=15; // 0 disables automatic snapshots
options.checkpointBudget=limiter;  // share across standalone GraphRuntime objects

PoolWorldBudgets poolOptions;
poolOptions.sharedCheckpointBudget=limiter;
GpuPoolWorld pool;
pool.init(device,poolOptions); // now every GPU group uses this same limiter

// After any presentation frame / callback deliveries:
const PoolCheckpointStats info=pool.checkpointStats();
// info.pendingGroups / staleGroups / freshGroups / missingGroups
// info.restoreEligibleGroups / budgetDenied / bytesReturned
// info.budget.bytesInFlight / chunksInFlight / frameBytesReserved

If sharedCheckpointBudget is omitted, GpuPoolWorld creates one limiter for all its own GPU groups using PoolWorldBudgets::checkpointReadback. The default ceiling is 512 KiB and 16 chunks per frame; 1536 KiB and 24 chunks in flight. Multiple worlds on the same graphics device must pass the same shared limiter to enforce one device-wide budget; independent worlds otherwise enforce only their local bounds. Standalone GraphRuntime keeps its old independent behavior unless GraphRuntimeOptions::checkpointBudget is supplied.

Pooled identical effects are grouped by complete serialized effect, GPU policy, and now checkpoint cadence. The pool rotates its per-frame GPU group submission start to prevent one permanently first group from consuming the entire shared checkpoint budget. This changes presentation-only dispatch ordering, not ECS simulation or authoritative gameplay.

PoolCheckpointStats is computed on demand without GPU readback and includes successful callback payload counts plus freshness classification from checkpointStatus(). Budget metrics reflect the entire limiter when intentionally shared with other worlds. A fresh checkpoint is merely current at the last submitted GPU simulation revision and is not proof of completed GPU/CPU numerical parity, source continuity, or lossless recovery. No stale snapshot is imported automatically.

Any already accepted graphics commands remain ordered in the device's command buffer; it is not an atomic rollback of earlier GPU DMA operations, and hardware completion still requires the RHI's Metal command-buffer health/fence contract. GpuCheckpointStatus::stagingRecoveryPending, ComputeStats::gpuStagingUploadFailures and PoolCheckpointStats::stagingRecoveryGroups / gpuStagingUploadFailures expose the state in the editor. No gameplay ECS data is affected.

Diagnostic checkpoint format V2 (supersedes Stage 39 V1)#

engine/fx/SpectraCheckpointExport.h now writes an explicit 48-byte V2 header containing a CRC32 over the payload. The bounded raw-body size remains 512 KiB of GPU particle/VM state plus 16 KiB of CPU lifespan mirrors at 4096 slots. The validateGpuCheckpointDiagnostic() function checks header magic, version, exact byte count, slot count and CRC32 without touching graphics hardware. The editor uses this validator before writing a .spfx file.

The earlier 40-byte V1 export is historical and superseded by V2; validateGpuCheckpointDiagnostic intentionally validates only the current V2 format. Neither V1 nor V2 is a portable savegame, stable across arbitrary compiler ABIs, replayable GPU history or authoritative ECS serialization. The binary can be inspected for integrity but does not provide a GPU state import.

Recovery retry and load-shedding hysteresis#

The native GpuPoolRecoveryHost retains its CPU-only PoolRecoveryManifest if importing effects on a newly created graphics Device fails. The host can supply a different healthy replacement Device and retry without requiring the original GPU pool to remain alive. Failed imports remain visibly in DeviceRecreationRequired state; live GPU particles and renderer-owned source handles are never resurrected.

The optional PoolLoadSheddingPolicy::recoverBelowPercent (default 85, range 1..100) introduces hysteresis for estimated particle-count pressure and Stage 32 readback bytes-in-flight pressure. Once automatic bursts are throttled, they stay throttled until the corresponding estimate reaches the lower recovery threshold. This avoids frame-to-frame on/off oscillation near a soft limit. Updating the policy between frames clears both hysteresis latches. Metrics include particlePressureLatched, readbackPressureLatched and pressureHeldFrames. The policy still does not apply to manual one-shot VFX, never queues skipped bursts, and is disabled by default.

Stage 41 — offline V2 checkpoint inspection and safe native capture requests#

V2 checkpoint inspector: no graphics Device required#

The new pure header engine/fx/SpectraCheckpointInspector.h provides inspectGpuCheckpointDiagnostic(bytes) and gpuDiagnosticErrorString(error). It validates one bounded same-build .spfx V2 diagnostic capture without accessing any Metal resources, rendering code, ECS state, or GPU readback API.

The inspector distinguishes invalid magic, unsupported V1/other versions, truncated headers/payloads, invalid header/physical slot counts, mismatched declared sizes, unexpected trailing bytes and CRC32 mismatch. Only after the complete bounded structure and checksum pass does it read individual 128-byte particle records and 4-byte CPU lifespan mirrors. A structurally valid file can still carry semantic warnings: NaN/nonfinite particle values, invalid ages, inconsistent CPU remaining-life mirrors or unusual lifetimes. It reports estimated live/dead physical slots and bounding coordinates for finite live positions. A structural success does NOT certify numerical CPU/Metal parity or a correct gameplay state.

The reusable offline CLI tools/spectrafx/inspect_spfx.cpp requires only a native C++20 compiler and the repository headers:

c++ -std=c++20 -O2 -I. tools/spectrafx/inspect_spfx.cpp -o inspect_spfx
./inspect_spfx path/to/checkpoint.spfx
./inspect_spfx --json path/to/checkpoint.spfx

The CLI checks disk file size before allocating and reading, caps memory at kGpuCheckpointExportMaxBytes (540,720 bytes at the current 4096-slot maximum), detects files that change while being read and emits plain or JSON diagnostics. It returns exit 0 for a structurally valid V2 file (even if it contains semantic warnings), exit 1 for invalid V2 format/integrity, and exit 2 for invalid invocation or I/O. Full usage and the same-build limitations are documented in tools/spectrafx/README.md.

The V2 checksum covers the checkpoint payload. The header and packet layout still depend on the native build's ABI and endianness; V1 conversion, arbitrary-version migrations, serialization portability, GPU buffer import and reverse GPU rewind are intentionally unsupported. Diagnostics may include world positions and graph parameters and should be treated as project data.

Native owner-thread capture and callback lifetime#

A new public <aiverselib/mechanics/SpectraFX.h> integration spectra::GpuPoolCaptureHost (implemented in libraries/include/aiverselib/mechanics/SpectraGpuCaptureHost.h) provides a bounded one-at-a-time request API:

GpuPoolCaptureHost captures(pool);
// Between frames: one requested GPU group with an explicit byte cap.
captures.request(0);
// Each frame, AFTER Device.beginFrame delivers earlier readbacks and
// BEFORE any new pool.step(dt) can invalidate the captured revision:
auto status=captures.pollBeforeStep();
// Between pool.step(0) and the scene render pass, on the same owner thread:
if(captures.status().phase==GpuCapturePhase::Queued)
    captures.submitAfterStepBeforePass();
// Once Ready, bytes are already copied and validated (no new GPU read).
std::vector<uint8_t> bytes;
if(captures.takeReady(bytes)) { /* offline diagnosis only */ }
// Always cancel before pool rollback, shutdown or graphics-Device recreation.
captures.cancel();

The controller maintains an exact GpuPoolWorld::lifecycleEpoch() and request ID, discards results from a recycled/recreated pool, retains at most one bounded byte vector, and permits up to 600 owner-thread graphics-frame polls before returning a timeout. Asynchronous RHI callbacks hold only weak references to the request's shared completion state; they do not capture a dangling host object or force a second graphics owner. Cancellation invalidates publication but cannot forcibly cancel already submitted Metal work; Stage 32 shared checkpoint budget and RHI callback settlement still apply. The status distinguishes Idle, Queued, InFlight, Ready and Failed, with a concrete error when a complete GPU readback has become stale before export.

The sample examples/spectrafx/native_ecs_attachments.h now embeds the capture controller into the single native render-frame lifecycle. It freezes VFX progression and defers read-only ECS source/pose synchronization while the capture is Queued/InFlight/Ready. Each frame continues drawing the current particles via pool.step(0); the host takes or cancels the result before normal presentation resumes. On rollback or device loss, the capture is cancelled before the Stage 38/39 recovery workflow, with no lost/old GPU particle state published as authoritative ECS data. Recovering a valid GPU state still requires the host's existing explicit new-Device reconstruction; captured V2 bytes are not imported.

Recovery hardening#

GpuPoolWorld::boundToDevice(device) allows the recovery controller to explicitly reject an attempted graphics Device replacement that supplies the SAME old Device object even if it temporarily reports healthy. A true recovery requires a different healthy gfx::Device, disposal of old GPU resources while the old Device still exists, import of the CPU-only effect manifest and fresh generation-safe ECS source reattachment. No callback, offline parser or checkpoint diagnostic may bypass this protocol.

Stage 42 — privacy-redacted diagnostics, per-group capture and explicit recovery requests#

Privacy-safe diagnostics are the default#

Stage 41's read-only inspector exposed world bounds and GPU frame identifiers in its JSON/console output. Stage 42 introduces engine/fx/SpectraDiagnosticReport.h and GpuDiagnosticReportPrivacy. The new gpuDiagnosticReportJson(inspection,privacy) returns a fixed aggregate-only schema, without original file paths, per-particle positions, VM scalar values or raw GPU binary data. By default it also redacts scene-coordinate bounds, GPU serial/revision and CRC-based content fingerprints. Each sensitive category requires its own intentional opt-in:

auto inspected=inspectGpuCheckpointDiagnostic(checkpointBytes);
GpuDiagnosticReportPrivacy privacy{}; // all sensitive categories OFF
std::string redacted=gpuDiagnosticReportJson(inspected,privacy);

// Only when a developer specifically requires bounds:
privacy.includeWorldBounds=true;
// Similarly, frame serial/revision/CRC fingerprints are opt-in:
privacy.includeGpuIdentifiers=true;

tools/spectrafx/inspect_spfx.cpp now defaults to redacted text and --json. The explicit --report <safe.json> argument creates one local JSON report, never auto-uploads or automatically includes the raw checkpoint. The optional --include-coordinates and --include-identifiers CLI flags enable only their respective aggregate fields. No CLI option ever prints the original per-particle VM parameter arrays.

The editor adds Save safe JSON report and an intentionally separate Save RAW GPU checkpoint (sensitive). A safe report contains aggregate inspection counters and at most 180 privacy-filtered GPU preview samples (sample ordinal, estimated particles, step result, fresh/stale/pending counts and pending kill count). It excludes exact RHI frame serials, authored graph names, filenames and per-particle positions and VM inputs. Checkboxes permit optional world-coordinate BOUNDS and GPU identifiers, but never raw state inside a safe report. Saving is a direct, local user action under platform::userDataDir()/spectrafx-diagnostics; the system does NOT upload diagnostics or create recurring jobs.

Group selection across a pooled GPU world#

GpuPoolWorld::gpuGroupCount() and gpuGroupSummary(index,out) expose a read-only PoolGpuGroupSummary: active state, estimated particle count, GPU buffer bytes, pending/fresh checkpoint revision status, most recent step/reset acceptance and whether a complete, current checkpoint can be exported. These APIs do not expose serialized effect graph keys or the source effect code. An invalid group index leaves the output unmodified.

The editor displays a bounded index selector for up to the existing 64 GPU-group maximum and scopes both binary saveFreshSpectraGpuCheckpoint(out,index) and saveSafeSpectraGpuReport(out,index,...) to the chosen group. The old one-argument binary-save API still auto-selects the first eligible group for compatibility. Only the editor-owned Metal preview group 0 can be captured directly by the editor; a separately attached external renderer pool remains non-owning telemetry and must run its own GPU capture between safe RHI passes. It is never driven out of render order by a diagnostics UI.

The native GpuPoolCaptureHost::requestNext(policy) selects one currently active group via GpuCaptureTargetPolicy::{RoundRobin,LargestEstimatedGroup, MissingOrStalestCheckpoint}. RoundRobin rotates starting group; the other modes use the previous CPU-estimated active count or the checkpoint's missing/stale revision. Groups already reading back are skipped. Exactly one capture remains queued/in flight per native host and the shared Stage 32 bytes/chunk budget is still authoritative. Requests are owner thread operations, with no background polling, extra GPU contexts or direct synchronous buffer reads.

Native reset and graphics recreation events#

GpuPoolRecoveryHost::requestPresentationReset(purpose) now explicitly schedules a visual reset without submitting GPU commands. On the next safe graphics frame, outside active encoders, the host calls retryPresentationReset(). PoolRecoveryPhase::ResetRequested is distinct from ResetRetryRequired (a failed/incomplete GPU-group reset) and DeviceRecreationRequired (lost GPU or failed new-device import).

PoolRecoveryEvent now includes a stable monotonic transitionSequence that changes only when an observable phase, progress, health or error detail changes. It also reports host reset-request and Device-replacement attempt counters, whether a reset was explicitly queued, and whether a CPU-only recovery manifest is being retained for retry. No event handler recreates a Device itself. A real platform host must construct a distinct healthy gfx::Device and keep the old Device alive until old pooled GPU resources have been released.

The updated examples/spectrafx/native_ecs_attachments.h exposes both explicit per-group and automatic policy-based capture, safe summary retrieval, and a queued reset/status workflow. VFX capture bytes and GPU physical-slot identifiers remain outside authoritative ECS, and lost GPU particles are never falsely reconstructed.

Stage 43 — explicit local safe ZIP bundles, native capture mailbox and bounded GPU recovery retries#

Safe local ZIP support package (no raw GPU state)#

A new header engine/fx/SpectraDiagnosticBundle.h provides makeSafeGpuDiagnosticZip(inspection,frames,output). This creates one bounded, deterministic ZIP STORE archive containing only three fixed filename entries:

manifest.json
checkpoint_summary.json
preview_timeline.json

No zlib or other compression library is required: each ZIP member contains strictly generated JSON and a CRC32. Only a structurally valid V2 inspection and up to 180 renderer-side aggregate GpuSafeTimelineFrame values are accepted. The total ZIP size is capped at 128 KiB, and invalid/oversized requests return false without modifying the caller's output.

The manifest declares the privacy restrictions explicitly: redacted=true, containsRawCheckpoint=false, containsWorldCoordinates=false, containsVmScalars=false, containsGpuIdentifiers=false, and uploadedAutomatically=false. The ZIP builder deliberately has no input argument for raw SPFX bytes, authoring graph paths or arbitrary ZIP entry names. Calling the builder cannot package a raw GPU snapshot accidentally. Even when a developer enables world bounds or GPU identifiers for a separate Stage 42 JSON report, the ZIP remains fully redacted. This is a local support artifact, not an ECS save, GPU replay or cross-build SPFX importer.

The editor's Save SAFE ZIP bundle action creates one .zip under platform::userDataDir()/spectrafx-diagnostics/ only after the user presses the button and an eligible current-revision V2 checkpoint is ready. It uses a local safe-bundle-group-N-M.zip filename, not a GPU frame serial, and refuses to overwrite an existing safe bundle. The related safe JSON report also uses serial-free filename numbering. Only when the report belongs to the editor's own GPU preview are its last 180 sanitized sample counters included; external GPU pools do not inherit unrelated editor preview history.

The offline tools/spectrafx/inspect_spfx.cpp utility now also supports:

./inspect_spfx --bundle /path/to/support.safe.zip /path/to/checkpoint.spfx

The offline ZIP has an empty preview timeline. The binary SPFX source is never added as an archive entry. There is no implicit upload, email, issue creation or external sharing. The existing Save RAW GPU checkpoint (sensitive) button is deliberately a separate user action.

Non-owning native capture mailbox#

The public <aiverselib/mechanics/SpectraFX.h> includes GpuCaptureRequestMailbox from libraries/include/aiverselib/mechanics/SpectraGpuCaptureMailbox.h. The mailbox is a same-owner-thread intent/status holder with states Idle / Requested / Claimed / InFlight / Ready / Failed / ReleaseRequested. It stores one requested group index, a monotonically increasing sequence and bounded failure information; it performs no GPU commands and carries no particle data, graphics handles, ECS mutation or background scheduling.

The native render host may expose a non-owning mailbox pointer to the editor through Editor::setSpectraGpuCaptureMailbox(mailbox). The UI can call Editor::queueSpectraExternalGpuCapture(groupIndex) or Editor::releaseSpectraExternalGpuCapture() on that mailbox, but cannot access gfx::Device or run readBufferAsync itself. The native presentation owner claims a request in its next safe pre-render phase, uses the existing one-at-a-time GpuPoolCaptureHost, keeps VFX state frozen while an async checkpoint is pending, and publishes the same request's state back to the UI. Release is consumed by the native host on the next presentation frame, not during ImGui drawing.

examples/spectrafx/native_ecs_attachments.h now demonstrates this integration and exposes captureMailbox(), poolTelemetry() and recoveryHost(). The application must detach all non-owning pointers from the editor before destroying the native host/graphics Device. If the pool is reset, recovered or shut down, the native host clears the mailbox and cancels the capture; late Metal callbacks cannot reattach to an obsolete source generation.

Recovery status and bounded retries#

GpuPoolRecoveryHost::serviceQueuedResetAtSafeFrame(ownerFrameOrdinal) adds an optional owner-thread reset retry pump. The host calls it only after gfx::Device::beginFrame, outside render/compute encoders. On a recoverable failed reset, the next attempt is spaced by a bounded exponential number of host frames (max 32); this avoids busy reset writes every frame. The returned PoolRecoveryServiceResult distinguishes NoWork, Deferred, ResetSucceeded, ResetFailed and NeedsNewDevice. A lost Device must be rebuilt by the native platform host; it is not retried as an ordinary reset.

The existing PoolRecoveryEvent adds consecutiveResetFailures and retryNotBeforeOwnerFrame, making retry/cooldown status visible without timers. Its transition counter changes on observable recovery state changes rather than spinning duplicate callbacks during the same recovery service call. The updated native example invokes this bounded service in its safe frame before beginning normal presentation and cancels any pending capture before GPU rollback. An optional non-owning Editor::setSpectraGpuRecoveryHost() attachment lets the editor show this status and enqueue a VFX-only reset intent. The editor never executes the actual GPU reset.

Privacy and execution limitations#

The editor resets both sensitive report opt-ins when the selected GPU group or GPU telemetry pool changes, preventing consent from carrying over to a different renderer. A safe ZIP never includes raw particle state or exact GPU device serials. Raw SPFX still contains scene positions/VM values and remains a deliberately sensitive export.
