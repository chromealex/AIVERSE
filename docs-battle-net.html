Battle networking for mobile PvP / PvE (hosted battles)#

Drone Fall-style battles (direct-control heroes, PvP and PvE, phones on Wi-Fi / LTE) run on the engine's own server and rollback stack. No compatibility with Drone Fall's LiteNetLib / ME.BECS protocol is kept; the behaviour it needs is reproduced: input rollback with hash sync, ping and server time, interpolation of corrections, reconnect / late join with a world catch-up, a startup payload per player (SpawnWanderData) and a compatibility key that splits incompatible builds.

Flow of one battle#

  1. The client pings every battle server it was told about (sendBattlePing / readBattlePong, 32-byte request, 10-byte answer with the server's load) and sends the pings plus its compatibility key "<appVersion>|protocol:<n>|map:<mapId>" to matchmaking (Drone Fall's GetCompatibilityKey format).
  2. Matchmaking (the meta backend, out of the engine) groups players, picks a server and calls its control port: allocate with match id, game id, compatibility key, map, seed, players (player id, slot, team, name, loadout bytes), game data, join timeout and time limit.
  3. Matchmaking issues one ticket per player with the server key it shares with the battle servers (issueTicket, or aiverse_battle ticket) and sends it to the player over its own TLS channel.
  4. The client connects: connectSecure(ClientTicket) and hands the connection to NetClient. The server seats the player by the ticket's player id and slot. It never trusts names, slots or ids that the client sends.
  5. When every allocated human is there, or the join timeout passes with at least one player, the match starts. Each client gets MatchPayload first, then MatchStart (matchReady()), builds the simulation from the payload, and calls attach(). Players who are not there join late and receive the whole confirmed history. Players who never come are counted as gone after the reconnect grace.
  6. When the match result is confirmed, every client sends its result blob (setResultReporter) and its result. The server compares the blobs. MatchReport (callback onMatchReport, queue takeReports(), control op reports) carries the result, per-player join / leave / connected state, filtered command counts, the agreed blob, consensus, desync, abort and replay path.

Secure transport#

A handshake works like netcode.io connect tokens, with its own wire format:

  • Request: 0xA1, version, the ticket's sealed part, zero-padded to 1000 bytes. The server opens it with the server key. It checks the expiry against its unix clock, then checks that it hosts that match, player, slot and compatibility hash (Server::admits).
  • Challenge: 0xA2, session id, random nonce, then a salt and cookie encrypted with the ticket's s2c key. Session keys are derived per handshake (BLAKE2b(ticketKey, label | sid | salt)), so 64-bit sequence nonces never repeat under one key, even after many reconnects with one ticket.
  • Response: 0xA3, the cookie encrypted with the derived c2s key. This proves the client holds the ticket keys and receives at its source address. A stolen sealed part is useless without the keys.
  • Data: 0xA4, session id, sequence number, then an XChaCha20-Poly1305 payload. The 13-byte header is authenticated. The payload carries the existing ReliableChannel or LatestChannel bytes, or bye / accept. A 256-packet replay window drops duplicates and replays.
  • NAT and handover: only the client initiates. Keepalives every 250 ms hold the NAT mapping. When an authenticated packet with a newer sequence number arrives from a new address, the session moves there (Wi-Fi to LTE, carrier NAT rebinding). Without path validation, an on-path attacker who races a fresh packet can redirect traffic until the real client sends its next packet. The attacker cannot read or forge that traffic.
  • No amplification: requests are 1000 bytes. Challenges (77 bytes) and pongs (10 bytes) are smaller. Rejected tickets get no answer: the client times out, and nothing becomes an oracle.
  • Half-open handshakes are limited to 256, expire after 5 s, and the oldest is dropped first. Sessions are limited to maxSessions.
  • Keys stay off the command line: servers read them from files (--server-key-file, --control-key-file, create them with aiverse_battle keygen, mode 0600). Tickets are secrets for the client. The game never sees session keys: SecureAccepted::claims has them wiped.

Web builds have no UDP. A browser battle client would need a WebSocket-over-TLS gateway. That gateway does not exist yet.

Loss and latency on mobile links#

SecureLinkConfig::redundancyMs (default 30) makes the reliable channel repeat unacknowledged messages of 256 bytes or less (input frames, tick batches, checksums). It repeats them in the first datagram of a flush after 30, 60, 90, ... ms, without waiting for an RTO. The test secure_stream_tolerates_mobile_loss measures a 20 Hz stream of input frames over 150 ms RTT, 40 ms jitter and 1% loss bursts of 4 packets:

independent lossp95 one-way delivery, with redundancywithout (plain RTO resends)
10%160 ms570 ms
20%260 ms2940 ms

Every message arrived in order in both cases. The base one-way delay is 75 ms plus up to 40 ms of jitter. Plain connectUdp keeps the old behaviour (redundancy off).

Rollback and prediction for a direct-control hero#

The existing RollbackSession (server-confirmed input, client prediction, snapshots, re-simulation) drives the battle. Hero input travels as sticky state (HeroInput.h). There is one scheme: the RTS module's top-down heroes (docs/topdown.md) use the engine-reserved ids, so games, the server's command filter, the load test and the tools all speak it.

  • kCmdHeroInput (0xF100) = kCmdTopDown: topdown::pack(Input) in Command::param: move angle in binary turns (0 = +z, 16384 = +x) and magnitude (per mille), aim angle and the aim / fire bits. The simulation keeps it until the next one and re-quantizes it to its rules (Drone Fall: 45 sectors, full speed or nothing). HeroInputQuantizer (or the client's TopDownControls) sends a command only when the quantized state changes, as Drone Fall's HandleMovement does.
  • When a remote player sends nothing, the session predicts "no command". With sticky state, that means "same input as before", so remote heroes keep moving and shooting. A misprediction only happens when a remote player changes input, and costs a short rollback.
  • kCmdHeroAbility (0xF101) = kCmdTopDownAbility: one button event, topdown::abilityParam(Ability): ability index (255 = escape), phase (tap, press, release, cancel), optionally the button's stick direction and distance; Command::point for a cursor / preview point. A bare index (stage-1 clients) is a tap. net::kCmdHeroAction is kept as an alias of kCmdHeroAbility.
  • The simulation decodes with topdown::unpack / unpackAbility and the fixed-point moveVector, aimVector, directionXZ. Hostile bit patterns are clamped or rejected.
  • Hosted allocations restrict a match to these types (allowedCommands = {kCmdHeroInput, kCmdHeroAbility}) and to maxCommandsPerTick per player. Anything else is dropped on the server and counted in the report.
  • battleSettings(tickRate) gives the mobile room settings: input delay 1, rollback window max(8, 0.6 s) (12 at 20 Hz), lag tolerance 250 ms, a checksum every second, no spectators. Drone Fall runs its logic at 10 Hz with input lag 0. The engine's 20 Hz with delay 1 gives the same 50 ms local response at twice the simulation resolution.
  • Presentation: RollbackSession::setRollbackHook(fn) calls fn(true) right before a rollback and fn(false) after the re-simulation, both at the same tick. Read hero positions in both calls and pass the difference to CorrectionSmoother::correct(). Draw at the interpolated sim position plus offset(), and call advance(dtMs) once per frame. The offset halves every 50 ms. Corrections over 4 units snap. The game client does this for heroes and squad members (TopDownPrediction, ClientTopDown.cpp), and the load test does it for every bot client, reporting corrections and the largest per-frame jump of the sim position versus the drawn position.
  • Local visual prediction: the client draws its own hero where the input already in flight takes it (input delay plus interpolation lag), render only (docs/topdown.md § Network).
  • Desync: checksums every checksumInterval ticks are compared on the server. Desync reaches every client (NetEvent::Kind::Desync), and the report has desync = true and no consensus.
  • The game must freeze outcome state once result() is non-zero, as HeroDuel does. Every client's result blob is then the same, however far past the result tick it has predicted. GameCore does this for every RTS game: the outcome system latches the first result and its blob (outcomeBlob()); see docs/topdown.md § Outcome.

Reconnect, late join and app suspend#

  • NetClient::setReconnect(...) with a lambda that calls connectSecure(ticket) again. After a drop, the client handshakes again with the same ticket. The ticket's expiry bounds this, so give it the match's time limit plus the grace period. The server moves the player's record to the new link. If the client still has the match running, it resumes with a delta: only the input confirmed since its last confirmed tick. Otherwise it gets a full MatchStart with the history and re-simulates.
  • Mobile lifecycle: call net.suspend(now) on FocusLost (iOS applicationWillResignActive, Android APP_CMD_LOST_FOCUS). It sends Away, so the server stops waiting for this player's input and the others do not stall. Call net.resume(now) on FocusGained. After more than 3 s away (the OS has probably killed the socket or the NAT mapping has expired), it reconnects right away instead of waiting for the 10 s silence timeout. The session then fast-forwards within catchUpBudgetMs per frame.

Game client (game.joinBattle)#

The game client joins a hosted battle from UI Lua with the ticket text its matchmaker returned (ClientTicket::encode(), the server address is inside):

local ok, why = game.joinBattle(ticketText, {name = profile.name, compatKey = "1.2.3|protocol:3|map:square"})
game.on("battleFailed", function(e) show_error(e.reason, e.text) end)   -- connect, disconnected, compat, error, ...

net::joinBattle (engine/net/BattleJoin.h) decodes the ticket, refuses an expired one ("expired") or one issued for another build ("compat": the ticket's compatibility hash against compatKey), connects with connectSecure(ticket) and gives NetClient a reconnect with the same ticket. The match then starts like any network match: when MatchPayload + MatchStart arrive the client checks the payload's compatibility key (battleCompatible), builds the map with applyBattlePayload — a seat's loadout that is a JSON object is merged into players[slot - 1] of the map (for example {"deck": {...}}, progression.md), match-wide gameData that is a JSON object becomes the map's "battle" key — and attaches the simulation. The result reporter sends GameCore::outcomeBlob(). On phones the client calls suspend / resume on focus loss / gain. A failed connect (rejected tickets get no answer: the 10 s connect timeout), a lost battle after the reconnect window or a payload for another build ends the battle, goes back to the menu and emits battleFailed {reason, text}. Web builds return "unsupported" (no UDP). Test: battle_join_by_ticket_payload_and_compat (aiverse_battle_tests).

net::ServerConfig cfg; cfg.hostedOnly = true; cfg.udpPort = cfg.wsPort = 0;
cfg.onMatchReport = [](const net::MatchReport& r) { /* send to meta */ };
net::Server srv(cfg);
srv.listenSecure(27017, serverKey);
net::MatchAllocation a; /* matchId, gameId, compatKey, map, seed, players + loadouts, gameData */
srv.allocateMatch(a, &error);
for (;;) srv.update(net::nowMs());

MatchPayloadMsg gives every client the same bytes: match id, compatibility key, map id, game data, and each slot's team, kind, name and loadout. These replace Drone Fall's SpawnWanderData startup packets. Build the simulation from them in setup, not through commands. In-match progression (rules progression, progression.md) reads each seat's battle deck (units per slot, unlock flags, initial perks, tech level) from the map's players[i].deck: decode the seat's loadout into that entry when building the match map, so every client builds the same decks. releaseMatch(id) aborts a match. hostedMatches() lists matches. Hosted matches skip the server's Elo, because ratings belong to meta. Lobby rooms, queues, the RTS relay and their protocol are unchanged (kProtocolVersion is still 3). The new messages are additive: Away and ResultReport from the client, MatchPayload from the server.

Dedicated process and orchestration#

aiverse_battle keygen > server.key; aiverse_battle keygen > control.key; chmod 600 *.key
aiverse_server --udp-port 0 --ws-port 0 --hosted-only --battle-port 27017 --server-key-file server.key \
  --control-port 27018 --control-key-file control.key --max-matches 64 --public-address play-eu1.example.com:27017
aiverse_battle control --key-file control.key --address 10.0.0.5:27018 allocate match.json   # see BattleControl.h
aiverse_battle control --key-file control.key --address 10.0.0.5:27018 status | reports | release 42
aiverse_battle ticket --key-file server.key --match 42 --player u1 --slot 1 --compat "1.2.3|protocol:14|map:square"
aiverse_battle ping play-eu1.example.com:27017

Each control line is <hex BLAKE2b-mac> <json>. A request carries ts (within 30 s of the server's clock) and a unique nonce. Responses are signed the same way. The channel carries no secrets, but keep it on a private network or loopback. Capacity is --max-matches, and allocate fails when the server is full. The orchestrator spreads matches over processes and machines using status (capacity, running, clients). It sends each player to the server with the best pings (the pong carries the load). It collects reports and calls release for matches it wants gone. There is no fleet autoscaler or cross-region directory. Both are backend work.

Load test#

aiverse_battle load --matches 50 --players 2 --seconds 30 --profile bad [--suspend] [--rebind] [--json]

This runs one hosted battle server with N HeroDuel matches (apps/battle/HeroDuel.h, a stand-in top-down shooter with heroes, projectiles, dashes and loadouts, speaking the same hero commands), or with --project DIR [--map FILE] [--rules-patch JSON] N matches of an RTS top-down project (apps/battle/RtsBattle.h: GameCore simulations, heroes steered by the computer pilot, ability taps, the frozen outcome blob as the report). Every player is a bot client with its own simulation, connected over the secure transport through the simulated mobile network, all on a virtual clock in one process. It reports finished matches, agreed results, desyncs, rollbacks, how far clients run ahead of confirmation, server update time (p50 / p99 / max), server CPU share and bytes per player. Profiles: lan, wifi, 4g, 3g, bad (20% loss + bursts, 150 ms RTT, 40 ms jitter, 1% duplicates). Override them with --loss, --rtt and --jitter.

Measured in the Linux VM (aarch64, gcc Release) with --matches 50 --players 2 --seconds 30 --profile bad: all 50 matches finished, all 50 result reports agreed, 0 desyncs. Clients ran on average 4.5 ticks (max 12, the window) ahead of confirmation. Server update time: p50 0.19 ms, p99 0.34 ms, max 2.2 ms, about 1.9% of one core for 100 players. Traffic per player, packet headers included: about 4.9 KB/s up and 9.3 KB/s down. The whole run took 1.3 s of wall time. Clients and server share one process and the network is simulated: these numbers show what the relay costs. They are not a WAN capacity figure. For the HeroDuel stand-in, most traffic is commands (about one per player per tick, because the bots re-aim constantly) and their redundant copies.

Visibility and anti-cheat: what this does and does not do#

  • Identity is server-side: slot and player come from the ticket, names come from the allocation, and a ticket is bound to one match, one slot and one compatibility hash.
  • Input is limited: a player can only command its own slots, command types are allowed per match, and commands per tick are capped. Results need every reporting client to agree on the blob, plus the existing checksum desync detection and server arbiter re-simulation (ServerConfig::arbiter) for disputed or abandoned matches.
  • Not solved: lockstep / rollback gives every client the whole simulation state, so map hacks (seeing through fog, enemy loadouts) cannot be prevented by the transport. Interest management needs server-authoritative snapshots, which is the FPS authority path (engine/net/authority), not this one. A PvE match with a single human has nobody to disagree with: run the arbiter on a sample of reports, or on all reports that grant valuable loot.
  • No TLS for the control channel (it is MAC-authenticated only), no key rotation, no DDoS scrubbing, no fleet orchestration service. These belong to deployment.
