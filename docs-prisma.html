PRISMA — universal AIVERSE post-processing#

PRISMA is the name of the full-screen effects and image-processing system. Not to be confused with SpectraFX, the particle/VFX system. Existing game formats do not change.

Ownership boundaries: PRISMA and SpectraFX#

PRISMA owns post-processing of the final image: HDR/tonemapping, Bloom, color grading/LUT, DoF, Motion Blur, FXAA/TAA/upscaling, screen-space GI/AO/SSR, camera volumes, screen-space Shader Graph (domain postfx), render-pass dependencies and performance budgets.

SpectraFX owns world visual effects before post-processing: emitters/particles, smoke, fire, explosions, ribbons, trail streams, CPU/GPU particle simulation, VFX graph authoring and ECS events. SpectraFX produces the scene's HDR contribution; PRISMA may then apply Bloom to the whole scene. The systems do not duplicate each other, do not depend on genre and are not part of deterministic gameplay state.

The canonical sources are now engine/render/Prisma.{h,cpp}, PrismaData.{h,cpp}, PrismaShaders.h, PrismaVolumes.h. Editor: apps/editor/core/PrismaOps.{h,cpp} and apps/editor/windows/PrismaWindow.cpp. Legacy PostFx headers forward to PRISMA; the legacy .cpp files contain no implementation. The stable JSON postfx, MCP postfx_* and editor saved id postfx must not be renamed: they are external formats, not code owners.

Current design#

  • Main C++ API: #include "engine/render/Prisma.h"; class aiverse::render::Prisma.
  • Compatibility: PostFx and PostFxData are source alias/forwarding includes; the main compilation goes through Prisma.cpp and PrismaData.cpp. The old postfx_* MCP names are kept.
  • Renderer3D requests PostProcess::scenePass and calls resolve(); with HDR/High, ScreenLighting performs screen-space lighting and TAA before the final resolve.
  • Parameters: game.json / map, postfx merged by effect type; the editor panel and MCP operations are already implemented.
  • GPU/RHI: GLSL/MSL, HDR RGBA16F with ACES and sRGB, RGBA8 fallback; the current chain has a fixed order. UI is drawn after PRISMA.

PrismaRenderGraph — stage 07 (GPU-free planner)#

engine/render/PrismaRenderGraph.h is the first RHI-independent implementation of a description of passes and resources. PrismaRenderGraph::addResource/addPass/compile build a stable topological order and check for one writer per resource, identifier errors, feedback read/write within a single pass and dependency cycles. PrismaGraphPlan contains order, resources (first/last use), slots and the number of bytes of allocated internal textures. Transient resources compatible in format and size with non-overlapping lifetimes share one slot; history and resources with allowAlias=false do not share a slot. External input/output/history are supplied by the caller and are not allocated by the planner.

Important: for now this is only a dependency graph + lifetime planner, not a GPU executor. The real Prisma::resolve() still executes the current fixed pipeline. Do not claim that the RenderGraph already drives rendering; the next stage is an RHI resource pool and execution callbacks with real pass bindings. Incorrect dependencies are deliberately rejected rather than fixed by an implicit shader blit.

Test code: tests/render/prisma_graph.cpp, CTest prisma_graph; with AIVERSE_BUILD_TESTS=ON it is included in the standard CMake ALL build and ./run-tests.sh. A native test run is still required.

Target interfaces#

  1. GPU-free PrismaProfile, PrismaVolume, PrismaVolumeStack and parameter resolution by camera position.
  2. A declarative PrismaGraph with typed resources (SceneColor, Depth, Velocity, History, LUT, Output), topological order and lifetimes, without ties to FPS/RTS.
  3. DepthOfField, MotionBlur, AutoExposure, GTAO and LensDistortion effects as separate passes with quality-tier fallback.
  4. MotionVectors / reactive masks and temporal upscaling; a separate history invalidation policy on camera cut/LOD/resize.
  5. GPU pass profiler, checks for resource-hazard dependencies, a node editor and full automated RHI verification.

For agents and integrations#

Official skill: skills/visuals/aiverse-prisma/SKILL.md, registered in tools/skills/catalog.py and skills/catalog.json. The old postfx_* commands belong to PRISMA as a compatible external API. The generic ShaderGraph compiler is shared infrastructure, but the full-screen postfx domain and its shaders belong to PRISMA. The old sources PostFx*.cpp and ScreenLighting.cpp are empty compatibility translation units; do not make changes in them. Follow the boundaries in AGENTS.md and write a handoff after every stage.

Camera Post Process Volumes — stage 08#

PrismaVolumeStack is now used in the game client and in the editor's Scene/Game viewports. At map start the client reads game.json["prismaVolumes"] and map["prismaVolumes"] via parsePrismaVolumes; before Renderer3D::render(...,&prisma) it calls prisma.applyCameraVolumes(stack,camera.eye()), and after resolvePrisma() it resets the settings to the base profile. The editor caches the profile by JSON signature and resolves it separately for each camera; the postfx change is not mutated.

Example game.json (the same top-level block can be given on a map):

"prismaVolumes": {
  "volumes": [
    {
      "id": "underwater",
      "shape": "box",
      "center": [12, -5, 20],
      "halfExtents": [15, 6, 12],
      "blendDistance": 3,
      "priority": 10,
      "layerMask": 4294967295,
      "weight": 1,
      "profile": {
        "effects": [
          {"type": "colorGrade", "saturation": 0.5, "temperature": -0.3},
          {"type": "vignette", "intensity": 0.4}
        ]
      }
    }
  ]
}

Shapes: global, sphere (center, radius) and box (center, axis-aligned halfExtents). weight is in [0,1], blendDistance is the fade distance beyond the outer boundary; priorities are processed in ascending order and equal priorities keep insertion order. layerMask filters cameras, enabled disables the volume.

The profile inside a volume uses the same existing postfx schema, not a new shader library. Specifying "hdr" or "enabled" explicitly enables the corresponding override; absence of these keys keeps the base profile's value. On a map, a volume with the same id replaces the game one; "replace":true in the map block removes all game volumes before applying the map list. Invalid entries are skipped with issues; authored JSON is not changed.

Limitations: the body volume is not yet an oriented box (no rotation), there is no spatial index/priority GPU culling, the camera mask defaults to all bits; the regular GameClient/Editor apply mask all. Interpolation changes only explicitly specified effect parameters (stage 09); other parameters, minQuality and LUT paths keep their base values. For a native C++ profile without masks the legacy full-profile behavior is kept. Discrete settings switch at weight >= 0.5, numeric parameters blend in float on the presentation side. Do not store such a float stack in authoritative ECS state. The new prismaVolumes data is optional and does not affect old projects. Code: PrismaVolumeData.{h,cpp}, PrismaVolumes.h; CPU tests: tests/render/prisma_volume.cpp / CTest prisma_volume (a test run is still required).

Stage 09 — per-parameter blending#

PrismaVolumeEffectMask in PrismaVolumes.h and PrismaVolumeData.cpp::authoredEffects map each effect to a bitmask of the parameters explicitly specified in JSON, including color components, the enabled/minQuality flags and the LUT text path. When a volume sets only colorGrade.exposure, the source colorGrade.saturation, contrast, lift/gamma/gain and minQuality are not overwritten. When the base effect is absent, a neutral profile with a smooth entry is added for ColorGrade/Bloom/effects with intensity or amount; for discrete effects the threshold is 0.5. For direct native C++ creation of a volume without effectMasks the old full-profile behavior is kept. The prisma_volume tests are extended to cover preservation of unrelated parameters, but a native run is still required.

Stage 10 — visual editing of Camera Volumes#

The PRISMA — Постобработка panel (apps/editor/windows/PrismaWindow.cpp) now contains a PRISMA Volumes section in the current scope: the whole game (game.json) or the open map. It can create a global/sphere/box volume, center the volume on the Scene camera, and edit id, enabled, sizes, priority, weight, blendDistance, layerMask and nested effects. Next to each effect parameter there is an inherit/override toggle: clearing an override removes the corresponding JSON key rather than writing the default. This matches PrismaVolumeEffectMask and prevents resetting the global contrast/saturation.

Authoring uses the shared GPU-free makePrismaVolumeJson(id, shape, center) from PrismaVolumeData.h — the same format as the runtime parser and the CPU test prisma_volume. Map changes go through MapDoc::beginEdit/touched (undo), game changes through saving the manifest, as in the existing PostFX sliders. The Scene camera shows the number of applicable effects/volumes and parser warnings.

Limitations: there are no volume gizmo outlines in the viewport and no Shader Graph payload editor inside a volume — the separate Shader Graph Editor remains for that. The UI uses the existing ImGui and editor layout. Neither compilation, nor GUI smoke/undo parity, nor GPU screenshots were verified at this stage; the agent must confirm them natively before merging. The old panel ID postfx and the MCP commands postfx_* are kept.

Stage 11 — GPU-free typed RenderGraph dispatch#

engine/render/PrismaGraphDispatch.h adds a header-only, genre-independent dispatchPrismaGraph<Handle>(graph, plan, bindings, callback) contract. PrismaGraphBindings<Handle> contains one entry per graph resource for external handles and one entry per compiled transient slot for physical allocations. PrismaGraphDispatchView::resource(id) resolves a logical resource through the compiled aliasing plan; the host supplies the typed RHI handles, command encoders and texture transitions.

Validation completes before any callback: invalid plans, mismatched binding counts, unbound handles, duplicate pass IDs and invalid resource references are rejected without partially drawing a frame. The callback runs in deterministic topological order, and returning false aborts subsequent passes with an error and exact number of completed passes.

This is not an RHI executor and does not allocate GPU textures, create encoder barriers, perform render passes or bind PRISMA's current fixed chain. An external integration must first create and retain physical slots, manage external/history resource lifetimes, provide synchronization and connect the existing Prisma::resolve calls. Keep the legacy renderer enabled by default until native Metal/GL validation and image parity tests pass.

Tests are appended to tests/render/prisma_graph.cpp / CTest prisma_graph. Native build, CTest and GPU tests have NOT RUN in the GitHub-only agent environment; see docs/handoffs/prisma-stage-11.md.

Stage 12 — Physical Resource Pool (GPU-agnostic)#

engine/render/PrismaGraphResourcePool.h provides a host-owned pool of physical render target handles for PrismaGraphPlan::slots. The host creates targets with a create(format,width,height) callback and releases them with release(handle); this header never calls GPU/RHI APIs.

  • prepare(graph, plan, create, release) reuses allocations with identical format/dimensions and matching history resource name, or creates new targets. It never selects the same allocation twice within a single frame. On allocation failure it releases targets allocated during that prepare call and preserves the previous pool entries.
  • markHistoryWritten(name) marks successfully produced temporal pixels valid; invalidateHistory() discards temporal contents on camera cuts/teleports without discarding reusable GPU storage. If prepare returns a false history-valid bit, the caller must avoid reading the old history and use a non-temporal fallback. Resize changes resource descriptors and always allocates a fresh history.
  • pruneUnused(release) frees allocations not selected by the last successful prepare; clear(release) releases all allocations. Call both only after GPU fence completion, not while earlier frames might still reference them.
  • Use one pool instance per independent camera/view/temporal stream, not one global mutable history across cameras. The pool does not allocate external resource bindings, compute barriers, issue render passes or integrate itself into the existing Prisma::resolve. It is an opt-in host contract.

Tests for reusable physical slots, valid/invalid history, resize/pruning, allocation rollback and clearing are in tests/render/prisma_graph.cpp. Native build/CTest/GPU screenshot verification is NOT RUN for Stage 12. See docs/handoffs/prisma-stage-12.md.

Stage 13 — Opt-in RHI graph adapter (not yet wired into Prisma::resolve)#

engine/render/PrismaRhiExecutor.h bridges the GPU-free Stage 11 graph and Stage 12 allocation pool to the existing gfx::Device API. It creates TextureDesc{renderTarget=true} targets, maps RGBA8/RGBA16F/Depth32F to the backend's supported formats, uses copyColor for one-input/one-output matching RGBA8 Copy passes, and executes Raster callbacks inside balanced beginPass/endPass scopes. Compute callbacks run outside render passes only if Device::supportsCompute() reports support.

A native host explicitly creates a per-camera PrismaRhiExecutor(device) and calls execute(graph,plan,external,raster,compute,optionalDepth) outside any existing pass. Raster callback signature is bool(gfx::Device&, PrismaGraphId, const PrismaGraphDispatchView<gfx::TextureHandle>&); it binds its own pipeline, uniforms and input textures. Compute has the same callback signature but is responsible for opening/closing any compute encoder it needs. optionalDepth must match raster target dimensions if the chosen Metal backend needs a depth attachment. The adapter never calls endFrame, presents, performs implicit shader conversions, or modifies ECS.

Compatibility constraints: currently no RG16F/R32F target formats in gfx::PixelFormat; these graphs fail preflight. The portable copyColor interface only guarantees same-size RGBA8; HDR/other copy operations need explicit raster shader passes. gfx::Device does not expose a universal resource-barrier API. GPU target release and pool reset must happen at a caller-managed safe point after in-flight work finishes. Temporal history is valid only after the host has successfully produced its pixels and explicitly marked it written.

Not a complete render pipeline migration. Prisma::resolve() still uses the legacy, shipped fixed pass chain by default, with no automatic RHI graph execution. The header is an opt-in integration point, and the test addition currently covers only RHI format mappings in tests/render/prisma_graph.cpp. Native build, driver smoke, screenshots and numerical parity remain NOT RUN. See docs/handoffs/prisma-stage-13.md.

Stage 14 — experimental graph-driven SDR FXAA#

The first production call site of PrismaRhiExecutor is an opt-in SDR FXAA prepass in Prisma::resolve(). Set AIVERSE_PRISMA_GRAPH_FXAA=1 to create a two-external-resource graph (scene-fxaa -> fxaa-output) and execute the existing FXAA pipeline, same uniforms and texture bindings, through a single RHI raster pass.

The default code path is unchanged. The experimental path is only used when FXAA is active, the scene is RGBA8/SDR, the FXAA pipeline is valid, both color textures exist, and the matching depth attachment was created. If the graph cannot be compiled/dispatched, the original direct draw() path runs instead. Graph preflight happens before any draw submission; the shader uses exactly one full-screen draw and writes the complete destination. The opt-in pass clears neither color nor depth.

The graph has no internally allocated targets; it uses the existing Sized per-view resources. It does not switch on graph-rendered HDR, bloom, temporal AA, or the final composite. There is no new JSON schema, editor toggle or change to SpectraFX. This is a guarded runtime foothold, not a whole-chain render-graph migration.

GPU parity and native CMake/CTest remain NOT RUN. The test source in tests/render/prisma_graph.cpp checks only graph structure and single-pass binding/dispatch logic, not Metal/GL pixel correctness. For reproduction and outstanding validation, read docs/handoffs/prisma-stage-14.md.

Stage 15 — Bloom Prefilter opt-in and legacy clear parity#

PrismaRhiExecutor::execute now defaults raster passes to the same opaque-black color clear and depth clear as Prisma::draw. An additional clearRasterTargets=false argument is available for explicitly overwrite-only pipelines, but the FXAA and Bloom experimental call sites use the default legacy-compatible behavior. This fixes a known Stage 14 parity risk.

AIVERSE_PRISMA_GRAPH_BLOOM_PREFILTER=1 opts only the first Bloom Prefilter raster pass into PrismaRhiExecutor. It uses the existing kPrefilter shader pipeline, uniform block and one source texture; the input/output resources are externally managed Sized targets (full-resolution input, lower-resolution output), and the graph does not allocate transient textures. In HDR mode both resources are declared RGBA16F, otherwise RGBA8. Both are supported by the existing conditional RHI path.

The rest of the Bloom downsample/upsample chain remains the original direct renderer; the FXAA experiment still uses its independent AIVERSE_PRISMA_GRAPH_FXAA=1 flag. The default path is unchanged and any preflight/allocation failure falls back to Prisma::draw. The experimental raster callback returns true after a submitted draw; failure after GPU submission cannot be rolled back. No full-frame parity has been established.

tests/render/prisma_graph.cpp now has CPU-only graph contracts for SDR and HDR prefilter sizes, bindings, single-dispatch and missing output preflight. These sources have not been compiled or run in this agent environment; Metal/GL screenshots and GPU timings are also NOT RUN. See docs/handoffs/prisma-stage-15.md.

Stage 16 — opt-in full Bloom down/up RenderGraph#

AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1 enables an experimental full Bloom Prefilter → Downsample → Upsample graph inside Prisma::resolve(). The flag is off by default. The graph declares one external Scene input and external per-level down/up targets backed by the existing Prisma::Sized per-view texture cache. Every downsample reads the previous mip; each upsample reads the lower intermediate plus the matching down mip. All passes use the existing kPrefilter, kDown and kUp GPU shader programs, exactly the original size-dependent uniforms, tint/radius normalization, source bindings and texture formats (SDR RGBA8; HDR RGBA16F). The host creates the depth attachments for each output size before execution.

The RHI executor now accepts an optional trailing std::function<gfx::TextureHandle(PrismaGraphId)> rasterDepthForPass. When supplied, that attachment replaces the shared rasterDepth for each pass; this is necessary on Metal for different Bloom mip dimensions. Existing Stage 14/15 executor users continue to use the previous optional shared depth and legacy-compatible clear defaults.

Scope/limitations: this is real RHI graph scheduling of Bloom raster passes, but it is not yet adoption of Stage 12's transient graph pool: the host supplies externally cached target textures, which already persist per viewport. There is no automatic RHI in-flight retirement queue or resource barrier API. The complete graph is rebuilt on each opt-in frame, and Prisma::resolve() retains the old path as fallback when graph preflight fails. On any unexpected failure after GPU pass submission, the graph is not replayed (partial rendering must not be double-submitted). No effect outside Bloom was migrated during this stage. If both AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN and the Stage 15 prefilter-only flag are set, the full-chain flag takes precedence on success.

New GPU-free graph tests check 1/2/4 downsample levels for SDR/HDR, topological order, valid binding resolution, and rejection of missing mip targets before pass execution. Those sources have NOT RUN in a native compiler or on a GPU; see docs/handoffs/prisma-stage-16.md.

Stage 17 — per-view compiled Bloom topology cache#

engine/render/PrismaBloomGraph.h provides a GPU-free PrismaBloomGraphCache. configure(sourceWidth,sourceHeight,format,mips) compiles the complete Bloom topology once per source size, HDR/SDR format and mip shape list. Repeated frames with the same structure reuse graph(), plan() and operations(); changed quality/mip sizes trigger compilation of a replacement graph. Failed reconfiguration leaves the previous valid configuration intact, but the renderer never executes that stale graph for the incompatible current layout.

The main Prisma::Sized viewport cache now owns a PrismaBloomGraphCache, so Scene/Game views have separate graph layouts and no cross-view history. The Stage 16 opt-in path AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1 uses the cached immutable graph and rebuilds only the frame bindings: threshold/knee/scatter, shader uniforms, source and output texture handles, and per-mip depth attachments. The existing fallback and default-off behavior are preserved. Stage 12 transient target pooling remains a separate future integration; cached topology itself allocates no GPU textures.

This is implementation-only work; CMake, CTest and real GPU validation were intentionally deferred at the user's request. See docs/handoffs/prisma-stage-17.md.

Stage 18 — GPU completion-gated retirement and persistent view executor#

engine/render/PrismaGpuRetirement.h introduces PrismaGpuRetirementQueue<Handle>: retire(handle,submissionFence) transfers an allocation to a pending queue; collect(completedGpuFence, release) invokes the release callback only when the GPU has reported completion through a caller-managed fence/event. drainAfterGpuIdle is valid only after an explicit GPU idle synchronization. A CPU frame counter or gfx::Device::frameSerial() is not a completion fence.

PrismaGraphResourcePool::retireUnused/retireAll now transfer allocations to the caller instead of destroying them immediately. PrismaRhiExecutor::retireUnused/retireAll/collectCompleted wires those operations to its queue and calls RHI destroyTexture after the supplied completed fence. resetAfterGpuIdle() also releases all pending and current allocations, but only if the host has ensured the GPU is idle.

Every Prisma::Sized viewport now holds a lazy persistent std::unique_ptr<PrismaRhiExecutor>, shared by its opt-in FXAA, Bloom prefilter and full Bloom graph calls. It retains resource pool state across frames rather than creating a new executor on every pass. Lifetime is tied to the existing Sized cache. This does not yet make PRISMA use graph-owned Bloom targets; those remain external RHI textures in Sized, and graph execution stays opt-in.

Backend integration constraint: Gfx does not yet provide a portable completed-GPU-fence API. Hosts must pass actual completion signals to collectCompleted. Existing viewport eviction and renderer shutdown still destroy their legacy textures at the current existing release points; they are not automatically made GPU-fence-safe by this opt-in queue. Actual backend fence wiring and transient Bloom pool migration remain future features. Testing/build/GPU verification deliberately deferred at user request. See docs/handoffs/prisma-stage-18.md.

Stage 19 — opt-in graph-owned Bloom mip allocation#

With both AIVERSE_PRISMA_GRAPH_BLOOM_CHAIN=1 and AIVERSE_PRISMA_GRAPH_BLOOM_POOL=1, the complete Bloom RenderGraph can now allocate its own downsample/upsample targets through PrismaGraphResourcePool in the persistent per-viewport RHI executor. Only the input Scene/FXAA color is external. The graph declares every Bloom mip as an internal resource, enabling the planner to alias identical-format/size GPU textures when their lifetimes do not overlap. Without the new pool flag, the existing Stage 16 graph still uses Sized::targets as external resources. Both experimental flags are off by default.

PrismaRhiExecution::resources now maps each logical graph resource to its actual external or pooled RHI texture handle. The final Bloom composite samples resources[cache.outputId()] when pooled mode succeeds. Per-pass depth attachments still come from the established Sized::depths cache; thresholds, scatter, shader pipelines and source UV conventions are unchanged. On graph preflight/allocation failure before GPU submission, the code allocates legacy mip targets and uses the existing Bloom fallback. A failure after GPU submission does not attempt to replay partial passes.

Ownership: pooled RHI textures persist with their viewport executor, rather than being released after each frame. Reconfiguration keeps unselected allocations until explicit safe retirement; their eventual release depends on GPU-completion reporting or a confirmed GPU-idle shutdown. No portable completed-fence backend is yet wired, so automatic mid-flight eviction is deliberately not used. Existing view eviction still follows legacy release assumptions, and memory benefits are not quantified. This experimental path needs build/GPU verification before being enabled by default.

Implementation-only stage: testing intentionally postponed at user request. See docs/handoffs/prisma-stage-19.md.

Stage 20 — Tilt Shift graph opt-in#

AIVERSE_PRISMA_GRAPH_TILT_SHIFT=1 routes the existing three-pass Tilt Shift (downsample, horizontal Gaussian blur, vertical Gaussian blur) through PrismaRhiExecutor. Four logical SSA resources describe the source, first A target, B target and final A target. The two versions of A are deliberately mapped to the same existing physical texture: they are never simultaneously needed, and the intermediate B is separate. Per-pass uniforms and original pipelines are preserved. The default path remains the legacy three draws. Missing resources or failures before GPU submission fall back to it; partially dispatched passes are not replayed. This stage does not yet migrate physical Tilt targets to the graph-owned pool, nor does it activate Tilt Shift by default. Native/GPU tests deliberately NOT RUN per user request. Handoff: docs/handoffs/prisma-stage-20.md.

Stage 21 — Sun Shafts graph opt-in#

AIVERSE_PRISMA_GRAPH_SUN_SHAFTS=1 enables a two-pass graph for the existing sunlight prefilter mask and radial scattering operation. The sun position, offscreen edge fallback, visibility threshold, color, quality tier, sample count and shader uniforms are unchanged. Three externally owned textures represent the source, mask and radial output, with the existing per-size depth attachment. The two-pass graph executes through the per-viewport RHI executor. Failure before any submission uses the legacy two-draw path; a partially submitted graph is never replayed. The path remains off by default and the HUD is still drawn after postprocessing.

No new serialised settings or shader variants were introduced. This stage is code-only, intentionally NOT compiled or GPU-tested yet. See docs/handoffs/prisma-stage-21.md.

Stage 22 — experimental depth-based Depth of Field#

The new depthOfField entry in postfx.effects is handled by the shared PRISMA data catalog (MCP and editor parameter discovery are data-driven). Parameters are focusDepth (0..1 GPU device depth, not metres), focusRange (depth interval), maxBlur (0..16 output pixels) and intensity (0..1). Defaults: 0.5, 0.08, 8, 1 respectively. This entry defaults to High post quality and is classified Heavy in the cost estimation model.

The opt-in AIVERSE_PRISMA_DOF=1 activates one full-resolution nine-neighbour blur pass before SDR FXAA and Bloom; it reads the scene color and render-target depth using the existing GLSL/MSL fullscreen-program path and produces a new color texture used as the source by subsequent effects. The hardware depth is deliberately not represented as physical focus distance, since the PostFrame currently lacks a portable inverse-projection/near-far contract. The blur radius follows the distance between sampled hardware depth and focusDepth, with a central sharp interval. The shader is a bounded, approximate defocus, not cinematic hexagonal bokeh, depth-layer separation or physically accurate lens simulation.

The pass samples the original scene depth, but uses its own scratch depth attachment of matching dimensions, avoiding read/write feedback on the same depth texture. It can run only when the configured effect, opt-in flag, necessary GPU resources and pipeline are present. Without the flag, existing image processing continues unchanged. DoF is disabled on low/medium quality by its default minQuality=high, unless a project explicitly overrides it.

Example game.json postfx.effects entry:

{"type":"depthOfField","focusDepth":0.65,"focusRange":0.08,"maxBlur":6,"intensity":0.8}

All native compilation, CTest and visual/GPU smoke are intentionally NOT RUN at the user's request. Real Metal/GL depth texture sampling compatibility, reverse-Z behavior and scene-depth interpretation need later validation. The next feature is true world-distance autofocus via camera projection data, followed by multi-resolution CoC separation and physically-inspired bokeh. See docs/handoffs/prisma-stage-22.md.

Stage 23 — HDR Auto Exposure (GPU log luminance + eye adaptation)#

postfx.effects can now contain {"type":"autoExposure"}. The optional feature remains disabled in rendering unless AIVERSE_PRISMA_AUTO_EXPOSURE=1 is set and the current scene is using linear HDR RGBA16F. On SDR/RGBA8, the effect has no GPU action, because clipped highlights cannot be recovered by metering.

The GPU pipeline in Prisma::resolve() is:

  1. Read scene-linear RGB and store log2 luminance in a half-resolution RGBA16F target (four color taps with Rec.709 luminance coefficients).
  2. Repeatedly average log luminance through a 2x2 pyramid to 1x1. This estimates geometric mean brightness, not a full per-bin histogram.
  3. Determine target exposure 2^(clamp(log2(keyValue)-meanLogL+ compensation, minEV, maxEV)). In a dedicated RGBA16F 1x1 ping-pong pass, blend from previous exposure using 1-exp(-speed*deltaSeconds). speedUp controls increasing exposure (dark->bright output); speedDown decreasing exposure. The time delta is clamped at 0.1s to avoid large jumps after stalls.
  4. Sample the resulting exposure multiplier as TEX8 in the final composite before HDR tonemapping and sRGB conversion. UI remains unprocessed. ColorGrade's manual exposure/compensation still multiplies the automatic result.

Parameters (regular PrismaData catalog and editor/MCP discovery):

parameterdefaultrangemeaning
keyValue0.180.01–1target scene middle grey
minEV-6-12–0lower automatic EV limit
maxEV60–12upper automatic EV limit
speedUp30.01–20brighten response rate, 1/s
speedDown10.01–20darken response rate, 1/s
compensation0-5–5EV bias

Example:

{"type":"autoExposure","keyValue":0.18,"minEV":-4,
 "maxEV":4,"speedUp":2.5,"speedDown":1.0,"compensation":0.0}

Per-Prisma::Sized temporal history uses two 1x1 HDR textures and a previous timestamp. Explicit native Prisma::resetAutoExposure() invalidates history for camera cuts. Project reconfiguration, postprocess toggle and quality changes reset it; a disabled HDR/auto mode also clears valid history. The first enabled frame snaps to the current measured exposure, avoiding reading an uninitialized history texture. No CPU brightness readback is used.

Limitations: the algorithm computes mean log luminance, not a percentile histogram; bright outliers may still influence adaptation, and the measurement is not a physically calibrated light meter. The existing Sized cache is keyed by dimensions rather than stable camera identity, so two viewport cameras of identical size can share their temporal history. A follow-up should add explicit stable view IDs. The fixed exposure sampler uses slot 8, which is also available for the fourth custom ShaderGraph texture (slots 5..8); automatic exposure is skipped for those graphs rather than clobbering user textures. HDR support and blending of 1x1 RGBA16F must be verified on real Metal/GL.

This is an opt-in source implementation with NO native/GPU tests run, per the user's features-first request. Do not enable it globally until verified. Handoff: docs/handoffs/prisma-stage-23.md.

Stage 24 — independent camera history and weighted GPU metering#

The presentation-only API Prisma::setViewId(uint64_t id) selects a stable camera/view identifier before rendering. viewId() const returns it. A view's two 1x1 RGBA16F exposure-history render targets, adaptation timestamp, valid bit and ping-pong index now live in Prisma::exposureViews_, keyed by that ID instead of render dimensions. resetAutoExposure(id) invalidates one view; the no-argument overload invalidates every view. The older target caches remain keyed by size for sharing ordinary temporary textures; exposure history no longer cross-contaminates identically sized Scene and Game cameras.

The editor sets view IDs 1 for Scene and 2 for Game before applyCameraVolumes; GameClient uses ID 3 within its own PRISMA instance. A native project that renders multiple cameras must assign distinct IDs itself. The default ID remains 0 for legacy native projects. Exposure histories are retained until Prisma::shutdown (no automatic per-camera removal/fence retirement yet). IDs must be stable, not increment every frame.

autoExposure has four additional configurable parameters:

  • centerWeight (default 0, range 0..1): 0 = uniform metering, 1 = strongly center-weighted.
  • centerRadius (default 0.35, range 0.05..1): normalized radius for Gaussian center weighting.
  • minMeterLogL (default -10, range -16..0) and maxMeterLogL (default 10, range 0..16): clamp individual pixel log2 luminance in the initial HDR metering pass, reducing extreme brightness influence. This is not percentile-based histogram clipping.

The first pyramid pass now outputs two channels: weighted sum of log2 luminance (R) and sum of weights (G); each later 2x2 pass reduces both components identically. The 1x1 adaptation shader divides R/G before computing target EV. No CPU readback, additional fullscreen texture or extra raster pass is required compared with Stage 23. The format stays RGBA16F throughout.

Example postfx.effects entry:

{"type":"autoExposure","keyValue":0.18,
 "centerWeight":0.75,"centerRadius":0.35,
 "minMeterLogL":-8,"maxMeterLogL":6}

All rendering remains opt-in via AIVERSE_PRISMA_AUTO_EXPOSURE=1, High-tier HDR only. Existing postfx schema is extended, not migrated. CMake, CTest and real Metal/GL validation are NOT RUN as requested. See docs/handoffs/prisma-stage-24.md.

Stage 25 — HDR camera motion vectors and Motion Blur (experimental)#

postfx.effects now accepts motionBlur through the shared, genre-independent PRISMA catalog. The new effect defaults to minQuality: "high" and is opt-in at runtime via AIVERSE_PRISMA_MOTION_BLUR=1; it additionally requires an HDR RGBA16F scene (signed RG motion vectors are not representable in the existing RGBA8 path without encoding).

Parameters: intensity (0..1, default 0.65), maxPixels (0..64, default 20), samples (2..16, default 8), shutterScale (0..2, default 1). Example:

{"type":"motionBlur","intensity":0.6,"maxPixels":20,
 "samples":8,"shutterScale":1.0}

The motion-vector pass samples the current hardware scene depth and reconstructs the world position from the inverse current viewProjection. It projects that position with the previous viewProjection, writing a signed UV velocity currentScreenUV - previousScreenUV into an RGBA16F texture. The next raster pass gathers current-frame scene color along this velocity and blends it with the sharp color. Motion blur is executed before depth of field, FXAA, Bloom and final composite; HUD/UI remains unprocessed. Separate scratch depth attachments avoid sampling and writing the scene depth simultaneously.

The previous camera matrix, validity flag and render dimensions are stored in Prisma::motionViews_ per stable setViewId(), using the same camera identity contract as Auto Exposure. The first rendered frame, resize, changed quality, postprocess toggle or explicit resetMotionHistory(viewId)/no-argument reset invalidates motion history and results in an unblurred frame; it then seeds the matrix for the next frame. setSettings also resets history.

Optional object velocity bridge: a native renderer may call prisma.setObjectMotionVectors(viewId, velocityTexture) each frame with a borrowed, full-resolution texture whose R/G values are signed current-minus-previous normalized screen UV and B is a valid-object pixel mask (B > 0.5). If present, that velocity overrides camera-only velocity for tagged pixels. The borrowed handle is cleared after each resolve. PRISMA does not yet generate per-object velocity buffers from mesh transforms/skinning; the adapter is an integration contract, not automatic object-motion rendering. These inputs are presentation state, not deterministic ECS.

Limitations: this is a camera-reprojection motion blur, not TAA or temporal image accumulation; it does not store previous color, and therefore does not synthesize missing disoccluded samples. Camera cuts must be signaled explicitly to avoid blur across teleports; material transparency and sky (depth≈1) receive zero camera velocity in the basic shader. Neither Metal/GL depth sampling, signed velocity rendering, nor image correctness have been tested. All compilation, CTest and GPU checks remain NOT RUN, per user request. See docs/handoffs/prisma-stage-25.md.

Stage 26 — automatic rigid-object motion vectors (experimental)#

When HDR motionBlur is active with AIVERSE_PRISMA_MOTION_BLUR=1, Renderer3D now has an optional GPU overlay pass for opaque rigid ModelDraw primitives with a stable persistentId. It runs between the scene pass and Prisma::resolve(), outside any open render pass, then sends the RGBA16F velocity texture to PRISMA through the new generic PostProcess bridge. It does not modify gameplay/ECS, and the existing camera-derived vectors remain the fallback for pixels without valid object velocity.

The renderer tracks the previous world transform of each (ModelDraw::persistentId, nodeIndex) in a per-view map. On the first frame or after a camera cut, it records current transforms without drawing a velocity overlay. Once the camera history is valid, it renders each eligible rigid primitive with a dedicated GLSL/MSL shader and ModelVertex position stream. Current and previous model-view-projection matrices produce signed current-minus-previous screen UV motion in RG. B=1 marks visible rigid pixels. A separate scratch depth texture is attached; the shader samples original scene depth and rejects fragments behind the visible surface, so world occlusion/terrain can hide moving objects without writing scene depth.

This pass operates on the existing ModelItems after ordinary batching: individual model node transforms are preserved even if the regular opaque pass used instancing/MDI. The velocity overlay currently uses one regular indexed draw per primitive (not an indirect/instanced velocity submission); it reuses the existing model vertex/index GPU buffers. The overlay render target and depth attachment are owned per PostProcess view ID by Renderer3D and released on its shutdown. No resource is shared between cameras with different stable IDs.

Only rigid, visible, opaque, non-deformed, stable-ID model primitives are eligible. Missing IDs, transparent/masked materials, skinned or baked animated meshes, morph targets, custom geometry and transient immediate draws are skipped. Their pixels continue using the camera-only motion reconstruction. The scene depth test is an approximate epsilon comparison, not a full material/alpha/deformation replay; fast disocclusions and edge artifacts remain possible.

Existing Prisma::setObjectMotionVectors(viewId,texture) stays available for custom native renderers; automatic Renderer3D generation uses the same borrowed-handle bridge via virtual PostProcess::acceptObjectMotionVectors. There is no ECS scheduling or genre-specific integration. Default behavior is unchanged when MotionBlur is not active.

Stage 27 — deformation-aware and instanced object motion vectors#

The optional HDR motionBlur path now contains two new Renderer3D velocity render variants, both active only with AIVERSE_PRISMA_MOTION_BLUR=1:

Rigid velocity instancing. Geometry-equivalent visible opaque rigid ModelItem instances are grouped by source model pointer, first index and index count. A separate 16-instance GLSL/MSL pipeline consumes per-instance current and previous MVP matrices, submitting one drawIndexed(..., instanceCount) per compatible group (up to 16 instances per group). The uniforms occupy at most 2064 bytes; a single item or missing batched pipeline still uses the Stage 26 singleton shader. Matching shader/geometry groups are presentation-only; the existing color draw batching is not altered.

Skinned and morph velocity. Palette-skinned objects and morph-target primitives with a nonzero stable persistentId can produce actual deformed vertex velocities. The renderer snapshots the current joint palette and eight morph weights per (persistentId, nodeIndex, geometryPrimitive), retaining the previous frame's values independently for each camera. A separate shader deforms each mesh vertex for both the current and previous pose, computes two clip positions and stores screen UV displacement. Current and previous U3/U4 blocks hold up to 80 joints (3 rows each); U5 contains the two 8-weight morph arrays and morph atlas parameters; tex8 reuses the existing morph delta texture. GPU skinning/morph math is kept separate from the deterministic simulation and is not a CPU-skinned mesh upload. A missing previous pose or changed source model identity causes the deformable primitive to skip object-velocity override rather than invent movement.

Depth-edge motion blur. Motion Blur now samples the original scene depth at each color gather position and reduces contributions across large depth discontinuities. This protects foreground outlines against unrelated background colors, although the rejection threshold is based on non-linear hardware depth, so it is a conservative approximation, not physically exact depth-layer motion reconstruction. Prisma::buildProgram supports depth2d<float> for explicitly marked depth samplers on Metal while keeping GLSL sampler2D conventions.

Eligibility remains intentionally conservative: visible, opaque non-displaced primitives with stable IDs. Baked animation (whose pose comes from clip textures), material ShaderGraph vertex displacement, transparent/masked models and custom geometry are not yet handled by the new deformed-velocity pipeline. Velocity target resize, first frame and camera cuts seed history rather than extrapolating invalid motion. Renderer3D owns lazy velocity shader/pipeline and target lifetime.

Stage 28 — baked clip motion, alpha-cutout velocity and depth thresholds#

The experimental motionBlur pipeline now includes a baked-clips vertex velocity shader variant. For a ModelItem with baked=true, the renderer records the current anim values (clip A row, clip B row, blend) and world matrix by stable (persistentId, nodeIndex, geometryPrimitive). The new GLSL/MSL vertex shader reads the original baked bone atlas (tex7) and original per-primitive joint palette. Current and previous clip rows and interpolation are sampled separately to reconstruct both deformed vertex positions. The velocity fragment then writes current-minus-previous normalized screen UV motion. The history snapshot is presentation-only; the animation and authoritative simulation aren't modified. This path intentionally skips baked + morph simultaneous deformation until a mixed permutation is available.

An optional alpha-cutout rigid velocity variant now replays the material's base texture alpha cutoff with KHR texture transform (offset/scale/rotation), base alpha and vertex-color alpha (when enabled). Because cutout surfaces contain empty pixels, the dedicated variant samples the base alpha texture and discards rejected fragments before depth-occlusion testing. These materials are kept out of the ordinary opaque instanced velocity draw and rendered separately. ShaderGraph-displaced surfaces and deformable alpha-cutout models are not included, since their visible shape requires matching additional material stages. Fully blended/transparent models remain excluded.

The rigid history now stores the source Model identity alongside its world transform, preventing a reused persistentId from picking up a different model's previous transform. Existing per-view reset, initial frame and resize behavior stays intact.

motionBlur also accepts depthThreshold (default 0.012, range 0.0005..0.05) for rejecting unrelated depth layers during the directional color gather. The shader falls back to the sharp sample if all gathered samples are rejected instead of blending black into the image. The threshold is in non-linear device depth units, not metres. Example:

{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"shutterScale":1,"depthThreshold":0.012}

All additional paths remain behind the pre-existing AIVERSE_PRISMA_MOTION_BLUR=1 and HDR/quality gates. They use the same masked velocity texture bridge and do not change gameplay ECS or SpectraFX. Baked clip pose and rigid alpha-cutout motion use new GLSL/MSL variants; no backend-specific testing has yet verified their image parity. CPU/GPU builds, CTest, shader compilation, screenshots and benchmarks are NOT RUN at the user's request. See docs/handoffs/prisma-stage-28.md.

Stage 29 — camera-cut epochs, reactive transparency and baked+morph velocity#

PRISMA's experimental HDR motionBlur path now has three additional presentation-only capabilities, all gated by the existing AIVERSE_PRISMA_MOTION_BLUR=1 runtime flag and configured quality.

Explicit camera/view lifecycle. Prisma::resetMotionHistory(viewId) increments a monotonically increasing per-view camera-cut epoch exposed by PostProcess::objectMotionEpoch(viewId). Renderer3D reads this epoch on each opt-in velocity pass and discards prior rigid and deformable transform snapshots when it changes. This keeps the camera reprojection and per-object pose histories in sync across camera cuts, teleports, quality changes and map reconfigurations without modifying gameplay ECS. The renderer also provides resetObjectMotionHistory(viewId) and resetAllObjectMotionHistory() for explicit standalone control. releaseObjectMotionViewAfterGpuIdle(viewId) releases the per-view GPU velocity, reactive and depth textures only after the host has confirmed GPU idle; CPU frame serials are NOT a GPU completion signal. No automatic viewport closure or backend GPU fences are wired yet.

A new read-only Renderer3D::objectMotionStats() returns the last velocity pass's view ID, submitted state and rigid instance/draw, cutout, skinned, baked, reactive and rejected draw counters. These values are CPU submission diagnostics, not measured GPU time or performance data.

Reactive masks. Renderer3D can emit a separate, current-frame RGBA8 reactive coverage texture for visible rigid, translucent ModelDraw primitives. It samples the final scene depth and uses a dedicated scratch depth attachment rather than modifying scene depth. The red channel is coverage strength, while an all-zero background means no reactive pixels. PostProcess::acceptMotionReactiveMask forwards the borrowed handle to PRISMA. Native renderers can instead provide a borrowed R=0..1 texture through Prisma::setMotionReactiveMask(viewId,texture) before resolve. The motion blur shader samples this mask at texture slot 3 and reduces local blur strength by 1 - reactive * reactiveStrength. A missing mask uses the black fallback, so motion blur remains unchanged.

The new optional effect parameter reactiveStrength defaults to 0.85 and has a range of 0..1. The renderer's reactive pass is a conservative geometric silhouette of translucent rigid models: it does not reproduce per-pixel blended texture alpha, alpha-test materials, skinning, particles or water drawn by other renderer modules. False-positive reactive coverage may reduce blur inside glass geometry, which is preferable to inventing object velocities. It remains an experimental approximation.

Baked clip + morph. The baked-velocity vertex shader now applies both the current and previous morph weights against immutable morph deltas (tex8) before sampling current and previous baked clip rows from tex7, matching the existing color shader's deformation order. Palette, animation and morph parameters are all per primitive and per view; a missing previous frame or changed model identity still suppresses object-velocity override. This does not add per-vertex CPU readback or change deterministic animation state.

LOD transition geometry that requires screen-space dithering is now conservatively excluded from object velocity until a matching LOD fade shader is implemented; camera motion reconstruction remains the fallback there.

Example:

{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"shutterScale":1,"depthThreshold":0.012,
 "reactiveStrength":0.85}

Stage 30 — animated reactive coverage, extensible water/particle masks, LOD fallback and velocity dilation#

The existing experimental motionBlur chain now supports animated, current-frame reactive coverage for translucent skinned, morph and baked-clip ModelDraw geometry. These reactive passes do not invent previous animation poses or feed object motion velocity: they evaluate the current GPU-deformed vertex position using the same vertex path as the Stage 27/29 motion shaders, sample the read-only scene depth for visibility, and mark covered pixels as reactive (R=1). The animated Metal shaders reuse the established skinned/baked vertex shader source while substituting a coverage-only fragment. This handles baked+morph current-pose silhouettes, but does not reproduce per-pixel transparent material alpha, ShaderGraph vertex displacement, screen-space water, or particles automatically. These may be more accurately supplied by the owning renderer.

Reactive coverage extension for all renderers#

Renderer3D::addMotionReactiveDraw(fn) registers a presentation-only, current-scene callback with signature

void(gfx::Device& device, gfx::TextureHandle sceneDepth,
     int width, int height)

Register after beginScene() and before resolvePrisma() (typically after the main scene/color pass has been submitted); callback registration is cleared automatically after the current scene's resolve. The callback is invoked inside an already open RGBA8 reactive render pass with a separate scratch depth target; it must never call beginPass/endPass. The provider binds its own shader, geometry, texture/constant state and writes red channel R in [0,1] (0 = no reaction, 1 = suppress blur according to the configured strength). Use coverage-union-friendly blending, such as gfx::BlendMode::Screen, so several water/particle/object providers combine rather than erase one another. The current sceneDepth handle may only be sampled: never rebind that texture as a writable depth attachment. The provider must keep any borrowed buffers/textures valid through the callback and cannot modify gameplay ECS state.

The generic callback is available for rendering engines and projects implementing water, particles, weather or custom presentation. Stage 30 does not automatically instrument existing water/VFX packages; those owners must register their respective reactive render callbacks to render the correct coverage with their own material/geometry semantics. No callbacks are invoked unless HDR MotionBlur is active and a valid camera history exists; registration by itself cannot force the postprocessing chain to run.

Built-in reactive pipelines now use Screen blending for accumulation of multiple overlapping masks. The rigid fallback also reproduces the pixel-dither coverage rule of ModelShaders for dithered LOD crossfades: these pixels mark themselves reactive rather than incorrectly receiving normal rigid-object velocities. This is coverage-aware blur suppression, not full motion-vector reconstruction across LOD changes.

Depth-matched velocity dilation#

The new motionBlur.velocityDilation parameter (default 1.0, range 0..2, 0 disables) samples four neighbouring velocity values at the requested radius, selecting a stronger velocity only when its device-depth closely matches the center pixel. This helps preserve motion around silhouettes without importing motion from clearly different depths. It is a local approximate depth check (hardware depth units, not metres) and costs up to four additional velocity and depth reads per blurred pixel. The cost estimator includes this additional work when enabled.

Example:

{"type":"motionBlur","intensity":0.65,"maxPixels":20,
 "samples":8,"depthThreshold":0.012,"reactiveStrength":0.85,
 "velocityDilation":1}

All additions use the existing AIVERSE_PRISMA_MOTION_BLUR=1 opt-in flag, HDR RGBA16F and appropriate quality tier. Reactive mask callbacks are a Renderer3D presentation extension, independent of FPS, RTS, water or SpectraFX ownership.

Stage 33 — GPU-completed fences for safe PRISMA resource retirement#

The renderer now exposes a separate GPU-completion timeline in the genre-independent gfx::Device interface:

uint64_t submitted = dev.gpuSubmissionFence(); // current GPU frame, 0 if unavailable
uint64_t completed = dev.gpuCompletedFence();  // GPU-confirmed completion only

The submitted token covers work encoded in the currently active GPU frame and is not the CPU frame counter. It can be attached to a target retirement before that frame is actually submitted; the backend will complete it only after GPU execution. A nonzero gpuCompletedFence() result is a real, contiguous completed GPU timeline token. Unsupported devices return zero. All values are per-device; never compare values from different devices, contexts or GPU queues.

Metal: GfxMetal.mm uses the current command buffer's frame token and updates an atomic completed counter in its addCompletedHandler only for MTLCommandBufferStatusCompleted. It does not turn frameSerial() into a completion fence. The asynchronous callback captures shared lifetime-safe state and the graphics owner thread polls it by reading gpuCompletedFence().

GL33 / GLES3 / WebGL2: after the frame's render commands the backend inserts glFenceSync(GL_SYNC_GPU_COMMANDS_COMPLETE,0) and flushes the command stream without waiting. At the next beginFrame, it calls glClientWaitSync(..., timeout=0) on its oldest pending fence, advancing completed tokens strictly in submission order and deleting signalled GL sync objects. The Windows GL33 dynamic loader now loads glFenceSync, glClientWaitSync, glDeleteSync. A failed fence is never treated as successful completion. No per-frame glFinish is added.

Vulkan: uses its already existing per-frame VkFence and serial_. gpuSubmissionFence is the currently recording GPU frame's serial; gpuCompletedFence returns only the highest serial whose slot fence has been successfully confirmed by vkWaitForFences. A lost device or unsuccessful wait does not advance the completed fence. This is the existing slot-wait path, not a new polling implementation that blocks extra frames.

Automatic motion target reclamation#

Renderer3D::beginScene now calls collectCompletedObjectMotion(dev.gpuCompletedFence()) on the graphics owner thread. When a viewport changes size, queueObjectMotionTexture takes the current dev.gpuSubmissionFence() if available and associates it with the old object velocity, reactive or scratch-depth target. On completion the old targets are destroyed; before then they are retained. retireObjectMotionView and setObjectMotionSubmittedFence remain available for externally managed submission lifecycles. On devices without submission-fence support, old targets remain in the Stage 32 quarantine until explicit GPU idle.

Deferred PRISMA Sized / RenderGraph targets#

Prisma::sized still keeps three active size entries for Scene/Game views, but when evicting the least-recently-used entry it now moves the whole Sized context — legacy raster targets, depth targets, cached Bloom graph and persistent PrismaRhiExecutor resource pool — into a fence-tagged retirement list instead of releasing it immediately. When the GPU reports that the last referencing submission completed, collectCompletedSizes frees the retired targets and safely resets the graph executor pool. In addition, Prisma::target now fence-retires targets replaced by size/HDR format changes, avoiding immediate destruction of a texture that may be in use by an earlier in-flight GPU command buffer.

Prisma::releaseRetiredSizesAfterGpuIdle() is the escape hatch for hosts that have explicitly waited for an idle GPU; the function also drains unfenced/quarantined individual targets. The shutdown path assumes the platform's normal device-teardown GPU-idle condition.

This stage is about resource lifetime correctness, not a change to image output, bloom topology, exposed postfx JSON, particle simulation or gameplay ECS. Existing experimental flags remain off by default.

Limits#

The new timeline only covers commands on the backend's regular graphics submission queue. External GPU queues or devices need their own fence tracking. Metal handles are released after the command buffer completion callback; GLES/WebGL sync capabilities and actual device behavior still require runtime validation. Vulkan may only advance its completion counter when rotating to a frame slot whose fence was waited. Without a GPU-completed token, retired resources are not released opportunistically and quarantine can grow.

Stage 34 — GPU-fenced per-camera history lifecycle and editor diagnostics#

PRISMA temporal history is now explicitly owned by stable view IDs instead of render-target size. The Stage 34 public APIs are:

prisma.retireView(viewId);               // close only this camera's history
prisma.collectGpuRetirements();          // nonblocking, GPU-completed fence
auto post = prisma.retirementStats();    // read-only CPU diagnostics
auto motion = renderer.motionRetirementStats();

retireView(id) removes the per-view Auto Exposure ping-pong 1×1 RGBA16F texture handles from the active exposure map and queues them via the existing GPU-fence-aware retireTarget() mechanism. An unfenced backend retains them until a host-confirmed GPU-idle drain; a completed GPU token permits collection without stalling. Per-view MotionBlur matrices, validity and borrowed current-frame velocity/reactive handles are discarded without destroying those externally owned borrowed resources. Importantly, retireView does not delete the shared Prisma::Sized scene render targets: multiple Scene/Game cameras of equal resolution may still use them.

Renderer3D::retireObjectMotionView(id, fence=0) is now callable without a manually supplied fence; the queue first queries the live backend gpuSubmissionFence(). Its separate current-frame GPU velocity, reactive and depth targets are retired independently from PRISMA exposure. Renderer3D::motionRetirementStats() reports retained per-view context count, fenced/unfenced texture count, backend completed GPU fence and known pending bytes.

Prisma::retirementStats() reports active/retired size contexts, exposure/motion view counts, fenced/unfenced textures, retired graph pool entries, the last GPU-completed fence and known minimum held GPU bytes. The byte estimate uses Device::textureInfo() on live RHI allocations, including the archive of Sized targets and depth attachments; it deliberately does not invent memory for internal graph retired allocations whose handle metadata has already been discarded. Statistics are not total VRAM use.

Scene/Game viewport transitions#

In the editor Editor::frame tracks which view actually rendered postprocess this GUI frame. When a Scene or Game tab is hidden, closed, switched to non-postprocessed diagnostic mode, or stops rendering, the editor retires that camera's PRISMA state plus its Renderer3D motion targets once, then continues collecting backend-confirmed GPU completions on subsequent editor frames even with no 3D viewport rendered. Reopening a view seeds fresh temporal history instead of reusing stale exposure after a long hidden period.

The Scene view uses stable ID 1 and Game uses 2. The editor previously used Game ID 2 even when the Scene tab reused the game renderer during play; Stage 34 passes explicit ID 1 in that path to prevent simultaneous same-resolution Scene/Game motion and exposure contamination. A hosted standalone game client uses its own PRISMA instance and view ID 3.

The native GameClient similarly retires view 3 on a new match before camera and map replacement, and continues checking pending GPU work on menu/loading frames when the 3D renderer is not rendering.

The editor's Statistics tab now shows a new PRISMA · GPU resource retirement section for completed GPU fence, active/retired size contexts, view histories, counts of fenced and unfenced textures, outstanding graph allocations, and the minimum known MiB retained by both PRISMA and Renderer3D. This is observational and creates no GPU readback or synchronizing GPU wait.

Project asset reloads#

Prisma::setImageLoader now GPU-fence-retires superseded LUT and user ShaderGraph textures rather than immediately destroying them while another frame might still reference them. Shared shader pipelines and graphs keep their existing ownership; this only changes the texture retirement policy.

Stage 35 — editor framebuffer GPU retirement and explicit pressure drain#

The editor's actual Viewport::color and Viewport::depth render targets now use the same GPU-completed-fence principles as PRISMA and Renderer3D. They are not owned by PRISMA: a new apps/editor/ViewportGpuRetirement.h owner lives in the Editor instance and outlives its Scene/Game/FX window objects. Viewport binds that owner during ensure(dev,w,h,owner), and release() / resize / viewport destruction transfer both GPU handles to the owner instead of directly destroying in-flight images.

The old color handle may still be in an ImGui draw command even after the window's Viewport::image() returns, so it is only destroyed after gfx::Device::gpuCompletedFence() covers the submission that may reference it. Unfenced resources are quarantined until the host has explicitly verified GPU idle. The owner also clears the viewport's stale drawnFrame / hover state when released.

All three editor producers (Scene, Game and FX windows) use this shared owner. They release hidden/closed offscreen render targets without relying on window destruction; the owner retains resources past window lifetime. A hidden/closed tab can later recreate a framebuffer with no stale ImGui texture handles.

Memory pressure policy#

ViewportGpuRetirement reports pending fenced/unfenced texture counts, metadata-derived knownPendingBytes, a threshold and an overBudget indicator. The default shared known-pending budget is 128 MiB, configurable through AIVERSE_PRISMA_RETIRE_BUDGET_MB (32..4096 MiB). The editor checks the sum of known pending bytes from Viewport, PRISMA and Renderer3D on the pre-render boundary of Editor::frame, before any new GPU draw submission. It normally collects already GPU-completed resources with no wait.

If that known pending memory exceeds the budget, it can call the new explicit gfx::Device::waitForSubmittedGpuWork() hook exactly at that safe point. On successful synchronization it drains the Viewport, PRISMA and Renderer3D GPU retirement queues, including unfenced quarantine. It never releases an in-flight texture based on the number of elapsed CPU frames.

This explicit pressure-only wait is implemented with glFinish() on GL33/GLES3 (excluding WebGL), waiting the last actually committed Metal command buffer (never the uncommitted buffer for the current frame), and vkQueueWaitIdle on Vulkan. These waits are not performed every frame; they can cause a visible one-time stall at memory pressure. The WebGL2 backend explicitly returns false because a portable synchronous idle barrier is not promised; resources remain quarantined until an external safe teardown. A positive wait result only covers previously submitted GPU commands, so the editor must call it before it encodes new frame work that uses those resources.

The Statistics tab now shows viewport fenced/unfenced resource counts, known pending MiB versus the configured budget, and a "Запросить безопасную очистку GPU" button. That button merely requests a one-shot cleanup at the next frame's pre-render boundary, not while the Statistics window's ImGui pass is active.

The threshold is an advisory pressure budget rather than a global hard GPU VRAM cap. Internal RenderGraph allocations, active resources, driver overhead, and unknown/unsupported RHI texture descriptors may not be included in the lower-bound estimate. If a backend cannot synchronize, the editor deliberately retains memory rather than risking GPU use-after-free.

The RHI's prior gpuSubmissionFence() / gpuCompletedFence() APIs are unchanged, and the new waitForSubmittedGpuWork() is optional. All postprocessing flags remain off by default; no ECS/gameplay ownership changes.

Stage 37 — generic GPU-fenced shaders, pipelines, buffers, FX hot reload#

Stage 37 extends the GPU-completion lifetime policy from textures and viewport resources to all RHI handle categories used by Shader Graph and VFX hot reload.

engine/render/GpuResourceRetirement.h introduces a genre-independent, graphics-owner-thread lifetime service with overloads for gfx::PipelineHandle, ShaderHandle, BufferHandle, TextureHandle, and ComputeHandle. Each retired handle is detached from its old owner and stored with the GPU submission token from gfx::Device::gpuSubmissionFence(). A zero token is quarantined. A verified gpuCompletedFence() allows nonblocking reclamation; explicit drainAfterGpuIdle() requires a real GPU-idle guarantee.

When multiple GPU handles become eligible at the same time, the service destroys pipelines before shaders, preserving dependencies. It also supports retireOwned(device,cleanup,knownBytes) for complex rendering-owner bundles whose internal destruction order is already encapsulated. The callback is invoked only after GPU completion on the graphics-owner thread, never from the Metal completion-handler thread. The service tracks pending resource-type counts, fenced/unfenced entries and optional known bytes; these are lower bounds, not complete VRAM metrics. It owns resources exclusively; do not hand it borrowed handles.

Shader Graph Preview: whole-bundle retirement#

The Shader Graph editor now retains the entire previous ShaderGraphPreview object on a graph asset/project/domain change. The archived object includes its Portrait/Renderer3D, ParticleSystem, PRISMA, TextureCache, shaders, pipelines, vertex buffers, and preview color/depth targets. The new preview is created separately. The old preview's shutdownAfterGpuCompletion() runs only when its last GPU submission fence has actually completed (or at explicit GPU idle). This avoids the former immediate pipeline/shader destruction while a previous GPU frame may still reference those resources.

A UI-only change to the node position field does not invalidate GPU shader preview resources; both the window and preview use a shared ShaderGraphPreview::resourceKey(graph) that excludes node screen positions. Actual changes to shader nodes, connections, parameters or domain still produce a new GPU preview bundle.

Editor FX and TextureCache hot reload#

fx::ParticleSystem exposes the optional setGpuResourceRetirement(owner) hook. When attached, reloadAll() retires each previous shader-graph variant pipeline and shader rather than directly calling destroyPipeline / destroyShader while previous draws may be in flight. The old immediate owner path remains for runtime clients without a retirement owner.

render::TextureCache likewise has an optional setGpuResourceRetirement(owner) hook. On reload/shutdown it deduplicates cached and atlas-page texture handles, queues each owned texture exactly once and preserves the default legacy cleanup path when no retirement owner is attached.

The editor's main FX producer (gameFx_ and fxTextures_) and the separate FX preview window are opted into this service. Existing rendering and ECS data are not modified.

The Editor owns GpuResourceRetirement independently of its windows; it collects GPU-completed resources on each pre-render frame and drains at a confirmed GPU-idle pressure/shutdown point. On window closure or loss of the selected dock tab, the old portrait is retired; reopening creates a new portrait without reusing the previous in-flight GPU handles. The standalone model-viewer and other clients with different ownership are not modified.

RHI buffer allocation metadata#

gfx::BufferInfo and the optional gfx::Device::bufferInfo(BufferHandle,BufferInfo&) provide a CPU-only live-resource query. The GL, Metal and Vulkan backends read their own buffer tables without waiting for the GPU or readback. The result contains logicalBytes and versions (dynamic buffer copies can take extra GPU memory). These describe logical buffer allocation size; Metal/Vulkan dynamic snapshots and GPU allocator padding can exceed that amount.

GpuResourceRetirement::retire(device,buffer) now automatically uses bufferInfo to estimate the retained bytes if the producer has not supplied them. Retired textures similarly use actual textureInfo width, height and pixel format. This improves the known-pending-memory estimate for Editor FX graph hot reload, model previews and texture caches. It is still not a precise total GPU VRAM counter; shader/pipeline driver allocations and complex preview owner bundles may have unknown size.

Terminal device-loss handling#

GpuResourceRetirement::collect() checks Device::gpuHealthy(); if the device is lost it does not call any destroyShader, destroyPipeline, destroyBuffer, destroyTexture or destroyCompute functions. The new explicit abandonDevice(device) removes pending raw RHI handles without calling dead GPU APIs. Complete owner bundles are more dangerous: destroying a captured ShaderGraphPreview object can transitively call Device in its destructor. Their callbacks are moved to an inert process-lifetime orphan sink with no destructor. This intentionally retains that CPU memory until process exit rather than risking use-after-free after terminal device loss.

A normal GpuResourceRetirement destructor also prevents unsafe bundle callbacks from being run implicitly if the host did not first drain at a verified GPU-idle point. The editor's shutdown integrates abandonDevice when gpuHealthy() is false. ClientHost::abandonOnDeviceLoss() provides a similar terminal path for deferred hosted GameClient owners, which otherwise might destroy nested renderers against a dead GPU Device. An archived client's device must match the verified completion source.

The Statistics window exposes abandoned handles/bundles for diagnostics. Abandonment is an emergency device-loss/teardown fallback, not ordinary memory reclamation, and does not replace restoring the device, recreating render targets or handling other rendering subsystems' old ownership policies.

The common GPU retirement service remains presentation-only, genre-independent and opt-in for owners that can guarantee the device is alive during normal collection. Stage 42 — opt-in HDR temporalResolve (full-resolution history reprojection)#

This feature extends the existing canonical Prisma pipeline, not the historical PrismaScreenLighting wrapper. The normal postfx catalog now supports a temporalResolve effect, with four editor/MCP/volume-configurable parameters. Existing effect IDs, postfx JSON roots, saved panel ID, and PostFx compatibility headers remain unchanged.

To activate, the host must use HDR/High and opt in explicitly with AIVERSE_PRISMA_TEMPORAL=1, in addition to an authored effect:

{
  "postfx": {
    "effects": [
      {
        "type": "temporalResolve",
        "minQuality": "high",
        "historyWeight": 0.86,
        "depthThreshold": 0.0075,
        "motionScale": 0.04,
        "reactiveStrength": 0.95
      }
    ]
  }
}

Prisma::resolve() now reuses a single full-resolution signed velocity pass for both Temporal Resolve and Motion Blur, if requested. Velocity is current-minus-previous normalized UV and includes camera reprojection and optional Renderer3D object/deformation velocity (RGBA16F, B presence bit); invalid provider metadata falls back to camera velocity. The current-frame RGBA8 reactive coverage is borrowed from Renderer3D/particle callbacks and never retained as temporal history.

Each viewId owns two full-resolution RGBA16F linear HDR textures, with color in RGB and prior hardware depth in alpha. The temporal shader reprojects by signed motion vectors, explicitly reconstructs four previous texel taps (nearest GPU sampling, separate depth checks), clamps accepted history against a 3×3 current-color neighborhood in a compressed HDR domain, then adjusts history weight by motion magnitude and reactive coverage. Missing/invalid history writes the current unblurred scene and seeds the next frame. Disoccluded pixels reject stale depth rather than using an interpolated history alpha. HDR tone mapping, Bloom, LUT, and HUD happen after the resolve. If opt-in Motion Blur is also active, it uses the temporally resolved source. HDR FXAA is skipped when temporal resolve ran: do not stack both AA approaches in one frame.

Automatic invalidation applies on resolution change and a large camera translation (>12 presentation-world units between frames); explicit Prisma::resetMotionHistory(viewId) also invalidates temporal history on camera cuts and profile switches. Prisma::retireView(viewId) moves owned history handles into the existing GPU-fenced retirement queue. Resource diagnostics report per-camera temporal history texture counts and lower-bound resident bytes, without charging them to the shared size-keyed render target cache.

What Stage 42 is not: it does not implement dynamic-resolution rendering, jittered subpixel supersampling, native TSR/FSR/DLSS upscaling, optical-flow motion estimation, a history confidence/rejection G-buffer, or proof of parity with the historical optional PrismaScreenLighting TAA. This is an opt-in, full-resolution temporal color stabilization pass. Sky pixels with no reconstructed surface depth are not accumulated, and moving silhouettes can still need more robust velocity dilation/occlusion masks. Stage 43 — optional subpixel jitter and confidence-aware temporal AA#

Stage 43 builds on Stage 42's canonical PRISMA temporalResolve without introducing a second TAA subsystem or rewriting stable postfx/MCP identifiers. The native-resolution history remains two per-camera HDR RGBA16F targets; no lower-resolution render target or temporal upscaler is introduced.

The effect adds two optional float parameters:

  • jitterPixels: 0..0.5 (default 0.5) controls the maximum subpixel projection offset. Jitter additionally requires AIVERSE_PRISMA_JITTER=1 and the original AIVERSE_PRISMA_TEMPORAL=1, with HDR + High quality and an authored enabled temporalResolve effect. Existing games are unmodified without both explicit environment flags.
  • historyConfidence: 0..1 (default 0.65) controls how aggressively previous HDR color is rejected near sharp luma/depth changes, in addition to the Stage 42 disocclusion depth/velocity/reactive rules.

C++ camera contract: Call setViewId(id), then applyCameraVolumes(stack, camera.eye()), then RTSCamera renderCamera = prisma.jitteredCamera(camera,w,h) immediately before renderer.beginScene(renderCamera,w,h). jitteredCamera returns a copy and never mutates camera itself: keep the original RTSCamera for mouse picking, editor gizmos, UI, and touch input. The standard GameClient, Editor Scene and Editor Game rendering paths have been updated to follow this sequence. ShaderGraph, FX and native preview owners may opt in separately. The real render projection uses RTSCamera::jitter, and the renderer's shadow-camera strips jitter already, avoiding artificial shadow-map projection shifts.

Shader behavior: Each view ID maintains its own 8-step Halton (2,3) sequence. Jitter is expressed in NDC by the camera; the temporal shader receives the current/previous jitter in unflipped normalized UV. Each stable output pixel samples the current HDR color/depth/velocity at pixel + currentJitter, then samples the prior history at reprojectedInputUV - previousJitter. This removes projection jitter from the history-addressing and from physical-motion confidence while retaining distinct subpixel samples for accumulation. GLSL and Metal use the same shader body, with the render-target Y flip applied only by the existing TUV macro. A 3×3 current compressed-HDR color neighborhood yields local mean/variance and bounds; the shader uses independently depth-validated previous taps, color disagreement and current depth-edge contrast as confidence multipliers. Moving silhouettes and reactive particles therefore receive lower history weight than smooth static surfaces.

On explicit camera cuts, projection type/FOV/near/far discontinuities, history changes, jitter mode/amplitude switches or viewport size changes, the temporal history restarts instead of blending incompatible pixels. The existing camera-position cutoff still applies. PrismaStats reports whether the last frame resolved temporal color, whether jitter was active, and the applied offsets in pixels; the PRISMA — Постобработка panel displays the values.

This is native-resolution temporal antialiasing, not jittered temporal upscaling, DLSS/FSR/TSR, optical flow or dynamic-resolution rendering. Transparent surfaces and screenspace effects may still alias if their producers do not supply suitable reactive or motion masks. PrismaScreenLighting contains an older optional independent TAA; do not activate both histories at once. The history and GPU-referenced resources remain subject to GPU-fence retirement from Stages 35–42.

Stage 44 — explicit internal render resolution and temporal upscaling#

Stage 44 extends the canonical opt-in temporalResolve / Halton TAA path with a true internal 3D render resolution that may differ from the final output target. It adds two catalog parameters to the existing postfx.effects[{type:"temporalResolve"}] payload:

  • renderScale (0.5..1, default 1): fraction of the output width and height used by 3D, depth and motion-vector passes. The chosen scale is quantized to 1/16 steps; actual pixel counts are rounded, bounded to 32px minimum and require at least 64px output dimensions.
  • reconstructionSharpness (0..0.5, default 0.15): mild color reconstruction/sharpening within the compressed-HDR current-frame neighborhood before confidence-weighted history accumulation.

The feature is disabled unless all three flags are explicitly set: AIVERSE_PRISMA_TEMPORAL=1, AIVERSE_PRISMA_JITTER=1 and AIVERSE_PRISMA_UPSCALE=1. An enabled temporalResolve authored in the normal game/map postfx catalog, HDR support, High quality, historyWeight>0, jitterPixels>0 and renderScale<1 are also required. Existing projects and low/medium/mobile quality tiers retain 1:1 rendering by default.

Host call order: after setViewId(id) and applyCameraVolumes(stack,camera.eye()), call auto [renderW,renderH] = prisma.renderSizeForOutput(outputW,outputH) and then prisma.jitteredCamera(camera,renderW,renderH). Pass this camera and the smaller dimensions to Renderer3D::beginScene but give Renderer3D::render the unchanged full-resolution destination pass. Draw 3D and particle reactive/motion contributions at the smaller size. Renderer3D::resolvePrisma sends the current viewProjection and internal dimensions to Prisma, which reads final output dimensions from the RHI output texture, the host's per-view size declaration, or the swapchain framebuffer. Draw HUD, labels, picking/gizmos and UI using the original camera/full output dimensions. Both Editor Scene/Game and GameClient now use these calls.

The main HDR path now performs shutter blur, DoF and other internal scene effects at the low render resolution; Bloom and sun-shaft buffers remain low-resolution inputs. The temporal pass runs immediately before final color composite and writes a viewId-private output-resolution RGBA16F history (RGB linear HDR, A prior hardware depth). Temporal samplers use separate reciprocal texel sizes: inputPx for current scene color/depth neighborhoods, px for output-history bilinear coordinates. Motion vectors remain current-minus-previous in normalized screen UV, so their coordinates do not require ad-hoc multiplication by the resolution ratio. The shader applies Stage 43 jitter correction, four individually depth-validated previous history taps, current luma/depth confidence, reactive coverage and bounded HDR sharpening. Final tonemap/composite and optional full-resolution UI remain output-size. HD/SDR FXAA is not layered over a successful HDR temporal resolve.

Per-view history invalidates/retires on changes to output or input dimensions, camera cuts, projection changes or effect quality. Old targets go through the existing GPU-fence retirement rather than immediate destruction. PrismaStats reports width,height (internal), outputWidth,outputHeight (presentation) and temporalUpscaled (successful spatial/temporal resolution step), which are displayed in the Prisma editor window. Source-level cost estimation is heuristic; actual GPU cost, bandwidth, ghosting and savings are unmeasured here.

Stage 45 — GPU-sampled adaptive resolution and pre-render stable fallback#

This stage extends the opt-in Stage 44 source/output temporal scale path. It does not change any defaults or the postfx JSON root, existing MCP IDs, editor tab ID, scene shaders or genre-specific simulation.

New effect controls in the existing temporalResolve catalog: adaptiveResolution (boolean, defaults false), targetGpuMs (4..50ms, default 16.6) and minRenderScale (0.5..1, default 0.5). The authored Stage 44 renderScale remains the quality ceiling and cannot be exceeded by the adaptive controller. To opt in, set AIVERSE_PRISMA_ADAPTIVE=1 in addition to all three Stage 44 flags (AIVERSE_PRISMA_TEMPORAL=1, AIVERSE_PRISMA_JITTER=1, AIVERSE_PRISMA_UPSCALE=1), choose HDR/High and author an enabled temporalResolve effect with adaptiveResolution:true.

PrismaAdaptiveResolution is a CPU-only, genre-independent policy in engine/render/PrismaAdaptiveResolution.h. It consumes only finite, positive, asynchronously completed Device::gpuFrameMs() readings from new, strictly increasing Device::gpuCompletedFence() tokens. A backend without reliable results (e.g. unsupported GL/Vulkan) stays at the authored scale; the policy never substitutes editor CPU frame time, FPS, frame serials or predicted GPU timings. On Metal the signal measures the whole GPU command frame, not an isolated Prisma pass or editor view; adapting multiple editor views to the same whole-frame measurement is conservative and can shift quality in both.

Hysteresis: GPU duration above 115% target for 12 distinct completed samples causes a 1/16 renderScale decrease; GPU duration below 80% target for 36 samples causes a 1/16 increase, up to authored ceiling. A changed scale starts 48 completed samples of cooldown, reducing rapid resize/reallocation loops. The floor and ceiling are clamped and quantized; Prisma::retireView removes per-view controller state when the viewport is closed.

Pre-render resource preflight: renderSizeForOutput() on the graphics thread now calls preflightUpscale() before returning any internal resolution smaller than the output. It checks the temporal and motion GPU programs, the guaranteed fallback composite, the HDR RGBA16F size-owned scene/velocity textures, internal scene/depth/scratch, the camera-private pair of output-size HDR temporal histories and the output-size scratch depth. History reallocations use existing GPU-fenced retirement. A failed preflight returns full input/output dimensions and inhibits jitter for that view. Allocation retries are rate-limited (60 render-size queries) so an unsupported or memory-constrained device is not hammered each frame. No GPU wait is introduced in this path.

Jitter-safe runtime fallback: if a temporal pass unexpectedly cannot run after a low-resolution jittered scene was already encoded, the final compositor uses graphFrame.zw as a current-jitter sampling offset s + currentJitter for source color and dependent screen effects. The offset is zero during a successful temporal resolve or normal non-jittered presentation. That keeps the fallback image on a stable output pixel grid while still allowing linear bilinear upscaling and HDR color processing. This is a visual stabilization measure, not a guarantee of production image quality or a replacement for real temporal accumulation. HUD and input remain full-size and unjittered.

PrismaStats adds adaptiveResolution, requestedRenderScale and temporalFallback; the existing PRISMA editor panel displays them alongside output/internal resolutions and optional asynchronously completed whole-frame GPU milliseconds. No precise GPU time is shown if unsupported.

Limitations: backend timing may be absent; whole-frame timing includes other GPU jobs; the fallback can still exhibit simple bilinear aliasing and thin-edge shimmer; a mid-frame device loss cannot be recovered with texture sampling; cached allocation pressure may temporarily rise around scale transitions until actual GPU-completed fences allow reclamation. Adaptive scaling does not synthesize true per-viewport GPU timing nor promise a frame-rate gain. Motion-vector reprojection, jitter sign and GLSL/MSL compilation still need native GPU validation.

Stage 46 — actual scoped GL33 viewport GPU timings and VRAM-pressure guard#

The timing distinction matters: RHI gfx::Device now has optional nonblocking beginGpuScope(tag)/endGpuScope() and a separate takeGpuScopeTimings() result queue. Unlike gpuFrameMs() and timeGpuFrame(), a scope measures only GPU commands submitted between its boundaries. Desktop OpenGL 3.3 on supported macOS/Windows paths uses a real GL_TIME_ELAPSED query. The backend refuses to start a scope while a whole-frame elapsed query or another scope is running (OpenGL does not allow nested same-target queries). takeGpuScopeTimings() only returns completed, nonblocking results and does not consume other takeGpuTimings() benchmark results. The bounded queue is capped at 64 pending entries. GL ES/WebGL/Linux fallback, Metal and Vulkan do not claim per-viewport timings: the default API returns false/empty. Metal's gpuFrameMs() is whole-command-buffer duration and must always be labeled as such.

Editor opt-in: AIVERSE_PRISMA_VIEWPORT_GPU_TIMING=1. For Scene/Game, the editor begins a GPU timing scope immediately before the graphics Renderer3D::render and ends it after Renderer3D::resolvePrisma and the last viewport pass. This covers rendered shadows, world, post-effects and scene FX in this interval, not prior CPU scene preparation, prior GPU asset streaming or other windows. When supported, the editor polls finished measurements at its pre-render safe boundary, passes them to Prisma::acceptViewGpuTiming(viewId,gpuMs) and lists per-viewport samples through Prisma::viewGpuTimings(). The source is presentation/diagnostic only, not the authoritative simulation or an ECS component. It is opt-in and never enables full-frame timing automatically.

Adaptive source selection: the existing PrismaAdaptiveResolution controller now prefers the latest completed scoped GL query for its particular view. Each accepted scoped query increments that view's completed-sample sequence; a repeat value cannot cause repeated hysteresis updates. If no scoped query is available, the controller retains the earlier whole-GPU-frame fallback gated by the genuine Device::gpuCompletedFence(). It does not convert CPU FPS to GPU milliseconds. Scoped interval duration still includes shared GPU shadow/reflection/FX passes and is not a pure postprocess-only cost. On unsupported backends this scope-specific diagnostic is explicitly unavailable.

Bounded known-memory pressure: temporalResolve gains maxPrismaMemoryMiB (32..4096, default 256 MiB) as an opt-in adaptive-resolution pressure threshold. Only when the Stage 45 adaptiveResolution effect and AIVERSE_PRISMA_ADAPTIVE=1 are active does the policy compare the threshold against Prisma::memoryStats().liveKnownBytes + Prisma::retirementStats().knownPendingBytes. These estimates count shared size-cache allocations once, add active per-view HDR histories and pending fence-retired textures exactly once, and exclude unknown/unobservable bytes and physical driver overhead. A known lower-bound overage counts as a pressure sample only on a new confirmed GPU completion (actual completed scope query or GPU fence). After 12 over-budget samples it may step scale down 1/16. Over-budget pressure blocks upward quality steps; normal fast/slow GPU timing and the existing 48-completed-sample cooldown continue to apply. Pressure alone does not allow unsafe GPU release, unconditional memory waits, or repeated CPU-frame counting. Without a verified GPU completion, no adaptation is attempted.

PrismaStats and the editor report the chosen timing source, last valid GPU milliseconds, known Prisma live+pending bytes, the configured threshold and whether it is exceeded. The Stats window also displays the recent completed GL33 Scene/Game intervals, rather than mislabeling Metal whole-frame timings as isolated view costs.

Caveats: gpuFrameMs and GL elapsed queries are GPU-timeline intervals, not identical to busy-time; scopes can include expensive shared renderer passes and do not measure earlier resource uploads. Using a shared whole-frame GPU measurement for two simultaneously active editor views is inherently conservative. The memory threshold is not total physical VRAM or a hard memory cap, and unmeasurable ShaderGraph/Portrait/driver allocations remain unknown. Over-budget known bytes may stay high until actual fence completion; bounded frame hysteresis prevents per-frame thrashing, but is not a promise of performance gain. A backend's unavailable query must not cause a false zero-time result or stale scope escalation.

Stage 47 — Metal hardware-scoped timings, renderer-owned memory and trustworthy source switching#

Metal GPU scope implementation: gfx::Device::beginGpuScope, endGpuScope and takeGpuScopeTimings now have a real optional engine/gfx/metal/GfxMetal.mm backend for compatible devices. It checks available MTLDevice.counterSets for timestamp counters and requires support for blit-boundary or stage-boundary counter sampling. It uses two samples per viewport scope in a MTLCounterSampleBuffer, encoded into lightweight blit encoders inside the same Metal command buffer as the actual Scene/Game work. Command-buffer submission/presentation, frame semaphores and GPU fences are unchanged.

Metal counters do not necessarily run in CPU nanoseconds. A timing sample is only accepted after the actual command buffer reaches MTLCommandBufferStatusCompleted and resolveCounterRange(NSMakeRange(0,2)) returns both valid timestamp values. It converts the GPU timestamp interval to CPU-clock nanoseconds by interpolating those clock pairs. Zero, error sentinel, nonmonotonic, nonfinite and out-of-range results are not published as valid time. Results are polled nonblockingly; pending scopes are capped at 64. Stage 53 — per-camera effect diagnostics (CPU read-only)#

Prisma::effectReport(viewId) const returns a pointer to a Prisma::ViewEffectReport captured after the last resolve() of that specific camera. The viewId identifiers are assigned by the host; the value 0 is the inherited default. effectReportViewIds() returns the sorted keys of the stored reports. The result creates no RHI shader/texture, does not call program()/composite(), does not wait for the GPU and does not change ECS.

ViewEffectReport: viewId, a sequence counter (only resolve calls for this ID), input dimensions, quality, HDR path, scene readiness and a list of EffectExecution for all elements of the current camera profile, including authored-disabled/low-tier effects. Each entry contains:

  • type — the PrismaType from the standard catalog; authored means present in the current profile.
  • requested — the effect is enabled at the current tier and its opt-in + numeric conditions (if any) are met; a low tier / disabled environment variable gives a specific reason and requested=false.
  • pipelinePrepared — the local cached RHI handles are available. This is not proof of GPU execution; for composite the actually selected variant is checked, and for multi-pass Bloom/TiltShift/SunShafts the specific prepared pipelines.
  • encoded — the corresponding effect actually entered the last render (a draw for MotionBlur/DoF/FXAA/Temporal, a resource attached to the submitted composite for Bloom, LUT, Bloom/etc). A partial failed GPU graph whose result is not used does not count as a successful effect. Shader readiness without a draw does not give encoded.
  • reason — the reason for skipping (camera cut/first frame, history quota, temporal preflight, HDR/tier/opt-in, missing LUT/pipeline, shadergraph/exposure texture-slot conflict, missing target, etc.). Empty for a successfully encoded effect.

The per-view report does not mix Scene/Game of the same size. On retireView / retireUnregisteredViews the snapshot is removed together with the camera state; on shutdown() and setSettings() old reports are cleared. An applyCameraVolumes() update is reflected on the next resolve; until then the snapshot is the history of the last render, not a plan of the current settings. Report pointers are invalidated on clearing or map update; do not cache them between frames.

The PRISMA — Постобработка editor displays a collapsible matrix View ID / effect / requested / pipeline / encoded / reason without creating resources while viewing. The existing global runtimeCapabilities() still describes the latest data from PrismaStats, not all cameras; for a per-view effect use the new API.

Especially important: encoded means GPU draw command issued, not a completed GPU fence, correct pixels, an image in the frame or effect parity across different RHIs. The last four claims are permitted only after real GPU tests.

Stage 55 — Auto Exposure together with four Shader Graph textures#

Before this stage PRISMA reserved a fixed sampler TEX8 for GPU HDR Auto Exposure, while the postfx Shader Graph used bindings TEX5..TEX8 for at most four independent textures. With four textures, author-enabled Auto Exposure was silently disabled, even though all its other conditions were met. This was a functional limitation, not a physical RHI restriction.

The new GPU-independent PrismaCompositeTextureLayout.h defines a shared, constexpr-computable resource map. The fixed composite occupies slots 0..4, the Shader Graph 5..8, and HDR Auto Exposure slot 8 while the graph uses 0..3 textures, and slot 9 with four textures. An unsupported texture count (more than 4) is explicitly rejected. Five static_asserts confirm the expected computations when the library is compiled; native compilation has NOT yet been performed. The scheme does not change serialization, JSON or the MCP API.

In Prisma.cpp the plan is used both when building ShaderDesc.textureSlots, when forming the masks for GLSL/MSL TEX0..TEX9 and in the actual Device::setTexture. PrismaShaders.h selects TEX9 only with PF_AUTO_EXPOSURE_SLOT9, otherwise it keeps TEX8. The composite cache key remains effectMask + ShaderGraph JSON: this is sufficient, since the layout is uniquely determined by the graph itself. If building the expanded pipeline fails, PRISMA keeps the old fallback: the same composite without Auto Exposure, and if that is also unavailable, the base composite without effects. Do not substitute a failed pass with "effect executed".

Prisma::ViewEffectReport now contains shaderGraphTextures and autoExposureTextureSlot. The latter is -1 when the final selected composite pipeline does not contain Auto Exposure; the entry is updated only after the fallback is resolved. The PRISMA — Постобработка editor shows the actual slot for each viewId without triggering a GPU shader compile for displaying diagnostics.

Stage 56 — Depth of Field: distance-based focus and silhouette protection#

The experimental depthOfField remains part of PRISMA and still requires AIVERSE_PRISMA_DOF=1 and a suitable quality tier. Old maps/JSON automatically use the previous mode: focusDepth and focusRange in hardware depth [0,1]; maxBlur and intensity stay unchanged. In the shader this mode is kept in a separate branch with the original formula and the 10-weight blur scheme, so that the old image is not reinterpreted as a physical distance.

New optional parameters of the same effect:

ParameterDefaultPurpose
metricFocusfalseExplicitly enable linear depth from camera data
focusDistance12Focus plane along the view direction (world units)
focusRangeMeters4Sharpness interval around the focus plane
occlusionToleranceMeters0.35Allowed depth difference between the center and a tap before blending is suppressed

The "meters" naming applies to projects where one world unit equals one meter. This is linear depth along the camera direction (view-space Z), not the spherical distance from the eye to an arbitrary point. For perspective: z = near * far / (far - depth * (far - near)); for orthographic: z = mix(near, far, depth). Renderer3D::resolvePrisma() already passes PostFrame.depthNear, depthFar and orthographic; the orthographic bounds of the current renderer can be negative -200..1000, which is supported correctly.

The Prisma.cpp code checks finite near/far and far > near; perspective additionally requires near > 0. If metricFocus is requested but the input projection is invalid, the RHI draw runs the old hardware depth, and Prisma::EffectExecution for this camera sets encoded=true, degraded=true and a specific reason. This prevents NaN and an empty frame. The report pointer stays read-only; degraded does not mean verified visual correctness of the effect on the GPU.

The metric shader computes CoC from linear depth and, among eight neighboring color taps, chooses the weight by the difference in linear depth. Points separated by a silhouette or belonging to sky/background (device depth >= 0.99999) are not blended; the transition between consistent and inconsistent layers is smoothed with smoothstep. GPU sampling stays in linear HDR; output alpha in the metric branch is inherited from the source SceneColor. The legacy branch keeps the previous output alpha=1 for compatibility. The sampled scene depth is never bound as a writable depth attachment; DoF uses a separate scratchDepth. The pass works with src.tex, which may contain the result of the preceding Motion Blur, and now checks that src.tex specifically is present before the draw.

PrismaData.cpp automatically exposes the new fields in the shared JSON/editor/MCP/volume-mask schema; do not create a separate implementation for FPS, RTS or SpectraFX. PrismaWindow.cpp gained a hint about mode selection and a visible degraded fallback in the effect matrix per viewId. Any old postfx without metricFocus will keep using the old path.

Limitations: this is an 8-tap screen-space defocus, not physically correct bokeh, Gather/Scatter DoF or full separated foreground/background scattering. At intersections of translucent surfaces the depth constraint can suppress blurring, but cannot recover colors hidden behind objects. Depth [0,1] semantics, camera and Metal/GL parity require verification on a real device.

autoExposure still requires the effect in the postfx profile, effective HDR and the variable AIVERSE_PRISMA_AUTO_EXPOSURE=1. Luminance measurement stays in linear scene-referred HDR before tonemapping and UI, and its separate 1×1 ping-pong history belongs to a stable viewId, independent of Scene/Game viewport sizes.

New optional parameters in the shared PrismaData catalog:

FieldDefaultRangeMeaning
highlightRejection00..0.95How much to reduce the influence of very bright pixels during metering

highlightRejection=0 by default keeps the previous weighted log-luminance estimator and the already existing centerWeight, centerRadius, minMeterLogL, maxMeterLogL, EV clamps and adaptation speeds. This is optional soft highlight weighting, not histogram/percentile metering.

The GPU shader kExposureLog computes the luminance of each of the four samples, clamps logL to the current minMeterLogL/maxMeterLogL, then reduces the base spatial weight: weight *= 1 - rejection * smoothstep(startEV, startEV+softnessEV, logL). The bound rejection <= 0.95 guarantees at least 5% of the original weight even for a fully bright frame and rules out a zero metering denominator. The kExposureReduce pyramid reduction still separately carries the weighted sum of log2 luminance and the sum of weights, and kExposureAdapt divides the former by the latter before computing EV. There is no hidden GPU readback or CPU luminance pass.

Now the check of motionView.previousCameraPos, finiteness and a jump of more than 12 world units runs at the start of Prisma::resolve, before Auto Exposure. The reset simultaneously invalidates velocity/temporal history and calls resetAutoExposure(viewId_). Explicit resetMotionHistory(id) / resetMotionHistory() also invalidate per-view/all-view exposure history without deleting GPU textures. The first adaptation pass of the new camera uses historyValid=false and is reinitialized from the current measurement. The reset does not require waiting for the GPU and does not confuse two cameras with the same resolution.

These are two independent authored multipliers, not two instances of the auto-adaptation algorithm; GPU history is strictly one per view. After all camera passes finish, the host passes the full set of live identifiers to Prisma::retireUnregisteredViews; the new overrides are included in unionTracked and are removed by retireView/ shutdown together with per-camera state. ViewEffectReport.autoExposureFrozen and autoExposureRegionMetered are updated only if the final encoded composite actually applies Auto Exposure. Frozen means "on this frame a valid history was reused, the meter was not run"; RegionMetered means "on this frame a measurement with a region was performed". When exposure is absent in the final fallback, both are false. The editor window shows them for each viewId and gives hints for the new generic fields; GUI reads do not trigger GPU creation.

Stage 59 — Manual EV, rectangular ROI and fault-tolerant HDR metering#

Manual EV is implemented inside the existing AutoExposure postfx effect; it does not start a second HDR owner, GPU history, a new fullscreen pass or an extra sampler. The PrismaData.cpp catalog extends Stage 58 with the fields:

Old postfx, editor IDs and MCP operations are preserved; for existing projects manualExposure=false and meterBox=false mean no changes. Ordinary automatic exposure still requires AIVERSE_PRISMA_AUTO_EXPOSURE=1, while an explicitly enabled manualExposure works without this flag (but requires an authored autoExposure, enabled postFX, an allowed tier and linear HDR).

Fixed EV and camera state#

In Prisma::resolve manual mode is selected from the camera profile and native override. With manualExposure active, GPU metering, kExposureLog/Reduce/Adapt, the 1×1 exposure history and the texture sampler TEX8/TEX9 are not used. Instead, the already existing CompositeU.filt[2] is multiplied by exp2(manualEV) after the author ColorGrade exposure is computed, but before the final HDR composite / ACES / sRGB / LUT / Shader Graph and UI. This means the fixed EV and the artistic ColorGrade exposure multiply compositionally, but there is no automatic adaptation in manual mode.

Manual EV from native calls and the C++ profile is checked for finiteness and clamped to [-12,+12] before HDR; NaN/Inf are not passed into the shader. On switching into/out of manual mode the camera-local exposure history is invalidated; on returning to automatic mode a new measurement of the current scene is taken instead of blending with the old luminance. Manual mode can work immediately on the first frame — unlike freezeExposure, which requires a valid preceding 1×1 adaptation. When a user Shader Graph fails, the fallback to composite(0) keeps the fixed EV, since filt[2] is applied outside PF_GRADE and PF_AUTO_EXPOSURE. With an invalid final pipeline the report does not declare manual EV as executed.

Native API:

prisma.setViewManualExposure(stableViewId, true, 1.5f);
prisma.setViewManualExposure(stableViewId, false, 0.0f); // explicit disable
prisma.clearViewManualExposure(stableViewId); // restore profile inheritance

Choosing setViewManualExposure(id,false,...) explicitly overrides the authored manualExposure=true; clear returns control to the profile and invalidates the AE history. Overrides belong to the stable presentation viewId, not to camera resolution/position. retireView, retireUnregisteredViews and shutdown remove them together with the rest of per-camera state, without freeing shared GPU texture caches.

Soft rectangle for HDR Metering#

The X difference is brought to the scale of frame height by the aspect multiplier; the soft edge uses smoothstep(0,feather,signedDistance). TUV(q) ensures the same Y direction in GL/Metal, and the existing meterOutsideWeight >= 0.02 keeps nonzero contributions outside the region. The global reduction (weighted log sum and weight sum) is unchanged.

Native ExposureMeterRegion extends the existing fields with bool box=false; float halfWidth=0.25, halfHeight=0.25 at the end of the struct, preserving old aggregate initializers. Setters clamp finite sizes to [0.01,0.5], and the ROI is not part of authoritative ECS. The camera view report is extended with autoExposureBoxMetered (only for actually encoded exposure). In manualEV mode no meterRegion runs on the frame.

Fallback on GPU metering failure#

The old per-camera sample is invalidated, the final composite keeps working without sampled Auto Exposure; a new attempt may be made in future frames. Partially encoded mip passes are not presented as successfully adapted lighting, and no separate GPU sync wait was added.

In the editor these parameters are available from the shared catalog with explanations and per-viewId status.

Stage 60 — graceful Shader Graph / LUT fallback that keeps ordinary effects#

Previously, on a failure of a user postfx Shader Graph (GLSL/MSL compilation, unsupported sampler layout or invalid input textures), Prisma::resolve() could end up jumping straight to composite(0), losing working fixed Bloom, ColorGrade, LUT, Vignette and other effects. PRISMA now uses the following ordered fallback system:

  1. The requested variant with Shader Graph and, if present, GPU Auto Exposure.
  2. The same Shader Graph, but without Auto Exposure, if the first attempt did not create a pipeline.
  3. Without Shader Graph: the full fixed-effect mask with Auto Exposure (if the prepared HDR 1×1 texture is still available).
  4. The same fixed-effect mask without Auto Exposure, if the previous pipeline is unsupported.
  5. Only as a last resort — composite(0) without fixed effects. If even that is unavailable, diagnostics do not claim a successful draw.

The set of fixed effects is kept as a separate copy fixedMask before the Shader Graph attempts. If a user Shader Graph texture is missing or was not uploaded to the GPU, the whole Shader Graph is excluded from the current composite, and working fixed effects keep running. Successfully creating a Shader Graph pipeline does not by itself mean the input textures loaded: graphInputsReady checks graphTextures_[path].valid() for all used paths after the upload attempt. A missing input is no longer silently presented as a valid "black" texture inside an executed Shader Graph.

Especially important after Stage 55: in the graph variant with four images, Auto Exposure uses TEX9. If the graph failed and the fixed-only fallback is used, the last actually selected pipeline requires TEX8. PrismaCompositeTextureLayout::plan(...) is now recomputed based on the actually selected Shader Graph, not the original authored texture list. Exactly this exposureSlot is used in GPU binding, ViewEffectReport and the shader variation. In a graphless fallback, textures in slots 5..8 are not bound unnecessarily. Stage 59 HDR manual EV, ColorGrade and Auto Exposure settings are preserved if the resulting variant is supported. The composite(mask,graphData) cache and deferred GPU-retirement ownership are unchanged.

Diagnostics and error caching#

ViewEffectReport.shaderGraphFallback indicates that the authored Shader Graph was skipped, and the rest of the chain could be used where its pipelines are valid. EffectExecution for ShaderGraph gets encoded=false and a specific reason: a missing/failed-upload texture or a shader compile/composite failure. For working fixed effects, encoded is determined by the final GPU mask, not by the facts of the original request. In the PRISMA — Постобработка editor a corresponding warning per stable viewId appeared.

In Prisma::lut(), a read error, an invalid LUT strip N²×N and a GPU upload error now set lastError() with a description and project-relative path. LUT is still negative-cached, so the other effects can keep running without it. graphTexture() now also negative-caches GPU upload errors: re-decoding and failing createTexture every frame are not needed. Resetting the cache via the existing setImageLoader() retires successful texture handles behind a real GPU fence and allows reloading; changing a file on disk without calling this procedure is not by itself live-reload and is not promised in this stage.

Unchanged: the postfx format in game.json, the PrismaData catalog, MCP API, ECS gameplay, default effect settings, SpectraFX, per-view exposure ownership and user Shader Graph formats.

Stage 61 — reactive transparent edges for Motion Blur and safe FXAA#

Stage 61 fixes two specific PRISMA presentation paths: SDR FXAA no longer substitutes an invalid texture for the input when creating the intermediate render target fails, and optional Motion Blur can suppress blending of color taps by the difference in reactive coverage at the edges of translucent objects/particles. The work stays genre-independent and does not touch authoritative ECS or the separate SpectraFX.

Motion Blur + reactive input#

A new optional parameter of the existing motionBlur: reactiveTapRejection, range 0..1, default 0. It is appended at the end of the effect catalog in PrismaData.cpp, so all previous numeric offsets, old postfx JSON, presets and native/volume profiles stay compatible. At zero the previous shader weight and previous filter apply.

MotionBlurU gained a fifth vec4 tapInfo. Only kMotionBlur uses the extended UBO; other passes (Temporal, DoF, Bloom, FXAA, ExposureLog) and the reactive texture format did not change. tapInfo.x receives reactiveTapRejection only with a valid input MotionTextureInput (RGBA8, size of the current scene render target, a check of declared metadata and the available RHI textureInfo). When the reactive mask is absent/rejected, the value is zero and the shader keeps the previous behavior.

If the filter is active, the current pixel and its neighboring color taps read TEX3 reactive R. Taps with substantially different coverage get a reduced weight: keep *= 1 - strength * smoothstep(0.1,0.8,abs(tapReactive-centerReactive)). This is an addition to the already existing depth filtering (hardware or linear depth), not its replacement. If the sum of weights is zero, the original sharp RGB is applied. In new HDR runs Motion Blur returns the original alpha centerColor.a, not 1.0, since the post effect changes radiance RGB, not scene transparency. Canonical TemporalResolve still itself writes depth into its own history alpha — this contract is unchanged.

Dependency on real reactive geometry: the mask is built separately by Renderer3D and additional providers (for example, particles/water), and the temporary mask image is NOT kept between frames. This stage does not attempt to fix missing coverage of a specific material or read GPU pixels back on the CPU.

ViewEffectReport per stable viewId now stores reactiveInputSupplied, reactiveInputAccepted and motionBlurReactiveEdgesEnabled. This is CPU metadata/RHI acceptance, not GPU pixel validation: a legacy borrowed handle without metadata may be considered acceptable when the backend does not provide introspection. The last field becomes true only when MotionBlur is actually encoded, the required input is verified and strength is greater than zero. The PRISMA editor shows mask availability and filter status.

Safe FXAA degradation#

Previously the SDR prepass did src=target(kAa) before checking whether the creation result was valid. With a failed RGBA8 target or depth attachment, composite could sample an invalid src. Now fxaaInput keeps the original scene/post-chain texture, fxaaOutput is created separately, and the prepass runs only if input/output and depth are valid. Graph FXAA (opt-in) and the ordinary direct draw use the same two verified handles, and src=fxaaOutput is assigned only after an encoded draw. If allocation failed, the rest of the chain continues with the previous src, without a false fxaaEncoded=true.

For the HDR fallback FXAA, which is applied after the final Composite and only if TemporalResolve did not run, a check of pipe.valid() was added before starting the intermediate AA target/pass. This rules out reading an empty composite target if the pipeline could not be obtained at all. The output target/depth check is kept. TAA and FXAA remain mutually exclusive on the single HDR presentation output.

No new GPU history or shared texture owners were introduced. Rendering keeps the current Stage 54 fence-retirement contracts.

Stage 62 — reactive mask on the first frame, Camera Cut and resize#

From this stage on, Renderer3D separates two independent presentation producers: (a) object velocity vectors, which require the previous camera and a history of current/previous transforms, and (b) current-frame RGBA8 reactive coverage, which does not need a preceding pose. Previously the whole reactive pass was inside if (history.target.valid() && history.depth.valid()), and the function exited with return on the first frame, on camera cut and on resize. Therefore the transparency of water, particles and morph/skinned translucent objects could be left uncovered by the reactive mask precisely where temporal history is invalid.

New Renderer3D structure#

renderObjectMotionVectors(PostProcess&) is still called on the final scene frame, before Prisma::resolve. In it, velocityHistoryReady is determined only by previousCameraValid && history.valid && !resize. When previous data is missing, no false/zero object-motion velocity frames are sent to Prisma. Current rigid/animated transform poses are collected as before; after the reactive pass they are saved for the next frame. If the viewport changed size, the target/depth/reactive textures are all placed into the existing GPU-fenced queue via queueObjectMotionTexture(...), rather than destroyed synchronously. This preserves the Stage 54 ownership contract.

The new private method Renderer3D::renderCurrentFrameReactiveMask(PostProcess&, ObjectMotionHistory&, gfx::TextureHandle sceneDepth,int w,int h) uses only the current viewProj_, model poses, scene depth and ready framebuffer sizes. This helper is called after the conditional object velocity pass and is not nested in it. It provides its own private depth attachment for reactive-only frames (Depth) and, when the required geometry is present, creates an RGBA8 reactive target. Scene depth from Prisma is passed as a borrowed sampler and never becomes a writable depth attachment. The absence of RGBA16F velocity does not block the helper at the Renderer3D level if a native post hook requested such reactive work and provided scene depth; the ordinary Prisma HDR policy still decides on its own whether it needs MotionBlur/Temporal Resolve at all.

Current coverage rendering keeps the previous sources: rigid transparent models and fading LOD, morph/skinned/baked translucent models with the current pose for both motion matrices, immediate water MeshVertex geometry, motionReactiveDraws_ from particles and custom native providers. The mask is still created/cleared only on the current frame, blending merges coverage, and it is passed to Prisma as MotionTextureInput::declared(reactive,w,h,RGBA8). Cases without reactive geometry/callback, or without an available depth/target/pipeline, are not declared a successful reactive pass.

Separate statistics and diagnostics#

Renderer3D::ObjectMotionStats now has: velocitySeedOnly — first frame / invalid/cut/resize, so as not to present pose initialization as GPU object velocity; and reactiveSubmitted — a separate flag for an actually encoded current-frame mask. The historical submitted remains an indicator of the object-velocity pass, not reactive-only.

The PRISMA camera stores ViewEffectReport.objectVelocityInputAccepted and reactiveWithoutObjectVelocity, taking into account a separate MotionTextureInput check: first the declared width/height/format are checked, then RHI textureInfo, if the backend supports introspection. These fields do not prove GPU pixel content. The editor shows mask-only pass for reactive coverage without a valid object velocity texture; the separate MotionBlur reactive edge rejection status still depends on an actually encoded blur and the configured parameter.

Kept unchanged: stable per-view identity regardless of two cameras having the same resolution; resetObjectMotionHistory(viewId) and the camera-cut epoch; GPU-fenced retirement; no ECS mutation; Prisma::resolve and HDR temporal history as the sole color history owner; HUD outside post-processing. The reactive mask does not become a long-lived temporal input.

Stage 63 — exact rigid alpha-cutout / dissolve reactive coverage and lifecycle callbacks#

This stage extends the current Renderer3D::renderCurrentFrameReactiveMask (Stage 62) without changing the architecture, the Prisma/MCP format, HDR color history or Reactives ownership. The reactive mask remains an RGBA8 current-frame input from Renderer3D to PRISMA; the per-camera motion history is an independent component.

Rigid models: exact AlphaMask, dissolve and LOD#

For rigid models with AlphaMode::Mask or dissolve > 0, a separate shader variant was added: reactive_shaders::kCutoutVS/kCutoutFS/kCutoutMSL and objectMotionReactiveCutoutPipeline_. The main water/transparent/mesh pipeline is left unchanged.

The shader repeats the fragment conditions of the ordinary ModelShaders: baseTex alpha, baseColor.a, optional vertex alpha (excluding vertex-occlusion/AO), alphaCutoff, KHR base-UV offset/scale/rotation, screen-space 4×4 LOD dither and the same object-space noise modelNoise3(opos*7)*0.7 + modelNoise3(opos*19)*0.3 for dissolve. TeamMode::BaseAlpha uses baseColor alpha without baseTexture alpha; for TeamMode::VertexAlpha it does not multiply vertex alpha twice, following the material. The scene still samples the foreign sceneDepth read-only; the reactive pass has its own writable history.depth. BlendMode::Screen is used to merge coverage. The shader source provides the same clipping logic in GLSL and Metal, but GPU parity requires real shader tests.

New uniforms layout only for this pipeline: ReactiveCutoutUniforms {mvp,params,lod,uv0,uv1,maskInfo}, 144 bytes. Vertex attributes are the real ModelVertex position[0], uv[2], color[4]. AlphaCutout texture bind slot 1, scene depth in slot 0. Since the shader precisely discards alpha holes, reactivity no longer paints the whole triangle for foliage/grilles. Shader Graph vertex displacement and geometry-driven models still require separate coverage producers; do not claim them as supported by this rigid path.

Animated transitions and callbacks#

For skinned/morph/baked translucent models, kAnimatedFS and its MSL generator gained an optional U1.reactiveLod (fragment buffer(2)) with exact 4×4 LOD dithering on the current frame. Animated LOD and dissolve now provide coverage even when the previous pose is absent. Dissolve for animated objects is conservative — the mask may cover fragments that the main ModelShaders discards by object-space noise. Exact animated alpha-cutout/actor aperture requires a new current-object-space varying or a separate material-specific shader, not implemented here.

In Renderer3D, mask readiness is checked per required source: separately for simple rigid, cutout/dissolve rigid, skinned, baked, MeshVertex or motionReactiveDraws_. The presence of an unsuitable pre-created shader (for example, a skin pipeline when the baked pipeline is missing) is no longer grounds to publish an empty reactive mask. When a callback was registered for the current scene frame but the active postprocess, scene depth or mask pipeline is unavailable, ObjectMotionStats.reactiveCallbacksDropped counts the unexecuted calls; the callback is not carried over to the next frame.

The registration contract is unchanged: addMotionReactiveDraw after beginScene, but before resolvePrisma. The renderer invokes callbacks only with the mask pass open: the provider must only record draws, not call beginPass/endPass, keep its GPU resources until submission completes and combine coverage without destroying previous pixels. The list is cleared after resolve, when the postprocess is inactive or at the start of a new scene frame. The intermediate mask is not cached across camera cuts and is not carried between viewIds.

Renderer3D::ObjectMotionStats was extended with cutoutReactiveDraws, dissolveReactiveDraws, reactiveCallbacksDropped; the previous reactiveDraws/reactiveAnimatedDraws/ reactiveCallbacks/reactiveSubmitted are kept. The counters mean CPU-encoded submissions / callback invocations, not GPU completion or proven pixel content. The shared per-view Prisma::ViewEffectReport from Stage 62 and the GPU-fenced retirement of Stage 54 were not changed.

Stage 64 — precise animated reactive alpha/dissolve and Actor Reveal#

Stage 64 completes the bounded functionality of the gap found in Stage 63: animated skin/morph/baked reactive coverage used to be produced only as a conservative silhouette, without applying the material AlphaMode::Mask, object-space dissolve and the local kDrawActorReveal aperture. In the new implementation the ordinary velocity pipeline stays unchanged, and the reactive path gets a separate GPU shader variant.

Reactive-only vertex stage#

Renderer3DReactiveShaders.h now provides two testable generation functions: reactive_shaders::animatedVertexGlsl(source,baked) and reactive_shaders::animatedMsl(source,baked). They take the existing kDeformedVS/kDeformedMSL or kBakedVS/kBakedMSL, substitute UV (ModelVertex attribute 2), vertex color/alpha (attribute 4) and the current deformed object-space pose, keeping the previous skin/morph/baked sources (attributes 5/6, U0/U3/U4/U5 and texture 7/8). The resulting local text variants are passed to createShader; the original motion shaders and velocity output stay the same. If the expected source anchor is missing, the generator returns an empty string, and Renderer3D does not create an invalid reactive pipeline.

kAnimatedFS (GLSL) and the generated MSL fragment use the new ReactiveAnimatedU1, 160 bytes: lod[4],uv0[4],uv1[4],maskInfo[4],world[16], reveal[4],revealAxis[4]. It occupies the ordinary uniform slot 1 (Metal buffer 2) and does not interfere with the skin/baked deformation slot U3/U4/U5. The shader still renders only current-frame RGBA8 reactive coverage, does not write velocity and does not use previous frame history. Depth is sampled from the foreign sceneDepth, and the writable attachment is the renderer-private history.depth.

For animated objects the same current-frame clipping conditions are now reproduced exactly: 4×4 LOD dither, UV offset/scale/rotation, the material cutoff baseTex alpha * baseColor alpha (+ vertex alpha, if allowed), and modelNoise3(currentDeformedLocalPos * 7) * 0.7 + modelNoise3(currentDeformedLocalPos * 19) * 0.3 for dissolve. The TeamMode::BaseAlpha and TeamMode::VertexAlpha settings do not multiply vertex/texture alpha twice; vertex occlusion/AO is not treated as opacity.

Actor Reveal for rigid and animated#

kDrawActorReveal with an active Renderer3D::actorReveal now makes the model a source of reactive coverage, even if it is fully opaque and has no LOD fade/dissolve. Only the main camera pass (geometryMainView_) passes the world-space actor center/radius, camera axis and view-dependent attenuation from the same Renderer3DModels.cpp formula. The fragment shader repeats the aperture: radial=length(delta-axis*depth), radius=actorRadius*max(0.01,1-depth*axisScale), coverage=(1-smoothstep(radius*.48,radius,radial))* smoothstep(.04,.24,depth) and 4×4 dither discard. In the inactive mode reveal.w=0 and this path does not affect the mask.

For the rigid alpha/dissolve shader, ReactiveCutoutUniforms was extended from 144 to 240 bytes, by adding the world matrix and reveal/axis in U0. GLSL and Metal receive the vertex's current world position. For animated, the current deformed local position is used, transformed through the passed world matrix in the fragment. This is not a separate draw pass and not an ECS system: the source remains the same current-frame reactive pass from Stage 62.

In Renderer3D::renderCurrentFrameReactiveMask, replay of animated materials now sets up ReactiveAnimatedU1, a separate baseTexture sampler slot 1 and the vertex attributes UV/color/skin. Actor reveal, dissolve, alpha cutoff and LOD parameters are set per ModelItem. The statistic ObjectMotionStats.actorRevealReactiveDraws complements the existing cutoutReactiveDraws, dissolveReactiveDraws, lodReactiveDraws. These are CPU-encoded draw counts, not confirmation of GPU visibility. Resources stay with Renderer3D; the existing GPU-fenced target retirement and stable per-viewId ownership are unchanged.

PRISMA owns PhysicalSky and LocalFog HDR passes. They run before exposure metering and motion/temporal processing, then normal bloom/tonemap. New target roles 200/201 do not overlap DoF (50), metering or motion buffers. Sample scene depth with the existing separate scratch depth attachment; size resources use PRISMA's normal fence-retirement path. Pipelines shut down after its GPU-idle barrier. These features are disabled by default. Native region/settings APIs are owner-wide: a multi-camera host must set each view's cosmetic data before its resolve, or use a separate Prisma owner. Camera-volume profile blending does not yet author or interpolate these atmosphere settings. No gameplay changes.

Structured fog continuation#

FogVolume::structure optionally shapes local fog with periodic 3D noise, per-axis world scale, height attenuation and wind; Prisma::setLocalFogTime provides a reproducible presentation clock. Default uniform fog is preserved. The existing local fog pass owns this, with no extra history or render targets. See the structured banks section in docs/local-volumetric-fog.md. No terrain sampling, gameplay visibility or PHYSIS state mutation is introduced.

Local fog now also supports heightVariation, three-dimensional warp, boundary edgeErosion and optional selfShadow/shadowDistance. Self-shadowing ray-marches all active volumes and reveal holes toward the sun, independently of the existing geometry shadow map. This is bounded single scattering; no new temporal buffers, shadow-map ownership, terrain dependency or authoritative simulation state.

Per-view physical-lens defocus (LENS P2, stage 96)#

Prisma::setViewDepthOfField(viewId, DepthOfFieldOverride{enabled, focusDistance, focusRangeMeters, maxBlur}) replaces the metric focus plane, sharp interval and maximum blur of the authored depthOfField effect for one stable view, in the same way setViewManualExposure overrides the authored exposure. The override forces the metric (camera-linear) branch and keeps the effect's intensity and occlusionToleranceMeters. enabled=false switches defocus off for that view. Values are clamped to the catalog bounds on ingress; clearViewDepthOfField and retireView remove the override. It still requires the authored effect and AIVERSE_PRISMA_DOF=1; nothing is added to the profile implicitly.

LENS drives it from CameraLensComponent::driveDepthOfField through CameraPostFxPool: the thin-lens sharp interval [near, far] becomes focusDistance = (near+far)/2, focusRangeMeters = far-near (an infinite far limit is capped at 500 m) and maxBlur = background disc radius at infinity in render pixels (clamped to 16). This is the same 8-tap screen-space defocus, not a physical bokeh. See docs/handoffs/prisma-stage-96-lens-physical-dof.md.
