Importing an engine project#

The implementation lives on agent-engine-import; the source specification is engine-import-spec.md. The simulation and template checksums are unchanged. This is a working import foundation, not completion of every stage of the specification. The coverage and outstanding work below are part of the handoff to MAIN.

CLI and intermediate data#

Python 3.8+; no Python packages are required. The executable launcher is tools/importers/port/aiverse_port (or use the explicit Python form below):

python3 tools/importers/port/aiverse_port.py scan /path/to/UnityProject
python3 tools/importers/port/aiverse_port.py extract /path/to/UnityProject --out /tmp/port.json
python3 tools/importers/port/aiverse_port.py emit /tmp/port.json --out /path/to/Imported
python3 tools/importers/port/aiverse_port.py /path/to/UnityProject --out /path/to/Imported --scale 1 --mode auto
python3 tools/importers/port/aiverse_port.py report /path/to/Imported
python3 tools/importers/port/aiverse_port.py item /path/to/Imported --id ITEM_ID
python3 tools/importers/port/aiverse_port.py resolve /path/to/Imported --id ITEM_ID --how lua --reason 'Verified by scenario…'

Every command prints JSON; failure exits with status 2. scan writes nothing. The input and output directories must not overlap. Do not run concurrent imports into the same destination. extract records source paths, complete serialized components, fields, script source and usage. emit writes a game manifest, rules, maps, .aiverse, copied assets, optional sprites/tiles/audio/fx, port.json, and JSON/Markdown reports. sourceRoot must still exist when emitting copied assets. Generated .rpakignore excludes the intermediate script index and reports from runtime packs. The manifest marks imported content external: true, which aiversebuild propagates into resource packs.

--scale means cells per metre; --mode auto|2d|3d selects the scene plane and camera. Unity 3D flips Z; Unity 2D projects XY onto the ground plane. Godot Vector2 maps to XZ. Origins are translated to keep map positions positive. No ownership is invented: only an explicit Unity owner field is mapped, with an approximation warning. Source player numbering must be checked.

lib/port/mapping.json defines field aliases. --mapping FILE adds or overrides aliases for supported targets. fireRate is interpreted as shots/second (reciprocal cooldown), explicitly marked approximate. Engine JSON cooldown/build times are seconds, not simulation ticks. Every inferred field has provenance, confidence and a target path.

Repeat imports#

.port-state.json stores generated file/type hashes. Edited or pre-existing files are preserved, including when an editor retained the ported marker. Rules merge per type; edited types lose that marker. New types can still be added. User changes to rules-level settings are preserved. Maps and binary files are protected as whole files. Obsolete generated files are not deleted. The state manifest is importer-owned; do not edit it.

Resolution annotations survive repeat imports only while the item and its relevant source entity/script fingerprint are unchanged. A changed source reopens the item for review.

Editor and MCP#

Open Project → Import engine project, or editor_window {id:"project_import", open:true}. Scan the source, choose destination/scale/2D/3D, then import. The UI runs the importer off the render thread and can open the result. Copy AI handoff copies an explicit task and opens the Agent window; it does not claim that an agent has been launched.

The current base branch has no “Make a game” wizard. Integration with the separate agent-gamewizard branch remains for MAIN; no unrelated branch was merged.

Registered operations (import settings can also be nested in options):

  • port_scan {path}: source discovery, serialization checks, asset/scene/script lists.
  • port_import {path,out,scale?,mode?,mapping?}: run extraction and emission.
  • port_report {path?}: read the destination report (defaults to the open project).
  • port_item {path?,id}: source item, components, linked scripts and generated types.
  • port_resolve {path?,id,how,reason}: annotate verified work (rules, lua, native, dropped).

Import is synchronous over MCP, like the existing VFX importer; large projects can take time. AIVERSE_PYTHON selects the interpreter. Windows shell metacharacters %, !, quotes and line breaks in command arguments are rejected rather than interpolated.

Agent workflow: inspect missing items, consult rules_schema, implement suitable mechanics as data, then Lua, then a native module if required. Use scenario_run and bot matches to compare DPS, production time and movement speed. Compare screenshots when the source image is supplied. Resolve only verified work; explain intentionally dropped behavior. No C#/GDScript/Blueprint execution is mechanically translated.

World: terrain, roads, meshes and map markers (agent-unity-terrain)#

Unity keeps native assets binary even with Force Text. Editor-saved files carry a type tree, so lib/unity/serialized.py (SerializedFile formats 9–22, little/big endian, Unity's built-in string table) reads every field by name with the standard library only. Files without a type tree (player builds) are rejected with a pointer to the fallback below.

SourceEngine result
Terrain component + TerrainData (lib/unity/terrain.py)All tiles of a scene are merged in Unity world space. Map terrain.cornersFile (maps/<id>.r16, int16 1/16 units, heights × --scale), terrain.detail {scale k, file, splat} with k = min(4, heightmap samples per cell) capped at 1.2M samples, RGBA8 splat per detail sample. The map is cut to the terrain (and map-config) rectangle; objects outside are dropped and reported. Every map also gets imported (ignored by the loader): markers with their source, class, fields and cell positions, roads, terrain tiles / height range, grid and bounds, so a later game port is data work. --mapping FILE may carry {"markers": [...]}; those rules are tried before the defaults. Rule keys: class (script class, namespace suffix), match (GameObject name regex), refType (managed reference class of a ScriptableObject, e.g. ME.BECS GDCMapData), when (field equality), kind, area, radius (number or field), bounds, points (dotted paths; the first part may be a local component reference), config/properties (grid), mapName/size/position (bounds; soft floats {rawValue} and FixedStringNBytes are decoded). The defaults describe Drone Fall (Ext-Client): GraphMask obstacles (type 0 → blocked, others → wall_N areas), extraction / summon / mob / crate points, FOW polygons, SpawnFlag starts, ExtPathfindingGrid + AgentTypesConfig, GD_Map-* (mapName, mapSize, mapPos).

--include GLOB (repeatable, Unity) walks only matching scenes / prefabs; ScriptableObjects outside the globs are kept only when an included object references them, scripts are indexed only when used, and only referenced assets are copied. Use it for big projects, e.g. aiverse_port.py import ExtClient --include 'Assets/ExtData/Scenes/World-Ira/*.unity' --include 'Assets/Maps/*' --scale 2 --out … (Drone Fall's pathfinding node is 0.5 m: --scale 2 gives one cell per node).

Fallback without type trees: copy tools/importers/unity_project/editor/AiverseTerrainExport.cs into the project's Assets/Editor and run Tools → AIVERSE → Export Terrain Data. It writes <project>/AiverseExport/terrain/<guid>.json (+ .r16, .splat, .details), which the importer prefers over the binary asset. The script was written against the documented TerrainData API and has not been run in Unity.

Tests: tools/importers/port/test_world.py (CTest world_importer) builds a synthetic binary TerrainData + Texture2D with a small SerializedFile writer and a Force Text scene (terrain tile, road spline, markers, GraphMask wall, built-in cube, map config) and checks heights, splat, palette, road and blocked cells, areas, starts, bounds, trees, detail PNGs, OBJ output, custom rules, --include, the editor-export path, repeat-import idempotence and (with AIVERSE_PORT_HEADLESS) loading in the engine.
